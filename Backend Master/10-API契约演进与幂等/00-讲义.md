# 第 10 章：API 契约演进与幂等

## 本章目标

把 API 当成跨团队、跨版本的长期契约；在超时、重复点击、代理重试和并发请求下，同一个业务意图最多产生一次可观察副作用。框架路由只是适配层，真正困难的是语义。

## 1. 契约不只是一份 TypeScript 类型

消费者看到的契约包含：方法、路径、认证、输入、输出、错误、状态码、缓存、幂等、顺序、分页、速率和兼容期限。TypeScript 会在运行时擦除，网络 JSON 必须从 `unknown` 解析。

OpenAPI/JSON Schema 可作为机器检查的契约入口，但描述文件不能证明实现正确；还需要 provider/consumer contract tests 和真实 HTTP 集成测试。

## 2. HTTP 方法与状态码表达语义

- GET/HEAD 安全且不应产生业务副作用；
- PUT 表示用给定表示替换目标，天然可设计为幂等；
- DELETE 多次执行后资源仍处于删除态；
- POST 通常非幂等，因此高价值创建需 Idempotency-Key；
- PATCH 是否幂等取决于补丁语义。

`200/201/202/204` 不可随意互换。异步任务用 `202` + 状态资源；创建用 `201` + Location；版本冲突用 `409` 或前置条件失败 `412`，并在契约中固定。

## 3. 错误也必须稳定

推荐 Problem Details 风格，机器读取 `type/code`，人读取 message：

```json
{
  "type": "https://api.example/problems/version-conflict",
  "status": 409,
  "code": "VERSION_CONFLICT",
  "traceId": "01...",
  "details": {"currentVersion": 8}
}
```

不要让消费者解析英文文案。验证错误给有限 path/code，不回显 secret、SQL、stack。未知内部错误统一 500，同时用 trace id 关联服务端记录。

## 4. 兼容演进的默认规则

通常安全：增加可选响应字段、增加新 endpoint、扩展消费者明确允许未知值的集合。通常破坏：删除/改名字段、改变类型/单位/时区、把可选变必填、收紧长度、改变排序或错误码。

枚举尤其危险。服务端新增值时，旧客户端若穷尽后抛错就会崩；协议应提供 unknown 分支，或用版本协商控制发布。

## 5. 版本不是逃避演进

优先在同版本做兼容扩展；真正语义不兼容再开版本。版本可在 path/header/media type，但必须有单一政策：owner、弃用通知、流量观测、迁移指南、停止日期。

数据库、事件和 API 不必共用版本号。不要因为内部表改列就发布 `/v2`。

## 6. Idempotency-Key 的不变量

客户端为一个业务意图生成高熵 key，重试沿用同一 key。服务端作用域至少是 tenant + actor/credential + operation；保存规范化请求 fingerprint、处理状态和最终响应。

```text
同 key + 同 fingerprint -> 返回同一结果
同 key + 不同 fingerprint -> 409 KEY_REUSED
新 key                     -> 新业务意图
```

只在进程内 `Set` 去重无法跨实例、重启和部署。只给数据库结果加 unique constraint 虽能防重复实体，却不能稳定重放原响应或区分 key 被误用。

## 7. 并发首次请求是核心难点

两个相同 key 同时到达时，必须只有一个 owner 执行业务事务。可在 PostgreSQL 插入 idempotency row；赢家处理，输家等待短时间读取完成结果，或返回 `409/425` + Retry-After。不要让两个请求都先调用外部支付再争数据库锁。

idempotency 记录与本地业务写应在同一事务完成。若还要调用外部系统，对方也必须接收稳定 operation id，或改用 outbox/后台状态机，第 13–14 章会完成这条链。

## 8. 失败和过期语义

请求在校验前失败可以不占 key；进入业务处理后记录 `processing`。确定性业务失败可缓存并重放；临时基础设施失败是否释放 key，要按“副作用是否可能发生”决定。

TTL 必须长于客户端最大重试和业务争议窗口。财务等关键 operation 不应依赖几分钟 Redis TTL；保留数据库业务唯一键与审计。

## 9. 乐观并发不是幂等

Idempotency-Key 合并同一意图；ETag/版本号阻止基于旧状态覆盖新状态。更新接口可要求：

```http
If-Match: "ticket-v8"
```

SQL 使用 `WHERE version = expected`，影响 0 行返回 412/409。两者经常同时需要：同一次保存的重试应幂等，不同用户基于旧版本的保存应冲突。

## 10. 稳定分页与游标

offset 在并发插入/删除时会跳项或重复，深分页也慢。游标应编码稳定排序键与 id，例如 `(created_at DESC, id DESC)`；服务端签名或验证结构，不相信客户端任意 SQL 字段。

响应提供 `nextCursor`，不承诺总数始终精确。改变默认排序属于契约变化。

## 11. Schema 驱动但不泄漏内部模型

DTO 与数据库 row 分离。输入使用 strict schema 拒绝未知高风险字段，输出显式投影，避免把新数据库列（如 `password_hash`）自动序列化。

Schema 单一源可以生成 TS client，但仍需测试真实 tarball/HTTP、错误响应和旧客户端 fixture。不要让客户端自行指定 `fetch<T>` 的返回泛型。

## 12. 观测与发布

记录 endpoint/version/status/error code/latency/idempotency outcome，不记录请求正文和 key 全值。发布前比较 OpenAPI diff；破坏变更阻止合并，兼容但高风险变更要求 consumer 测试。

弃用要按实际流量和客户端版本判断，而不是文档发布日期。无法识别调用者的公共 API 更需要长兼容窗口。

## 13. 评审清单

- 方法、状态码、错误和异步语义是否稳定？
- 所有输入是否 runtime parse，输出是否显式投影？
- 同 key 同请求是否重放；同 key 异请求是否拒绝？
- 两个并发首次请求是否只有一个副作用 owner？
- 幂等、乐观版本与业务唯一约束是否分工清楚？
- 分页是否有稳定全序，游标是否不接受任意字段？
- OpenAPI diff、旧 consumer fixture 和弃用流量是否进 CI？

## 本章速记

可靠 API 的高级感不在路由装饰器，而在长期兼容和失败语义：重复请求不会重复写，旧客户端不会被无意破坏，并发冲突不会静默覆盖。
