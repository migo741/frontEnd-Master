# 学习方法与版本策略

> 建议周期：30–36 周，每周 8–12 小时。目标不是刷完 44 道题，而是让每个结论留下能复核的工程证据。

## 1. 先接受一个现实

你已有前端经验，优势是 TypeScript、浏览器、交互和产品感；短板通常不是“不会写接口”，而是：

- 把进程内变量误当可靠状态；
- 把 TypeScript 类型误当运行时或数据库约束；
- 只测成功路径，不定义超时、重复、乱序和崩溃；
- 会用 ORM，却解释不了 SQL plan、隔离级别和锁；
- 能 Docker 启动，却没有发布、回滚、备份和恢复证据；
- 接上模型 API，就把它叫作 AI 工程。

因此本课的学习单位不是“知识点”，而是“不变量 + 失败实验 + 可复核证据”。

## 2. 每章固定工作流

### 第一步：15 分钟诊断

不看讲义，回答本章自检问题。把答案分为三类：

- 能解释因果并设计实验；
- 只记得结论；
- 完全陌生。

只有第一类可以快读，第二类仍需做实验。

### 第二步：读讲义并画失败链

每读一个设计，写出：

```text
输入或故障
  → 哪个边界失守
  → 哪个状态可能错误
  → 用户能观察到什么
  → 用什么测试或遥测证明
```

只抄 API 名称没有价值。你应该能解释“为什么这个不变量必须放在数据库或持久状态机中”。

### 第三步：先做练习 1

练习 1 是经典正确性题。建议独立限时 60–90 分钟：

1. 先写契约与失败用例；
2. 再写最小实现；
3. 最后运行并发、边界或攻击测试；
4. 记录第一次失败的根因。

### 第四步：再做练习 2

练习 2 会注入生产故障。独立限时 90–150 分钟。做不出可以看答案，但先写下：

- 你认为最危险的竞态；
- 失败后权威状态在哪里；
- 哪些操作可以安全重试；
- 需要保留哪一条证据。

### 第五步：照抄、合上、复写

照抄答案不是失败，停在照抄才是。正确流程：

1. 运行参考实现及测试；
2. 给每个关键分支写一句因果解释；
3. 合上答案，从空文件复写；
4. 改一个条件，例如并发数、超时、租户或故障点；
5. 让实现再次通过。

### 第六步：合入同一个项目

不要产生 44 个孤立 Demo。每章练习先在小型 sandbox 证明，再把正确模式合进统一毕业项目。每 3–4 章提交一次可运行 checkpoint。

## 3. 六阶段节奏

| 阶段 | 章节 | 标准周数 | 每阶段必须留下的证据 |
|---|---:|---:|---|
| Node 运行时与边界 | 01–03 | 3–4 | 资源清单、关闭测试、HTTP 超时测试、架构依赖图 |
| PostgreSQL | 04–07 | 6–7 | DDL、并发测试、SQL plan、迁移回滚、恢复校验 |
| SaaS 边界 | 08–11 | 5–6 | 会话威胁模型、授权矩阵、租户攻击测试、幂等记录 |
| 异步与 Agent 边界 | 12–17 | 8–10 | 重复/乱序/崩溃测试、Outbox、SSE 重放、审批审计 |
| 生产质量 | 18–21 | 6–7 | 安全测试、trace、容量报告、灰度回滚、恢复演练 |
| 毕业项目 | 22 | 6–8 | 部署、演示、ADR、runbook、复盘、答辩录像 |

如果每周只能投入 5 小时，把周期拉到 45–52 周，不要牺牲练习和证据。每周能稳定投入 15 小时且已熟练 TS，可压缩到 22–26 周，但数据库和毕业阶段不压缩。

## 4. 每周模板

建议固定三个学习块：

- 2 小时：讲义、官方文档、失败链；
- 3–5 小时：两道练习及测试；
- 3–5 小时：合入毕业项目、写证据、复盘。

周末用 20 分钟更新四项：本周不变量、最意外失败、留下的证据、下周风险。

## 5. 证据目录建议

毕业项目内维护：

```text
evidence/
├── sql-plans/
├── concurrency-tests/
├── security-tests/
├── traces/
├── load-tests/
├── migrations/
├── recovery-drills/
├── adrs/
├── runbooks/
└── incidents/
```

截图只作为辅助。优先保留可重新执行的 SQL、测试命令、负载脚本和机器可读输出。

## 6. 版本基线

课程编写日期为 2026-08-16。建议基线：

| 技术 | 课程基线 | 更新原则 |
|---|---|---|
| Node.js | 24 LTS | 生产只用官方 Active / Maintenance LTS；不要以 Current 为主线 |
| TypeScript | 6.x strict、ESM | 固定 lockfile；升级先过 typecheck、测试和契约测试 |
| Fastify | 5.x | 只依赖公开 API；关注 Node 支持矩阵 |
| NestJS | 11.x | 作为企业架构映射，不把装饰器当核心能力 |
| PostgreSQL | 18 当前小版本 | 主版本固定，始终更新到受支持的最新小版本 |
| Redis | 8.x | 先验证持久化、过期、淘汰和故障策略，再升级 |
| Kafka | 4.x | 只有出现事件日志、跨消费者或吞吐需求时才引入 |
| Kubernetes | 当前受支持稳定分支 | 学声明式发布、探针、资源和回滚，不背 YAML |

版本是实验环境，不是岗位能力。即使库升级，事务、幂等、deadline、授权、背压和恢复这些不变量仍然成立。

## 7. 每次开课前的版本检查

1. 查看 Node 官方 release status，选择 LTS。
2. 查看 PostgreSQL versioning，确认主版本仍受支持并使用最新小版本。
3. 查看框架的 Node 支持范围和 migration guide。
4. 更新容器 digest 与 lockfile，在独立分支执行测试、迁移和恢复演练。
5. 把版本差异写成 ADR，不直接改生产。

不要在 Markdown 中机械替换版本号。API 或默认行为改变时，同时更新失败案例、答案和验收测试。

## 8. 本地实验环境

最低配置建议：

- Node LTS、corepack 和一个固定版本包管理器；
- Docker Desktop 或兼容容器运行时；
- PostgreSQL、Redis；队列可从 Redis-backed worker 起步；
- `psql`、`curl`、`openssl`、`jq`；
- Node 自带 test runner 或 Vitest；Testcontainers 用于真实依赖测试；
- OpenTelemetry Collector 与本地 trace 后端；
- k6 或同类负载工具。

不要第一周一次性安装所有组件。每章只引入验证本章不变量需要的最少设施。

## 9. ORM 学习规则

顺序必须是：

1. 写出业务不变量；
2. 写 DDL 与约束；
3. 写 SQL 并查看 plan；
4. 明确事务边界；
5. 再决定 ORM / query builder 是否降低重复。

如果一个 ORM 调用生成了你不能解释的 SQL，它尚不具备进入关键链路的资格。不要把 N+1、长事务、隐式 cascade 或迁移锁风险归咎于“数据库太慢”。

## 10. AI Coding 使用规范

这套课允许并鼓励使用 AI，但要把它当不可信结对伙伴：

- 先由你写契约、不变量和失败测试，再让 AI 给实现候选；
- 要求它指出事务边界、重试条件、资源 owner 和安全假设；
- 所有生成 SQL 都跑 plan；所有生成配置都核对官方 schema；
- 不向模型粘贴密钥、个人数据或生产日志；
- 保留 prompt 不如保留测试。通过测试的实现才是证据；
- 面试前必须能在没有 AI 的情况下解释关键链路并现场修改。

## 11. 从前端思维迁移时的常见陷阱

| 前端习惯 | 后端风险 | 新习惯 |
|---|---|---|
| 刷新可恢复一切 | 进程重启会丢内存状态 | 权威事实持久化，派生状态可重建 |
| 类型检查即安全 | 网络输入、旧消息和 DB 数据不受 TS 保证 | 边界校验 + DB 约束 + 契约测试 |
| 请求失败让用户再点 | 重试可能重复扣费或发送 | 幂等键、状态机和 durable intent |
| 全局 store 很方便 | 多租户数据串读、并发请求串上下文 | 请求作用域、可信租户上下文 |
| loading / success / error | 后台任务有租约、取消、恢复、补偿 | 显式持久状态机 |
| 先拆微前端/微服务 | 网络与运维复杂度提前爆炸 | 模块化单体，证据驱动拆分 |

## 12. 阶段门禁

只有满足门禁才进入下一阶段：

- 01–03：能列出所有打开资源，并在 SIGTERM 后证明无新请求进入。
- 04–07：能用数据库而非 if 语句保证核心不变量；能恢复备份。
- 08–11：任意对象 ID、缓存 key、文件 key 都不能绕过租户与授权。
- 12–17：重复、乱序和进程崩溃不产生重复业务副作用。
- 18–21：故障可发现、可定位、可回滚、可恢复。
- 22：陌生评审者能按 README 从空环境复现黄金链路和故障演练。

## 13. 卡住时如何处理

- SQL 不会：先用最小表和 `psql` 复现，不要退回 ORM 猜测。
- 并发不稳定：加 barrier 固定交错顺序，不用循环一万次碰运气。
- 分布式题太大：先写单一权威状态和状态机，再接队列。
- 安全题不会：先画信任边界、资产、攻击者能力和默认拒绝点。
- 部署失败：区分 build、startup、readiness、runtime、migration 五个阶段。

连续两周没有可运行证据时，暂停新章节，回到最后一个通过门禁的 checkpoint。

## 14. 面试训练并行进行

每学完一章，用五分钟录音回答：

1. 本章最重要的不变量是什么？
2. 一个常见实现为什么在并发或故障下失败？
3. 你如何测试并观察它？
4. 你的项目做了什么取舍？
5. 规模扩大十倍时先坏哪里？

这五问比背 100 道八股更接近高级岗位的追问方式。毕业阶段再把它们整理为系统设计答辩。

## 15. 进度的真实定义

| 状态 | 定义 |
|---|---|
| 未开始 | 尚未做诊断 |
| 阅读完成 | 能解释不变量与失败链 |
| 练习完成 | 两题独立尝试并通过测试 |
| 掌握 | 合上答案复写且改变条件仍通过 |
| 项目化 | 已合入毕业项目并留下生产证据 |

只有“项目化”计入最终能力。使用 [课程总索引](./课程总索引.md) 跟踪，而不是只给讲义打勾。
