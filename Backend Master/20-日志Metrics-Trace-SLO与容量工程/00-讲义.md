# 第 20 章：日志、Metrics、Trace、SLO 与容量工程

> 核心不变量：**日志解释单次事件，Metrics 描述总体，Trace 还原因果；遥测必须可关联、可限量、可脱敏，告警必须对应用户伤害。**

## 学完你要能做到什么

- 为请求、队列和 Python worker 传播同一条 trace。
- 设计结构化日志、低基数指标和有用 span。
- 定义 Agent 产品的成功率、延迟、等待与成本 SLI/SLO。
- 使用 error budget 和 burn rate 设计可执行告警。
- 用负载测试找到系统容量拐点，而不是只报平均 QPS。
- 从队列等待、模型调用、数据库和 SSE 区分瓶颈。

## 1. 三类遥测各自回答什么

**日志**回答：“这一个请求或任务发生了什么？”

**Metrics**回答：“过去十分钟所有请求整体怎样？”

**Trace**回答：“一次跨组件调用的时间和因果花在哪里？”

不要把所有内容都塞进日志，也不要给每个用户建一个 metric label。

同一事件应通过 `traceId/requestId/runId` 关联，而不是复制完整 payload 到三个系统。

## 2. 结构化日志

推荐稳定字段：

```text
timestamp level service environment version
event requestId traceId tenantId runId jobId
durationMs outcome errorCode
```

字段名是 API，需要版本与治理。

错误日志记录稳定 code、错误类别和受控 stack；客户端输入错误通常不应全部记 error。

禁止记录：密码、Cookie、Authorization、数据库 DSN、完整 Prompt、附件正文和工具凭证。

脱敏应发生在日志序列化之前，并有自动测试。

## 3. Metric 与基数

典型 metric：

- HTTP 请求数与 duration histogram；
- 活跃请求、连接池使用率和 event-loop lag；
- queue depth、oldest age、处理时间和重试数；
- Agent run 成功/失败/取消与总耗时；
- 模型调用 latency、token、限流和成本；
- tool intent 提出、拒绝、审批、执行；
- SSE 连接数、重连和背压。

适合 label：`service/route/method/status_class/error_code/model_family`。

危险 label：`userId/runId/rawUrl/prompt/errorMessage`。

高基数字段放日志或 trace，可通过 exemplar 从 metric 跳到样本 trace。

## 4. Histogram 而不是平均值

平均延迟会隐藏尾部。

一个 50 ms 请求和一个 20 秒请求平均 10 秒，但两类用户体验完全不同。

使用与 SLO 对齐的 histogram bucket，或支持原生 histogram 的系统。

p95/p99 是窗口统计，不应把各实例 p95 再取平均。

容量规划同时观察吞吐、并发、队列等待、错误率和资源饱和。

## 5. Trace 设计

推荐 span：

```text
HTTP POST /runs
  db.transaction
  outbox.insert
queue.publish
queue.wait
agent.run
  model.call
  tool.intent
tool.execute
SSE deliver
```

不要给每个 token 建 span；这会制造成本和噪声。

token 数作为 span attribute 或 metric，关键步骤使用 event。

span 名称保持低基数；不要把真实 URL ID 放进名称。

异常要设置 status 与稳定 `error.type`，但不要把敏感 payload 放 attributes。

## 6. 跨异步边界传播

HTTP 自动 instrumentation 只能覆盖进程内调用。

写入队列时注入 W3C Trace Context；消费时提取并创建 consumer span。

原始入队 span 与几小时后的任务通常用 link 比父子关系更合理，取决于 tracing backend 和任务模型。

不能无条件传播客户端提交的 baggage；它可能泄密、制造高基数或伪造租户。

tenant 仍来自已认证任务记录，不来自 trace header。

## 7. Sampling

全量 trace 在高吞吐系统中成本很高。

策略可以组合：

- 低比例 head sampling；
- 错误、慢请求和高价值流程 tail sampling；
- 生产与开发不同采样率；
- 安全事件独立审计，不依赖 trace sampling；
- 保持 metric 全量聚合。

采样不能让错误率计算失真，因此 SLI 通常来自 metrics 或权威事件表，而不是样本 trace。

## 8. 从用户旅程定义 SLI

Agent 产品不能只看 HTTP `200`。

一次“创建 run 成功”可能最终超时或给出错误结果。

可定义：

- API 可用性：合法请求中返回预期结果的比例；
- Run 完成率：符合条件的 run 中成功且通过结果校验的比例；
- 首次可见延迟：创建到第一个有意义事件；
- 端到端完成时间：创建到终态；
- 队列等待：入队到 worker 开始；
- 工具正确执行率：获批 intent 中成功且无重复副作用的比例；
- 单位成功成本：总模型/工具成本除以成功 run。

必须明确分母：用户取消、恶意请求和计划维护是否纳入。

## 9. SLO 与 Error Budget

示例：滚动 28 天内，符合条件的 run 有 99% 在 60 秒内进入正确终态。

允许失败比例 1%，就是 error budget。

如果短时间消耗预算的速度远高于正常速度，需要告警。

Burn rate 约为：

```text
当前错误比例 / 允许错误比例
```

告警应使用长短双窗口：短窗口快速确认正在发生，长窗口避免瞬时噪声。

每个告警必须链接 dashboard、runbook、owner 和缓解动作。

CPU 高但用户无损不一定需要叫醒人；成功率下降即使 CPU 正常也需要处理。

## 10. 容量模型

Little's Law 提供基本关系：

```text
并发数 ≈ 到达率 × 平均停留时间
```

每秒 10 个任务、平均执行 30 秒，意味着约 300 个并发在系统中。

但尾延迟、重试和批量流量会让实际需求更高。

需要分别预算：

- Node 活跃请求和 SSE 连接；
- PostgreSQL 连接、IOPS、锁等待；
- Redis 内存与命令延迟；
- 队列积压和 worker 并发；
- 模型供应商 RPM/TPM；
- 单租户峰值与公平性；
- 日志和 trace 本身的成本。

## 11. 负载测试不是打满 CPU

先定义工作负载模型：

- 请求比例和 payload 大小；
- 新建 run、读取状态、SSE 和工具审批的组合；
- 正常与突发到达；
- 热租户与普通租户；
- 模型快慢分布与失败比例；
- 预热、稳定、升压和冷却阶段。

寻找拐点：吞吐不再上升，但 queue wait、p95 或错误率突然增加。

这通常表示某个有限资源饱和，而不是“机器还没 100%”。

## 12. 性能诊断顺序

1. 先确认 SLI 是否真的受损；
2. 从 trace 判断等待发生在哪个组件；
3. 看对应饱和指标和错误分类；
4. 用 profile、SQL plan 或队列记录验证；
5. 改一个变量；
6. 重跑同一负载；
7. 加回归门槛。

不要看到慢就先加缓存或提高 worker 数；可能会把数据库或模型限流打得更严重。

## 13. 成本是容量的一部分

AI 产品需要同时优化质量、延迟和成本。

记录模型、输入/输出 token、缓存命中、工具调用和成功结果，但不把 Prompt 正文作为 label。

“每请求成本”会被大量失败请求美化或恶化，优先观察“每个成功业务结果成本”。

成本异常也可以是安全告警，例如泄漏 key 或无限 Agent loop。

## 14. Dashboard 分层

- 第一层：用户旅程 SLO、流量、错误、延迟；
- 第二层：Node、DB、Redis、queue、worker、模型依赖；
- 第三层：单次 trace、日志和审计；
- 第四层：容量预测、成本与版本对比。

Dashboard 不应需要先知道事故根因才能找到正确图表。

## 章末检查

- 日志、metric 和 trace 是否能通过 ID 关联？
- metric label 是否存在用户、run 或原始 URL 高基数？
- 队列等待是否与任务执行分开测量？
- trace 是否跨 Node、队列与 Python？
- SLO 是否描述用户结果而非进程存活？
- 分母和排除项是否明确？
- 告警是否有 owner、runbook 与用户伤害？
- 压测是否包含突发、慢模型和热租户？
- 是否知道当前安全容量和最先饱和的资源？
