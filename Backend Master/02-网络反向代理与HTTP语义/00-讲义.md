# 第 02 章：网络、反向代理与 HTTP 语义

> Controller 收到的并不是“用户直接发来的请求”。在它前面可能已有 CDN、WAF、负载均衡和网关；每一跳都可能改变连接与元数据。

## 学习目标

- 能沿 DNS、TCP/TLS、代理、HTTP server 到 handler 定位问题。
- 能在可信代理模型下解析客户端 IP、scheme 与 host。
- 能正确使用方法、状态码、缓存验证器和条件请求。
- 能区分连接超时、请求 deadline、上游超时和空闲超时。
- 能设计体积、速率与头部上限，抵抗慢连接和资源耗尽。

## 1. 一次请求经过哪些层

典型生产路径是：

```text
浏览器 → DNS → CDN/WAF → L7 LB → Ingress/反向代理 → Node → 下游
```

浏览器看到 HTTPS，不代表 Node socket 也是 TLS；TLS 可能已在负载均衡器终止。Node 看到的 peer IP 往往是代理地址，而不是最终用户。排查时先确认失败发生在哪一跳，不要把所有 `502` 都归因于应用。

至少区分：DNS 解析失败、TCP 建连失败、TLS 握手失败、代理无法连接 upstream、upstream 超时、应用主动返回错误。

## 2. 反向代理是信任边界

`X-Forwarded-For`、`X-Forwarded-Proto` 和 `X-Forwarded-Host` 都是普通请求头。客户端可以自行发送；只有当直接连接 Node 的 peer 是受控代理时，才能采用代理写入的值。

安全算法不是“永远取最左边 IP”，而是：

1. 把真实 socket peer 放在链尾。
2. 从右向左扫描。
3. 跳过你明确控制的可信代理。
4. 遇到的第一个非可信地址才是客户端边界。

如果平台承诺覆盖而非追加 forwarding header，可按平台契约简化；契约必须写进部署配置和测试。代理拓扑改变而应用不更新信任范围，会导致审计、限流和安全判断错误。

## 3. Host 不能直接用于安全决策

Host 会影响绝对 URL、重定向和租户路由。若直接拼接用户提供的 Host，可能产生恶意重定向、缓存投毒或密码重置链接劫持。

生产服务应配置公开 origin allowlist；生成邮件链接时优先使用配置，而不是请求头。确需多域名时，先规范化并匹配已登记域名。

## 4. 请求身份与链路身份

客户端可携带 request ID，但它不一定可信或唯一。边缘层或应用应生成规范 ID，并把原始值作为单独字段保存。W3C Trace Context 用于分布式追踪，不等于用户身份，也不能替代幂等键。

日志至少包含规范 request ID、trace ID、可信 client IP、route 模板和结果；不要把 token、cookie 或完整查询串直接写入日志。

## 5. HTTP 方法表达意图

- `GET`、`HEAD` 应安全，不改变业务状态。
- `PUT`、`DELETE` 按语义应幂等：重复相同请求，目标状态相同。
- `POST` 通常非幂等，需要第 10 章的幂等协议。
- `PATCH` 是否幂等取决于 patch 文档和服务约定。

“幂等”不表示每次响应完全相同，也不表示内部没有日志。它约束重复操作后的资源状态。

不支持的方法返回 `405` 并带 `Allow`，而不是一律 `404`。认证失败用 `401` 并给出 challenge，已识别但无权用 `403`；冲突用 `409`，前置条件失败用 `412`，缺少必需前置条件可用 `428`。

## 6. 状态码是机器可读控制流

客户端、代理和监控会根据状态码采取不同动作。把所有错误包装成 `200 { success:false }` 会破坏缓存、重试、SLO 与浏览器语义。

错误体可以采用 Problem Details，至少有稳定 `type`、`title`、`status` 和请求实例。不要把数据库错误、堆栈或内部路径暴露给用户。

## 7. 缓存不是“加一个 max-age”

新鲜度回答“多久内不用问服务器”；验证器回答“内容是否仍是同一版本”。`ETag` 可基于资源版本，不必对大响应重新哈希。

`If-None-Match` 命中时，GET/HEAD 返回 `304` 且无消息体。对更新请求，`If-Match` 可实现乐观并发：只有客户端见过的版本仍然存在才修改，否则返回 `412`。

带认证的响应默认不要进入共享缓存。`Vary` 告诉缓存哪些请求头影响表示；遗漏会把压缩、语言或租户表示串给错误用户。`Vary: *` 基本等于不可复用。

## 8. HEAD 不是“返回空 JSON”

HEAD 应返回 GET 会返回的状态和表示头，但不能发送消息体。它适合检查元数据与缓存验证器。Node handler 中要显式避免写 body，并保证 `Content-Length` 指向 GET 表示长度。

`204`、`304` 同样不能携带消息体。代理可能丢弃违规 body，因此本地“看起来能用”不是证据。

## 9. 请求体是潜在的无界资源

不要先把任意请求完整读入内存再验证。入口要限制：头部数量与大小、body 字节数、压缩后膨胀、multipart 文件数、字段数和读取时间。

体积超过上限时尽早返回 `413` 并停止读取。媒体类型不支持返回 `415`；语法损坏用 `400`；语法正确但业务字段无效可用 `422`。上传大对象应流式进入对象存储，详见第 11 章。

## 10. 四类时间边界

- connect timeout：连不上下游多久放弃。
- headers timeout：多久必须收到完整头部。
- request deadline：整次业务允许多久。
- keep-alive/idle timeout：空闲连接保留多久。

反向代理与 Node 的时间配置需要留出层级差。例如外层 5 秒、应用 4.5 秒、下游 4 秒，让应用有机会返回可解释错误。反过来会由代理先产生模糊 `504`。

## 11. 重试发生在哪里

浏览器、CDN、网关、SDK 和业务代码都可能重试。同一调用若每层重试三次，会形成乘法放大。只有在请求可重试、有总 deadline、具备退避与预算时才重试。

网络断开时调用方不知道服务器是否已提交，这是“结果未知”，不能当作必然失败。非幂等写操作必须用幂等键或后续查询确认。

## 12. 代理配置也是代码

需要版本化验证：可信 CIDR、最大 body、转发头覆盖策略、连接与上游超时、WebSocket/SSE 缓冲、健康检查路径。应用测试不能证明 Nginx/Ingress 配置正确，至少要有部署环境的契约测试。

不要在 Node 中盲目实现所有边缘功能。TLS、基础 DDoS 防护和静态压缩通常在边缘；应用负责业务 deadline、认证、授权和语义错误。

## 13. 本章不变量

- 只有可信直接 peer 才能让应用采用 forwarding headers。
- client IP 是审计信号，不是身份凭证。
- GET/HEAD 不产生业务副作用；条件写入必须原子验证版本。
- 无 body 状态不写 body；错误状态与 Problem Details 保持一致。
- 每一跳都有体积、速率、连接与时间上限。

## 14. 常见错误与自检

- `req.headers.host` 直接生成密码重置 URL。
- 永远取 `X-Forwarded-For` 第一个元素。
- `304` 仍发送 JSON，或 HEAD 的长度为零。
- 代理比应用更早超时，导致诊断信息丢失。
- 无差别重试 POST，制造重复订单。

自检：若攻击者直连 Node 并伪造 forwarding headers，你的算法输出什么？一次 PUT 响应丢失后，为何可以安全重试？`If-Match` 检查为何必须与写入原子完成？
