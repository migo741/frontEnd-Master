# 第 22 章：毕业项目、系统设计与面试

> 核心不变量：**作品必须证明你能把用户问题变成可运行、可度量、可恢复、可解释的系统；框架数量、代码行数和“接了大模型”都不是结果。**

## 1. 毕业项目是什么

统一项目名：**多租户 AI 工单与运营工作台（Operations Copilot）**。

它把四套现有课程与 Backend Master 收束成一个旗舰作品：

- JavaScript/浏览器：取消、流、SSE、离线、Worker、安全、性能证据；
- TypeScript：领域状态机、Schema、Brand、Result、模块与大型工程；
- React：路由、服务端状态、并发 UI、可访问性、测试、性能、RSC/SSR 取舍；
- AI Agent：工具循环、Context、RAG 取舍、MCP、HITL、Eval、成本与安全；
- Backend：租户、数据、事务、队列、可靠性、观测、发布和恢复。

它不是一个换皮聊天框。

## 2. 用户问题

一个运营团队每天处理大量客户工单，需要：

- 多人分派、评论、附件和状态流转；
- 快速总结长上下文并建议分类、优先级和回复；
- 对关闭工单、发送外部邮件等动作进行人工审批；
- 在模型失败时仍能人工完成业务；
- 对每次自动化的质量、成本和责任进行追踪。

先找真实的 3–10 位目标用户访谈。

如果没有真实用户，可把现公司中一个内部流程匿名化，但不能使用生产数据或秘密。

## 3. 明确不做什么

第一版不做：

- 通用聊天机器人；
- 任意代码执行；
- 十种模型和五种向量数据库；
- 为了微服务而拆十个服务；
- 复杂计费和完整 CRM；
- 没有用户证据的多 Agent；
- 声称 exactly-once；
- 追求像素数量而牺牲可靠性。

范围约束是高级工程能力的一部分。

## 4. 角色与权限

建议角色：

| 角色 | 权限 |
|---|---|
| agent | 查看/处理被授权项目工单，发起 Agent 建议 |
| manager | 分派、审批高风险工具、查看团队指标 |
| tenant_admin | 管理 membership、角色、集成与配额 |
| platform_operator | 受审计的跨租户运维，不属于普通产品角色 |

所有资源都属于 tenant。

用户知道 UUID 不能获得访问权，缓存、对象、任务和事件也必须保持租户隔离。

## 5. 核心领域模型

```text
Tenant ─ Membership ─ User
   ├── Project ─ Ticket ─ Comment
   │                  └── Attachment
   ├── AgentRun ─ Checkpoint
   │          └── ToolIntent ─ Approval ─ ToolExecution
   ├── UsageLedger
   ├── IdempotencyRecord
   ├── OutboxEvent / InboxMessage
   └── AuditEvent
```

不要从数据库表开始；先写状态与业务不变量，再映射表和约束。

## 6. 系统边界

主线使用模块化单体：

```text
React/Next Web
    ↕ HTTP + SSE
Node/TypeScript API
    ├── PostgreSQL：权威事实
    ├── Redis：缓存、限流
    ├── Object Storage：附件
    ├── Outbox → Queue
    └── Tool Executor：真实副作用
                  ↕ versioned messages
Python Agent Worker
    └── Model / retrieval / planning
```

Python worker 不直连业务主库、不持有用户 token、不直接执行高风险工具。

## 7. 十条毕业不变量

1. 所有查询与副作用都由可信 tenant scope 限定。
2. 同一 HTTP 幂等键只创建一个业务结果。
3. 消息重复、乱序和 worker 重启不会重复真实副作用。
4. PostgreSQL 是权威；Redis 清空后可恢复。
5. Agent 输出通过 Schema、策略与当前事实再验证。
6. 高风险工具必须绑定精确参数、审批人和过期时间。
7. 断开 SSE 不取消 run；显式取消持久、幂等且可观察。
8. terminal 后任何迟到 worker/event 都不能回退状态。
9. 每个请求/run/tool 能跨 Node、queue、Python 用 trace 关联。
10. 新版本、migration 和灾难恢复不会破坏以上九条。

这些不变量应映射到数据库约束、代码边界和自动测试，而不是停留在 README。

## 8. 黄金路径

```text
登录 → 选择 tenant/project → 创建工单 → 上传附件
→ 幂等启动 triage run → Outbox 入队 → Python 处理
→ SSE 展示步骤/结果 → Agent 提出关闭或通知 intent
→ manager 查看精确影响并审批 → Node 二次授权与执行
→ audit/usage/metric 落库 → 用户看到唯一终态
```

非 AI 路径必须始终可用：用户可以手工分类、回复和关闭工单。

Agent 是增强，不是单点故障。

## 9. AI 能力边界

首版只做三个可评测能力：

- 工单结构化分类与优先级建议；
- 基于当前工单/附件的摘要与回复草案；
- 提出一个受控工具 intent。

RAG 只有在用户问题确实需要租户知识库且 Eval 证明收益时加入。

Prompt、框架和模型细节回到 [AI Agent Master](../../AI%20Agent%20Master/课程总索引.md)，本章只要求结果可控、可测和可降级。

## 10. API 与事件

最小 API：

```text
POST   /api/tickets
GET    /api/tickets?cursor=...
POST   /api/tickets/:id/attachments/presign
POST   /api/tickets/:id/agent-runs
GET    /api/runs/:id
GET    /api/runs/:id/events
POST   /api/runs/:id/cancel
POST   /api/tool-intents/:id/approve
POST   /api/tool-intents/:id/reject
GET    /api/audit-events?cursor=...
```

写接口有幂等语义，列表使用稳定游标，错误使用统一机器码。

事件协议沿用第 16 章序号、重放和 terminal 规则。

## 11. 非功能目标

示例目标需按真实负载修订：

- 普通 API p95 < 500 ms；
- 首个有意义 Agent 事件 p95 < 3 s；
- 合格 run 99% 在 60 s 内正确终结；
- 跨租户访问测试 100% 拒绝；
- 同一 intent 外部副作用不重复；
- RPO ≤ 5 min，RTO ≤ 60 min；
- 单位成功成本有 dashboard 和预算；
- 正常容量保留至少 30% 已验证余量。

目标不是承诺，而是需要证据验证的假设。

## 12. 分阶段交付

### 阶段 A：问题与不变量

- 用户访谈、工作流、威胁模型；
- 状态机、ERD、权限矩阵；
- ADR 与范围外清单；
- 验收测试先行。

### 阶段 B：无 AI 的可靠 SaaS

- 身份、多租户、工单、评论、附件；
- PostgreSQL 约束、游标、事务、迁移；
- React 核心界面和 E2E；
- 云上部署与备份。

### 阶段 C：异步运行底座

- run 状态机、Outbox、queue、checkpoint；
- SSE 回放、取消、重试和限流；
- Redis 删除后恢复；
- 故障测试。

### 阶段 D：Agent 与 HITL

- Node/Python 契约；
- 固定 Eval 集；
- tool intent、审批、执行、审计；
- Prompt Injection 和成本上限。

### 阶段 E：生产证据

- logs/metrics/traces/SLO；
- 压测、容量、canary、回滚；
- DR game day；
- 真实用户迭代。

### 阶段 F：公开答辩

- 5 分钟产品演示；
- 30–45 分钟系统设计；
- 一次现场变更；
- 一次故障复盘；
- 中英文 README 与架构文档。

## 13. 证据比功能更多重要

作品至少保存：

- 用户问题与范围决策；
- 架构图、ERD、状态机、威胁模型；
- SQL plan 与迁移演练；
- 契约、并发、E2E、故障测试；
- 性能 baseline、trace 和容量拐点；
- Eval 数据集、结果、成本和失败分类；
- 安全攻击报告；
- canary/rollback 与 DR 时间线；
- 一份真实事故或演练复盘；
- 用户反馈和三轮改进。

简历写“使某指标从 A 到 B”，不能只写“使用了 Redis/Kafka/AI”。

## 14. 系统设计答题顺序

1. 澄清用户、规模、关键旅程与合规边界；
2. 写业务和安全不变量；
3. 粗算流量、并发、数据和成本；
4. 定 API、状态机和数据权威；
5. 画同步与异步路径；
6. 处理超时、重复、乱序和部分成功；
7. 加多租户、授权、审计和秘密；
8. 定 SLI/SLO、容量、发布与恢复；
9. 说明取舍、演进点和未解决风险。

不要先说“上微服务、Kafka、Kubernetes”。

## 15. 面试官真正会追问什么

- 为什么 PostgreSQL 是权威，Redis 丢了怎么办？
- HTTP 成功但队列失败如何避免半完成？
- queue 重复投递为什么不会重复发邮件？
- worker 迟到结果如何防止覆盖新 generation？
- SSE 回放和实时订阅之间的竞态怎么处理？
- 用户批准后参数被替换怎么办？
- Python worker 被 Prompt Injection 后能做什么？
- migration 为什么能与旧 Pod 共存？
- 99% SLO 的分母是什么？
- 外部工具“可能成功但响应丢失”如何恢复？

答案要引用代码、测试、trace 或演练证据。

## 17. 毕业判断

只有同时满足下面条件才算毕业：

- 陌生人能按 README 在干净环境运行；
- 黄金路径与人工降级路径可用；
- 十条不变量都有自动证据；
- 至少完成一次压测、故障注入、canary 回滚和 DR；
- Agent 有固定 Eval，不以“聊起来不错”验收；
- 有真实用户或真实内部团队反馈；
- 能在 45 分钟内解释取舍，并诚实说出仍未解决的风险。

课程结束不是把你包装成“架构师”，而是让你拥有接近高级岗位要求的可验证作品。真实职级仍来自生产规模、业务结果与跨团队影响力。
