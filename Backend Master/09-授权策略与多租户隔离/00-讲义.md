# 第 09 章：授权策略与多租户隔离

## 本章目标

让“已登录用户”只能访问被明确允许的资源，并把租户隔离同时落实到应用层、数据库层、缓存、队列与审计。高级后端不把隐藏按钮当权限，也不相信客户端提交的 `tenantId`。

## 1. 认证结果不是授权结论

认证只给出 principal；授权必须回答：谁，在什么租户和上下文中，对哪个资源，执行什么动作。资源状态变化后结论也可能变化。

```text
principal + action + resource + environment -> allow / deny + reason
```

默认拒绝。缺少 principal、策略、资源或必要属性时都不能“先放过去”。401 表示尚未认证，403 表示已认证但禁止；为防资源枚举，对不该知道存在性的资源可统一返回 404。

## 2. RBAC、ABAC 与关系授权

- RBAC：角色到权限，适合稳定职责；
- ABAC：根据 tenant、部门、金额、时间、资源状态决策；
- ReBAC：根据 owner/member/parent 等关系决策。

生产系统常组合使用：角色给出候选能力，资源关系和业务条件进一步收紧。不要把每个例外都变成新角色，也不要让 controller 散落数百个字符串判断。

## 3. Policy Decision 与 Enforcement

策略函数应纯、可测试，HTTP/GraphQL/任务消费者都是 enforcement point。用动作常量和明确输入：

```ts
type Decision = {allow: true} | {allow: false; reason: 'ROLE' | 'TENANT' | 'STATE'}
type Action = 'ticket:read' | 'ticket:update' | 'ticket:refund'
```

controller 只负责解析请求；service 在读取/修改资源的同一可信边界重新授权。只在路由中间件检查 `isAdmin` 会漏掉具体资源归属和状态。

## 4. tenantId 只能来自可信上下文

URL/body/header 中的 tenant id 是请求参数，不是事实。当前租户必须由 Session 中允许的 membership 与显式切换流程确定。每次切换产生新的、可审计的上下文；不能仅修改 localStorage。

查询必须同时带 `tenant_id` 与实体 id。只按全局 id 查询后再在 JavaScript 比租户，既可能提前泄漏数据，也容易在某条路径忘记检查。

## 5. 表结构先支持隔离

共享表方案应让 tenant 成为键的一部分：

```sql
PRIMARY KEY (tenant_id, id)
FOREIGN KEY (tenant_id, project_id) REFERENCES project(tenant_id, id)
```

这样数据库会拒绝跨租户外键。仅给每表加一列却继续用全局外键，不能形成结构性保护。极高隔离需求才考虑 schema/database per tenant，其迁移和连接成本更高。

## 6. PostgreSQL RLS 是第二道门

Row-Level Security 可在漏写 where 时阻止跨租户读取/修改：

```sql
ALTER TABLE ticket ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON ticket
USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

请求必须在数据库事务中 `SET LOCAL` 上下文。连接池会复用连接，使用普通 `SET` 而忘记重置可能把 A 租户带到 B 请求。应用账号不能拥有 `BYPASSRLS`，表 owner 默认也可能绕过，需要专门验证部署角色。

## 7. RLS 不是唯一授权系统

RLS 擅长行隔离，不理解“退款必须低于限额且工单已批准”等业务动作。应用策略仍需检查角色、关系和状态；RLS 负责最后的租户安全网。

后台迁移/报表若需要跨租户权限，使用独立最小权限身份、显式租户批次和审计，不能让普通 Web 进程永久拥有超级权限。

## 8. 列表、批量和导出最容易漏

授权不能只保护详情页。列表查询必须先按可见范围过滤；批量接口逐资源或用等价集合条件授权；导出任务要在创建与执行时都验证授权快照/当前策略，并记录请求者、租户、过滤条件与产物权限。

“先查全部再过滤”会泄漏计数、排序、时延甚至内存中的敏感数据。

## 9. TOCTOU 与事务内再检查

授权检查与写入之间，资源 owner、状态或权限可能变化。高风险写操作把读取、策略判断和条件更新放在同一事务，使用版本条件或行锁：

```sql
UPDATE ticket SET status = 'refunded', version = version + 1
WHERE tenant_id = $1 AND id = $2 AND status = 'approved' AND version = $3;
```

影响行数为 0 表示前置条件已失效，不能当成功。

## 10. 缓存也有授权边界

缓存 key 至少包含 tenant 与影响结果的权限版本/主体维度。`ticket:42`、只按 URL 的 CDN key 或跨用户共享 GraphQL DataLoader 都可能泄漏。

权限撤销要求可接受的传播窗口。高风险动作实时查权威源；普通读可用短 TTL 和 membership/policy version 主动失效。不要缓存最终 allow 决策却不包含资源版本。

## 11. 队列和事件不能信任 payload 身份

生产者可以写入 `requestedBy` 作为审计，但消费者不能仅凭消息中的角色授权。消费者从可信数据库加载任务、租户和当前策略；消息签名也只证明来源，不证明用户此刻仍有权限。

跨租户 worker 必须每个 job 建立并清理 tenant context，日志、metric、临时文件和对象存储 key 同样隔离。

## 12. 审计是不可抵赖的业务事实

高风险决策记录 actor、effective tenant、action、resource、decision、policy version、request/trace id 和结果。拒绝事件需采样/限流，避免攻击者制造日志 DoS；敏感字段做最小化。

审计表不应允许业务角色更新历史记录。需要更强保证时追加写并异步归档到受保护存储。

## 13. 测试策略

除示例测试外，生成“任意 tenant A principal 永远读不到 tenant B resource”的属性测试；覆盖列表、详情、搜索、导出、缓存命中、队列重放和管理员路径。用两个真实数据库角色验证 RLS，而不是只 mock repository。

## 14. 评审清单

- tenant 是否来自可信 Session/membership，而不是请求体？
- 每条查询、外键、缓存 key、对象 key、job 是否包含 tenant？
- 应用策略与 RLS 是否各自承担正确职责？
- 连接池中的 tenant context 是否 transaction-local？
- 批量、搜索、导出、后台任务是否同样授权？
- 权限撤销、资源变化和并发写是否有确定语义？
- 审计能否回答谁在何时依据哪个策略做了什么？

## 本章速记

多租户隔离不是一个 `WHERE tenant_id`。它是一条贯穿 Session、策略、键、外键、RLS、缓存、任务、对象存储和审计的不可绕过不变量。
