# 第 19 章：测试、契约与故障验证

> 核心不变量：**Mock 只用于团队真正拥有的边界；关键业务不变量必须在真实 PostgreSQL、Redis、队列和故障时序下得到验证。**

## 学完你要能做到什么

- 按失败成本选择单元、集成、契约、E2E 和故障测试。
- 让时间、随机 ID、外部调用和并发时序可控制。
- 使用真实 PostgreSQL 验证约束、事务、锁和迁移。
- 用消费者驱动或共享 fixture 验证跨服务协议。
- 主动制造重复、乱序、超时、崩溃和部分成功。
- 区分“测试实现细节”和“证明系统不变量”。

## 1. 后端测试不是覆盖率比赛

覆盖率只能说明哪些行运行过，不能说明并发、约束和失败语义正确。

更有价值的问题是：

- 两个请求同时执行时，不变量是否仍成立？
- 事务提交后进程崩溃，消息重放会发生什么？
- Redis 被清空，系统还能否从 PostgreSQL 恢复？
- Python worker 升级后能否读取旧任务？
- 外部服务成功但响应丢失，重试会不会重复副作用？
- 时间刚好越过 deadline，状态属于谁？

测试计划应从风险清单推导，而不是从文件列表推导。

## 2. 五种测试的职责

| 类型 | 主要证明 | 不应承担 |
|---|---|---|
| 单元测试 | 纯领域规则、状态机、解析器 | 数据库事务语义 |
| 集成测试 | SQL、约束、锁、缓存、消息适配器 | 整个用户旅程 |
| 契约测试 | 两端对同一协议的理解 | 服务内部实现 |
| E2E 测试 | 少量关键业务旅程 | 穷举全部边界 |
| 故障测试 | 重复、乱序、崩溃、依赖故障 | 每次提交都跑全量灾演 |

比例不是固定金字塔；数据与并发密集的后端需要更多集成测试。

## 3. 什么可以 Mock

适合 Mock 的边界：

- 团队封装的模型供应商 port；
- 邮件、支付等外部服务的 adapter；
- clock、UUID、随机数；
- 罕见错误注入点。

不应只用 Mock 验证：

- PostgreSQL 唯一约束、隔离级别和 SQL；
- Redis 原子脚本；
- 框架的 HTTP 序列化；
- 实际 JSON Schema/Pydantic 兼容性；
- Docker 健康检查和启动顺序。

如果 Mock 的行为是你猜出来的，它只能证明代码符合你的猜测。

## 4. 真实基础设施与隔离

Testcontainers 能为测试启动指定版本的 PostgreSQL、Redis 或消息系统。

每个测试需要确定的隔离策略：

- 每测试事务并回滚：快，但无法覆盖多连接提交行为；
- 每测试 schema/database：隔离强，但较慢；
- truncate 已知表：折中，必须正确处理 FK 和 sequence；
- 每测试容器：最强也最慢，适合迁移/启动测试。

并发测试必须使用不同数据库连接，不能共享一个事务连接制造假并发。

生产迁移应原样用于测试环境，不能另写一份简化 schema。

## 5. 可控时间与 ID

直接散落 `Date.now()`、`new Date()` 和 `randomUUID()` 会让过期、重试和排序测试抖动。

把它们作为窄依赖：

```ts
interface Clock { now(): Date }
interface IdGenerator { next(): string }
```

不要把所有依赖都包装成接口；只抽出不确定、昂贵或外部的边界。

Fake timer 不应替代数据库 `now()` 的集成测试。两种时钟需要明确谁是权威。

## 6. 测试业务不变量

好的断言：

- 同一个幂等键只产生一条订单；
- 跨租户查询永远为空；
- terminal 后没有状态回退；
- 重复消息不会重复外部副作用；
- deadline 后不会启动新模型调用；
- 审批参数变化后不可执行。

脆弱断言：

- 某 repository 方法恰好被调用一次；
- 内部函数按特定顺序调用；
- 私有字段等于某个值；
- 完整错误文本逐字相同；
- 大片无意义 snapshot。

测试公共结果、持久事实和可观察副作用。

## 7. 并发测试

并发测试不是 `Promise.all` 两个立即完成的内存函数。

需要 barrier 让两个事务都到达临界点，再同时继续。

可用：

- 数据库 advisory lock；
- 测试专用 barrier；
- adapter 注入的 hook；
- 受控 fake server 延迟响应。

测试必须设置总超时，失败时打印连接状态和关键行，避免 CI 永久挂住。

多跑几十次只能增加发现概率，不能替代确定性时序控制。

## 8. 契约测试

Node 与 Python 的 Agent 消息至少共享：

- 有效最小 fixture；
- 每种判别分支；
- 未知字段；
- 缺失必填字段；
- 边界时间、数字和 Unicode；
- 当前版本与上一版本；
- 超大 payload 拒绝。

契约测试要在生产者和消费者 CI 中都运行。

Schema Registry 能帮助治理，但不能替代语义兼容说明。

新增字段如果改变默认行为，即使 JSON Schema 兼容，也可能是业务破坏。

## 9. 故障注入目录

至少能注入：

- 调用前失败；
- 外部副作用后、记录结果前崩溃；
- 数据库 commit 后、消息 ack 前崩溃；
- 超时但上游最终成功；
- 重复、乱序和迟到消息；
- Redis 数据消失；
- 队列不可用；
- 磁盘/连接池/线程池耗尽；
- 部署时新旧版本并存。

每种故障先写期望最终状态和人工修复入口。

## 10. E2E 的边界

E2E 应覆盖少量黄金路径：

- 登录并创建工单；
- 启动 Agent、看到流式事件；
- 审批工具并看到唯一副作用；
- 断线恢复；
- 权限撤销。

不要在 E2E 中穷举所有 Schema 字段。

外部模型可使用录制响应或本地 fake provider，但协议、超时和流式分块必须与真实 adapter 契约一致。

定期在隔离环境运行少量真实模型 smoke/eval，避免 fake 漂移。

## 11. 数据与测试清理

测试数据也属于安全边界。

- 不复制生产 PII 到开发机；
- fixture 使用合成数据；
- 测试对象存储和队列有独立 namespace；
- CI 失败日志仍需脱敏；
- 容器和临时凭证在 finally 中清理；
- 并行测试使用唯一数据库/schema 前缀。

测试清理失败不能误删共享或生产资源。

## 12. Flaky 测试治理

Flaky 不是“偶尔重跑即可”。

常见根因：真实时间、端口冲突、未等待异步清理、共享数据、依赖网络、无界重试、事件顺序假设。

处理流程：保留失败证据 → 隔离影响 → 找到不确定源 → 改成可控制边界 → 移除重试掩盖。

禁止长期把失败测试标为 skip 而没有 owner 和退出日期。

## 13. 测试结果也是证据

毕业作品应保存：

- 测试分层说明；
- 数据库版本矩阵；
- 契约兼容报告；
- 并发与故障时间线；
- 覆盖到的不变量列表；
- 未覆盖风险与原因；
- flaky 数与修复记录；
- 测试总时长和并行策略。

## 章末检查

- SQL 和事务是否在真实 PostgreSQL 上验证？
- 并发测试是否真的使用不同连接并控制时序？
- clock、ID 和外部响应是否可控？
- Node/Python 是否共同消费契约 fixture？
- 是否测试 commit 后、ack 前崩溃？
- 重复和乱序消息是否进入日常测试？
- E2E 是否聚焦用户结果而非内部调用？
- 测试日志和 fixture 是否无生产秘密与 PII？
