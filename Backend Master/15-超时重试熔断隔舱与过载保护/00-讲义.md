# 第 15 章：超时、重试、熔断、隔舱与过载保护

## 本章目标

让服务在依赖变慢、部分失败和突发流量中“有界地失败”，而不是用重试把小故障放大成全站雪崩。你应能从端到端 deadline 推导每跳预算，并组合 retry、circuit breaker、bulkhead 与 admission control。

## 1. 最危险的故障是慢

明确失败会快速释放资源；无限等待会占满连接、内存、队列和线程池。每个网络、数据库、队列和外部操作都需要 deadline，且调用方取消要向下传播。

超时只表示调用方不再等待，不证明服务端没有执行。写操作超时后先按 operation id 查状态，不能换 id 重做。

## 2. Deadline 优于层层独立 timeout

入口携带绝对 deadline 或剩余预算。下游预算包含网络、执行和返回余量：

```text
remaining = requestDeadline - now
childBudget = min(configuredMax, remaining - safetyMargin)
```

若预算不足，尽早拒绝，不开始注定无法完成的工作。层层都设置 5 秒会让三跳请求拖到 15 秒以上。

不要盲信客户端传来的超长 deadline；服务端有上限，并使用单调时钟计算时长。

## 3. Node 中传播取消

Node 24 的 fetch、timer promises 和许多驱动支持 `AbortSignal`。为子调用组合父 signal 与 deadline；结束后清理 timer/listener。

取消是协作协议。数据库查询是否真的取消、第三方是否接收断连，需要按驱动验证；未取消的服务端操作仍要幂等。

## 4. 只重试有机会成功的错误

可重试候选：连接暂断、明确 429/502/503/504、乐观冲突（重读后）、provider 指示的临时错误。不可重试：Schema/权限/余额不足、绝大多数 4xx、确定性业务拒绝。

写操作还要求幂等。无法判断副作用是否发生时状态是 unknown，不属于普通 retryable。

## 5. Backoff、jitter 与 Retry-After

指数退避限制频率，full jitter 打散客户端同步：`random(0, min(cap, base * 2^attempt))`。尊重合法 Retry-After，但仍受总 deadline 和本方上限约束。

每次请求最大尝试数之外还要 retry budget，例如滚动窗口内 retry 不超过原始请求的 10%。依赖大面积故障时，预算会主动停止放大。

## 6. 重试应在哪一层

通常由最了解幂等、deadline 和错误协议的一层重试一次。网关、SDK、service、driver 若各重试 3 次，三层可放大 27 倍。

在架构图标出 retry owner，其他层关闭默认重试或只做连接级安全恢复。记录 attempt 与最终 outcome。

## 7. Circuit Breaker 的状态机

- closed：正常放行并统计结果；
- open：快速拒绝，等待 cooldown；
- half-open：只允许少量探针；成功达到阈值后关闭，失败立即重开。

breaker 按真正故障域分组，如 provider/region/operation；全站一个 breaker 会让单个接口拖垮全部功能，每用户一个又产生无界状态。

只把依赖故障计入，不把业务 400 当失败。breaker 保护资源，不保证数据正确；fallback 仍需业务批准。

## 8. Bulkhead 隔离资源

为依赖/任务类型设置独立并发 semaphore、连接池与有界等待队列。慢报表不能占光登录连接，单一 tenant 不能耗尽全局 provider 配额。

队列满时立即 429/503，而不是继续把 Promise 堆在内存。并发上限根据压测与下游容量调整，不靠 CPU 核数猜。

## 9. Admission control 与负载削减

在最便宜的入口尽早拒绝：请求体大小、认证、租户额度、全局 inflight、队列深度、deadline。优先保留健康检查和关键写完成路径，关闭昂贵可选功能。

负载削减需要明确优先级与公平：不能总让小租户被大客户挤掉，也不能让高优先级无限饿死后台修复。

## 10. 过载中的排队论直觉

到达率长期大于处理率，队列必然无界增长；扩 timeout 只增加同时等待人数和尾延迟。监控 utilization、queue wait、service time、oldest age，而非只看平均响应时间。

设置 Little's Law 意识：inflight ≈ throughput × latency。依赖延迟翻倍而吞吐不变，所需 inflight 也翻倍；若资源无余量就必须降载。

## 11. Hedging 的严格边界

对高尾延迟、幂等只读请求，可在分位阈值后向独立 replica 发第二请求，首个成功后取消其余。hedge 会增加负载，故障时可能更糟，必须受小预算控制。

禁止默认 hedge 写请求；同一故障域的两个副本也没有价值。

## 12. Fallback 与降级

可接受：返回明确标记的旧公开内容、关闭推荐、把写入保存为待处理 proposal。不可接受：权限服务失败时默认 allow、RAG/数据库失败时编造、支付未知时显示失败并鼓励再付。

降级状态应进入响应和指标，客户端知道结果是 stale/partial。恢复路径定期演练。

## 13. 防止恢复风暴

依赖恢复后，积压、定时任务、缓存 miss 和客户端重试同时涌入。使用 jitter、渐进提高并发、tenant fairness、warm cache 与 retry budget；breaker half-open 探针数量有限。

自动扩容不是瞬时，且可能把压力传给数据库。扩容策略与连接池/依赖配额联动。

## 14. 参数不是复制来的常量

从 SLO、下游 P95/P99、连接池、允许并发和故障演练校准 deadline、queue、breaker 窗口。配置版本化、可灰度、带上下限；不能让运行时动态配置把 timeout 设为 0 或无限。

每次变更观察成功率、tail latency、shed、retry amplification 和 downstream saturation。

## 15. 评审清单

- 是否有端到端 deadline，并向下传播 AbortSignal？
- timeout 后未知副作用是否 reconciliation，而非盲重试？
- retry 分类、幂等、jitter、Retry-After 与总预算是否齐全？
- 是否只有一层拥有重试，放大倍数可否计算？
- breaker 故障域/half-open 是否有界？
- bulkhead、队列、tenant fairness 和入口 shed 是否明确？
- fallback 是否不会绕过权限或伪造成功？
- 恢复风暴是否演练并有渐进放量？

## 本章速记

韧性不是“多重试几次”。真正的韧性是预算、隔离与背压：工作必须在有限时间、有限并发和有限重试内结束，失败时保住核心不变量。
