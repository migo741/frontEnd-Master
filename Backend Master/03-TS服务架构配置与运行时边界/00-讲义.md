# 第 03 章：TypeScript 服务架构、配置与运行时边界

> `strict: true` 能约束你写下的代码，却不能让环境变量、HTTP body、数据库结果或模型输出自动变安全。

## 学习目标

- 能把 TypeScript 静态类型与运行时数据证明分开。
- 能在启动阶段一次性解析、校验并冻结配置。
- 能组织 domain、application、adapter 与 composition root。
- 能让业务用例不依赖 Fastify、NestJS、ORM 或全局变量。
- 能把失败稳定映射为公开错误，而不泄漏内部异常。

## 1. TypeScript 在运行时会消失

下面的断言不会校验任何数据：

```ts
const body = request.body as CreateTicketInput;
```

编译后 `as` 不存在。HTTP、环境变量、数据库 JSON、队列消息和 AI 输出都应从 `unknown` 开始，经运行时 schema 证明后，才进入内部类型世界。

高级类型、品牌类型与 Schema 单一事实来源见 `TS Master` 第 09、10、12 章。本章不重讲类型体操，只处理“证明发生在哪一层”。

## 2. 边界解析，而不是到处防御

在 adapter 入口完成：

1. 大小与媒体类型限制；
2. 语法解析；
3. schema 校验与规范化；
4. 转为 application command。

用例内部不应反复判断 `title` 是否字符串。如果边界已经证明，内部类型就是可信契约。相反，从数据库读取 JSONB、调用第三方 API 或消费旧版消息时又越过了新边界，必须重新验证。

## 3. 配置也是不可信输入

`process.env.PORT` 的类型是 `string | undefined`。`Boolean("false")` 是 `true`，`Number("")` 是 `0`；随意转换会制造静默错误。

配置应在启动阶段：

- 只读取一个命名空间，例如 `APP_*`；
- 明确 required、default 与合法范围；
- 聚合报告全部问题；
- 返回不可变的规范对象；
- 失败即拒绝 ready，而不是运行到第一条请求才爆炸。

业务模块不能直接读 `process.env`。否则测试结果依赖进程全局状态，同一个值还可能在不同模块被解析成不同语义。

## 4. 秘密不是普通字符串

数据库密码、OIDC secret 与模型 key 需要字符串形态才能交给驱动，但不应被默认序列化、日志化或拼进错误。可用 `SecretString` 包装，只有最靠近 SDK 的 adapter 才调用 `reveal()`。

包装不是保险箱：堆内存里仍有明文。真正控制包括秘密管理器、最小权限、轮换、日志脱敏和禁止进入模型上下文。

## 5. 四层足够开始

```text
domain       业务实体、不变量、领域错误
application  用例、端口接口、事务边界
adapters     HTTP、PostgreSQL、队列、第三方 SDK
main         配置、实例化、生命周期与启动
```

这不是要求每个文件夹都有几十个抽象。规则是依赖方向向内：domain 不导入 Fastify，application 不导入 `pg`，adapter 实现 application 定义的端口，main 负责连接它们。

## 6. Controller 只做翻译

HTTP adapter 的职责是把 method、身份上下文和已校验 body 翻译为 command，再把 use-case result/error 翻译为 HTTP。它不应决定工单能否关闭，也不应拼接 SQL。

同一用例未来可从 HTTP、CLI、队列或定时任务调用。若用例参数是 `FastifyRequest`，复用和测试都会被框架绑死。

## 7. 端口应围绕用例设计

不要创建万能 `Database` 接口或“所有实体通用 Repository”。用例需要什么，就声明窄端口：

```ts
interface TicketWriter {
  insert(ticket: NewTicket): Promise<Ticket>;
}
```

窄端口让测试 fake 简单，也让数据库行为显式。事务需要跨多个 repository 时，端口应提供一个业务事务操作，而不是让用例偷拿底层 client。

## 8. 把不确定性注入

时间、ID、随机数和外部调用会让测试不稳定。通过 `Clock`、`IdGenerator`、repository 等依赖注入，而不是在用例深处调用 `Date.now()`、`crypto.randomUUID()` 或全局 singleton。

不需要为了 DI 安装容器。普通对象参数和工厂函数已经能表达依赖。NestJS provider 是一种 wiring 方式，不应成为领域模型。

## 9. 错误需要分层

至少区分：

- 输入错误：调用者可修正，通常是 `400/422`；
- 认证授权错误：第 08、09 章处理；
- 冲突或前置条件错误：稳定业务语义；
- 依赖暂时失败：可能返回 `503`，但要服从重试预算；
- 程序缺陷：记录内部 cause，公开统一 `500`。

不要根据错误 message 做控制流，也不要把 PostgreSQL constraint 名称直接暴露。adapter 只映射受控错误类型，其余全部进入内部诊断。

## 10. 返回错误还是抛异常

预期业务分支可用 discriminated union；无法继续的基础设施失败可抛受控异常。两种风格都可以，关键是团队一致，且不能让“所有异常都变 400”。

`catch (error)` 在 strict 下是 `unknown`。先识别受控类型，再记录不可识别异常。不要用 `error as Error` 逃掉证明。

## 11. Composition root 是唯一组装点

`main.ts` 的顺序应清晰可见：加载配置 → 创建 telemetry → 创建 pool → 创建 repository/use case → 创建 HTTP adapter → listen → 注册 shutdown。

模块 import 不应连接数据库、启动 server 或读取秘密。无副作用 import 让测试、迁移 CLI 和 worker 可以复用同一 application 层。

## 12. ESM 与包边界

本课使用 Node 24 LTS、TS 6 strict ESM。模块与 package export 细节见 JavaScript 课程第 07 章。后端特别注意：

- 源码 import 使用与产物一致的 `.js` specifier；
- `package.json` 明确 `type: module`；
- 测试和生产采用同一解析策略；
- 不依赖 import 顺序注册全局副作用。

不要把转译器的宽松行为误认为 Node 的真实模块语义。

## 13. 框架只是 adapter

Fastify 适合看清 request lifecycle、schema 和 plugin encapsulation；NestJS 适合理解企业模块、provider 和 decorator。课程主线用薄 adapter，随后映射到 NestJS，而不是分别重写业务规则。

验证 schema 应能导出为 OpenAPI 或共享 SDK，但生成物不是权威业务规则。React 和 Python worker只依赖版本化契约，不依赖后端内部类。

## 14. 测试分层

- domain/application：纯单元测试，fake clock、ID 与端口。
- adapter：真实 parser、序列化、数据库和错误映射集成测试。
- composition：启动最小应用，验证配置失败和生命周期。
- contract：验证 OpenAPI/JSON Schema 对客户端与 worker 保持兼容。

大量 mock 框架对象通常说明边界放错。比起 mock `FastifyRequest`，直接测试 use case command 更稳定。

## 15. 本章不变量与常见错误

- 所有外部值从 `unknown` 开始；验证只在真实边界发生。
- `tenantId` 来自可信身份上下文，绝不取自 body。
- 配置只解析一次，启动失败不进入 ready。
- domain/application 不依赖框架、ORM、环境变量和系统时钟。
- 未识别错误不泄漏内部 detail。

常见错误：`as` 冒充验证、Controller 承载业务、模块顶层连库、全局 service locator、把每个函数都包成无意义 class、把 secret 整个打印进配置日志。

## 16. 自检

1. 数据通过 schema 后，在哪些位置会再次变成不可信？
2. 为什么 `process.env` 分散读取会造成语义漂移？
3. 用例若导入 Fastify 类型，未来队列消费者会付出什么成本？
4. 哪些错误可以稳定公开，哪些只应通过 request ID 查询内部日志？
5. 如何证明请求 body 中的 `tenantId` 无法覆盖身份上下文？
