# 第 07 章：Schema 演进、迁移与恢复

> 迁移不是“在数据库运行一段 SQL”。它是旧应用、新应用、历史数据和恢复系统共同参与的分布式发布。

## 学习目标

- 能按 expand → migrate → contract 演进 schema。
- 能让前后两个应用版本在滚动发布期间同时工作。
- 能评估 DDL 的锁、扫描、WAL 与失败后状态。
- 能设计可重入 backfill、验证门和 contract 删除条件。
- 能用真实恢复演练证明备份满足 RPO/RTO。

## 1. 为什么一次 rename 会停机

滚动发布时，旧实例和新实例会共存。若先把 `priority` 直接 rename 为 `severity`，旧实例立即报“列不存在”；若先部署只认识 severity 的新实例，它又无法读取旧 schema。

数据库发布必须兼容至少 N 与 N-1 应用版本。迁移顺序是协议，不只是文件编号。

## 2. Expand、migrate、contract

典型列替换：

1. expand：新增 nullable 列，不删除旧列。
2. compatibility：新代码双读/双写，必要时短期触发器兼容旧实例。
3. migrate：小批量回填历史数据，可暂停、可重跑。
4. validate：证明新列完整、一致、查询计划达标。
5. cutover：新代码以新列为主，仍保持旧版本兼容。
6. contract：确认旧实例和回滚窗口消失后，删除旧依赖。

每阶段都要可独立部署和观察。不要把六步塞进一个巨大事务。

## 3. 向后兼容与向前兼容

旧应用遇到新列通常无感，但遇到新 enum/status 值可能解析失败。新应用读取旧行时也要容忍新列尚未回填。

兼容不仅是 DDL：API、队列消息、缓存、CDC、BI 查询和 Python worker 也可能依赖旧字段。contract 前要通过依赖清单和实际使用证据，而不是“仓库搜索不到”。

## 4. DDL 也会持锁

许多 `ALTER TABLE` 需要短暂但强的锁。即使命令本身毫秒级，如果前面有长事务，它会排队；排队中的 DDL 又可能阻塞后续查询，形成事故。

迁移会话设置较短 `lock_timeout`，宁可安全失败后重试，也不要无限等锁。`statement_timeout` 控制扫描上限。发布前查长事务、锁队列和表大小。

## 5. Add column 不都一样

新增 nullable 列通常是快速 metadata 操作。现代 PostgreSQL 对某些 immutable constant default 可避免重写整表，但不能把所有 default 都当免费；volatile expression、类型变化和 generated 数据仍需评估。

稳妥路径常是：先 nullable → 应用写新值 → 分批 backfill → 加/验证约束 → 再设 NOT NULL。不要在大表一条 UPDATE 回填全部行，制造长事务、WAL 洪峰和 replica lag。

## 6. 可重入 backfill

backfill 每批按稳定主键选取，predicate 只处理尚未完成的行，更新后记录速率、剩余量、锁等待和复制延迟。

多个 worker 可用 `FOR UPDATE SKIP LOCKED` 分工，但必须接受跳过正在锁定的行，并循环到剩余为零。任务崩溃重跑不能重复破坏结果。

节流以数据库健康为准，而不是追求最快完成。停止 backfill 后在线流量必须继续正确。

## 7. 约束分两阶段验证

大表可先：

```sql
ALTER TABLE ... ADD CONSTRAINT ... CHECK (...) NOT VALID;
```

新写入会受约束，历史行暂未扫描。随后 `VALIDATE CONSTRAINT` 检查历史数据。验证成功的合适 CHECK 还能帮助后续 `SET NOT NULL` 避免重复全表证明。

`NOT VALID` 不是永久状态；监控必须发现长期未验证约束。

## 8. 在线创建索引

`CREATE INDEX CONCURRENTLY` 降低对写入的阻塞，但耗时更长、额外扫描，而且不能位于事务块中。失败可能留下 `indisvalid = false` 的索引，需要检测并安全删除后重试。

迁移工具若默认把每个文件包进事务，要为 concurrent index 提供显式非事务步骤。创建后用真实 query plan 证明它被正确使用，再删除旧索引。

## 9. 类型与状态值演进

缩窄类型、改变时区、text 转 numeric 都可能失败或改变语义。先新增目标列并显式转换，记录不可转换行，而不是在生产 `USING` 中假设全都干净。

新增业务状态要先让所有 reader 能容忍/认识它，再让 writer 产生它。删除状态则先停止写入、迁移存量、验证为零，最后收紧约束。

## 10. 迁移执行权

应用运行时角色不应拥有 DDL 权限。迁移由单独 job/角色执行，使用 advisory lock 或平台互斥保证同一环境只有一个 migrator。

不要让每个应用实例启动时自动跑迁移；扩容会产生竞争，迁移失败还可能让所有实例无法启动。应用启动只检查 schema 是否位于兼容范围。

## 11. Migration ledger

记录 migration ID、checksum、开始/结束时间、执行者、应用版本和结果。已经执行的 migration 文件不可静默修改；checksum 变化应阻止继续部署。

失败后不要盲目重新标记成功。先判断 PostgreSQL 是否回滚了事务、是否留下 concurrent invalid index、backfill 到哪一批，再按 runbook 恢复。

## 12. 回滚不等于 down migration

应用回滚通常比 schema 回滚安全，因此 expand 阶段要保持旧代码可运行。删除列后 down migration 不能恢复数据；给它重新加列只得到空值。

破坏性 contract 要有观察期、备份/恢复点和负责人批准。优先 roll forward 修复，除非已验证 down path 不丢数据且锁风险可接受。

## 13. 备份、恢复与 PITR

`pg_dump` 是逻辑备份，适合可移植恢复、对象级检查和中小规模场景；物理 base backup + 连续 WAL 归档支持 point-in-time recovery。云数据库的“自动备份”也必须核对保留期、加密、跨区域与恢复权限。

- RPO：最多能接受丢失多长时间的数据。
- RTO：从宣布事故到恢复服务允许多久。

每天备份不自动等于 RPO 24h；备份可能损坏、WAL 链可能断、恢复可能超时。只有隔离环境恢复成功并通过业务校验，备份才是证据。

## 14. 恢复演练验证什么

恢复到新实例，绝不覆盖源库。验证：

- schema migration ledger 与预期版本；
- 关键表行数和时间范围；
- 无孤儿外键、无跨租户关联、核心 CHECK 成立；
- 最近已知业务 marker 是否存在；
- 应用只读 smoke test 与关键查询 plan；
- 实测恢复耗时和人工步骤。

敏感生产数据恢复到测试环境前必须满足访问、脱敏和销毁政策。

## 15. PITR 的边界

PITR 可恢复到错误操作之前，但会形成新的数据库时间线。恢复点后的合法写入也不在新实例中，必须决定是否重放、对账或补偿。不要一发现误删就直接切换所有流量。

先停止继续破坏，记录时间/LSN，隔离恢复，比较差异，再按事故指挥流程切换或提取丢失数据。

## 16. 发布观测与终止条件

迁移期间观察锁等待、查询延迟、错误率、WAL、replica lag、表膨胀、backfill 速率和新旧字段差异。任何一项越过阈值就暂停，而不是“已经跑一半所以坚持”。

contract 的门槛应机器可查：旧版本实例数为零、旧字段读写指标持续为零、差异查询为零、备份恢复演练通过、回滚窗口结束。

## 17. 本章不变量与自检

- 发布兼容 N/N-1；破坏性变化拆成多次可观察发布。
- backfill 可重入、可暂停、有上限，不与在线流量争光资源。
- concurrent index 与非事务 DDL 有失败清理路径。
- 应用角色无 DDL 权限，migration checksum 不可漂移。
- 备份只有恢复到隔离环境并通过业务校验才算有效。

自检：为什么先 rename 列会破坏滚动发布？`NOT VALID` 保护哪些数据？PITR 到误删前会损失哪些合法写入？
