# 第 05 章：SQL、索引、执行计划与稳定分页

> “本地很快”不是性能证据。高级后端必须能把查询、不变量、索引顺序和真实执行计划连成一条因果链。

## 学习目标

- 能从访问模式反推 SQL 与复合索引列序。
- 能阅读 `EXPLAIN (ANALYZE, BUFFERS)` 的关键节点。
- 能解释选择性、统计估算、heap fetch 与排序成本。
- 能实现有唯一 tie-breaker 的 keyset pagination。
- 能为 cursor 绑定版本和过滤条件，并验证并发插入行为。

## 1. 从访问模式开始

不要先为每列建索引。先写出高价值查询：谁调用、租户范围、过滤条件、排序、返回列、P95 目标、数据量和读写比例。

示例：某租户按单一状态查看最新工单，每页 50 条：

```sql
WHERE tenant_id = $1 AND status = $2
ORDER BY created_at DESC, id DESC
LIMIT 51
```

自然索引候选是 `(tenant_id, status, created_at DESC, id DESC)`：等值列在前，排序列随后，唯一 ID 完成全序。若还有“不筛状态”的高频列表，需要另一个 `(tenant_id, created_at DESC, id DESC)`；一个索引很难同时最优覆盖两种路径。

## 2. B-tree 是有序数据结构

复合 B-tree 按列从左到右形成字典序。能否利用后续列，取决于前导列的约束。只有 `(status, created_at)` 时，按 tenant 查询无法有效缩小范围；多租户系统通常先放 tenant。

索引可以反向扫描；显式 DESC 的价值在混合方向和表达设计意图。`ORDER BY a DESC, b ASC` 需要与索引方向匹配，不能靠整体反向扫描解决混合方向。

## 3. 索引不是免费缓存

每个索引增加 INSERT、UPDATE、DELETE 成本、WAL、磁盘和 vacuum 压力。低基数单列如 status 往往选择性差；与 tenant 和排序列组成访问路径才有价值。

删除未使用索引前先观察一段完整业务周期。索引使用数为零不一定无用：它可能服务月末任务、外键检查或故障场景。

## 4. INCLUDE 与 index-only scan

`INCLUDE` 把只用于返回、不参与搜索和排序的列放进叶子页。它可能支持 index-only scan，但不是保证：只有 visibility map 表明 heap page 对当前 snapshot 全可见时，才可避免 heap fetch。

把大 text/JSON 全部 INCLUDE 会膨胀索引，降低缓存命中并提高写放大。列表页只选择需要字段，不要 `SELECT *`。

## 5. Partial 与 expression index

只查未关闭工单可考虑 partial index：

```sql
CREATE INDEX ... WHERE status <> 'closed';
```

查询 predicate 必须让 planner 能证明与索引 predicate 相容。状态分布改变后，partial index 价值也会改变。

大小写搜索可用规范化列或 expression index。若每次写入已存 `normalized_email`，普通唯一索引通常比所有查询都写 `lower(email)` 更清晰。

## 6. EXPLAIN 先看估算，再看现实

`EXPLAIN` 只显示估算，不执行；`EXPLAIN ANALYZE` 会真实执行，不能随意用于 DELETE/UPDATE。常用：

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL, FORMAT JSON) SELECT ...;
```

阅读顺序：

1. actual rows 与 estimated rows 是否数量级偏差；
2. 循环次数 `loops`，内层小成本乘巨大 loops 也会昂贵；
3. 是否出现不必要 Sort、Seq Scan 或大量 Rows Removed by Filter；
4. shared hit/read、临时文件与 heap fetch；
5. 总时间是否包含冷缓存、网络与客户端序列化之外的限制。

## 7. 估算错误通常有原因

统计信息过期、列相关性、数据倾斜和参数类型都可能误导 planner。先 `ANALYZE`，再比较实际与估算；必要时提高列 statistics target 或用 extended statistics 表达列相关性。

不要用 `SET enable_seqscan = off` 当修复。小表或返回大比例行时 Seq Scan 本来更快。优化目标是正确代价，不是强迫计划节点名称。

## 8. 参数与 prepared plan

同一 SQL 对小租户和巨型租户可能需要不同计划。PostgreSQL 在 custom 与 generic plan 间权衡；数据高度倾斜时要检查真实参数下的计划。

参数类型不明确会导致隐式转换或错误估算。SQL 中必要时显式 `$1::uuid`、`$2::text`，不要把 UUID 列转 text 去迁就输入，那会让索引失效。

## 9. OFFSET 分页的两个问题

`OFFSET 100000 LIMIT 50` 仍要找到并丢弃前十万行，越后越慢。更重要的是，并发插入或删除会让行位置移动，产生重复或遗漏。

OFFSET 适合小型后台页、明确需要跳页且数据有限的场景。无限滚动、时间线和高数据量 API 应使用 keyset pagination。

## 10. Keyset 必须有全序

只按 `created_at DESC` 不稳定：多行可以同一时间。加不可变唯一 `id DESC`，cursor 保存最后一条已返回记录的 `(created_at, id)`：

```sql
AND (created_at, id) < ($after_time, $after_id)
ORDER BY created_at DESC, id DESC
```

获取 `limit + 1` 行判断是否还有下一页；next cursor 指向“最后一条已返回行”，不是额外探测行。

## 11. Cursor 是协议，不是 base64 小技巧

cursor 至少含版本、排序键和过滤条件指纹。客户端改变 status 后复用旧 cursor 应被拒绝，否则分页语义混乱。

cursor 可以透明，但必须严格验证类型、长度、日期和 ID。若要防止篡改和构造昂贵跳转，可加 HMAC；签名不替代授权，tenant 仍来自可信上下文而不是 cursor。

版本字段允许未来改变排序。不要序列化数据库内部 offset 或把完整 SQL 放进 cursor。

## 12. 并发下“稳定”的准确含义

Keyset 保证基于不可变排序键向后遍历时，不因前方新插入而重复或跳过已有后续行。它不提供数据库 snapshot：分页期间被删除的行会消失，状态变化可能改变过滤集合。

若产品要求导出时看到一个固定快照，应创建导出任务并持有可恢复的业务快照边界，而不是跨几十分钟持有数据库事务。

排序字段若会更新，记录可能跨越 cursor。时间线用不可变 `created_at/id`；按可变优先级排序时要明确弱一致语义或引入版本化视图。

## 13. 搜索与模糊匹配

`LIKE '%word%'` 通常无法使用普通 B-tree。先判断需求是前缀、全文还是相似度，再选择 B-tree pattern ops、PostgreSQL FTS 或 trigram。不要看到搜索就立即引入独立搜索集群。

任何搜索索引仍要带 tenant 过滤，并验证查询成本上限。用户控制的排序字段只能映射到 allowlist SQL 片段，不能直接字符串拼接。

## 14. 生产验收

保存代表性数据规模下的 plan JSON、数据分布、PostgreSQL 版本和参数。CI 不应断言精确成本或节点名称，但可做防退化基准：最大扫描行数、临时磁盘、P95 与结果正确性。

上线索引用 `CREATE INDEX CONCURRENTLY` 以降低写阻塞，但它不能放在事务块中，失败后可能留下 invalid index；第 07 章处理发布步骤。

## 15. 本章不变量与自检

- 所有租户查询从可信 tenant 条件开始。
- 列表排序形成唯一且尽量不可变的全序。
- cursor 绑定版本与过滤条件，不能提供 tenant 身份。
- 索引选择必须有真实 plan 和数据分布证据。
- 性能测试同时验证结果无重复、无越界。

自检：为什么 `(status, tenant_id, created_at)` 常不如 tenant 在前？index-only scan 为何仍可能 heap fetch？新行插入第一页后，第二页 keyset 与 OFFSET 分别怎样变化？
