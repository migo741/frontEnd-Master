# 第 21 章：容器、CI/CD、云上发布与灾难恢复

> 核心不变量：**构建一次，逐环境晋级同一不可变制品；健康检查区分 alive 与 ready；发布、迁移、回滚和恢复都必须经过演练。**

## 学完你要能做到什么

- 构建可复现、非 root、最小权限的 Node/Python 镜像。
- 设计从提交到生产的质量、供应链和审批门禁。
- 正确配置 startup、readiness、liveness 与 graceful shutdown。
- 使用 expand/contract migration 完成不停机发布。
- 选择 rolling、blue-green 或 canary 并定义自动回滚条件。
- 用 RTO/RPO 设计 PostgreSQL、对象存储和队列恢复演练。

## 1. 制品而不是服务器

CI 产生一个带 digest 的镜像，测试、预发和生产晋级同一 digest。

禁止在生产机器 `git pull && npm install`。

重新构建会引入依赖、时间、镜像层和供应链差异，使“预发测过”失去意义。

制品应带：

- Git commit 与版本；
- 基础镜像 digest；
- 锁文件；
- SBOM；
- 漏洞扫描结果；
- 构建来源证明与签名；
- 数据库最低/最高兼容版本。

## 2. 可复现 Node 镜像

多阶段构建把编译依赖留在 builder。

运行阶段：

- 明确 Node 版本和基础镜像 digest；
- 只复制运行所需文件；
- 使用非 root 用户；
- 只读根文件系统；
- 由 init 进程回收僵尸子进程；
- 不在镜像中写秘密；
- 固定 locale/timezone 语义；
- 暴露的端口不等于安全边界。

Alpine 更小，但 musl 与 native addon 可能带兼容成本；不要只按镜像大小选择。

## 3. 配置与秘密

镜像不区分环境，配置在运行时注入并启动时验证。

普通配置可来自 ConfigMap/环境变量；秘密优先来自云工作负载身份和 Secret Manager。

Kubernetes Secret 的 base64 不是加密。

不要让每个 Pod 获得云账户永久 key，也不要在 CI 日志展开 secret。

配置变更同样需要版本、审查、灰度和回滚。

## 4. 三类健康检查

**startup**：应用是否完成启动；用于慢启动，避免过早 liveness 杀进程。

**liveness**：进程是否进入无法自愈的卡死；失败会重启。

**readiness**：当前实例是否应该接收新流量；失败只摘流量。

不要让 liveness 依赖数据库、Redis 和模型供应商，否则公共依赖故障会触发全体重启风暴。

readiness 可以考虑关键本地状态、连接池初始化和 draining，但也要避免每次探针制造昂贵依赖流量。

## 5. 优雅发布

Pod 收到 SIGTERM 后：

1. readiness 变为 false；
2. 停止接收新请求和任务；
3. 等待负载均衡传播；
4. 排空普通 HTTP；
5. 告知 SSE 客户端重连；
6. checkpoint 或归还队列 lease；
7. 关闭数据库、Redis、遥测 exporter；
8. 在 termination grace deadline 前退出。

如果超时，进程会被 SIGKILL，因此业务不能依赖 finally 一定执行。

关键事实应在平时就持久化，而不是关机时才抢救。

## 6. 数据库 migration 不是启动副作用

多个 Pod 同时启动时自动跑 migration 会竞争或把发布卡死。

把 migration 作为独立、可观察、单实例的发布步骤。

不停机演进：

1. expand：增加兼容列/表/索引；
2. 部署兼容新旧 schema 的应用；
3. 限速 backfill；
4. 切换读写并观察；
5. 下一次发布再 contract 删除旧结构。

删除列、修改含义和大表锁操作不能与代码切换塞进同一步。

rollback 代码不等于 rollback 数据；迁移策略需单独说明。

## 7. 发布策略

**Rolling**：简单、省资源；要求新旧版本并存兼容。

**Blue-green**：切换快、回退直观；需要双份容量和数据兼容。

**Canary**：用少量真实流量验证；需要可靠指标、流量分配和自动分析。

选择取决于风险和基础设施，不是成熟度排名。

AI 功能 canary 还要比较结果质量、成本和安全拒绝率，不能只看 HTTP 错误。

## 8. 自动回滚条件

回滚应基于相对于基线的：

- API 错误与 p95；
- Agent 正确完成率；
- queue age 与 retry；
- tool 拒绝/重复副作用；
- 数据库锁等待和连接池；
- 单位成功成本；
- 新错误码与安全事件。

指标存在遥测延迟，发布系统要避免在数据不足时误判成功。

回滚前确认 schema 与消息仍兼容旧代码。

## 9. CI/CD 门禁

合理顺序：

```text
format/lint/typecheck
→ unit/contract/integration
→ build once
→ SBOM/vulnerability/license/signature
→ ephemeral environment smoke/E2E
→ staging migration rehearsal
→ canary
→ automated analysis
→ progressive production
```

不是所有步骤都要串行；无依赖检查可以并行。

受保护环境、最小 CI 权限、OIDC 短期云身份和审批日志比共享部署密码可靠。

## 10. RTO 与 RPO

**RTO**：业务允许多久恢复。

**RPO**：允许丢失多少时间的数据。

它们是业务决策，会决定备份频率、跨区复制、成本和演练方式。

例如 RPO 5 分钟意味着每日全量备份显然不够。

不要为所有数据承诺相同等级：业务事实、附件、缓存和 trace 的价值不同。

## 11. PostgreSQL 恢复

需要组合：

- 定期全量备份；
- WAL/PITR；
- 备份加密与访问隔离；
- 跨故障域副本；
- 恢复到隔离环境；
- 数据完整性与业务不变量校验；
- 应用连接切换和 DNS/secret 更新。

只看到备份任务绿色，不能证明文件可解密、WAL 连续或应用能读取。

## 12. 对象存储、队列和 Redis

对象存储需要版本、保留策略、清单和数据库引用一致性校验。

队列通常不是长期事实来源；恢复 PostgreSQL 后可从 Outbox 重建待发布事件。

这会制造重复投递，因此消费者必须幂等。

Redis 可清空并从数据库/流量回暖；如果无法重建，就应重新评估它是否偷偷变成权威数据源。

## 13. 灾难恢复不是普通回滚

应用回滚处理坏版本；灾难恢复处理区域、数据或控制面不可用。

DR runbook 应明确：

- 谁宣布事故与选择恢复点；
- 如何冻结写入；
- 如何建立隔离恢复环境；
- 如何验证 tenant、额度、审批和审计不变量；
- 如何处理恢复点之后的外部副作用；
- 如何重放 Outbox 并抑制重复；
- 如何切流和通知；
- 原区域恢复后如何防 split-brain。

## 14. Game day

演练应包含真实计时和意外：

- 删除一张非生产关键表；
- 使用损坏或缺失的一段备份；
- 模拟区域网络隔离；
- 恢复后队列重复投递；
- 对象存在但数据库引用缺失；
- 旧版本应用误连新数据库。

记录实际 RTO/RPO，而不是设计文档里的目标。

演练后必须更新自动化、runbook 和 owner。

## 15. 成本与退出策略

高可用不是无限复制。

按业务损失决定多区、热备、冷备和保留时长。

同时保留供应商退出路径：数据导出、Schema、对象清单、密钥轮换和 DNS 控制。

不要为了简历在小项目部署复杂 Kubernetes；单容器平台也能练习不可变制品、探针、灰度、备份和恢复。

## 章末检查

- 测试和生产是否运行同一镜像 digest？
- 镜像是否非 root、无秘密并带 SBOM？
- liveness 是否错误依赖共享数据库？
- SIGTERM 是否停止接单并有有界排空？
- migration 是否由独立步骤执行并兼容 N/N-1？
- canary 是否同时看正确率、成本和安全？
- 是否定义业务认可的 RTO/RPO？
- 最近一次恢复演练何时完成，实际结果是多少？
- 恢复后 Outbox 重放是否会制造危险副作用？
