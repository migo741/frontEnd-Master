# 第 12 章：Redis 缓存、限流与协同

## 本章目标

把 Redis 当作有明确失败语义的加速器和协调组件，而不是第二个随意写入的数据库。你应能处理缓存击穿、旧值回填、热 key、限流原子性、租户公平与 Redis 故障。

## 1. 先问“Redis 丢了会怎样”

若 Redis 全部清空后业务事实丢失，说明它已成为事实源，必须按数据库标准设计持久化、备份和一致性。本章默认 PostgreSQL 保存权威状态，Redis 可重建。

适合 Redis：短期缓存、Session 活跃索引、限流、短期去重、任务协调。财务账本、唯一订单状态、长期幂等记录不应只靠 TTL key。

## 2. Key 是公共契约

key 包含环境、schema version、tenant、实体和影响结果的维度：

```text
prod:ticket:v3:{tenantId}:{ticketId}
prod:rate:v2:{tenantId}:{principalId}:{routeGroup}
```

tenant 不能省略。Redis Cluster 中 `{...}` 是 hash tag，应只包需要原子处理的稳定片段；错误 hash tag 会把所有租户压到一个 slot，制造热点。

值带业务 version 与生成时间，反序列化从 `unknown` 校验。部署新 schema 时改 key version，而不是让新代码猜旧 JSON。

## 3. Cache-aside 基本路径

读：查缓存 → miss 查 PostgreSQL → 写缓存。写：提交 PostgreSQL → 删除缓存。不要先删缓存再提交 DB，否则事务回滚后缓存缺失并可能回填旧值。

即使“DB 后删缓存”，仍有竞态：慢读在更新前读取旧 DB，更新提交并删 key 后，慢读又把旧值写回。解决依赖版本，而不是迷信双删延时。

## 4. 版本化防旧值回填

缓存写入携带 row version，并通过 Lua/Redis Function 只接受更高或相等版本；或用实体版本组成不可变 key，再由短指针指向当前版本。

数据库更新后发布失效事件，但事件可能重复/延迟；消费者用 version 幂等。高风险读取可绕过缓存或验证版本，不用“最终一致”掩盖权限错误。

## 5. TTL 的意义

TTL 是风险上界与容量控制，不是正确失效机制。加入随机 jitter，避免大量 key 同时过期；负缓存只对确定不存在且短 TTL，避免攻击者填满随机 id。

不同数据用不同 staleness budget。权限、封禁和价格不能照搬文章列表的 TTL。

## 6. 缓存击穿、穿透、雪崩

- 穿透：大量不存在 key；输入限制、短负缓存、必要时 Bloom filter；
- 击穿：单个热 key 过期；进程内 singleflight + 跨实例短 lease，只有 owner 回源；
- 雪崩：大量 key/Redis 同时失败；TTL jitter、容量保护、DB bulkhead、降级和预热。

拿不到 lease 的请求不能无限自旋；可短等、返回稍旧值或被 admission control 拒绝。

## 7. stale-while-revalidate

缓存同时保存 freshUntil/staleUntil。fresh 内直接返回；stale 区只允许一个刷新者，其他返回旧值；超过 staleUntil 必须回源或失败。

只适用于允许短暂过期的数据。用户撤权、账户冻结等安全事实不能返回 stale allow。

## 8. 限流不是一个 INCR

固定窗口简单但边界可突刺；滑动日志精确但成本高；token bucket 支持稳定速率和有限 burst，常用于 API。检查与扣减必须原子，使用 Redis Lua/Function。

限流维度组合 IP、principal、tenant、route、风险等级。只按 IP 会误伤 NAT；只按用户会被匿名攻击绕过。租户全局预算之外还需用户子预算，防单用户吃光租户额度。

## 9. 时间与精度

多实例本机时钟可能漂移。Lua 内用 Redis `TIME`，所有 token 计算在一个原子脚本内。浮点误差可用整数微 token 或接受并测试误差边界。

响应提供 `RateLimit-*`/Retry-After 时不能暴露内部敏感配额；客户端退避仍不替代服务端保护。

## 10. Redis 故障时 fail open 还是 closed

按动作风险决定：公共只读内容可局部 fail open 并用进程 bulkhead 保护 DB；登录、退款、防暴力破解通常 fail closed 或进入更保守本地限额。

不能在 Redis 超时时无限直打 PostgreSQL。缓存故障是流量放大器，必须有回源并发上限和熔断。

## 11. 分布式锁的边界

锁有 lease；持有者暂停超过 lease 后，另一个持有者可进入。旧持有者恢复后仍可能写，所以关键资源需要单调 fencing token，由数据库拒绝旧 token。

如果数据库唯一约束、行锁或幂等键能解决，不要先上分布式锁。释放锁必须 compare owner token 后删除，不能 `DEL` 别人的新锁。

## 12. Pub/Sub 不是可靠事件日志

Redis Pub/Sub 断线期间消息会丢，只适合可丢通知。需要恢复、consumer group、pending/ack 时考虑 Redis Streams 或专用队列，但仍设计重复投递、trim 和持久化边界。

缓存失效不能只依赖一次 Pub/Sub；TTL/version/reconciliation 提供兜底。

## 13. 大 key、热 key 与内存

限制 value、集合成员和单命令复杂度；禁止无界 `KEYS`、大范围 `SMEMBERS`。用 SCAN 仍要控制节奏。热 key 可本地短缓存、拆读副本或请求合并，但拆分计数会改变原子语义。

监控 hit ratio 之外还看 miss 回源量、evictions、latency、blocked clients、hot keys、memory fragmentation、script errors 和每租户占用。

## 14. Redis 8 与部署纪律

启用 ACL 最小权限、TLS/私网、命令超时和明确 eviction policy；客户端设置连接池、offline queue 策略与断线上限。脚本按内容 hash/函数版本发布，升级前做 cluster 与 failover 测试。

不要让开发环境的单机语义冒充生产 Cluster/Sentinel/托管服务语义。

## 15. 评审清单

- Redis 清空后能否从权威源恢复？
- key 是否带 tenant/schema/version，value 是否 runtime parse？
- 慢读旧值能否覆盖新缓存？
- TTL、jitter、负缓存和回源 bulkhead 是否明确？
- 限流是否原子、分层、公平，并定义 Redis 故障策略？
- 锁释放是否比较 owner，关键写是否有 fencing？
- Pub/Sub 丢消息后是否仍能恢复正确状态？

## 本章速记

Redis 提供速度，不自动提供正确性。版本、数据库约束、原子脚本、过载保护和可重建性，才决定缓存与协调在故障中是否安全。
