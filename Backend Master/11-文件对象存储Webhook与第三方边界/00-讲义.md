# 第 11 章：文件、对象存储、Webhook 与第三方边界

## 本章目标

安全接收大文件和第三方事件，并在不可信网络、重复投递、乱序、恶意内容、SSRF 与提供方故障下保持正确。文件名、Content-Type、Webhook JSON 和远端 URL 都只是输入，不是事实。

## 1. 文件上传是状态机

推荐把上传分为：申请 → 上传到隔离区 → 完成确认 → 校验/扫描 → 可用或拒绝。业务数据库保存状态，object store 保存字节；两者通过稳定 object id 关联。

```text
pending -> uploaded -> scanning -> ready
                    \-> rejected
pending/uploaded --expiry--> abandoned
```

不要在 API 进程内把整个文件读进 Buffer。大文件使用流或预签名直传；服务端仍决定 key、大小上限、允许类型、过期时间和后续校验。

## 2. 对象 key 不能来自文件名

客户端文件名仅作为经过净化的展示元数据。对象 key 使用 tenant + 随机 object id，禁止 `../`、绝对路径、控制字符和覆盖已有对象。

bucket 默认私有；下载先做资源级授权，再签发短寿命 URL，或由服务端流式代理。长期公开 URL 会绕过未来权限撤销。

## 3. Content-Type 不可信

浏览器和对象 metadata 声明的 MIME 可伪造。服务端按 magic bytes/解析器识别允许格式，限制压缩层数、解压后大小、像素数、页数和解析时间，防 zip bomb、图片炸弹和解析器漏洞。

富文本/HTML/SVG 即使“只是附件”也可能在浏览器同源执行。主动内容使用独立下载域、`Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`；需要预览时做严格转换/净化。

## 4. 完整性与 TOCTOU

申请上传时声明字节数与 SHA-256；完成后通过可信对象存储 metadata 或流式计算验证。校验/扫描通过前对象只在 quarantine。promote 应复制到不可变 final key 或使用对象版本，并把精确 version/checksum 写入数据库。

否则攻击者可能在扫描后覆盖同一个 key，让“已扫描”的记录指向新内容。

## 5. 生命周期与一致性

数据库事务无法与对象存储原子提交。必须允许 orphan：

- DB 有 pending、对象未上传：过期任务清理；
- 对象已传、回调丢失：reconciler 根据前缀/记录恢复；
- DB 标 ready、对象删除失败：重试删除并告警；
- 用户删除：先撤销访问，再异步物理清理。

每个清理动作幂等，并保留合规 retention/legal hold 的优先级。

## 6. 下载与 Range

下载响应明确长度、类型、ETag/checksum 和 disposition。代理 Range 时验证单/多区间策略，限制并发和带宽，防超大范围放大。对私密对象，CDN cache key 和签名必须包含权限边界，响应不得被公共缓存。

## 7. 入站 Webhook 的五步

1. 在限制大小的前提下保留原始请求字节；
2. 校验时间戳窗口与签名，使用常量时间比较；
3. 根据 provider/event id 在 inbox 去重；
4. 先持久化再快速返回 2xx；
5. 后台按业务状态机处理，容忍重复和乱序。

签名必须覆盖时间戳和 raw body。先 JSON parse 再 stringify 会改变字节，导致错误验证或安全歧义。

## 8. 密钥轮换与重放

Webhook secret 放 secret manager，日志不打印。轮换窗口允许 current/previous 两把 key，并记录命中的 key version；窗口结束删除旧 key。时间戳只限制重放时间，event id 唯一约束才阻止窗口内重放。

签名正确只证明提供方发过这段字节，不证明事件顺序、资源当前状态或该动作仍被允许。处理前按远端 API 或本地版本规则确认。

## 9. 乱序事件

`payment.succeeded` 可能先于 `payment.created`，旧 `failed` 可能晚于新 `succeeded`。使用 provider resource version/sequence；若没有，就把 Webhook 当“资源可能变化”的 hint，再拉取权威快照。

不要按到达时间做 last-write-wins。无法识别顺序时，保守进入 reconciliation，而不是猜。

## 10. 出站 Webhook

出站 payload 包含 event id、occurred_at、schema version；以本方 secret 对 timestamp + body 签名。投递至少一次，指数退避、有限尝试、DLQ/手动重放；消费者必须幂等。

不能在业务事务中同步等待客户 endpoint。先写 outbox，第 14 章会完成可靠投递。

## 11. 第三方 HTTP 与 SSRF

任何用户可影响的 URL 都可能访问 metadata、localhost、内网和重定向目标。优先让用户选择预注册 integration，而不是接受任意 URL。

若必须请求：协议/域名 allowlist、解析后拒绝 private/link-local/loopback IP、连接时固定已验证地址或使用受控 egress proxy、每次重定向重新校验、禁用自动携带内部凭证、限制 DNS/连接/响应时间与字节数。

仅在请求前 `new URL()` 不防 DNS rebinding；仅屏蔽字符串 `127.0.0.1` 不防 IPv6、十进制和重定向绕过。

## 12. 第三方失败边界

为 connect、headers、body、整体 operation 分别设 deadline；只对安全/幂等动作重试。保存 provider request id、我方 operation id 和结果摘要，未知状态先查询 reconciliation API，不盲目再写。

响应从 `unknown` 做 Schema 解析；字段缺失、HTML 错误页、200 内业务失败都要分类。第三方错误不能原样回显给用户或模型。

## 13. 观测与审计

指标：上传各状态数量/停留时间、扫描失败、orphan、下载拒绝、Webhook 验签/重复/延迟/乱序、第三方超时与未知结果。标签用 provider/type/key-version 等有限集合，不放 URL、文件名、正文。

## 14. 评审清单

- 对象 key、类型、大小、checksum 是否由服务端验证？
- 扫描前是否隔离，扫描后是否绑定不可变版本？
- orphan 与删除失败是否有 reconciler？
- Webhook 是否基于 raw bytes 验签、timestamp + event id 防重放？
- 重复、乱序和未知状态是否安全？
- 任意 URL、redirect、DNS 和响应大小是否受控？
- 文件、secret、签名和正文是否不会进入日志？

## 本章速记

文件和 Webhook 都跨越了无法原子提交的外部系统。正确设计依赖状态机、不可变身份、原始字节验证、幂等 inbox/outbox、隔离区与 reconciliation。
