# 第 06 章：事务、隔离、锁与并发控制

> 并发正确性不能靠“这两行代码离得很近”。只要中间有一次等待，其他事务就可能改变你刚看到的世界。

## 学习目标

- 能解释 PostgreSQL MVCC snapshot 与三种隔离级别。
- 能识别 lost update、write skew、幻读和结果未知。
- 能在原子 UPDATE、行锁、乐观版本和 SERIALIZABLE 之间选择。
- 能按稳定顺序加锁并处理 deadlock/serialization retry。
- 能写可重复的并发测试，而不是靠手点两个请求。

## 1. 事务保护业务不变量

事务不是为了把 SQL “写在一起”，而是声明一组事实要么一起成立，要么都不成立。转账的核心不是两条 UPDATE，而是“总额守恒、余额不负、同一租户、重复失败不留下半成品”。

先写不变量，再选择最小事务边界。事务过小会暴露中间状态，过大会长时间持锁、积累旧版本并占住连接。

## 2. ACID 不等于自动无竞态

Atomicity 保证事务提交或回滚；Consistency 依赖你定义的约束与逻辑；Isolation 决定并发事务互相能观察什么；Durability 取决于提交和持久化配置。

数据库不会猜“至少一名医生值班”或“库存不能超卖”。没有约束、锁或正确隔离，这些规则仍会被并发破坏。

## 3. PostgreSQL MVCC

更新不是在所有读者眼前原地覆盖；PostgreSQL 为行版本记录可见性，事务按 snapshot 判断能看到哪个版本。读通常不阻塞写，写通常不阻塞普通读，这是高并发基础。

代价是旧版本需要 vacuum 回收。长事务会长期保留旧 snapshot，造成表膨胀、复制延迟和 vacuum 压力。HTTP 请求不要开启事务后等待用户、模型或第三方服务。

## 4. READ COMMITTED

默认级别下，每条语句取得新的 snapshot。同一事务先后两次 SELECT 可以看到不同已提交结果。

典型错误：先 `SELECT balance`，在 JavaScript 判断，再 `UPDATE balance = newValue`。两个请求都读到 100，各减 80，最终可能只保留一次写入或产生不符合预期结果。

优先把检查和写入合成原子语句：

```sql
UPDATE inventory
SET remaining = remaining - 1
WHERE id = $1 AND remaining > 0
RETURNING remaining;
```

影响零行就是库存不足，不需要先查。

## 5. REPEATABLE READ

事务内使用固定 snapshot，避免不可重复读。PostgreSQL 的实现会对部分并发更新报 serialization failure，但它仍允许 write skew：两个事务读取同一组行，然后分别更新不同的行，使跨行不变量失效。

例如两名医生都看到“还有两人值班”，各自把自己设为 off-call。它们写不同记录，没有普通行写冲突，最终可能无人值班。

## 6. SERIALIZABLE

PostgreSQL Serializable Snapshot Isolation 检测可能无法等价为串行顺序的依赖结构，并中止其中一个事务，SQLSTATE `40001`。它不是把所有读都变成阻塞锁，应用必须准备重试完整事务。

Serializable 能保护正确写出的读-判断-写逻辑，但不是魔法：若代码根本没读取决定不变量的集合，数据库无从建立依赖；若事务外已发送邮件，重试会重复副作用。

## 7. 四种并发策略

1. 单条原子 SQL：最优先，往返少、锁时间短。
2. 悲观行锁 `SELECT ... FOR UPDATE`：先锁定即将修改的已知行。
3. 乐观 CAS：`UPDATE ... WHERE version = $expected`，影响零行表示冲突。
4. SERIALIZABLE + retry：适合跨行 predicate 不变量或复杂读写组合。

选择依据是冲突概率、涉及行数、用户体验和不变量形状。高冲突热点用不断失败的乐观重试可能更差；低冲突编辑用长时间行锁又浪费容量。

## 8. 行锁必须有顺序

事务 A 先锁钱包 1 再锁 2，事务 B 先锁 2 再锁 1，会形成 deadlock。PostgreSQL 会检测并中止一个事务，SQLSTATE `40P01`。

统一按稳定键排序加锁能显著减少死锁。仍要把 deadlock 当可观察、可有限重试的正常并发现象，而不是假设永不发生。

`NOWAIT` 适合不能等待的交互；`SKIP LOCKED` 适合多个 worker 竞争任务，但会跳过繁忙行，不适合普通财务或授权查询。

## 9. 锁住什么，没锁住什么

`FOR UPDATE` 只锁选中的现有行。对“目前没有满足条件的行”这类 predicate，它不能像范围锁一样保护不存在的事实。可锁稳定父行作为协调点，建立唯一/排除约束，或使用 SERIALIZABLE。

advisory lock 是应用定义的协作锁，不自动关联行，也不会阻止不遵守协议的代码。使用前必须定义 key、防碰撞、生命周期和监控。

## 10. 数据库约束仍是最后防线

即使用应用锁，也应保留 `CHECK balance >= 0`、UNIQUE 和外键。锁协议可能被新脚本绕过，约束仍能拒绝非法提交。

约束冲突不是都可重试：唯一冲突常是业务结果；外键失败可能是输入或竞态；`40001`/`40P01` 才通常适合完整事务重试。

## 11. 重试必须重跑整个事务

serialization failure 后当前事务已失败。ROLLBACK，开启新事务，重新读取、重新判断、重新写入。不能只重试最后一条 UPDATE，因为先前 snapshot 与决策已经过期。

有限次数、指数退避与 full jitter 能减少再次碰撞；还要服从总 deadline。超过预算返回明确暂时失败并记录 attempt 数。

## 12. 事务内禁止不可回滚外部副作用

事务持锁期间调用支付、邮件或模型，会延长冲突窗口；数据库回滚也不能撤回外部请求。正确结构通常是事务内写业务事实和 outbox，提交后由后台消费者执行外部动作，第 14 章详述。

同理，不要在事务内等待用户输入或 HITL 审批。先持久化状态，释放连接，再由新事务继续。

## 13. 结果未知

客户端发送 COMMIT 后连接断开，可能不知道事务是否提交。盲目重放非幂等操作会重复。业务需要稳定 operation ID 和查询确认路径；第 10 章实现 HTTP 幂等。

这也是为什么“catch 到网络错误就 rollback”不够：连接已断时，服务器端结果可能已完成，客户端的 rollback 根本没送达。

## 14. 时间与资源保护

每个事务应设置合理 `lock_timeout`、`statement_timeout` 和 `idle_in_transaction_session_timeout`。应用 deadline 要早于代理 deadline，并在取消时向驱动传播。

连接池大小不是越大越好。大量等待锁的连接会占满池，让无关请求饥饿。监控 transaction duration、lock wait、deadlock、serialization retry 和 pool wait。

## 15. 并发测试方法

顺序单元测试无法证明并发。使用两个真实连接、barrier 精确控制“都读完后再写”，重复运行并检查最终不变量。不要只断言某个请求报错；还要查数据库最终状态、总额和行数。

测试 READ COMMITTED/REPEATABLE READ 的失败示例，再证明修复。保留故意错误实现有助于验证测试真的能抓到竞态。

## 16. 本章不变量与自检

- 检查与写入尽量合成原子 SQL；多行锁按稳定顺序取得。
- 跨行 predicate 不变量使用约束、协调锁或 SERIALIZABLE。
- 只对明确瞬态 SQLSTATE 重试，而且重跑完整事务。
- 事务中不执行不可回滚网络副作用。
- 并发正确性由真实双连接测试和最终状态证明。

自检：为什么 RR 仍可能 write skew？`FOR UPDATE` 如何保护“不存在的行”？COMMIT 响应丢失后为何是结果未知？
