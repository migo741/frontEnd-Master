# 第 14 章：Outbox、Inbox、Saga 与跨系统一致性

## 本章目标

在 PostgreSQL、消息系统和第三方服务之间无法使用一个 ACID 事务时，仍避免“数据库成功但消息丢失”和“消息重复导致副作用重复”。你将用 Outbox/Inbox、版本化事件、Saga 与 reconciliation 管理事实，而不是承诺魔法般 exactly-once。

## 1. 双写为什么一定会出错

业务代码常做：更新订单 → publish 事件。无论顺序如何都有窗口：

- 先提交 DB，进程在 publish 前 crash：状态变了但无事件；
- 先 publish，DB 后续回滚：消费者看见不存在的事实；
- publish 成功但客户端超时，重试产生重复。

重试不能补上“到底成功没”的知识。必须把待发布意图与业务写放进同一个本地事务。

## 2. Transactional Outbox

业务事务同时写 aggregate 和 outbox row。独立 relay 扫描未发布 row，发送后标记。DB 保证“业务状态与发送意图同生共死”。

```text
BEGIN -> update order + insert outbox -> COMMIT
                            |
                       relay publish (至少一次)
```

relay 在 publish 后、mark 前 crash 会重复发送，所以消费者仍需 Inbox/业务幂等。Outbox 解决不丢，不解决不重。

## 3. 事件是已发生事实

命名 `OrderApproved`，不叫 `ApproveOrder`。包含 event id、aggregate id、aggregate version、tenant、occurred_at、schema version、最小业务数据。不要把完整数据库 row、secret、PII 快照塞进事件。

事件 id 全局稳定；重发不生成新 id。correlation/causation id 帮助追踪，但不能当幂等键替代 event id。

## 4. Relay 的 claim 与并发

多个 relay 使用 `FOR UPDATE SKIP LOCKED` claim 一批，写 lease/fencing 后提交，再发布。发送成功后条件 mark。也可使用 CDC，但仍需处理 schema、重放、顺序和消费者幂等。

Outbox 表会增长；按时间分区/归档，保留期覆盖最大重放和审计需求。不能未确认所有消费者就删除。

## 5. Inbox 去重

消费者在自己的数据库事务先 `INSERT inbox(consumer,event_id) ON CONFLICT DO NOTHING`，插入成功才执行业务写；业务写与 inbox 完成必须同一事务。

若先标 inbox done 再业务写，crash 会永久丢处理；若业务写后再标，crash 会重复。把二者放本地事务即可。

## 6. 幂等不等于忽略重复

重复 event payload 若与同 event id 的已存 fingerprint 不同，应报警并拒绝，这是生产者 bug 或攻击。消费者还需业务唯一约束，例如每个 `payment_operation_id` 只能入账一次。

Inbox retention 不能短于消息可能重放的窗口；长期财务事件用业务唯一键永久兜底。

## 7. 顺序只在明确范围内成立

全局顺序昂贵且通常无意义。对同一 aggregate 使用单调 version，消费者要求：

- version <= current：重复/旧事件，忽略但记录；
- version == current + 1：应用；
- version > current + 1：缺口，暂存并触发补取/reconciliation。

多分区队列只能在 partition key 内保持顺序，key 应是 tenant + aggregate id，同时评估热点。

## 8. Schema 演进

事件是长期公共契约。新增可选字段通常兼容；删除/改单位/改枚举可能破坏。消费者先支持新旧，生产者后切换，最后清理旧版。保留 upcaster 或双读窗口，不让消费者直接依赖生产者内部 ORM 类型。

事件重放时按事件发生时的 schema/业务语义处理，不能用今天的默认值悄悄重写历史。

## 9. Saga 是一组本地事务

跨库存、支付、工单无法用数据库事务。Saga 把流程拆成可持久化 step，每步有 command、成功事件和补偿。两种组织：

- orchestration：一个 durable coordinator 决定下一步，易观察；
- choreography：服务对事件反应，耦合隐蔽且难看全局。

复杂高风险流程优先显式 orchestration；简单独立反应可 choreography。

## 10. 补偿不是回滚

退款不是“撤销时间”，库存释放后可能已被别人购买，邮件无法收回。补偿是新的业务动作，有权限、失败、重试、审计和人工介入。

在设计正向 step 时同时定义：是否可重试、是否可补偿、补偿前置条件、无法补偿时谁处理。不可逆动作尽量最后执行，或先 proposal/approval。

## 11. Saga 状态与并发

coordinator 保存 saga id/version/current step/status；command 带 saga id + step operation id。迟到响应只在 expected state/version 匹配时推进，不能把 compensated 又改成 completed。

取消是另一事件：尚未开始的 step 停止；已完成 step 逆序补偿；正在执行的未知结果先 reconciliation。

## 12. 跨系统时间与真相

不同服务时钟不可用于全局 last-write-wins。使用本地 version、provider sequence 或状态机规则。received_at 用于观测，不作为业务因果的唯一依据。

查询展示可能最终一致；命令路径必须在权威服务判定。不要因为搜索索引显示“有库存”就直接扣款。

## 13. Reconciliation 修复未知状态

定期比较：本地 pending operation 与第三方查询、outbox 未发布年龄、inbox 缺口、Saga 卡步、业务表与投影。修复动作同样幂等、有并发 claim、限速和审计。

没有 reconciliation 的“最终一致”只是愿望。必须定义最大收敛时间和超时后的人工队列。

## 14. 观测

指标：outbox oldest age/publish attempts、inbox duplicate/conflict、version gaps、saga duration/step failures/compensation、unknown operation、reconciliation backlog。trace 传播 correlation id，但每个服务保留自己的 span 与业务 id。

## 15. 评审清单

- 业务写与 outbox 是否同一事务？
- relay publish 后 crash 是否只导致安全重复？
- inbox 与消费者业务写是否同一事务？
- event id 重发是否稳定，payload 冲突是否报警？
- aggregate version 缺口、乱序和 schema 演进是否处理？
- 每个 Saga step 是否可重试、补偿或人工处理？
- 未知外部结果是否先 reconciliation 而非盲重试？
- 是否有收敛 SLO、积压告警和受控重放工具？

## 本章速记

跨系统一致性不是把事务拉长，而是承认至少一次和局部失败，用本地原子写、稳定身份、幂等消费、显式状态机、补偿与 reconciliation 收敛。
