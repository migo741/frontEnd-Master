# 第 04 章：PostgreSQL 关系建模、约束与租户数据

> 数据库不是“存对象的地方”。它是并发请求共享的事实来源，也是最后一个能拒绝非法状态的边界。

## 学习目标

- 能从业务事实与不变量推导表、键、关系和约束。
- 能区分实体身份、业务键、外键和展示编号。
- 能用复合键阻止跨租户引用。
- 能正确选择 `NOT NULL`、`UNIQUE`、`CHECK` 与 `FOREIGN KEY`。
- 能把 RLS 作为纵深防御，并证明缺少租户上下文时默认拒绝。

## 1. 先写事实，不要先画 ORM 类

以多租户工单系统为例，先写可证伪陈述：

- 一个账户属于一个租户。
- 同一租户内规范化邮箱唯一，不同租户可以相同。
- 工单的请求人必须与工单属于同一租户。
- 状态只能处于有限集合。
- 创建时间不可为空，更新时间不能早于创建时间。

每条都应落在数据库约束、事务或明确的跨系统协议上。只写进 TypeScript interface，旧版本服务、迁移脚本和并发请求仍可破坏它。

## 2. 行代表事实，列保持原子含义

不要把频繁查询、约束和关联的数据塞进一个 JSONB 大对象。JSONB 适合变化快、结构稀疏、无需强关系约束的扩展字段；租户、owner、状态、金额等核心字段应有明确列和类型。

“原子”取决于业务。如果地址永远整体展示，一个复合值可能足够；如果要按城市过滤、做唯一性或统计，就需要可查询结构。规范化是减少事实重复，不是机械追求表数量。

## 3. 主键与业务键解决不同问题

代理主键如 UUID 便于引用和演进，但不能替代业务唯一性。账户有 UUID 主键，仍需 `UNIQUE (tenant_id, normalized_email)`。

展示编号可以改变格式，不应被所有外键依赖。外部可猜 ID 不是授权漏洞的根因；真正保护来自身份、租户与权限校验。但随机 ID 能降低枚举和跨系统冲突。

## 4. 多租户表为什么常带 tenant_id

共享 schema 模式下，把 `tenant_id` 放在每张租户数据表中，能让索引、查询、分区和审计都以租户开头。即使可从父表推导，冗余的 tenant_id 也能成为本地约束的一部分。

仅有 `ticket.requester_id REFERENCES account(id)` 不足以证明同租户。应让账户具备 `UNIQUE/PRIMARY KEY (tenant_id, id)`，再建立复合外键：

```sql
FOREIGN KEY (tenant_id, requester_id)
  REFERENCES account (tenant_id, id)
```

这样跨租户 requester 会被数据库拒绝，而不是依赖应用先查一次。

## 5. NULL 是未知或不适用，不是空字符串

`NULL` 参与三值逻辑；`NULL = NULL` 不是 true。若字段对每个有效事实都必需，使用 `NOT NULL`。不要为了省判断，把未知时间写成 epoch、把未知字符串写成 `''`。

PostgreSQL 的普通 `UNIQUE` 允许多个 NULL。需要“NULL 也只能一个”时可用 `NULLS NOT DISTINCT`；需要只约束有效记录时用 partial unique index。

## 6. CHECK 约束只判断当前行

`CHECK` 适合范围、格式和同一行列关系，例如优先级集合、`updated_at >= created_at`。它不适合查询另一张表或依赖会变化的函数；跨行不变量需要 UNIQUE、EXCLUDE、外键或事务锁。

状态集合用 `CHECK (status IN (...))` 比随意 text 强。PostgreSQL enum 更严格，但删除/重命名值的演进成本不同；第 07 章会比较迁移策略。

## 7. 外键不仅防止孤儿

外键还定义删除语义：

- `RESTRICT/NO ACTION`：仍被引用时拒绝删除。
- `CASCADE`：父事实消失时子事实一并消失。
- `SET NULL`：关系可选且需要保留子记录。

不要给所有关系默认 CASCADE。租户删除往往需要冻结、导出、异步清理和审计，而不是一次巨大事务级联删除。

被引用列必须唯一；引用列通常还需要单独索引，否则删除/更新父行时检查子表可能代价很高。PostgreSQL 不会自动为外键的 referencing side 建索引。

## 8. 数据类型表达语义

- 时间点用 `timestamptz`，以 UTC 语义存储；显示时再转时区。
- 金额用最小单位整数或明确精度 `numeric`，不用浮点。
- ID 用 UUID/text/bigint 依契约选择，前端不能安全承载的 bigint 应以字符串传输。
- 自然语言用 `text`，长度规则通常由 grapheme/业务定义，`varchar(255)` 不是性能优化。

数据库 collation 与大小写规范会影响唯一性。邮箱等字段应在边界规范化并存入独立列，约束规范形态；不要在每个查询临时 `lower()` 后假设没有竞态。

## 9. 租户隔离有多层

应用查询必须显式带 tenant 条件；复合外键防止错租户关联；Row-Level Security 可以在漏写条件时继续保护。三层解决不同故障，不互相替代。

RLS policy 使用数据库 session 中的可信 tenant context。应用在每个事务开始后用参数化 `set_config(..., true)` 设置事务局部值；连接归还池后自动清除。不能用普通 `SET` 留下 session 级租户，否则连接复用会串租户。

## 10. RLS 的危险细节

表 owner 和 superuser 默认可能绕过 RLS；运行时角色不应拥有表，也不应有 `BYPASSRLS`。高风险表可 `FORCE ROW LEVEL SECURITY`。迁移角色、运维角色与应用角色必须分离。

policy 要同时写 `USING` 与 `WITH CHECK`：前者控制可见/可修改的旧行，后者控制插入或更新后的新行。只写 USING 可能让写入路径不符合预期。

缺少 context 时函数应返回 NULL，使比较结果不为 true；不要 fallback 到“全部租户”。认证失败与后台任务也必须显式建立合法上下文。

## 11. 约束名是运维接口

给关键约束稳定命名，例如 `ticket_requester_same_tenant_fk`。日志可记录约束名，adapter 再把已知冲突映射为稳定业务错误。不要把完整 PostgreSQL message 暴露给客户端。

修改约束属于 Schema 演进。上线前统计现有脏数据，新增大表约束可考虑 `NOT VALID` 后再 `VALIDATE CONSTRAINT`，避免长时间阻塞，详见第 07 章。

## 12. 删除与审计

软删除不是给每张表加 `deleted_at` 就结束。它会影响唯一性、外键、默认查询、RLS 和索引。若邮箱在删除后可重用，应使用只覆盖 active 行的 partial unique index；若法律要求不可重用，则保留普通唯一约束。

审计事实应 append-only，记录 actor、tenant、动作、目标与 request/trace ID。不要只保存一份会被覆盖的 `updated_by`。

## 13. 验证模型的方法

为每个不变量写一条“故意违法”的 SQL 集成测试。约束只有在数据库真实拒绝时才算完成。检查 `SQLSTATE` 与稳定约束名，不依赖本地化 message。

同时生成最小种子数据和删除顺序，验证外键策略。画出哪张表是事实来源、哪些字段可重建、哪些删除需要审计。

## 14. 本章不变量与自检

- PostgreSQL 是事实来源；核心不变量尽量由数据库拒绝。
- 每个租户数据关系都能在键层证明“同租户”。
- `tenantId` 只来自可信上下文；RLS 缺 context 时默认不可见、不可写。
- 运行时角色不拥有表、不具备 `BYPASSRLS`。
- 约束测试检查 SQLSTATE/约束名，不检查易变 message。

自检：复合外键为何优于先查 requester 再 insert？普通 UNIQUE 如何处理 NULL？连接池下为什么必须使用事务局部 tenant context？
