# 第 17 章：Node 与 Python Agent 的信任边界

> 核心不变量：**Node 服务拥有身份、授权、业务事实和真实副作用；Python Agent worker 只接收最小能力，只能返回经过 Schema 验证的结果或工具意图。**

## 学完你要能做到什么

- 划分 Node 产品后端与 Python Agent worker 的职责。
- 设计可版本演进、可重放、可隔离的跨语言消息协议。
- 把模型输出当作不可信输入，而不是“内部服务结果”。
- 让工具审批绑定精确参数、租户、过期时间和执行次数。
- 解释为什么 Agent 不应直接持有主数据库写权限或用户令牌。
- 用契约测试证明 TypeScript 与 Pydantic 对同一 fixture 理解一致。

## 1. 为什么这里允许拆服务

课程其他业务模块默认留在 Node 模块化单体中。

Python worker 是合理边界，因为它往往有独立的：

- SDK 和模型生态；
- 依赖、运行时与资源规格；
- 扩缩容和失败率；
- 网络出口与安全策略；
- 发布频率和评测门禁。

拆分不是为了“看起来像大厂”，而是为了隔离不确定执行。

即使拆开，也不意味着 Python 可以成为第二个业务后端。

## 2. 职责矩阵

| 能力 | Node 产品服务 | Python Agent worker |
|---|---|---|
| 用户身份与 Session | 拥有 | 不接收原始凭证 |
| tenant 与授权策略 | 拥有并强制执行 | 只接收已裁剪 scope |
| PostgreSQL 业务写入 | 拥有 | 默认禁止直连 |
| Agent 规划与模型调用 | 发起、预算、取消 | 执行 |
| 工具真实副作用 | 校验、审批、幂等执行 | 只提出 intent |
| Agent checkpoint | 定义业务状态 | 返回可验证 checkpoint |
| Eval 与模型选择 | 保存质量门槛 | 运行并上报测量 |
| 审计 | 形成权威记录 | 提供结构化事件 |

一个简单判断：如果该动作会改变用户可观察的业务事实，它最终必须经过 Node 的策略与持久化边界。

## 3. 消息不是函数调用

跨进程消息会重复、延迟、乱序，生产者和消费者版本也会短暂不一致。

一个任务 envelope 至少包含：

```json
{
  "schemaVersion": 1,
  "messageId": "msg_...",
  "runId": "run_...",
  "tenantId": "tenant_...",
  "attempt": 1,
  "deadline": "2026-08-16T10:00:00Z",
  "inputRef": "object://...",
  "capabilities": ["kb.read", "ticket.suggest"],
  "traceparent": "00-..."
}
```

不要在消息里塞：

- 浏览器 Cookie 或用户 bearer token；
- 数据库 DSN；
- 全量用户档案；
- 永不过期的工具密钥；
- 无上限的历史对话；
- 未脱敏的 trace baggage。

大 payload 放对象存储，消息只放带租户校验的引用和哈希。

## 4. 版本演进

协议版本必须区分：

- 新增可选字段：通常向后兼容；
- 修改字段含义或必填性：破坏性变化；
- 新工具、新事件类型：旧消费者应进入隔离队列而非猜测；
- 主版本未知：拒绝并告警。

滚动发布顺序一般是：消费者先兼容新旧 → 生产者开始发送新格式 → 观察 → 删除旧格式。

把 JSON Schema 作为协议制品，并由 TypeScript 与 Pydantic 各自生成/验证容易漂移；更重要的是一组共享的正反 fixture。

## 5. 模型输出是不可信的

即使 Python 服务属于同一家公司，模型生成内容仍来自非确定系统，也可能被 Prompt Injection 操纵。

因此 worker 返回：

- `result`：可展示但需 Schema 和内容策略验证；
- `tool_intent`：想做什么，不代表获准；
- `checkpoint`：可恢复状态，不代表业务已完成；
- `usage`：计量候选，服务端还需与供应商记录对账；
- `error`：稳定错误码，原始异常留在受控日志。

禁止 worker 返回任意 SQL、shell 命令或 URL 后由 Node 无条件执行。

## 6. Capability 不是角色名

传给 worker 的 capability 应是当前任务的最小能力，例如：

```text
kb.read:project_123
ticket.propose:update:ticket_456
attachment.read:object_789
```

它应绑定：

- tenant；
- run；
- 具体资源；
- 动作；
- 有效期；
- 最大调用次数或预算。

“admin”不是适合跨边界传递的 capability。

worker 即使伪造更大 scope，Node 也必须依据当前用户、资源状态和策略重新判定。

## 7. Tool Intent 与 HITL

高风险动作流程：

1. 模型提出结构化 intent；
2. Node 验证 Schema、工具白名单和参数边界；
3. Node 以当前业务事实重新授权；
4. 计算规范化参数的 hash；
5. 持久化 intent 与审批状态；
6. 用户看到人类可理解的影响预览；
7. 审批绑定 intent ID、hash、tenant、审批人和过期时间；
8. 执行器再次验证所有条件；
9. 以 intent ID 作为幂等键执行；
10. 写审计与结果事件。

用户批准“给 Alice 发 10 元退款”，不能被复用于“给 Bob 发 1000 元退款”。

因此审批不能只绑定工具名。

## 8. 规范化与哈希

对象键顺序不应改变 hash，数字、Unicode、空值和数组顺序必须有统一语义。

可以采用经过验证的 canonical JSON 标准或协议层固定序列化方式。

不要直接对普通 `JSON.stringify` 的任意对象做安全签名，除非先递归排序并限制为 JSON 值。

hash 用来绑定内容，不替代授权，也不保密。

## 9. 执行时再次检查

审批到执行之间，业务事实可能变化：

- 用户已离开 tenant；
- 工单已经关闭；
- 额度已经被其他请求消耗；
- intent 已过期；
- 工具被紧急禁用。

执行必须在最新事实下重新授权。

需要强一致的不变量与执行记录应放入同一数据库事务；外部副作用使用第 10、14 章的幂等键、Outbox 与补偿。

## 10. 超时、取消和重试

Node 设置业务 deadline，worker 不能自行延长。

取消流程是持久状态，不只是发一个临时信号。

worker 需周期性观察取消，停止发起新工具 intent，并提交安全 checkpoint。

消息重复时，`messageId/runId/attempt` 帮助去重，但真正的副作用仍按 `intentId` 幂等。

worker 崩溃后可以重新计算建议；已经执行过的工具不能因为重新计算而重复执行。

## 11. 隔离和秘密

- Python worker 使用独立服务账户；
- 默认禁止访问主数据库和内部管理网；
- 模型 API key 从短期秘密挂载获得，不进入消息；
- 工具凭证由 Node 执行器持有，或换取任务级短期 token；
- 对象读取使用单资源、短时、只读 URL；
- 日志只记录引用、hash、大小和错误码，不记录敏感正文。

Agent 安全的纵深细节将在第 18 章完成。

## 12. 可观测和审计

跨边界至少传播 `traceparent`，但不要传播用户可控 baggage。

指标包括：

- 协议验证失败与版本不兼容；
- queue wait、模型 latency、工具审批等待；
- 每种 intent 的拒绝率；
- 重复消息与幂等命中；
- deadline 超时、取消生效延迟；
- 每成功 run 的 token 与成本。

审计记录“谁在何时批准了哪个精确 payload”，而不是只记“用户批准工具”。

## 13. 与 AI Agent Master 的关系

Prompt、Context、RAG、LangGraph、多 Agent 和 Eval 已在 [AI Agent Master](../../AI%20Agent%20Master/课程总索引.md) 系统讲解。

## 章末检查

- Python 是否能绕过 Node 直接修改业务数据库？
- 消息是否携带了不必要的用户令牌或秘密？
- 未知协议版本会不会被静默接受？
- tool intent 是否经过当前事实下的二次授权？
- 审批是否绑定精确参数 hash 与过期时间？
- 重复投递是否可能重复真实副作用？
- worker 崩溃后是否可以从持久 checkpoint 恢复？
- 两种语言是否共同运行同一组契约 fixture？
