# 第 16 章：SSE、实时事件、背压与断线恢复

> 核心不变量：**连接只是状态的投影，不是状态本身。每条业务事件必须有稳定序号、可重放、可取消；慢消费者不能无限占用服务端内存。**

## 学完你要能做到什么

- 区分“业务任务仍在运行”和“浏览器连接已经断开”。
- 解释 SSE、WebSocket 和轮询各自适合的方向与失败语义。
- 为事件设计单调序号、断点续传、心跳和终态。
- 在 Node.js 中正确处理 `write()` 返回 `false` 的背压信号。
- 让代理超时、客户端刷新、重复事件和短暂断网不破坏状态。
- 用指标回答连接数、重连率、积压量和端到端延迟。

## 1. 先把两个状态机分开

一个 Agent run 至少包含两个独立状态机：

1. 业务状态：`queued → running → waiting_approval → succeeded | failed | cancelled`；
2. 传输状态：`disconnected → connecting → streaming → reconnecting → closed`。

浏览器关闭标签页，只能证明传输断了。

它不能自动证明用户要求取消任务。

如果把二者绑定，移动网络抖动就会误杀昂贵任务；反过来，如果用户点击取消只关闭连接，后台仍可能继续扣费和执行工具。

因此取消必须是一个有鉴权、幂等、可审计的业务命令，例如 `POST /runs/:id/cancel`。

## 2. 为什么这里选择 SSE

SSE 是服务器到浏览器的单向 UTF-8 文本流，浏览器原生支持重连语义。

它适合：

- Agent token、步骤、审批提示和终态；
- 构建进度、导入进度、通知流；
- 客户端命令仍走普通 HTTP 的场景。

WebSocket 更适合真正高频的双向协作、游戏或自定义二进制协议。

轮询适合低频、容忍秒级延迟、希望基础设施最简单的场景。

不要因为“实时”两个字就默认 WebSocket；先问数据方向、重连、代理兼容和运维复杂度。

## 3. SSE 帧不是随便拼几行字符串

一个完整事件可以是：

```text
id: 42
event: run.step
data: {"runId":"run_1","step":"searching"}

```

空行结束一帧。

同一个事件的多行 `data:` 会由客户端以换行拼接。

推荐字段：

| 字段 | 作用 |
|---|---|
| `id` | 断点续传游标，必须来自持久化事件序号 |
| `event` | 稳定、版本化的事件类型 |
| `data` | JSON 数据，不把秘密或内部异常栈发送给客户端 |
| `retry` | 可选的客户端重连提示，不替代指数退避 |

心跳可用注释帧 `: heartbeat\n\n`，防止代理把空闲连接回收。

## 4. 事件日志是事实投影

最小事件表可以包含：

```sql
create table run_events (
  run_id uuid not null references agent_runs(id),
  seq bigint not null,
  tenant_id uuid not null,
  type text not null,
  payload jsonb not null,
  created_at timestamptz not null default now(),
  primary key (run_id, seq)
);
```

`seq` 对单个 run 单调递增即可，不需要全局序号。

事件与对应状态变化应在同一数据库事务中提交。

客户端收到事件不等于事件存在；只有数据库提交才代表事实成立。

短生命周期 token 可以选择批量持久化，关键步骤、工具意图、审批和终态必须持久化。

## 5. 重连协议

浏览器原生 `EventSource` 会把上一事件 ID 放入 `Last-Event-ID`。

自定义 `fetch` 流客户端也应显式保存最后连续序号。

服务端流程：

1. 鉴权并确认 run 属于当前 tenant；
2. 解析游标，拒绝负数、非整数和超大值；
3. 从数据库回放 `seq > cursor`；
4. 再订阅新事件；
5. 对交界处重复事件按 `seq` 去重；
6. 遇到序号缺口时停止增量应用，重新获取快照。

“先订阅再查历史”与“先查历史再订阅”都可能有竞态。

可靠实现需要订阅层提供游标，或允许重复并用持久序号去重，不能依赖恰好的时序。

## 6. 背压不是性能优化，而是正确性

Node `ServerResponse.write(chunk)` 返回 `false` 表示内部缓冲区已超过高水位。

此时继续写会把慢客户端的延迟转换成服务端内存增长。

正确做法是暂停生产或该订阅的读取，等待 `drain`，同时保留取消和超时路径。

还要设置：

- 每连接最大待发送字节数；
- 每租户最大并发连接数；
- 单连接最大持续时间或令牌预算；
- 慢消费者断开策略；
- 全局负载保护。

不要为每个 token 建立一个无界 Promise 队列。

可以在服务端合并非关键 token，但不能合并或跳过审批与终态事件。

## 7. 心跳、代理和缓冲

生产链路常经过 CDN、负载均衡、Nginx 或平台网关。

需要关注：

- `Content-Type: text/event-stream; charset=utf-8`；
- `Cache-Control: no-cache, no-transform`；
- 关闭代理响应缓冲，例如受控环境中的 `X-Accel-Buffering: no`；
- 网关 idle timeout 大于心跳间隔；
- 压缩可能增加缓冲延迟，SSE 通常不需要压缩；
- HTTP/1.1 每域连接上限与 HTTP/2 多路复用差异。

心跳只证明连接还可写，不证明业务健康。

readiness 也不能因为一个模型供应商失败就必然变红，否则滚动发布可能放大故障。

## 8. 错误和终态必须进入协议

连接异常与业务失败不同：

- 网络断开：客户端重连并回放；
- `run.failed`：业务进入终态，不应自动重启整个 run；
- 单个可重试步骤失败：由后台状态机决定重试，流只投影结果；
- 未知事件版本：客户端停止增量应用并刷新快照；
- 鉴权过期：连接以明确 HTTP 状态失败，客户端重新认证。

终态一旦写入，迟到的 token 或 step 事件不能把状态改回 running。

## 9. 安全边界

SSE 是 GET 请求，但响应中仍可能包含敏感数据。

- 查询必须同时限定 `tenant_id` 与 `run_id`；
- 不把访问令牌放进 URL，因为 URL 会进入历史、代理和日志；
- 使用 Cookie 时维持 SameSite/CSRF 整体策略；
- 禁止把模型原始内部提示、密钥或工具凭证推给浏览器；
- payload 输出前仍需 Schema 与字段投影。

授权发生在建立连接时，长连接还要考虑成员权限被撤销后的最大生效时间。

高风险系统可以定期重新验证 membership，或通过内部撤权事件主动断开连接。

## 10. 可观测性

至少记录：

- 当前连接数，按租户和结果分组但避免高基数用户标签；
- 连接建立失败率、重连率、平均持续时间；
- `write()` 背压次数与持续时间；
- 最新持久序号与已发送序号之差；
- 从业务事件提交到浏览器可见的延迟；
- 因超时、慢消费者、权限撤销而关闭的数量。

日志必须包含 `requestId`、`runId`、`tenantId` 和最后发送序号，不记录 token 正文。

## 章末检查

- 连接断开会不会误取消业务任务？
- 用户显式取消是否会真正停止后台工作？
- 每个关键事件是否持久化且有单调序号？
- 重放与实时订阅交界处是否允许重复并去重？
- `write()` 返回 `false` 后是否停止继续生产？
- 终态后能否拒绝迟到事件？
- 代理超时和响应缓冲是否经过真实环境验证？
- 是否能从 trace 定位“生成快还是传输慢”？
