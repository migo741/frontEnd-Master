# 第 01 章：Node 运行时、进程与资源生命周期

> 后端服务不是“永远运行的函数”。它是一个会启动、接流量、耗尽资源、收到终止信号并被替换的进程。

## 学习目标

- 能解释 Node 进程、事件循环、线程池与操作系统资源的边界。
- 能为请求、连接、定时器和后台任务指定 owner、deadline 与取消路径。
- 能实现 `starting → ready → draining → stopped` 生命周期。
- 能区分“停止接新请求”“等待在途请求”“强制退出”三个动作。
- 能用测试证明清理顺序、重复关闭与超时关闭都正确。

## 1. 从浏览器心智切换到常驻进程

浏览器页面出错，用户通常还能刷新；服务进程出错，可能同时影响成千上万个请求。前端组件卸载时忘记一个监听器会泄漏一小块内存，后端每个请求泄漏一个定时器会持续累积，最终让整个实例失效。

Node 默认只有一个执行 JavaScript 的主线程，但“单线程”不等于“一次只做一件事”。网络 I/O 由操作系统驱动，文件、DNS、加密等部分工作会进入 libuv 线程池。真正危险的是在主线程执行长时间 CPU 计算：它会阻塞所有连接的回调、健康检查和终止流程。

通用 Promise 与事件循环基础见 `《JavaScript 与浏览器高级学习问题》` 第 05 章；本章只讨论它们在服务生命周期中的后果。

## 2. 事件循环延迟也是资源指标

服务 CPU 没到 100%，仍可能因为同步 JSON 处理、正则灾难回溯或过多微任务而无法及时响应。应同时观察：

- 事件循环延迟与利用率；
- 堆、RSS、外部内存与文件描述符；
- 活跃请求、连接、队列长度和任务年龄；
- 每类下游调用的并发数。

“异步”只表示结果稍后到达，不代表无限并发安全。一次性 `Promise.all` 一万个数据库请求，会先把连接池和下游打满。

## 2.1 请求上下文与 AsyncLocalStorage

浏览器常把当前用户放进全局 store；后端不能用模块级变量保存“当前请求”，因为多个请求会交错执行。Node 的 `AsyncLocalStorage` 可以让 request ID、trace ID 等诊断上下文跨 `await` 传播：

```ts
import { AsyncLocalStorage } from "node:async_hooks";

type RequestContext = Readonly<{ requestId: string; tenantId: string }>;
const requestContext = new AsyncLocalStorage<RequestContext>();

requestContext.run({ requestId, tenantId }, () => routeHandler(request));
```

必须为每个请求使用 `run` 建立新作用域，不把可变对象复用给其他请求，也不要随意用 `enterWith` 污染仍在同一同步链上的处理器。数据库驱动、回调库或自建事件发射器若切断异步上下文，需要用并发测试验证，不能凭日志看起来正常就相信。

`tenantId` 仍必须来自已经验证的 Principal；AsyncLocalStorage 只传播可信结果，不负责认证，也不能成为绕过显式 repository 参数的隐式授权魔法。高风险数据访问继续显式传递 tenant，并由 PostgreSQL RLS 纵深保护。

## 3. 每项工作都要有 owner

请求创建的数据库查询、外部 HTTP 调用和临时文件，owner 通常是该请求。请求断开或 deadline 到期时，仍继续运行的工作是在浪费容量。

进程级消费者、刷新任务和连接池的 owner 是应用生命周期。它们应由 composition root 创建，由统一 shutdown coordinator 逆序释放。

一个资源至少要回答四个问题：

1. 谁创建它？
2. 正常结束时谁关闭它？
3. 超时或取消时怎样停止？
4. 关闭失败时系统怎样暴露失败？

## 4. deadline 与 timeout 不相同

`timeout = 2s` 是某一步最多执行多久；`deadline = 14:03:05` 是整条工作剩余到何时。跨多个下游时，应传递剩余 deadline，而不是每层重新获得完整两秒，否则总时长会层层膨胀。

在 Node 中用 `AbortSignal` 传播取消原因。取消是协作式协议：只有下游 API 接收 signal，工作才会真正停止。仅仅 `Promise.race` 一个计时器，会让调用方返回，但被“输掉”的 I/O 仍在后台占资源。

## 5. 资源上限必须显式

数据库连接池、HTTP agent、Worker、上传体积、并发任务和缓存条目都必须有上限。无上限队列不会消灭过载，只会把拒绝变成更晚、更昂贵的崩溃。

选择上限时记录等待时间和拒绝数。满载时应快速返回可识别的失败，例如 `503` 配合 `Retry-After`，而不是让所有请求一起超时。

## 6. 启动不等于就绪

`process` 已启动，只说明操作系统创建了进程。应用只有在配置校验、数据库连通和必要迁移检查完成后才 ready。

- liveness：进程是否仍能工作；失败会触发重启。
- readiness：当前是否应该接收新流量；失败只应摘流。
- startup：慢启动期间是否仍应等待。

不要让 readiness 依赖每个外部供应商，否则供应商抖动会把全部实例同时摘掉。只检查无法服务核心请求的本地依赖。

## 7. 优雅关闭是一段状态机

收到 `SIGTERM` 后的推荐顺序：

1. 原子地从 ready 切到 draining，拒绝重复启动关闭流程。
2. 给负载均衡器一点时间观察 readiness 变化。
3. 停止接受新连接和新队列任务。
4. 向在途工作广播取消或等待其在 deadline 内结束。
5. 逆序关闭消费者、HTTP server、数据库池和遥测 exporter。
6. deadline 到达后强制关闭剩余连接，并以失败状态退出。

关闭必须幂等。`SIGTERM`、管理接口和测试 teardown 可能同时触发；第二次调用应复用同一个 Promise，而不是再次释放资源。

## 8. 为什么要逆序释放

资源通常按依赖顺序创建：先数据库，再 repository，再消费者。关闭时必须反过来：先阻止消费者产生新查询，再关闭数据库。类似嵌套的 `try/finally`，LIFO 可以避免“上层还在用，下层已消失”。

即使一个 cleanup 失败，也要继续执行其余 cleanup，最后用 `AggregateError` 报告。吞掉关闭错误会制造看似成功、实际丢失遥测或任务的发布。

## 9. 致命错误的处理边界

`uncaughtException` 往往意味着进程状态未知。记录最小化诊断、触发有界关闭并让进程管理器替换实例，通常比继续接流量安全。不要在这里执行复杂业务或无限等待。

`unhandledRejection` 不应靠全局监听器“修好”；根因是 Promise 没有 owner。后台任务必须显式保存、观察并在关闭时等待。

业务失败、请求取消和进程缺陷要分开：业务失败映射为稳定响应；取消通常不记 error；进程缺陷触发告警与替换。

## 10. CPU 密集任务放在哪里

压缩大文件、解析巨型文档或执行模型前处理时，先测事件循环延迟。需要并行 CPU 时使用有界 Worker 池或独立服务；不要为每个请求创建新 Worker。Worker 也要有并发上限、任务 deadline、崩溃替换和关闭协议。

进程内 Worker 共享故障域。需要独立扩容、不同运行时或强资源隔离时，应交给后续队列与 Python worker，而不是继续堆在 HTTP 进程里。

## 11. 可观测关闭

至少记录一次结构化 shutdown 事件：触发原因、开始时间、在途数量、各清理步骤耗时、是否超期。指标应区分正常发布关闭和崩溃关闭。

日志 exporter 自身也是资源，通常最后关闭；否则最后几步的错误永远发不出去。退出码 `0` 表示完成预期关闭，非零表示 deadline 或 cleanup 失败。

## 12. 本章不变量

- 每个请求、任务和资源都有 owner、deadline、取消路径和上限。
- readiness 先变红，再停止接流量。
- shutdown 只运行一次，清理按依赖逆序，单项失败不阻断后续清理。
- CPU 工作不能让健康检查和终止信号失去响应。
- 强制退出是最后一道有界保险，不是日常控制流。

## 13. 常见错误

- 在模块顶层创建连接池，使测试无法替换或关闭。
- 用 `process.exit(0)` 代替关闭，截断响应和遥测。
- 只关闭监听 socket，不处理 keep-alive 与在途请求。
- `Promise.race` 超时后不取消真实操作。
- 捕获所有异常继续运行，让损坏状态长期存在。
