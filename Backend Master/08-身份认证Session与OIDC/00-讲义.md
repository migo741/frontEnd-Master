# 第 08 章：身份认证、Session 与 OIDC

## 本章目标

把“登录成功”理解成一条持续受攻击的身份生命周期，而不是一次密码比较。学完后你应能设计密码登录、服务端 Session、OIDC Authorization Code + PKCE，并能解释轮换、撤销、CSRF、重放和并发请求的边界。

## 1. 先分清四个概念

- 认证（authentication）：当前请求是谁发出的；
- 授权（authorization）：这个身份能否对这个资源执行动作；
- OAuth 2.x：委托访问协议，不等于登录协议；
- OIDC：在 OAuth 授权流程上增加可验证身份声明。

本章只解决认证。不要因为 ID Token 里有 `role` 就把授权永久写死在 token 中；角色和资源状态可能在 token 有效期内变化，第 09 章会处理授权。

## 2. 密码不是可逆秘密

服务端只保存带随机 salt 的慢哈希，优先使用经过审计的 Argon2id 实现。成本参数应由目标硬件基准决定，并允许登录成功后渐进升级。

登录接口必须统一“账号不存在”和“密码错误”的外部响应，限制每个账号、IP、设备的尝试速率，记录风险信号但不把密码、验证码、完整 token 写入日志。高价值操作还需要 MFA 或重新认证；登录成功不代表永久可信。

## 3. Session 的真正含义

浏览器只持有高熵、无业务含义的 session id；用户、租户、认证时间、过期时间和撤销状态保存在服务端。Cookie 建议：

```http
Set-Cookie: __Host-session=<opaque>; Path=/; HttpOnly; Secure; SameSite=Lax
```

`__Host-` 要求 Secure、Path=/ 且不能设置 Domain，可减少子域覆盖风险。`HttpOnly` 降低 XSS 直接读取凭证的机会，却不能阻止 XSS 以用户身份发请求；CSP、输出编码仍然必要。

## 4. Session id 也不应明文落库

数据库保存 `SHA-256(sessionId)`，请求到达后对 Cookie 做同样摘要再查库。数据库泄漏时，攻击者不能直接把摘要当 Cookie 使用。session id 至少 256 bit 随机，不使用用户 id、时间戳或可预测 UUID。

```text
浏览器 Cookie ──hash──> session_hash ──lookup──> user/tenant/auth_time
```

登录、权限提升、绑定 MFA 后轮换 session id，旧 id 原子撤销。否则攻击者可在用户登录前固定一个自己知道的 id，这就是 session fixation。

## 5. 空闲过期、绝对过期与撤销

- idle expiry：长期无活动后失效；
- absolute expiry：即使持续活动也必须重新认证；
- revoked_at：登出、改密、封禁、管理员踢出后立即失效；
- credential_version：用户全局撤销版本，避免逐条扫描全部 session。

不要在每次请求都无条件延长数据库过期时间，这会产生写放大。可按分钟粒度触碰，或把短期活跃信息放到缓存，但数据库仍是撤销事实源。

## 6. Cookie Session 与 CSRF

Cookie 会被浏览器自动附带，所以写操作仍需防 CSRF。SameSite 是一道防线，不是完整方案：

1. 限制可信 Origin/Referer；
2. 对写操作校验不可预测的 CSRF token；
3. GET/HEAD 不产生副作用；
4. 高风险操作重新认证或二次确认。

CORS 只控制脚本读取跨域响应，不会自动阻止浏览器发送表单请求。

## 7. OIDC Code + PKCE 因果链

推荐流程：生成 `state`、`nonce`、`code_verifier`；保存到一次性登录事务；用 `code_challenge` 跳转授权端；回调先验证 `state`，再以 code + verifier 换 token，最后验证 ID Token。

ID Token 至少验证：签名算法白名单、`iss`、`aud`、`exp/iat`、`nonce`；多 audience 时按提供方规则验证 `azp`。JWKS 轮换要按 `kid` 缓存和刷新，但未知 `kid` 不能触发无限请求风暴。

`state` 防止登录 CSRF；`nonce` 把 ID Token 绑定到本次事务；PKCE 降低授权码被截获后兑换的风险。三者不能互相替代。

## 8. 回调 URL 是安全边界

应用的 OIDC callback 使用注册时固定的 URL。登录完成后的站内跳转只能从服务端 allowlist 或受限相对路径恢复，禁止把任意 `returnTo=https://evil.example` 原样重定向。

登录事务必须一次消费。两个并发 callback 即使拿到相同 code，也只能一个创建 Session；另一个返回已处理或失败，不能产生两条长期会话。

## 9. 为什么不把长期 JWT 放 localStorage

localStorage 中的 bearer token 可被同源 XSS 读取并带离设备，撤销也困难。企业 Web 应用通常优先服务端 Session；需要 API access token 时令其短寿命、最小 audience/scope，并在可信 BFF 中保管 refresh token。

JWT 的签名只证明签发者和完整性，不证明请求者仍有权限，也不自动加密载荷。任何 token 都要检查 issuer、audience、时效和用途。

## 10. 框架只是适配层

核心接口应与 Fastify/Nest 解耦：

```ts
type Principal = Readonly<{
  userId: string
  sessionId: string
  tenantId: string
  authTime: Date
}>

interface Authenticator {
  authenticate(cookie: string | undefined, now: Date): Promise<Principal | null>
}
```

HTTP adapter 负责取 Cookie、设置响应和映射错误；认证服务负责哈希、事务、过期和审计。这样同一规则可用于 HTTP、后台任务和测试。

## 11. 观测与隐私

建议指标：登录成功率、按原因聚合的失败率、OIDC callback 延迟、未知 `kid`、session 轮换/撤销、可疑重放。日志只保留 session 的短摘要或内部 row id，不记录 Cookie、code、verifier、ID Token 和密码。

异常峰值要按账号与网络维度分析，同时防止高基数标签拖垮指标系统。

## 12. 评审清单

- session id 是否随机、摘要落库并在权限提升后轮换？
- Cookie 属性、CSRF、Origin 检查是否形成完整链？
- 登出、改密、封禁能否立即撤销？
- OIDC 是否验证 state、nonce、PKCE、issuer、audience、时间和算法？
- callback、returnTo 和 JWKS 刷新是否有限制？
- 并发 callback、重复登出和旧 Cookie 是否有确定语义？
- 日志和 trace 是否绝不包含凭证？

## 本章速记

认证不是“发一个 JWT”。可靠身份系统由一次性登录事务、可撤销 Session、Cookie/CSRF 边界、严格 OIDC 验证和审计共同组成。
