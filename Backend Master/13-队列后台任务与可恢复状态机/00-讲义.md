# 第 13 章：队列、后台任务与可恢复状态机

## 本章目标

把超过一次 HTTP 请求寿命的工作建模成可恢复状态机。你应能面对重复投递、worker crash、lease 过期、取消、毒消息、部署升级和租户争抢，而不重复副作用或永久卡住。

## 1. 为什么不能 `void doWork()`

请求返回后，进程可能退出、容器可能滚动、未处理 rejection 无人观察。没有持久状态，用户无法查询、取消或重试，也无法回答工作到底执行到哪里。

后台任务至少有稳定 job id、权威状态、输入引用、尝试记录和可观测结果。HTTP 提交返回 `202 Accepted` 与 status URL。

## 2. 队列不等于状态库

消息队列负责交付信号；PostgreSQL 负责业务状态。消息只放稳定 id 与路由元数据，不塞大正文、secret、用户角色或整个对象快照。

```text
API -> job row/outbox -> queue -> worker -> job step/result
          ^                         |
          +------ status API -------+
```

队列消息丢失可由 dispatcher/reconciler 补发；队列重复不会重复业务结果。

## 3. 默认接受 at-least-once

worker 处理完成但 ack 丢失，消息必然重投。所谓 exactly-once 常把重复隐藏在某一层，外部副作用仍需 idempotency key/inbox/业务唯一约束。

handler 先问：同一 job/step 执行两次会怎样？若答案是重复扣款或重复邮件，就还没有完成设计。

## 4. 明确状态机

通用状态：`queued -> running -> succeeded|failed|cancelled`，另有 `retry_wait`。每次转移带 expected state/version；非法转移被拒绝。

不要用多个互相矛盾布尔值 `isRunning/isDone/hasError`。失败记录 error code、retryable、attempt 与 next_run_at；用户可理解的结果与内部 stack 分离。

## 5. Claim、lease 与 fencing

worker 原子 claim 到期任务，写 `lease_owner/lease_until/fencing_token`。长任务定期 heartbeat；lease 过期后其他 worker 可接管。

旧 worker 暂停后恢复仍可能写，所以 finish/update 必须携带 fencing token，并要求仍是 owner 且 lease 有效。仅检查 owner 字符串不够，同一个 worker id 也可能重启。

## 6. PostgreSQL `SKIP LOCKED`

中等规模可以用 PostgreSQL job table：事务内 `SELECT ... FOR UPDATE SKIP LOCKED LIMIT n`，立即更新 claim 后提交，再在事务外执行慢工作。

不能持数据库锁调用第三方 API。`SKIP LOCKED` 提高吞吐，却不保证严格公平；需要按 tenant/priority/created_at 调度并防饿死。

## 7. Retry 分类

可重试：明确的临时网络错误、429/503、lease 冲突。不可重试：Schema 错、权限拒绝、业务规则失败。未知副作用状态先 reconciliation，不直接重做。

指数退避 + jitter、最大尝试、总 deadline 和 retry budget 缺一不可。attempt 次数不是唯一预算，跨天任务还看总年龄与成本。

## 8. 毒消息与 DLQ

同一输入稳定失败会消耗 worker。达到阈值进入 dead-letter/failed，保留安全摘要、错误类别、代码版本和重放工具。修复后重放必须创建审计记录，并沿用原业务 operation id。

不要自动无限重放 DLQ，也不要把含 PII 的完整 payload 复制到多个系统。

## 9. 取消是意图

queued 可直接条件转 cancelled；running 时写 `cancel_requested_at`，worker 在安全点检查并停止。已经提交的外部副作用不能“取消回来”，可能需要补偿。

取消与成功并发时要定义赢家：通常权威副作用已确认则 succeeded，否则在安全点取消。不能让迟到 worker 把 cancelled 覆盖为 running。

## 10. 进度不是事实承诺

可记录 step、processed/total 和最后 heartbeat，但总量会变化时不要伪造精确百分比。进度事件可重复，前端按 job version/sequence 合并。

大结果放对象存储，job row 只存 artifact id/checksum。用户日志与内部 trace 分开。

## 11. 调度、公平与背压

设置全局、每 tenant、每 job type 并发上限；高优先级不能永久饿死普通任务。队列深度、最老等待时间和 tenant lag 比单纯消息数更有意义。

下游变慢时停止 claim 或降低 concurrency，不把所有消息拉入内存等待。生产者也要 admission control，队列不是无限缓冲。

## 12. 部署与版本演进

job 保存 workflow/schema version。滚动升级期间旧、新 worker 必须都能处理已有 job，或按版本路由；状态迁移要向前兼容。删除 handler 前确认旧队列和 retry_wait 已清空。

graceful shutdown：停止 claim，新任务拒绝；等待有限时间；延长或释放 lease；未完成任务让其安全重投。不要收到 SIGTERM 后立即 `process.exit()`。

## 13. Reconciler 是必需组件

周期扫描：queued 太久未投递、running lease 过期、retry_wait 到期、外部 operation 未知、artifact 缺失。修复动作使用 compare-and-set 并有速率限制，避免事故时全表扫描和重发风暴。

Reconciler 与 worker 同样需要 tenant、公平、审计和指标。

## 14. 观测

指标：enqueue rate、queue age、claim/finish、attempt、retry reason、lease expiry、zombie write rejection、DLQ、cancel latency、tenant fairness、downstream latency。trace 用 job id/attempt/step 关联，不把正文放 attribute。

## 15. 评审清单

- 业务状态是否持久化，队列是否只做交付？
- handler 重复执行是否安全，外部 operation id 是否稳定？
- claim/heartbeat/finish 是否带 lease 与 fencing？
- retry 是否按错误分类、有总预算和 jitter？
- cancel/success、lease 接管与迟到 worker 是否有确定语义？
- tenant 公平、队列上限、部署版本和 reconciler 是否设计？
- DLQ 重放是否安全、可审计且不泄漏数据？

## 本章速记

可靠后台任务不是“加一个队列”。它是持久状态机、至少一次处理、幂等副作用、lease/fencing、有限重试、公平背压与 reconciliation 的组合。
