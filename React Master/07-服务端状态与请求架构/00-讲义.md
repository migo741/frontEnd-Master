# 第 07 章：服务端状态与请求架构

## 本章目标

区分客户端状态与服务端状态；用缓存的“新鲜度、身份、所有权、失效”思维设计请求，而不是在每个组件复制 loading/data/error 三件套。本章以 TanStack Query 思维和 API 为主要案例，原则同样适用于路由 loader、SWR、RTK Query。

## 1. 服务端状态的特殊性

它不是客户端独占：

- 远端才是权威，客户端只是某时刻的缓存快照；
- 可能过期、被其他用户修改；
- 有延迟、失败、重试、取消和权限；
- 多个组件需要去重与共享；
- mutation 后要协调失效、更新或乐观回滚。

把服务器响应复制进 Redux/local state，随后手写同步，通常是在重造缓存。

## 2. Query Key 是缓存身份

key 必须包含影响结果的全部输入，并可稳定序列化：

```ts
const userKeys = {
  all: ['users'] as const,
  lists: () => [...userKeys.all, 'list'] as const,
  list: (filters: UserFilters) => [...userKeys.lists(), filters] as const,
  detail: (id: string) => [...userKeys.all, 'detail', id] as const,
}
```

不包含 filter 会把不同结果当同一缓存；包含临时函数/不稳定对象则难以命中和失效。key 工厂也让失效范围更清晰。

## 3. 新鲜度与驻留时间

两个概念不要混：

- `staleTime`：多久内视为新鲜，新订阅者通常无需重取。
- `gcTime`：没有订阅者后，缓存多久再回收。

它们必须来自业务：国家列表可以很久；交易报价可能数秒；用户资料更新后按事件精确失效。`staleTime: Infinity` 不是性能开关，需要明确刷新机制。

默认重试也应分类：网络抖动/5xx 可指数退避；400 校验、401/403、404 通常不盲重试；mutation 默认更谨慎，避免重复副作用。

## 4. 请求函数契约

```ts
async function getUser(id: string, signal?: AbortSignal): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`, {signal})
  if (!response.ok) throw await toDomainError(response)
  return userSchema.parse(await response.json())
}
```

- `fetch` 对 4xx/5xx 不自动 reject，必须检查 `ok`。
- TypeScript 类型不验证网络 JSON，关键边界用 schema 运行时校验。
- 接收 query 提供的 AbortSignal。
- 错误转换为领域错误，保留 status/cause/requestId，去除敏感信息。
- queryFn 纯粹返回数据，不在里面 toast/导航；这些是上层策略。

## 5. 缓存不是业务数据库

Query cache 可做展示所需轻量变换，但不应成为复杂客户端事务系统。避免把同一远端数据又复制到局部 state；若用户要编辑，建立明确 draft，并处理基准版本变化/冲突。

`select` 只改变订阅者看到的结果，不应偷偷改缓存；保持纯并注意引用稳定性。TanStack Query 会做结构共享，但顶层 result 对象不保证稳定，不要把整个 result 放 Effect 依赖。

## 6. Mutation 的三种同步策略

1. **失效重取**：简单可靠，额外网络成本；适合服务端会计算复杂结果。
2. **用响应精确更新缓存**：低延迟，要求响应包含权威实体，并更新所有相关缓存。
3. **乐观更新**：最快，但要处理取消进行中的 query、快照/补丁、回滚、并发 mutation、服务端归并。

经典乐观流程：

```ts
onMutate: async next => {
  await client.cancelQueries({queryKey: key})
  const previous = client.getQueryData(key)
  client.setQueryData(key, optimistic(previous, next))
  return {previous}
},
onError: (_error, _next, context) => {
  client.setQueryData(key, context?.previous)
},
onSettled: () => client.invalidateQueries({queryKey: key})
```

单一 `previous` 回滚在并发 mutation 时可能抹掉后一个成功更新。高级方案使用 mutation id/补丁队列、服务端版本、只回滚自己的 patch，最终重取权威状态。

## 7. 分页、无限列表与 placeholder

分页 key 包含 page/filter。切页时可保留上一页 placeholder，避免闪烁，但 UI 必须表达“正在更新”，不能让旧内容看似属于新页。

无限列表要定义：`initialPageParam`、`getNextPageParam`、最大页数/内存、重复 item 去重、过滤变化重置、快速连续 fetch 的串行/并行语义。cursor 通常比 offset 更能应对数据插入，但服务端必须支持。

## 8. Router + Query 协作

路由知道“即将进入哪里”，Query 知道“缓存是否新鲜”。loader 中 `ensureQueryData` 可在导航时预取/复用，组件 `useQuery` 订阅同一 key。这样代码、数据并行，仍享有缓存与后台刷新。

不要让 loader 和组件用不同 key/不同 fetcher 各请求一次。SSR 时还需 dehydrate/hydrate 与 per-request QueryClient，避免用户间缓存泄漏。

## 9. 请求瀑布与预取

开发者工具中画出：HTML → JS → route chunk → parent data → child data。能并行的请求应提前声明/批量/服务端聚合。prefetch 不是越多越好，要受用户意图、网络、权限、缓存和服务端容量约束。

## 10. 评审清单

- 这是服务端状态还是客户端状态？
- key 是否完整稳定？
- freshness/gc/retry 来自什么业务 SLA？
- 请求能否取消，JSON 是否验证，错误是否分类？
- mutation 选择失效、响应更新还是乐观，为什么？
- 并发 mutation 和旧响应如何处理？
- router/SSR 是否复用同一缓存身份？
- 是否有瀑布、过度预取、无限内存、敏感数据缓存风险？

## 本章速记

高级请求层不是“封装 axios”。它为远端快照定义身份、时效、失败、并发、失效和所有权。先写缓存不变量，再调库 API。
