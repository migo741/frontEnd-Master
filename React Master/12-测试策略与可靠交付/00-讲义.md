# 第 12 章：测试策略与可靠交付

## 本章目标

按风险选择测试层，不把实现细节测试成重构枷锁；能用 Vitest、React Testing Library、MSW、Playwright 覆盖并发、网络和关键路径。

## 1. 测试的是契约与风险

高价值测试回答：用户能否完成任务？错误/竞态/权限下是否安全？重构后公共行为是否保持？低价值测试只证明内部 `setState` 被调用、某个 Hook 次数或私有类名。

Testing Library 的核心原则是像用户一样通过角色、名称和可见行为查询。优先：

1. `getByRole` + accessible name；
2. label/text（按语义）；
3. test id 作为没有合适语义时的逃生舱。

这同时推动可访问性。

## 2. 测试层

- 纯单元：reducer、codec、selector、领域规则，快且精确。
- 组件/集成：真实组件 + Router/Query Provider + MSW，覆盖用户流程和网络状态。
- E2E：真实浏览器/后端测试环境，覆盖少量高价值关键路径、浏览器行为、部署集成。
- 静态：TypeScript、ESLint、schema/type tests，是最便宜的第一道门。

“测试金字塔”不是固定比例。React 页面的大多数信心来自适量集成测试，E2E 少而关键。

## 3. Vitest + RTL

每个测试独立 arrange/act/assert。用 `userEvent.setup()` 模拟完整交互；异步用户动作 `await`。不要滥用 `act` 包裹一切来掩盖未等待更新。

```tsx
it('submits a valid form', async () => {
  const user = userEvent.setup()
  render(<RegisterPage />)
  await user.type(screen.getByLabelText('邮箱'), 'a@example.com')
  await user.click(screen.getByRole('button', {name: '注册'}))
  expect(await screen.findByRole('heading', {name: '欢迎'})).toBeVisible()
})
```

## 4. MSW 在网络边界拦截

不要 mock 自己的 `useUsers()` 返回对象，那绕过请求、schema、缓存、错误处理。MSW 拦截 HTTP，让真实数据层运行。每个测试显式覆盖 handler，未处理请求应报错；测试后 reset handlers。

用可控 deferred Promise 模拟乱序，不靠随机延迟。验证 abort 时可检查 signal/请求取消或最终可见行为。

## 5. 假定时器的边界

debounce/retry 可用 fake timers，但 userEvent 需配置 timer advance。Promise microtask、React 调度和 timer 混用容易产生假绿。尽量把 scheduler/clock 注入纯逻辑；集成测试保留少量真实时序。不要用任意 `waitFor(() => true)`。

`waitFor` 回调内只做可能成功的断言；它会重试，所以不要在里面执行点击等副作用。

## 6. StrictMode 与并发回归

关键 Hook/订阅组件可在 StrictMode 渲染，验证 setup/cleanup 对称。测试不要断言开发模式精确 render 次数；断言活动连接数、最终 UI、事件只造成一次业务副作用（服务端幂等也要保证）。

竞态测试要控制顺序：A 请求开始 → B 开始 → B 成功 → A 成功/失败；最终 UI 必须属于 B。

## 7. Playwright E2E

只覆盖高价值旅程：登录、核心创建/付款/权限、发布路由、文件上传、跨浏览器关键交互。使用角色定位，等待可观察状态，不 `waitForTimeout(3000)`。

测试隔离：每用例独立账号/数据或 API fixture；并行运行不能互相污染。失败保留 trace、video/screenshot、console/network；重试只辅助定位 flaky，不能把不稳定藏起来。

## 8. Contract 与视觉/可访问性

- API schema/consumer contract 防后端形状漂移；
- 类型测试防组件公共 API 退化；
- Story/视觉回归覆盖组件状态与布局，但需控制字体/动画/时间；
- axe 自动检查能发现部分 a11y 问题，键盘/屏幕阅读器仍需人工验收。

## 9. 覆盖率不是目标函数

行覆盖 100% 也可能没有断言正确行为。用风险矩阵：影响 × 发生概率 × 可探测性。优先支付、权限、数据丢失、竞态、迁移、离线等。变更 PR 要有“为何此测试层最合适”。

## 10. CI 门禁

快速反馈顺序：format/lint/type/unit → integration → build → E2E/性能/视觉。缓存依赖但 lockfile 为 key；测试分片、失败重跑要收集原始失败；合并必须基于确定性信号。

## 本章速记

可靠测试逼近真实行为，但把不确定性放在可控边界。Mock HTTP，不 mock 业务世界；控制并发顺序；E2E 少而关键；覆盖率服务于风险，而不是相反。
