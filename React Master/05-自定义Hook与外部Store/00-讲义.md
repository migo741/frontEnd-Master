# 第 05 章：自定义 Hook 与外部 Store

## 本章目标

写出有稳定契约、可组合、可测试的 Hook；理解 Hook 共享的是**有状态逻辑**而不是 state 实例；能用 `useSyncExternalStore` 正确接入 React 外部数据源。

## 1. 自定义 Hook 的价值

好的 Hook 把“如何与某系统同步”封装成调用者能理解的领域接口：

```tsx
const status = useOnlineStatus()
const user = useCurrentUser()
const {data, retry} = useReport(reportId)
```

坏 Hook 只是把几行代码藏起来，返回十几个底层 setter/ref，调用者仍需理解内部时序。

判断是否抽 Hook：

- 同一同步协议在多个组件重复；
- 逻辑可用领域输入/输出描述；
- 组件因此更接近“声明 UI”；
- 封装能建立不变量或统一取消/错误策略。

不要因为 Effect 长就抽；先判断 Effect 是否该存在。

## 2. Hook 共享逻辑，不共享状态

两个组件调用 `useCounter()` 会获得两个独立 state。共享 state 需要提升、Context 或外部 store。Hook 可以在内部连接同一个外部单例，但那是外部资源提供共享，不是 Hook 魔法。

Hook 名以 `use` 开头，让 lint 能执行调用规则：只在组件/自定义 Hook 顶层调用，不在条件、循环、普通回调中调用。React 依靠调用顺序把 Hook 槽位与状态对应。

## 3. 设计返回值

返回值是公共 API：

- 单一值就直接返回值；
- 多值对象比位置敏感的长 tuple 更易演进；
- 命令用领域名称，如 `retry()`，不要暴露 `setState`；
- 状态用判别联合，避免 `data/error/isLoading` 产生非法组合；
- 不承诺无意义的引用稳定性；若稳定性是契约，文档和测试都要明确。

```ts
type Resource<T> =
  | {status: 'loading'}
  | {status: 'success'; data: T; refresh(): void}
  | {status: 'error'; message: string; retry(): void}
```

## 4. 参数中的回调

调用者传 inline callback 时，每次 render 引用不同。Hook 若把它放入订阅 Effect 依赖，会反复订阅；若删依赖又可能 stale。

选择取决于语义：

- callback 的变化应重建资源：诚实依赖，并要求调用者/Hook 适当稳定。
- callback 只是外部事件发生时读取最新逻辑：React 19.2 可用 Effect Event，React 18 可封装 latest ref。
- 更好的 API 可能是不接 callback，而返回状态让组件渲染。

不要在 Hook 内无条件 `useCallback(callback, [])`，那只是冻结旧闭包。

## 5. 外部 Store 的三件套

React 外部 store 必须提供：

```ts
type Store<T> = {
  getSnapshot(): T
  subscribe(listener: () => void): () => void
}
```

组件通过：

```tsx
const snapshot = useSyncExternalStore(
  store.subscribe,
  store.getSnapshot,
  store.getServerSnapshot,
)
```

约束：

- store 未变化时，`getSnapshot()` 必须返回 `Object.is` 相同的缓存快照；不能每次 `{...state}`。
- store 变化后，先更新快照，再同步通知订阅者。
- `subscribe` 引用最好稳定，否则 React 会重新订阅。
- SSR 的 `getServerSnapshot` 必须与水合时初始客户端快照一致，否则 hydration 不匹配。

## 6. 为什么不用 `useEffect + setState`

手写：

```tsx
useEffect(() => store.subscribe(() => setState(store.getState())), [])
```

在 render 与 Effect 订阅之间可能错过更新；并发渲染时不同组件可能读到不同版本（tearing）；SSR 初始值也难协调。`useSyncExternalStore` 让 React 能在提交前再次验证快照。

## 7. Selector 与细粒度订阅

大型快照每次变化都会让所有消费者检查更新。状态库通常提供 selector 与 equality。原则：

- selector 必须纯；
- 不要每次返回新对象，除非 equality 能正确处理；
- 只选择渲染所需最小切片；
- 规范化实体，避免深层对象复制扩散更新；
- 测量后再优化。

`useSyncExternalStore` 是协议，不是完整状态库。不要无必要手写 Redux/Zustand 替代品。

## 8. Hook 测试策略

优先通过使用该 Hook 的小组件测试可观察行为；纯 reducer/转换函数单测。避免把实现细节如内部 Effect 次数当核心断言。需要验证订阅协议时，测试：

- 首次快照；
- 更新通知；
- 卸载取消；
- 同值不触发无意义更新；
- StrictMode 重订阅无泄漏；
- SSR 快照一致。

## 9. API 评审清单

- 名称是否描述领域能力？
- 输入/输出是否最小且类型排除非法状态？
- cleanup/取消/竞态是否封装？
- 引用稳定性有哪些承诺？
- 多实例是共享还是独立，文档是否明确？
- 能否改用已有成熟库/浏览器 API？
- SSR 与并发渲染是否正确？

## 本章速记

自定义 Hook 是同步协议和状态逻辑的模块边界；`useSyncExternalStore` 是 React 与外部可变数据源的正式桥梁。高级不是抽得多，而是契约窄、语义稳、失败可控。
