# 第 01 章：现代 React 心智模型与协调

## 本章目标

学完后你应能仅凭代码预测一次更新会渲染什么、Effect 看见什么、局部 state 是否保留；遇到“数据显示旧值”“输入框串行”“为什么渲染两次”时，不靠试错改依赖数组。

## 1. 组件不是长期运行的对象，而是一次计算

函数组件每次渲染都会重新执行。该次调用读到的 props、state、事件处理器和局部变量组成一个**快照**。旧渲染创建的闭包继续引用旧快照：

```tsx
function Counter() {
  const [count, setCount] = useState(0)

  function handleClick() {
    setCount(count + 1)
    setTimeout(() => console.log(count), 1000)
  }

  return <button onClick={handleClick}>{count}</button>
}
```

点击时安排了下一次渲染，但当前处理器中的 `count` 不会原地变成新值。定时器打印的是创建该闭包的渲染快照。这不是“setState 异步”一句话能完整解释的；关键是**快照不可变**。

更新依赖前值时使用函数式更新：

```tsx
setCount(c => c + 1)
setCount(c => c + 1) // 同一事件内最终 +2
```

函数式 updater 不是“拿到实时全局变量”，而是进入该 state 的更新队列，React 按顺序折叠。

## 2. render 与 commit

一次更新至少要区分：

1. **触发**：初次挂载或 state/父级/context/外部 store 更新。
2. **render**：React 调用组件，计算下一棵 UI 描述；这一步必须纯，可以暂停、重试或放弃。
3. **commit**：把差异应用到宿主环境（DOM），更新 ref，并运行相关 Effect。
4. **浏览器绘制**：通常在普通 `useEffect` 前后由浏览器调度；`useLayoutEffect` 会在绘制前同步执行，滥用会阻塞画面。

“组件 render 了”不等于 DOM 一定改了；“render 被启动”也不等于一定 commit。并发渲染下，纯渲染不是风格偏好，而是正确性约束。

render 阶段禁止：发请求、写 localStorage、改外部变量、订阅、操作 DOM、调用不幂等接口。事件处理器和 Effect 才是执行副作用的位置。

## 3. 批处理与更新优先级

React 18 的 `createRoot` 会对更多来源的更新自动批处理。批处理减少不必要的中间渲染，但不要依赖“每次 setter 后立刻读新 DOM”。

高优先级输入和可中断的非紧急更新可以分开：输入框值应立即更新，大列表过滤可放进 Transition。Transition 不是延时器，也不会让昂贵代码本身变快；它让 React 能优先响应更紧急工作。

只有和必须立刻读取更新后 DOM 的第三方 API 对接时才考虑 `flushSync`，它是逃生舱，不是常规方案。

## 4. 协调：类型、位置、key 决定身份

React 用上一棵树与下一棵树协调。粗略理解：

- 同一位置、同一组件类型：默认保留 state，更新 props。
- 类型改变：旧子树卸载，新子树挂载，state 重置。
- 列表中 `key` 告诉 React 哪个逻辑实体跨渲染仍是同一个。
- `key` 只需在兄弟中唯一且稳定，不会作为普通 prop 传给组件。

典型错误：

```tsx
items.map((item, index) => (
  <Row key={index} item={item} />
))
```

若列表会插入、删除、排序，索引代表“位置”而不是“实体”。`Row` 内的输入值、展开状态或请求结果可能被错误地复用给另一个 item。正确 key 应来自数据身份，例如数据库 id。

不要使用 `Math.random()`：每次 render 都变，导致所有节点重挂载、丢 state、反复执行 Effect。需要重置一个子树时，**有意改变稳定 key**反而是清晰方案：

```tsx
<Editor key={documentId} documentId={documentId} />
```

## 5. 不可变更新不是仪式

React 依赖值/引用变化表达“下一快照”。直接修改旧对象同时破坏：

- 前后快照的可比较性；
- memo/selectors/外部 store 的引用判断；
- 撤销、日志、并发安全和调试。

```tsx
// 错：修改当前快照
user.profile.name = name
setUser(user)

// 对：构造下一快照
setUser(prev => ({
  ...prev,
  profile: {...prev.profile, name},
}))
```

“不可变”指不修改已存在快照；新对象在发布前可以在纯函数内部组装。Immer 通过 draft 提供便利，但输出仍是结构共享的新快照，不能把任意对象突变合理化。

## 6. StrictMode 的“双调用”在帮你

开发环境 Strict Mode 会额外调用部分逻辑、重新执行 Effect 的 setup/cleanup，用来暴露不纯渲染和不完整清理。生产不是简单地“所有东西跑两遍”。看到重复请求时，先问：

- 请求是否应该移到框架 loader 或 query cache？
- Effect 是否能正确取消/忽略过期结果？
- cleanup 是否与 setup 对称？

删除 StrictMode 只是隐藏脆弱性。

## 7. 与 Vue 3 的关键差异

Vue 的响应式依赖让你容易形成“变量原地改变”的直觉。React 中应先画出一系列快照：`S0 -> update queue -> S1`。JSX 只是该快照的计算结果；组件函数不会因闭包内某个变量后来变化而自动获得新值。

`computed` 常对应 React 渲染中的普通派生表达式，而不是另一个 state：

```tsx
const visible = todos.filter(matchesFilter) // 通常已经足够
```

只有测量表明确认计算昂贵，或下游确实依赖引用稳定时才考虑 memo。

## 8. 排错算法

遇到诡异 UI，按顺序问：

1. 触发更新的是哪个事件/订阅？
2. 该函数来自哪次渲染快照？
3. updater 队列按什么顺序折叠？
4. 哪些组件被 render，哪棵树最终 commit？
5. 元素身份是否因 type/key/position 改变？
6. 是否修改了旧快照？
7. 是否把 render 阶段副作用误认为只执行一次？

## 本章速记

- React 组件是从快照到 UI 的纯计算。
- setter 安排下一次渲染，不修改当前闭包中的值。
- render 可被丢弃，commit 才改变 DOM/运行 Effect。
- state 绑定在树中的身份上；身份由 type、position、key 共同决定。
- 稳定数据 id 做 key；有意换 key 可重置子树。
- StrictMode 揭露不纯和清理问题，不是 bug。
