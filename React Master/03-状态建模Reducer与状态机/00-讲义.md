# 第 03 章：状态建模、Reducer 与状态机

## 本章目标

从“需要什么就加一个 `useState`”升级为：从业务不变量推导最小状态、用事件描述变化、用类型排除不可能状态，并知道何时使用 reducer 或状态机。

## 1. 先分类，再存储

看到一个值先问：

1. 能否由当前 props/state 在 render 中计算？能则不要存。
2. 是否属于 URL，可分享/可前进后退？是则交给路由。
3. 是否是远端资源的缓存副本？是则交给 query/loader。
4. 是否只是表单草稿？放在表单/字段边界。
5. 是否跨组件树共享且由客户端拥有？才考虑 Context/外部 store。
6. 改变它是否需要重新渲染？不需要且只保存可变句柄，考虑 ref。

冗余 state 会产生同步问题：

```tsx
const [firstName, setFirstName] = useState('Ada')
const [lastName, setLastName] = useState('Lovelace')
const [fullName, setFullName] = useState('') // 冗余

const fullName = `${firstName} ${lastName}` // 渲染时派生
```

## 2. 状态结构应编码不变量

三个布尔值：

```ts
{isLoading: boolean; isSuccess: boolean; isError: boolean}
```

允许八种组合，业务也许只允许四种。改成判别联合：

```ts
type RequestState<T> =
  | {status: 'idle'}
  | {status: 'loading'; requestId: string}
  | {status: 'success'; data: T}
  | {status: 'error'; error: string}
```

“让非法状态不可表达”同时改善渲染分支、测试用例和日志。

## 3. 规范化与身份

嵌套复制不是唯一问题，更大的问题是同一实体出现多个副本：

```ts
type State = {
  projects: Project[] // 每个 project 内又复制 users
  selectedUser: User  // 第三份副本
}
```

优先使用实体表 + id 关系：

```ts
type State = {
  usersById: Record<UserId, User>
  projectIds: ProjectId[]
  selectedUserId: UserId | null
}
```

规范化适合频繁按 id 更新、同一实体多处引用的大型状态；小而固定的表单对象不必机械规范化。

## 4. `useReducer` 何时优于多个 setter

适合 reducer 的信号：

- 多字段总要一起变化；
- 更新规则分散在多个 handler；
- 下一状态依赖复杂事件；
- 需要日志、回放、单测；
- 想把“发生什么”与“如何变化”分开。

Action 应表达领域事件，而不是 setter：

```ts
type Action =
  | {type: 'itemAdded'; product: Product}
  | {type: 'quantityChanged'; productId: string; quantity: number}
  | {type: 'checkoutSubmitted'}
```

`setLoadingTrue`、`setError` 把一个业务事件拆成多条命令，容易出现中间非法状态。reducer 必须纯：不请求、不读时间/随机数、不写 localStorage。把 id、时间等作为 action payload 从事件边界注入。

## 5. Reducer 的不变量

```ts
function cartReducer(state: CartState, action: Action): CartState {
  switch (action.type) {
    case 'quantityChanged': {
      if (action.quantity < 0) return state
      // 返回新快照
      return {...state, /* ... */}
    }
    default:
      return assertNever(action)
  }
}
```

关键测试不是“调用了几次 dispatch”，而是：给定状态与领域事件，输出是否满足库存、金额、选择等不变量。

## 6. 状态机：当“允许的转换”比“字段值”更重要

上传流程可能是：idle → selecting → uploading → success/error → retry/cancel。普通联合类型只描述可存在的状态，状态机还描述哪些转换合法。

```ts
type UploadState =
  | {status: 'idle'}
  | {status: 'ready'; file: File}
  | {status: 'uploading'; file: File; progress: number; requestId: string}
  | {status: 'success'; assetId: string}
  | {status: 'error'; file: File; message: string}
```

Reducer 可以实现小状态机；当存在并行状态、层级状态、守卫、延迟、复杂可视化时再考虑专门状态机库。库不是建模的替代品。

## 7. State、Ref 与普通变量

- state：跨渲染保留，更新安排 render。
- ref：跨渲染保留，修改不安排 render；适合 DOM、timer id、最新句柄、imperative 实例。
- 普通局部变量：每次 render 重建。
- 模块变量：所有实例共享，容易造成请求/用户数据串扰，除非它本来就是模块级缓存并有严格契约。

不要用 ref 躲开渲染：如果 UI 依赖它，它就是 state。

## 8. 状态归属和提升

把状态放到所有真正消费者的最近共同拥有者。提升过高会让更新范围扩大、API 变成 prop drilling；放得过低会产生两个真相。

“把一切放 Context”不是解决 prop drilling。优先组合 children，把数据和操作靠近使用点；Context 适合主题、会话、路由/表单 family 等跨树环境值，但每次 provider value 变化会通知消费者，应按变化频率和领域拆分。

## 9. 设计流程

1. 写实体、身份和业务不变量。
2. 列所有领域事件，不写 UI setter。
3. 推导最小状态，使非法状态尽量不可表达。
4. 写纯 reducer 和表驱动测试。
5. UI 只负责把用户/系统事件翻译成 action。
6. 异步工作在事件/服务层完成；用 requestId 或取消信号防止旧响应覆盖新状态。

## 本章速记

状态管理的第一工具是删除 state，第二工具是更好的类型，第三才是 reducer/store 库。好的模型使正确更新自然、错误更新困难。
