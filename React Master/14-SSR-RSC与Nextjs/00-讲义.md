# 第 14 章：SSR、RSC 与 Next.js App Router

## 本章目标

能按页面选择 CSR/SSG/SSR/streaming/RSC，理解 Server/Client Component 边界、缓存、hydration、Server Function 安全，并能排查用户间数据泄漏和版本漏洞。

## 1. 先分清几个概念

- CSR：浏览器 JS 获取数据并渲染。
- SSG/prerender：构建时生成 HTML，适合可缓存内容。
- SSR：请求时生成 HTML。
- Streaming SSR：HTML 分段发送，边界就绪后逐步 reveal。
- Hydration：客户端 React 接管服务器 HTML 并绑定交互。
- RSC：组件在服务器环境执行，输出序列化的组件载荷；它与 SSR 可组合但不是同一件事。

RSC 不等于“页面完全没有 JS”。Client Component 仍会进入客户端 bundle；而 Client Component 首次也可在服务器参与预渲染。

## 2. 按页面选择，不按信仰

静态营销页：SSG/CDN；个性化但可缓存壳：静态/缓存 + 动态边界；搜索/商品：SSR/streaming 可能改善首屏；高度交互内网工具：CSR 可能最简单；敏感 per-user 页面：动态且严格缓存隔离。

比较 TTFB、FCP/LCP、客户端 JS、服务器成本、缓存命中、复杂度。SSR 不是只为 SEO，也不保证更快：慢服务端会提高 TTFB。

## 3. Server/Client Component 边界

Next App Router 默认页面/布局是 Server Components。需要 state、事件、Effect、浏览器 API或自定义客户端 Hook 时使用 Client Component。

原则：

- 在服务器取靠近数据源的数据、读取秘密、减少客户端 JS；
- 把 `'use client'` 边界尽量下推到交互叶子；
- Server 传给 Client 的 props 必须可序列化；
- Client Component 不应 import server-only 模块；用 `server-only` 防环境污染；
- Provider 通常是 Client Component，但只包真正需要的子树。

官方当前说明：[Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)。

## 4. 数据获取与请求去重

Server Component 可以直接 `await` 数据。要区分：

- 单次 render/request 内去重；
- 跨请求持久缓存；
- CDN/路由缓存；
- 数据库/业务缓存。

不同框架版本的 fetch/cache 默认语义会变，必须以项目当前官方文档和配置为准，不背旧博客。任何 per-user/tenant 数据默认动态且 key 包含身份；缓存函数若闭包捕获用户却 key 不含用户，会造成严重泄漏。

失效按标签/路径/实体事件设计；不要 mutation 后清全站缓存。更新与 revalidate 的时序要能解释一致性窗口。

## 5. Streaming 与 Suspense

布局壳先发，慢资源放 Suspense 边界流式 reveal。避免：在 page 顶部 await 所有数据再返回；在边界内部才串行启动可并行请求；fallback 改变布局尺寸。

流式错误要有服务端日志和客户端边界。响应部分发送后 HTTP status 可能无法再改，错误 UI/监控设计要考虑。

## 6. Hydration 不匹配

服务器和客户端首次 render 必须相同。常见根因：

- render 中 `Date.now/Math.random`；
- 按 `window` 分支；
- 时区/locale 不一致；
- 无效 HTML 嵌套被浏览器修正；
- 服务端/客户端拿到不同缓存快照；
- 浏览器扩展修改 DOM。

修复根因，不到处 `suppressHydrationWarning`。随机 id 使用 `useId`（不可用于列表 key）；时间/locale 由服务器明确传值或 hydration 后更新非关键部分。

## 7. Server Functions/Actions 安全

把它们当公开 HTTP 端点：

- 每次认证、授权（资源级），不依赖页面 loader 已检查；
- schema 校验 FormData/参数；
- CSRF/Origin/同站策略按框架部署确认；
- 幂等、速率限制、审计；
- 只返回最小安全错误；
- 不把秘密/服务端对象序列化给 Client。

“函数写在组件文件里”不会让它变成可信内部调用。

## 8. RSC 安全版本纪律

React 官方 2025-12 公告披露 Server Components/Functions 相关未认证 RCE（CVE-2025-55182），影响若干 19.0/19.1/19.2 初始版本；随后还有 DoS/源码暴露更新。课程练习不得固定到已知受影响的 `19.2.0`，必须使用当前支持线最新安全补丁，同时升级受影响框架/`react-server-dom-*` 包。

权威入口：[React RSC 安全公告（含 2026 更新）](https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components)。CI 应能盘点版本、阻止已知漏洞进入、在公告后数小时/天级完成补丁，而不是等季度升级。

## 9. 多租户/SSR 隔离

每个请求创建或安全获取 request-scoped 会话、QueryClient、日志上下文；不能把当前用户、headers、缓存对象放模块可变变量。进程会服务多个并发用户，Serverless 实例也会复用。

缓存 key 包含 tenant/resource/locale/permission-dependent variant；敏感响应设置正确 Cache-Control/Vary，CDN 不得公共缓存 private HTML/RSC payload。

## 10. 评审清单

- 为什么选择该渲染策略，测量目标是什么？
- `'use client'` 边界能否下推？序列化 props 是否最小？
- 缓存作用域、key、失效、per-user 隔离是什么？
- 并行请求是否被顶层 await 串行化？
- hydration 首次输出是否确定？
- Server Function 是否像公开端点一样鉴权/校验/幂等？
- React/框架/RSC 包是否在最新安全补丁，如何紧急升级？

## 本章速记

SSR/RSC 把更多前端决策带到服务器：缓存和安全错误的爆炸半径也更大。高级能力不是会写 `'use client'`，而是能证明边界、隔离、加载序列和补丁纪律正确。
