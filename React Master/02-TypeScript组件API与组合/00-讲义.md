# 第 02 章：TypeScript 组件 API 与组合设计

## 本章目标

从“给 props 加类型”升级到“让错误用法无法表达”。高级组件设计的价值不是少写几行 JSX，而是把业务不变量编码进 API，同时保持可组合、可访问、可演进。

## 1. Props 是模块边界

不要先写组件内部，再随手导出十几个布尔 prop。先列使用者真正需要控制的维度、互斥状态和事件契约。

坏 API：

```ts
type AlertProps = {
  success?: boolean
  warning?: boolean
  error?: boolean
  message?: string
}
```

它允许 `success && error`、三者都不传等非法组合。用判别联合：

```ts
type AlertProps =
  | {kind: 'success'; message: string; retry?: never}
  | {kind: 'warning'; message: string; retry?: never}
  | {kind: 'error'; message: string; retry: () => void}
```

组件内部 `switch (props.kind)` 能自动收窄；新增 kind 时用 `never` 做穷尽检查：

```ts
function assertNever(value: never): never {
  throw new Error(`Unhandled: ${JSON.stringify(value)}`)
}
```

## 2. 不要默认使用 `React.FC`

直接声明函数通常推断更清楚：

```tsx
type ButtonProps = {
  children: React.ReactNode
  onPress: () => void
}

export function Button({children, onPress}: ButtonProps) {
  return <button onClick={onPress}>{children}</button>
}
```

只有真正接受 children 的组件才声明 `children`。区分常用类型：

- `ReactNode`：可渲染内容，包括字符串、数字、元素、null、数组。
- `ReactElement`：一个 React 元素对象，常用于必须接收单一元素的约束。
- `ComponentPropsWithoutRef<'button'>`：复用原生元素 props。
- `ElementRef<'button'>` 或 `ComponentRef`：需要推导 ref 目标时使用。

事件优先使用具体类型，如 `React.ChangeEvent<HTMLInputElement>`；但业务层回调更适合暴露业务值：`onValueChange(value: string)`，不要迫使上层依赖 DOM event。

## 3. 受控与非受控必须是清晰契约

组件若同时接受 `value`、`defaultValue`，应避免调用者同时传入：

```ts
type Controlled<T> = {
  value: T
  defaultValue?: never
  onValueChange: (value: T) => void
}

type Uncontrolled<T> = {
  value?: never
  defaultValue?: T
  onValueChange?: (value: T) => void
}

type SelectProps<T> = BaseProps<T> & (Controlled<T> | Uncontrolled<T>)
```

组件生命周期内不要从受控切换到非受控。受控模式把真相交给父层，适合校验、联动和集中提交；非受控模式减少上层样板，适合局部临时值。

## 4. 组合优于配置爆炸

当 `Card` 出现 `showHeader`、`headerIcon`、`headerActions`、`footerAlign`、`compact` 等大量 prop，通常说明调用者需要组合槽位：

```tsx
<Card>
  <Card.Header>
    <Card.Title>订单</Card.Title>
    <OrderActions />
  </Card.Header>
  <Card.Body><OrderTable /></Card.Body>
</Card>
```

常见组合方式：

- children/命名槽位；
- compound components + Context；
- render prop（调用者需要接收内部状态）；
- headless hook（行为与视觉完全分离）。

Context 只传 compound family 必需的稳定状态，不把组件的所有内部细节暴露出去。运行时检查“子组件必须在 Root 内”能提供更好错误。

## 5. 泛型组件的边界

泛型不是为了炫技。它应从 `items` 推断 `T`，并确保 value/render/key 的关系：

```tsx
type ListProps<T> = {
  items: readonly T[]
  getKey: (item: T) => React.Key
  renderItem: (item: T) => React.ReactNode
}

function List<T>({items, getKey, renderItem}: ListProps<T>) {
  return <>{items.map(item => <Fragment key={getKey(item)}>{renderItem(item)}</Fragment>)}</>
}
```

不要把 `keyof T` 当万能方案：字段可能不是合法 React key，展示与身份也可能需要组合逻辑。回调通常更灵活、意图更清楚。

## 6. 多态 `as` 的真实代价

设计系统常允许 `<Text as="label">`。一个完整多态 API 需要处理：

- 原生属性随 `as` 变化；
- 自有 prop 与原生 prop 冲突；
- ref 类型随元素变化；
- 语义和可访问性不能被 `as="div"` 悄悄破坏；
- 泛型复杂度会传播给使用者。

若只需要两个语义明确的变体，分别导出 `Button` 和 `LinkButton` 往往更好。让组件库 API 更窄是长期维护能力。

## 7. ref 是逃生舱

React 19 可把 `ref` 作为 prop 传入函数组件；React 18 库仍常用 `forwardRef`。无论语法如何，原则不变：

- 优先声明式 props；
- ref 用于 focus、selection、measure、滚动、第三方 imperative API；
- 用 `useImperativeHandle` 暴露最小能力，而不是整个 DOM 节点。

```tsx
export type DialogHandle = {focusFirst(): void}
```

库需要同时支持 React 18/19 时，以实际编译目标和类型版本为准，不要为了语法新而破坏消费者。

## 8. 组件 API 评审清单

- 非法状态能否被类型排除？
- 谁拥有值？受控与非受控是否互斥？
- 事件暴露 DOM 细节还是业务语义？
- 是否使用稳定身份，而不是数组索引？
- 是否能组合，还是布尔 prop 正在爆炸？
- 默认 DOM 语义是否正确？键盘/焦点/ARIA 是否有完整责任人？
- ref 是否最小化？
- 删除/重命名 prop 如何迁移？
- 类型测试和行为测试是否覆盖公共契约？

## 本章速记

高级 TypeScript 的目标不是复杂，而是让错误更早、更局部。判别联合建模互斥状态；泛型连接数据和回调；组合解决开放式布局；受控/非受控表达所有权；可访问性是 API 的一部分。
