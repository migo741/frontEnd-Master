# 第 06 章：路由与 URL/数据边界

## 本章目标

把路由理解为应用状态机和数据边界，而不是“点击 Link 换组件”。能设计可分享 URL、并行数据加载、pending/error 状态、权限与安全重定向。

## 1. URL 是用户拥有的状态

满足以下特征的状态优先放 URL：

- 刷新后应保留；
- 可以复制分享/收藏；
- 浏览器前进后退应恢复；
- 服务端/日志/分析需要理解页面上下文。

典型：分页、搜索词、排序、筛选、选中 tab、实体 id。临时输入草稿、弹窗动画、未保存密码不要放 URL。

URL 是不可信输入。解析后得到领域类型，序列化时用一个规范格式：

```ts
type Sort = 'relevance' | 'price-asc' | 'price-desc'

function parseSort(value: string | null): Sort {
  return value === 'price-asc' || value === 'price-desc' ? value : 'relevance'
}
```

不要同时在 `useState` 和 search params 保存同一筛选条件，否则形成双真相。

## 2. 现代 React Router 的三种模式

当前 React Router 文档区分：Declarative、Data、Framework。

- Declarative：基础匹配/导航，适合已有完整数据层的简单 SPA。
- Data：route config 在 render 外，提供 loader、action、pending、revalidation、error boundary。
- Framework：在 Data 上加 Vite 集成、类型安全 route module、智能代码分割和 SPA/SSR/SSG 策略。

学习重点是 loader/action/boundary 的数据流，不死背某个导入路径。官方入口：[Picking a Mode](https://reactrouter.com/start/modes)。

## 3. 路由是数据依赖边界

组件 `useEffect(fetch)` 要等代码下载、组件 render、commit 后才发请求；父子 Effect 还可能形成瀑布。route loader 可以让路由匹配后并行拉代码和数据，并在进入页面前建立 pending/error 语义。

```tsx
const router = createBrowserRouter([{
  path: '/projects/:projectId',
  loader: projectLoader,
  Component: ProjectPage,
  ErrorBoundary: ProjectError,
  lazy: () => import('./project-route'),
}])
```

loader 应支持 `request.signal` 取消；检查 `response.ok`；把 404/403 变成路由可理解的响应。不要在组件 render 后再把路由级错误变成一个飘忽的 toast。

## 4. action、表单与重验证

数据路由把 mutation 放 action，表单能获得 navigation pending、错误和渐进增强。成功后框架按约定重新验证 loader，减少手写“改完再 set 本地副本”。

仍需明确：

- 服务端必须鉴权与校验，路由守卫不是安全边界；
- mutation 是否幂等，重复提交如何处理；
- 哪些 loader 需要 revalidate；
- optimistic UI 如何回滚；
- 表单错误应靠近字段/表单，不只 toast。

## 5. Pending UI 的层级

- 全局导航指示：短延迟后展示，避免快速导航闪烁；
- 路由 skeleton：保留布局与尺寸，减少 CLS；
- 局部 fetcher pending：只禁用相关按钮，不冻结整页；
- optimistic state：即时反馈，但明确失败回滚和重复操作。

不要一导航就清空整个旧页面并显示白屏 spinner。保留可用旧内容、对目标区域显示 pending 通常更稳。

## 6. 错误边界是故障域

边界放置决定一个失败影响多大：根边界处理应用壳灾难；路由边界处理页面资源；小部件边界隔离非关键模块。

错误 UI 应包含：用户可理解的信息、重试/返回路径、追踪 id；日志记录 route、参数、release、错误 cause，但不泄露 token/PII。

404（资源不存在）、401（未认证）、403（无权限）、5xx（服务失败）不能全叫“加载失败”。

## 7. 权限与重定向安全

客户端 loader/guard 只改善体验，真正授权在服务端。认证后回跳常见 open redirect：

```ts
const next = new URL(request.url).searchParams.get('next')
```

绝不能直接 `location.href = next`。仅允许同源相对路径，拒绝 `//evil.com`、协议、反斜杠/编码绕过。更可靠是后端生成受签名或 allowlist 的 return target。

路由 chunk 加载失败可能来自版本发布后旧 HTML 指向已删除资源。需要 immutable 资源 + 保留旧版本一段时间，或一次受控刷新，不能无限 reload。

## 8. 代码分割与预取

按路由分割只是起点。预取应基于意图（hover/focus/viewport）和网络条件；同时并行加载组件与数据，避免 `lazy` render 后才开始数据请求。分析 bundle，避免公共 barrel 导入把大库重新拉回首包。

## 9. 路由评审清单

- URL 是否是唯一真相，解析/默认/序列化是否可逆？
- loader 是否并行、可取消、区分 HTTP 错误？
- action 是否防重复、服务端鉴权、错误就近？
- pending 是否保留布局和可操作区域？
- boundary 是否与故障域匹配？
- redirect 是否同源安全？
- 代码与数据能否并行预取？
- 刷新、深链、前进后退、离线/慢网是否测试？

## 本章速记

URL 是公共状态协议；loader/action 是路由级数据协议；pending/error boundary 是可靠性协议。高级路由设计关注加载序列和故障域，而不只是路径表。
