# 第 09 章：表单、Actions 与乐观交互

## 本章目标

能设计高可靠、可访问、可重复提交防护的表单；理解 React 19 Actions 解决了什么，以及它们不能替代服务端校验、鉴权和幂等。

## 1. 表单首先是 Web 平台能力

优先使用 `<form>`、`label`、正确 `type`、`name`、浏览器输入语义和 FormData。这样键盘 Enter、密码管理器、自动填充、无 JS 降级和可访问性都有基础。

不要所有按钮都忘记 `type`：form 内 `<button>` 默认 submit。不要用 clickable div 代替 button。

## 2. 受控、非受控与表单库

- 受控：React state 是当前值；便于联动/格式化，但大表单每按键可能扩大更新。
- 非受控：DOM 保存当前值，提交时读 FormData；简单、性能好。
- React Hook Form 等库常利用非受控/细粒度订阅降低大型表单重渲染。

选型看约束，不以代码行数为唯一指标。即使使用库，也要理解 HTML 语义、字段数组身份、server error、dirty/reset。

## 3. 验证有三层

1. HTML 约束：required、type、minLength，提供即时基础反馈。
2. 客户端 schema：提升体验、与 UI 类型集成。
3. 服务端验证：唯一可信安全边界，必须重复验证权限、业务规则和数据形状。

客户端和服务端可以共享 schema 定义，但不能因为“共享”就跳过服务端执行。错误模型至少区分字段错误、表单级错误、认证/权限、网络/系统失败。

错误应与字段通过 `aria-describedby` 关联，summary 可聚合并聚焦；不要只用红色或 toast。

## 4. React 19 Actions

React 19 允许把 async function 作为 form action/transition 中的 Action，自动管理 pending、错误与乐观更新的协作。常用：

- `useActionState(action, initialState)`：保存最近 action 结果与 pending；
- `useFormStatus()`：在 form 子树读取 pending/data/method/action；
- `useOptimistic()`：在 action 进行时投影临时状态；
- `<form action={fn}>`：提交 FormData。

```tsx
const [result, submit, isPending] = useActionState(createUser, initial)
return <form action={submit}>...</form>
```

Action 的参数/返回签名与普通函数不同，按当前官方类型为准。它是交互协调模型，不等于请求缓存库，也不会自动提供后端事务/鉴权。

## 5. Pending 不是“禁用整个世界”

提交按钮 pending 时应防同一意图重复触发并显示进度；但用户是否能取消/编辑取决于操作。`useFormStatus` 必须在目标 form 的子组件中调用，不能在同一个返回 form 的组件顶部期待读取该 form 状态。

pending 文案不要造成布局跳动；用 `aria-live` 谨慎播报。失败后保留用户输入，敏感字段按安全策略处理。

## 6. 乐观 UI 的适用边界

适合成功率高、可逆、用户预期明确的操作：评论临时出现、点赞、列表重排。不适合不可逆付款、权限授予、库存最终承诺等用“假成功”误导。

每个 optimistic item 需要临时身份和状态：

```ts
type OptimisticComment = Comment & {
  clientId: string
  status: 'sending' | 'failed'
}
```

服务端成功后用权威 id/时间替换；失败允许重试/删除。不要用数组 index 或文本内容匹配响应。

## 7. 重复提交与幂等

禁用按钮不能覆盖：双窗口、网络重试、客户端崩溃、代理重放。关键 mutation 带 idempotency key，服务端在用户/操作域去重并返回第一次结果。客户端保存 key 的生命周期要与一次用户意图一致，重试复用，新的明确操作生成新 key。

支付/订单类还需服务端事务、状态查询与对账；前端“只发一次”不构成保证。

## 8. 并发表单与冲突

编辑实体时携带 version/ETag。服务端 409/412 表示基准过期：展示差异、重新加载并允许用户合并，而不是静默覆盖。dirty 表单收到后台更新时要定义策略：冻结基准、提示更新、字段级 merge。

## 9. 安全

- CSRF：Cookie 认证的跨站 mutation 需 SameSite、CSRF token/Origin 检查等后端策略。
- XSS：React 默认转义文本，但 `dangerouslySetInnerHTML`、URL、第三方 HTML 需净化与 CSP。
- Server Action/Function 是公开可调用端点：每次校验身份、授权、输入，不依赖按钮是否可见。
- 错误返回不泄露数据库/栈/用户存在性。

## 10. 评审清单

- 原生表单语义是否保留？
- 值所有权、dirty/reset、动态字段身份是否清晰？
- 服务端是否重新校验/鉴权？
- 字段/表单/系统错误是否可访问？
- pending、取消、重复提交、幂等如何处理？
- optimistic item 如何匹配、回滚、重试？
- 并发编辑冲突如何处理？

## 本章速记

React 19 Actions 把异步 mutation 与 pending/optimistic UI 更自然地连接起来；生产可靠性仍由 Web 语义、服务端验证、幂等、授权和冲突策略共同构成。
