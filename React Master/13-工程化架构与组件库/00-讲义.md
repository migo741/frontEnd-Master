# 第 13 章：工程化、架构与组件库

## 本章目标

能把个人 Demo 变成多人长期维护的系统：工具链可升级、模块边界可执行、组件库契约稳定、CI/CD 有门禁、架构决策有证据。

## 1. 工程化的目标是降低变更成本

工具不是清单。每项配置应减少一种风险：

- TypeScript：错误状态/接口在编译期暴露；
- ESLint：React purity/Hooks/边界/安全规则；
- Formatter：消除无价值格式争论；
- Tests：保护行为；
- Build/bundle budgets：保护交付产物；
- CI/CD：把约定变成每次执行的系统。

无法解释风险的复杂配置就是维护负担。

## 2. 现代项目基线

React 官方已弃用 CRA。客户端 SPA 可用 Vite/Rsbuild；需要路由数据、SSR/RSC 时优先选择集成框架。不要因为“Vite 快”就认为它自动解决路由、数据、鉴权、SSR 和部署。

TypeScript 建议严格模式；`noUncheckedIndexedAccess` 暴露数组/字典缺失，`exactOptionalPropertyTypes` 区分缺省与显式 undefined。升级时先修真实模型，不用大量 `as` 把错误压回去。

ESLint 使用当前 flat config 与官方 hooks/Compiler 规则；lint 在 CI `--max-warnings=0`，但规则应分阶段引入并给迁移窗口。

## 3. 按业务能力切分

```text
src/
├── app/        # composition root、providers、router
├── pages/      # 路由组合（若框架不接管）
├── features/   # checkout/search/comment 等用户能力
├── entities/   # 稳定领域实体和展示
└── shared/     # 无业务含义的 UI/lib/config
```

层名不是重点，依赖方向才是：shared 不反向依赖 feature；一个 feature 不穿透另一个 feature 的内部文件；app 负责组装。用 ESLint boundaries、package exports、tsconfig project references 等把边界自动化。

避免两个极端：一个 `components/` 装全世界；每个按钮拆成独立 package。边界应围绕独立演进、owner、发布和测试需求。

## 4. Composition Root 与依赖注入

在 app 入口组装 Router、QueryClient、Store、API、feature flags、analytics。业务模块依赖接口/Context，不在模块顶层到处创建单例。这样测试可注入 fake，SSR 可 per request 创建实例，多租户不会串数据。

```tsx
<AppServices api={api} telemetry={telemetry} flags={flags}>
  <RouterProvider router={router} />
</AppServices>
```

## 5. 组件库分层

- tokens：颜色、间距、字体、动效、层级；
- primitives：Button、Dialog、Input，负责语义/交互/a11y；
- patterns：FormField、DataTable、PageHeader；
- domain components：OrderStatus、Price，不应塞进通用库。

组件库要提供：公共类型、受控/非受控契约、主题、可访问性、SSR、tree-shaking、版本迁移、Story/视觉回归。优先组合成熟 headless primitive，不轻易重造焦点管理。

不要通过一个巨型 `index.ts` 把整个库拉入 bundle；定义 package `exports` 和 sideEffects，验证消费者构建。

## 6. Monorepo

适合多个应用/库共享原子变更、统一工具、依赖图和缓存。需要：workspace、唯一 lockfile、任务拓扑、affected build/test、包边界、版本/发布策略。

Monorepo 不能自动带来复用；错误的 shared package 会让所有团队耦合。先证明代码有稳定共同抽象再上移。

## 7. 微前端的决策

微前端主要解决组织独立交付，不是组件复用。代价包括重复依赖、运行时集成、路由/认证/样式隔离、跨应用状态、可观测性、版本兼容和性能。

仅当团队边界、发布节奏、技术异构/遗留迁移收益足以抵消复杂度时采用。模块联邦等工具只是机制。定义 shell 契约、共享依赖版本、故障隔离、独立降级和端到端 owner。

## 8. CI/CD 与供应链

典型流水线：

1. lockfile 安装、依赖来源固定；
2. lint/type/unit/integration；
3. production build + bundle/许可证/漏洞扫描；
4. preview 环境 + E2E/视觉/性能预算；
5. 产物一次构建，多环境注入配置；
6. 签名/溯源、渐进发布、监控、自动/人工回滚。

依赖安全不能只跑 audit：评估可达性、维护状态、更新 SLA；React/RSC 安全公告要能快速定位所有应用和版本。

## 9. Feature Flag 与发布

flag 是短期迁移工具，必须有 owner、创建/到期日、默认值、服务端授权边界和删除任务。前端 flag 不能保护秘密/权限。灰度比较错误率、性能、业务指标；回滚包括代码、配置、数据库/API 兼容。

## 10. ADR 与技术方案

```md
# 决策标题
## 背景/约束/非目标
## 驱动指标
## 选项（含维持现状）
## 决策与理由
## 代价/风险/缓解
## 迁移、灰度、回滚
## 何时重新评估
```

高级工程师不是永远选最先进，而是让团队看见取舍并能撤销。

## 11. 代码评审清单

- 模块依赖方向是否正确？
- 状态/副作用/缓存是否有单一所有者？
- 公共 API 是否最小、兼容、可测试？
- a11y/security/observability 是否进入定义完成？
- bundle/性能/错误域是否变化？
- 迁移和回滚是否真实可执行？
- 文档写的是不明显的“为什么”，不是复述代码。

## 本章速记

工程化把个人习惯变成可重复系统；架构把变化限制在边界内；组件库把交互质量集中治理。工具越多不代表越成熟，可执行的约束和低变更成本才是。
