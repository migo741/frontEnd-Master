# 第 04 章：Effect 与外部系统同步

## 本章目标

Effect 是 React 最容易写出“能跑但不可靠”代码的地方。本章建立一个硬边界：**Effect 用来让 React 与外部系统保持同步，不是用来编排普通业务数据流。**

## 1. 先问“外部系统是谁”

合理的 Effect 通常同步：

- 浏览器 API：事件监听、媒体查询、IntersectionObserver；
- 网络/长连接：WebSocket、SSE、订阅；
- 非 React 组件：地图、播放器、图表实例；
- analytics/曝光（但要定义去重语义）；
- 不能由 React 直接控制的 DOM。

如果说不出外部系统，通常不需要 Effect。以下都是常见误用：

```tsx
// 冗余 state + Effect
useEffect(() => setFullName(`${first} ${last}`), [first, last])

// 应在事件中完成的业务动作
useEffect(() => {
  if (submitted) postOrder(cart)
}, [submitted, cart])
```

`fullName` 在 render 派生；提交订单由点击/表单 action 触发。Effect 方案会引入额外渲染、重复提交和模糊因果。

## 2. setup/cleanup 是一个可重复事务

正确 Effect 能执行任意次数的 `setup → cleanup → setup`，最终外部系统与当前 props/state 一致：

```tsx
useEffect(() => {
  const connection = connect(roomId)
  connection.open()
  return () => connection.close()
}, [roomId])
```

cleanup 不只是“组件卸载时”。依赖改变时，React 先清理旧同步，再建立新同步。开发 StrictMode 额外循环用来验证对称性。

清理必须针对这次 setup 创建的确切资源。不要用共享全局变量保存 connection，多个组件实例会互相关闭。

## 3. 依赖数组不是调度开关

Effect 中读取的每个响应式值（props、state、组件内定义的函数/对象）都应在依赖中。不要为了“只跑一次”删除依赖；那是向 React 隐瞒同步关系。

解决依赖频繁变化的顺序：

1. 是否根本不需要 Effect？
2. 是否能把对象/函数创建移进 Effect？
3. 是否能使用基本值依赖？
4. 是否应把非响应式逻辑移到事件处理器？
5. React 19.2 是否适合用 `useEffectEvent` 读取最新值但不触发重连？
6. 最后才考虑 memo 化依赖。

```tsx
// options 每次 render 新建，导致重连
const options = {serverUrl, roomId}
useEffect(() => connect(options), [options])

// 在 Effect 内创建，只依赖原始值
useEffect(() => {
  const connection = connect({serverUrl, roomId})
  return () => connection.close()
}, [serverUrl, roomId])
```

## 4. 事件与 Effect Event

聊天连接应在 `roomId` 改变时重连；但“连接成功”通知希望使用最新 theme，又不想 theme 改变导致重连。

React 19.2：

```tsx
const onConnected = useEffectEvent(() => {
  showToast('已连接', theme)
})

useEffect(() => {
  const c = connect(roomId)
  c.on('connected', onConnected)
  c.open()
  return () => c.close()
}, [roomId])
```

Effect Event 只用于“概念上是事件、恰好由 Effect 触发”的非响应式逻辑，不是消除 lint 的万能工具；声明和调用都有规则，由新版 hooks lint 校验。

React 18 中可通过“同步外部资源”与“显示通知”分层、稳定服务对象或谨慎的 latest ref 模式处理，但 ref 会绕开响应式检查，必须封装并测试。

## 5. 数据请求竞态

组件 Effect 请求的经典竞态：用户先查 A，马上查 B；B 先返回，A 后返回并覆盖 B。

最低防线：

```tsx
useEffect(() => {
  let ignore = false
  setState({status: 'loading'})
  fetchUser(userId).then(data => {
    if (!ignore) setState({status: 'success', data})
  })
  return () => { ignore = true }
}, [userId])
```

更好是同时使用 AbortController 和结果身份检查。Abort 节省资源，ignore/requestId 保正确性。错误处理中要区分 abort 与真实失败。

但生产请求通常更适合路由 loader、框架或 TanStack Query：它们能做预取、缓存、去重、SSR、错误/重试，避免“render 后才发请求”的瀑布。Effect fetch 是底层能力，不是默认架构。

## 6. `useEffect`、`useLayoutEffect` 和 `useInsertionEffect`

- `useEffect`：默认选择，不阻塞浏览器绘制。
- `useLayoutEffect`：commit DOM 后、绘制前同步运行；用于必须测量并在同一帧调整的布局。它会阻塞绘制，服务端也没有布局。
- `useInsertionEffect`：主要给 CSS-in-JS 库注入样式，业务代码几乎不需要。

如果 `useLayoutEffect` 中做数据请求或重计算，就是方向错了。

## 7. 订阅外部 Store 不应手写 Effect

需要从 React 外部可变 store 读取快照时，使用 `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)`。它为并发渲染、SSR 水合和撕裂问题提供协议。第五章深入。

## 8. Effect 评审清单

- 外部系统是什么？
- setup 建立了什么，cleanup 是否完全对称？
- 依赖是否诚实？为什么每一项改变都需要重同步？
- 是否存在过期响应、重复订阅、失序事件？
- StrictMode 循环是否仍正确？
- 可否改为事件、渲染派生、loader/query 或 `useSyncExternalStore`？
- 错误、取消、重试和卸载如何处理？
- 测试如何证明没有竞态和泄漏？

## 本章速记

Effect 不是生命周期回调的函数版。它描述“当前 React 快照应与某外部系统建立怎样的同步”。依赖是同步关系，不是运行频率开关；cleanup 是协议的一半。
