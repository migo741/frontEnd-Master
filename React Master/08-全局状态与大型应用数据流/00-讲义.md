# 第 08 章：全局状态与大型应用数据流

## 本章目标

不再问“Redux 还是 Zustand 谁更好”，而是先判断状态归属、变化频率、协作与调试约束，再选择最小工具。掌握现代 Redux Toolkit，而不是手写旧 Redux 样板。

## 1. 五种状态，不要混仓

| 类别 | 例子 | 首选拥有者 |
|---|---|---|
| URL | 搜索、分页、选中实体 | Router |
| Server cache | 用户、订单、列表 | Query/loader |
| Form draft | 输入、校验、dirty | 表单边界/表单库 |
| Local UI | 展开、hover、临时选择 | 最近组件 |
| Shared client domain | 工作流草稿、跨页编辑、离线队列 | Context/外部 store |

认证用户资料通常来自 server cache；只把客户端需要的会话状态/token 策略放合适边界，敏感 token 优先 HttpOnly cookie 而不是全局 JS store/localStorage。

## 2. Context 不是状态库

Context 传递当前 value；Provider value 变化会通知读取它的消费者。适合低频环境值、依赖注入、compound family。问题：

- 巨型 `{state, actions}` 每次变化波及大量消费者；
- 缺少 selector、DevTools、中间件、持久化迁移等；
- 嵌套 provider/测试依赖可能变复杂。

可将 state 与 dispatch 分 Context、按变化频率/领域拆分、稳定 action；但如果你正在重建 selector 和 DevTools，就应选成熟 store。

## 3. Zustand 何时合适

优势是轻、selector 直接、外部 store 可在 React 外访问，适合局部复杂交互、编辑器/画布、无需严格事件日志的小中型共享状态。

风险不是库本身，而是无结构：任何地方随手 set、服务端数据也塞进去、action 命名成 setter、持久化无版本。仍需领域 slice、selector、action、不变量和迁移策略。

## 4. Redux Toolkit 何时合适

适合：

- 复杂跨功能数据流，需要统一事件日志和 DevTools；
- 多团队协作，约定比少几行代码更重要；
- 中间件/审计/回放/持久化流程；
- 大量规范化实体与派生 selector；
- 需要 RTK Query 的完整生态。

现代 Redux 使用 `configureStore`、`createSlice`、Immer、typed hooks；异步服务器缓存优先 RTK Query，而不是手写 `REQUEST/SUCCESS/FAILURE` 三 action。

官方明确推荐 Redux Toolkit 作为今天写 Redux 的方式：[Why Redux Toolkit](https://redux-toolkit.js.org/introduction/why-rtk-is-redux-today)。

## 5. Action 是事实，不是远程 setter

```ts
// 弱：UI 实现泄漏
dispatch(setSidebarOpen(false))

// 强：领域/用户事实
dispatch(navigationCompleted())
```

并非所有 action 都必须宏大；关键是重要流程能从日志看懂。Reducer 负责多个字段原子变化，不让组件 dispatch 三个 setter 制造中间状态。

## 6. 规范化与 selector

RTK 的 `createEntityAdapter` 管理 ids/entities 和常见操作。State 存最小事实，selector 派生：

```ts
const selectVisibleTasks = createSelector(
  [selectAllTasks, selectFilter],
  (tasks, filter) => tasks.filter(task => matches(task, filter)),
)
```

selector memo 化依赖输入引用。如果 reducer 每次无意义重建所有实体，memo 无法帮助。不要用 selector 做副作用或返回不稳定新对象后再抱怨重渲染。

## 7. Store 边界与模块化

按业务 feature 组织，而不是全局 `actions/ reducers/ types/`：

```text
features/
  checkout/
    model/checkoutSlice.ts
    model/selectors.ts
    api/checkoutApi.ts
    ui/CheckoutPanel.tsx
```

公共 UI 不应直接依赖业务 store；通过 props/adapter 保持复用。Feature 之间通过公共事件/API 交互，避免跨 slice 直接修改内部结构。

## 8. 持久化与迁移

localStorage 不是数据库：容量、同步阻塞、跨 tab、敏感信息、schema 演进都有风险。持久化必须：

- 只保存必要字段；
- 带 schema version 和 migration；
- 对损坏/旧数据安全回退；
- PII/token 不明文长期存；
- 多 tab 定义冲突策略；
- 与服务端 state 明确谁权威。

## 9. 状态库决策模板

先回答：消费者数量/距离、更新频率、状态寿命、是否服务端权威、是否要跨页/刷新持久、是否需事件审计/DevTools、并发编辑、团队规模、SSR。

选型不是永久婚姻。用 facade Hook 隔离库 API，让业务组件依赖 `useCheckout()` 领域契约，迁移成本更低；但别包装到连 DevTools 类型都丢失。

## 本章速记

“全局”描述可见范围，不描述数据本质。先给状态归类，再选工具；工具的核心价值往往是约束、可观测性和团队协作，不只是少写代码。
