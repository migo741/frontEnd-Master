# 第 03 章：Vue 与 TypeScript——让非法状态难以表达

> 生产基线：Vue 3.5.x、TypeScript `strict`、`vue-tsc --noEmit`。类型系统的目标不是让代码“没有红线”，而是把错误尽量提前到组件调用处、领域边界和 CI。

## 0. 事故钩子：四个 boolean 拼出了不存在的页面

某用户详情页使用以下状态：

```ts
interface UserViewState {
  loading: boolean
  saving: boolean
  user?: User
  error?: string
}
```

线上出现：`loading=true`、`user` 有值、`error` 也有值；模板一边显示骨架，一边显示旧用户，顶部又弹错误。TypeScript 没报错，因为这个接口允许 `2 × 2 × 2 × 2` 类组合，而业务只允许少数状态。

高级类型设计的顺序应是：

```text
业务状态机 → 类型表达合法状态 → 组件 props/events/slots 传递契约
          → 外部 unknown 运行时校验 → 模板与 CI 验证
```

“加了 `lang="ts"`”只是开始；到处 `as User`、`!`、`any` 会把保护拆掉。

---

## 1. 三层边界：编译期、运行时、框架编译器

| 边界 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| TypeScript | 已纳入程序的静态关系、调用契约、穷尽性 | 网络 JSON 真符合类型、权限一定存在 |
| Vue SFC 编译器 | 宏转换、模板表达式、props/emit/slot 暴露 | 任意动态字符串组件的所有运行时行为 |
| 运行时 schema/业务校验 | 外部值的形状、约束、版本兼容 | 后续代码永远不破坏不变量 |

错误：

```ts
const user = await response.json() as User
```

`as` 没有生成任何运行时代码。正确边界：

```ts
const payload: unknown = await response.json()
const dto = UserDtoSchema.parse(payload)
const user = toUser(dto)
```

DTO 与 Domain 应分开。后端的 `snake_case`、nullable、字符串日期和兼容字段，不应渗透每个组件。

## 2. 先建模状态，再写 ref

### 2.1 判别联合

```ts
type UserScreen =
  | { status: 'idle' }
  | { status: 'loading'; previous: User | null }
  | { status: 'ready'; user: User }
  | { status: 'not-found'; userId: string }
  | { status: 'forbidden' }
  | { status: 'error'; error: Error; retryable: boolean }
```

模板不再猜组合：

```vue
<template>
  <UserSkeleton v-if="screen.status === 'loading'" />
  <UserCard v-else-if="screen.status === 'ready'" :user="screen.user" />
  <NotFound v-else-if="screen.status === 'not-found'" :id="screen.userId" />
  <Forbidden v-else-if="screen.status === 'forbidden'" />
  <RetryPanel v-else-if="screen.status === 'error'" :error="screen.error" />
</template>
```

“非法状态难以表达”不等于创造巨大联合。只把真正互斥、影响行为的状态编码；悬浮、折叠等局部 UI 状态可独立存在。

### 2.2 穷尽检查

```ts
function assertNever(value: never): never {
  throw new Error(`Unhandled state: ${JSON.stringify(value)}`)
}

function labelOf(state: UserScreen): string {
  switch (state.status) {
    case 'idle': return '尚未加载'
    case 'loading': return '加载中'
    case 'ready': return state.user.name
    case 'not-found': return '用户不存在'
    case 'forbidden': return '无权限'
    case 'error': return state.error.message
    default: return assertNever(state)
  }
}
```

新增状态时，遗漏分支会在 CI 失败，而不是线上显示空白。

## 3. `<script setup>` 宏不是运行时函数

`defineProps`、`defineEmits`、`defineModel`、`defineSlots`、`defineExpose` 是编译器宏：通常无需导入；参数和作用域受编译转换约束。不要把它们当普通函数动态调用。

### 3.1 `defineProps`：输入契约与默认值

```vue
<script setup lang="ts">
interface Props {
  title: string
  pageSize?: number
  tags?: readonly string[]
}

const props = withDefaults(defineProps<Props>(), {
  pageSize: 20,
  tags: () => [],
})
</script>
```

对象/数组默认值用工厂，避免实例共享。Vue 3.5 支持响应式 props 解构：

```ts
const { title, pageSize = 20 } = defineProps<Props>()
watchEffect(() => console.log(title)) // 编译器保持同一 SFC 中的 prop 读取
```

但把值传出边界时要表达“这是动态 getter”：

```ts
useTitle(() => title) // 而不是 useTitle(title)
```

props 在子组件中只读。对象 prop 的深层字段从 JavaScript 角度仍可修改，但那是绕过单向数据流；通过 emit 请求拥有者修改。

### 3.2 `defineEmits`：事件名和 payload 都是协议

```ts
const emit = defineEmits<{
  select: [id: string]
  save: [draft: Readonly<Draft>, reason: 'manual' | 'autosave']
  cancel: []
}>()

emit('save', draft, 'manual')
```

事件描述“已经发生的意图/领域事件”，如 `save`、`selectionChange`，而不是把内部 DOM 细节泄漏成 `leftButtonClicked`。事件不冒泡穿过组件树；深层跨层通信应重构上下文或状态，而非假设 DOM 冒泡。

运行时 emits validator 可用于开发诊断，但 TypeScript 类型会被擦除，外部不可信数据仍要运行时校验。

### 3.3 `defineModel`：受控协议的语法糖，不是本地真相

```ts
const open = defineModel<boolean>('open', { required: true })
const query = defineModel<string>('query', { default: '' })
```

概念上分别对应 `open` prop + `update:open` emit。写 `open.value = false` 是发更新请求，由父组件的新 prop 决定最终值。

警惕有 default、父组件又不传值的情况：子组件内部默认值可能与父侧 `undefined` 不同步。关键业务模型优先 `required: true`，或明确受控/非受控两种模式，不要半受控。

自定义 modifier：

```ts
const [model, modifiers] = defineModel<string>({
  set(value) {
    return modifiers.trim ? value.trim() : value
  },
})
```

不要在 setter 隐藏昂贵请求或不可逆业务副作用。

### 3.4 `defineSlots`：结构扩展点也要有类型

```ts
const slots = defineSlots<{
  default(props: { row: User; selected: boolean }): unknown
  empty(props: { query: string }): unknown
  error?(props: { error: Error; retry: () => void }): unknown
}>()
```

slot 是“由调用方拥有结构，组件提供数据和能力”。它比二十个显示开关更可扩展，但过多 slot props 会形成隐形框架；命名要稳定、文档要有示例。

### 3.5 `defineExpose`：最小命令式能力

`<script setup>` 默认不把内部绑定暴露给父 template ref：

```ts
function focus(): void {
  input.value?.focus()
}

defineExpose<{ focus(): void }>({ focus })
```

适合 `focus()`、`selectAll()`、`validate()` 等命令；不应暴露整个内部 state 让父组件任意修改。若行为可由 props 表达，仍优先声明式协议。

## 4. 泛型 SFC：复用关系，而非炫技

一个选择器的 item 类型由调用方决定，但 `modelValue` 必须与 item 的 key 同类型：

```vue
<script setup lang="ts" generic="TItem, TKey extends PropertyKey">
defineProps<{
  items: readonly TItem[]
  getKey: (item: TItem) => TKey
  getLabel: (item: TItem) => string
}>()

const model = defineModel<TKey | null>({ required: true })

defineSlots<{
  option(props: { item: TItem; selected: boolean }): unknown
}>()
</script>
```

泛型的价值是保留关系：`items` 是 `User[]` 时，slot item 是 User，model key 按 `getKey` 推断。适合 Table、Listbox、Tree、Form field adapter 等库级组件。

不适合：只在一个业务页使用、领域语义强、泛型参数比 props 还难懂的组件。此时明确的 `UserPicker` 更易维护。

有些复杂调用点需要 `@vue-generic` 或显式组件实例类型；必须以项目当前 Volar/vue-tsc 能力验证，不能只看编辑器“似乎有提示”。

## 5. provide/inject：类型安全的上下文协议

字符串 key 容易碰撞且无法稳定推导。定义模块级 `InjectionKey<T>`：

```ts
// selection-context.ts
import type { InjectionKey, Ref } from 'vue'

export interface SelectionContext {
  selectedIds: Readonly<Ref<ReadonlySet<string>>>
  toggle(id: string): void
  isSelected(id: string): boolean
}

export const selectionKey: InjectionKey<SelectionContext> =
  Symbol('SelectionContext')
```

提供者拥有可变状态，只给后代只读状态和动作：

```ts
provide(selectionKey, {
  selectedIds: readonly(selectedIds),
  toggle,
  isSelected,
})
```

消费者不要使用危险非空断言：

```ts
export function useSelection(): SelectionContext {
  const context = inject(selectionKey)
  if (!context) {
    throw new Error('useSelection must be used under SelectionProvider')
  }
  return context
}
```

provide/inject 适合组件族的局部上下文（Form、Tabs、Table），不应成为无边界全局 store。上下文依赖隐形，测试必须使用 provider factory 或明确 wrapper。

## 6. template ref 类型：DOM 与组件实例要区分

Vue 3.5 的 `useTemplateRef` 能根据模板位置改善推断：

```vue
<script setup lang="ts">
import { onMounted, useTemplateRef } from 'vue'

const searchInput = useTemplateRef<HTMLInputElement>('searchInput')

onMounted(() => {
  searchInput.value?.focus()
})
</script>

<template><input ref="searchInput" type="search" /></template>
```

组件实例：

```ts
import ChildForm from './ChildForm.vue'
import { useTemplateRef } from 'vue'

type ChildFormInstance = InstanceType<typeof ChildForm>
const form = useTemplateRef<ChildFormInstance>('form')
form.value?.validate()
```

ref 在未挂载、`v-if` 为 false 或卸载后是 null；类型不应靠 `!` 抹掉。`v-for` template ref 是数组语义，顺序不应被当业务身份。

如果只为了让父组件触发子组件业务保存而使用 ref，通常意味着数据流应改成 props/events 或共享 feature service。命令式 ref 只留给真正的 DOM/控件能力。

## 7. `satisfies`、窄化与配置表

配置既要检查形状，又要保留字面量：

```ts
type RouteName = 'users' | 'orders'
interface NavItem {
  label: string
  route: RouteName
  permission: 'user:read' | 'order:read'
}

const nav = [
  { label: '用户', route: 'users', permission: 'user:read' },
  { label: '订单', route: 'orders', permission: 'order:read' },
] as const satisfies readonly NavItem[]

type FirstRoute = typeof nav[0]['route'] // 'users'，没有被拓宽成 RouteName
```

`as NavItem[]` 更像“请相信我”；`satisfies` 是“请检查我，同时保留推断”。

自定义 type guard 必须真的验证：

```ts
function isUser(value: unknown): value is User {
  if (typeof value !== 'object' || value === null) return false
  const record = value as Record<string, unknown>
  return typeof record.id === 'string' && typeof record.name === 'string'
}
```

复杂 schema 优先成熟库；手写 guard 漏字段很常见。

## 8. 常见逃逸方式与根因

### 8.1 `as any`

它让错误沿调用链传播。边界暂时未知时用 `unknown`，迫使使用前窄化。

### 8.2 非空断言链

```ts
user.value!.company!.owner!.name
```

这通常说明加载状态/nullable 领域没有建模。让模板在 `ready` 分支获得非空 User。

### 8.3 到处 `Partial<T>`

`Partial<User>` 允许 id/name/email 全缺，既不是创建 DTO，也不是编辑草稿。定义精确类型：

```ts
type UserDraft = Pick<User, 'name' | 'email'> & { id?: string }
```

### 8.4 万能 `ApiResponse<T>`

不同端点的分页、404、字段错误、冲突语义不同。泛型 envelope 可复用传输形状，但不能抹平领域错误。

### 8.5 巨型组件 public instance

`defineExpose({ ...allState, ...allMethods })` 把子组件变成可远程操控对象，破坏封装与测试。只暴露最小命令。

### 8.6 类型正确，运行时错误

模板动态组件名、第三方 slot、后端字段、localStorage、URL query 都是运行时边界。静态类型不会净化输入。

## 9. CI 与类型测试

最低检查：

```json
{
  "scripts": {
    "typecheck": "vue-tsc --noEmit",
    "test": "vitest run"
  }
}
```

对泛型组件和 emits 可写编译期契约测试：

```ts
// type-contract.test-d.ts（由 vue-tsc/相应 type test 工具检查）
const id: string = selectedUserId
// @ts-expect-error user id 不是 number
const wrong: number = selectedUserId
```

`@ts-expect-error` 必须有意图：如果错误消失，指令自身会失败，能提示契约意外放宽。不要用 `@ts-ignore` 消音。

类型检查、单测、组件行为测试各自抓不同错误：

```text
vue-tsc：调用契约/模板类型
unit：状态迁移/转换函数
component：props/emits/slots 与 DOM 行为
e2e：浏览器、路由、焦点与后端契约集成
```

## 10. 排障路线

遇到“类型看似对，运行却错”：

1. 值最初来自哪里？是否是 `unknown` 外部边界？
2. 哪个 `as` / `!` / `any` 第一次取消了证明？
3. DTO 与 Domain 是否混用？
4. 状态接口是否允许非法组合？
5. 组件宏表达的是 props 还是内部状态？
6. 泛型关系是否在 wrapper/slot 处被拓宽？
7. 编辑器语言服务与 CI 的 vue-tsc 版本是否一致？
8. template ref 的 null 是否代表真实生命周期分支？

---

## 11. 生产边界

- 类型越复杂不代表架构越高级；调用者无法理解的条件类型是维护成本。
- 组件库 public 类型是版本契约，删除联合成员、收窄 slot props、改变 emit payload 都可能是 breaking change。
- runtime props validator 不能替代 API schema；它只处在组件边界。
- 泛型 SFC 的 IDE 推断会受 Vue language tools 版本影响，必须在 CI 验证。
- provide/inject 的 Symbol 必须来自同一模块实例；重复打包库可能制造不同 key，组件库要注意 bundling 与 peer dependency。
- template ref 是时序敏感能力；SSR 没有 DOM，mounted 前不可用。
- `readonly` 类型和代理是协作边界，不是安全沙箱。

---

## 12. 速记卡

```text
先画状态机，再写 ref；判别联合消灭 boolean soup。
外部数据先 unknown + schema，再进入 Domain。
defineProps 是输入，defineEmits 是事件，defineModel 是受控协议。
slot 的结构归调用方，slot props 也必须类型化。
defineExpose 只暴露最小命令，不暴露整个内部世界。
泛型用于保留类型关系，不用于展示技巧。
InjectionKey + fail-fast hook，让隐式上下文至少可追踪。
template ref 天生 nullable；生命周期分支不能用 ! 抹掉。
CI 用 vue-tsc 检查模板，不只跑 tsc。
```
