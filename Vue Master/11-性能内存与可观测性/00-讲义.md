# 第 11 章：性能、内存与可观测性

> 稳定生产基线：Vue 3.5。学习目标不是记住一组“优化 API”，而是能完成一条可审计的证据链：用户哪里慢 → 浏览器时间花在哪里 → Vue 为什么做了这些工作 → 改动为何有效 → 如何防止回退。

## 1. 先看一场真实生产事故

一个工单系统上线“万人客户列表”后出现三类投诉：

- 4G 手机第一次进入要等 6 秒才看到主内容；
- 输入筛选条件后，字符已经输入，界面却隔一拍才响应；
- 客服在地图页和列表页之间切换半小时后，标签页占用超过 1 GB；
- 开发机的 Lighthouse 却有 96 分，团队最初认为是“用户电脑太差”。

后来得到的证据是：首屏同步下载并解析了并未显示的图表库；一次筛选同步排序 50,000 行，随后 patch 了数千个不稳定的行组件；地图 SDK、`ResizeObserver` 与 window listener 在离开页面后仍被闭包持有。三个症状分别属于加载、更新和资源所有权，不能靠同一个“缓存一下”解决。

高级工程师首先改写问题：

```text
“页面很慢”
   ↓ 分场景、设备、版本、路由
加载慢 / 交互慢 / 视觉跳动 / 越用越慢
   ↓ 指标 + trace + heap + Vue 触发链
网络、解析、长任务、patch、layout、资源未释放
   ↓ 最小且可验证的干预
预算、自动回归、真实用户验证
```

## 2. 本章术语

| 术语 | 本章中的准确含义 |
| --- | --- |
| 性能预算 | 在开发和 CI 阶段可执行的上限，如关键路由初始 JS、DOM 数、长任务、LCP/INP/CLS |
| Lab | 固定机器、网络、数据下的可重复测量，适合回归，不代表用户分布 |
| RUM | 真实用户监控，能看设备、地区、版本与路由的分位数，但噪声更大 |
| LCP | 最大内容元素完成呈现的时间，描述主要内容何时可见 |
| INP | 一次访问期间交互延迟的代表值，覆盖输入到下一帧呈现的完整链路 |
| CLS | 无用户预期的布局位移累计值 |
| Long Task | 主线程连续占用超过约 50ms 的任务；它会阻塞输入与绘制 |
| 更新稳定性 | 父组件更新时，子组件接收的 props/slot/依赖是否尽量保持不变 |
| 虚拟列表 | 只挂载可视窗口附近的项目；它减少 DOM 和 patch，不减少后端总数据量 |
| retained path | heap snapshot 中从 GC root 到对象的引用链，回答“是谁还拥有它” |
| release | 一次可定位的构建版本，错误、指标和 source map 都必须与之绑定 |

常用“良好”参考线是 LCP 不高于 2.5s、INP 不高于 200ms、CLS 不高于 0.1，并以真实访问的 p75 判断。它们是通用参考，不是产品 SLO 的替代品。交易确认、编辑器输入和大屏首屏还需要业务指标。

## 3. 性能因果模型：不要从 API 开始

一次交互可以粗略拆成：

```text
用户输入
  → event handler
  → 同步 JavaScript / 响应式失效
  → Vue scheduler 合并 job
  → computed 求值 / component render
  → virtual DOM patch
  → style / layout / paint
  → 浏览器提交下一帧
```

一次加载可以粗略拆成：

```text
HTML/SSR 响应
  → 发现 CSS/JS/字体/图片
  → 网络等待
  → JS parse + compile + execute
  → Vue mount/hydrate
  → 关键数据与图片到达
  → LCP 元素绘制
```

因此“把 computed 改成 method”“全部加 `v-memo`”“拆更多 chunk”都不是诊断。它们只对特定瓶颈有效，还可能把复杂度转移到缓存失效、请求瀑布或正确性。

### 3.1 一份最小证据清单

1. 复现条件：URL、账号数据量、设备、CPU/网络限制、缓存冷热、构建版本。
2. 用户指标：RUM 的 p50/p75/p95，并按路由、设备、版本分段。
3. 浏览器证据：Network waterfall、Performance trace、Long Animation Frame、Memory snapshot。
4. Vue 证据：组件更新高亮、Vue Devtools performance、`onRenderTracked` / `onRenderTriggered`。
5. 业务证据：例如“输入到表格可操作”“保存完成”“搜索首个结果”。
6. 对照实验：一次只改变关键变量，保留 before/after trace。

## 4. 加载性能：体积只是总账的一部分

### 4.1 路由级拆分与正确的 chunk 边界

```ts
import { createRouter, createWebHistory } from 'vue-router'

export const router = createRouter({
  history: createWebHistory(),
  routes: [
    {
      path: '/reports',
      component: () => import('./pages/ReportsPage.vue'),
    },
  ],
})
```

动态导入把报告页移出初始 chunk，但还要回答：

- 用户是否高概率下一步进入它，是否值得在空闲时预取？
- chunk 是否把多个路由共同依赖复制了多份？
- 是否因拆得太细形成串行 waterfall？
- 缓存是否稳定，还是每次修改一行业务代码都会让 vendor hash 全变？
- 第三方库是否可 tree-shake，是否无意导入整个图标/日期库？

`defineAsyncComponent` 适合组件级边界，同时必须设计 loading、error、timeout 与重试，不应让用户面对空白区域：

```ts
import { defineAsyncComponent } from 'vue'

export const RichEditor = defineAsyncComponent({
  loader: () => import('./RichEditor.vue'),
  loadingComponent: () => import('./EditorSkeleton.vue'),
  errorComponent: () => import('./EditorLoadError.vue'),
  delay: 120,
  timeout: 15_000,
  onError(error, retry, fail, attempts) {
    if (attempts <= 2 && /fetch|network/i.test(error.message)) retry()
    else fail()
  },
})
```

上面为了展示机制而简写；真实项目通常同步引入很小的 skeleton/error 组件，避免再制造一个加载瀑布。

### 4.2 性能预算应能使构建失败

预算至少分三层：

- 资源预算：关键入口 gzip/brotli 后体积、最大异步 chunk、字体与关键图片；
- 运行预算：关键交互长任务、节点数量、一次更新组件数、内存平台值；
- 用户预算：Web Vitals 与业务指标的 p75/p95。

不要直接复制别人的 300KB 阈值。先记录当前基线，确认目标设备和网络，然后逐版本收紧。预算的价值是让退化在 PR/灰度阶段变成一个明确决策，而非上线后争论。

## 5. 更新性能：让“没有变化”真的不更新

### 5.1 Props stability

反例：每个父组件更新都为每行创建新对象，且每行都收到变化的 `activeId`：

```vue
<UserRow
  v-for="user in users"
  :key="user.id"
  :user="{ ...user }"
  :active-id="activeId"
/>
```

更稳定的设计是把父层可计算的布尔值传下去，并保持实体引用稳定：

```vue
<UserRow
  v-for="user in users"
  :key="user.id"
  :user="user"
  :active="user.id === activeId"
/>
```

当 `activeId` 从 A 变 B 时，只有两行的 `active` 改变。不要为了“引用稳定”原地篡改对象；稳定性必须与状态更新规则一致。

### 5.2 `computed`、`v-once` 与 `v-memo`

- `computed` 缓存派生值，并根据响应式依赖失效；适合昂贵且可复用的纯派生。
- `v-once` 让子树只渲染一次；只用于生命周期内真正静态的内容。
- `v-memo="[a, b]"` 在依赖数组未变化时跳过子树更新；它是局部、证据驱动的最后杠杆。

```vue
<article
  v-for="row in rows"
  :key="row.id"
  v-memo="[row.version, selectedId === row.id]"
>
  <ExpensiveRow :row="row" :selected="selectedId === row.id" />
</article>
```

若 `row.name` 改了却没有同步增加 `row.version`，界面会陈旧。这说明 `v-memo` 把正确性压到了失效协议上。先用稳定 props、拆组件和数据结构解决，再考虑它。

### 5.3 深响应式的真实成本

对 50,000 个不可变记录做深代理往往没有必要：

```ts
import { shallowRef, triggerRef } from 'vue'

interface Row {
  readonly id: string
  readonly score: number
}

const rows = shallowRef<readonly Row[]>([])

function replaceRows(next: readonly Row[]): void {
  rows.value = next
}

// 只有在你明确选择了内部可变协议时才这样做：
function unsafePatchFirst(score: number): void {
  const first = rows.value[0]
  if (!first) return
  ;(first as { score: number }).score = score
  triggerRef(rows)
}
```

推荐让 `shallowRef` 配合不可变替换。`triggerRef` 暴露了“内部曾被突变”的隐式协议，团队很容易漏掉。

### 5.4 虚拟列表不是切片

`rows.slice(0, 50)` 只是丢掉后面的项目。虚拟列表需要：

1. 根据 scroll offset 计算 start/end；
2. 用占位容器保持总滚动高度；
3. 将可视项平移到正确位置；
4. 处理 overscan、动态高度、键盘焦点、滚动锚点；
5. 保证 item key 与实体身份稳定。

```ts
import { computed, type Ref } from 'vue'

export function useFixedVirtualWindow<T>(options: {
  items: Ref<readonly T[]>
  scrollTop: Ref<number>
  viewportHeight: Ref<number>
  itemHeight: number
  overscan?: number
}) {
  const overscan = options.overscan ?? 5
  const start = computed(() =>
    Math.max(0, Math.floor(options.scrollTop.value / options.itemHeight) - overscan),
  )
  const end = computed(() =>
    Math.min(
      options.items.value.length,
      Math.ceil(
        (options.scrollTop.value + options.viewportHeight.value) /
          options.itemHeight,
      ) + overscan,
    ),
  )
  const visible = computed(() =>
    options.items.value.slice(start.value, end.value),
  )
  const offsetY = computed(() => start.value * options.itemHeight)
  const totalHeight = computed(
    () => options.items.value.length * options.itemHeight,
  )

  return { start, end, visible, offsetY, totalHeight }
}
```

生产中优先评估成熟虚拟化库。可访问表格、动态行高、展开行与浏览器查找都使自研复杂度急剧上升。

### 5.5 CPU 任务与 Web Worker

Worker 只能搬走纯计算；DOM、Vue ref 与函数不能直接传输。结构化克隆大对象也有成本。更好的协议是传紧凑数据或 transferable buffer，返回 id/索引而非复制整张表。先量 trace：若瓶颈是 layout 或 patch，Worker 不会解决。

## 6. 如何定位 Vue 更新

开发环境可使用：

```ts
import { onRenderTracked, onRenderTriggered } from 'vue'

onRenderTracked((event) => {
  console.debug('render tracked', event.type, event.key)
})

onRenderTriggered((event) => {
  console.debug('render triggered', event.type, event.key)
})
```

它们用于诊断，不要作为生产日志。推荐顺序：

1. 在 Performance 录制一次明确交互，定位长任务和 layout；
2. 用 Vue Devtools 的组件更新/性能工具确认哪些组件参与；
3. 用触发钩子缩小到依赖键；
4. 检查 props、slot、列表 key、派生值与响应式深度；
5. 修改后复录同一场景，比较 CPU、更新数和用户指标。

## 7. 内存：泄漏是“失去业务用途却仍可达”

内存上涨不必然是泄漏：缓存预热、JIT、图片解码和 GC 未运行都会上涨。泄漏的关键证据是完成相同生命周期后，本应释放的实例仍沿 retained path 可达，并随循环单调增长。

常见所有者：

- `window/document` listener；
- timer、RAF、Observer；
- WebSocket、SSE、BroadcastChannel；
- 地图、图表、编辑器 SDK 实例；
- 闭包持有的大数组或 detached DOM；
- 无上限 `Map`/缓存；
- `KeepAlive` 中 deactivate 后仍运行的轮询；
- 在组件作用域之外创建且从未停止的 watcher/effect scope。

### 7.1 资源所有权写进 Composable

```ts
import {
  onActivated,
  onBeforeUnmount,
  onDeactivated,
  onMounted,
  ref,
  type Ref,
} from 'vue'

export function useElementSize(target: Ref<Element | null>) {
  const width = ref(0)
  const height = ref(0)
  let observer: ResizeObserver | undefined

  function start(): void {
    if (observer || !target.value) return
    observer = new ResizeObserver(([entry]) => {
      if (!entry) return
      width.value = entry.contentRect.width
      height.value = entry.contentRect.height
    })
    observer.observe(target.value)
  }

  function stop(): void {
    observer?.disconnect()
    observer = undefined
  }

  onMounted(start)
  onActivated(start)
  onDeactivated(stop)
  onBeforeUnmount(stop)

  return { width, height }
}
```

这里同时处理 unmount 和 KeepAlive deactivate。若 target 会变化，还应 watch 它并把旧元素 unobserve；这正是生产边界，而不是把 `disconnect()` 背下来。

### 7.2 Heap 调查流程

```text
固定数据与操作脚本
 → baseline snapshot
 → 进入/操作/退出页面 10 次
 → 等待空闲，并在可控环境触发 GC
 → comparison 按 retained size / constructor 排序
 → 检查 Vue component、Detached DOM、SDK 对象
 → 沿 retaining path 找真正 owner
 → 修复 owner 的生命周期
 → 重复 20 次验证进入稳定平台
```

把局部变量设为 `null` 不保证释放；只要 listener registry、observer、SDK 或全局缓存仍引用对象，GC 就不能回收。

## 8. 从 Web Vitals 到可行动的观测

一条可用事件至少包含：

```ts
interface FrontendMetric {
  name: 'LCP' | 'INP' | 'CLS' | 'route_ready' | 'save_latency'
  value: number
  rating?: 'good' | 'needs-improvement' | 'poor'
  release: string
  route: string
  navigationType: string
  deviceClass: 'low' | 'mid' | 'high' | 'unknown'
  sampleRate: number
  traceId?: string
}
```

生产上通常用维护良好的 Web Vitals 采集库处理浏览器差异，不建议手写一套不完整算法。采集后还要：

- 按 page view 去重并控制采样；
- 避免 URL、表单值、用户姓名等敏感信息；
- 把 route template 而非高基数真实 URL 作为维度；
- 关联 release、feature flag、trace/request id；
- source map 上传到错误平台并限制访问，不必公开部署；
- 同时记录业务结果，避免只追技术分数。

### 8.1 告警是 SLO，不是 `console.error`

示例：`/orders` 移动端 LCP p75 连续 15 分钟高于产品预算，且样本数足够、相比前一 release 恶化 25%，才触发发布告警。低流量、单个极慢用户或第三方脚本偶发错误不应直接叫醒值班人。

### 8.2 发布闭环

```text
PR: bundle/单测/固定场景 trace
  → 预发: 弱机与关键数据规模
  → 灰度: release + feature flag 对照
  → 全量: RUM p75/p95 + 业务转化
  → 复盘: 原因、收益、回退条件、预算更新
```

## 9. 常见反例与边界

1. **只看 Lighthouse 总分**：它是一次 lab 样本且是加权结果，不能证明所有真实用户快。
2. **把所有组件都包 memo**：增加失效协议，可能产生陈旧 UI，且对网络/layout 瓶颈无效。
3. **看到内存曲线涨就判泄漏**：必须用重复生命周期、GC 后平台值和 retained path 证明。
4. **只减 gzip 体积**：解析执行、主线程工作和请求瀑布同样关键。
5. **为性能删除语义和可访问性**：虚拟化后键盘导航、读屏语义与焦点不能消失。
6. **上报所有事件**：成本、高基数和隐私会反噬；先定义问题、采样和保留期。
7. **盲目深响应式**：大型不可变数据可用 `shallowRef`；但编辑表单需要细粒度更新时，深响应式可能更简单正确。

## 10. 一份高级工程师的排障口述模板

> 我先把“慢”限定为哪个路由、哪类设备、哪个版本和哪段用户旅程。然后比较 lab trace 与 RUM 分位数：前者用于定位主线程/网络阶段，后者确认影响面。若 trace 显示组件更新长任务，我会用 Vue Devtools 和 render trigger 找到更新源，检查 props 稳定性、列表 DOM、派生计算和响应式深度；若是加载则检查 waterfall、chunk ownership 与关键资源。改动后用同一 fixture 复录，并用预算和灰度 RUM 防回退。内存问题则用重复生命周期和 retained path 找 owner，不凭曲线猜。

## 11. 速记卡

- 先场景、指标、证据，再选优化手段。
- Lab 负责可重复；RUM 负责真实分布。
- 首屏：waterfall + parse/execute + hydrate/mount + LCP 元素。
- 交互：handler + scheduler + render/patch + layout/paint。
- 优先稳定 props、减少 DOM、控制响应式深度，再谈 `v-memo`。
- 虚拟化减少挂载项，不等于分页，也不免除可访问性设计。
- 泄漏 = 无业务用途但仍可达；retained path 找 owner。
- 观测必须关联 route、release、feature 和业务结果。
