# 第 11 章：性能、内存与可观测性

## 先定义用户问题

性能优化从指标、场景、设备和预算开始。加载关注 LCP、INP、CLS、资源体积与缓存；运行时关注长任务、输入延迟、内存、DOM 数；业务还要关注“工单首屏可操作时间”“图表切换延迟”。实验室 Lighthouse 用于稳定回归，RUM 用于真实分布，两者不能互相替代。

## 加载路径

路由级 code split 是起点，不是终点。检查 waterfall、preload、缓存头、字体和图片；避免无意导入整个组件库/图标库；分析 source map 和 chunk ownership。过度拆包会产生请求和执行开销，chunk 应围绕路由与缓存稳定性。

## 更新路径

用 Vue Devtools、`onRenderTriggered` 和 Performance profile 找到谁触发、耗时在哪。常见杠杆：稳定 props、减少深响应式、`shallowRef` 管理大型不可变结构、虚拟列表、Web Worker 搬纯 CPU 任务、把排序/聚合移出 render。memoization 只有命中率和失效成本可控时才有价值。

## 内存

内存泄漏常来自未释放的事件、timer、observer、socket、第三方 widget、闭包缓存和 KeepAlive 页面。用 Memory heap snapshot 的 retaining path 找所有者；反复进入/退出页面，观察节点与 listener 是否回落。只看到内存上涨不等于泄漏，GC 时机也要考虑。

## 观测闭环

前端错误包含 release、route、feature、requestId、用户匿名维度和 breadcrumbs；source map 应上传到监控后受控，不一定公开部署。指标做 p75/p95 与版本对比，告警绑定 SLO 和业务影响，避免每个 console.error 都叫醒人。

## 自检

Lighthouse 100 分为何不能证明真实用户快？`shallowRef` 的性能收益与正确性代价是什么？怎样证明是泄漏而非 GC 未运行？
