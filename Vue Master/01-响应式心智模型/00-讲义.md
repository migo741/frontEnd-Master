# 第 01 章：响应式心智模型——从 `track/trigger` 到可取消副作用

> 稳定生产基线：Vue 3.5.x、Composition API、`<script setup lang="ts">`、TypeScript `strict`。

## 0. 事故钩子：搜索结果为什么“穿越”了

用户依次输入 `v`、`vu`、`vue`，页面启动了三个请求：

```text
时间 ────────────────────────────────────────────────>
输入        v          vu          vue
请求        A----------┐
                       └─返回（慢，最后返回）
                       B----┐
                            └─返回
                                   C--┐
                                      └─返回（本应保留）
页面结果                  vu          vue       v  ← 错误覆盖
```

开发者明明使用了 `watch(keyword, fetchData)`，为什么仍会错？因为响应式只保证“值变化后重新执行副作用”，不替你定义异步任务之间的先后关系。高级 Vue 开发者要同时回答四个问题：

1. 读了什么，为什么会被追踪？
2. 写了什么，哪些 effect 会被通知？
3. effect 何时执行，是否会被批处理？
4. 上一轮副作用何时失效，资源由谁清理？

本章的目标不是背 API，而是建立一条能用于排障的因果链：

```text
状态读取 → track 建边 → 状态写入 → trigger 找边
        → scheduler 入队/去重 → effect 重新运行
        → 清理旧依赖/旧资源 → 生成新的依赖与副作用
```

---

## 1. 术语先对齐

| 术语 | 本章中的精确定义 | 常见误解 |
| --- | --- | --- |
| reactive value | 读取和写入可被 Vue 拦截的值 | “对象变成了另一个普通对象” |
| dependency | 某个 effect 对某个 `target/key` 的读取关系 | “组件依赖整个 store” |
| effect | 需要在依赖失效时重跑的函数；组件渲染、computed、watch 都建立在它之上 | “只有 `watchEffect` 才是 effect” |
| track | 在活动 effect 与被读取的 `target/key` 之间建边 | “读取会立即更新 DOM” |
| trigger | 某个键写入后找到相关 effect，并通知或调度它们 | “写一次就同步 render 一次” |
| scheduler | 决定 effect 何时执行、如何去重和排序 | “`nextTick` 是定时器” |
| invalidation | 旧一轮计算或副作用不再有效 | “Promise 会自动取消” |
| ownership | 谁创建资源，谁负责停止资源 | “组件卸载会清理任何地方创建的 watcher” |

把“响应式”和“异步正确性”分开：响应式解决传播，取消、版本号、幂等和错误语义解决业务正确性。

## 2. 最小依赖图：`WeakMap → Map → Set`

下面是教学模型，不是 Vue 源码的逐行复制，但足以解释绝大多数行为。

```ts
type Effect = () => void

const bucket = new WeakMap<object, Map<PropertyKey, Set<Effect>>>()
let activeEffect: Effect | undefined

function track(target: object, key: PropertyKey): void {
  if (!activeEffect) return

  let depsMap = bucket.get(target)
  if (!depsMap) {
    depsMap = new Map()
    bucket.set(target, depsMap)
  }

  let dep = depsMap.get(key)
  if (!dep) {
    dep = new Set()
    depsMap.set(key, dep)
  }

  dep.add(activeEffect)
}

function trigger(target: object, key: PropertyKey): void {
  const effects = bucket.get(target)?.get(key)
  if (!effects) return

  // 复制集合，避免 effect 重跑时清理/重新添加导致迭代异常。
  for (const effect of new Set(effects)) effect()
}
```

对象为什么用 `WeakMap`？依赖桶不应强行延长原始对象的生命周期。当目标对象没有其他强引用时，它仍有机会被垃圾回收。

### 2.1 `reactive` 与 `ref` 拦截方式不同

`reactive` 对对象使用 Proxy：

```ts
function reactive<T extends object>(raw: T): T {
  return new Proxy(raw, {
    get(target, key, receiver) {
      track(target, key)
      return Reflect.get(target, key, receiver)
    },
    set(target, key, value, receiver) {
      const oldValue = Reflect.get(target, key, receiver)
      const changed = !Object.is(oldValue, value)
      const ok = Reflect.set(target, key, value, receiver)
      if (ok && changed) trigger(target, key)
      return ok
    },
  })
}
```

`ref` 是带 `.value` getter/setter 的容器。它可以包原始值，也可以包对象；对象值通常会转换成深层响应式代理。

```ts
interface RefLike<T> { value: T }

function refLike<T>(initial: T): RefLike<T> {
  const target = { value: initial }
  return {
    get value() {
      track(target, 'value')
      return target.value
    },
    set value(next: T) {
      if (Object.is(next, target.value)) return
      target.value = next
      trigger(target, 'value')
    },
  }
}
```

记住一句话：**变量本身不能被 Proxy 拦截，属性访问可以。** 因此，`ref` 用 `.value` 提供可拦截的属性访问。

## 3. 身份、解构与深浅边界

### 3.1 代理不等于原对象

```ts
const raw = { count: 0 }
const state = reactive(raw)

console.log(state === raw) // false
```

不要在业务代码中混用 raw 和 proxy 作为 `Map` key 或做身份判断。`toRaw()` 适合短暂与第三方库交互、调试；长期持有 raw 并写入，会绕过响应式。

### 3.2 为什么普通解构会断开连接

```ts
const state = reactive({ count: 0 })
const { count } = state

state.count++
console.log(count) // 仍是 0
```

读取 `state.count` 时发生了一次 Proxy `get`，但 `count` 得到的是普通 number。以后读取局部变量不会经过 Proxy。

需要保持属性连接时：

```ts
const state = reactive({ count: 0 })
const { count } = toRefs(state)

state.count++
console.log(count.value) // 1
```

注意：Vue 3.5 对 `defineProps()` 的解构有编译器转换，模板和同一 `<script setup>` 中的访问可以保持响应性；这不代表所有 `reactive()` 解构都变安全。把解构后的 prop 传给 `watch` 时仍应传 getter：

```ts
const { userId } = defineProps<{ userId: string }>()
watch(() => userId, loadUser)
```

### 3.3 深响应不是“递归启动一万个 watcher”

Vue 的深层代理通常按访问懒创建，但访问巨型数据、深层遍历 watcher、频繁细粒度写入仍会扩大依赖和代理成本。

| 工具 | 适用边界 | 写入方式 |
| --- | --- | --- |
| `ref` | 单值、整体替换、对象均可，默认常用 | `x.value = next` |
| `reactive` | 一组始终作为对象操作的可变状态 | `state.key = next` |
| `shallowRef` | 不可变大数据、编辑器实例、第三方对象 | 替换 `.value`；深改后可 `triggerRef`，但优先整体替换 |
| `shallowReactive` | 只有根属性需要响应 | 修改根属性 |
| `markRaw` | 明确永不代理的实例/对象图 | 变化不通知 Vue |
| `readonly` | 对外暴露只读契约 | 由拥有者通过动作修改 |

不要为了“性能”到处 `markRaw`。它是架构边界：一旦标记，调用方必须接受深层变化不会驱动 UI。

## 4. 动态依赖必须清理

考虑条件读取：

```ts
const state = reactive({ ok: true, a: 'A', b: 'B' })
const text = computed(() => state.ok ? state.a : state.b)
```

第一次依赖 `ok` 和 `a`；`ok` 变成 false 后，下一次应依赖 `ok` 和 `b`，不再依赖 `a`。

```text
第一次：effect ──> ok
             └──> a

切换后：effect ──> ok
             └──> b
          （旧的 a 边必须删除）
```

真实 effect 会记录自己属于哪些 dep；重跑前移除旧边，运行时再收集新边。没有清理会产生：无效重跑、内存增长，甚至集合迭代死循环。嵌套 effect 还需要 effect 栈，执行完恢复父 effect，不能只用一个永不恢复的全局变量。

## 5. `computed`、`watch`、`watchEffect` 分工

### 5.1 `computed` 是缓存的纯派生

```ts
const firstName = ref('Ada')
const lastName = ref('Lovelace')

const fullName = computed(() => `${firstName.value} ${lastName.value}`)
```

概念上，computed 同时是：

1. 一个订阅上游依赖的 effect；
2. 一个能被下游读取的 ref；
3. 一个保存缓存与失效状态的节点。

```text
firstName ─┐
           ├─> computed(fullName) ─> component render
lastName ──┘
```

上游变化时 computed 先“失效/通知”，通常不需要立刻执行 getter；下一次读取时再求值。因此 getter 必须是纯函数：不要发请求、写 store、打日志或修改另一个 ref。

错误：

```ts
const total = computed(() => {
  auditLog.value.push('recalculate') // 副作用，读取次数会改变行为
  return cart.value.reduce((sum, item) => sum + item.price, 0)
})
```

### 5.2 `watch`：依赖显式，适合精确副作用

```ts
const page = ref(1)
const filters = reactive({ status: 'active' as 'active' | 'disabled' })

watch(
  [page, () => filters.status],
  ([nextPage, nextStatus], [oldPage, oldStatus]) => {
    console.log({ nextPage, nextStatus, oldPage, oldStatus })
  },
)
```

常见 source：ref、reactive object、getter、source 数组。不要写 `watch(state.count, ...)`，因为传入时已经求值得到 number；应写 `watch(() => state.count, ...)`。

`deep: true` 会遍历深层属性以收集依赖，成本和对象图规模相关，而且嵌套修改时 `newValue` 与 `oldValue` 可能仍指向同一对象。优先 watch 明确字段，或在数据入口转换成稳定查询键。

### 5.3 `watchEffect`：依赖自动，适合简单同步联动

```ts
watchEffect(() => {
  document.title = `${unreadCount.value} unread`
})
```

它立即运行，并追踪同步执行阶段读取的响应式值。异步函数只会自动追踪第一个 `await` 前发生的读取：

```ts
watchEffect(async () => {
  const id = userId.value       // 会追踪
  await Promise.resolve()
  console.log(locale.value)     // 不会成为本轮自动依赖
  await fetchUser(id)
})
```

异步业务通常用显式 `watch` 更容易审查。

### 5.4 选择表

| 需求 | 首选 | 理由 |
| --- | --- | --- |
| 从已有状态得到一个值 | `computed` | 单一真相、缓存、无副作用 |
| 精确观察字段并访问新旧值 | `watch` | 依赖和触发条件显式 |
| 少量同步副作用，依赖就是函数内所读 | `watchEffect` | 代码紧凑 |
| 把 A 持续复制到 B | 通常重构成 `computed` | 双份真相会漂移 |
| 一次性事件处理 | 事件 handler | 不要为命令建长期 watcher |

## 6. 调度：写入不等于立即更新 DOM

组件渲染 effect 和默认 watcher 会进入调度队列。一个同步调用栈内多次写入通常会合并：

```ts
count.value++
count.value++
count.value++
// JavaScript 状态现在已是 +3；DOM 通常尚未刷新三次，而是稍后统一刷新。
```

简化时间线：

```text
同步调用栈
  ├─ state write → job 入队
  ├─ state write → 相同 job 去重
  └─ state write → 相同 job 去重
          ↓
微任务刷新队列
  ├─ pre watcher / component jobs（带父子顺序约束）
  ├─ patch DOM
  └─ post watcher / nextTick continuation
          ↓
浏览器布局与绘制（不由 nextTick 保证）
```

### 6.1 `flush` 是语义，不是性能开关

| `flush` | 何时使用 | 风险 |
| --- | --- | --- |
| `'pre'`（默认） | 数据联动；不读取本组件更新后的 DOM | 回调中读取 DOM 可能仍是旧的 |
| `'post'` | 必须在 Vue 更新完组件 DOM 后测量/操作 | 仍不保证浏览器已完成绘制 |
| `'sync'` | 极少数必须同步失效的小布尔状态 | 不批处理；数组循环写入会触发很多次 |

`await nextTick()` 表示等待当前 Vue 更新刷新完成；它不等待请求、不等图片加载，也不承诺浏览器已经 paint。需要读取更新后 DOM，可用 post watcher 或 nextTick；需要等下一帧绘制，再明确使用 `requestAnimationFrame`。

## 7. 副作用清理：失效不是卸载的同义词

watcher 会反复运行。每一轮都可能创建请求、计时器、订阅；**下一轮开始前**要清理上一轮，组件卸载时也要清理当前轮。

Vue 3.5 提供 `onWatcherCleanup`：

```vue
<script setup lang="ts">
import { onWatcherCleanup, ref, shallowRef, watch } from 'vue'

interface User { id: string; name: string }

const userId = ref('1')
const user = shallowRef<User | null>(null)
const error = shallowRef<Error | null>(null)

watch(userId, async (id) => {
  const controller = new AbortController()

  // 必须在当前 watcher 的同步阶段注册，不能等 await 之后。
  onWatcherCleanup(() => controller.abort())

  error.value = null
  try {
    const response = await fetch(`/api/users/${encodeURIComponent(id)}`, {
      signal: controller.signal,
    })
    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    user.value = await response.json() as User // 本章暂略运行时 schema 校验
  } catch (cause: unknown) {
    if (cause instanceof DOMException && cause.name === 'AbortError') return
    error.value = cause instanceof Error ? cause : new Error(String(cause))
  }
}, { immediate: true })
</script>
```

也可使用 watcher 回调第三个参数 `onCleanup`，尤其当清理注册位置需要跨越异步边界时。但最稳妥的结构仍是先同步创建资源并注册清理，再 `await`。

### 7.1 Abort 还不够时，加“代次令牌”

不是所有异步 API 都支持取消；服务端也可能已完成请求。用单调递增版本阻止旧结果提交：

```ts
let generation = 0

watch(query, async (value, _oldValue, onCleanup) => {
  const current = ++generation
  let active = true
  onCleanup(() => { active = false })

  const result = await legacySearch(value)
  if (!active || current !== generation) return
  rows.value = result
})
```

这实现 latest-wins。支付提交等业务可能需要 first-wins、幂等键或串行队列，不能把搜索语义照搬。

## 8. `effectScope`：把多个 effect 变成一个可释放资源

组件 `setup()` 同步创建的 watcher 通常会绑定组件作用域，卸载时自动停止。但以下场景需要显式作用域：动态工作区、标签页模型、插件、组件外创建的一组 effects。

```ts
import { effectScope, onScopeDispose, ref, watch } from 'vue'

export function createDraftSession(draftId: string) {
  const scope = effectScope()

  const api = scope.run(() => {
    const dirty = ref(false)
    const intervalId = window.setInterval(() => {
      if (dirty.value) void saveDraft(draftId)
    }, 5_000)

    watch(dirty, value => console.debug('dirty:', value))
    onScopeDispose(() => window.clearInterval(intervalId))

    return { dirty }
  })

  if (!api) throw new Error('draft scope failed to initialize')

  return {
    ...api,
    stop: () => scope.stop(),
  }
}

declare function saveDraft(id: string): Promise<void>
```

资源所有权图：

```text
DraftSession(scope)
  ├─ watch(dirty)
  ├─ autosave interval
  └─ future subscriptions

session.stop()
  └─ 一次释放全部资源（重复调用也应安全）
```

陷阱：在 `setTimeout`/请求回调中晚些时候创建 watcher，可能不再绑定原组件当前作用域。尽量同步创建 watcher，把异步结果写进已有 ref。

## 9. 一个可生产化的请求状态机

三个松散布尔值会表达非法组合：`loading=true`、`data!=null`、`error!=null`。用判别联合明确状态：

```ts
type RemoteData<T> =
  | { status: 'idle' }
  | { status: 'loading'; previous: T | null }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error; previous: T | null }
```

一次 latest-wins 查询的合法迁移：

```text
idle ──query──> loading ──resolve──> success
                    └────reject───> error
success ─query─> loading(previous=data)
error   ─retry─> loading(previous=previous)
旧请求 resolve/reject ─────────────> 丢弃（不得提交）
```

这张图比 `isLoading` 更有价值，因为它告诉测试应该覆盖哪些迁移。

## 10. 常见反例与根因

### 10.1 用 watch 复制派生状态

```ts
const first = ref('Ada')
const last = ref('Lovelace')
const full = ref('')

watch([first, last], () => {
  full.value = `${first.value} ${last.value}`
}, { immediate: true })
```

问题：多一份可写真相、需要立即同步、可能出现中间状态。改为 `computed`。

### 10.2 对整个路由或 store 深监听

```ts
watch(route, refetchEverything, { deep: true })
```

问题：不相关字段也触发，难以解释，深遍历成本不可控。改为：

```ts
watch(
  () => [route.params.projectId, route.query.page] as const,
  ([projectId, page]) => loadPage(String(projectId), Number(page ?? 1)),
)
```

### 10.3 `JSON.stringify` 伪造依赖

它会掩盖数据模型问题，制造 O(n) 序列化和顺序/不可序列化边界。建立显式查询键或不可变更新。

### 10.4 computed 里写状态

读取 computed 的位置和次数本应不影响业务。写状态会造成循环更新、SSR 差异和难复现错误。

### 10.5 把复杂第三方实例深度 reactive

编辑器、图表、WebSocket 客户端通常使用私有字段和身份比较。用 `shallowRef` 或 `markRaw`，并显式管理销毁。

## 11. 测试与排障

### 11.1 测什么

1. 派生是否纯、条件依赖切换后旧依赖是否不再触发；
2. 同一 tick 多次写入是否只产生预期可观察效果；
3. 旧异步任务晚返回是否不能覆盖新结果；
4. abort 是否不被显示成业务错误；
5. scope/组件卸载后计时器、listener、请求是否停止。

### 11.2 可控 Promise 比真实延时可靠

```ts
function deferred<T>() {
  let resolve!: (value: T) => void
  let reject!: (reason?: unknown) => void
  const promise = new Promise<T>((res, rej) => {
    resolve = res
    reject = rej
  })
  return { promise, resolve, reject }
}
```

测试中手动让第二个请求先完成、第一请求后完成，稳定复现竞态。不要用 `setTimeout(100)` 猜网络顺序。

### 11.3 排障路径

```text
1. 值真的被写了吗？（Vue Devtools / 断点）
2. 读取发生在响应式上下文吗？（是否解构/拿了 raw）
3. source 是否正确？（getter vs 已求值 primitive）
4. 是否被 computed 缓存/条件依赖切换？
5. job 在 pre/post/sync 哪个阶段？
6. DOM 读取是否早于 patch？
7. 上一轮副作用有无 cleanup？
8. 是否存在旧 Promise 回写？
```

开发环境可用 `onTrack` / `onTrigger` 调试 computed 或 watcher 的依赖事件；它们用于诊断，不应成为业务逻辑。

## 12. 生产边界

- 响应式不是事务系统：跨多个 store 的业务原子性仍需动作/领域服务设计。
- AbortController 取消客户端等待，不等于服务端回滚；写请求需要幂等键或服务端协议。
- `readonly` 是运行时代理约束，不是安全边界；恶意代码仍不受你的类型系统控制。
- deep watcher 的数字深度等版本能力需要核对项目实际 Vue 版本，不要把示例当跨版本契约。
- SSR 中全局可变 reactive 单例可能跨请求泄漏；请求状态必须按请求创建，本主题在 SSR 章展开。
- 不要用 `toRaw`、`markRaw`、`triggerRef` 修补看不懂的更新问题；先画依赖和所有权。

computed 做纯派生，watch 做显式副作用。
pre 看数据，post 看更新后 DOM，sync 极少用。
nextTick 等 Vue 刷新，不等网络，也不保证 paint。
每轮副作用先注册 cleanup，再开始 await。
