# 第 14 章：大型应用、微前端与迁移

## 架构是约束，不是目录美学

大型前端的问题来自团队与变化规模：依赖失控、发布耦合、共享状态、标准漂移。模块化单体通常是第一选择：feature 边界、public API、依赖规则、独立测试。只有团队需要独立部署、技术栈/发布节奏不同且组织能承担平台成本时，才评估微前端。

## 微前端代价清单

运行时集成会带来重复依赖、路由/样式隔离、认证、跨应用通信、错误隔离、性能与观测关联。共享一个全局 store 会重新耦合；优先 URL、后端 API 和版本化事件契约。壳应用负责导航、会话能力和公共体验，不应知道每个子应用内部状态。

决策要有量化信号：发布冲突频率、构建时间、团队 ownership、故障域、独立回滚需求。若只是“大仓库看起来乱”，先修边界。

## 迁移 Vue 2/旧项目

使用 strangler pattern：建立稳定适配层、按路由/feature 渐进替换、双运行期记录行为差异。先升级测试和构建可观测性，再迁代码。把 Options API 全改 Composition API 不等于业务价值；可维护旧组件无需为了风格重写。

## ADR 与评审

ADR 包含上下文、驱动因素、候选、决策、后果、回滚/复审条件。高级工程师会写“何时这个决定不再成立”，也会明确不做什么。
