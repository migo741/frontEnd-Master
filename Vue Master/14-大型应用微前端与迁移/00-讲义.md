# 第 14 章：大型应用、微前端与渐进迁移

> 稳定生产基线：Vue 3.5。本章把架构当成约束协作与变化成本的工具，不把“微前端”“DDD”“Vapor”当职位级别装饰。

## 1. 生产事故：拆成五个应用，发布反而更慢

一个 60 人前端团队认为单体太乱，于是按菜单拆成五个微前端。半年后：

- shell 和子应用各带一份 Vue、组件库、监控与请求层；
- 同一个“当前租户”有六份状态和三种刷新时序；
- 订单页需要同时升级客户、权限、计费三个子应用；
- 每个应用单独能跑，组合后路由、样式、焦点和错误边界才出问题；
- 一次登录协议变更要协调五个仓库，交付从一天变一周。

团队解决了“仓库很大”的表象，却没有解决业务边界和依赖，反而增加运行时分布式成本。更合理的路径通常是：

```text
先建立模块化单体
  → 业务边界、依赖方向、契约、所有权、测试清晰
  → 记录仍无法解决的组织/发布瓶颈
  → 只有满足条件的边界才提取为独立部署单元
```

## 2. 术语

| 术语 | 本章含义 |
| --- | --- |
| modular monolith | 单一部署/运行单元内按业务模块形成可执行边界 |
| bounded context | 某个业务模型和词汇保持一致的边界；不是简单目录名 |
| DDD-lite | 借用领域语言、边界、实体/值对象、应用服务等实用部分，不照搬全套仪式 |
| dependency rule | 明确哪些层/模块可以导入哪些对象，并由工具验证 |
| anti-corruption layer | 把 legacy/外部模型转换为新模型，防止污染扩散 |
| microfrontend | 多个可独立交付的前端单元在一个用户体验中组合 |
| shell | 组合层，常负责导航、身份入口、错误边界与公共体验 |
| contract | 跨单元稳定协议：路由、事件、API、版本、错误、性能、安全 |
| custom element | 浏览器自定义元素边界；Vue 可将组件包装为 custom element |
| strangler migration | 新能力逐步包围/替换旧系统，而非一次重写 |
| ADR | Architecture Decision Record，记录上下文、选项、决定、后果和复查触发条件 |

## 3. 模块化单体：先让边界可见且可执行

### 3.1 不按技术类型横切整个项目

低内聚结构：

```text
src/
├─ components/  # 全业务混放
├─ stores/
├─ api/
└─ utils/
```

更可控的业务切片：

```text
src/
├─ app/                  # composition root、router、providers
├─ modules/
│  ├─ orders/
│  │  ├─ domain/         # 纯规则与类型，不依赖 Vue/HTTP
│  │  ├─ application/    # 用例与端口
│  │  ├─ infrastructure/ # HTTP/storage adapter
│  │  ├─ ui/             # Vue 页面/组件/composable
│  │  └─ public.ts       # 唯一公开入口
│  ├─ customers/
│  └─ billing/
└─ shared/
   ├─ kernel/            # 少量稳定跨域值，如 Money/EntityId
   ├─ ui/                # design system adapter
   └─ platform/          # logging/feature flags 等端口
```

`shared` 不是垃圾桶。一个工具只有在语义稳定、至少有真实复用且没有领域偏见时才进入 shared。

### 3.2 依赖方向

```text
UI → application → domain
        ↑
infrastructure implements ports

orders --只能通过 customers/public.ts--> customers
```

domain 不导入 Vue、Pinia、fetch、浏览器或具体日期库。application 描述用例和 port：

```ts
// modules/orders/application/ports.ts
export interface OrderSummary {
  id: string
  customerId: string
  totalCents: number
  status: 'draft' | 'submitted' | 'paid'
}

export interface OrderRepository {
  get(id: string, signal?: AbortSignal): Promise<OrderSummary | null>
  submit(id: string, idempotencyKey: string): Promise<OrderSummary>
}
```

UI 注入 `OrderRepository`，测试可替换；infrastructure 将后端 DTO 校验/转换成领域类型。不要让页面到处调用共享 `request('/anything')`，那会绕过边界。

### 3.3 用工具执行规则

规则可以由 ESLint import restrictions、dependency-cruiser、构建 graph 或自定义 Vite plugin 验证：

- 禁止导入其他模块内部路径；只能用 `public.ts`；
- domain 禁止依赖 Vue/Pinia/browser/infrastructure；
- shared 禁止反向依赖 modules；
- app 可以组装所有模块，但不承载业务规则；
- 检测循环依赖、跨层 shortcuts 与未声明 public API。

架构图若不能使 CI 失败，数月后常只剩愿望。

## 4. DDD-lite：只引入能降低误解的部分

适合前端的实践：

1. 用业务语言命名 command/state，而非 `handleData`、`type=1`；
2. 把金额、时间区间、订单状态转换写成纯规则；
3. 以应用用例组织跨组件流程，如 `submitOrder`；
4. 后端 DTO 在 adapter 边界校验转换；
5. 用判别联合表达合法状态，避免十几个 boolean；
6. 模块事件表达已经发生的业务事实，而不是任意组件消息。

```ts
type CheckoutState =
  | { type: 'editing' }
  | { type: 'submitting'; idempotencyKey: string }
  | { type: 'succeeded'; orderId: string }
  | { type: 'failed'; reason: 'validation' | 'network' | 'conflict' }
```

不必在简单 CRUD 页面制造 aggregate factory/repository class 大军。DDD 的价值在复杂规则、多人协作与变化隔离；仪式成本也要进入 ADR。

## 5. 何时微前端才可能值得

至少同时观察以下信号：

- 团队有真实、长期且相对独立的业务所有权；
- 需要独立发布/回滚，当前单体 pipeline 是证据明确的瓶颈；
- 业务边界和 public contracts 已稳定；
- 跨边界同步交互少，能容忍版本并存与部分失败；
- 有平台团队承担 shell、契约测试、观测、安全与依赖治理；
- 收益大于重复 runtime、网络、调试、a11y 和一致性成本。

以下通常不是充分理由：仓库大、菜单多、想混用框架、主管希望“更先进”。Monorepo、增量构建、CODEOWNERS、模块边界和发布优化往往成本更低。

### 5.1 决策矩阵

| 维度 | 模块化单体 | 微前端 |
| --- | --- | --- |
| 原子跨模块变更 | 容易 | 需协议/兼容窗口 |
| 独立发布 | 较弱 | 强，但要付组合验证成本 |
| 运行时复杂度 | 低 | 高：加载、隔离、版本、失败 |
| 用户一致性 | 易统一 | 需平台治理 |
| 故障隔离 | 构建/模块级 | 可运行时隔离，也可由 shell 形成级联 |
| 适合团队 | 边界仍变化、协作密集 | 边界稳定、自治需求真实 |

## 6. 微前端契约：独立不是无约束

### 6.1 Shell 的最小职责

- 顶层导航、route ownership 与 404；
- 可信身份/session 的获取入口，但子应用的对象授权仍由服务端完成；
- 全局 design token、语言/时区、错误边界和观测上下文；
- 加载超时、fallback、版本/健康信息与回滚；
- overlay/focus 的跨应用协调（若允许跨边界 modal）；
- release、trace、应用名注入。

不要把所有业务状态塞进 shell 的全局 event bus。跨应用共享状态越多，独立部署越假。

### 6.2 契约清单

```ts
interface MicroAppManifest {
  name: string
  version: string
  entry: string
  routeBase: string
  requiredShellRange: string
  integrity?: string
  capabilities: readonly string[]
}

type ShellEvent =
  | { type: 'navigation.requested'; to: string }
  | { type: 'locale.changed'; locale: string }
  | { type: 'session.expired'; reason: 'unauthorized' | 'revoked' }
```

事件应有 schema、版本、发送者、幂等/顺序语义和 PII 规则。不要发任意 `{ type: string; payload: any }`。

还要约定：

- route 冲突与 deep link；
- shared dependencies 的版本/单例策略；
- CSS/token/name collision；
- auth/CSRF/CSP/SRI 与第三方供应链；
- loading/error/timeout/offline；
- 性能预算和预加载；
- contract test、组合 E2E、canary 与回滚；
- source map、trace id、日志字段和 ownership。

## 7. 集成方式与 Custom Elements

### 7.1 方式不是宗教

- 构建时 package：最简单、类型和 tree-shaking 好，但不能独立运行时发布。
- 运行时 module/remote：可独立部署，需版本、共享依赖、加载失败与信任治理。
- iframe：强隔离，适合低耦合/不可信内容；路由、尺寸、a11y、通信和一致体验更难。
- custom element：框架中立 DOM 契约，适合可嵌入 widget；复杂对象、SSR、表单、样式与依赖仍需设计。

### 7.2 Vue Custom Element

```ts
import { defineCustomElement } from 'vue'
import SupportWidget from './SupportWidget.ce.vue'

const SupportWidgetElement = defineCustomElement(SupportWidget)

if (!customElements.get('acme-support-widget')) {
  customElements.define('acme-support-widget', SupportWidgetElement)
}
```

对外尽量使用 attributes/properties 和标准 `CustomEvent`：

```ts
host.dispatchEvent(new CustomEvent('ticket-created', {
  detail: { ticketId },
  bubbles: true,
  composed: true,
}))
```

边界问题：

- attribute 只有字符串语义，复杂对象应使用 property 或受版本化的 JSON schema；
- Shadow DOM 提供样式隔离，也改变全局主题、portal、测试 selector 和无障碍关系；
- Vue runtime 是内嵌还是 external/shared，要用包体与兼容风险决策；
- host 页何时升级，旧 element 与新 shell 是否兼容；
- `CustomEvent.detail` 仍是不可信输入，宿主必须校验；
- widget 失败必须局部降级，不能拖垮 host。

## 8. Vue 2 / Legacy 渐进迁移

### 8.1 先盘点，不先重写

盘点矩阵：

- 页面流量/业务风险/变更频率/owner；
- Vue 2 API、filters、mixins、class components、私有库；
- router/store/UI library/SSR/build/test 的兼容性；
- 隐式 DOM contract、全局 event bus、直接 store mutation；
- 性能、错误和关键用户旅程基线；
- 可抽离的纯 domain/application code。

### 8.2 Strangler 路径

```text
建立行为基线与可观测
 → 升级构建/TypeScript/测试等地基
 → 用 adapter 隔离 legacy API
 → 按路由/业务切片迁移，不按文件类型迁移
 → 新旧通过窄契约通信
 → 灰度 + 对照指标
 → 删除旧切片和 adapter
```

可选策略包括 Vue 兼容构建、在同页挂独立 Vue 3 island、按路由切新应用、custom element widget。具体选择依赖 SSR、路由、全局库和发布能力。不要永久停在“两个框架都有但无人删除”的中间态；每个 adapter 要有 owner、指标和删除条件。

### 8.3 Anti-corruption layer

```ts
interface LegacyOrderDto {
  order_id: number
  state: 0 | 1 | 2
  amount: string
}

interface Order {
  id: string
  status: 'draft' | 'submitted' | 'paid'
  totalCents: number
}

export function mapLegacyOrder(dto: LegacyOrderDto): Order {
  const status = ({ 0: 'draft', 1: 'submitted', 2: 'paid' } as const)[dto.state]
  const totalCents = Math.round(Number(dto.amount) * 100)
  if (!Number.isSafeInteger(totalCents)) throw new Error('Invalid legacy amount')
  return { id: String(dto.order_id), status, totalCents }
}
```

新组件不理解 `state=2`，旧模型的变化止于 adapter。金额转换还应使用明确十进制策略；这里仅展示边界思想。

## 9. 版本策略：框架、平台与业务要分层

建议维护：

- 生产支持矩阵：Vue、Router、Pinia、Vite、Nuxt、Node、浏览器；
- lockfile 与自动依赖 PR，但升级按风险分组；
- canary/staging/feature flag 与明确 rollback；
- security patch SLA；
- 框架 minor/major 的 changelog、类型、构建、SSR、性能和消费者测试；
- 不在同一发布同时升级框架、重构架构、替换组件库且无隔离开关。

“始终最新”不是策略，“永不升级”也不是。策略要回答谁负责、多久评估、如何验证、何时强制、失败怎样回退。

## 10. ADR：把当时为何这样做留下来

```md
# ADR-0xx: 是否将 Billing 提取为微前端

## Status
Proposed / Accepted / Superseded

## Context
可测量的交付瓶颈、团队边界、变更耦合、约束。

## Decision drivers
独立发布、原子变更、性能、安全、平台成本、期限。

## Options
1. 继续单体并强化边界
2. package 化
3. runtime microfrontend

## Decision
选择及范围；明确不做什么。

## Consequences
正面、负面、风险、owner、预算。

## Validation / rollback
指标、契约测试、灰度、回退。

## Revisit triggers
团队/发布频率/边界发生什么变化时重审。
```

ADR 不是为已经决定的方案写宣传稿。必须保留被拒选项与代价。

## 11. Vapor Mode：前沿观察，不是当前生产默认

截至本课程调研截点，Vue 3.6 仍处于 RC；Vapor Mode 是显式 opt-in 的新编译/渲染路径，并且支持的是 Vue API 子集，和现有 vnode 组件互操作仍有需要验证的边界。因此本课程：

- 生产必修与项目基线仍使用 Vue 3.5 稳定路径；
- Vapor 只在独立实验、性能敏感叶子/页面或小型新应用评估；
- 不因为 benchmark 就全量迁移；先确认 API、库、Devtools、SSR/hydration、测试和错误语义；
- 建 canary、同场景 correctness/performance 对照和一键退回稳定编译模式；
- 禁止在一次架构迁移中同时把 Vapor 当必要前提。

评估实验：

```text
同一业务 fixture
  ├─ Vue 3.5 stable build
  └─ 3.6 RC + opt-in Vapor experiment

比较：功能、DOM/ARIA、SSR/hydration、错误、第三方库、bundle、CPU、memory
结论：采用 / 局部采用 / 等稳定版 / 拒绝，并记录版本与证据
```

RC 的 API 和限制可能改变。任何具体迁移方案都要重读所用版本官方 release notes，不能把本章文字当未来永久承诺。

## 12. 常见反例

1. **目录改名叫 domain 就完成 DDD**：没有领域语言、依赖规则和用例边界，仍是旧耦合。
2. **microfrontend 等于团队自治**：若契约、发布和服务端仍强耦合，只增加协调面。
3. **所有共享依赖都 singleton**：版本冲突和隐式全局状态会放大故障；需逐项决策。
4. **event bus 传所有数据**：无 schema/ownership，演变成分布式全局 store。
5. **重写比迁移干净**：没有行为基线和灰度，常在最后发现多年隐含规则。
6. **兼容层永久保留**：双模型长期存在，认知与测试成本持续上升。
7. **RC benchmark 直接变生产路线**：忽略 API 子集、生态、回滚和正确性。

## 13. 速记与自检

### 速记卡

- 先模块化单体，证明确有组织/发布问题再分布式。
- 业务切片 + `public.ts` + CI 依赖规则。
- DDD-lite 为减少模型误解，不为增加类。
- 微前端契约覆盖 route、identity、event、version、failure、security、a11y、performance。
- Custom Element 是 DOM 协议，不会消除版本和状态边界。
- Legacy 迁移：盘点 → 基线 → adapter → 业务切片 → 灰度 → 删除。
- ADR 保存上下文、替代方案、后果、验证和复查触发器。
- Vue 3.5 是稳定生产基线；3.6 RC/Vapor 只前沿观察与受控实验。

### 自检题

1. 模块化单体与普通“大单体”的可执行差异是什么？
2. 为什么 domain 不应导入 Vue/Pinia/fetch？
3. 哪些证据足以让微前端收益大于成本？
4. 跨应用“当前租户”应该怎样共享，哪些授权不能交给 shell？
5. Custom Element 的 attribute、property、event、Shadow DOM 各有何边界？
6. Strangler 迁移怎样防止永久双栈？
7. ADR 为什么要记录 rejected options 和 revisit triggers？
8. 为什么 Vue 3.6 RC/Vapor 不能成为本课程默认生产必修？
