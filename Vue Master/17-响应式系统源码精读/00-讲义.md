# 第 17 章：Vue 3.5.42 响应式系统源码精读

> 本章唯一源码基线：`vuejs/core` 标签 **`v3.5.42`**，发布提交 **`d63616c`**。  
> 不使用 `main`，不混入 Vue 3.6 的响应式重构，也不把早期教程中的 `WeakMap → Map → Set<effect>` 当作 3.5.42 的真实实现。

## 0. 为什么这一章必须固定版本

源码学习最危险的不是“看不懂”，而是把三个时代的实现拼成一个不存在的 Vue：

- 用 Vue 3 早期的 `Set<ReactiveEffect>` 解释依赖集合；
- 用 Vue 3.5 的 `Dep.version` 解释 computed；
- 又拿 Vue 3.6 `main` 的新结构补细节；
- 最后写出一份每句话单独看似合理、整体却无法对应任何 tag 的笔记。

Vue 3.5 的响应式系统已经采用**版本计数 + 双向链表依赖追踪**。`targetMap` 仍然存在，但它只负责从原始对象和 key 找到 `Dep`；一个 `Dep` 连接哪些订阅者，不再以 `Set` 为真实存储结构，而是通过 `Link` 节点组成订阅者链。

本章每个内部字段、调用顺序和测试结论均以以下固定入口为准：

- [v3.5.42 release](https://github.com/vuejs/core/releases/tag/v3.5.42)
- [reactivity/src 固定目录](https://github.com/vuejs/core/tree/v3.5.42/packages/reactivity/src)
- [reactivity tests 固定目录](https://github.com/vuejs/core/tree/v3.5.42/packages/reactivity/__tests__)

源码链接中的 `v3.5.42` 不能替换成 `main`。以后升级课程时，应新开版本差异说明，而不是静默改写旧章。

## 1. 学完本章，你应该获得什么能力

不是背出私有字段，而是具备四种能力：

1. 从一行 `state.count++` 手工追到 Proxy trap、`trigger()`、`Dep.notify()`、batch 和 effect scheduler；
2. 从一次 computed 读取手工追到消费者依赖收集、source deps 刷新和版本同步；
3. 面对“条件分支切换后仍被旧字段触发”“watch 泄漏”“Map 迭代异常”等故障，能定位到正确语义层；
4. 阅读下一个 patch 版本时，能通过测试、调用图和 benchmark 判断变化，而不是凭字段名猜测。

你不应该在业务代码里：

- 读取 `runner.effect.deps` 决策业务；
- 修改 `Dep.version`；
- 依赖 `EffectFlags` 的位值；
- import `packages/reactivity/src/dep.ts`；
- 假设链表顺序是公共契约；
- monkey patch Vue 私有方法后发布生产。

源码知识服务于排障、性能判断、框架贡献和更准确的 API 使用，不是鼓励业务层耦合内部实现。

## 2. 先分清“公共语义”和“内部实现”

### 2.1 可以依赖的公共语义

在当前 Vue 3.5 API 范围内，应用可以依赖：

- `reactive()` 返回能追踪读取、触发相关更新的代理；
- 对同一原始对象重复 `reactive()` 会得到稳定代理身份；
- `ref()` 通过 `.value` 读写并追踪；
- `computed()` 惰性求值，并在依赖未造成结果变化时避免无意义下游工作；
- `watch()`/`watchEffect()` 可停止，Vue 3.5 的 handle 还支持 pause/resume；
- watcher cleanup 在下一次执行前或停止时运行；
- `effectScope()` 能统一停止其中创建的 effect/watch/computed 相关副作用；
- 数组、Map、Set 的常用读取、迭代和变更具备响应式语义；
- `onTrack`/`onTrigger` 在开发调试场景提供依赖事件。

### 2.2 只能作为 v3.5.42 阅读事实的内部实现

以下都不是业务契约：

- `Dep`、`Link` 和 `Subscriber` 的具体字段；
- `nextDep/prevDep/nextSub/prevSub`；
- `activeLink/prevActiveLink`；
- `Dep.sc` 的计数方式；
- `globalVersion` 何时递增；
- `prepareDeps()` 使用 `-1` 作为哨兵；
- computed 的 flags 组合和 batch 链；
- `targetMap`、proxy cache map 的命名；
- effect 和 computed 的通知顺序细节；
- Map/Set 对迭代 key 的内部 symbol；
- runtime-core 如何向基础 watch 注入 scheduler。

内部事实可以帮助你解释本 tag，但升级后必须重新核对。

### 2.3 一个实用判断

问自己：

> 如果 Vue 在不改变文档行为的前提下把链表换成别的数据结构，我的业务代码会不会坏？

会坏，说明你依赖了内部实现；只有源码实验、框架测试或受控诊断工具才应这样做。

## 4. `reactive()`：先选代理，不在这里收集依赖

`reactive()` 的关键不是 `track()`，而是把目标交给哪组 handlers。

概念调用链：

```text
reactive(target)
  -> 如果 target 已 readonly，直接返回
  -> createReactiveObject(
       target,
       isReadonly=false,
       mutableHandlers,
       mutableCollectionHandlers,
       reactiveMap
     )
```

`createReactiveObject()` 依次处理：

1. 非对象：开发环境警告并原样返回；
2. 已经是合适代理：直接返回；
3. `__v_skip` 或不可扩展对象：原样返回；
4. 对应 WeakMap 已有 proxy：返回缓存；
5. 根据 raw type 分类；
6. Object/Array 使用 base handlers；
7. Map/Set/WeakMap/WeakSet 使用 collection handlers；
8. 创建 Proxy 并放入对应 proxy cache。

### 4.1 四套代理缓存

v3.5.42 中分别维护：

- `reactiveMap`；
- `shallowReactiveMap`；
- `readonlyMap`；
- `shallowReadonlyMap`。

因此“同一 raw 对象的 reactive proxy”和“readonly proxy”不是同一个对象；同一种转换重复调用则可命中缓存。

### 4.2 为什么 Date、RegExp、普通 class 不一定被代理

`targetTypeMap()` 明确只把 Object/Array 归为 COMMON，把四类集合归为 COLLECTION，其余类型 INVALID。普通 class instance 的 raw type 通常是 `Object`，可以被 base handlers 代理；但具有私有字段、内部槽或强身份语义的实例可能不适合代理，生产上常用 `markRaw()` 或 `shallowRef()` 保存第三方实例。

### 4.3 `toRaw()` 不是写入捷径

`toRaw()` 递归取回原始对象。对 raw 直接写不会经过 proxy trap，因此不会 trigger。短时读取、身份归一和框架内部处理可以使用；长期同时持有 raw/proxy 并混合写入会制造“数据变了但 UI 不变”的事故。

## 5. `baseHandlers.ts`：Object/Array 属性读取主线

考虑：

```ts
const state = reactive({ count: 0, nested: { ok: true } })
effect(() => console.log(state.count))
```

读取 `state.count` 的主路径：

```text
Proxy.get(rawState, 'count', receiver)
  -> 处理 ReactiveFlags 等内部 key
  -> 数组时先查 arrayInstrumentations
  -> Reflect.get(rawState, 'count', receiver)
  -> 排除内建 Symbol / 不追踪 key
  -> track(rawState, GET, 'count')
  -> shallow ? 原值 : ref 解包 / 嵌套对象懒代理 / 基本值原样
```

### 5.1 嵌套对象为什么是“访问时代理”

getter 拿到对象后才调用 `reactive(res)` 或 `readonly(res)`。这意味着深响应式不是创建根对象时遍历整棵图，而是在访问嵌套值时惰性转换，并通过 proxy map 保持身份。

### 5.2 ref 解包的数组例外

普通 reactive 对象属性若是 ref，getter 返回 `ref.value`；但 Array 的整数索引不解包：

```ts
const r = ref(1)
const obj = reactive({ r })
const arr = reactive([r])

obj.r       // 1
arr[0]      // Ref<number>，不是 1
arr[0].value
```

这是公共可观察语义；内部条件位于 base handler。

### 5.3 GET、HAS、ITERATE 是不同依赖

```ts
effect(() => state.count)          // GET count
effect(() => 'count' in state)     // HAS count
effect(() => Object.keys(state))   // ITERATE
```

`has` trap 调 `track(..., HAS, key)`；`ownKeys` 对对象使用 `ITERATE_KEY`，对数组使用 `length`。这些差异决定 ADD/DELETE 时应该唤醒谁。

## 6. 属性写入：先判断 SET 还是 ADD，再选择 Dep

`MutableReactiveHandler.set()` 并非一句 `Reflect.set + trigger`。它处理：

1. 取旧值；
2. 识别 Array 整数 key；
3. 深模式下把可归一的新旧值转 raw；
4. 若旧值是 ref、新值不是 ref、且不是数组整数位，写入旧 ref 的 `.value`；
5. 判断 key 原先是否存在；
6. `Reflect.set`；
7. 确保当前 target 是 receiver 对应的原始对象，避免原型链重复触发；
8. 新 key 发 ADD；
9. 已有 key 且 `hasChanged()` 发 SET；
10. 写入失败则不触发。

### 6.1 这个细节解释了对象属性的 ref 赋值

```ts
const n = ref(1)
const state = reactive({ n })

state.n = 2
```

在深 reactive 普通对象上，内部会写 `n.value = 2`，而不是把 raw 属性替换为数字。Array 整数索引例外，不做此转换。

### 6.2 `hasChanged` 使用值变化语义

同值赋值不 trigger。不要把“setter 被调用”与“响应式更新一定发生”混为一谈。

### 6.3 `deleteProperty`

只有删除成功且 key 原先存在才发 DELETE。DELETE 不只影响该 key 的读取订阅，还可能影响对象迭代订阅。

## 7. 真实依赖图：`targetMap` 后面是 Dep，不是 Set

v3.5.42 对普通 reactive 属性的路由层是：

```text
targetMap: WeakMap<rawTarget, Map<key, Dep>>
```

到这里，旧教程和真实实现仍有相似外形；关键差异从 `Dep` 开始。

真实多对多关系：

```text
Source side                              Subscriber side

Dep(count)                               Effect(render)
  subs tail ─┐                           deps head ─┐
             v                                      v
          Link A  <==============================> Link A
             ^                                      |
             |                                      v
          Link B  <==============================> Link C
             ^                                      |
             |                                      v
          ...                                    deps tail
```

每一条“某 Subscriber 依赖某 Dep”的边由一个 `Link` 实例表示。同一个 Link 同时位于两条双向链：

- `nextDep/prevDep`：从 Subscriber 看“我依赖哪些 Dep”；
- `nextSub/prevSub`：从 Dep 看“哪些 Subscriber 依赖我”。

### 7.1 三个核心实体

#### `Dep`

表示一个可订阅 source：

- 普通 reactive 对象的某个 key 有一个 Dep；
- 一个 RefImpl 自带一个 Dep；
- 一个 computed 自带一个面向消费者的 Dep；
- `version` 表示该 source 的变化版本；
- `subs` 指向订阅者链尾；
- `subsHead` 仅开发环境用于按原顺序发 onTrigger；
- `activeLink` 帮助当前追踪上下文复用 Link；
- `map/key/sc` 支持属性 Dep 无订阅者后的清理。

#### `Subscriber`

v3.5.42 中至少有两种重要实现：

- `ReactiveEffect`；
- `ComputedRefImpl`。

Subscriber 拥有 `deps/depsTail`、flags、`notify()`。这就是 computed 可以依赖其他 source 的原因：它本身也是订阅者。

#### `Link`

一条关系边，包含：

- `sub`：订阅者；
- `dep`：来源；
- `version`：本订阅者上次确认该来源时观察到的 dep version；
- 两组双链指针；
- `prevActiveLink`：嵌套追踪时恢复 Dep 的 activeLink。

### 7.2 为什么双链适合条件依赖

effect 可能本轮读 A，下轮读 B：

```ts
effect(() => {
  output = state.useA ? state.a : state.b
})
```

需要快速完成：

- 从 effect 侧遍历旧 deps；
- 复用本轮仍访问的 Link；
- 删除不再访问的 Link；
- 从旧 Dep 的 subs 链中 O(1) 摘除；
- 保留新的访问顺序。

双向指针使一条边可以从两侧拆除，无需在线性 Set/数组中搜索。

## 8. 第一次收集依赖：从 `effect()` 到 `Dep.track()`

固定 tag 中的主调用链：

```text
effect(fn)
  -> new ReactiveEffect(fn)
       -> 若 activeEffectScope 存在，登记到 scope.effects
  -> e.run()
       -> flags 加 RUNNING
       -> cleanupEffect(e)
       -> prepareDeps(e)
       -> 保存 previous activeSub/shouldTrack
       -> activeSub = e; shouldTrack = true
       -> fn()
            -> proxy get
            -> track(rawTarget, GET, key)
                 -> targetMap 找/建 Map
                 -> Map 找/建 Dep
                 -> dep.track()
       -> finally cleanupDeps(e)
       -> 恢复 activeSub/shouldTrack/flags
  -> 返回绑定 runner，并挂 runner.effect
```

### 8.1 `Dep.track()` 新建 Link

只有同时满足以下条件才追踪：

- 有 `activeSub`；
- `shouldTrack` 为 true；
- 当前订阅者不是该 Dep 所属的 computed 自己，避免自订阅。

没有可复用 activeLink 时：

1. `new Link(activeSub, dep)`；
2. 追加到 activeSub 的 deps 尾部；
3. `addSub(link)` 把它追加到 dep 的 subs 尾部；
4. 更新 subscriber counter；
5. 开发模式触发 `onTrack`。

### 8.2 `activeLink` 的作用

同一个 effect 执行过程中可能多次读取同一属性。`dep.activeLink` 指向当前追踪上下文对应 Link，可复用而不重复建边。嵌套 effect/computed 又需要恢复外层状态，因此 Link 保存 `prevActiveLink`。

不要把 activeLink 理解为“Dep 只能有一个订阅者”。它只是当前收集上下文的快速入口；完整订阅者仍在 subs 双链上。

## 9. 条件分支重跑：`prepareDeps()` 与 `cleanupDeps()`

这是本章最重要的机制。

### 9.1 重跑前：标记旧边待确认

`prepareDeps(sub)` 从 deps head 向后：

```text
for each old Link:
  link.version = -1
  link.prevActiveLink = link.dep.activeLink
  link.dep.activeLink = link
```

`-1` 不是 Dep 的真实版本，而是“本轮尚未重新访问”的哨兵。

### 9.2 重跑中：访问到旧 Dep 就复活 Link

若 `Dep.track()` 发现 activeLink 属于当前 subscriber 且 `link.version === -1`：

- 把 link.version 同步为当前 dep.version；
- 如果访问顺序改变，把此 Link 移到 subscriber deps 尾部；
- 不重复 addSub。

因此 deps 链最终顺序与最近一次实际读取顺序一致。

### 9.3 重跑后：删除未复活 Link

`cleanupDeps(sub)` 从旧 tail 逆向遍历：

- `version === -1`：本轮未访问；从 dep.subs 和 sub.deps 两侧删除；
- 其他 Link：保留，并据此重建 head；
- 恢复每个 Dep 的 previous activeLink；
- 更新 sub.deps 和 depsTail。

条件表达式从 `a` 切到 `b` 后，`a` 的 Link 会被拆除。后续写 `a` 不应再通知此 subscriber。

### 9.4 属性 Dep 的回收

`removeSub()` 在非 soft 移除时减少 `dep.sc`。计数归零且 Dep 记录了所属 map/key 时，会从 `depsMap` 删除这个 property Dep。raw target 仍活着，也不必永久保留曾经访问过的所有属性 Dep。

这是理解长寿命大对象内存行为的关键，但 `sc` 的精确语义仍是内部实现，不要用于业务监控。

## 10. 从 `state.count++` 到 effect 重跑

主链路：

```text
Proxy.set
  -> trigger(rawTarget, SET, 'count', newValue, oldValue)
       -> depsMap = targetMap.get(rawTarget)
       -> 选择 key 对应 Dep，以及必要的 iteration Dep
       -> startBatch()
       -> dep.trigger()
            -> dep.version++
            -> globalVersion++
            -> dep.notify()
                 -> startBatch()
                 -> 遍历 dep.subs
                 -> sub.notify()
                      -> 去重后 batch(sub)
                 -> endBatch()
       -> endBatch()
            -> flush batched effects
            -> effect.trigger()
                 -> paused ? 入 pausedQueueEffects
                 -> scheduler ? scheduler()
                 -> 否则 runIfDirty()
                      -> isDirty() 比较 versions
                      -> run()
```

### 10.1 `Dep.version` 与 `globalVersion`

- `Dep.version`：某一个 source 的局部版本；
- `globalVersion`：任意已触发响应式变化的全局版本信号，用于 computed 快速判断“全局是否完全没有变化”。

`Dep.trigger()` 同时递增两者。若对一个从未被追踪过、连 depsMap 都不存在的 raw target 调 trigger，源码也会推进 globalVersion 后返回。不要把 globalVersion 当精确 mutation 数：一次业务操作可能触发多个 Dep，也可能因同值赋值根本不触发。

### 10.2 batch 的两个目的

1. 用 `NOTIFIED` flag 对同一个 subscriber 去重；
2. 延迟到嵌套 batch 全部结束再调度普通 effects。

`Dep.notify()` 自身会嵌套 start/end batch，外层 `trigger()` 也有 batch。只有最外层 depth 回到零才 flush。

### 10.3 computed 和普通 effect 分开入队

源码维护 batched computed 与 batched ordinary subscriber 两条内部链。computed 的 notify 主要把自己标 dirty，并把其面向消费者的 Dep 继续通知；实际 computed 往往在消费者做 dirty check 或读取 `.value` 时刷新，而不是 mutation 时立即求值。

### 10.4 scheduler 不等于 Vue 组件队列本身

`ReactiveEffect` 只知道调用 `scheduler()`。组件 render effect 的 job queue、watch 的 pre/post flush 等在 runtime-core 层配置。不要从 `effect.ts` 直接推导所有 DOM 时序。

## 11. Dirty check：Link version 是“我上次看见的版本”

`isDirty(sub)` 沿 subscriber 的 deps 链检查：

```text
若 link.dep.version !== link.version
  -> dirty

若 dep 属于 computed
  -> 先 refreshComputed(dep.computed)
  -> 再比较 computed dep version 与 link.version
```

Link.version 不是 mutation 总数，也不是 effect 运行次数。它表示这个 subscriber 对这个 Dep 最近一次同步时观察到的版本。

### 11.1 为什么 computed 需要先 refresh 再判断下游

上游 source 变了，不代表 computed 的**输出**一定变：

```ts
const n = ref(1)
const parity = computed(() => n.value % 2)

n.value = 3
```

source version 变了，但 parity 仍为 1。如果 computed 刷新后结果通过 `hasChanged` 判断没有变化，它自己的 `dep.version` 不递增，下游 effect 可被 dirty check 挡住。

这就是“上游失效”和“下游值改变”不同。

---

## 12. computed：既是 Subscriber，也是 Source

`ComputedRefImpl` 的双重身份：

```text
source refs/reactive deps
       ↓ Link.nextDep 链
ComputedRefImpl（Subscriber）
       |
       | owns
       v
computed.dep（Source）
       ↓ Link.nextSub 链
render effect / watch / other computed
```

所以 computed 同时拥有：

- `deps/depsTail`：它读取的 source；
- `dep`：读取它 `.value` 的消费者；
- `_value`：缓存；
- `flags`；
- `globalVersion`；
- `fn` 和可选 setter。

### 12.1 读取 `.value`

顺序非常重要：

1. `computed.dep.track()`：先让外部 active subscriber 订阅此 computed；
2. `refreshComputed(this)`：必要时刷新缓存；
3. 若第一步得到 Link，把 `link.version` 同步为刷新后的 `computed.dep.version`；
4. 返回 `_value`。

若在刷新前就固定 Link version，第一次计算导致 dep.version 变化，会让消费者立刻误判 dirty。

### 12.2 notify 只标脏，不直接计算

source Dep 通知 computed 时，computed：

- 加 DIRTY；
- 若尚未 NOTIFIED 且不是自通知，则进入 computed batch；
- 返回 true，让调用方继续通知 computed 自己的 dep；
- 不在此处执行 getter。

### 12.3 `globalVersion` 快路径

computed 保存上次检查时的 globalVersion。若再次读取时全局版本完全没变，直接复用缓存，无需逐个扫描 deps。

若全局有变化，但不是它依赖的 source，才进一步用各 Link/Dep version 做精确 dirty 判断。

### 12.4 何时增加 computed.dep.version

刷新 getter 后：

- 首次求值；或
- `hasChanged(newValue, oldValue)` 为 true；或
- getter 抛错时，为确保后续状态正确；

才推进 computed 面向消费者的 dep version。普通 source 的失效只把 computed 标 dirty，不等价于 computed 输出版本增加。

### 12.5 无消费者 computed 的解绑

当 computed 的 dep 失去最后一个订阅者时，内部会清 TRACKING，并对 computed 的 source deps 做 soft unsubscribe，使其可被回收，同时仍保留 computed 自身的 deps 信息以支持惰性刷新。再次获得首个消费者时，`addSub()` 会重新启用追踪并订阅 source deps。

这是 3.5.42 的内部优化，不要依赖 computed 在无消费者时的具体链表形态。

## 13. `ref.ts`：ref 自己持有 Dep

普通 reactive 属性通过 `targetMap` 路由到 Dep；`RefImpl` 直接创建：

```text
RefImpl
  _rawValue  用于变化比较
  _value     对象值可能已 toReactive
  dep        new Dep()
```

读取 `.value`：`dep.track()`；写 `.value`：归一 raw、`hasChanged`、更新缓存，然后 `dep.trigger()`。

### 13.1 为什么同时保存 rawValue 与 value

```ts
const raw = {}
const proxy = reactive(raw)
const holder = ref(raw)

holder.value = proxy
```

深 ref 会把可转换值比较为 raw，避免 raw/proxy 表示不同却语义同一时无意义触发；对外 `_value` 又可返回 reactive proxy。

### 13.2 shallowRef

shallow ref 的 `_value` 直接保存输入，不把内部对象变 reactive。深改不会触发它自己的 Dep；`triggerRef()` 可显式触发。

### 13.3 customRef

factory 得到绑定到一个 Dep 的 `track` 和 `trigger`。防抖 customRef 必须在 getter 调 track、在真正提交新值时 trigger；若每次 getter 返回全新对象，即使没有 trigger，也可能因父组件重渲染造成子组件 prop 身份变化，这属于 API 设计问题，不是 Dep 漏触发。

### 13.4 toRef 的 property ref

`ObjectRefImpl` 通过源对象属性读写，`dep` getter 用 raw object + normalized key 查找真实 property Dep。数组整数 key 在 3.5 后续 patch 中有过修复，因此研究 bug 时必须 pin patch 版本，不能只写“Vue 3.5”。

## 14. 数组不是普通对象陷阱的简单合集

base handler 对 mutable array 优先返回 `arrayInstrumentations[key]`。原因包括：

- 数组读取方法可能访问大量 index；
- 返回项需要按 deep/shallow/readonly 规则包装；
- `includes/indexOf/lastIndexOf` 要兼容 raw/proxy 身份；
- `push/pop/shift/unshift/splice` 会隐式读写 length，容易自订阅和递归；
- 一次数组方法会触发多个底层 set，需要 batch。

### 14.1 `ARRAY_ITERATE_KEY`

优化读取方法通常对 raw array 追踪一个专用 `ARRAY_ITERATE_KEY`，而不是把每个元素访问都留给原始方法隐式追踪。任何数字索引变化会通知该 iterate Dep。

### 14.2 身份敏感查询重试 raw

```ts
const raw = {}
const arr = reactive([raw])
const observed = arr[0]

arr.includes(observed) // 应按实现的 raw/proxy 兼容逻辑工作
```

`searchProxy()` 先用原参数查 raw array；失败且参数是 proxy 时，再用 `toRaw(arg)` 重试。

这并不意味着你可以任意混用 raw/proxy 作为所有容器身份；它只是数组查询的特定兼容语义。

### 14.3 改变 length 的方法为何 pauseTracking

`push()` 内部会读取/写 length。若正在运行的 effect 因 push 意外订阅 length，后续触发可能递归。`noTracking()`：

```text
pauseTracking()
startBatch()
raw method applied with proxy receiver
endBatch()
resetTracking()
```

`pauseTracking` 阻止不该收集的内部读取；batch 合并多个底层触发。二者解决不同问题。

### 14.4 数组 trigger 选择

- 写 `length`：通知 length、ARRAY_ITERATE_KEY，以及被截断的索引 Dep；
- 写数字 index：通知该 index 和 ARRAY_ITERATE_KEY；
- ADD 新数字 index：还通知 length；
- delete 某 index：不会等同于改变 length；
- 非整数自定义属性：按普通对象 key 处理。

### 14.5 ref 索引不解包再次出现

数组回调方法会把元素按目标的 reactive/readonly/shallow 语义包装，但 `arr[index]` 对 ref 保持 ref。这类细节应由官方 tests 验证，不要凭“Vue 会自动解包 ref”概括所有上下文。

## 15. Map/Set：必须绕开原生内部槽限制

原生 Map 方法要求合法的 Map receiver，不能仅靠普通 Proxy get 后直接调用。因此 collection handler 返回一套 instrumentations。

### 15.1 `Map.get(key)`

内部会：

1. 取 collection raw target；
2. 计算 rawKey；
3. mutable 时根据 key 是否已是 proxy，可能同时追踪 key 与 rawKey；
4. 先查传入 key，再查 rawKey；
5. 按 shallow/readonly/reactive 包装返回值；
6. 处理 `readonly(reactive(Map))` 的内层追踪。

### 15.2 key iteration 与 value iteration 不同

```ts
effect(() => [...map.keys()])
effect(() => [...map.values()])
```

Map keys 只在新增/删除 key 时变化；设置已有 key 的 value 不应使 keys 语义变化。v3.5.42 用：

- `MAP_KEY_ITERATE_KEY`：Map 的 keys 迭代；
- `ITERATE_KEY`：values、entries、forEach、size 等集合观察。

trigger 规则：

- ADD：key Dep + ITERATE + Map key iterate；
- DELETE：同上；
- Map SET existing：key Dep + ITERATE；
- CLEAR：通知该 target depsMap 中全部 Deps。

### 15.3 Set.add 的 raw/proxy 身份

插桩会归一 value，并检查 raw/proxy 的现有身份，避免把同一对象的两个表示重复加入。开发模式还会在 collection 同时含 raw 和 reactive identity 时警告。

生产规则仍应简单：选定一种身份，通常通过 reactive API 操作并避免长期保存 raw 引用。

### 15.4 iterator 包装

collection iterator 的 `.next()` 会把 key/value 按 shallow/readonly/reactive 规则包装。Map entries 和默认 iterator 返回 pair，分别包装二者。

### 15.5 WeakMap/WeakSet

它们没有可枚举 size/iterator，因此只参与 get/has/set/add/delete 等适用路径，不存在全量迭代依赖。

## 16. watch 不是另一套响应式系统

固定 tag 的基础 `watch.ts` 最终创建一个 `ReactiveEffect(getter)`：

```text
watch(source, cb, options)
  -> 把 source 规范化为 getter
  -> 必要时包 traverse
  -> 创建 job
  -> new ReactiveEffect(getter)
  -> effect.scheduler = 注入 scheduler 或 job
  -> 首次 effect.run() 建 deps
  -> source trigger
  -> scheduler(job)
  -> job 检查 dirty
  -> effect.run() 得 newValue
  -> 比较 / deep / forceTrigger
  -> cleanup
  -> callback(new, old, boundCleanup)
```

### 16.1 source 规范化

- Ref：getter 读 `.value`；
- reactive object：通过 traverse 触达属性；
- source array：逐项处理 ref/reactive/getter；
- function + callback：function 是 getter；
- function + no callback：形成 watchEffect 风格 getter；
- 非法 source：开发警告。

### 16.2 watch reactive object 的深度

直接 watch reactive object 且未显式 deep，基础实现会深 traverse；`deep: false` 或 `0` 只 traverse root；Vue 3.5 支持数字深度。深 watch 的 old/new 常可能是同一个对象身份，因为 Vue 没为每次嵌套修改深拷贝快照。

### 16.3 `traverse()` 的成本

它根据 depth 访问：

- ref.value；
- 数组每项；
- Map/Set values；
- plain object 可枚举字符串 key；
- 可枚举 symbol key；
- 用 seen + depth 处理环和重复路径；
- 遇 `__v_skip` 停止。

对巨大图 `deep: true` 意味着每次收集都可能访问大量节点。优先 watch 精确 getter，或用数字 depth 限制。

### 16.4 cleanup 的真实生命周期

`cleanupMap` 是 `WeakMap<ReactiveEffect, cleanup[]>`。cleanup：

- callback 下一次真正执行前调用；
- watchEffect 下一次运行 getter 前调用；
- stop 时调用；
- 调用 cleanup 时要避免意外收集依赖。

Vue 3.5 的 `onWatcherCleanup()` 依赖当前同步 active watcher，因此必须在同步执行栈注册，不能在 `await` 后才调用：

```ts
watch(id, async (nextId) => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())
  const data = await load(nextId, controller.signal)
})
```

第三参数 `onCleanup` 是绑定到该 effect 的兼容入口；无论使用哪种，最好在第一个 await 前注册，代码意图最清晰。

### 16.5 `flush` 在哪里

`@vue/reactivity/src/watch.ts` 的 options 有 scheduler，没有组件 API 中熟悉的 `flush: 'pre' | 'post' | 'sync'`。主包 `watch()` 由 [`runtime-core/src/apiWatch.ts`](https://github.com/vuejs/core/blob/v3.5.42/packages/runtime-core/src/apiWatch.ts) 包装并注入队列策略。

所以：

- 响应式 core 决定 getter、dirty、cleanup；
- runtime-core 决定组件上下文中的调度时机和错误处理；
- DOM 更新顺序不能只读 reactivity/watch.ts 得出。

## 17. pause/resume：暂停执行，不是记录每一条事件

`ReactiveEffect.pause()` 加 PAUSED flag。触发时 effect 不运行，而是进入 `pausedQueueEffects: WeakSet`。

resume：

1. 清 PAUSED；
2. 若 WeakSet 中存在此 effect，删除；
3. 调 `trigger()`；
4. scheduler 或 dirty check 以当前最终状态执行一次。

因此暂停期间多次 mutation 通常会收敛为恢复时一次工作，不会按事件历史逐条 replay：

```ts
const handle = watch(source, callback)
handle.pause()
source.value = 1
source.value = 2
source.value = 3
handle.resume() // callback 观察最新值；不是保证收到 1、2、3 三个事件
```

如果业务需要审计每次事件，响应式 state 不是事件日志，应该使用 command/event/outbox。

EffectScope pause/resume 会递归处理子 scopes 和 effects。实现使用数组副本，是为了应对 resume/stop 期间 effect 列表变化。

## 18. `effectScope`：依赖关系解决“何时更新”，Scope 解决“活多久”

`ReactiveEffect` 构造时若存在 activeEffectScope，会加入 `scope.effects`。非 detached 子 scope 记录 parent，并进入 parent.scopes。

```ts
const scope = effectScope()

scope.run(() => {
  watchEffect(/* ... */)
  watch(source, /* ... */)
  onScopeDispose(() => closeSocket())
})

scope.stop()
```

stop 顺序概念上：

1. 标 inactive；
2. stop 自己登记的 effects；
3. 跑 cleanups；
4. stop child scopes；
5. 从 parent scopes 中解除引用；
6. 清 parent。

### 18.1 O(1) 子 scope 移除

子 scope 保存自己在 parent.scopes 的 index。单独 stop 时，parent pop 最后一个 scope，把它填到空位并更新 index，避免中间 splice 的线性移动。数组顺序因此不是公共契约。

### 18.2 detached scope

`effectScope(true)` 不自动挂父 scope。适合明确的应用级/资源级生命周期，但 owner 必须手工 stop。组件 composable 无理由 detached，极易在卸载后继续监听。

### 18.3 v3.5.42 的 async scope 边界

`on()/off()` 是 runtime 内部集成点，处理 active scope 恢复，固定 tag 中还考虑了异步 continuation 交错时从 active chain 中解除中间 scope。业务代码应使用 `scope.run` 和组件生命周期，而不是直接调用内部 on/off 编排异步上下文。

### 18.4 已停止 scope 内新建 effect

v3.5.42 的 `ReactiveEffect` 构造器会检查 active scope 是否仍 active；已停止时使新 effect 不再成为失控孤儿。这是 patch 级实现事实，也说明为什么“只看 3.5.0 文章”不足以排查 3.5.42 行为。

## 19. 一次完整手工追踪

使用：

```ts
const state = reactive({ useA: true, a: 1, b: 10 })
const selected = computed(() => state.useA ? state.a : state.b)

let output = 0
const runner = effect(() => {
  output = selected.value
})
```

### 19.1 首次执行

```text
E = outer ReactiveEffect
C = ComputedRefImpl

E reads selected.value
  selected.dep.track(E)
    -> Link EC，加入 E.deps 与 selected.dep.subs
  refreshComputed(C)
    C reads state.useA
      -> Dep(useA).track(C) -> Link CU
    C reads state.a
      -> Dep(a).track(C) -> Link CA
    selected output from undefined -> 1
      -> selected.dep.version 0 -> 1
  Link EC.version 同步为 1
```

最终：

```text
E.deps: selected.dep
C.deps: Dep(useA) -> Dep(a)
selected.dep.subs: E
Dep(useA).subs: C
Dep(a).subs: C
Dep(b): 尚不存在
output = 1
```

### 19.2 `state.a = 2`

```text
base set -> trigger Dep(a)
Dep(a).version++ / globalVersion++
notify C
  C 标 DIRTY，进入 computed batch
  selected.dep.notify() 通知 E
batch flush E
  E dirty check 遇到 computed dep
  refresh C
    getter 仍读 useA 与 a
    result 1 -> 2
    selected.dep.version++
  E 确认 dirty -> run
  selected.value 再读，命中已刷新缓存
  Link EC.version 同步
output = 2
```

### 19.3 `state.useA = false`

C 重算前：Link CU、CA 的 version 设为 -1。getter 新读取顺序：useA、b。

- CU 被复用并同步；
- 新建 CB；
- CA 保持 -1；
- cleanup 从 Dep(a).subs 与 C.deps 删除 CA；
- C.deps 顺序成为 CU -> CB；
- 若 Dep(a) 无其他 subscriber，property dep 可从 key map 删除。

此后 `state.a = 3` 不再通知 C；`state.b = 11` 才会更新 output。

### 19.4 一个重要误区

不要写成：

```text
WeakMap -> Map -> Set(computed)
切分支时把 Set 里的 computed 删除
```

这个描述漏掉：Link 双向关系、版本同步、访问顺序、computed source dep、soft unsubscribe、batch 与 dirty check。它可以作为十分钟自制响应式练习，却不是 v3.5.42 源码追踪答案。

## 20. 生产排障：先用公开调试能力，再进入固定源码

推荐顺序：

### 第一步：确认状态是否真的通过 proxy/ref 写入

- 是否持有 raw 并直接写？
- 是否用了 shallowRef 却深改？
- 是否解构 reactive 后丢失访问路径？
- 是否同值赋值？
- 是否把第三方实例 markRaw？

### 第二步：使用 `onTrack/onTrigger`

开发环境给 computed/watchEffect/effect 配置调试 hook，记录：

- target 类型或安全 ID；
- type：get/has/iterate、set/add/delete/clear；
- key；
- effect 名称；
- 不记录敏感值。

组件还有 renderTracked/renderTriggered 调试 hooks。不要在生产持续打印完整 target。

### 第三步：缩成 `@vue/reactivity` 最小复现

删除组件、DOM、Router、Pinia，只留下：

- reactive/ref/computed/watch/effect；
- 最少 source；
- 明确操作序列；
- 可断言输出；
- 当前 `vue` 和 `@vue/reactivity` 精确版本。

### 第四步：在 tag checkout 中写失败测试

优先复制到最相关的官方 spec 风格：

- conditional dep：effect/computed spec；
- arrays：reactiveArray spec；
- collections：collections spec；
- watch cleanup：watch spec；
- lifecycle leak：effectScope spec。

只有测试稳定复现，才考虑最小源码 patch。

## 21. 常见生产故障与源码路由

| 症状 | 先查公共用法 | 再看源码位置 |
|---|---|---|
| 条件切换后旧字段仍触发 | getter 是否真的不再读旧字段 | prepareDeps/cleanupDeps、Link order |
| computed 每次都重算 | getter 是否每次创建/读取全局变化 | globalVersion、isDirty、输出 hasChanged |
| computed 不更新 | raw 写、shallow、未读取 `.value` | baseHandlers/ref/Dep.track |
| push 导致递归 | effect 内是否修改自己依赖数组 | array noTracking、RUNNING/ALLOW_RECURSE |
| includes 找不到对象 | raw/proxy 身份混用 | searchProxy |
| Map keys effect 多/少触发 | 订阅的是 keys 还是 entries | MAP_KEY_ITERATE_KEY/ITERATE_KEY |
| watch 深对象很慢 | deep true 范围过大 | traverse depth/seen |
| watch 旧请求覆盖新请求 | 未注册 cleanup/无 generation | watch cleanup 生命周期 |
| pause 后没收到每条值 | 把 state 当事件流 | paused WeakSet 合并语义 |
| 组件卸载后仍运行 | detached/global scope 未 stop | effectScope parent/stop |
| 内存随动态 key 增长 | effect 条件依赖未释放或仍持有 scope | removeSub、dep.sc、scope owner |

源码定位不能替代业务层竞态模型。例如 watcher cleanup abort 旧 fetch 仍不能证明第三方 Promise 一定不 resolve，提交 state 时仍建议 generation/latest-wins。

## 22. Benchmark：测什么，不能证明什么

Vue 仓库包含 reactivity benchmarks。运行 benchmark 前：

1. 固定 tag、commit、Node、pnpm、机器电源模式；
2. 安装 frozen lockfile；
3. 先跑正确性测试；
4. warm-up；
5. 多轮运行，报告分布而不是一次最快值；
6. 对照未改动 baseline checkout；
7. 检查内存、GC、分支数据规模；
8. instrumentation 构建与 benchmark 构建分开。

### 22.1 不要在插桩后直接宣称性能回退

给每个 Dep/Link 分配字符串 ID、console.log、JSON 序列化，会严重改变对象大小、分配和热路径。插桩版用于解释调用链；性能比较必须关闭插桩，或让 baseline/patch 使用同等低成本计数器。

### 22.2 microbenchmark 不能证明组件更快

`Dep.track()` 纳秒级改进不一定改变真实页面，因为瓶颈可能是：

- 组件更新范围；
- DOM/layout；
- 大列表创建；
- 深 watch；
- 网络；
- 第三方组件。

框架 benchmark、应用 trace 和用户指标三者都要看。

### 22.3 patch 性能验收

至少同时证明：

- 目标 case 改善；
- 常见 steady-state 不回退；
- 条件依赖 cleanup 不回退；
- computed chain 不回退；
- array/collection 相关 case 不受影响；
- 内存/GC 没恶化；
- 全量 unit tests 通过。

## 24. 反例速查

| 错误说法/做法 | 问题 | 精确表达 |
|---|---|---|
| Vue 3 就是 WeakMap→Map→Set | 把旧教学实现冒充 3.5.42 | targetMap 到 Dep，Dep 通过 Link 双链连接 Subscriber |
| computed source 变了就立即重算 | 忽略 lazy refresh | 先 dirty/notify，读取或 dirty check 时刷新 |
| source 变了 computed 下游必跑 | 忽略输出 version | 输出未变时 computed.dep.version 可不变 |
| batch 是异步 nextTick | 混淆 reactivity batch 和 runtime queue | batch 内部去重；scheduler 可再入组件队列 |
| pause 会缓存每个中间值 | 把状态观察当事件日志 | paused effect 在 WeakSet 合并，resume 看最新状态 |
| deep watch 会保存旧快照 | 没有自动深拷贝 | old/new 可同身份；需要业务快照自行复制 |
| toRaw 后写更快 | 绕过 trigger | toRaw 是逃生口，不是写入 API |
| Map 所有迭代依赖相同 | 忽略 key-only 语义 | keys 用 MAP_KEY_ITERATE_KEY，value/entry 用 ITERATE_KEY |
| 读取源码私有字段做监控 | 升级即碎 | 公开 debug hooks + 固定版本实验 |
| 插桩 benchmark 变慢证明 patch 慢 | 测到了日志开销 | baseline/patch 同等无日志构建比较 |

## 26. 速记卡

### 一句话总模型

> v3.5.42 用 WeakMap/Map 把 raw target + key 路由到 Dep，再用一个 Link 同时挂在 Dep 的 subscribers 双链和 Subscriber 的 dependencies 双链；版本计数负责 dirty 判断，batch 负责去重调度，scope 负责生命周期。

### 三条主链

```text
READ:
proxy get -> track -> Dep.track -> Link -> Subscriber.deps + Dep.subs

WRITE:
proxy set -> trigger -> Dep.version/globalVersion -> notify -> batch -> scheduler/runIfDirty

RERUN:
prepare old links(-1) -> execute/refresh used links -> cleanup unused links
```

### computed

```text
source Dep -> Computed as Subscriber -> computed.dep -> consumer Subscriber
```

### 生命周期

```text
activeEffectScope -> captures ReactiveEffect -> pause/resume/stop -> cleanup child resources
```
