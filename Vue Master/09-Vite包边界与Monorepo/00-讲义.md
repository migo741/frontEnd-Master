# 第 09 章：Vite、包边界与 Monorepo——理解两套执行模型

> 生产基线：当前稳定 Vite + Vue 3.5。具体配置项会随 Vite 大版本演进，本章强调长期稳定的模型：开发按需转换，生产构建整图优化；插件参与生命周期；环境变量进客户端即公开；包边界必须由工具执行。

## 0. 事故现场：开发秒开，CI 构建爆炸，密钥还进了 JS

一个项目本地开发正常，生产却出现：

- 首屏加载一个 4.8MB 的 `vendor.js`；
- workspace 中装出两份 Vue，组件库 `inject` 失效；
- 从 `packages/ui/src/internal/theme.ts` 深导入，发布后文件移动导致应用崩溃；
- 开发者把服务端密钥改名为 `VITE_ADMIN_SECRET`，“方便前端请求”；
- CI 偶发使用旧缓存，产物与 lockfile 不一致。

这不是五个孤立配置错误，而是没有建立工程边界：

```text
source graph
  ├─ dev: browser ESM request -> Vite transform/plugin -> module
  │       dependencies -> pre-bundled cache
  └─ build: crawl whole graph -> transform -> tree shake -> chunk -> assets

workspace graph
  app -> feature -> shared/ui -> tokens
             X 反向导入 app/internal
```

高级工程化不是背配置，而是能解释“这段代码在哪个环境、被谁转换、成为哪个 chunk、从哪个公开入口被依赖”。

---

## 1. Vite 开发服务器：按浏览器需求转换

浏览器请求 `/src/main.ts` 时，Vite 解析并转换这个模块，重写 bare import，按需服务依赖。修改一个 Vue SFC 时，HMR 尽量只替换相应边界，而不是重新打整个 bundle。

```text
browser GET /src/App.vue
  -> resolveId
  -> load
  -> transform (Vue SFC plugin + other plugins)
  -> rewritten ESM + source map
  -> browser imports next modules
```

这解释了两个现象：

- 项目越大，开发启动不一定随全图线性变慢，因为源模块按需；
- 某些 CommonJS/大量小模块依赖在浏览器原生 ESM 下效率差，因此需要 dependency pre-bundling。

### 1.1 依赖预构建

`optimizeDeps` 通常完成：

1. 把 CommonJS/UMD 依赖转成 ESM 可消费形式；
2. 把包含数百内部模块的依赖合并，减少开发期请求；
3. 缓存结果，并根据 lockfile/config 等变化失效。

不要一遇到问题就把所有包手工塞进 `include/exclude`。先定位：

- 包是否错误声明 module/export？
- workspace linked package是否应当按源码处理？
- 同一依赖是否出现多版本？
- 条件导出是否选错 browser/import 分支？
- 缓存是否因 lockfile/config 变化而失效？

可以临时 `--force` 验证是否缓存问题，但不应把“每次强制重建缓存”当永久修复。

### 1.2 HMR 边界不是业务状态保存协议

Vue 插件能对组件热替换并尽量保留状态，但：

- 模块顶层副作用可能重复执行；
- singleton service 可能累积监听器；
- store HMR 需要按 Pinia 协议接受更新；
- `import.meta.hot.dispose` 应清理插件/模块级资源；
- HMR 行为不能代表完整刷新和生产构建行为。

重要流程仍要测冷启动、生产 preview 和部署后的旧 chunk 场景。

## 2. 生产构建：整张图上的静态优化

生产构建会遍历入口可达模块，完成转换、tree shaking、chunk 切分、资源处理、hash 和 manifest。当前 Vite 底层实现可能演进，但稳定概念是：**build 看到更完整的图，因此能做开发服务器不做的全局决策。**

### 2.1 Tree shaking 的前提

Tree shaking 依赖静态 ESM 结构和副作用声明：

```ts
// 更可分析
export function formatDate() {}
export function formatMoney() {}

// 动态访问让分析更保守
export default { formatDate, formatMoney }
```

`package.json` 的 `sideEffects` 错标为 false 会删除必要 CSS 或注册代码；不标又可能保留过多模块。组件库常见：

```json
{
  "sideEffects": ["**/*.css"]
}
```

具体要通过打包消费者 fixture 验证，不能只看库自身构建成功。

### 2.2 动态 import 形成异步边界

```ts
const TicketPage = () => import('./TicketPage.vue')
```

动态 import 允许 route-level split，但“切得越碎越快”是错的。每个 chunk 都有请求、调度、解析和压缩开销；共享依赖还可能重复或形成 waterfall。

以用户路径设计边界：

- 首屏关键路由尽量少瀑布；
- 低频重模块（图表、编辑器）延迟；
- 相同业务模块可聚合；
- 用真实网络和 Coverage/性能数据验证；
- 不把所有 node_modules 硬塞一个长期 vendor chunk，更新任一依赖都会让整块缓存失效。

### 2.3 `manualChunks` 是手术刀

错误配置：按包名生成数百 chunk，或一个巨型 vendor。合理配置来自指标：首屏下载/执行、重复依赖、缓存变更频率、请求瀑布。改动后比较构建可视化和真实导航，避免“产物文件变小了，但总执行更慢”。

## 3. Vite 插件生命周期

Vite 插件与 Rollup 插件接口有交集，同时存在 dev server 专属能力。核心 hooks：

| Hook | 问题 |
|---|---|
| `config` | 合并/修改用户配置 |
| `configResolved` | 读取最终配置、区分 command/mode |
| `configureServer` | dev server 中间件/HMR |
| `resolveId` | 把 import specifier 解析为模块 ID |
| `load` | 为某 ID 提供源码 |
| `transform` | 转换已有模块源码 |
| `handleHotUpdate` | 自定义 HMR 受影响模块 |
| build hooks | 产物生成、bundle 审查等 |

### 3.1 虚拟模块协议

用户导入公开 ID，插件内部使用以 `\0` 开头的 resolved ID，避免其他解析器当正常路径：

```ts
import buildInfo from 'virtual:build-info'
```

```ts
const publicId = 'virtual:build-info'
const resolvedId = '\0virtual:build-info'

export function buildInfoPlugin(info: BuildInfo): Plugin {
  return {
    name: 'ops:build-info',
    resolveId(id) {
      return id === publicId ? resolvedId : null
    },
    load(id) {
      if (id !== resolvedId) return null
      return `export default ${JSON.stringify(info)}`
    },
  }
}
```

必须用 `JSON.stringify` 生成字面量，不能把未经转义的 commit message 拼进 JS 源码。只暴露允许公开的 build id、时间、release channel；不要读取并导出整个 `process.env`。

### 3.2 插件顺序和 apply/enforce

插件可按 `enforce: 'pre' | 'post'` 调整转换阶段，按 `apply: 'serve' | 'build'` 限制场景。顺序冲突要用最小复现验证：一个插件 transform 的输入可能已经被前一插件改变。

插件应该：

- name 唯一且带 namespace；
- 对不处理的 ID 返回 `null`；
- 保留/生成正确 source map；
- 缓存以完整输入为 key；
- 生产构建不依赖 dev-only server 状态；
- 不在 import 时执行不可控网络调用。

## 4. 环境变量：进了客户端 bundle 就是公开信息

Vite 默认只向客户端暴露特定前缀（通常 `VITE_`）的变量，并通过 `import.meta.env` 替换。前缀是“允许公开”的标记，不是加密：

```ts
const apiBase = import.meta.env.VITE_API_BASE_URL // 用户可在产物中看到
```

绝不能暴露：数据库密码、云密钥、服务端签名 secret、私有 API token、管理凭证。

### 4.1 编译期配置与运行时配置

- 编译期：每个环境产一个 bundle，`import.meta.env` 可 tree shake；配置改变需重建。
- 运行时：容器启动或 HTML 请求时注入公开 config，同一镜像可跨环境；需要 runtime schema 和 CSP/XSS 安全序列化。

```ts
interface PublicRuntimeConfig {
  apiBaseUrl: string
  release: string
  sentryDsn?: string
}
```

“public”不等于“无风险”：Sentry DSN 等虽可公开，也要限制滥用、采样和 origin；feature flag 客户端值不能保护隐藏功能或密钥。

### 4.2 mode 不是 NODE_ENV 的同义词

Vite mode 决定加载哪些 `.env.[mode]`，生产/开发行为还与 command 和 `NODE_ENV` 相关。不要在自定义 `staging` mode 中想当然地推断所有依赖都是 development 或 production。把目标行为写进测试/构建脚本并打印脱敏摘要。

`.env.local` 等本机文件通常不提交；但“不提交”也不能挽救已经打进 bundle 的 secret。CI 应扫描产物和 source map 中的 secret pattern。

## 5. Alias 与边界：路径变短不等于架构变好

```ts
resolve: {
  alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) }
}
```

`@/` 让任何模块都能方便地深导入任何模块。它解决寻址，不解决依赖方向。需要规则：

```text
app/composition
  -> features/*/public
      -> domain + shared
  -> shared/ui

禁止：shared -> feature
禁止：feature-a -> feature-b/internal
禁止：任意层 -> app/internal
```

用 ESLint `no-restricted-imports`、dependency-cruiser、madge、自定义 architecture test 等执行。边界失败应在本地/CI 快速报错，而不是写在 wiki 里靠自觉。

## 6. Monorepo：一个仓库，不等于一个大泥球

### 6.1 每个包都要回答五个问题

1. 它的职责和 owner 是谁？
2. 公开入口是什么？
3. 允许依赖哪些层？
4. 是发布包、内部构建包还是仅源码包？
5. 版本、测试、构建缓存如何确定？

示例：

```text
apps/
  admin-web/
packages/
  ticket-domain/      # 无 Vue，纯领域
  ui/                 # Vue peer dependency
  api-contract/       # 生成 DTO/decoder
  tooling-eslint/
```

### 6.2 `exports` 是消费者防火墙

```json
{
  "name": "@ops/ui",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./tokens.css": "./dist/tokens.css"
  },
  "files": ["dist"],
  "sideEffects": ["**/*.css"],
  "peerDependencies": {
    "vue": "^3.5.0"
  }
}
```

只暴露 `.` 和明确 subpath，消费者无法依赖 `src/internal/*`。但 workspace 工具和 tsconfig alias 若绕过包名直接指向 src，仍会破坏发布真实性；要有“打包后 consumer fixture”测试。

### 6.3 Vue 应通常是 peerDependency

组件库把 Vue 打入自己 bundle，应用又有一份 Vue，可能导致：

- 体积重复；
- provide/inject 或 symbol identity 跨 runtime 失配；
- Devtools/响应式行为混乱。

库将 Vue 声明为 peerDependency，构建时 external；开发依赖可在 devDependencies 提供类型和测试。应用负责安装兼容版本。CI 用包管理器的 explain/list 检查是否多版本。

### 6.4 源码消费与预构建消费

- 源码包：应用 Vite 直接转 TS/Vue，开发联调快；要求工具链一致，发布语义弱。
- dist 包：更接近真实 npm 消费者，边界清晰；本地改动需构建/watch。
- 混合：开发条件导出 source、生产导出 dist，容易出现“dev 能跑 build 坏”，需要严谨条件和双通道测试。

选择一种作为正式契约，另一种必须有 CI 验证。不要让 `paths` 随意绕开 `exports`。

## 7. Library Mode：产物是给未知消费者的 API

应用构建可以假设自己的 HTML 和浏览器目标；库构建要考虑消费者：

```ts
export default defineConfig({
  build: {
    lib: {
      entry: resolve(__dirname, 'src/index.ts'),
      formats: ['es'],
      fileName: 'index',
    },
    rollupOptions: {
      external: ['vue'],
    },
  },
})
```

发布前检查：

- JS 格式和 `package.json type/exports` 一致；
- `.d.ts` 可被消费者解析，未泄漏内部路径类型；
- Vue 等 peer 未打包；
- CSS 是否独立、是否需要显式 import；
- `sideEffects` 不误删 CSS；
- sourcemap 是否含本机路径/源码隐私；
- `files` 只发布需要产物；
- 从 tarball 安装到空白 fixture，完成 build/typecheck/SSR（若声明支持）。

库不应读取宿主应用的 `import.meta.env` 私有约定；通过显式 options/provide 注入配置。

## 8. 构建缓存、CI 与可复现性

任务缓存 key 至少包含：

```text
source files
+ relevant package.json
+ lockfile
+ tsconfig/vite config
+ codegen schema/version
+ Node/package-manager version
+ allowlisted env inputs
```

漏掉 env/schema 会命中错误缓存；把所有环境变量都放 key 又降低命中率并可能泄密。只声明真正影响产物的输入。

CI 基线：

1. 固定 package manager 与 Node 大版本；
2. frozen lockfile 安装；
3. codegen 后检查工作区是否干净；
4. lint + typecheck + unit；
5. architecture tests；
6. build + bundle budget；
7. preview smoke/E2E；
8. library tarball consumer test；
9. 产物 secret/source map 扫描。

构建产物应带 release/build ID 供错误追踪，但不要带未脱敏 git remote、用户名或 CI secret。

## 9. 性能诊断顺序

开发慢：

1. 是冷启动、页面首次模块请求，还是 HMR 慢？
2. 查看插件耗时、transform 数、依赖预构建失效原因；
3. 是否有大 barrel 导致一改全失效？
4. 是否同时存在重复依赖/错误条件导出？
5. workspace 是否跨出 root 导致 watch 范围巨大？

生产慢：

1. 构建可视化看模块归属和重复；
2. 网络 waterfall + compression 后大小；
3. 主线程 parse/compile/execute，而非只看原始 KB；
4. 路由加载是否串行；
5. chunk cache 是否在小改动时整体失效；
6. 建预算并在 CI 阻止回退。

不要用“Vite 很快/很慢”代替阶段定位。

## 10. 反例速查

| 反例 | 后果 | 改进 |
|---|---|---|
| `VITE_SECRET` | secret 出现在 bundle | secret 留服务端 |
| 导出 `process.env` 虚拟模块 | 全量泄密 | 显式公开白名单 |
| 所有依赖一个 vendor chunk | 巨大执行/缓存联动 | 按用户路径和数据验证 |
| 每包一个 manual chunk | 请求碎片/瀑布 | 少量稳定异步边界 |
| `@/feature/internal` 任意导 | 架构无边界 | public entry + lint graph |
| workspace 直接深导 src | 发布后失效 | exports + consumer fixture |
| UI 包打入 Vue | 双 runtime | peer + external |
| `sideEffects:false` | CSS/注册代码被摇掉 | 精确声明 + 消费测试 |
| 永久 `optimizeDeps.force` | 每次冷启动变慢 | 找缓存/元数据根因 |
| 缓存 key 不含 lockfile | 错产物复用 | 声明完整输入 |

## 11. 速记与自检

> Vite 开发按需服务模块，生产在整图上优化；Monorepo 的价值不是共享一切，而是让依赖方向、公开入口和构建契约可执行。

你应能解释：

1. dev server 与 production build 为什么可能行为不同？
2. dependency pre-bundling 解决哪两类问题？
3. `resolveId/load/transform` 分别做什么？
4. 虚拟模块为什么使用公开 ID 与 `\0` 内部 ID？
5. 为什么任何 `VITE_` 变量都必须视为公开？
6. route dynamic import 怎样影响 chunk 图？
7. manualChunks 为什么必须用真实指标验证？
8. alias 为什么不是架构边界？
9. `exports`、ESLint 边界、consumer fixture 各防什么？
10. Vue 组件库为何通常把 Vue 设 peer/external？
11. `sideEffects` 标错会发生什么？
12. 构建缓存 key 为什么既不能少也不能包含全部 env？

给 AI 的追问锚点：

- “请用一次 import 请求画出 Vite dev 的 resolve-load-transform 链路。”
- “请比较源码 workspace 包与 dist workspace 包的失效模式。”
- “请给我一个双 Vue runtime 导致 inject 失败的最小因果解释。”
