# 第 09 章：Vite、包边界与 Monorepo

## 理解工具链的工作阶段

Vite 开发时利用原生 ESM 与依赖预构建，生产构建走打包器。常见问题应先区分 dev server、transform、bundle、chunk、asset 和 runtime；“开发没问题、生产白屏”往往涉及 base path、动态 import、环境变量、浏览器目标或依赖副作用。

插件钩子要用最小范围：resolveId 决定模块身份，load 提供内容，transform 变换已有模块。虚拟模块应使用 `virtual:` 公共 id 和 `\0` 内部 id，避免被其他解析器当真实路径。

## 包边界

按领域/feature 组织比 components/utils 大仓库更能限制依赖。每个 feature 暴露 public API，禁止跨 feature 深层 import。共享包分 design-system、domain contracts、infra 等，避免一个 `shared` 垃圾桶。

Monorepo 只在多包独立发布、跨应用复用或工具链统一有收益；单应用强拆包会增加版本、构建与协作成本。用 workspace protocol、统一 lint/typecheck/test，明确 peerDependencies 和 exports。

## 质量门禁

本地格式化只是体验；CI 才是事实。建议门禁：lockfile frozen install、lint、`vue-tsc`、unit/component tests、production build、关键 E2E、bundle/performance budget、依赖与 secret 扫描。Husky 不能替代 CI，因为 hook 可跳过。

## 环境与配置

所有 `VITE_*` 都可能进浏览器 bundle。配置在启动时做 schema 校验，区分 build-time 与 runtime config。不要为每个客户重打包同一镜像时把租户配置烘焙进 bundle，可由受控 `/config.json` 注入非敏感运行时配置。
