# 第 12 章：SSR、Hydration 与 Nuxt 4

> 稳定生产基线：Vue 3.5 与 Nuxt 4 稳定版。本章要求你能解释“一次请求从边缘/Node 到浏览器接管”的完整状态流，而不只是会写 `useFetch`。

## 1. 生产事故：A 公司看见了 B 公司的名字

某 B2B 控制台为了 SEO 和首屏速度迁到 SSR。上线后出现四个现象：

- 极少数用户首屏闪过另一家公司的名称；
- 控制台反复出现 hydration mismatch；
- `/api/profile` 在服务端和浏览器各请求一次；
- CDN 把已登录页面缓存给下一位用户。

根因并非“SSR 不稳定”：开发者在模块顶层创建了一个全局 reactive store，使所有请求共享状态；模板直接渲染 `Date.now()` 和浏览器时区；客户端没有复用服务端 payload；缓存头把个性化 HTML 标为 public。

这类事故说明 SSR 的首要问题不是 API，而是**隔离、一致性、传输与缓存边界**。

```text
HTTP request A ─┐
                ├─ 若共享模块级状态 → A/B 污染 → 数据泄漏
HTTP request B ─┘

server render tree
  + serialized state/payload
  + HTML
        ↓ 网络
client 用同一输入产生同一初始 tree
        ↓
hydrate：复用已有 DOM，并挂事件/建立响应式
```

## 2. 术语与心智模型

| 术语 | 准确定义 |
| --- | --- |
| SSR | 在服务器把组件树渲染成 HTML；不等于数据天然安全或无需客户端 JS |
| CSR | 浏览器下载 JS 后创建主要 UI；可与 SSR/SSG 混合 |
| SSG / prerender | 构建时生成 HTML，适合内容在构建间稳定的页面 |
| Hydration | 客户端把响应式和事件连接到服务器已有 DOM，而不是从零重建 |
| mismatch | 客户端首次期望的 vnode/DOM 与服务端 HTML 不一致 |
| request isolation | 每个请求拥有独立 app、router、store 与可变上下文 |
| payload | 服务端安全序列化给客户端、用于接管和避免重复取数的数据 |
| universal rendering | 同一页面先服务器渲染，再在客户端 hydrate |
| hybrid rendering | 不同路由选择 SSR、CSR、prerender、缓存/边缘策略 |
| Nitro | Nuxt 的服务端引擎，提供 server routes、middleware 与多运行时部署 |
| edge | 在边缘运行时执行服务端逻辑；通常有 API、CPU、连接与包体限制 |

## 3. 原生 Vue SSR：先看见框架替你做了什么

### 3.1 每请求 app factory

共享代码必须返回新实例：

```ts
// app.ts
import { createSSRApp, type App } from 'vue'
import { createMemoryHistory, createRouter, type Router } from 'vue-router'
import Root from './Root.vue'
import { routes } from './routes'

export interface AppContext {
  app: App<Element>
  router: Router
}

export function createApp(): AppContext {
  const app = createSSRApp(Root)
  const router = createRouter({
    history: createMemoryHistory(),
    routes,
  })
  app.use(router)
  return { app, router }
}
```

服务端为每个请求调用它：

```ts
// entry-server.ts
import { renderToString } from '@vue/server-renderer'
import { createApp } from './app'

export async function render(url: string): Promise<string> {
  const { app, router } = createApp()
  await router.push(url)
  await router.isReady()
  return renderToString(app)
}
```

客户端也用同一工厂，但采用浏览器 history 的项目通常会把 history 创建参数化。关键点是 `createSSRApp(...).mount('#app')` 看到服务端 DOM 后执行 hydration：

```ts
// entry-client.ts
import { createApp } from './app'

const { app, router } = createApp()
await router.isReady()
app.mount('#app')
```

上例用于展示生命周期。生产方案还必须：匹配 browser/memory history、转义 HTML shell、序列化状态、处理 redirect/status/headers、收集 preload links 与流式错误。通常使用 Nuxt 而非手搭全套。

### 3.2 危险的模块级 singleton

```ts
// ❌ Node 进程内所有请求共享
export const session = reactive({ organizationName: '' })
```

正确方式之一是每请求创建并注入：

```ts
import { inject, provide, reactive, type InjectionKey } from 'vue'

interface SessionState {
  organizationName: string
}

const sessionKey: InjectionKey<SessionState> = Symbol('session')

export function installSession(name: string): void {
  provide(sessionKey, reactive({ organizationName: name }))
}

export function useSession(): SessionState {
  const session = inject(sessionKey)
  if (!session) throw new Error('Session is not installed')
  return session
}
```

更常见是 app factory 内创建 Pinia，并只序列化允许公开给浏览器的数据。服务端 secret、原始 cookie、内部 token 不属于 payload。

## 4. Hydration 一致性的因果链

Hydration 要求两端**第一次渲染**在结构和文本上等价：

```text
服务端输入 S ─→ render(S) ─→ HTML H
客户端输入 C ─→ render(C) ─→ 期望 H'

若 S ≠ C，或 render 含随机/时间/环境副作用
                ↓
H ≠ H' → mismatch → 警告、节点修复、事件错位或视觉闪烁
```

常见来源：

1. 模板中调用 `Math.random()`、`Date.now()`、随机 UUID；
2. 服务端 UTC、客户端本地时区导致格式不同；
3. 首次 render 读取 `window`、viewport、localStorage、媒体查询；
4. 无效 HTML 被浏览器 parser 自动纠正，如 `<p><div>…</div></p>`；
5. 服务端和客户端使用不同数据或排序不稳定；
6. 第三方库在 import 时访问 DOM 或修改 DOM；
7. 条件分支只在一端成立；
8. payload 序列化丢失 `Date`、`Map`、`undefined` 等语义。

### 4.1 确定性与延迟到 mounted

服务端需要的随机值必须生成一次并随 payload 传输；仅浏览器需要的 UI 才延迟：

```vue
<script setup lang="ts">
import { onMounted, ref } from 'vue'

const mounted = ref(false)
const compact = ref(false)

onMounted(() => {
  mounted.value = true
  compact.value = window.matchMedia('(max-width: 640px)').matches
})
</script>

<template>
  <nav v-if="mounted" :class="{ compact }">...</nav>
  <nav v-else aria-hidden="true" class="nav-skeleton">...</nav>
</template>
```

这会牺牲该区域 SSR 的真实内容，因此不应滥用。更好的响应式布局通常交给 CSS；只有行为确实依赖浏览器能力时才延迟。

### 4.2 时区策略

可选策略：

- 服务端和首次客户端都显示显式 UTC，mounted 后再切用户时区；
- 用户时区由 cookie/偏好在请求前已知，两端使用同一值；
- 首屏显示稳定占位，同时保留尺寸避免 CLS。

不要在 hydration warning 上直接使用“忽略 mismatch”作为默认修复；先证明差异是不可避免且无安全/交互后果。

## 5. Nuxt 4 的渲染模式：按路由选，而不是信仰统一答案

```text
营销/文档：prerender 或带失效的缓存 SSR
商品详情：SSR/ISR/SWR，关注 SEO 与新鲜度
登录后控制台：SSR 或 CSR，严禁 public cache 个性化 HTML
浏览器重型编辑器：client-only 岛/路由，提供可理解 fallback
低延迟读请求：可考虑 edge，但先核对运行时限制
```

Nuxt 可通过 route rules 为不同路径配置策略。概念示例：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },
    '/blog/**': { swr: 3600 },
    '/dashboard/**': { ssr: true, headers: { 'cache-control': 'private, no-store' } },
    '/editor/**': { ssr: false },
  },
})
```

具体可用字段与部署适配器要以所用 Nuxt/Nitro 版本为准。`ssr: false` 并非“性能更好”的同义词；它把首屏内容与数据工作移给浏览器，并影响 SEO、弱机体验和错误边界。

## 6. `useFetch`、`useAsyncData`、`$fetch` 与 payload

### 6.1 选择规则

- `$fetch`：一次普通请求；若直接在页面 setup 中两端执行，可能服务端一次、客户端又一次。
- `useFetch`：对 URL 请求的 SSR-aware 封装；将结果放入 Nuxt payload，客户端 hydrate 时复用。
- `useAsyncData`：包裹任意异步函数，并用稳定 key 管理去重、缓存、状态和刷新。
- `useState`：SSR-safe 的跨组件状态；工厂按请求初始化并序列化到 payload。

```vue
<script setup lang="ts">
interface OrderSummary {
  id: string
  totalCents: number
}

const route = useRoute()
const page = computed(() => Number(route.query.page ?? 1))

const { data, status, error, refresh } = await useFetch<{
  items: OrderSummary[]
  total: number
}>('/api/orders', {
  query: { page },
  key: 'orders:list',
  watch: [page],
})
</script>
```

key 必须表达缓存身份。若两个调用共用 key，却有不同 handler/options，可能共享错误数据；若 key 包含随机值，则无法复用 payload。

### 6.2 `useAsyncData` 的可控副作用

```ts
const tenantId = useState<string>('tenant-id')

const { data: report } = await useAsyncData(
  () => `report:${tenantId.value}`,
  () => $fetch('/api/report', { query: { tenantId: tenantId.value } }),
  { watch: [tenantId] },
)
```

handler 应尽量是幂等、可重复的取数函数。发邮件、扣款、写审计日志等命令不能因 SSR、刷新或 retry 被隐式重复。命令应由显式用户动作提交，并设计幂等键。

### 6.3 Payload 不是秘密保险箱

浏览器最终能看到 payload。只放 UI 需要且允许用户看到的数据，避免：

- access token、数据库字段、内部风控原因；
- 整个大对象导致 HTML 和解析成本膨胀；
- 不安全字符串拼接造成 `</script>` 等序列化注入；
- 不可序列化对象导致两端语义不同。

使用框架提供的安全序列化通道，不手写 `JSON.stringify(state)` 拼进 `<script>`。

## 7. `useState` 与跨请求隔离

Nuxt 中不要用模块顶层 `ref` 保存请求状态：

```ts
// ❌ server process 中可能跨请求共享
const currentTenant = ref<string | null>(null)
```

使用命名且可序列化的 state：

```ts
export function useCurrentTenant() {
  return useState<{ id: string; name: string } | null>(
    'current-tenant',
    () => null,
  )
}
```

`useState` 解决的是 Nuxt 请求上下文中的安全状态与 hydration 传输，不等于任何全局缓存都安全。模块级 LRU 若缓存公开内容可以存在，但 key 必须含租户/语言/权限等所有影响结果的维度，并有容量、TTL 与清除策略；个性化敏感数据通常不应进进程公共缓存。

## 8. Nitro server routes：BFF 也要有边界

```ts
// server/api/orders/[id].get.ts
interface UpstreamOrder {
  id: string
  ownerId: string
  totalCents: number
  internalRiskScore: number
}

export default defineEventHandler(async (event) => {
  const user = await requireUser(event)
  const id = getRouterParam(event, 'id')
  if (!id) throw createError({ statusCode: 400, statusMessage: 'Missing id' })

  const upstream = await $fetch<UpstreamOrder>(`https://internal/orders/${id}`, {
    headers: { authorization: `Bearer ${useRuntimeConfig(event).serviceToken}` },
  })

  if (upstream.ownerId !== user.id) {
    throw createError({ statusCode: 404, statusMessage: 'Order not found' })
  }

  setHeader(event, 'cache-control', 'private, no-store')
  return { id: upstream.id, totalCents: upstream.totalCents }
})
```

代码强调四件事：身份在服务端验证；对象级权限不是前端按钮控制；secret 来自私有 runtime config；响应 DTO 不泄漏内部字段。真实项目还应做输入 schema 校验、超时/取消、request id、审计、速率限制与统一错误映射。

## 9. SEO、缓存与安全是一套联合设计

### 9.1 SEO

SSR 只提供可抓取 HTML 的机会。仍需正确：

- 唯一 title/description、canonical、语言替代；
- 语义 HTML 与结构化数据；
- 真实 HTTP status（404 不能返回 200 的错误页面）；
- sitemap/robots 以及分页策略；
- 内容与 hydration 后一致，避免爬虫看到占位。

Nuxt 页面可用 `useSeoMeta`，动态内容必须源于同一份已校验数据。

### 9.2 缓存矩阵

| 内容 | 常见策略 | 关键风险 |
| --- | --- | --- |
| 带 hash 静态资源 | `public, max-age=..., immutable` | 部署清理错误 |
| 公共文章 | CDN/SWR/按 tag 失效 | 陈旧内容、语言 key 缺失 |
| 商品公共详情 | 短 TTL + stale/revalidate | 价格/库存新鲜度 |
| 登录后 HTML/API | `private, no-store` 或严格用户私有缓存 | 跨用户泄漏 |
| 含 cookie 差异的公共响应 | 正确 `Vary` 或避免共享缓存 | cache key 爆炸/串值 |

不要把 `Vary: Cookie` 当万能药；它可能几乎消灭命中率且仍难审计。优先明确公共与私有边界。

### 9.3 SSR 安全

- Vue 默认插值会转义文本；`v-html` 仍需要可信、经过专业 sanitizer 的内容。
- 不把未经安全序列化的用户输入拼入 HTML shell/script。
- Cookie 采用合适的 HttpOnly、Secure、SameSite；状态改变请求考虑 CSRF。
- 服务端 fetch 不接受用户任意 URL，防 SSRF；使用 allowlist/固定上游。
- 客户端 runtime config 是公开的；真正 secret 只能在服务端。
- 错误页不能把 stack、路径、上游响应和 token 发给浏览器。

## 10. 调试与测试

### 10.1 mismatch 排查顺序

1. 保存服务器原始 HTML，不要只看 hydration 后 Elements。
2. 记录客户端首次 render 使用的 payload、locale、timezone、feature flag。
3. 从第一处 mismatch 向上找结构差异；后续警告可能是连锁反应。
4. 检查随机、时间、DOM API、无效 HTML、排序与序列化。
5. 禁用第三方组件或缩成最小 tree。
6. 分别测无 JS HTML 与 hydrate 后交互。

### 10.2 必备测试

- 两个并发请求使用不同用户，HTML/payload 不可交叉；
- SSR HTML 与 hydration 后关键文本/结构一致，控制台无 mismatch；
- `useFetch/useAsyncData` 在首次导航不重复请求；
- 404/redirect/status/header 正确；
- public/private cache 规则与 tenant key 正确；
- JS 加载失败时，服务端内容仍可理解；
- Nitro route 的身份、对象级权限、输入校验、上游超时都有测试。

## 11. 常见反例与边界

1. **所有页面都 SSR**：登录后高交互页面未必受益，成本包括服务器容量、TTFB、hydration 和双环境约束。
2. **所有页面都 CSR**：营销、内容和弱机首屏可能付出明显代价。
3. **用 `process.client` 包住所有 mismatch**：掩盖输入不一致，且产生空白/CLS。
4. **模块级 ref 做缓存**：没有 request/tenant identity，可能直接泄漏。
5. **页面 setup 直接 `$fetch`**：两端执行可能重复取数；应选 SSR-aware API 或明确仅客户端执行。
6. **把 Nitro 当授权代理的自动替代**：server route 也必须鉴权、授权、校验与裁剪 DTO。
7. **Edge 是更快的 Node**：运行时 API、依赖、连接、CPU 与地域数据源都可能不同。

## 12. 速记与自检

### 速记卡

- SSR 四条主线：隔离、一致、传输、缓存。
- 每请求创建 app/router/store；公共缓存必须显式定义 identity。
- Hydration 比较两端第一次 render，不是最终稳定后的 DOM。
- `useFetch/useAsyncData` 用 payload 避免重复取数；key 就是缓存协议。
- `useState` 可按请求初始化，但 payload 对浏览器可见。
- route rules 让路由选择渲染策略；不要全站一刀切。
- 个性化页面默认拒绝 public cache。
- Nitro BFF 仍需身份、对象权限、schema、DTO、安全头与观测。

### 自检题

1. 为什么 app factory 能阻止跨请求状态污染？
2. 时间、随机数和时区分别如何制造 mismatch，怎样传递确定性？
3. 页面 setup 中 `$fetch` 与 `useFetch` 的首次导航行为有何不同？
4. `useAsyncData` 的 key 缺租户维度会发生什么？
5. 为什么 payload 中不能放 secret，即使 HTML 经 HTTPS 传输？
6. 哪些页面适合 prerender、SWR、SSR、CSR？依据是什么？
7. 如何写一个并发请求测试来证明 request isolation？
8. CDN 缓存 SSR 页面时，哪些 header/key 错误会造成跨用户泄漏？
