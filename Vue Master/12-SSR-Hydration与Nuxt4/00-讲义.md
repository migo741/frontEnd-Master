# 第 12 章：SSR、Hydration 与 Nuxt 4

## 为什么 SSR 更难

SSR 在服务端把组件树渲染为 HTML，客户端用同一逻辑 hydrate 并接管事件。它改善首屏/SEO 的潜力伴随新边界：浏览器 API 不存在、请求状态必须隔离、服务端与客户端首次输出必须一致、数据不能重复请求、缓存不能串用户。

Nuxt 4 提供文件路由、server engine、data fetching 和约定，但高级工程师必须理解约定背后的请求生命周期，而不是只会 `useAsyncData`。

## Hydration mismatch

常见来源：`Date.now/Math.random`、时区/locale、服务端无 window 导致分支不同、无效 HTML 被浏览器纠正、第三方库改 DOM、请求数据不一致。修复首选让两端输入确定一致；客户端专属内容可 mounted 后显示。`data-allow-mismatch` 只用于不可避免且理解后果的差异，不是关闭报警按钮。

Vue 3.5 的 lazy hydration 可按 idle/visible/interaction 等策略推迟异步组件接管，减少首屏工作，但被延迟组件在 hydrate 前不可交互，策略必须匹配 UX。

## 请求隔离与缓存

每请求创建 app/router/store。缓存分 CDN/public、服务端数据 cache、用户私有 cache；key 必须包含所有影响输出的维度，私有响应不能被公共缓存。序列化 payload 要转义 `</script>` 等注入向量。服务端 token 不能泄到客户端 payload。
