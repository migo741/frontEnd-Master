# 第 15 章：综合项目、生产交付与高级面试

> 这一章不是再堆知识点，而是把前 14 章变成可审查的工程证据。高级工程师的作品应让别人看见：你如何限定问题、设计契约、处理失败、验证假设、交付上线并解释取舍。

## 1. 为什么“功能都能点”还不够

某候选人的项目有登录、列表、详情、增删改查和漂亮动画。但面试追问后发现：

- 所有状态都进一个 Pinia store；
- token 保存在 localStorage；
- route guard 只隐藏按钮，API 没有对象级授权；
- 搜索乱序时旧结果覆盖新结果；
- 10,000 行全部挂 DOM；
- 测试只有三张 snapshot；
- SSR 页面跨请求共享状态；
- 没有 release、指标、回滚或事故记录。

这仍是 demo，不是生产工程。生产质量由多个相互约束的证据组成：

```text
业务结果与不变量
  ↓
边界/状态/失败模型
  ↓
实现与可访问交互
  ↓
测试 + 性能 + 安全 + SSR 证据
  ↓
构建/发布/观测/回滚
  ↓
事故复盘与架构答辩
```

## 2. 本章综合项目：FlowOps 多租户运营台

建议只做一条深 vertical slice，而不是十个浅页面：

```text
登录态已由可信服务建立
 → 选择租户
 → 查询/筛选工单
 → 打开工单详情
 → 分配处理人（权限 + 并发冲突）
 → 添加评论（乐观体验 + 幂等提交）
 → 实时看到状态变化
 → 错误可恢复、操作可审计
```

### 2.1 角色与不变量

| 角色 | 能力 |
| --- | --- |
| viewer | 查看本租户工单 |
| agent | viewer + 评论、接单 |
| manager | agent + 分配、关闭、查看团队指标 |

关键不变量：

1. 用户永远不能读取/修改未加入租户的数据；
2. 前端隐藏按钮不是授权，服务端每个对象重新验证；
3. 一张工单同一时刻只有一个有效 assignee；冲突不能静默覆盖；
4. 评论重试不能生成重复记录；
5. URL 可分享的筛选必须在 route query，而非只存 store；
6. 刷新页面后 server state 可重取，草稿需明确恢复策略；
7. SSR HTML/payload 不能含 secret 或其他租户数据；
8. 键盘和读屏可完成搜索、打开详情、分配和评论。

### 2.2 非功能预算

数字要按真实目标设备校准，示例预算：

- 关键路由移动端 LCP p75 ≤ 2.5s、INP p75 ≤ 200ms、CLS ≤ 0.1；
- 初始 JS gzip ≤ 团队基线，例如 350–450KB；重编辑器/图表不进首屏；
- 10,000 工单场景 DOM 有明确上限；筛选不产生明显长任务；
- 错误带 route/release/trace，敏感字段不入日志；
- 核心旅程在 supported browsers 可完成；
- RTO/RPO、API timeout、retry/idempotency 与回滚时间有约定。

预算不是为了追满分，而是把质量变成发布决策。

## 3. 从需求到可执行规格

### 3.1 用场景 + 不变量 + 失败写需求

低质量故事：“实现分配处理人”。

可执行规格：

```text
Given agent A 正在查看 ticket version=12
And manager B 已把 ticket 分给 agent C，服务端 version=13
When A 仍提交 assign-to-self(baseVersion=12)
Then API 返回 409 + current representation
And UI 不把本地成功状态当真
And 显示冲突、当前 assignee、刷新/重试入口
And audit/trace 能关联该失败
```

每个关键用例都要覆盖：成功、空、慢、超时、取消、权限、冲突、重复、离线/重连以及用户离开。

### 3.2 Definition of Ready

实现前至少有：

- 用户/业务结果、范围与不做项；
- 数据/事件 schema 与权限矩阵；
- 状态所有权和 route identity；
- loading/error/empty/conflict 文案；
- 可访问键盘路径；
- 性能/安全/兼容预算；
- rollout/rollback 和 telemetry；
- 未决问题的 owner/截止时间。

## 4. 架构：一条 vertical slice 如何落地

```text
src/
├─ app/                  # router, providers, error boundary, shell
├─ modules/tickets/
│  ├─ domain/            # Ticket/Permission/Conflict 纯类型与规则
│  ├─ application/       # list/open/assign/comment 用例和 ports
│  ├─ infrastructure/    # validated HTTP, realtime adapter
│  ├─ ui/                # pages/components/composables
│  └─ public.ts
├─ shared/ui/            # design-system adapter
└─ shared/platform/      # logger, metrics, feature flag ports
```

### 4.1 状态所有权表

| 状态 | owner | 原因 |
| --- | --- | --- |
| `tenantId`, filter, page | Router query/path | 可分享、刷新、前进后退 |
| ticket list/detail | server-state cache | 远端真相、失效/重试/去重 |
| current public session/capability | session store | 跨页面客户端投影；服务端仍授权 |
| comment draft | component/form + optional scoped persistence | 本地未提交编辑 |
| Dialog open/active option | component/headless state | 短生命周期视图状态 |
| realtime connection | application/session resource owner | 生命周期、退避、去重 |

“全放 Pinia”会混淆 URL、服务端缓存、表单和视图状态的更新语义。

### 4.2 Domain 与 wire schema 分离

```ts
export type TicketStatus = 'open' | 'in_progress' | 'closed'

export interface Ticket {
  id: string
  tenantId: string
  title: string
  status: TicketStatus
  assigneeId: string | null
  version: number
  updatedAtIso: string
}

export type AssignResult =
  | { type: 'assigned'; ticket: Ticket }
  | { type: 'conflict'; current: Ticket }
  | { type: 'forbidden' }
  | { type: 'unavailable'; retryable: boolean }
```

后端 JSON 是 `unknown`，经 schema 校验和 mapper 才成为 `Ticket`。HTTP 409 转为显式 conflict，不要在组件里到处判断 `error.response?.status`。

### 4.3 Port 让用例可测试

```ts
export interface TicketRepository {
  list(query: TicketQuery, signal: AbortSignal): Promise<TicketPage>
  assign(input: {
    ticketId: string
    assigneeId: string
    baseVersion: number
    idempotencyKey: string
  }): Promise<AssignResult>
}

export function createAssignTicket(repository: TicketRepository) {
  return async (input: Parameters<TicketRepository['assign']>[0]) => {
    return repository.assign(input)
  }
}
```

生产 adapter 负责 HTTP、schema、timeout、trace；测试 adapter 可精确返回 conflict/slow/forbidden。Vue 组件只调用用例并渲染状态。

## 5. 前端交互：正确处理并发和资源

### 5.1 查询竞态

筛选改变时：URL 是 query 真相；请求 key 包含 tenant/filter/page；旧请求 abort；即使 abort 不生效也用 generation 防提交。保留旧数据还是显示 skeleton 要依据用户体验明确定义，不应随机闪空。

### 5.2 Mutation 与失效

分配处理人可选择：

- 保守更新：提交后再更新 cache，简单但反馈慢；
- 乐观更新：立即显示，失败 rollback；必须有 snapshot、并发 mutation 顺序和 conflict 方案；
- hybrid：按钮立即 pending，实体仍显示服务端确认值。

对高冲突操作，hybrid 常比盲目 optimistic 更诚实。mutation 成功后按实体 key 更新 detail/list，并使统计 query 失效；不要清空全站所有缓存。

### 5.3 Realtime

```text
connect(session)
 → snapshot/version baseline
 → receive event(eventId, entityVersion)
 → dedupe eventId
 → 若 version 连续：patch cache
 → 若缺口/乱序：标 stale 并 refetch
 → reconnect with backoff+jitter
 → deactivate/logout: stop and clear scoped state
```

WebSocket event 不是自动可信：runtime validate、租户/对象权限仍由服务器通道保证，客户端避免把错误事件写入错误 tenant cache。

## 6. SSR/Nuxt 4 渲染策略

FlowOps 可选择：

- 公共帮助/登录说明页 prerender；
- 登录 dashboard universal SSR，响应 `private, no-store`，只发送公开 session DTO；
- 重型时间线/编辑器异步 client boundary；
- `useFetch/useAsyncData` 通过稳定 tenant/query key 将服务器数据放 payload，避免首次重复请求；
- `useState` 按请求创建，不使用模块级用户 ref；
- Nitro BFF 隐藏服务凭证、做身份/对象授权、schema 和 DTO 裁剪。

若 dashboard SSR 的服务器成本和 hydration 大于首屏收益，可经实验选择 CSR；作品要展示对照证据，而不是为了简历强上 SSR。

## 7. 安全威胁模型

至少画出 trust boundaries：

```text
Browser (untrusted input/state)
  ↕ HTTPS cookie/CSRF policy
Nuxt/Nitro BFF (authn/authz/schema/rate limit)
  ↕ service credential
Internal API / DB
  ↘ audit log
```

检查：

- XSS：插值默认转义；富文本 sanitizer；CSP；第三方脚本；
- Auth：HttpOnly/Secure/SameSite cookie 或批准的 token 流；不把 token 放 localStorage 示例中；
- CSRF：状态改变命令需要正确 SameSite/origin/token 策略；
- IDOR/BOLA：每个 ticket 按可信 session + tenant 验证；
- SSRF：BFF 不 fetch 用户任意 URL；
- schema/mass assignment：只接受 allowlist 字段；
- replay/duplicate：mutation idempotency key；
- 日志/遥测：不记录评论正文、token、完整 query；
- source map：上传监控且受控访问；
- dependency/secret scanning 和安全 patch SLA。

前端权限主要改善 UX，不构成安全边界。

## 8. 测试策略：按风险选择层

### 8.1 测试地图

| 风险 | 最便宜且可信的层 |
| --- | --- |
| 状态转换/权限投影/mapper | pure unit/property tests |
| composable 请求竞态/cleanup | unit + fake adapter/timer |
| 组件键盘/ARIA/表单 | component interaction |
| router/query/cache 协作 | integration |
| 登录→筛选→分配→冲突→评论 | browser E2E |
| SSR isolation/hydration/status | server integration + real browser |
| 性能/内存 | fixed fixture trace + RUM/heap |
| API 授权/安全 | server contract/security tests |

不追求测试数量，而追求风险证据。不要用 E2E 重复纯函数所有分支，也不要用 unit mock 宣称真实 cookie、focus、hydration 已正确。

### 8.2 必做故障注入

- list A 慢 B 快；
- assign 409 conflict；
- comment 请求成功但响应丢失，再 retry；
- WebSocket 断开、乱序、重复和 gap；
- async chunk 404；
- API 401/403/429/500/timeout 与 offline；
- SSR 两租户并发；
- payload 含恶意字符串；
- KeepAlive 来回 20 次；
- 低端 CPU 下 10,000 行。

## 9. 性能与可观测性

### 9.1 先定义业务指标

- `ticket_list_ready`：进入路由到列表可筛选；
- `assign_feedback`：点击到 pending/结果可见；
- `comment_confirmed`：提交到服务器确认；
- conflict rate、retry success、reconnect recovery；
- LCP/INP/CLS、JS/chunk、long task、heap platform。

事件字段包含 route template、release、feature flag、匿名 device class、trace id；tenant/user 使用不可逆匿名分组且符合隐私规则。高基数 ticket id 不进入普通指标 label。

### 9.2 Performance plan

- route/chunk ownership，编辑器/图表延迟加载；
- 稳定 row props、server pagination/virtualization、`shallowRef` 只用于大型不可变结构；
- Profile 证明后才用 `v-memo`/Worker；
- PR bundle budget、预发弱机 trace、灰度 RUM；
- heap snapshot 证明 SDK/listener/socket owner 可释放。

## 10. 发布：从 commit 到可回退 release

```text
PR
 ├─ format/lint/type
 ├─ unit/component/integration
 ├─ boundary/schema/security checks
 ├─ bundle + SSR smoke
 └─ preview + accessibility review
        ↓
main immutable artifact
        ↓
staging：migration/contract/E2E/perf
        ↓
canary：员工/1%/指定租户 + feature flag
        ↓
逐级放量，观察 release dashboard
        ↓
全量或 rollback artifact / disable flag
```

数据库/API 变化必须向后兼容：expand → 双版本兼容 → migrate → contract。前端旧 tab 可能长时间存在，服务端不能只兼容“最新 JS”。

### 10.1 Definition of Done

- 验收场景与不变量通过；
- 类型/schema/边界可执行；
- a11y keyboard/reader 关键路径；
- error/empty/loading/conflict/retry；
- security review 与日志隐私；
- performance/bundle/heap 证据；
- SSR/hydration/cache isolation（若适用）；
- dashboard/alert/runbook/owner；
- canary/rollback 演练；
- ADR/migration/release note；
- 临时 flag/adapter 有删除日期。

## 11. 事故响应与复盘

### 11.1 处理顺序

```text
Detect → Triage → Contain → Mitigate/Recover → Verify → Learn
```

1. 先确认用户影响、范围、release/flag、数据/安全风险；
2. 建单一 incident channel/timeline/commander；
3. 优先关闭 flag、pin/rollback、禁用危险 cache；
4. 保留日志/trace/heap/HTML 等证据，不在生产盲修多处；
5. 恢复后验证用户旅程和数据一致性；
6. 无责复盘：触发、放大、为何未提前发现、哪些 guardrail 要改变。

### 11.2 一份有用的 postmortem

- 影响和持续时间；
- 分钟级时间线；
- 技术根因与组织/流程促成因素；
- 检测、响应、恢复哪里有效/无效；
- corrective actions 有 owner、优先级、截止时间、验证；
- 反事实：“若只有某个动作存在，事故会否避免/缩短？”

“提醒大家更小心”不是可验证 action。CI 规则、缓存默认、contract test、runbook 和 ownership 才是系统改进。

## 12. 高级面试：展示推理，不背术语

### 12.1 通用回答框架

```text
1. Clarify：用户、规模、SLO、约束、现状、时间
2. Invariants：安全/正确性绝不能破坏什么
3. Model：状态、数据流、边界、失败、identity
4. Options：至少两种，写收益与代价
5. Decision：当前为何选它；明确不做什么
6. Evidence：测试、指标、trace、contract
7. Delivery：灰度、兼容、回滚、owner
8. Evolution：什么信号会重审
```

### 12.2 “为什么”比 API 名更重要

面试官问 `watch` 与 `computed`，高级回答不止定义：说明纯派生/副作用、缓存失效、flush 时序、cleanup 和生产 bug。问 Pinia，说明客户端状态与 server/URL/form 状态为何分开。问 SSR，说明隔离、一致、payload、缓存和安全。问微前端，先问团队/发布边界，不直接画框。

### 12.3 STAR + 深挖

项目叙述包含：

- Situation：业务规模与痛点，不夸大；
- Task：你的责任和限制；
- Action：你做的决定、反对意见、证据；
- Result：前后指标、负面后果、后续；
- Deep dive：根因、替代方案、失败尝试、复盘和可迁移经验。

“我们把 LCP 从 4.1s 降到 2.3s”后要能解释样本、p75、设备、release、具体 trace 与业务影响。

## 14. 常见反例

1. **功能越多越高级**：浅 CRUD 十页不如一条含冲突、权限、故障与观测的深切片。
2. **为了作品集自研所有基础设施**：成熟库能降低非核心风险；选择与封装理由才是能力。
3. **所有失败都 toast**：字段错误、页面错误、冲突、离线与 fatal 需要不同恢复路径。
4. **只测试成功路径**：生产事故多来自竞态、重复、慢、部分失败和生命周期。
5. **指标只写 README 目标**：要有可复现实验、原始 evidence 与 CI/RUM 检查。
6. **部署成功等于发布成功**：需要 canary、用户结果、回滚与旧客户端兼容。
7. **面试答案先说技术名**：没有约束和决策驱动，只是在背题。
8. **事故复盘找个人责任**：会隐藏系统性弱点并减少真实信息。

## 15. 速记卡与毕业自检

### 速记卡

- 深 vertical slice：正确性、失败、安全、性能、交付全贯通。
- 需求 = 场景 + 不变量 + 失败 + 可量验收。
- 状态按 URL/server/session/form/view/resource owner 分治。
- wire `unknown` → schema → domain；HTTP 错误 → 判别联合。
- 核心旅程必须注入乱序、冲突、重复、断线、SSR 并发和 chunk 失败。
- CI → immutable artifact → staging → canary → rollout/rollback。
- 观测关联 release/route/flag/trace，不采敏感正文。
- 面试回答：clarify → invariants → options → evidence → delivery → evolution。

### 毕业自检

1. 能否在 5 分钟内画出 FlowOps 的状态所有权和 trust boundary？
2. 能否解释为什么按钮权限、route guard 都不是对象授权？
3. 能否写出 query 竞态、mutation conflict、realtime gap 的处理？
4. 能否证明 SSR 不串租户、不重复取数、无 mismatch？
5. 能否用 trace/Devtools/RUM 讲清一次性能改进，而非报分数？
6. 能否说明每层测试能证明什么、不能证明什么？
7. 能否在 10 分钟内完成一次 release rollback 决策？
8. 能否对自己的架构说出至少三个负面后果和重审信号？
9. 能否不看答案讲清一场事故的检测、止血、恢复和 guardrail？
10. 能否回答“如果规模小十倍/团队只两人，你会删掉什么”？
