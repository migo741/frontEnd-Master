# 第 04 章：Composable 与副作用治理——把资源所有权写进 API

> Composable 不是“把 setup 搬到 useX 文件”。它是一个有输入、状态、命令、生命周期、并发和失败语义的小型模块。

## 0. 事故钩子：弹窗开十次，消息处理十次

客服弹窗每次打开都调用：

```ts
function useChat() {
  socket.addEventListener('message', event => messages.value.push(event.data))
}
```

弹窗关闭只隐藏 DOM，或 KeepAlive 只是 deactivated；listener 从未移除。第十次打开，一条消息追加十遍。团队随后加 `messages = unique(messages)`，掩盖了症状，却留下十个闭包、十次解析和十次日志。

真正的问题不是“忘写 onUnmounted”这么简单，而是 API 没回答：

```text
谁创建 socket/listener？
何时开始？何时暂停？何时最终释放？
一个 composable 被多个消费者调用时资源共享还是独占？
组件卸载、作用域 stop、输入变化分别触发哪种清理？
```

本章用“资源所有权”重构 composable 思维。

---

## 1. 一个高级 composable 的七项契约

设计前写出：

| 项 | 要回答的问题 |
| --- | --- |
| 输入 | plain / Ref / getter？变化后重新绑定还是只读一次？ |
| 输出 | 哪些只读状态？哪些动作？有无可写双向模型？ |
| 启动 | 调用即启动、显式 start、首次读取懒启动？ |
| 停止 | 输入失效、scope dispose、deactivate、手动 stop 各做什么？ |
| 并发 | latest-wins、first-wins、queue、every-result、singleflight？ |
| 错误 | throw、状态、回调、全局上报如何分层？Abort 算错误吗？ |
| 环境 | SSR、浏览器、多实例、测试时依赖从哪里来？ |

如果这些只存在作者脑中，`useRequest()` 越通用越危险。

---

## 2. 输入归一化：`MaybeRefOrGetter` 与 `toValue`

希望调用者可传静态值、ref 或 getter：

```ts
import type { MaybeRefOrGetter } from 'vue'

function useProject(id: MaybeRefOrGetter<string>) { /* ... */ }
```

`toValue(input)`：

- plain 值：直接返回；
- ref：读取 `.value`；
- getter：调用 getter。

关键不是“在哪里调用都一样”，而是**在响应式 effect 内调用才会追踪**：

```ts
watch(
  () => toValue(projectId),
  id => load(id),
  { immediate: true },
)
```

错误：

```ts
const initialId = toValue(projectId)
watchEffect(() => load(initialId)) // 永远只用初始化值
```

### 2.1 不要滥收三种输入

如果语义要求调用者明确传 reactive source（例如会持续跟踪查询），只接受 `Ref` 或 getter可能更清晰。宽松输入会增加测试矩阵：plain 不变、ref 变化、getter 多依赖、getter throw 都要定义。

### 2.2 函数输入可能有二义性

`MaybeRefOrGetter<T>` 在 `T` 本身是函数时无法仅凭类型判断“值函数”还是 getter。此类 API 应拆参数或要求 ref，别靠 `toValue` 猜。

---

## 3. 输出：只读状态 + 显式命令

坏接口：

```ts
return { data, loading, error } // 三个可写 ref，调用方能制造任意组合
```

更稳：

```ts
type ResourceState<T> =
  | { status: 'idle' }
  | { status: 'loading'; previous: T | null }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error; previous: T | null }

const state = shallowRef<ResourceState<User>>({ status: 'idle' })

return {
  state: readonly(state),
  refresh,
  reset,
}
```

拥有者通过动作维持不变量；消费者只能请求状态迁移。`readonly` 不意味着深冻结或安全沙箱，而是协作契约。

返回一个 reactive 对象时，调用方解构可能丢响应性。对库 API，返回“refs 的对象”通常更耐解构；或明确要求 `toRefs`。选择后保持一致。

---

## 4. 三种生命周期：调用、响应式失效、作用域销毁

### 4.1 每一轮 watcher 的失效

输入变化时，上一轮资源要先清理：请求 abort、旧 target 移除 listener、旧订阅 unsubscribe。

```ts
watch(
  () => toValue(target),
  (nextTarget, _oldTarget, onCleanup) => {
    if (!nextTarget) return
    nextTarget.addEventListener('resize', listener)
    onCleanup(() => nextTarget.removeEventListener('resize', listener))
  },
  { immediate: true },
)
```

### 4.2 当前 effect scope 的销毁

组件 setup 同步执行时有组件 effect scope；scope 内同步创建的 watcher 会自动停止。Composable 自己创建非 watcher 资源时使用 `onScopeDispose`：

```ts
onScopeDispose(() => socket.close())
```

若 composable 只能在 scope 内使用，可 fail fast：

```ts
if (!getCurrentScope()) {
  throw new Error('useChat must be called inside an active effect scope')
}
```

有些纯工具希望组件外也能手动管理，则返回 `stop()`，且无 scope 时不注册自动清理。不要默默创建永久资源。

### 4.3 activate/deactivate

KeepAlive 下组件并未销毁。轮询、快捷键、动画往往应在 `onDeactivated` 暂停、`onActivated` 恢复，最终 `onScopeDispose/onUnmounted` 释放。把 pause 与 dispose 区分：

```text
active ─pause─> paused ─resume─> active
   └────dispose───────────────> disposed（不可恢复）
```

## 5. 每个资源都有对称操作

| acquire/start | release/stop |
| --- | --- |
| `addEventListener` | `removeEventListener`（同 target/type/listener/capture） |
| `setInterval` | `clearInterval` |
| `new AbortController` | `abort` |
| `store.subscribe` | unsubscribe |
| `new WebSocket` | remove handlers + close |
| `new ResizeObserver` | disconnect |
| `URL.createObjectURL` | `URL.revokeObjectURL` |
| `effectScope()` | `scope.stop()` |
| focus/scroll lock | restore previous focus/unlock |

清理函数必须：幂等、能处理半初始化、不会因一个清理失败阻止其余清理。复杂资源可用 disposable stack 思维。

```ts
const cleanups = new Set<() => void>()

function dispose(): void {
  const errors: unknown[] = []
  for (const cleanup of cleanups) {
    try { cleanup() } catch (error) { errors.push(error) }
  }
  cleanups.clear()
  if (errors.length) console.error('cleanup failures', errors)
}
```

## 6. 并发不是实现细节

| 语义 | 含义 | 典型业务 |
| --- | --- | --- |
| latest-wins | 只有最新一轮可提交 | 搜索、切用户详情 |
| first-wins | 进行中时忽略后续触发 | 防止重复提交按钮 |
| queue | 按顺序逐个执行 | 有顺序的离线写队列 |
| every-result | 每个结果都处理 | 独立文件上传、遥测 |
| singleflight | 相同 key 的并发调用共享同一个进行中 Promise | 多组件同时加载同一配置 |

`debounce` 是触发频率策略，不是并发语义；`retry` 是失败恢复策略，也不定义谁可提交。

### 6.1 latest-wins：取消 + 代次

详见第 01 章。核心是旧任务不具备提交权限，Abort 只负责尽量停止工作。

### 6.2 first-wins

```ts
let pending: Promise<void> | null = null

function submit(): Promise<void> {
  if (pending) return pending
  pending = doSubmit().finally(() => { pending = null })
  return pending
}
```

按钮 disabled 只是 UI 防护；API 层仍要 first-wins 或幂等键，因为命令可从键盘、测试或其他调用处触发。

### 6.3 singleflight 不等于 cache

```text
singleflight：只合并“同时进行中的同 key 请求”；完成后可以立刻忘记
cache：完成后在一段时间保存结果，并定义 stale/invalid/revalidate
```

把它们混为一谈会产生“为什么 refresh 仍拿旧数据”的隐式行为。

简化 registry：

```ts
const inFlight = new Map<string, Promise<User>>()

function loadOnce(key: string): Promise<User> {
  const existing = inFlight.get(key)
  if (existing) return existing
  const promise = loadUser(key).finally(() => inFlight.delete(key))
  inFlight.set(key, promise)
  return promise
}
```

生产版还要决定：所有消费者离开时是否 abort；一个消费者取消是否影响其他消费者；错误是否缓存；invalidate 如何阻止旧结果回填。

## 7. `effectScope`：动态模块的资源容器

当你创建“不是一个组件，却拥有多个 watcher”的对象时：

```ts
import { effectScope, readonly, ref, watch } from 'vue'

export function createFilterSession() {
  const scope = effectScope()
  const result = scope.run(() => {
    const query = ref('')
    const normalized = ref('')
    watch(query, value => { normalized.value = value.trim().toLowerCase() })
    return { query, normalized: readonly(normalized) }
  })
  if (!result) throw new Error('failed to initialize filter session')
  return { ...result, dispose: () => scope.stop() }
}
```

作用域是所有权容器，不是全局 store。调用方必须知道何时 dispose。若将它放模块顶层，SSR 和 HMR 都可能产生超出预期的生命周期。

---

## 8. SSR：模块全局不是“每个用户一份”

危险：

```ts
// 模块只初始化一次，多个 SSR 请求可能共享。
const currentUser = ref<User | null>(null)
export function useCurrentUser() { return currentUser }
```

在长期运行的 Node server 中，请求 A 的用户可能被请求 B 读取。原则：

```text
纯配置/无用户数据的 immutable 单例：可全局
请求状态、auth、locale、缓存：按 app/request 创建
浏览器 DOM、window、localStorage：只在 client 生命周期使用
```

工厂 + provide：

```ts
export function createUserSession(initial: User | null) {
  const user = shallowRef(initial)
  return { user: readonly(user), setUser: (next: User | null) => { user.value = next } }
}

// 每次 SSR request createApp 时创建并 provide，而不是模块 singleton。
```

`typeof window !== 'undefined'` 只解决 API 是否存在，不自动解决 hydration 初始状态一致。服务端与客户端首次 render 必须得到一致的可序列化状态。

## 9. 依赖注入让 composable 可测试

不要在深处硬编码时间、网络、全局存储：

```ts
export interface Clock {
  now(): number
  setTimeout(callback: () => void, ms: number): unknown
  clearTimeout(handle: unknown): void
}

export interface UserGateway {
  getUser(id: string, signal: AbortSignal): Promise<User>
}

export function useUser(
  id: MaybeRefOrGetter<string>,
  deps: { gateway: UserGateway; clock: Clock },
) { /* ... */ }
```

生产注入 fetch/真实 clock；测试注入 deferred Promise/fake clock。依赖不是越多越好，先注入不稳定或有 I/O 的边界。

### 9.1 日志也要有语义

Composable 可报告技术事件：开始、取消、失败、耗时、key、generation；不要记录 token/敏感 payload。取消不是 error，预期 404 未必是 error，监控级别由领域语义决定。

## 10. 常见反模式

1. **异步创建 watcher**：`setTimeout(() => watch(...))` 可能脱离组件 scope；同步建 watcher，异步结果写 ref。
2. **返回可写 state**：调用方能绕过动作；返回 readonly。
3. **万能 useRequest**：默认缓存、重试、debounce、toast 混在一起；拆成正交层。
4. **一个消费者 abort 共享请求**：其他消费者也失败；共享层需引用计数或只取消订阅。
5. **模块全局缓存用户数据**：SSR 跨请求泄漏；按请求建 client。
6. **catch 全部吞掉**：Abort 可忽略，真实错误必须进入状态或上报。
7. **cleanup 只在 unmount**：输入切换时旧资源仍活着。
8. **watch deep 巨型对象**：用稳定 key、getter 或不可变替换。
9. **在 composable 直接弹 toast/跳路由**：复用与测试困难；返回领域错误，由上层编排 UI。
10. **stop 不幂等**：重复 lifecycle/人工调用导致异常。

## 11. 测试矩阵

至少按三个轴组合：

```text
输入：plain / ref变化 / getter变化 / null
时序：顺序完成 / 乱序 / reject / abort / dispose 后完成
生命周期：首次启动 / retarget / pause-resume / scope stop / manual stop twice
```

工具：

- `effectScope()` 在单测中模拟所有权；
- deferred Promise 控制乱序；
- fake timers 验证 debounce/polling/TTL；
- spy target 验证 add/remove 参数完全对称；
- 测试只读输出与非法状态不可达；
- 每个用例结束检查 timer/listener/in-flight registry 是否归零。

不要用真实 `setTimeout(500)`，它慢且不稳定。

## 12. 排障路线

```text
重复执行？
  → composable 被调用几次？listener 是否同一函数？activated 是否重复 start？
卸载后仍写状态？
  → watcher 是否同步建在 scope？Promise 是否有 generation/active 门卫？
切换输入仍收旧事件？
  → cleanup 是否注册在每轮 watcher，而非只 onUnmounted？
相同请求发多次？
  → 是否确实需要 singleflight？key 是否稳定/规范化？
SSR 串用户？
  → mutable 值是否模块全局？client/cache 是否按请求创建？
测试很难写？
  → fetch、clock、storage、ID 生成是否硬编码？
```

## 13. 生产边界

- 所有权必须与产品体验结合：KeepAlive 的暂停、后台标签页节流、离线恢复都不是单纯 API 选择。
- singleflight 只对幂等或允许共享结果的同 key 读取安全；写操作不能随便合并。
- 缓存 key 必须包含影响结果的 tenant、locale、permission scope 等，避免数据串域。
- Abort 并不回滚服务端副作用；写操作依赖幂等协议。
- SSR request scope client 若被错误保存到模块单例，工厂也救不了。
- DOM composable 在 SSR 应无副作用，但客户端 hydration 时仍要保证初始结构一致。
- 错误对象可能含敏感响应，暴露给 UI/日志前要归一化。

---

## 14. 速记卡

```text
Composable = 契约 + 所有权 + 并发 + 失败语义，不是文件搬家。
toValue 要在 effect 内读，才会追踪 getter/ref。
状态 readonly，修改走动作；不要暴露非法组合。
每轮失效清旧资源，scope dispose 做最终释放。
pause 可恢复，dispose 不可恢复；二者不要混淆。
latest/first/queue/every/singleflight 是不同业务协议。
singleflight 合并进行中，cache 保存已完成。
SSR 的 mutable request state 绝不放模块全局。
时间、网络、存储注入，测试用可控依赖。
```
