# 第 20 章：内置组件、Vue Router 与 Pinia 源码专题——理解跨边界协调

> 固定源码基线：Vue Core `v3.5.42`（commit `d63616c`）、Vue Router `5.3.0`（commit `0e91ac8`）、Pinia `4.0.3`（commit `5d6ac5b`）。本章以 2026-09-02 的稳定标签为阅读坐标。`<Suspense>` 的公开文档仍标为 experimental；Vapor/3.6 RC 不作为生产基线。

## 0. 为什么把这些主题放在同一章

`KeepAlive`、`Teleport`、`Suspense`、Router 与 Pinia 看似属于五个 API，实际上都在解决同一类高级问题：**某个对象的逻辑所有权、物理位置、异步生命周期和请求上下文不再一致时，如何保持正确性。**

生产事故通常不是“API 不会用”，而是边界混淆：

- 页面被 KeepAlive deactivated，却仍持续轮询和占用 WebSocket；
- Modal Teleport 到 `body` 后，CSS、焦点与测试仍按原 DOM 祖先推断；
- Suspense fallback 消失了，异步请求却失败，开发者误以为它是 error boundary；
- 新导航已经开始，旧导航 loader 最后返回并覆盖页面；
- SSR 两个并发请求共享 Pinia，用户 A 的数据进入用户 B HTML；
- 解构 Pinia store 后失去响应性，却误判 renderer 或 Vue reactivity 有 bug。

这一章不会逐行覆盖三个仓库，而是选择**高价值调用链和不变量**。

## 2. 为什么内置组件能直接参与 renderer

普通用户组件通过 component instance 和 render effect 返回 subTree。某些 built-ins 带内部标记并接收 renderer internals：

```text
patch(vnode)
  ├─ ShapeFlags.COMPONENT → processComponent
  ├─ ShapeFlags.TELEPORT  → TeleportImpl.process(..., internals)
  └─ Suspense type        → SuspenseImpl.process(..., internals)
```

KeepAlive 更特殊：renderer 在挂载 KeepAlive 实例时，把自己的 internals 注入 instance context；KeepAlive 再把 `activate` / `deactivate` 暴露回 renderer。这样既避免 runtime-core 对实现做难以 tree-shake 的直接耦合，又允许它控制 VNode 的移动、patch 和卸载。

这类协议是内部实现。业务组件不应模仿 `__isKeepAlive` 或读取 `instance.ctx.renderer`。

## 3. KeepAlive：缓存的是组件实例，不是 HTML 字符串

### 3.1 核心数据结构

固定版本使用：

```ts
const cache = new Map<CacheKey, VNode>()
const keys = new Set<CacheKey>()
let current: VNode | null = null
```

默认 cache key 是 `vnode.key ?? componentType`。如果同一个组件类型代表多个业务实体，而你没有提供 key，它们可能被当成同一缓存身份：

```vue
<KeepAlive>
  <DocumentEditor :key="documentId" :document-id="documentId" />
</KeepAlive>
```

### 3.2 activate 不是 remount

命中缓存后，KeepAlive 把旧 VNode 的 `el` 与 `component` 复制到新 VNode，打上 kept-alive flag。renderer 遇到它时调用 `activate`：

```text
move vnode from storage container to live container
  → patch(old instance.vnode, new vnode)，应用变化的 props/slots
  → post-render: isDeactivated=false
  → onActivated hooks
```

没有重新执行整套首次 mount。实例、局部 ref 和 effect scope 仍在。

### 3.3 deactivate 不是 unmount

离开活跃分支时：

```text
move vnode to hidden storage container
  → post-render onDeactivated
  → instance.isDeactivated=true
```

因此：

- `onUnmounted` 不会在每次切 tab 时触发；
- setup 中创建的 watcher/effect 通常仍存在；
- timer、WebSocket、observer 是否暂停，必须由组件所有权策略决定；
- DOM 被移走，依赖可见布局的逻辑不能继续假定元素在页面中。

推荐模式：

```ts
let stopPolling: (() => void) | undefined

onActivated(() => {
  stopPolling = startPolling()
})

onDeactivated(() => {
  stopPolling?.()
  stopPolling = undefined
})

onUnmounted(() => {
  stopPolling?.()
})
```

仍需防止初次 mounted 与 activated 双启动，最好让 `startPolling` 幂等或由一个显式状态机管理。

### 3.4 max 与 LRU

命中 cache 时，key 从 Set 删除再添加，成为最新；新增后若超过 `max`，删除 `keys.values().next().value` 指向的最旧项。被淘汰项会真正 unmount。

这说明 `max` 不是“最多显示多少个”，而是实例缓存预算。预算还要考虑：

- 每个页面保留的响应式图与 DOM；
- 编辑器、图表、第三方控件的外部资源；
- 缓存命中收益；
- 用户切换模式；
- 移动端内存上限。

### 3.5 include/exclude 的名称陷阱

过滤依据组件 name；异步组件已解析后会看内部组件名。匿名组件、构建变换和不稳定 name 会让过滤行为不符合预期。关键页面更推荐明确 component name、稳定 key 和自动化测试，而不是只看模板字符串。

## 4. Teleport：逻辑树与物理 DOM 树分离

```vue
<Teleport to="#overlays">
  <ModalDialog />
</Teleport>
```

逻辑上 Modal 仍是原父组件的子孙：provide/inject、props、events 和组件生命周期沿 Vue tree。物理上 DOM children 被挂到 target。

### 4.1 源码中的双锚点

主 container 会放 teleport start/end placeholders；target 也有 target anchors。更新时 children 可能位于：

- 原 container：`disabled`；
- target：正常 teleport；
- 延迟挂载队列：defer 或 pending Suspense；
- 新 target：`to` 改变后 move。

所以 Teleport 不是“render 时 querySelector 然后 appendChild 一次”。它必须在 patch、target 变化、disabled 切换、卸载与 hydration 中保持两边锚点一致。

### 4.2 生产影响

| 关注点 | 结论 |
| --- | --- |
| CSS descendant selector | 按物理 DOM，不再受原父元素选择器约束 |
| provide/inject | 按逻辑 Vue tree，仍可用 |
| `position: fixed` | 避开祖先 transform/overflow 常是使用目的 |
| 事件 | Vue 组件事件仍按组件关系；原生 DOM 事件按物理 DOM 冒泡 |
| a11y | 必须自行实现 dialog 语义、focus trap、restore focus、Escape、背景 inert |
| SSR/hydration | target 与服务端输出结构必须可对应；不能在客户端任意重排后期待无 mismatch |
| 测试 | wrapper DOM 可能不包含 target 内容；应 attachTo 并查询真实 document target |

target 应在 Teleport 挂载前存在。固定版本支持 `defer` 的延迟目标解析，但不要把它当作任意时间后出现的 portal manager。

## 5. Async Component 与 Suspense：加载、等待、错误是三件事

### 5.1 `defineAsyncComponent`

它包装一个 loader，并管理：

- `pendingRequest`：同一 wrapper 的并发加载复用；
- 已解析组件缓存；
- retry/fail；
- delay 后显示 loading component；
- timeout 后产生错误；
- error component；
- `suspensible` 与父 Suspense 的协作；
- hydration strategy 等 3.5 能力。

一个稳健定义：

```ts
const AuditPanel = defineAsyncComponent({
  loader: () => import('./AuditPanel.vue'),
  delay: 150,
  timeout: 10_000,
  loadingComponent: PanelSkeleton,
  errorComponent: PanelLoadError,
  onError(error, retry, fail, attempts) {
    if (isTransientChunkError(error) && attempts <= 2) retry()
    else fail()
  },
})
```

重试必须有上限，并区分部署后旧 chunk 404、离线、权限与真正代码异常。盲目无限 retry 会制造请求风暴。

### 5.2 Suspense boundary 的内部状态

Suspense 是直接接入 renderer 的特殊 built-in。核心概念：

```text
activeBranch   当前显示的 content 或 fallback
pendingBranch  正在离屏容器中构建的新 content
deps           未解决的 async dependencies
effects        等待 boundary resolve 后再提交的 post-render effects
```

挂载时，default branch 可先在隐藏容器构建。若 deps > 0，显示 fallback；deps 归零后 resolve，把 pending branch 移入真实 container，并 flush 被缓冲的 effects。

### 5.3 Suspense 不是 error boundary

Suspense 主要协调 pending/fallback。异步依赖 reject 后的错误仍进入 Vue error handling；你需要 `onErrorCaptured`、app errorHandler、route error UI 或产品自己的错误状态。

而且官方仍将 Suspense 标为 experimental。因此生产采用要：

- 固定支持版本；
- 限定使用范围；
- 有无 Suspense 也正确的 loading/error 状态模型；
- 覆盖 resolve、reject、timeout、快速切换与 nested boundary 测试；
- 不让核心数据正确性依赖 fallback 动画。

## 6. Transition 与 TransitionGroup：状态生命周期，不只是 CSS 类名

BaseTransition 负责 enter/leave hooks、mode、appear、取消与序列；runtime-dom 再把 CSS transition/animation 细节接上。`TransitionGroup` 还要记录旧/新位置，对 retained children 应用 move class。

高级实现必须处理：

- enter 被 leave 中断；
- 同 key 才能表示同一项移动；
- 快速切换时取消旧 callback；
- JS hook 必须调用 done 或返回可管理 Promise；
- `prefers-reduced-motion` 下提供无运动版本；
- 测试不要等待真实 300ms，禁用动画或控制结束事件。

动画不能承担业务状态提交。DOM 是否存在、焦点是否恢复和请求是否取消，必须独立正确。

## 7. Vue Router 源码地图：它是导航事务协调器

`createRouter(options)` 首先创建 matcher，持有 history、currentRoute、pendingLocation、guard registries 等。一次 programmatic navigation 的主线可概括为：

```text
router.push(rawLocation)
  → pushWithRedirect
  → resolve(rawLocation)
  → 判断 redirect / duplicated
  → navigate(to, from)
    → 提取 leaving / updating / entering records
    → 分阶段运行 guards
    → 每阶段检查导航是否已被新导航取消
  → finalizeNavigation
    → history push/replace
    → currentRoute.value = to
    → scroll handling
  → afterEach
```

### 7.1 matcher 不是简单正则数组

`createRouterMatcher` 把 route records 转为 normalized matchers。path 经 tokenizer 变成 segment/token，再由 parser/ranker 生成解析/字符串化逻辑与 score，用于确定静态、参数、可选、重复等路径的匹配优先级。

因此：

- 不要依赖“声明顺序一定覆盖一切”的模糊直觉；
- 路由冲突应在构建/测试阶段用 `router.resolve` 证明；
- params 是 URL 输入，必须校验业务格式；
- name navigation 比手拼 path 更能表达契约；
- typed routes 提升编译期体验，但不替代运行时权限和输入校验。

Router 的 typed routes 在 4.4 引入，当前 5.3 延续并增强；不要把版本历史写成“现在仍是 Router 4”。

### 7.2 guard pipeline

普通导航的主要阶段：

```text
leaving components beforeRouteLeave + record leaveGuards
  → global beforeEach
  → reused components beforeRouteUpdate + updateGuards
  → entering records beforeEnter
  → entering components beforeRouteEnter
  → global beforeResolve
  → finalize navigation
  → global afterEach
```

每组之间加入 cancellation check。若 B 导航开始后 C 成为新的 pending location，B 后续不能再 finalize。

### 7.3 guard 不是数据缓存

守卫适合：

- 身份/权限决策；
- redirect；
- 离开未保存页面确认；
- 在最终确认前阻止不合法导航。

但 loader/cache/dedup/revalidation 需要独立协调器。否则 guard 中到处 fetch 会遇到：

- 重复导航重复请求；
- 旧导航响应回写；
- redirect 前已产生副作用；
- SSR/client 两套执行差异；
- 无法表达 stale-while-revalidate。

### 7.4 所有 route 输入都不可信

`params`、`query`、`hash` 来自 URL；`meta` 来自应用配置但会合并。不能因为 TypeScript 写了类型就跳过 runtime validation：

```ts
const TicketId = z.string().uuid()
const parsed = TicketId.safeParse(route.params.ticketId)
if (!parsed.success) {
  return { name: 'not-found' }
}
```

权限判断必须以后端为最终边界。前端 guard 只改善 UX，不是安全控制。

## 8. Pinia 源码地图：store 属于 Pinia 实例，不属于模块单例

### 8.1 `createPinia`

固定版本中，一次调用大体创建：

```text
effectScope
root state ref<Record<storeId, state>>
plugin list
store registry Map
install(app): setActivePinia + app.provide(piniaSymbol, pinia)
```

每个应用/SSR 请求应拥有独立 Pinia 实例。`pinia._s` 以 store id 缓存该实例下已经创建的 stores。

### 8.2 `defineStore` 不会立即创建全局 store

`defineStore(id, ...)` 返回 `useStore`。调用 `useStore(pinia?)` 时：

1. 优先使用显式 pinia 或 injection context；
2. 必要时更新 activePinia；
3. 若该 pinia registry 没有 id，创建 options/setup store；
4. 从 registry 返回 store。

所以同一个 `useAuthStore` 定义可以在不同 Pinia 实例中产生隔离 store。真正危险的是在服务端模块顶层提前调用并持有某个 store，或跨请求复用 app/pinia。

### 8.3 Options Store 最终也进入 Setup Store 主路径

Options state 被放进 `pinia.state.value[id]`，再用 refs、actions、computed getters 组装 setup 结果，最后交给 `createSetupStore`。后者负责：

- store scope；
- state hydration；
- `$patch`；
- `$subscribe` / `$onAction`；
- action wrapper 与 after/onError；
- plugin；
- HMR；
- `$dispose`。

理解这一点可以解释 options/setup store 的共同能力，也能看出哪些差异属于 API 层。

### 8.4 `$patch` 为什么能分组订阅

执行 patch 时临时关闭普通监听，把 mutation metadata 聚合，再手工触发 subscriptions；`nextTick` 后恢复监听。它不是数据库事务：

- 没有跨 store rollback；
- 不能阻止外部网络副作用；
- 不提供多客户端并发控制；
- 不会自动持久化。

### 8.5 action wrapper

Pinia 包装 action，使 `$onAction` 能拿到 name、args、store、after、onError。同步错误重新抛出；Promise resolve/reject 分别触发对应 callbacks。

适合做 telemetry、审计上下文和测试 probe，但插件必须：

- 不记录 password/token/PII；
- 处理 async action；
- 返回 unsubscribe；
- 避免自己触发 action 递归；
- 明确 SSR 请求边界。

### 8.6 `storeToRefs`

直接解构：

```ts
const { user } = useAuthStore() // user 是当下值，常失去后续响应连接
```

正确：

```ts
const auth = useAuthStore()
const { user } = storeToRefs(auth)
const { logout } = auth // action 直接从 store 取
```

源码会遍历 raw store，只把 computed/ref/reactive 属性转为 refs，方法和刻意非响应属性不进入结果。

## 9. SSR：最高风险是跨请求污染

错误架构：

```ts
// server.ts 模块顶层，只创建一次
const app = createSSRApp(App)
const pinia = createPinia()
app.use(pinia)

export async function render(request: Request) {
  const auth = useAuthStore(pinia)
  auth.user = await identify(request)
  return renderToString(app)
}
```

并发请求共享 app、router、pinia 和 store registry。即使 JavaScript 单线程，两个 async request 仍会交错。

正确工厂：

```ts
export function createRequestApp(url: string) {
  const app = createSSRApp(App)
  const pinia = createPinia()
  const router = createRouter({
    history: createMemoryHistory(),
    routes,
  })

  app.use(pinia)
  app.use(router)

  return { app, pinia, router, url }
}
```

每个请求：

```text
createRequestApp(url)
  → 显式 useStore(pinia)
  → router.push(url)
  → await router.isReady()
  → load request-scoped data
  → renderToString(app)
  → 安全序列化 pinia.state
  → 丢弃请求实例
```

Pinia 4 的开发诊断明确提醒：没有 injection context 时回退全局 `activePinia`，服务端可能暴露 cross-request pollution。高级工程师要用并发测试证明隔离，而不是说“每个请求理论上会新建”。

### 9.1 序列化也是安全边界

不能把 state 用字符串拼进 `<script>`。需要安全序列化，防止 `<`、`</script>`、Unicode separators 等破坏上下文；secret、服务端 token 和不应暴露的用户数据不得进入 hydration payload。

## 10. Router 与 Pinia 的正确组合

常见需求：guard 读取 auth store。

SPA app install 后：

```ts
router.beforeEach(to => {
  const auth = useAuthStore()
  if (to.meta.requiresAuth && !auth.isAuthenticated) {
    return { name: 'login', query: { redirect: to.fullPath } }
  }
})
```

SSR 或 app 外部模块更稳妥：

```ts
export function installGuards(router: Router, pinia: Pinia): void {
  router.beforeEach(to => {
    const auth = useAuthStore(pinia)
    // ...
  })
}
```

显式参数让所有权可见、测试可控、请求隔离可证明。

不要在 `guards.ts` 模块顶层写：

```ts
const auth = useAuthStore() // import 时可能尚未 install；SSR 还可能锁住错误实例
```

### 10.1 导航竞态

即使 Router 会取消旧 navigation finalize，你在 guard/loader 启动的外部请求仍需处理陈旧响应：

```ts
let navigationVersion = 0

router.beforeResolve(async to => {
  const version = ++navigationVersion
  const result = await loadRouteData(to)
  if (version !== navigationVersion) return false
  commitRouteData(to, result)
})
```

更完整方案会用 AbortController、query cache 和以 route key 索引的数据，确保取消、去重与 SSR hydration 一致。Router cancellation 不自动撤销你的 fetch 或数据库副作用。

## 11. 一条跨仓库调用链怎样读

例：访问 `/tickets/42`，guard 读 auth store，页面是 async component，外层有 KeepAlive/Suspense。

```text
router.push('/tickets/42')
  → matcher.resolve
  → guard pipeline
    → useAuthStore(requestPinia)
      → registry 命中或 createSetupStore
  → finalizeNavigation
  → currentRoute ref 变化
  → RouterView render 新 component VNode
  → KeepAlive 计算 cache key
    ├─ hit: activate + patch props
    └─ miss: mount async wrapper
      → loader pending
      → Suspense registers dep / fallback
      → loader resolved
      → renderer mounts content
      → boundary resolve + post effects
```

每一箭头都问：

- 谁拥有状态？
- 能否取消？
- 旧结果会不会覆盖新意图？
- deactivated 与 unmounted 有何不同？
- SSR 请求是否隔离？
- 错误进入哪里？
- 哪个行为是 public contract？

这就是源码阅读比 API 清单更有价值的地方。

## 12. 生产故障排查表

| 现象 | 第一证据 | 常见根因 |
| --- | --- | --- |
| 切 tab 后仍轮询 | activated/deactivated/unmounted 日志 | 把 deactivate 当 unmount |
| KeepAlive 状态串页 | component name/key/cache hit | key 缺失或错误 |
| Modal 样式失效 | 真实 target DOM 与 computed style | Teleport 改了物理祖先 |
| Modal 键盘不可用 | focus trace、axe、Tab 流程 | 只做了 portal，没有 dialog 行为 |
| fallback 永不消失 | Suspense deps、loader resolve/reject | 未处理 reject/嵌套依赖 |
| 路由偶发回退旧页 | pending navigation、request version | 旧 loader 回写 |
| SSR 用户串号 | app/pinia/router identity | 模块级单例跨请求 |
| store 解构不更新 | isRef/storeToRefs | 直接解构 reactive proxy |
| 插件重复记录 | subscription dispose | HMR/重复安装/无 cleanup |

## 13. 何时不要使用这些能力

- KeepAlive：页面状态本来就应由 URL/server state 恢复，实例缓存只会增加隐式状态；
- Teleport：内容无需逃离 clipping/stacking context，普通 DOM 更简单；
- Suspense：团队不能接受 experimental 风险，显式 loading/error 状态更清楚；
- 全局 Router guard：规则只属于一个 route/module，局部 loader/组件边界更合适；
- Pinia：状态只属于一个组件子树或 server query cache，局部 composable/query library 足够；
- 源码 fork：问题可以用公开扩展点解决，不值得承担长期维护。

高级不是用最多能力，而是知道不使用的理由。

## 14. 升级与回归策略

升级 Vue/Router/Pinia 时，不需要锁死内部变量名；保护这些行为：

- KeepAlive：身份、deactivate/activate、max eviction、cleanup；
- Teleport：target 变化、disabled/defer、focus/a11y、unmount；
- async/Suspense：resolve/reject/timeout/navigation-away；
- Router：route conflict、guard order 的公开语义、redirect、cancellation、scroll；
- Pinia：store isolation、hydration、action errors、plugin unsubscribe、SSR concurrency。

源码 diff 流程：

```text
读 release/migration notes
  → 在新 tag 重跑固定行为测试
  → 只对失败行为追新源码
  → 更新 ADR 与 source links
  → canary + rollback version
```

## 15. 本章速记

1. KeepAlive 缓存组件实例；deactivate 不是 unmount。
2. cache key 默认是 component type，多个实体应给稳定 key；max 是实例内存预算。
3. Teleport 保留逻辑组件树，改变物理 DOM 树；CSS、原生事件和焦点按物理树处理。
4. Async component 负责加载策略；Suspense 协调 pending branch，但不是 error boundary，且仍 experimental。
5. Router 是可取消的导航事务；matcher、guard pipeline 和 finalize 是三层。
6. Router 取消 finalize 不等于自动取消你的 fetch。
7. `defineStore` 返回 useStore；store 实际属于某个 Pinia 实例及其 registry。
8. SSR 每请求新建 app/router/pinia，外部代码显式传 pinia。
9. `storeToRefs` 只提取响应 state/getters，不提取 actions。
10. 源码结论必须固定版本，并与 public contract 分开。
