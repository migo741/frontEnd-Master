## 1. 生产事故：一行状态写入，引发三种互相矛盾的日志

一个工单页包含父级筛选器、子级表格和自动滚动逻辑：

```ts
const selectedId = ref<string | null>(null)

watch(selectedId, () => {
  console.log('pre', document.querySelector('[aria-selected="true"]'))
})

watch(
  selectedId,
  () => {
    console.log('post', document.querySelector('[aria-selected="true"]'))
  },
  { flush: 'post' },
)

async function select(id: string) {
  selectedId.value = id
  console.log('sync', document.querySelector('[aria-selected="true"]'))
  await nextTick()
  console.log('tick', document.querySelector('[aria-selected="true"]'))
}
```

日志中 `sync` 和默认 watcher 看到旧 DOM，post watcher 与 `nextTick` 才看到新 DOM。开发者于是到处加 `nextTick()`，后来又出现滚动跳动和重复请求。

真正需要建立的是阶段模型：

```text
同步阶段
  写响应式状态
  → trigger 使组件 render effect / watcher 失效
  → scheduler 只入队，不马上 patch

一次微任务 flush
  pre jobs
  → component update jobs
  → renderComponentRoot
  → patch(oldSubTree, newSubTree)
  → post jobs / mounted / updated

flush Promise 完成
  → await nextTick() 后续代码
```

`nextTick` 不是“等浏览器完成绘制”，也不是数据一致性的补丁。它只让你等待 Vue 当前调度轮次完成。需要等待 layout/paint 时，还要根据需求组合 `requestAnimationFrame`，并说明你究竟等待 DOM commit、layout 还是下一帧。

### 2.1 runtime-core 为什么不直接调用 DOM

`createRenderer(options)` 接收 host operations，例如：

```ts
interface HostOperations<Node, Element extends Node> {
  insert(child: Node, parent: Element, anchor?: Node | null): void
  remove(child: Node): void
  createElement(type: string): Element
  createText(text: string): Node
  setElementText(el: Element, text: string): void
  patchProp(el: Element, key: string, prev: unknown, next: unknown): void
}
```

runtime-core 负责 VNode、组件和 diff；runtime-dom 提供真实 DOM 操作。这解释了：

- Vue renderer 的核心可以跨平台；
- `Teleport`、`Suspense` 等不是浏览器标签，却能参与同一个 patch 协议；
- 我们可以创建记录操作的测试 renderer，而不依赖浏览器截图。

## 3. `patch()`：renderer 的交通枢纽

在固定版本中，`patch(n1, n2, container, anchor, ...)` 先处理三件事：

1. `n1 === n2`：完全同一 VNode 对象，无事可做；
2. 旧、新 VNode 不是同一类型：找到后继锚点、卸载旧树，把这次操作转为挂载；
3. 根据 `type` 与 `shapeFlag` 分流。

概念化结构：

```ts
function patch(oldVNode: VNode | null, nextVNode: VNode): void {
  if (oldVNode && !isSameVNodeType(oldVNode, nextVNode)) {
    unmount(oldVNode)
    oldVNode = null
  }

  switch (nextVNode.type) {
    case Text:
      return processText(oldVNode, nextVNode)
    case Fragment:
      return processFragment(oldVNode, nextVNode)
  }

  if (nextVNode.shapeFlag & ShapeFlags.ELEMENT) {
    return processElement(oldVNode, nextVNode)
  }
  if (nextVNode.shapeFlag & ShapeFlags.COMPONENT) {
    return processComponent(oldVNode, nextVNode)
  }
  if (nextVNode.shapeFlag & ShapeFlags.TELEPORT) {
    return TeleportImpl.process(/* renderer internals */)
  }
}
```

这段简化代码只用于理解分派，不可复制替代真实源码。真实 `patch` 还携带 parent component、Suspense boundary、namespace、slot scope ids、优化标记等上下文。

### 3.1 `type + key` 定义身份

`isSameVNodeType` 的核心不是“DOM 看起来一样”，而是 type 与 key 的身份判断。下面两次渲染不应复用同一个组件实例：

```vue
<UserEditor v-if="mode === 'user'" key="editor" />
<TeamEditor v-else key="editor" />
```

key 一样但 type 不同，旧树仍要卸载。反过来，在 siblings 列表里同 type、同 key 表示同一个逻辑实体；组件本地状态、DOM 节点和 effect scope 都会随该身份复用。

### 3.2 `anchor` 不是 index

DOM 插入 API 需要“插到哪个真实节点前面”。Fragment、组件、Teleport 可能对应多个或异地 host nodes，不能把 VNode 数组下标直接当 DOM 位置。renderer 因此持续传递 anchor，并通过 `getNextHostNode`、VNode 的 `el` / `anchor` 等信息解析真实插入点。

## 4. 组件挂载调用链

普通同步有状态组件首次挂载的主路径：

```text
patch(null, componentVNode)
  → processComponent
    → mountComponent
      → createComponentInstance
      → setupComponent
      → setupRenderEffect
        → componentUpdateFn（mount 分支）
          → beforeMount hooks
          → renderComponentRoot(instance)
          → patch(null, instance.subTree)
          → initialVNode.el = subTree.el
          → queuePostRenderEffect(mounted hooks)
```

这里有三个必须分清的对象：

| 对象 | 它表示什么 | 更新时怎样变化 |
| --- | --- | --- |
| component VNode | 父组件本轮如何使用子组件 | 父 render 后产生新的 VNode |
| component instance | 某次挂载的持久运行时实例 | type+key 相同通常复用 |
| `instance.subTree` | 子组件上次 render 的结果 | 新 render 结果与旧 subTree 做 patch |

### 4.1 为什么 mounted hook 不是同步调用

组件 render 后，子树还要真正 patch。`mounted` 被放到 post-render 阶段，保证它运行时本轮 DOM 提交已经完成。若存在 Suspense，post-render effect 还可能被 boundary 暂存，等依赖解决后再提交。

### 4.2 async setup 的分支

当 `setup()` 返回 Promise，实例保存 async dependency。处在 Suspense boundary 中时，boundary 注册依赖；非 hydration 场景会先放一个 comment placeholder。依赖解决后才建立正常 render effect。

这解释了为什么：

- async `setup()` 与普通生命周期时序不同；
- 没有 `<Suspense>` 时不能想当然地把 fallback、错误和超时都交给 Vue；
- 服务端渲染与 hydration 还存在另外的入口，不能用 SPA 的单一路径推导全部行为。

## 5. 更新调用链：为什么父 render 不必让所有子组件重跑

复用组件 VNode 时进入 `updateComponent(n1, n2, optimized)`：

```text
拿到旧 VNode 上的 instance
  ↓
shouldUpdateComponent(oldVNode, newVNode, optimized)
  ├─ false：复制 el，更新 instance.vnode，不运行子 render
  └─ true：instance.next = newVNode，运行 instance.update()
```

当更新真正执行，`componentUpdateFn` 走 update 分支：

```text
应用 next VNode
  → updateComponentPreRender
    → update props / slots
    → flush 当前实例的 pre callbacks
  → renderComponentRoot(instance)
  → patch(oldTree, newTree)
  → instance.subTree = nextTree
  → queue updated hooks
```

高级优化不是到处 `computed` 或 `v-memo`，而是先问：

- 父组件为什么重新 render？
- 子组件收到的 props 是否真的变化？
- slot 是否被标记为动态？
- 每行是不是收到一个全局变化值，而不是已经计算好的稳定布尔值？
- key 是否稳定？
- compiler 是否能保留 patch flag / block 优化？

`shouldUpdateComponent` 是跳过组件 render 的边界，而 patch flags/dynamic children 是组件内部跳过稳定节点的边界。两者层次不同。

## 6. Render Effect：响应式系统与 renderer 的接缝

`setupRenderEffect` 创建一个 `ReactiveEffect(componentUpdateFn)`。其核心关系可简化为：

```ts
const effect = new ReactiveEffect(componentUpdateFn)
const update = effect.run.bind(effect)
const job = effect.runIfDirty.bind(effect)

job.id = instance.uid
job.i = instance
effect.scheduler = () => queueJob(job)

update() // 首次运行，收集 render 读取到的依赖
```

重要区别：

- `effect.run()`：立即执行 effect；
- `effect.scheduler()`：依赖变化时决定何时执行；
- `runIfDirty()`：flush 时再次确认是否仍需运行；
- `instance.uid`：给 job 一个稳定排序 ID，使父实例通常先于子实例。

当 render 读取 `selectedId.value`，响应式系统把 render effect 与该 dep 建立联系。写入时 dep 通知 effect；effect 不直接 patch，而是把 job 交给 scheduler。因此同一同步调用栈内多次写入通常只导致一轮组件更新：

```ts
count.value++
count.value++
count.value++
// 同一组件 update job 在当前队列中去重
```

注意：去重的是 job，不是“所有业务副作用”。`flush: 'sync'` watcher、在不同任务中的写入、每次显式网络调用都可能执行多次。

## 7. Scheduler 的四个不变量

固定版本的 `scheduler.ts` 有主队列 `queue`、待执行 post callbacks、当前 flush Promise 和若干 job flags。

### 7.1 同一 job 一轮只排一次

`QUEUED` flag 防止重复入队。finally 中即使某个 job 抛错，也要清理剩余 job 的 flag；否则它们可能永远无法再次入队。这是异常安全不变量。

### 7.2 父组件通常先于子组件

实例创建时父早于子，uid 通常更小。主队列按 job id 升序；如果父更新期间卸载子组件，调度器可跳过已 disposed 的子 job。

这不是业务可依赖的“所有小 id 都先执行”API。它是内部实现为组件拓扑服务的排序规则。

### 7.3 pre job 在对应组件更新前

pre watcher 与组件 update job 使用关联 id，并带 `PRE` flag。二分插入时，同 id 的 pre job 放在组件 update 前。`updateComponentPreRender` 还会针对当前实例 flush pre callbacks，让 props/slots 更新后的 watcher 能在 render 前稳定状态。

### 7.4 post job 在 DOM commit 后

post callbacks 被去重并排序，在主队列清空后执行。mounted、updated 和 `flush: 'post'` watcher 都依赖这一阶段。

### 7.5 新任务在 flush 中产生怎么办

flush 的 finally 会：

1. 清理队列；
2. 执行 post callbacks；
3. 释放 `currentFlushPromise`；
4. 若期间又加入主 job 或 post callback，继续 drain。

因此“一轮”可能包含嵌套产生的新工作。不要拿一个静态三段图替代真实队列状态。

### 7.6 递归更新保护

开发模式会统计同一 job 在一次 drain 中出现的次数，固定版本上限为 100，超过后报告 maximum recursive updates。上限数字是内部细节，真正的错误通常是：

```ts
watch(source, () => {
  source.value++ // 回调持续修改自己的输入，且没有收敛条件
})
```

或在 `updated` / render 中写回本次渲染读取的状态。正确做法是明确状态机与终止条件，不是提高限制。

## 8. `watch` flush、生命周期与 `nextTick`

| 阶段 | 典型工作 | 此时组件自己的 DOM |
| --- | --- | --- |
| 同步调用栈 | 写状态、`flush:'sync'` watcher | 通常仍是旧 DOM |
| pre | 默认 watcher、`beforeUpdate` 附近的准备 | 组件本轮 patch 前 |
| component job | render + patch | 正在变更 |
| post | `flush:'post'`、mounted、updated | 本轮 DOM 已提交 |
| `nextTick` continuation | 当前 flush Promise 完成后 | 本轮 Vue flush 已完成 |
| browser layout/paint | 浏览器渲染管线 | 不由 `nextTick` 保证 |

### 8.1 怎样选择

- 业务派生：优先 computed 或普通函数，不读 DOM；
- 状态变化触发取消/请求：默认 pre 通常足够，必须做失效清理；
- 读取本组件更新后的 DOM：post watcher 或 mounted/updated；
- 在一次命令后等待 Vue 提交：`await nextTick()`；
- 等待布局稳定或下一帧：在解释目标后使用 `requestAnimationFrame`；
- 极少量必须同步的桥接：`flush: 'sync'`，同时评估批处理丢失和递归风险。

### 8.2 外部 Promise 的顺序不是一句“微任务先后”能概括

Vue flush 使用 Promise 微任务。你自己注册的 `Promise.then`、`queueMicrotask` 与 `nextTick` 的相对顺序取决于它们何时入队。应写可执行实验，不要背一个脱离注册顺序的日志答案。

## 9. Keyed Diff 的五段式主路径

`patchKeyedChildren(c1, c2, ...)` 处理同一父级下的新旧 keyed children。固定版本的主要阶段：

1. 从头同步相同 VNode；
2. 从尾同步相同 VNode；
3. 旧列表先耗尽：挂载剩余新节点；
4. 新列表先耗尽：卸载剩余旧节点；
5. 两边都有未知中段：建立 key map、patch/unmount、检测移动、LIS、反向 mount/move。

为什么先首尾同步？常见 UI 更新是尾部追加、尾部删除、头部小范围变化；快速路径可以避免建立 Map 和计算 LIS。

### 9.1 手算真实例子

```text
old: A B C D E
new: A C B F E
```

首尾同步后：

```text
A 已 patch
E 已 patch

old unknown: B C D       old index 1..3
new unknown: C B F       new index 1..3
```

建立 `keyToNewIndexMap`：

```text
C -> 1
B -> 2
F -> 3
```

`newIndexToOldIndexMap` 长度为 3，初始全 0。保存旧 index + 1，因为 0 必须表示“全新节点”：

| 遍历旧节点 | 新位置 | 写入后的数组 | 动作 |
| --- | ---: | --- | --- |
| B（old 1） | 2 | `[0, 2, 0]` | patch B |
| C（old 2） | 1 | `[3, 2, 0]` | patch C，并发现新 index 下降，`moved=true` |
| D（old 3） | 无 | `[3, 2, 0]` | unmount D |

对非零旧位置序列 `[3, 2]` 求 LIS，最长长度只有 1。固定实现得到一个稳定索引骨架；随后从右向左：

```text
F：数组值为 0 → mount before E
B：若处于 LIS → 保持
C：不在 LIS → move before B
```

最终为 `A C B F E`。

### 9.2 为什么保存 old index + 1

旧 index 可能恰好是 0。如果直接保存 index，0 同时表示“来自 old[0]”与“新节点”，算法无法区分。`i + 1` 是一个小但关键的不变量。

### 9.3 为什么从右向左

右侧目标节点已经就位，可直接充当 `insertBefore` 的 anchor。若从左向右，目标右邻居可能尚未挂载或移动，锚点更难稳定。

### 9.4 LIS 优化的边界

LIS 的目标不是求业务排序，而是在已经确认可复用的节点中，找出相对次序已经递增的一组，减少 DOM move。

- 新节点（map 中为 0）不参加稳定子序列；
- 没检测到移动时根本不求 LIS；
- LIS 优化不了错误 key；
- DOM move 少不等于总成本一定小，组件 render、layout、图片和第三方控件仍可能占主导。

## 10. key 的生产契约

一个正确 key 必须：

1. 在同一 siblings 范围唯一；
2. 跨 render 稳定；
3. 表示业务实体身份，而非当前位置；
4. 不在 render 中随机生成。

错误案例：

```vue
<!-- 重排时组件状态跟着位置走 -->
<EditableRow v-for="(row, index) in rows" :key="index" :row="row" />

<!-- 每轮都重建，丢失焦点、状态和缓存 -->
<ChartPanel :key="Math.random()" />

<!-- 标题可修改、可重复，不是身份 -->
<DocumentTab v-for="doc in docs" :key="doc.title" :doc="doc" />
```

有意重置子树时可以换 key，例如文档编辑器切换不同 `documentId`。这是一项明确的生命周期策略，应有测试证明旧 effect、请求与 DOM 引用被清理。

重复 key 在开发模式会给警告，但你不能把生产正确性寄托在警告上。数据入口应验证 ID 唯一性，列表测试应覆盖插入、删除、重排与本地状态保持。

## 11. DOM move 为什么不等于组件 remount

同 type+key 的 VNode 在 keyed diff 中可被 `move()`，对应组件实例仍然存在；`mounted` 不应因为列表重排再次触发。若你观察到 remount，优先检查：

- key 是否变化；
- type 是否变化；
- 条件分支是否把节点移出原 siblings 边界；
- 父级是否整体被换 key；
- HMR / dev-only 行为是否干扰；
- 是否把业务日志误放在 render/setup 可重复路径。

`TransitionGroup` 会在 renderer move 之外增加位置记录和动画阶段；这属于第 20 章内置组件专题。

## 12. 性能判断：算法复杂度只是第一层

unknown keyed middle 大体需要：

- 建立新 key map：`O(n)`；
- 遍历旧中段：`O(n)`；
- LIS：`O(n log n)`；
- patch / mount / move / unmount：与实际子树工作相关。

但生产体验还取决于：

- render effect 依赖面；
- VNode 分配与 GC；
- DOM mutation 数量；
- style recalculation、layout、paint；
- 同步第三方组件的成本；
- 一帧内 job 数量；
- 长列表是否应该虚拟化，而不是继续优化全量 diff。

不要看到 `O(n log n)` 就断言 renderer 是瓶颈。先用 Vue Devtools、Chrome Performance、User Timing 和可重复 fixture 定位 render、patch、layout 哪一段超预算。

### 12.1 合理的测量实验

固定以下条件：

- 同一浏览器、硬件和构建模式；
- warm-up 后重复采样；
- 多个规模：100、1,000、10,000；
- 分开 append、reverse、随机 shuffle、局部插入；
- key 正确且数据生成固定 seed；
- 同时报告 duration、long task、DOM nodes、内存，而不是只报一次平均值。

## 13. 用源码排查四类故障

### 13.1 DOM 测量总是旧值

证据链：

```text
状态写入只 queueJob
→ 当前同步栈没有 patch
→ 默认 watcher 属于 pre
→ post / nextTick 才在本轮 DOM commit 后
```

修复不是全局加 `setTimeout`，而是把 DOM 测量放到正确 phase，并在卸载/连续变化时取消过期工作。

### 13.2 一个同步动作触发多次请求

组件 job 会去重，但 watcher 中的业务请求不天然 singleflight，也不自动取消旧请求。检查 watcher 是否多实例注册、是否同时存在 route watch 与 component watch、是否用 `flush:'sync'` 绕过批处理，以及 cleanup 是否 abort 旧请求。

### 13.3 输入框内容跑到另一行

先记录 old/new key 序列和组件 instance uid。如果同一个 uid 被复用给另一个实体，通常是 key 使用 index 或重复业务字段。问题位于身份契约，不应靠 `forceUpdate` 修复。

### 13.4 Maximum recursive updates

记录每个写入点：render、computed setter、watch callback、updated hook。画出：

```text
effect A reads x
  → callback writes y
  → effect B reads y
  → callback writes x
  → 回到 A
```

找到环后定义单向数据流、状态机收敛条件或事件边界。不要依赖内部递归上限。

## 14. 源码实验的安全边界

可以做：

- clone 固定 tag，在本地测试中插日志；
- 用 custom renderer 记录 host operations；
- 写最小 SFC fixture，断点跟调用链；
- 在 Vue 官方测试附近增加复现用例；
- 比较 3.5.42 与未来版本的行为和内部差异。

不应做：

- 业务代码导入未公开的 `runtime-core/src/*`；
- monkey patch scheduler 或 renderer 作为生产方案；
- 把内部 flag 数字、私有字段名写进业务契约；
- 只凭当前源码推断所有未来小版本；
- 在未跑测试的 fork 上长期承载生产。

源码阅读产物应写成：

```text
公开可依赖的语义
  + 当前固定版本如何实现
  + 哪些是内部细节
  + 最小复现实验
  + 升级时怎样重新验证
```

## 16. 速记

1. `patch` 按 VNode type/shape 分派，type+key 决定身份。
2. 组件实例持久存在；每次 render 产生新 subTree，与旧 subTree patch。
3. render 是 `ReactiveEffect`，依赖变化后由 scheduler 排 job。
4. 主 job 去重并大体按父到子执行；pre 在组件更新前，post 在 DOM commit 后。
5. `nextTick` 等 Vue 当前 flush，不保证浏览器 paint。
6. keyed diff 先首尾快速路径，再处理中段；`newIndexToOldIndexMap` 的 0 表示新节点。
7. LIS 用于减少 move，不修复错误 key。
8. 高级源码能力是用调用链和测试解释现象，而不是背内部变量。
