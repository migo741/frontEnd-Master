# 第 07 章：Vue Router——导航事务、数据竞态与权限边界

> 生产基线：Vue 3.5.42、Vue Router 5.3.0。Router 不是“URL 切组件”的小工具，而是浏览器历史、异步任务、用户意图与应用生命周期的协调器。

## 0. 事故现场：先渲染再鉴权的一帧泄漏

运营后台把权限判断写在页面的 `onMounted`：

```ts
onMounted(async () => {
  if (!(await canAccess(route.meta.permission))) {
    await router.replace('/403')
  }
})
```

慢网下，敏感页面先渲染 300ms，再跳走；埋点记录了一次错误页面曝光；页面 setup 已经发出数据请求。另一个 bug 是用户从 `/ticket/1` 快速跳到 `/ticket/2`，1 的慢响应最后覆盖 2。

这两个事故来自同一误解：**导航不是一次同步赋值，而是一段可能成功、重定向、取消、失败或被新导航取代的异步事务。**

```text
用户意图 push(/b)
  -> 路由匹配
  -> 离开/更新/进入守卫
  -> 数据或权限前置判断
  -> 导航确认（URL 与 route 生效）
  -> DOM 更新
  -> afterEach / scroll
```

前端守卫负责 UX 与流量控制，后端授权负责安全。二者缺一不可，但不能互相替代。

## 1. 路由记录是应用契约

### 1.1 用路由元信息表达需求，不把逻辑塞进页面

```ts
// router-meta.d.ts
import 'vue-router'

declare module 'vue-router' {
  interface RouteMeta {
    title: string
    requiresAuth: boolean
    permission?: PermissionCode
    keepAlive?: boolean
    dataPolicy?: 'before' | 'after'
  }
}
```

```ts
const routes: RouteRecordRaw[] = [
  {
    path: '/tickets/:id',
    name: 'ticket-detail',
    component: () => import('@/features/ticket/pages/TicketDetailPage.vue'),
    meta: {
      title: '工单详情',
      requiresAuth: true,
      permission: 'ticket:read',
      keepAlive: false,
      dataPolicy: 'before',
    },
    props: route => ({ ticketId: String(route.params.id) }),
  },
]
```

`meta` 是匹配记录的合并视图，父级元信息可向子级生效。字段要有稳定语义：`permission` 表示访问页面所需能力，而不是把任意 callback 塞进去。

### 1.2 params、query 和 history state

- `params`：资源身份和层级，如 `/projects/:projectId/tickets/:ticketId`；
- `query`：可选视图状态，如筛选、分页、排序；
- `hash`：文档内锚点；
- history `state`：短期导航附加信息，不适合作为可复制 URL 的核心状态。

所有路由输入都来自外部。TypeScript 类型不能验证地址栏字符串；进入领域层前要解析：

```ts
function parsePositiveInt(value: unknown, fallback: number): number {
  const raw = Array.isArray(value) ? value[0] : value
  const parsed = typeof raw === 'string' ? Number(raw) : NaN
  return Number.isInteger(parsed) && parsed > 0 ? parsed : fallback
}

const page = computed(() => parsePositiveInt(route.query.page, 1))
```

## 2. 完整导航解析流程

从已挂载页面 A 导航到页面 B，核心顺序可记为：

```text
1 失活组件 beforeRouteLeave
2 全局 beforeEach
3 复用组件 beforeRouteUpdate
4 新路由记录 beforeEnter
5 解析异步路由组件
6 激活组件 beforeRouteEnter
7 全局 beforeResolve
8 导航确认
9 全局 afterEach
10 DOM 更新 / beforeRouteEnter 回调 / scrollBehavior
```

具体细节以当前 Router 官方文档为准；工程上最重要的是各阶段职责：

- `beforeRouteLeave`：保护页面本地未提交意图；
- `beforeEach`：登录态、通用重定向、租户上下文；
- `beforeRouteUpdate`：同一组件实例参数改变时重取/重置；
- `beforeEnter`：某条路由特有的静态规则；
- `beforeResolve`：所有组件已解析、确认前的最后异步门，适合昂贵前置数据或能力检查；
- `afterEach`：已确认后的标题、埋点、遥测；不能取消导航。

### 2.1 守卫返回值

```ts
router.beforeEach(async (to) => {
  const session = useSessionStore()

  if (!to.meta.requiresAuth) return true

  if (!session.ready) await session.restore()

  if (!session.isAuthenticated) {
    return {
      name: 'login',
      query: { redirect: safeInternalPath(to.fullPath) },
      replace: true,
    }
  }

  if (to.meta.permission && !session.can(to.meta.permission)) {
    return { name: 'forbidden', replace: true }
  }

  return true
})
```

守卫可以返回：

- `true`/`undefined`：继续；
- `false`：取消，URL 会恢复；
- route location：重定向，产生新导航；
- 抛出错误：导航失败，并触发错误处理。

避免旧式 `next` 风格；多分支漏调或重复调用很难审查。重定向必须保证终止条件，否则形成循环：登录页也标 `requiresAuth` 就会无限跳。

### 2.2 `afterEach` 必须辨认失败

```ts
router.afterEach((to, from, failure) => {
  if (failure) {
    navigationMetrics.failed({
      from: from.name,
      to: to.name,
      kind: classifyNavigationFailure(failure),
    })
    return
  }

  document.title = `${to.meta.title} · OpsBoard`
  pageViews.track({ routeName: String(to.name) })
})
```

不要把取消或重复导航算作成功 PV。埋点只记录 route name 和脱敏维度，不应把 URL 中的搜索词、token 或个人信息原样上报。

## 3. Typed Routes：消灭拼写错误，不能消灭运行时脏数据

类型化路由从 Vue Router 4.4 起进入官方能力，当前 Router 5.3 继续提供并扩展相关工具。生产项目通常用官方生态生成器或构建期插件从文件/配置生成 route name、params 类型，而不是手写一份易漂移的巨大映射。

概念上，类型系统应让下面错误在编译期失败：

```ts
router.push({
  name: 'ticket-detail',
  params: { id: 'T-42' },
})

// ❌ 如果类型映射要求 id，此调用缺少 params
router.push({ name: 'ticket-detail' })
```

但 typed routes 不会把地址栏 `/tickets/not-a-valid-id` 变成可信值。仍需：

- 运行时解析 params/query；
- 领域 ID 格式验证；
- 未找到返回 404；
- 不把 `route.params.id as TicketId` 当验证。

类型生成要纳入 CI，检测生成物与 route source 是否漂移；避免开发机生成而 CI 未生成。

## 4. 两种数据加载策略：先导航还是先数据

### 4.1 导航后获取（after navigation）

页面先出现骨架，再加载：

```vue
<script setup lang="ts">
const route = useRoute()
const ticketId = computed(() => parseTicketId(route.params.id))

const { data, pending, error, reload } = useTicketQuery(ticketId)
</script>

<template>
  <TicketSkeleton v-if="pending && !data" />
  <ErrorState v-else-if="error" :error="error" @retry="reload" />
  <TicketView v-else-if="data" :ticket="data" />
</template>
```

优点：URL 快速响应，有自然骨架/流式体验；缺点：页面必须处理 loading/error/empty，且切参时要治理竞态。

适合大多数可独立展示骨架的业务页。

### 4.2 导航前获取（before navigation）

在 `beforeResolve` 或路由专属 loader 中准备关键数据：

```ts
router.beforeResolve(async (to) => {
  if (to.name !== 'ticket-detail') return true

  const id = parseTicketId(to.params.id)
  if (!id) return { name: 'not-found', replace: true }

  try {
    await ticketQueries.ensureDetail({
      tenantId: requireTenant(to),
      id,
    })
    return true
  } catch (error) {
    if (isNotFound(error)) return { name: 'not-found', replace: true }
    throw error
  }
})
```

优点：确认导航时已有数据，避免敏感页面先闪；缺点：URL/页面看起来“卡住”，需要全局进度、取消和错误路由。

适合权限/存在性决定能否进入、或不希望空页面闪烁的关键页面。不要把所有非关键请求都塞进守卫，导航会成为瀑布。

### 4.3 混合策略

常见生产方案：

- 守卫只确认会话、租户、粗粒度能力和关键实体存在；
- 主实体可在确认前 `ensure`；
- 次要 Tab、统计、推荐在页面内并行获取；
- 已有新鲜缓存时立即继续；
- 全局进度只覆盖真正阻塞导航的工作。

## 5. 参数变化与异步竞态

Vue 会复用同一路由记录的组件实例：`/tickets/1 -> /tickets/2` 不一定卸载重建，因此只在 `onMounted` 取数据是错误的。

### 5.1 最小 latest-wins loader

```ts
import { onScopeDispose, ref, watch, type Ref } from 'vue'

type LoadState<T> =
  | { status: 'idle'; data: null; error: null }
  | { status: 'loading'; data: T | null; error: null }
  | { status: 'success'; data: T; error: null }
  | { status: 'error'; data: T | null; error: unknown }

export function useRouteResource<K, T>(
  key: Ref<K | null>,
  load: (key: K, signal: AbortSignal) => Promise<T>,
) {
  const state = ref<LoadState<T>>({ status: 'idle', data: null, error: null })
  let generation = 0
  let controller: AbortController | null = null

  const stop = watch(key, async (next) => {
    const current = ++generation
    controller?.abort('route changed')
    controller = null

    if (next === null) {
      state.value = { status: 'idle', data: null, error: null }
      return
    }

    controller = new AbortController()
    const previous = state.value.data
    state.value = { status: 'loading', data: previous, error: null }

    try {
      const data = await load(next, controller.signal)
      if (current === generation) {
        state.value = { status: 'success', data, error: null }
      }
    } catch (error) {
      if (current !== generation || isAbortError(error)) return
      state.value = { status: 'error', data: previous, error }
    }
  }, { immediate: true })

  onScopeDispose(() => {
    stop()
    controller?.abort('scope disposed')
  })

  return { state }
}
```

Abort 与 generation 各解决一半问题：

- Abort 节省客户端工作，但服务端可能已经处理，某些 Promise 也不支持取消；
- generation 防止任何旧结果提交到新视图，是最终正确性门。

### 5.2 不要双向 watcher 制造 URL 循环

推荐 URL 为筛选真相源，UI 事件用 `router.replace` 写回：

```ts
const filter = computed(() => decodeFilter(route.query))

async function setStatus(status: TicketStatus | null) {
  await router.replace({
    query: encodeFilter({ ...filter.value, status, page: 1 }),
  })
}
```

不要另建 `const localFilter = ref(...)`，再用两个 watcher 互相同步；规范化差异会导致循环和历史污染。高频输入先在本地编辑，提交/防抖后一次写 URL。

## 6. RBAC：前端控制体验，后端执行授权

### 6.1 分三层

```text
路由守卫：是否允许进入页面（UX / 避免无意义请求）
组件能力：按钮、字段、操作是否可见/可用（UX）
服务端授权：每一次读写是否允许（安全边界）
```

即使前端删除按钮，用户仍可构造 HTTP 请求；即使 token 内带角色，服务端也要校验资源和租户。前端 permission code 不应等同于“安全已完成”。

### 6.2 防止首屏闪烁

会话恢复应该有三态，而不是 `false` 默认：

```ts
type SessionStatus = 'unknown' | 'authenticated' | 'anonymous'
```

`unknown` 时显示应用壳或恢复页，不先渲染受保护路由。全局守卫只触发一次共享 `restorePromise`，避免并发导航重复 `/me`。

### 6.3 登录 redirect 必须防开放重定向

```ts
function safeInternalPath(value: unknown): string {
  if (typeof value !== 'string') return '/'
  if (!value.startsWith('/') || value.startsWith('//')) return '/'
  return value
}
```

登录成功后直接 `window.location = route.query.redirect` 可能把用户送到攻击者站点。只接受应用内相对路径，或用 route name 白名单。

### 6.4 动态路由不是权限证据

`addRoute/removeRoute` 可用于按模块加载和减少菜单噪音，但：

- 刷新深链时必须先恢复会话再解析动态路由；
- logout 要清理动态记录；
- 多次添加需幂等；
- 构建产物中代码存在与否不等于用户有权限；
- 后端仍必须授权。

很多应用无需动态路由：静态 route + meta permission + 服务端授权更可预测。

## 7. 未提交表单与离开守卫

```ts
onBeforeRouteLeave(async () => {
  if (!draft.dirty) return true

  const decision = await confirmLeave({
    title: '有未保存修改',
    choices: ['stay', 'discard'],
  })

  return decision === 'discard'
})
```

边界：

- 只覆盖 Router 内导航；关闭标签页/刷新需要 `beforeunload`，浏览器只允许通用提示；
- 自动保存时 `dirty` 要区分本地修改、保存中、已确认；
- 守卫弹窗必须可访问、可取消，避免多次导航出现多个 dialog；
- 不要在守卫中静默保存后无论成功失败都放行。

## 8. Scroll、KeepAlive 与缓存身份

### 8.1 `scrollBehavior`

```ts
const router = createRouter({
  history: createWebHistory(),
  routes,
  scrollBehavior(to, from, savedPosition) {
    if (savedPosition) return savedPosition
    if (to.hash) return { el: to.hash, behavior: 'smooth', top: 72 }
    if (to.name === from.name) return false
    return { top: 0 }
  },
})
```

`savedPosition` 主要用于 popstate 前进/后退。异步内容会改变页面高度；必要时返回 Promise 等待关键布局，但不要无限等待资源。

### 8.2 KeepAlive 不是页面数据缓存

```vue
<RouterView v-slot="{ Component, route }">
  <KeepAlive :include="['TicketListPage']" :max="8">
    <component
      :is="Component"
      v-if="route.meta.keepAlive"
      :key="keepAliveKey(route)"
    />
  </KeepAlive>
  <component
    :is="Component"
    v-if="!route.meta.keepAlive"
    :key="route.fullPath"
  />
</RouterView>
```

需要谨慎：

- `include/exclude` 匹配组件 `name`，匿名异步组件会让策略失效；
- key 决定实例身份。`fullPath` 会为每个筛选组合建实例，可能爆内存；
- activated/deactivated 不等于 mounted/unmounted；资源订阅可能要在 `onActivated/onDeactivated` 控制；
- KeepAlive 保存组件实例和本地 UI，不替代 query cache；
- 缓存页回来仍需根据 stale 策略重验证服务端数据。

列表返回位置可以用 Router 的 scroll restoration + URL + query cache 实现，未必需要缓存整个页面实例。

## 9. 路由错误、懒加载失败与可观测性

```ts
router.onError((error, to) => {
  reportError(error, {
    routeName: to?.name,
    phase: 'router',
  })
})
```

部署后旧 HTML 可能引用已删除的 chunk，动态 import 会失败。恢复策略要有界：

1. 识别 chunk load 类错误；
2. 每个 build/version 最多自动刷新一次；
3. 再失败显示可操作的错误页；
4. 不对所有导航错误无限 reload。

导航指标建议：

- navigation start -> confirmed；
- confirmed -> critical content rendered；
- 守卫耗时按阶段；
- cancellation/redirect/error 分类；
- 路由名称而非原始敏感 URL。

## 10. 反例与排障

| 反例 | 后果 | 修复方向 |
|---|---|---|
| `onMounted` 才鉴权 | 页面先闪、请求已发 | 导航确认前恢复会话/守卫 |
| 守卫只判断 `localStorage.role` | 可篡改、过期 | `/me` + 后端授权 |
| 每次守卫都请求 `/me` | 导航瀑布 | singleflight 恢复 + session cache |
| route param 只在 mount 读取 | 组件复用时旧数据 | watch param + abort/generation |
| 两个 watcher 同步 URL/本地 | 循环、历史污染 | URL 单一真相源 |
| `afterEach` 总记成功 PV | 取消也计数 | 检查 failure |
| `redirect` 接受任意 URL | 开放重定向 | 内部路径/路由名白名单 |
| `KeepAlive :key=fullPath` 无上限 | 实例爆炸 | 明确身份和 `max` |
| 动态路由当安全机制 | 可绕过 | 后端逐请求授权 |

排障先问：这次导航最终是成功、取消、重定向还是错误？然后记录 `from/to name`、守卫阶段、navigation id、请求 generation。不要只在页面里 `console.log(route)`，响应式 route 对象会在控制台展开时显示新值，容易误判历史。

## 11. 速记与自检

> 导航是一段可取消的异步事务；URL 是可分享视图状态；前端守卫优化体验，后端授权才是安全边界。

你应能不看答案说明：

1. `beforeEach`、`beforeResolve`、`afterEach` 的职责差异；
2. 为什么 `afterEach` 要检查 navigation failure；
3. 导航前与导航后数据加载各自的 UX 和失败模型；
4. Abort 为什么仍需 generation/sequence；
5. typed routes 为什么不能替代运行时 params 校验；
6. `unknown/authenticated/anonymous` 三态如何避免权限闪烁；
7. 前端 RBAC 为什么不构成安全边界；
8. `redirect` 参数怎样形成开放重定向；
9. KeepAlive key 选错会怎样；
10. 同一路由记录参数变化为何不一定重新挂载组件。

- “请画出 Vue Router 从 leave guard 到 afterEach 的时序，并举每阶段适合的任务。”
