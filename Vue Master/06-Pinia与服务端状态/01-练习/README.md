# 第 06 章练习：状态所有权与并发一致性

> 规则：只做两题。题 1 训练“状态属于谁”，题 2 训练“缓存怎样在失败和乱序中保持正确”。先写决策和不变量，再写代码。

## 题 1：为多租户 OpsBoard 设计状态地图（机制题）

### 背景

OpsBoard 是一个多租户工单后台。登录用户可以切换租户；列表页支持筛选、分页、列宽和列显隐；详情页可以编辑草稿；服务端通过 WebSocket 通知工单版本变化；应用支持 SSR 首屏和多标签页。

需要处理这些候选状态：

1. 当前用户摘要；
2. 当前租户 ID；
3. 权限代码集合；
4. 列表 `status/assignee/page/pageSize`；
5. 当前鼠标 hover 的行；
6. 列宽和列显隐；
7. 工单列表响应；
8. 工单详情响应；
9. 尚未提交的编辑草稿；
10. 全局 toast 队列；
11. WebSocket 实例和重连次数；
12. 用户 token；
13. “是否正在保存”；
14. 从列表派生的“逾期工单数”。

### 契约

输出以下内容：

1. 一张状态地图，每项必须写：`owner`、唯一真相源、生命周期、持久化策略、失效/清理时机、SSR 注意点；
2. 一个 Pinia `useSessionStore`，同时维护 `user/tenantId/permissionCodes` 的不变量；
3. 一个版本化的表格偏好持久化 envelope 与 `v1 -> v2` 迁移函数；
4. 画出“切换租户”的顺序：取消请求、断开资源、清缓存、切上下文、重新加载；
5. 说明哪些状态**不能**进入 Pinia，为什么。

### 规模与约束

- 10 万用户、每用户最多 30 个租户；
- 同一浏览器可能开 3 个标签页；
- SSR Node 进程会并发处理不同用户；
- 不允许在 `localStorage` 保存 token、权限集合或服务端工单数据；
- URL 必须可复制后恢复列表视图；
- TypeScript 开启 `strict`，不允许用 `as` 跳过反序列化校验。

### 失败语义

- 持久化数据损坏或版本未知：应用仍能启动，使用默认偏好；
- 切换租户过程中任一步失败：不能展示上一个租户的缓存；
- 多标签页冲突：必须说明采用 last-write-wins、提示冲突或不做同步中的哪一种；
- SSR：两个请求的状态绝不能共享。

### 验收清单

- [ ] 每项只有一个权威 owner，派生值没有重复存储；
- [ ] 列表筛选和分页在 URL 中；
- [ ] 服务端数据标为可失效缓存，而不是会话真相；
- [ ] WebSocket 被视为资源而不是普通可序列化状态；
- [ ] `useSessionStore` 使用意图型 action，并能彻底清空租户上下文；
- [ ] 持久化有白名单、版本、运行时验证、损坏降级；
- [ ] SSR 使用每请求 `createPinia()`；
- [ ] 至少写 4 个单元测试名称及其断言目标。

### 发散问题

- 草稿是否应该跨刷新保存？若保存，如何避免另一个标签页覆盖？
- 如果租户切换频繁，是清空全部旧租户缓存，还是按租户隔离并保留？决策取决于什么？

## 题 2：实现可回滚、抗乱序的工单更新（生产开放题）

### 背景

列表 key 由 `tenantId/status/assignee/page/pageSize` 决定，详情 key 由 `tenantId/id` 决定。用户可以快速把同一工单标题从 `A` 改成 `B`，再改成 `C`。服务端每个实体含单调递增的 `version`，更新接口要求 `expectedVersion`，冲突返回 `409`。WebSocket 也可能重复或乱序推送快照。

### 契约

设计并实现一个最小查询/写入协调层，公开：

```ts
interface TicketMutationCoordinator {
  updateTitle(input: {
    tenantId: string
    id: string
    title: string
    expectedVersion: number
  }): Promise<Ticket>

  acceptPush(event: {
    tenantId: string
    id: string
    snapshot?: Ticket
  }): void
}
```

你的方案必须说明或实现：

1. 稳定的 list/detail query key；
2. 同一实体两个写入是排队、取消旧写入，还是并发 + sequence，三选一并证明不会让旧响应覆盖新值；
3. 乐观更新前取消相关读取，保存可回滚状态；
4. 网络失败回滚，`409` 进入冲突状态，成功后使用服务端实体；
5. detail 如何精确更新，哪些 list 可以 patch，哪些只能 invalidate；
6. 推送只有更高 `version` 才能覆盖当前实体；
7. 登出/切租户时如何取消在途请求和清理敏感缓存。

### 规模与约束

- 一个用户可观察 20 个列表 key、200 个详情 key；
- WebSocket 峰值 100 条/秒，消息可能重复和乱序；
- 网络 p95 为 800ms；
- 不要求自己完整实现 TanStack Query，但核心协调逻辑必须可运行或可用 fake query client 测试；
- 不得用 `invalidateQueries()` 无条件清空全应用缓存。

### 失败语义

| 情况 | UI 要求 |
|---|---|
| 网络错误 | 回滚到最后一个已确认版本，显示可重试错误 |
| 409 冲突 | 不盲重试；保存用户意图，展示服务端新版本供合并 |
| 旧响应晚到 | 不得覆盖更新的本地意图或已确认版本 |
| 旧推送晚到 | 按 `version` 丢弃 |
| 断线重连 | 通过 HTTP 重验证，不假定推送完整 |

### 验收清单

- [ ] key 含租户与全部响应输入，且结构稳定；
- [ ] 写入并发策略有明确线性化点；
- [ ] 网络失败、409、成功三条路径都有代码和测试；
- [ ] 两次更新乱序的测试能稳定复现并通过；
- [ ] 重复/旧版/新版 WebSocket 事件都有断言；
- [ ] 列表失效是有界的；
- [ ] 日志不包含工单正文、token 等敏感内容；
- [ ] 解释为何支付、权限修改等场景不应复用此乐观策略。

### 发散问题

- 如果服务端不提供 `version/ETag`，你最多能保证什么？
- 离线编辑 30 分钟后重连，应该采用 last-write-wins、字段级合并还是人工解决？列出选择依据。
