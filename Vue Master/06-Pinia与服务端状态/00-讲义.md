# 第 06 章：Pinia 与服务端状态——先决定所有权，再写 Store

> 稳定生产基线：Vue 3.5.42、Pinia 4.0.3。Pinia 4 的主要迁移变化包括 ESM-only 与 devtools 依赖调整；本章状态所有权、actions、plugins、testing 与 SSR 模型仍按当前官方契约讲解。示例使用 `<script setup lang="ts">`、严格 TypeScript。

## 0. 事故现场：一个“万能 Store”如何制造幽灵数据

某运营后台把用户、当前租户、搜索条件、工单列表、弹窗开关、上传进度都放进 `useAppStore`。上线后出现了三个看似无关的问题：

1. A 租户退出后，B 租户进入列表页，先闪现 A 租户的工单；
2. 编辑详情成功，详情页是新的，返回列表却仍是旧标题；
3. 用户点两次保存，第一次慢、第二次快，最后旧响应覆盖了新响应。

根因不是“Pinia 不好用”，而是团队把性质完全不同的状态都当成了一个可变对象：

```text
业务事实 ──复制──> Pinia ──复制──> 页面 ref ──复制──> 表单
   ↑                  │              │
   └──── WebSocket ───┴──── HTTP 响应 ┘
```

每多一个副本，就多一条同步边；每条同步边都有竞态、失效和回滚问题。高级工程师首先问的不是“该用哪个 API”，而是：

- 这个状态的**唯一真相源**是谁？
- 谁能修改它，谁只是派生它？
- 它何时创建、何时销毁、何时过期？
- 跨刷新、跨标签页、跨 SSR 请求是否应该存在？

本章的目标，是把 Pinia 从“全局变量盒子”还原成**有边界的客户端领域状态容器**，并把服务端状态当作另一类问题处理。

## 1. 五类状态：分类错误比 API 错误更危险

| 类型 | 例子 | 推荐所有者 | 生命周期 | 典型失效方式 |
|---|---|---|---|---|
| 组件瞬时状态 | hover、弹窗局部步骤 | 组件 `ref` | 组件实例 | 卸载即消失 |
| URL 状态 | 分页、筛选、可分享 Tab | Router query/params | 浏览历史 | 导航替换 |
| 客户端领域状态 | 当前租户、未提交草稿、购物车 | Pinia/feature scope | 会话或业务流程 | action 显式修改 |
| 本地偏好 | 列宽、主题、密度 | 版本化持久层 | 跨会话 | schema 迁移/用户重置 |
| 服务端状态 | 工单列表、详情、统计 | 查询缓存/Repository | 有 stale 时间 | refetch/invalidate/push |

还有一类常被误放入响应式树：**资源对象**，如 WebSocket、AbortController、地图实例、编辑器实例。它们不是“要展示的数据”，而是有创建和销毁语义的资源，通常由 service/composable 持有；若必须挂到 store，使用 `markRaw` 并明确清理责任。

### 1.1 真相源、缓存与草稿不是一回事

- **真相源**：当前系统认可的权威值，例如服务端数据库中的工单版本。
- **缓存**：真相源的可丢弃副本，允许过期，必须有重取策略。
- **草稿**：用户尚未提交的意图，不能被后台刷新静默覆盖。
- **派生值**：可由其他状态纯计算得到，应优先用 getter/computed，而不是再次存储。

一个常见错误是把 `filteredTickets` 存入 state，同时也存 `tickets` 和 `filter`。三者立刻形成不变量：

```text
filteredTickets === filter(tickets, filter)
```

只要有一处更新遗漏，不变量就破坏。用 getter 保证它始终派生：

```ts
const visibleTickets = computed(() =>
  tickets.value.filter(ticket => matches(ticket, filter.value)),
)
```

## 2. Pinia 的两种 Store：语法不同，设计责任相同

### 2.1 Options Store：结构显式、约束清楚

```ts
import { defineStore } from 'pinia'

interface SessionState {
  user: { id: string; name: string } | null
  tenantId: string | null
  permissionCodes: string[]
}

export const useSessionStore = defineStore('session', {
  state: (): SessionState => ({
    user: null,
    tenantId: null,
    permissionCodes: [],
  }),
  getters: {
    isAuthenticated: state => state.user !== null,
    can: state => (code: string) => state.permissionCodes.includes(code),
  },
  actions: {
    establish(payload: {
      user: NonNullable<SessionState['user']>
      tenantId: string
      permissionCodes: string[]
    }) {
      this.$patch({ ...payload })
    },
    clear() {
      this.$reset()
    },
  },
})
```

Options Store 自带 `$reset()`；state 工厂在每个 Pinia 实例中创建新对象。它适合规则稳定、结构清楚的领域状态。

### 2.2 Setup Store：组合能力强，也更容易泄漏副作用

```ts
import { computed, ref } from 'vue'
import { defineStore } from 'pinia'

export const useDraftStore = defineStore('ticket-draft', () => {
  const ticketId = ref<string | null>(null)
  const title = ref('')
  const baselineTitle = ref('')

  const dirty = computed(() => title.value !== baselineTitle.value)

  function load(input: { id: string; title: string }) {
    ticketId.value = input.id
    title.value = input.title
    baselineTitle.value = input.title
  }

  function reset() {
    ticketId.value = null
    title.value = ''
    baselineTitle.value = ''
  }

  return { ticketId, title, dirty, load, reset }
})
```

Setup Store 可以使用 watcher、其他 composable 和注入值，但要回答：

- watcher 在 SSR 中是否会执行？
- HMR 后是否会重复注册订阅？
- 谁停止定时器/外部监听？
- 两个 store 在 setup 顶层互读会不会形成循环？

两个 store 可以互相调用 action，但不要在各自 setup 顶层立即读取对方尚未创建的值。出现循环依赖时，优先提取纯领域服务，或在 action 执行时延迟获取另一个 store。

## 3. 读取与修改：不要在解构时丢掉响应式

### 3.1 `storeToRefs` 与 action 解构

```vue
<script setup lang="ts">
import { storeToRefs } from 'pinia'
import { useSessionStore } from '@/stores/session'

const session = useSessionStore()
const { user, tenantId, isAuthenticated } = storeToRefs(session)
const { clear } = session // action 已绑定 store，可直接解构

// 错误：const { user } = session
// user 只是此刻的普通值，后续变化不会驱动模板更新。
</script>
```

### 3.2 直接赋值、`$patch` 和意图型 action

Pinia 允许三种更新：

```ts
store.tenantId = 'tenant-b'

store.$patch({
  tenantId: 'tenant-b',
  permissionCodes: ['ticket:read'],
})

store.$patch((state) => {
  state.cart.items.push(newItem)
  state.cart.updatedAt = Date.now()
})
```

技术上都可用，架构含义不同：

- 组件内改一个纯 UI 值，直接赋值可以接受；
- 多字段原子维护不变量，使用 action 包住 `$patch`；
- 集合变更或需要审计的业务动作，用 `cart.addItem()` 这类**意图型 action**；
- 不要让组件拼装领域对象并任意 `$patch`，否则校验、审计和副作用散落在 UI。

```ts
async function switchTenant(nextTenantId: string) {
  if (nextTenantId === tenantId.value) return
  const previous = tenantId.value

  await tenantRuntime.leave(previous)
  tenantId.value = nextTenantId
  permissionCodes.value = []
  await tenantRuntime.enter(nextTenantId)
}
```

`$patch` 是一次 devtools mutation 记录，但它不是数据库事务，也不会自动回滚异步失败。

## 4. 订阅、审计与横切逻辑

### 4.1 `$subscribe`：观察状态提交，不等于领域事件

```ts
const stop = session.$subscribe(
  (mutation, state) => {
    console.debug('session mutation', mutation.type, mutation.storeId)
    persistPreference(pickSafePreference(state))
  },
  { flush: 'post', detached: true },
)

// detached 订阅不会随创建它的组件 scope 自动停止，必须由应用生命周期 stop。
```

订阅适合持久化、调试和通用遥测；不适合依赖“某个业务动作发生”的规则。状态 A 变成 B 并不能说明为什么变化。

### 4.2 `$onAction`：围绕 action 做时延、结果和错误观测

```ts
const unsubscribe = store.$onAction(({ name, args, after, onError }) => {
  const startedAt = performance.now()

  after(() => {
    metrics.action({
      store: store.$id,
      name,
      durationMs: performance.now() - startedAt,
      ok: true,
    })
  })

  onError((error) => {
    metrics.action({
      store: store.$id,
      name,
      durationMs: performance.now() - startedAt,
      ok: false,
    })
    reportError(error, { action: name, args: redact(args) })
  })
})
```

不要把密码、token、完整表单或个人信息打入日志。可观测性本身也是数据处理系统，必须脱敏和采样。

### 4.3 Pinia 插件：统一能力，而不是隐式魔法

```ts
// pinia.d.ts
import 'pinia'

declare module 'pinia' {
  export interface PiniaCustomProperties {
    readonly $traceId: string
  }
}
```

```ts
import type { PiniaPluginContext } from 'pinia'

export function tracingPlugin({ store }: PiniaPluginContext) {
  const traceId = crypto.randomUUID()

  store.$onAction(({ name, onError }) => {
    onError(error => reportError(error, { store: store.$id, action: name, traceId }))
  })

  return { $traceId: traceId }
}
```

插件适合审计、埋点、依赖注入和统一持久化协议。插件若在创建 store 时偷偷发请求，会让依赖顺序、测试和 SSR 都变得不可预测。

## 5. 持久化：白名单、版本、迁移、失败降级

“把整个 `$state` 放进 localStorage”是危险默认值：

- token 和敏感资料可能被 XSS 读取；
- 旧 schema 在升级后无法解析；
- 多标签页并发写入造成覆盖；
- 服务端缓存被永久化，过期语义丢失；
- 大对象同步序列化阻塞主线程。

用明确 envelope 和迁移函数：

```ts
interface PreferenceV2 {
  version: 2
  updatedAt: number
  data: {
    theme: 'light' | 'dark' | 'system'
    density: 'comfortable' | 'compact'
    columns: string[]
  }
}

function migratePreference(raw: unknown): PreferenceV2 | null {
  if (!isRecord(raw)) return null

  if (raw.version === 2 && isPreferenceV2(raw)) return raw

  if (raw.version === 1 && isRecord(raw.data)) {
    return {
      version: 2,
      updatedAt: Date.now(),
      data: {
        theme: isTheme(raw.data.theme) ? raw.data.theme : 'system',
        density: 'comfortable',
        columns: stringArray(raw.data.columns),
      },
    }
  }

  return null
}

function loadPreference(storage: Storage): PreferenceV2 | null {
  try {
    const text = storage.getItem('ops.preference')
    return text === null ? null : migratePreference(JSON.parse(text))
  } catch {
    return null
  }
}
```

持久化建议：

1. 只允许显式白名单字段；
2. 运行时校验反序列化结果，不能用 `as PreferenceV2` 欺骗类型系统；
3. 版本不认识就丢弃或逐级迁移；
4. 敏感凭证优先 HttpOnly Cookie，不进入 JavaScript 可读存储；
5. 多标签同步需要明确冲突策略，例如 `updatedAt + tabId`；
6. IndexedDB 适合较大离线数据，但仍需版本和失效协议。

## 6. 服务端状态不是普通全局状态

服务端状态天然携带以下语义：

```text
QueryKey ──> CacheEntry
             ├─ data / error
             ├─ status: idle|loading|success|error
             ├─ fetchedAt / staleAt
             ├─ observers
             ├─ inFlight Promise（去重）
             └─ cancel / retry / garbage collection
```

Pinia 可以保存数据，却不会自动提供 key 规范化、请求去重、stale time、重试、焦点重取、分页保留、mutation 回滚等协议。成熟项目可使用 TanStack Query for Vue 等查询层，也可以建立受约束的内部抽象；不要在每个 store 里重新发明不兼容的缓存。

### 6.1 稳定 Query Key

```ts
interface TicketQuery {
  tenantId: string
  status?: 'open' | 'closed'
  assigneeId?: string
  page: number
  pageSize: number
}

const ticketKeys = {
  all: ['tickets'] as const,
  lists: () => [...ticketKeys.all, 'list'] as const,
  list: (query: TicketQuery) => [
    ...ticketKeys.lists(),
    canonicalTicketQuery(query),
  ] as const,
  details: () => [...ticketKeys.all, 'detail'] as const,
  detail: (tenantId: string, id: string) => [
    ...ticketKeys.details(), tenantId, id,
  ] as const,
}

function canonicalTicketQuery(query: TicketQuery) {
  return {
    tenantId: query.tenantId,
    status: query.status ?? null,
    assigneeId: query.assigneeId ?? null,
    page: query.page,
    pageSize: query.pageSize,
  }
}
```

key 必须包含影响响应的全部输入，尤其是租户、语言、权限视图和分页。遗漏租户就是跨租户数据串读风险。不要把不稳定对象、函数或随机值放进 key。

### 6.2 缓存失效不是“全部刷新”

mutation 成功后有三种策略：

- **精确写缓存**：响应返回完整新实体，可立即更新 detail；
- **精确 patch 列表**：能证明筛选、排序、分页归属不变时才安全；
- **标记失效并重取**：无法证明时，让相关 key stale，在当前观察或下次进入时请求。

```text
更新详情成功
   ├─ detail(id) <- response.entity
   ├─ 当前可见 list 若能证明仍属于该页 -> patch
   └─ 其他 lists -> invalidate，不猜测位置
```

“失效”通常表示缓存仍可暂时显示，但需要重验证；“删除缓存”意味着丢掉数据。两者 UX 完全不同。

### 6.3 乐观更新是一段可回滚事务

```ts
interface UpdateTitleInput {
  tenantId: string
  id: string
  title: string
  expectedVersion: number
}

async function updateTitleOptimistically(input: UpdateTitleInput) {
  const key = ticketKeys.detail(input.tenantId, input.id)

  await queryClient.cancelQueries({ queryKey: key })
  const previous = queryClient.getQueryData<Ticket>(key)

  if (previous) {
    queryClient.setQueryData<Ticket>(key, {
      ...previous,
      title: input.title,
      pending: true,
    })
  }

  try {
    const confirmed = await ticketRepository.updateTitle(input)
    queryClient.setQueryData(key, confirmed)
    queryClient.invalidateQueries({ queryKey: ticketKeys.lists() })
    return confirmed
  } catch (error) {
    queryClient.setQueryData(key, previous)
    throw error
  } finally {
    queryClient.invalidateQueries({ queryKey: key })
  }
}
```

生产上还要处理两个并发 mutation 的回滚覆盖。简单“保存一个 previous”只适合单 mutation；更稳妥的方案是串行同实体写入、mutation queue，或以服务端 `version/ETag` 做比较交换。收到 `409/412` 时不要无限自动重试，应该提示冲突并让用户合并。

不适合乐观更新的场景：扣款、库存分配、权限变更、服务端复杂校验、失败成本高、不可幂等操作。

### 6.4 WebSocket 不是第二个真相源

推送消息最好携带 `entityId + version` 或只发 invalidation：

```ts
function applyTicketEvent(event: TicketChangedEvent) {
  const key = ticketKeys.detail(event.tenantId, event.id)
  const current = queryClient.getQueryData<Ticket>(key)

  if (event.snapshot && (!current || event.snapshot.version > current.version)) {
    queryClient.setQueryData(key, event.snapshot)
  }

  queryClient.invalidateQueries({ queryKey: ticketKeys.lists() })
}
```

消息重复、乱序、断线漏失都是正常情况。连接恢复后必须用 HTTP 重验证，不能假设推送序列完整。

## 7. SSR：每个请求都必须拥有独立状态容器

错误做法是在模块顶层创建单例 Pinia：

```ts
// ❌ Node 进程处理多个用户，这个实例会跨请求共享
export const pinia = createPinia()
```

正确做法是应用工厂：

```ts
import { createSSRApp } from 'vue'
import { createPinia } from 'pinia'

export function createApp() {
  const app = createSSRApp(App)
  const pinia = createPinia()
  const router = createRouterForRequest()

  app.use(pinia)
  app.use(router)
  return { app, pinia, router }
}
```

请求流程：

```text
request
  -> createApp() / createPinia()
  -> router.push(url) + router.isReady()
  -> preload request-scoped data
  -> renderToString(app)
  -> 安全序列化 pinia.state.value
  -> HTML
client
  -> 在 mount 前恢复 state
  -> hydrate
```

必须同时守住：

- store、query client、router、用户上下文按请求创建；
- 只序列化 JSON 安全且允许暴露给浏览器的数据；
- JSON 内的 `<` 等字符要安全转义，避免注入闭合 `<script>`；
- 不把服务端 secret、内部权限决策或完整错误栈放入 hydration payload；
- 客户端恢复状态要在创建对应 store 后、挂载前按框架协议进行。

前端权限集合只是 UI 能力提示，服务端仍必须对每个请求授权。

## 8. 一个生产状态架构的最小分层

```text
Vue Component
  ├─ local ref（瞬时 UI）
  ├─ Router（可分享状态）
  ├─ Pinia action（客户端领域意图）
  └─ useQuery/useMutation（服务端状态）
          ↓
     Repository（HTTP/schema/error/idempotency）
          ↓
       Backend
```

组件不直接知道 token 刷新、缓存 key 序列化、API DTO 迁移；store 也不应该吞下整个 HTTP 客户端。每层有一个明确问题：

- Router：这个视图如何被定位与恢复？
- Pinia：这个客户端业务过程如何保持不变量？
- Query cache：服务端副本何时新鲜、如何失效？
- Repository：边界数据如何验证、错误如何归一？

## 9. 测试与排障

### 9.1 Store 测试关注不变量

```ts
import { beforeEach, describe, expect, it } from 'vitest'
import { createPinia, setActivePinia } from 'pinia'

beforeEach(() => setActivePinia(createPinia()))

it('clear 后不会残留上一租户权限', () => {
  const store = useSessionStore()
  store.establish({
    user: { id: 'u1', name: 'Ada' },
    tenantId: 't1',
    permissionCodes: ['ticket:write'],
  })

  store.clear()

  expect(store.user).toBeNull()
  expect(store.tenantId).toBeNull()
  expect(store.permissionCodes).toEqual([])
})
```

### 9.2 缓存测试关注时间与竞态

至少覆盖：

- 同 key 并发读取只发一次请求；
- key 包含 tenantId，不串数据；
- mutation 失败恢复 UI；
- 两次 mutation 乱序不会让旧版本获胜；
- WebSocket 重复/乱序事件幂等；
- logout/switch tenant 取消请求并清理敏感缓存；
- SSR 两个请求的 state 不互相可见。

### 9.3 现场排障顺序

1. 在 Vue Devtools 看是哪个 store、哪次 mutation 改值；
2. 检查请求的 query key 与租户/筛选是否完整；
3. 对比 response version、mutation sequence、WebSocket event version；
4. 检查组件是否把 store 值复制进本地 ref 后不再同步；
5. 检查持久层是否恢复了旧 schema；
6. SSR 问题用两个并发用户请求做隔离测试，不要只本地单用户刷新。

## 10. 反例速查

| 反例 | 为什么坏 | 更好的方向 |
|---|---|---|
| 一个 `useAppStore` 包全站 | 生命周期和权限边界混杂 | 按业务能力和所有权拆分 |
| 列表、详情各复制一份实体 | 修改后难保持一致 | 查询缓存 + key/失效协议 |
| 组件到处 `$patch` 领域对象 | 不变量和审计散落 | 意图型 action |
| `const { user } = store` | 解构丢响应式 | `storeToRefs` |
| 整个 `$state` 持久化 | 泄密、版本和过期问题 | 白名单 + schema + migrate |
| 把 WebSocket 放 reactive state | 代理/序列化/清理混乱 | resource service / `markRaw` |
| SSR 导出全局 Pinia | 跨请求用户泄漏 | 每请求应用工厂 |
| 所有写操作都乐观 | 回滚和冲突成本失控 | 按失败成本选择策略 |
| 更新后 `invalidate all` | 浪费网络、UI 抖动 | 精确写 + 有界失效 |

## 11. 速记卡与自检

### 一句话速记

> Pinia 管“客户端拥有的领域过程”，查询层管“服务端真相的可失效副本”；高级状态管理的核心是所有权、生命周期、失效和冲突，不是把值放进全局。

### 你应该能不看答案解释

1. 为什么搜索、分页通常属于 URL，而不是 Pinia？
2. `storeToRefs` 解决了什么，为什么 action 不需要它？
3. `$subscribe` 与 `$onAction` 分别适合什么？
4. 持久化为什么必须有白名单、运行时校验和版本迁移？
5. query key 漏掉 `tenantId` 为什么不仅是 bug，还可能是安全事故？
6. 为什么“详情成功就 patch 所有列表”在筛选和分页下不可靠？
7. 乐观更新的取消、快照、回滚、重验证分别解决什么？
8. 为什么 SSR 必须每请求创建 Pinia 与 query client？
9. WebSocket 为什么不能被当作无缺失、严格有序的真相源？
10. 哪些操作不应该乐观更新？

### 给 AI 二次追问的锚点
