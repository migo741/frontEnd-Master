# 第 10 章：测试策略与可测试设计

## 测试按风险分层，不按覆盖率崇拜

单元测试适合纯业务规则、parser、composable；组件测试验证 props/事件/DOM 交互；集成测试让组件、router、Pinia 和 mock API 合作；E2E 覆盖登录、支付/提交等少数关键旅程。越接近真实越有信心，也越慢、越难定位，所以组合使用。

Vue 官方推荐 Vite 项目优先 Vitest；组件可用 Vue Test Utils。MSW 在网络边界模拟协议，避免每个测试 mock axios 内部。Playwright/Cypress 等 E2E 以用户行为操作生产构建。

## 验证行为，不验证实现

优先按 role、label、可见文本和 test id 定位，避免 class、组件内部 ref、快照大字符串。不要只测“调用了某方法”，要测用户能看到的结果和协议副作用。异步测试等待可观察结果，不随手堆 `nextTick`/timeout。

## Pinia 与 Router

组件测试可用 testing Pinia，但要明确 action 是 stub 还是执行；测试 store 本身用真实 Pinia。每个 router 测试创建全新 memory history，并 await `router.isReady()`，防全局状态污染。

## 可测试设计

把纯规则从组件抽出，把 clock/random/network 注入；这不是为测试扭曲代码，而是显式依赖。避免把所有依赖 mock 掉后只证明“mock 按预期工作”。关键集成路径应使用尽量真实的子组件和协议 mock。

## 自检

一个表单验证应该在哪几层测？为什么大快照脆弱？测试中何时 mock store action，何时必须真实执行？
