# 第 10 章：测试策略与可测试设计——用最少测试覆盖最大风险

> 工具基线：Vitest、Vue Test Utils（VTU）或 Testing Library、MSW、Playwright；Vue 3.5。工具会更新，测试边界的思想更重要。

## 0. 事故现场：覆盖率 92%，结账按钮仍然坏了

某团队要求每个 composable、组件 method、computed 都达到 90% 行覆盖。PR 有 2,000 个测试，发布后“确认支付”在真实 Router + Teleport Dialog + 401 refresh 场景中失效。原因：

- 单元测试把 Router、Pinia、API 全 mock 成永远成功；
- 测试直接调用组件内部 method，没有模拟用户点击；
- snapshot 很大，更新时没人阅读；
- fake timers 没恢复，污染后续文件；
- E2E 共用账号和数据，并行时互相删除；
- 没有任何测试覆盖构建产物、SSR hydration 或真实焦点。

覆盖率只说明哪些语句曾执行，不说明断言是否有价值。测试策略应从风险倒推：

```text
风险 = 发生概率 × 影响 × 难发现程度

高风险业务路径 -> 少量跨层测试
复杂纯逻辑     -> 快速单元测试
组件用户契约   -> 组件/集成测试
浏览器平台行为 -> E2E/visual/a11y
类型/架构规则  -> 静态检查
```

高级工程师追求的不是最多测试，而是**最快、最稳定地证明最重要的事情**。

## 1. 测试分层：边界不同，失败解释也不同

| 层 | 适合证明 | 不擅长 | 常用工具 |
|---|---|---|---|
| 静态 | 类型、lint、依赖方向、生成物漂移 | 运行时数据和浏览器 | TypeScript/ESLint/architecture tests |
| 纯单元 | parser、状态机、排序、策略 | Vue/DOM 集成 | Vitest node |
| 组件 | props/emits/slot、交互和可访问 DOM | 真浏览器布局 | VTU/Testing Library + DOM env |
| 集成 | Vue + Router + Pinia + API 边界 | 全浏览器平台 | Vitest + real plugins + MSW |
| E2E | 用户主路径、真实导航/焦点/下载 | 穷举边界 | Playwright |
| Visual/a11y | 视觉回退、浏览器可访问性 | 业务正确性全部 | screenshot + axe/manual |
| SSR/hydration | 请求隔离、HTML 与客户端一致 | 所有业务路径 | server renderer + browser smoke |

“测试金字塔”不是固定比例。富交互 Vue 应用通常需要较多组件/集成测试；支付、权限、上传等关键路径需要少量高价值 E2E。每层都 mock 所有邻居会留下接缝空白。

### 1.1 一条风险对应最低充分层

- `canonicalizeQuery()` 排序错误：纯单元足够；
- Button emit payload 错：组件测试；
- 401 singleflight + 页面恢复：API 集成测试；
- Dialog focus trap/浏览器 tab 顺序：真实浏览器；
- SSR 跨请求 Pinia 泄漏：并发 server test；
- 字体/布局错位：visual，不靠 DOM snapshot。

越高层越慢、定位越粗；越低层越可能错过真实接缝。选择“能捕获该故障的最低成本层”。

## 2. 可测试设计：测试困难常暴露生产耦合

### 2.1 将纯决策与副作用分离

```ts
// 纯函数：无需 mount、网络、timer
export function nextRetryDelay(input: {
  attempt: number
  baseMs: number
  capMs: number
  random: number
}): number {
  const upper = Math.min(input.capMs, input.baseMs * 2 ** input.attempt)
  return Math.floor(input.random * upper)
}
```

```ts
// shell 负责调用真实能力
const delay = nextRetryDelay({
  attempt,
  baseMs: 200,
  capMs: 5000,
  random: Math.random(),
})
await sleep(delay, signal)
```

把 clock、random、ID、transport 作为窄接口注入，不意味着为每个函数建 DI 容器：

```ts
interface Runtime {
  now(): number
  randomId(): string
}
```

### 2.2 测公开契约，不测实现纹理

组件公开契约：

- props 输入；
- emits 输出；
- slots 扩展点；
- 可访问 DOM/键盘行为；
- 对外暴露的 imperative API（仅必要时）；
- 加载/错误/禁用状态。

不要断言：内部 ref 名字、computed 次数、私有 method、具体子组件层级、Tailwind class 全串（除非它就是公共视觉契约）。重构内部实现不应让所有测试破裂。

### 2.3 用真实的小依赖，mock 不稳定的外部边界

- Router/Pinia 创建真实内存实例通常比全 mock 更可信；
- API 用 MSW 在网络边界拦截，比 mock repository 每个 method 更能捕获 URL/body/schema 错误；
- 第三方支付、地图等可以 adapter mock；
- 不要 mock Vue 的 `ref/watch/nextTick`。

## 3. Vitest 环境与隔离

纯逻辑测试用 `node` 环境更快；组件测试用 `jsdom` 或 `happy-dom`。它们不是完整浏览器：没有真实布局、部分 observer/selection/focus 行为不同。对依赖布局、滚动、下载、导航、安全策略的行为，用 Playwright。

每个测试应隔离：

- Pinia、Router、query client 新建；
- MSW handler 在测试后 reset；
- spies/mocks/timers 恢复；
- DOM cleanup；
- storage 清理；
- 环境变量 stub 恢复；
- 不依赖用例执行顺序。

```ts
afterEach(() => {
  vi.useRealTimers()
  vi.restoreAllMocks()
  localStorage.clear()
  server.resetHandlers()
})
```

不要全局清理掉测试框架/库需要的长期 handler；区分 `resetHandlers` 与关闭 server 的 suite 生命周期。

## 4. VTU 与 Testing Library：查询方式表达测试哲学

VTU 提供 Vue 专属 wrapper、props/emitted/component 查找，适合精确组件契约。Testing Library 鼓励按 role/name/label 查询，适合用户视角。可以选择其一为主，也可按场景组合，但不要两个工具对同一 DOM 重复抽象。

优先查询：

1. `getByRole('button', { name: '保存' })`；
2. `getByLabelText('标题')`；
3. 可见文本；
4. 稳定 `data-testid`（仅无语义元素/难定位状态）；
5. CSS class/DOM 层级最后。

如果测试找不到按钮的可访问名称，真实屏幕阅读器用户通常也找不到。这是测试帮助设计，而不是“测试工具麻烦”。

### 4.1 `mount` 与 `shallowMount`

`shallowMount`/全局 stub 能聚焦父组件，但会隐藏：slot、provide/inject、子组件 emit、Teleport、可访问 DOM 的真实组合问题。默认优先 mount 业务小切片；只 stub 慢/不可控/已独立验证的边界组件。

不要用自动 stub 所有子组件的 snapshot 证明页面“渲染正确”。

## 5. Vue 更新队列：`nextTick` 与 `flushPromises` 不是同义词

```text
修改 reactive state
  -> Vue 调度 DOM patch（microtask） -> await nextTick()

Promise/network mock resolve
  -> Promise continuation -> state mutation
  -> Vue DOM patch
  -> 可能需要 flushPromises() + nextTick()/用户工具自带等待
```

### 5.1 `nextTick`

等待 Vue 已安排的 DOM 更新：

```ts
await wrapper.get('button').trigger('click')
// VTU trigger 本身返回 nextTick，DOM 通常已更新
expect(wrapper.text()).toContain('已展开')
```

它不会凭空等待任意未决网络 Promise。

### 5.2 `flushPromises`

让当前已 resolve/reject 的 Promise 回调链推进。它不能：

- 完成尚未 resolve 的 deferred Promise；
- 自动推进 fake timer；
- 保证所有新产生的任务都结束；
- 替代明确的 UI `findBy.../waitFor` 条件。

测试应控制事件：resolve 请求、推进 timer、等待可观察 UI，而不是连续写五次 `flushPromises()`。

### 5.3 推荐 Arrange–Act–Assert 时间线

```ts
const request = deferred<Ticket>()
renderPage({ repository: { load: () => request.promise } })

expect(screen.getByRole('status', { name: '加载中' })).toBeVisible()

request.resolve(ticket)
await screen.findByRole('heading', { name: ticket.title })

expect(screen.queryByRole('status', { name: '加载中' })).toBeNull()
```

断言用户观察到的条件，比推测内部 microtask 数量稳定。

## 6. Fake Timers：只控制你要控制的时钟

防抖、重试、toast 超时适合 fake timers：

```ts
it('停止输入 300ms 后搜索一次', async () => {
  vi.useFakeTimers()
  const search = vi.fn()
  render(SearchBox, { props: { search } })

  await user.type(screen.getByRole('searchbox'), 'vue')
  expect(search).not.toHaveBeenCalled()

  await vi.advanceTimersByTimeAsync(299)
  expect(search).not.toHaveBeenCalled()
  await vi.advanceTimersByTimeAsync(1)
  expect(search).toHaveBeenCalledWith('vue')
})
```

风险：user-event、Vue、Promise 和 timer 交织。所选 user simulation 库可能需要传 `advanceTimers` 配置。测试结束前检查没有预期外 timer，并在 `finally/afterEach` 恢复 real timers。

不要用 fake timers 测真实浏览器性能，也不要冻结全 suite 时钟。对于 production code，注入 scheduler/clock 往往比全局 monkey patch 更清楚。

## 7. MSW：在 HTTP 边界保留真实请求代码

```ts
const server = setupServer(
  http.get('/api/tickets/:id', ({ params }) => {
    if (params.id === '404') {
      return HttpResponse.json(
        { title: 'Not Found', status: 404, code: 'TICKET_NOT_FOUND' },
        { status: 404 },
      )
    }
    return HttpResponse.json(ticketDto)
  }),
)
```

优势：真实执行 URL、headers、body、client decoder、error mapping；handler 仍快速确定。建议未匹配请求设为 error，防测试意外访问外网或悄悄绕过 mock。

测试不要重新实现服务端所有逻辑。只返回代表性合同：成功、边界、协议错误、延迟、断线、401/403/409/422/500。后端自身验证由后端测试负责。

Contract testing/codegen drift 可补充验证前后端 schema，但不能替代 UI 行为测试。

## 8. Router、Pinia 与组件集成

建立工厂而不是在每个测试复制 setup：

```ts
async function renderWithApp(component: Component, options?: RenderOptions) {
  const pinia = createPinia()
  const router = createRouter({
    history: createMemoryHistory(),
    routes: testRoutes,
  })

  if (options?.route) await router.push(options.route)
  await router.isReady()

  const result = render(component, {
    global: { plugins: [pinia, router] },
  })
  return { ...result, pinia, router }
}
```

每测一个 route guard 不必启动浏览器；memory history 集成测试可验证重定向、meta、store 交互。真正的 back/forward、scroll、地址栏和 chunk load 留给 E2E。

Pinia action 测试分两类：

- 领域不变量：真实 store + fake repository；
- 组件集成：真实 store，按需要用 `createTestingPinia` stub actions，但必须有另外的测试验证真实 action。否则全项目只验证“假 action 被调用”。

## 9. 组件契约测试

以 Dialog 为例，测试的不只是“HTML 存在”：

- `modelValue` 控制显示；
- Escape 发出关闭意图；
- `beforeClose` 拒绝时不关闭；
- 初始焦点进入，关闭后恢复触发器；
- Tab 被约束在 dialog；
- aria role/name/description；
- Teleport 到目标；
- 多 Dialog stack 只允许顶层处理 Escape；
- SSR 初始 DOM 可水合。

其中 props/emits 可在组件环境；真实 focus trap、Tab、Teleport stacking 最好用 Playwright component/E2E。选择层由 DOM 模拟器能力决定。

快照只适合短小、稳定、值得逐字符审查的输出，例如序列化 schema 或错误 summary。几百行 HTML snapshot 不是可维护规格。

## 10. SSR 与 hydration 测试

三层：

1. `renderToString`：给定 route/state 输出关键 HTML，无访问浏览器全局；
2. 请求隔离：两个用户并发创建独立 app/store/query client；
3. 浏览器 hydration：服务端 HTML + 客户端相同初始 state，无 mismatch，交互可用。

```ts
it('并发请求不共享用户', async () => {
  const [htmlA, htmlB] = await Promise.all([
    renderRequest({ userId: 'A', url: '/profile' }),
    renderRequest({ userId: 'B', url: '/profile' }),
  ])

  expect(htmlA).toContain('user-A')
  expect(htmlA).not.toContain('user-B')
  expect(htmlB).toContain('user-B')
})
```

不要通过屏蔽 hydration warning 让测试绿。时间、随机 ID、locale、浏览器条件分支都要固定或延后到 mount。

## 11. Playwright E2E：测试用户价值，不复制所有单元边界

高价值路径示例：

- 登录/会话恢复/退出；
- 创建并编辑核心实体；
- 权限不足无敏感 DOM/请求；
- 支付/发布/上传的关键状态；
- 浏览器 back/forward 和深链；
- 错误恢复与草稿保护。

### 11.1 数据隔离

- 每 worker 独立租户/用户或唯一 namespace；
- API seed 返回创建实体 ID；
- 测试只删除自己创建的数据；
- 不依赖测试顺序和共享“固定工单 1”；
- cleanup 即使失败也执行，但保留失败诊断所需信息；
- 不用生产环境跑破坏性测试。

### 11.2 Locator 与等待

优先 role/label；利用 Playwright auto-wait。不要 `waitForTimeout(2000)` 猜速度。等待业务条件：响应完成、按钮 enabled、heading 出现、URL 确认。

Network mock E2E 快且可测前端错误；真实 staging E2E验证部署集成。两者可分层，不能把全部路径都依赖不稳定外部环境。

### 11.3 Trace-first 诊断

失败保留 trace、截图、video（按策略）、console、network、release/build ID。重跑通过不能自动证明是“偶发”；先分类根因。

## 12. Visual 与可访问性测试

Visual regression：固定 viewport、字体、DPR、动画、时区、数据和主题；只截图稳定区域。像素差异需阈值，但阈值过大等于忽略错误。动画/异步图表应用显式 ready signal，不用 sleep。

自动 a11y 扫描能发现：缺名称、颜色对比、某些 ARIA 错误；不能证明键盘流程、焦点顺序、读屏语义和认知可用性。关键组件还需：

- 只用键盘走完；
- 焦点可见、顺序合理；
- 错误与输入关联；
- 状态变化适当 announce；
- zoom/reflow；
- 至少一次真实屏幕阅读器人工验收（按产品重要性）。

## 13. Flaky 治理：重试是诊断工具，不是垃圾桶

常见根因分类：

| 类型 | 症状 | 修复 |
|---|---|---|
| 时间 | sleep 后偶发找不到 | 等业务条件/控制时钟 |
| 数据 | 并行互相覆盖 | worker 隔离/唯一 ID |
| 网络 | 外部服务抖动 | 边界 mock + 少量真实 smoke |
| 环境 | 字体/locale/CPU 差异 | 固定镜像和环境参数 |
| 清理 | timer/listener/handler 泄漏 | afterEach + scope disposal |
| 选择器 | DOM 重构即坏 | role/label/test id 契约 |
| 产品竞态 | 旧响应偶发覆盖 | 修生产代码，不调测试等待 |

治理流程：

1. 记录 flake rate、首次失败 seed/worker/release；
2. quarantine 必须有 owner、issue、截止时间，且关键路径不能长期隔离；
3. retry 后仍上报首次失败，不把绿色二次运行当无事发生；
4. 修复后重复运行、随机顺序、并发验证；
5. 删除低价值、长期噪声且无法修好的重复测试。

## 14. 覆盖率、变异测试与测试选择

覆盖率用作“哪里完全没测”的信号，不作为单一 KPI。更有价值的问题：

- 核心状态机的每条转移是否断言？
- 错误和取消分支是否可达？
- 一个关键判断翻转，测试会红吗？
- 高变更/高事故模块是否有更强保护？

变异测试会修改条件/返回值，观察测试是否捕获；适合支付计算、权限策略、parser 等纯逻辑，不必全仓运行。按 changed files + dependency graph 选择 PR 快速测试，主干/夜间跑完整矩阵；但共享底层变更要扩大 affected 范围。

## 15. 反例速查

| 反例 | 为什么坏 | 替代 |
|---|---|---|
| 只追 90% 行覆盖 | 可无断言执行 | 风险矩阵 + mutation/branch |
| 调组件私有 method | 重构即碎 | 用户事件 + props/emits/DOM |
| 所有子组件 shallow stub | 接缝未测试 | mount 业务切片 |
| 连续五次 flushPromises | 不知道在等什么 | 控制事件 + 等 UI 条件 |
| fake timers 不恢复 | 污染 suite | afterEach real timers |
| MSW 未匹配请求放行 | 偷跑外网/假绿 | onUnhandledRequest error |
| E2E `waitForTimeout` | 慢机 flaky | locator/response/URL 条件 |
| 所有 E2E 共用固定数据 | 并行冲突 | worker namespace |
| 巨型 DOM snapshot | 更新无人读 | 小契约断言/visual |
| Flake 统一 retry 3 次 | 掩盖竞态 | trace + owner + 根因治理 |

## 16. 速记与自检

> 测试的单位不是函数或文件，而是风险；选择能捕获该风险的最低成本层，并让失败能解释。

你应能回答：

1. 行覆盖率为什么不能证明行为正确？
2. 哪些行为必须真实浏览器才能可靠测试？
3. `nextTick`、`flushPromises`、fake timers 分别推进什么？
4. 为什么真实 Router/Pinia 往往比全 mock 更好？
5. MSW 比 mock `api.get` 多覆盖了哪些接缝？
6. 组件公共契约包含什么，不应断言什么？
7. SSR 至少需要哪三层测试？
8. E2E 为什么要按 worker 隔离数据？
9. 自动 a11y 扫描为什么不够？
10. 怎样判断一个 flaky 是测试问题还是产品竞态？

给 AI 的追问锚点：

- “请用 Vue 的 scheduler 解释 nextTick 与 Promise continuation 的先后关系。”
- “请把一个支付页面风险拆到 static/unit/component/integration/E2E 五层。”
- “请给一个测试 retry 变绿但生产代码仍有竞态的时间线。”
