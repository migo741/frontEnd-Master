# 第 02 章：渲染、编译与更新调度

## 从模板到 DOM

SFC 模板先被编译为 render function，运行时得到 VNode，再由 renderer 执行 mount/patch/unmount。Vue 的优势不是“虚拟 DOM 一定快”，而是编译器能标记动态节点：静态提升、patch flags、block tree 让更新时少做无效比较。

看到一次异常更新，按这条链排查：状态写入 → reactive trigger → scheduler 入队 → render effect → 新 VNode → patch → DOM。不要一上来就加 `nextTick`。

## key 的真实含义

`key` 表示同级节点在新旧两次渲染中的身份，不是消除 warning 的装饰。用数组下标做 key，在插入/重排时会让“位置身份”替代“业务身份”，输入框本地状态、组件实例和过渡可能跟错数据。稳定、唯一、来自数据域的 id 才是正确 key。

有 key 的 children diff 会尽量复用与移动。Vue 的实现会使用头尾同步、key map，以及最长递增子序列减少移动。你不必手写完整 renderer，但要能手算小列表并解释为什么某些 DOM 被 move 而不是 recreate。

## 批处理、nextTick 与 flush

同一 tick 内多次同步写状态会进入队列并去重，所以 DOM 通常只更新一次。`nextTick` 等待当前刷新队列完成；它不是网络等待，也不保证浏览器已经完成绘制。测布局有时还需 `requestAnimationFrame`。

watch 的 flush 是业务语义：默认 `pre` 适合更新前逻辑；`post` 适合读取组件更新后的 DOM；`sync` 绕过批处理，除少数缓存失效场景外应谨慎。

## 组件边界与更新成本

父组件每次 render 不等于所有 DOM 都变化，但子组件 props 稳定性会决定是否跳过更新。把 `activeId` 传给每行会导致很多行接收变化；传 `active: item.id === activeId` 让多数行 props 保持稳定。对真正静态子树使用 `v-once`，对大列表中内容不变但父更新频繁的节点可评估 `v-memo`，前提是 profile 证明收益。

## 自检

解释 `v-if` 与 `v-show` 的更新成本差异；说明为什么随机 key 会让性能和状态都变坏；说明 `await nextTick()` 后什么成立、什么不成立。
