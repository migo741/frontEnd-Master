# 第 18 章：SFC 与编译器源码精读——模板如何变成可优化的 Render Function

> 源码基线：Vue Core `v3.5.42`，commit `d63616ca17de965ed32dcb449a4c5cd9982f15d2`。Compiler AST、内部 transforms、patch flag 数值和生成代码形态不是业务 API；本章通过固定版本建立模型，并用 snapshot/fixture 验证升级。

## 0. 本章目标

学完后，你应能回答：

1. 一个 `.vue` 文件怎样被拆成 template/script/style/custom blocks？
2. `<script setup>` 为什么无需手写 return，`defineProps` 为什么不能在运行时调用？
3. `parse → transform → codegen` 各自做什么，AST 与 codegen node 有何区别？
4. `v-if`、`v-for` 为什么不仅是字符串替换？
5. patch flags、block tree、dynamicChildren 怎样把编译期知识交给 renderer？
6. scoped CSS 为什么不是 Shadow DOM，`:deep()`、`:slotted()` 改了什么？
7. source map、loc 和 compiler errors 如何定位回原 SFC？
8. 怎样实现一个不会靠正则误判的 SFC 诊断工具？
9. 哪些编译扩展适合生产，哪些只应作为实验？

目标不是成为 Vue compiler maintainer，而是能读懂生成结果、解释优化边界、定位 SFC 构建故障，并安全地做有限编译工具。

## 1. 事故钩子：一条“安全扫描”规则误伤 300 个组件

团队用正则扫描模板：

```ts
if (source.includes('v-html=')) {
  throw new Error('禁止 v-html')
}
```

结果：

- 注释中的示例也被拦截；
- custom block 里的文档被拦截；
- 动态参数和换行格式产生漏报；
- 报错没有 line/column；
- autofix 把字符串内容改坏；
- 真正危险的运行时 template string 完全没被发现。

高级解决方式不是更复杂的正则，而是使用 SFC parser 找到 template block，再使用 compiler AST 找到 `v-html` directive，保留 `loc`，并把“语法事实”与“业务信任判断”分开。

这要求先理解 Vue 的编译流水线。

---

## 2. 总流水线：一个 SFC 不只编译一次

```text
Component.vue source
  ↓ @vue/compiler-sfc parse
SFCDescriptor
  ├─ template block
  ├─ script block
  ├─ scriptSetup block
  ├─ style blocks
  └─ custom blocks

script / script setup
  ↓ compileScript
组件 setup 代码 + bindings metadata + runtime props/emits options

template
  ↓ compileTemplate → compiler-dom → compiler-core
render function code + AST + errors/tips + source map

styles
  ↓ compileStyle
CSS（scoped/module/vars transforms）+ map/errors

bundler plugin（如 @vitejs/plugin-vue）
  ↓ 组合模块、HMR、资源 URL、scope id
浏览器可执行组件模块
```

compiler-sfc 负责 SFC 文件语义；compiler-core 负责平台中立模板编译框架；compiler-dom 加入浏览器 DOM 特有 parser/options/directive transforms；compiler-ssr 生成服务端 render 路径。

## 4. SFC `parse()` 与 Descriptor

`parse(source, options)` 使用 compiler DOM 的 SFC parse mode，把顶层 blocks 放入 descriptor：

```ts
interface SFCDescriptor {
  filename: string
  source: string
  template: SFCTemplateBlock | null
  script: SFCScriptBlock | null
  scriptSetup: SFCScriptBlock | null
  styles: SFCStyleBlock[]
  customBlocks: SFCBlock[]
  cssVars: string[]
  slotted: boolean
}
```

每个 block 还保留 content、attrs、lang、loc/map 等信息。parser 会收集错误，而不是让调用者只能看到一个无位置字符串。

### 4.1 Descriptor 不是 template AST

Descriptor 解决的是“这个文件有哪些块”；template AST 解决“template 内有哪些元素、指令和表达式”。两层不能混用：

```text
SFC AST/descriptor
  └─ template.content（字符串 + block loc）
       ↓ compiler-dom.parse
     template RootNode
       └─ Element / Directive / Interpolation ...
```

### 4.2 Parse cache

固定版本基于 source/options key 缓存 parse result。工具不能修改返回 descriptor/AST 后再假定下一次是干净对象；更稳妥是只读使用或显式 clone 自己需要的数据。缓存策略是实现细节。

### 4.3 文件结构错误

应测试：重复 template、script setup lang 与普通 script lang 不一致、空 block、错误 HTML nesting、preprocessor 不存在。诊断工具先保留 compiler errors，不能为了运行自定义规则把语法错误吞掉。

## 5. `<script setup>`：编译期语法糖，不是隐藏的运行时框架

### 5.1 宏会被编译器识别

固定版本宏集合包括：

```text
defineProps
defineEmits
defineExpose
defineOptions
defineSlots
defineModel
withDefaults
```

它们无需导入，编译后通常被消除或转成组件 options/setup context。不要：

```ts
import { defineProps } from 'vue' // 在 SFC 宏上下文通常不需要

function later() {
  defineProps<{ id: string }>() // 宏不允许随意放在运行时分支/函数
}
```

### 5.2 为什么顶层变量能在 template 使用

compileScript 分析 imports、变量声明、refs、reactive、literal 等，生成 bindings metadata。SFC 组装时 template compiler 利用 metadata，知道一个标识符来自 props、setup ref、setup const 或 imported component，从而生成正确访问与 unwrap 方式。

普通 setup 需要 return：

```ts
setup() {
  const count = ref(0)
  return { count }
}
```

script setup 由编译器生成等价暴露路径。不是 runtime 扫描模块所有变量。

### 5.3 宏参数的 hoist 边界

defineProps/defineEmits 的 runtime options 会提升到模块作用域，不能引用 setup 局部变量：

```ts
const required = computeAtRuntime()

defineProps({
  title: { required }, // 无法安全提升，编译应拒绝或无法表达
})
```

imported bindings 可在模块层存在；是否允许以当前版本 compiler 诊断为准。

### 5.4 类型信息与运行时验证不是一回事

```ts
const props = defineProps<{ ticketId: string }>()
```

compiler 可从类型生成一定 runtime props metadata，但复杂外部类型不等于完整 runtime schema。URL/API 输入仍需 Zod/Valibot/手写 validator。TypeScript 在浏览器运行时已被擦除。

### 5.5 顶层 await

script setup 支持顶层 await，并通过编译变换保存/恢复 async context。即便如此，组件 async setup 仍需要 Suspense/SSR 生命周期理解；不要因此把每个请求直接写在顶层 await。

## 6. `compileTemplate()` 是适配层

它处理：

- template preprocessor；
- asset URL transform；
- source map/input map；
- scoped/slotted id；
- bindings metadata；
- DOM vs SSR compiler；
- errors/tips；
- compiler options/custom transforms。

然后进入 compiler-dom/compiler-core。若使用 Pug 等 preprocessor，缺失依赖应产生明确错误；不能悄悄返回空 render 后继续构建。

生产诊断必须记录：filename、id、scoped、isProd、ssr、compiler options。相同 template 在不同 options 下生成代码可能不同。

## 7. Compiler Core 三阶段

### 7.1 Parse：字符串 → 语法 AST

示例：

```vue
<h2 :class="tone">{{ title }}</h2>
```

概念 AST：

```text
ROOT
└─ ELEMENT h2
   ├─ DIRECTIVE bind
   │  ├─ arg: class
   │  └─ exp: tone
   └─ INTERPOLATION
      └─ SIMPLE_EXPRESSION title
```

parse 负责结构与 loc，不负责决定最终 helper 或 patch flag。

### 7.2 Transform：遍历 AST，建立语义和 codegen nodes

Node transforms 可在进入节点时工作，并返回 exit callback。为什么需要 exit？父节点 codegen 常依赖已经处理完的 children：

```ts
const transformExample: NodeTransform = node => {
  // enter
  return () => {
    // exit：children 已完成 transform
  }
}
```

transform context 跟踪：

- 当前/父节点与 child index；
- helpers/components/directives；
- identifiers 与 expression scope；
- hoists/cached expressions；
- node replacement/removal；
- scopes（v-for/v-slot）；
- root codegen node。

### 7.3 Codegen：codegen AST → JavaScript 字符串

generator 不重新理解 HTML 语义。它根据 transforms 已准备的 VNode calls、JS calls、conditional expressions、function expressions 等输出 helper imports、hoists 和 render function。

```text
source AST 告诉“写了什么”
transform/codegen nodes 告诉“怎样生成”
```

自定义分析工具通常只需 parse AST，不应调用完整 transform 后修改 private codegen node，除非你愿意承担版本维护。

## 8. 一个模板的逐步编译

输入：

```vue
<section class="card">
  <h2>{{ title }}</h2>
  <button :disabled="saving" @click="save">Save</button>
  <p>Static note</p>
</section>
```

概念判断：

| 节点 | 动态来源 | 可给 runtime 的知识 |
| --- | --- | --- |
| section class | 无 | static |
| h2 text | `title` | TEXT flag |
| button disabled | `saving` | PROPS + dynamic prop name |
| button click | `save` | handler，可按选项 cache |
| p | 无 | 可 hoist/cache/static stringify |

概念生成代码：

```ts
const _hoisted_1 = /*#__PURE__*/ _createElementVNode(
  'p',
  null,
  'Static note',
  -1,
)

export function render(_ctx: unknown, _cache: unknown) {
  return (
    _openBlock(),
    _createElementBlock('section', { class: 'card' }, [
      _createElementVNode(
        'h2',
        null,
        _toDisplayString(_ctx.title),
        1 /* TEXT */,
      ),
      _createElementVNode(
        'button',
        { disabled: _ctx.saving, onClick: _ctx.save },
        'Save',
        8 /* PROPS */,
        ['disabled'],
      ),
      _hoisted_1,
    ])
  )
}
```

这是教学近似；exact output 受 `mode`、`prefixIdentifiers`、`hoistStatic`、`cacheHandlers`、binding metadata、dev/prod 等影响。练习必须保存真实输出，而不是把本段当快照。

## 9. Patch Flags：compiler 与 renderer 的协议

常见类别：

- TEXT：动态文本；
- CLASS/STYLE；
- PROPS：已知动态 prop names；
- FULL_PROPS：有动态 key/spread，需要更完整比较；
- NEED_HYDRATION；
- STABLE/KEYED/UNKEYED_FRAGMENT；
- NEED_PATCH；
- DYNAMIC_SLOTS；
- BAIL/CACHED 等特殊标记。

数字位值是内部共享实现，不应在业务里硬编码。阅读生成代码时使用注释名称解释。

### 9.1 `:prop` 与 `v-bind="object"`

```vue
<button :disabled="saving" />
```

compiler 知道动态 key 是 disabled，可生成 PROPS + `['disabled']`。

```vue
<button v-bind="buttonProps" />
```

运行时对象 key 不确定，往往需要 FULL_PROPS。不是说 spread 一定慢到不能用，而是编译器静态知识变少。组件 API 应以清晰契约为先，性能敏感热路径再 profile。

### 9.2 Block tree 与 dynamicChildren

block 在创建过程中收集动态后代：

```text
section block
├─ h2 TEXT       → dynamicChildren
├─ button PROPS  → dynamicChildren
└─ p static      → 跳过热路径
```

renderer 在 optimized path 可只 patch dynamic children。若遇到 BAIL、HMR 或无法保证结构，会回退完整 diff。

编译优化不是“没有 VDOM”，而是用静态信息缩小 VDOM 工作集。

## 10. `v-if` 与 `v-for` 是结构变换

### 10.1 `v-if`

transformIf 把相邻 `v-if/v-else-if/v-else` 组织成 IF/branches，codegen 通常成为 conditional expression。分支需要稳定 key 来区分身份；compiler 可注入分支 key。

注释、空白和不相邻元素会影响 else 关联。诊断工具应使用 AST，不要用“上一行字符串”猜。

### 10.2 `v-for`

transformFor 解析 source、value/key/index aliases，建立 FOR node 与 scope。fragment flag 取决于 source/children/key：

```text
稳定已知 source → STABLE_FRAGMENT（条件严格）
提供 key        → KEYED_FRAGMENT
未提供 key      → UNKEYED_FRAGMENT
```

`key` 应放在正确的 `<template v-for>` 或实际生成节点上。错误 key 会直接进入第 19 章 keyed diff 身份事故。

### 10.3 expression scope

`item` 在 `v-for="item in items"` 内是局部 alias；slot props 也建立局部 scope。分析未定义标识符或改写表达式时必须维护 scope，不能把所有 identifier 都前缀为 `_ctx.`。

## 11. Compiler DOM 的平台特有工作

compiler-dom 在 core transforms 上加入：

- DOM parser options / namespace；
- `v-html`、`v-text`；
- DOM `v-model`；
- `v-on`；
- `v-show`；
- static style transform；
- Transition 与 HTML nesting 开发诊断；
- 忽略/警告 side-effect tags；
- static stringify。

例如 `v-html` 最终走 innerHTML 类能力；Vue 不会替你 sanitize。compiler 能发现 directive 存在，不能自动知道表达式数据是否可信。

## 12. Scoped CSS 的真实模型

```vue
<style scoped>
.card .title { color: red; }
</style>
```

编译后概念上成为：

```css
.card[data-v-abcd] .title[data-v-abcd] { color: red; }
```

render/runtime 给相关 elements 添加 scope id attribute。它不是 Shadow DOM：

- 全局 CSS 仍可影响元素；
- specificity 仍按普通 CSS；
- DOM/querySelector 仍看到同一文档树；
- slot content、child root 有特别规则；
- Teleport 内容的 scope id 仍由 VNode/runtime 协调，但物理 CSS 祖先改变。

`:deep()` 允许选择器穿透 child internals，`:slotted()` 针对 slot content，`:global()` 退出 scoped。它们都增加耦合，应限制在设计系统明确定义的扩展点。

### 12.1 CSS `v-bind()`

compiler-sfc 收集 CSS vars，并生成把组件表达式桥接为 custom properties 的代码。表达式仍属于组件状态；大量高频变化 CSS vars 也会产生 style 更新，应 profile。

### 12.2 CSS Modules

CSS Modules 与 scoped 解决不同问题：前者把 class names 映射为模块对象，后者以 scope attribute 限定选择器。可组合，但会增加工具链复杂度。

## 13. Source Maps 与错误定位

一条错误可能跨：

```text
original .vue
  → preprocessor output
  → script setup transformed code
  → template generated render
  → TypeScript/Babel
  → bundled chunk
```

每阶段 source map 需要正确衔接。诊断工具至少输出：

```ts
interface Diagnostic {
  filename: string
  rule: string
  severity: 'error' | 'warning'
  message: string
  line: number
  column: number
  source?: string
}
```

Template AST loc 通常相对于 template content；要映射到整个 SFC，需结合 template block loc。不要默认 `node.loc.start.line` 已是最终文件行，实际用当前 API fixture 验证。

### 13.1 诊断稳定性

测试应断言 rule id、line/column 和关键 message，不必锁死 compiler 全部 error 文案。升级 compiler 后 golden files 人工审查，不要盲目 update snapshots。

## 14. 自定义 Compiler Transform 的风险

可以用 compiler AST 做只读诊断；直接改变 codegen 的 transform 风险更高：

- AST/codegen structures 可变；
- transform order 影响 scope/helpers/hoists；
- SSR 与 client 可能需要两套行为；
- source map 容易错；
- HMR/IDE/vue-tsc 可能与 bundler transform 不一致；
- 新 Vue 版本内部优化可改变。

优先级：

```text
ESLint / official template parser rule
  → Vite plugin 的 source-level transform（有 map）
  → compiler-sfc public API 的只读分析
  → custom node/directive transform（固定版本 + 全矩阵）
  → fork compiler（极少）
```

若只是组件 API 抽象，不要用 compiler transform 隐藏业务语义。

## 15. 安全边界：绝不编译不可信模板

Vue template 可以访问组件上下文并生成可执行 render function。服务端存储用户 template 再交给 runtime compiler，等同把代码执行权限交给用户。

富文本应使用：

- 受限文档 schema；
- 安全 renderer；
- HTML sanitizer + CSP（若确需 HTML）；
- component allowlist；
- 不允许任意表达式、directive 或 event handler。

`v-html` 的 compiler 诊断只是提醒，真正安全要求数据来源、sanitizer、URL policy 和 DOM sink 都有契约。

---

## 16. 编译性能与构建诊断

大型项目编译慢，先分阶段：

- SFC parse/compileScript；
- template compile；
- TS/vue-tsc；
- CSS preprocess/PostCSS；
- bundler transform；
- plugin hooks；
- minify/source map。

不要凭 `.vue` 文件数量猜。用 Vite debug/plugin inspect/build profile，记录 cold/warm、缓存、CPU/内存和 changed files。

优化可能包括：

- 删除重复 expensive transforms；
- 缩小 include/exclude；
- preprocessor cache；
- 避免每个 plugin 重复 parse 同一 SFC；
- 把只读诊断移到独立 CI 并缓存 content hash；
- 升级 compiler 前跑 output/behavior regression。

不要共享并修改 compiler parse cache result。

## 17. 从生成代码排查问题

### 17.1 属性每次都全量 patch

看生成代码是 PROPS 还是 FULL_PROPS，再回到 template 是否有动态 `v-bind="object"`、动态 argument 或不透明 helper。先 profile，再决定拆显式 props。

### 17.2 静态内容没有 hoist

检查编译 options、节点是否真的依赖 scope/slot/directive、是否处于 v-for、是否被 custom transform 改写。不要只凭肉眼“这段看起来静态”。

### 17.3 组件没有被解析

检查 binding metadata、import name、`isCustomElement`、component resolution 与大小写。DOM custom element 与 Vue component 的编译分流不同。

### 17.4 SSR hydration mismatch

对比 client/SSR 生成路径和第一次状态。compiler output 能解释节点结构，但真正根因常是 `Date.now()`、随机数、浏览器 API、请求级状态污染。

---

## 18. 测试策略

编译工具至少四层：

1. fixture parse：descriptor/block/loc；
2. transform unit：指定 AST input → diagnostics/metadata；
3. golden output：少量人工审查的 generated code/map；
4. runtime behavior：真正 mount/SSR render，验证输出行为。

Snapshot 只适合审 generated artifact，不能替代用户行为测试。compiler 小版本可能合法改变生成代码但行为不变；升级时先分类“仅输出变化”与“行为变化”。

---

## 19. 本章速记

1. SFC parse 产生 descriptor；template parse 产生另一层 AST。
2. compileScript 处理 script setup 宏、bindings 和生成 setup 代码。
3. 宏是 compile-time，不是任意位置可调用的 runtime function。
4. compiler core 是 parse → transform → codegen。
5. source AST 表达语法，codegen nodes 表达怎样生成。
6. patch flags/block tree 把静态知识交给 renderer，数值不是业务 API。
7. v-if/v-for 是结构 transform，并维护 branch/alias scope。
8. scoped CSS 是 selector + scope attribute 变换，不是 Shadow DOM。
9. AST 适合只读诊断；修改 codegen 的插件维护风险更高。
10. 永远不要编译不可信 template。
