# 第 10 章：渲染流水线、调度与动画

## 本章目标

能区分 JavaScript、样式计算、布局、绘制与合成，识别强制同步布局和长任务；能用 requestAnimationFrame、Observer、CSS/WAAPI 与分块调度构建流畅且尊重 reduced motion 的交互，并用 Performance 证据验证。

## 1. 浏览器提供渲染机会，不承诺固定帧率

主线程大致处理 task、清空 microtask，再在合适时机更新渲染。浏览器可以因后台标签、节能、负载或显示器刷新率跳过/合并帧。

“16.7ms 一帧”只是 60Hz 的参考，不是计时器契约。120Hz 设备预算更紧；后台页的 `requestAnimationFrame` 常被暂停或节流。

## 2. 一帧不是只执行 JavaScript

典型流水线可理解为：

```text
JavaScript -> style -> layout -> paint -> composite
```

- style：计算哪些 CSS 规则和最终值生效；
- layout：确定几何尺寸与位置；
- paint：生成文字、颜色、边框、阴影等绘制指令；
- composite：把已有图层组合到屏幕。

实际引擎会缓存、跳过或并行部分阶段。这个模型用于定位成本，不用于背诵固定实现顺序。

## 3. 写后立刻读可能强迫布局

修改 class/style 使布局失效后，读取 `offsetWidth`、`scrollTop`、`getBoundingClientRect()` 或部分 computed style，浏览器为了给出当前答案可能同步完成 style/layout。

```js
for (const row of rows) {
  row.style.width = container.clientWidth / 2 + 'px'
  total += row.getBoundingClientRect().height
}
```

循环中读写交替会形成 layout thrashing。问题不是调用了某个“禁用 API”，而是在脏布局状态下反复要求几何真相。

## 4. 按阶段批量读取与写入

先收集所有几何读取，再批量修改 DOM；需要读取修改后布局时，将它作为下一阶段，并确认只触发必要次数。

```js
const width = container.clientWidth
const heights = rows.map(row => row.getBoundingClientRect().height)
for (const row of rows) row.style.width = width / 2 + 'px'
```

若多个功能都在一帧读写，单个函数内分组还不够。可建立轻量 measure/mutate 队列，或让框架/动画系统统一所有权，避免模块彼此穿插。

## 5. requestAnimationFrame 是绘制前回调

`requestAnimationFrame(callback)` 在下一次渲染更新前调用；回调拿到高精度时间戳。同一帧的多个 callback 通常共享时间戳。

动画应按 elapsed time 计算进度，而不是“每帧移动 2px”，否则高刷新率更快、掉帧更慢。长 callback 仍会阻塞该帧；rAF 不是把重计算自动变快。

取消视图或新动画取代旧动画时，保存 id 并 `cancelAnimationFrame`，同时用任务/实体身份阻止旧结果提交。

## 6. CSS、WAAPI 与 JS 循环如何选择

简单过渡和关键帧优先 CSS；Web Animations API 适合需要 play/pause/reverse、完成 Promise 和动态关键帧的场景；逐帧 JS 适合物理模拟或必须读取实时状态的场景。

无论选择哪种，状态所有权要单一。CSS transition、WAAPI 和 JS 同时写同一 `transform`，会出现覆盖、取消和“跳回”。

`Element.getAnimations()` 可用于检查和取消当前动画；取消、替换与卸载都必须有策略。

## 7. transform/opacity 通常更接近合成

动画 `left/top/width/height` 常会触发布局或绘制；`transform` 与 `opacity` 更可能只需合成。但“更可能”不是绝对保证，滤镜、巨大图层、混合与设备内存会改变成本。

`will-change` 会提示浏览器提前准备资源，长期滥用会增加图层和显存。只在确有证据、短生命周期的热点使用，动画结束后移除。

## 8. FLIP 把布局变化转成视觉变换

FLIP：

1. First：记录变化前位置；
2. Last：应用最终 DOM 状态并记录新位置；
3. Invert：计算新旧差值；
4. Play：从反向 transform 动画到 0。

它让布局只负责最终状态，过渡由 transform 完成。快速连续重排、进入/退出元素、已有 transform 与容器滚动都要定义，否则 demo 流畅、生产跳动。

## 9. Observer 不是免费回调

ResizeObserver 适合观察元素尺寸，但在回调中反复改变被观察尺寸会形成反馈循环。先收集合并最新尺寸，再在后续帧写入。

IntersectionObserver 适合可见性、懒加载与近似曝光，不保证逐像素同步；滚动吸附或精确几何仍需合适的布局/滚动 API。

MutationObserver 回调在 microtask 时机批量得到 DOM 变更。观察范围过大、subtree + 全属性会产生噪声和分配，应限制目标与过滤条件。

## 10. 长任务需要减少、分块或转移

50ms 以上只是常用的 long task 观察阈值，不代表 49ms 就适合所有交互。一次长 JS 会推迟输入、rAF、布局和绘制。

处理顺序：

- 优化算法并减少 DOM；
- 把非关键工作拆到后续 task，检查 AbortSignal；
- 纯计算移 Worker；
- 空闲工作可在能力检测后使用 idle/scheduler API，但关键流程不能依赖“浏览器总会有空”。

用 Promise 链切成微任务通常不会给渲染让路，因为微任务会在渲染机会前被清空。

## 11. 动画也必须可访问

检测 `prefers-reduced-motion: reduce`，减少大幅位移、视差、闪烁与非必要自动动画。减少运动不总等于零动画；短淡入可保留因果，但产品应给用户控制。

动画不能成为唯一状态提示。焦点、读屏 live region、完成/错误文本要在动画关闭时仍正确。DOM 重排尽量移动同一节点，不要无故销毁当前焦点。

## 12. DevTools 验证路径

1. Performance 录制同一交互，查看 Main、Frames、Long Tasks、Recalculate Style、Layout、Paint。
2. 展开调用栈，找到哪次几何读取触发 Forced Reflow，而不是只怪最后一行。
3. Rendering 开启 FPS、Paint flashing、Layout Shift Regions 辅助观察。
4. Layers/内存检查合成层是否过多。
5. 固定设备、数据、缩放与动画设置，保存 before/after trace。

平均 FPS 会掩盖一次严重卡顿；同时关注交互延迟、最长任务、掉帧与布局次数。

## 13. React 与 Vue 迁移提示

React 的 layout effect 和 Vue 的 mounted/updated 后几何读取都可能强制布局。仅在必须“绘制前测量并修正”时使用；普通副作用不要升级为同步布局副作用。

不要用命令式代码重排框架拥有的 DOM。让 state 决定最终顺序，再在组件/指令边界测量和播放 FLIP。React key 或 Vue key 必须来自实体身份，动画 wrapper 不应破坏焦点。

框架 concurrent/transition 能调整更新优先级，不能中断一个正在执行的 300ms 同步函数，也不能修复 layout thrashing。

## 14. 评审清单

- 几何读写是否按阶段批量，是否有 forced layout 证据？
- 动画是否按时间戳运行并可取消/替换？
- 是否优先 transform/opacity，却仍验证 paint/composite 成本？
- Observer 是否合并更新并防反馈循环？
- 长任务是否先减量，再分块/Worker？
- reduced motion、焦点和非动画状态提示是否完整？
- 性能结论是否来自 production 页面和可复现 trace？

## 本章速记

- 渲染机会不等于固定 60fps。
- 写后读几何可能同步 layout；批量 measure，再 mutate。
- rAF 对齐绘制，但不会让长函数变短。
- FLIP 用 transform 呈现已完成的布局变化。
- Observer 需要范围、合并与生命周期。
- 流畅度、正确性和 reduced motion 必须一起验收。
