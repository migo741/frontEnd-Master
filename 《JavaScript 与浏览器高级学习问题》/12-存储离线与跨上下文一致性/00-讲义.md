# 第 12 章：存储、离线与跨上下文一致性

## 本章目标

学完后，你应能按数据规模、同步成本、生命周期和一致性选择浏览器存储；能正确使用 IndexedDB 事务与升级；能设计多标签页/Service Worker 共用的离线 outbox，处理幂等、租约、冲突、配额和恢复，而不是把 `localStorage` 当小型数据库。

## 1. 先按数据职责选存储

浏览器里没有一个“最好的存储”：

| 能力 | 合适用途 | 主要限制 |
|---|---|---|
| Cookie | 服务端会话、少量请求状态 | 每次请求可能携带；安全属性与 CSRF 策略必须成套 |
| `sessionStorage` | 单标签页、当前会话少量字符串 | 同步 API、容量有限、不是可靠持久数据 |
| `localStorage` | 少量非敏感偏好、兼容信号 | 同步阻塞、字符串、无事务，不适合队列/大对象 |
| IndexedDB | 结构化数据、索引、事务、离线队列 | 异步模型和升级复杂，仍可能被清理 |
| Cache Storage | Request/Response 资源缓存 | 不是通用查询数据库，失效与版本要显式设计 |
| OPFS | 大文件/高性能文件型工作负载 | 能力与线程模型需检查，业务索引仍要自己设计 |

敏感信息“加密后放 localStorage”并不能自动抵抗 XSS：若页面脚本能拿到解密密钥，也能解密。客户端存储首先按最小化、生命周期和威胁模型决定。

## 2. `localStorage` 是同步共享状态

序列化、磁盘/进程协调和大字符串操作可能阻塞主线程。它没有原子 compare-and-swap，也没有跨多个 key 的事务。读 → 改 → 写会在两个标签页间丢更新：

```js
const count = Number(localStorage.getItem('count') ?? 0)
localStorage.setItem('count', String(count + 1))
```

两个标签页都读到 0，最后仍可能是 1。`storage` 事件通常通知其他同源文档，不会给发起写入的当前文档发送；它是变化提示，不是可靠消息队列。

## 3. IndexedDB 的核心是事务

IndexedDB transaction 把一组对象仓库操作变成原子提交。事务作用域和 mode 在创建时确定；`readonly` 可并行读，`readwrite` 在重叠作用域上串行协调。

关键陷阱：事务会在没有待处理请求且当前任务结束后自动提交。不要在事务中等待网络、timer 或任意与该事务无关的 Promise：

```js
const tx = db.transaction('outbox', 'readwrite')
const item = await request(tx.objectStore('outbox').get(id))
await fetch('/api/send', {body: JSON.stringify(item)}) // 错：事务早已可能 inactive
tx.objectStore('outbox').delete(id)
```

正确做法是短事务领取/标记 → 事务提交 → 网络 I/O → 新事务按身份确认结果。

## 4. schema 升级也是分布式问题

对象仓库和索引只能在 `versionchange` 事务中演进。旧标签页保持连接会阻塞新版本升级，因此必须处理：

- 新连接的 `blocked`：提示用户关闭/刷新旧页面；
- 旧连接的 `versionchange`：尽快 `db.close()` 并进入刷新流程；
- 升级函数可从任意受支持旧版本逐步前进；
- 大规模数据回填不要让一次 upgrade 长时间锁死，可把 schema 变更与后台数据迁移拆开。

页面、Worker、Service Worker 可能同时打开数据库；升级协议必须把它们都算作参与者。

## 5. 离线不是“请求失败就缓存”

离线写入至少需要状态机：

```text
queued -> claimed -> sending -> confirmed
                     ├-> retryable -> queued
                     ├-> conflicted
                     └-> permanent-failure
```

每条操作包含唯一 mutation id、实体 id、base version、payload、创建时间、尝试次数和下次重试时间。服务端必须按 mutation id 幂等，否则断线后的“不知道是否成功”会造成重复操作。

只监听 `online` 事件不够：`navigator.onLine` 只能给出粗信号，不能证明目标服务可用、身份仍有效或写入会成功。

## 6. 请求的“不确定结果”

客户端超时可能发生在服务端提交之前或之后。不能因为没收到响应就断言“失败”。安全恢复依赖：

- 幂等键让同一 mutation 重试只生效一次；
- 服务端提供按 mutation id 查询结果，或响应返回权威实体版本；
- 非幂等动作需要业务补偿/人工确认，不能盲目指数重试；
- 客户端保持 `unknown/confirming` 状态，而不是立即回滚成旧事实。

## 7. 多标签页协调：通知不是事实

BroadcastChannel 适合同源上下文发送小型通知，但消息不持久，晚加入者看不到历史，页面崩溃也没有确认。常用模式：

```text
IndexedDB = 权威本地事实
BroadcastChannel = “请重新读取某实体/队列”的提示
```

不要广播完整可变缓存并假设所有标签页严格按同一顺序收到。消息带 schema version、entity id、authoritative version 和 sender id；接收端仍按版本决定是否重读。

## 8. 单领导者与租约

多个标签页同时 flush outbox 会重复发送。优先考虑 Web Locks API（目标环境支持时）做互斥；跨 Service Worker/页面仍要依赖数据库状态和服务端幂等作最终防线。

若实现租约，记录 `ownerId`、`leaseUntil` 和单调 fencing token。旧领导者暂停很久后恢复，不能仅凭“我曾经持有 lease”继续确认任务；每次完成都必须校验当前 owner/token。

客户端 wall clock 会跳变，租约只是减少重复，不应成为金额/权限正确性的唯一保证。

## 9. 冲突不是错误弹窗

离线编辑基于旧版本，服务端已更新时，需要领域策略：

- last-write-wins：简单但可能静默丢数据；
- 字段级合并：适合互不冲突字段；
- 三方合并：base/local/remote，适合文本或结构化编辑；
- 服务端拒绝并让用户选择：适合高风险业务；
- CRDT/OT：只有真实协作需求和团队能力足够时采用。

“取更新时间更大者”依赖不可靠客户端时钟，也没有表达业务冲突。

## 10. Service Worker 的正确位置

Service Worker 可以拦截请求、管理 Cache Storage、在能力允许时处理 Background Sync，但生命周期由浏览器控制，可能随时终止；后台同步也不是所有环境都保证及时发生。

因此：

- 队列事实持久化在 IndexedDB；
- 每一步可重入、可幂等；
- 不把内存变量当长期锁/进度；
- 页面重新打开时也能恢复；
- SW 更新时新旧 schema 有兼容窗口。

App Shell 资源缓存与业务数据缓存分开版本/失效，避免新 HTML、旧 chunk 和新 API schema 混装。

## 11. 配额、清理与持久化

浏览器存储有配额，并可能在空间压力、隐私设置或无痕模式下受限/被清理。使用 `navigator.storage.estimate()` 观察用量；对确有长期离线价值的站点可申请 `persist()`，但用户代理可以拒绝。

必须有：容量预算、TTL/LRU、按用户隔离、退出清理、导出/恢复或明确数据丢失体验。Blob/Object URL、Cache Storage 与 IndexedDB 都计入资源预算，不只看 JS heap。

## 12. React 接入

存储与 BroadcastChannel 是外部系统：在 Effect/外部 store 中订阅，cleanup 关闭 channel/连接。渲染阶段不直接写存储。对 React 使用 `useSyncExternalStore` 时，`getSnapshot` 返回缓存的不可变值；通知到达先读权威 DB，再发布新快照。

自动保存应由显式状态机管理，不把“每次 state 变化都 Effect 写库/发请求”当设计。卸载不保证异步写一定完成，关键草稿要在正常编辑过程中增量持久化。

## DevTools 验证

1. Application 面板检查 IndexedDB、Cache Storage、Service Worker 生命周期；
2. 同时打开两个标签页，手动暂停其中一个再恢复，验证旧领导者不能确认新租约；
3. DevTools Offline/网络失败与真实服务 500 分开测试；
4. 清理站点数据、配额失败、upgrade blocked 都要有可理解 UI；
5. 记录队列长度、最老等待时长、冲突、重复、配额和迁移失败。

## 评审清单

- 为什么选这个存储，容量/同步/事务需求是什么？
- 事务里是否等待了网络或 timer？
- mutation 是否有幂等键和权威版本？
- 多标签页通知是否只当提示，事实是否可重读？
- 领导者是否有租约/栅栏，旧实例能否误确认？
- 配额、清理、退出登录和 schema 升级如何处理？

## 本章速记

- localStorage 是同步字符串槽，不是事务数据库。
- IndexedDB 事务要短；网络 I/O 放在事务外。
- IndexedDB 保存事实，BroadcastChannel 发送提示。
- 离线写要有幂等、版本、冲突与“不确定结果”。
- Service Worker 可随时终止，流程必须可重入恢复。
