# 05 · 四个故障现场

启动本机服务器，进入 `/web/faults.html`，保持学生模式。只修改 `labs/05-faults/src/index.js`；其他文件提供可控环境。

## 第一阶段：不看答案收集现场

### A：搜索结果偶尔不对

点击“复现操作”，等待所有请求完成。记录用户最后输入、请求开始/完成顺序、每次显示的内容。期望最终显示最后一次搜索意图对应的结果。

还要验证：旧请求失败不能覆盖新状态；dispose后迟到结果不能显示；当前请求失败仍通过onError呈现。fetchRows可能忽略取消，不能依赖取消总能成功。

### B：页面恢复了，资源是否恢复？

刷新后取基线Heap Snapshot；开关100次再取快照；再开关100次取第三次。DOM当前面板数应归零，订阅资源应回到基线。

不要先把问题归因于垃圾回收。检查对象类型、数量和retaining path，给出至少一个被排除的假设。不要在Console长期保存可疑对象；记录对象本身也可能影响回收观察。

### C：调整表格时卡顿

录制Performance并点击调整尺寸。页面固定2000行，保持相同数据和窗口。指出耗时集中在哪类活动，再提出改法。

输出的汇总高度必须与新宽度下的实际高度一致；不能通过跳过工作、返回缓存旧值来“优化”。修复前后至少5次同条件样本，中位数之外说明波动。

### D：同一发布，部分会话启动后空白

进入 `/web/release.html`。先启动全新会话，再启动历史会话，对比 iframe 内容和日志。提供了真实的旧 Service Worker、旧缓存响应、新 API 路由、前端发布产物、发布清单与 source map。

先不改代码，至少记录：web release id、API/缓存响应版本、控制页面的Service Worker、实际网络来源和错误栈。尝试通过Sources映射到原源码。不要只用“清缓存重试”作为最终解决方案，需解释灰度窗口内如何让旧会话继续工作。

增加/修复 `readFeature(config)`：兼容发布清单中schema1和schema2的布尔配置；未知版本、错误字段类型明确抛TypeError。页面入口将错误写入运行日志；基本修复要求两种受支持协议都能启动。为未知协议增加用户可见降级页面属于迁移挑战。

完成后点击“清理本实验历史会话”。只注销 `/release/old/` 作用域和本实验的缓存，不清理其他站点数据。

## 第二阶段：修复与回归

实现/修复三个原有接口：createSearch({fetchRows,render,onError})、mountPanel({root,events})→dispose、resizeRows(rows,width)→totalHeight。保持页面接口不变。

`node scripts/test.mjs 05` 的8项公开测试通过；浏览器操作确认上述四种现象已消失。切换 `?mode=reference` 只用于结果对照，勿把对照结果当作自己的修复证据。

Node布局测试模拟“写后首次读触发flush”，只能发现读写交错回归。真实浏览器可能有其他布局成本；必须检查trace。资源测试同样只检查订阅等生命周期，不证明所有内存都无泄漏。

交付四份短报告，每份包含复现、两个假设、关键证据、根因、最小修复和回归。另加一个你自己的反例。
