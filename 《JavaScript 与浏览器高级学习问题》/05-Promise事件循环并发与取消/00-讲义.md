# 第 05 章：Promise、事件循环、并发与取消

> 异步代码的核心不是“用了 await”，而是明确任务的所有权、顺序、失败与终止。

## 学习目标

- 能画出 task、microtask 与渲染机会的 happens-before 关系。
- 能解释 Promise resolution、thenable assimilation 与异常传播。
- 能区分并发、并行、限流、防抖和竞态处理。
- 能用 AbortSignal 建立协作式取消协议。
- 能设计“子任务全部被结算”的结构化并发边界。

## 1. 事件循环首先保证 run-to-completion

一段正在执行的 JavaScript task 不会被另一个 task 从中间抢占。 浏览器在 task 之间选择下一项工作，并在合适时机进行渲染。 定时器回调、用户输入、MessageChannel 消息来自不同 task source。 同一来源通常保持自身顺序，但不同来源之间不要猜一个跨浏览器总顺序。

`setTimeout(fn, 0)` 表示达到最小延迟后可以排队，不表示立刻执行。

长 task 会同时阻塞输入处理、定时器和渲染。

## 2. microtask checkpoint

Promise reaction、`queueMicrotask`、MutationObserver 使用 microtask 机制。 当前 JavaScript 栈清空后，浏览器会执行 microtask checkpoint。 checkpoint 会持续清空队列；microtask 新增的 microtask 也会在本轮继续执行。 因此递归补充 microtask 可以饿死 task 与渲染。

```js
function starve() {
  queueMicrotask(starve);
}
```

微任务“比定时器先”是常见现象，但真正规则是当前 task 后的 checkpoint。 不要把 microtask 当成高性能任务队列。

## 3. 渲染不是普通 Promise 回调

浏览器通常在 task 与 microtask checkpoint 之后获得渲染机会。 “机会”不等于每轮必定渲染；后台页、刷新率和主线程负载都会影响它。

`requestAnimationFrame` 回调在将要绘制一帧前运行，适合基于帧的视觉更新。

rAF 回调中的 microtask 会在浏览器继续后续渲染步骤前被处理。 定时器与 rAF 的具体先后不能脱离注册时刻和渲染机会武断回答。 高级推演应写出保证顺序与未规定顺序，而不是背一串日志。

## 4. Promise 是未来结果的状态机

Promise 有 pending、fulfilled、rejected 三种状态。 settled 后状态不可再次改变。

`resolve(x)` 不总是立刻 fulfilled；若 x 是 Promise/thenable，会采用其最终状态。

读取 thenable 的 `then` getter 也可能抛错或有副作用。 每次 `.then` 都返回一个新的 Promise。 回调返回普通值会兑现下游，抛错会拒绝下游，返回 Promise 会被吸收。 这就是链式错误传播成立的原因。

## 5. async/await 是 Promise 控制流

调用 async 函数总会得到 Promise，即使函数体直接 return 普通值。 执行会同步前进到第一个 await 表达式求值处。 await 后的续体以异步 reaction 继续，不会在当前栈中直接恢复。 try/catch 可捕获 await 的拒绝，但捕获不到没有 await/return 的“悬空 Promise”。

```js
async function wrong() {
  try {
    doAsyncWork(); // 没有 await，也没有 return
  } catch {}
}
```

调用者会过早看到 wrong 已成功，后台拒绝可能成为 unhandled rejection。

## 6. 并发不等于并行

并发表示多个任务生命周期重叠。 主线程 JavaScript 仍通常一次执行一段代码。 网络、计时器和部分浏览器服务可在外部推进，再把结果送回主线程。 真正 CPU 并行需要 Worker 等执行环境。

`Promise.all(items.map(fetch))` 会立即启动全部 fetch，不提供限流。

大型批量请求应根据服务端、浏览器连接、内存和交互优先级设置并发上限。

## 7. Promise 组合器的失败语义

`Promise.all` fail-fast，但其他输入并不会因此自动取消。

`Promise.allSettled` 等待所有结果，适合批处理报告。

`Promise.any` 首次成功；全部失败时给出 AggregateError。

`Promise.race` 首个 settled 决定结果，也不会终止输家。

“不再关心结果”和“任务已经停止”是两回事。 组合器选择必须与资源所有权和失败策略一起设计。

## 8. AbortSignal 是协作协议

AbortController 负责发出一次取消信号。 任务应在启动前检查 `signal.aborted`，运行中监听 abort，并在结束后清理监听。 支持 signal 的平台 API 通常以 AbortError 或 `signal.reason` 结束。 JavaScript 不能安全地强杀任意函数；忽略 signal 的任务无法被控制器强制停止。 取消应尽可能向子任务传播，但不能把父级或兄弟无关任务误取消。 现代 API 可组合超时与多个信号；使用前应按目标运行环境验证兼容性。

## 9. 结构化并发

一个并发作用域应拥有其启动的子任务。 作用域结束前，子任务应已成功、失败或取消并被观察。 不能把 Promise 启动后丢在后台，除非明确交给更高层生命周期管理。 失败策略通常有两种：一个失败取消同组任务，或收集所有独立结果。 无论哪种，都要避免未处理拒绝和作用域结束后继续写状态。 限流器、页面 loader 和批量上传都应显式说明这一契约。

## 10. 竞态与版本

单线程也会有竞态，因为多个异步操作在 await 处分段交错。 搜索 A 先发、搜索 B 后发，不保证 A 先完成。 常用策略包括取消旧请求、比较单调版本、按 key 去重、串行化提交。 取消用于节省资源，版本检查用于保证最终正确；关键路径常同时使用。 不要把 debounce 当竞态修复，它只降低频率，不能证明完成顺序。

## 11. 生产失败案例：fail-fast 后仍写入

页面用 `Promise.all` 加载三个资源，其中一个快速失败。 catch 触发卸载，但另两个请求仍继续，完成回调写入已经销毁的 store。 根因链：误解 fail-fast 为 cancel → 子任务失去所有者 → 迟到副作用发生。 修复是共享作用域 AbortSignal、所有完成路径都受生命周期检查，并结算已启动任务。

## 12. 常见反例

```js
items.forEach(async (item) => {
  await save(item);
});
// forEach 不等待回调 Promise
```

```js
await items.map(save); // await 一个普通数组，不会等待数组内 Promise
```

顺序执行用 for...of + await；全并发用 Promise.all；限并发用明确调度器。 不要在 Promise 构造器里包一个本来已返回 Promise 的函数，这会增加错误通道。

## 13. DevTools 与验证

Performance 面板可观察 Long Task、计时器和渲染时机。 Network 面板可确认取消是否真的中止请求，而非只忽略结果。 在任务开始/结束日志中记录 taskId、parentId、版本和 abort reason。 启用浏览器的 Promise rejection 暂停，定位未处理拒绝的原始位置。 用受控 deferred Promise 测试所有完成排列，不要靠真实 setTimeout 制造竞态。 并发测试记录 active 与 maxActive，证明上限而不是目测。

## 14. React/Vue 迁移

React Effect 的 cleanup 应取消或使旧任务失效，尤其在开发期重复挂载验证下。 事件处理器启动任务时，要决定结果属于哪次渲染意图，而不是只写 setState。 Vue 的 watch/watchEffect 也提供清理时机，旧异步结果同样可能覆盖新值。 从 Vue 到 React 不要依赖 watcher 自动排序；从 React 到 Vue 也不要忽略 Promise 的独立生命周期。 框架能提供生命周期入口，不能替你定义取消和竞态政策。

## 15. 速记与自检

- 当前栈结束后清空 microtask；不同 task source 的跨源顺序不要猜。
- Promise 链的每个 then 都产生新 Promise。
- all 的 fail-fast 不等于取消其他任务。
- AbortSignal 是协作取消，正确性仍需版本或所有权约束。
- 启动的任务必须有人等待、观察或明确接管。

自检：为什么递归 microtask 会卡住页面？await 一个 Promise 数组为何无效？如何证明并发池没有孤儿任务？
