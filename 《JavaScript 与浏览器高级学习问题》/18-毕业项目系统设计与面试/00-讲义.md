# 第 18 章：毕业项目、系统设计与面试

## 本章目标

把前 17 章从“我学过”变成可审查证据：完成一个 React 生产级项目，面对性能、竞态、离线、安全、可访问性和发布故障仍能解释并守住不变量；能在系统设计面试中从需求、规模和失败模式推导方案。

## 1. 毕业项目：高性能协作工单运营台

你要构建一个面向客服/运营的工单系统。它不是另一个 CRUD：同一账号可能开多个标签页；列表有万级数据和实时更新；编辑要自动保存、离线恢复并处理版本冲突；高风险操作要鉴权和审计；系统还要在慢网、弱机和部分服务失败下可用。

建议主栈：React 19.2 当前稳定补丁、严格 TypeScript、Vite 或合适 React 框架。若目标公司仍以 React 18 为主，保留兼容分支并记录差异。TypeScript 深化直接复用 TS Master，不在本章重复语法。

## 2. 核心用户旅程

1. 通过 URL 可分享的筛选条件进入工单列表；
2. 键盘浏览、搜索和打开详情，列表位置不丢失；
3. 编辑字段/富文本，自动保存，网络断开时写入 outbox；
4. 其他标签页/同事修改时收到提示，按版本解决冲突；
5. 批量操作需要权限、二次确认、幂等与可回滚反馈；
6. 实时新消息以有限频率合并，不阻塞输入；
7. 错误边界允许局部重试，不能整页白屏或静默丢数据。

## 3. 强制非功能约束

### 正确性

- 每个实体有稳定 id/version；旧响应不能覆盖新状态；
- mutation 有幂等键，乐观更新可回滚且与乱序完成兼容；
- 离线队列显式 `queued/sending/confirmed/conflicted/failed`；
- 多标签页消息有 generation/version，不能用“最后写入 localStorage”冒充一致性协议。

### 性能

- 万级列表 DOM 数量受控；筛选计算不长时间占主线程；
- 目标环境 p75：LCP `<= 2.5s`、INP `<= 200ms`、CLS `<= 0.1`；
- 路由级代码分割，关键路由有 JS/资源预算；
- 无持续增长的 heap、listener、timer、Worker 或缓存。

### 安全与隐私

- 服务端逐请求鉴权；UI 权限只改善体验；
- 富文本使用受控 sanitizer，提供 CSP 上线计划；
- Cookie/CSRF/CORS 形成完整方案；
- `postMessage`（若做嵌入）严格校验；
- token、正文和个人信息不进入 URL/日志/不必要存储。

### 可访问性

- 核心流程全键盘可用；焦点在弹窗、路由和错误后可预测；
- 虚拟列表仍有合理语义；表单错误可被辅助技术理解；
- 支持 reduced motion，颜色不是唯一状态信号；
- axe 无 serious/critical，关键组件做手工读屏验证。

### 可靠交付

- typecheck、lint、unit/integration、关键 E2E、build 全绿；
- release id、错误、Web Vitals 和关键业务状态可关联；
- feature flag 有默认/所有者/过期时间；
- 静态资源缓存、Service Worker（若用）和 API schema 支持灰度/回滚。

## 4. 推荐架构：先边界后目录

先划分状态：

- URL 状态：筛选、排序、当前选中 id；
- 服务端状态：工单、评论、权限、版本；
- 客户端会话状态：草稿、选择、面板布局；
- 外部系统状态：在线状态、BroadcastChannel、Worker、SSE；
- 短暂 UI 状态：hover、菜单开关。

再按业务垂直切片组织：

```text
src/
├── app/              # 路由、providers、错误边界
├── features/tickets/ # 领域状态、UI、请求与测试
├── features/editor/
├── entities/
├── shared/browser/   # Worker、storage、telemetry adapter
├── shared/ui/
└── server/           # 若框架/BFF 需要
```

依赖方向要可执行检查。不要建立一个可导入任何东西的 `utils/`，也不要让领域规则散落在组件 Effect。

## 5. 数据流设计

读路径：路由参数 → 校验/规范化 → query key → 缓存/请求 → 不可变 snapshot → 视图。写路径：用户意图 → client validation → mutation id/version → 乐观层/outbox → server authorization → authoritative result → 合并/冲突。

每条异步边界回答：

- 谁拥有请求？
- 如何取消？
- 如何识别迟到结果？
- 是否可安全重试？
- 失败归谁展示？
- 缓存何时失效？
- 离线和多标签页如何处理？

## 6. 分阶段实现

### M0：约束与证据计划

写用户旅程、数据规模、浏览器矩阵、SLO、威胁模型和 5 个初始 ADR。先定义怎么验收，再写组件。

### M1：可靠读模型

路由/筛选/详情、schema 校验、请求取消与错误边界；用 mock server 控制慢网、乱序和错误。

### M2：编辑与离线

自动保存状态机、幂等/版本、IndexedDB outbox、冲突 UI、多标签页通知。

### M3：性能平台

虚拟列表、Worker 过滤/聚合、流更新合并、代码分割；提交基线和优化 profile。

### M4：安全与可访问性

富文本、CSP/CSRF、权限测试、键盘/焦点/读屏；写威胁模型复审。

### M5：测试与可观测

风险分层测试、契约、关键 E2E、Web Vitals/错误/业务指标、Source Map release 映射。

### M6：发布与故障演练

预览、灰度、flag、缓存兼容、回滚；运行本章练习二的故障注入。

### M7：AI-native 扩展（建议）

增加“工单摘要/建议动作”面板：SSE 流式事件、取消/重试、结构化输出校验、tool call 需人类确认、引用证据、成本/延迟/错误观测。AI 输出永远是建议，不能绕过权限直接执行高风险动作。

## 7. 架构决策记录（ADR）

至少写：

1. 为什么选择当前路由/数据框架；
2. 为什么某状态在 URL、query cache、外部 store 或局部 state；
3. Worker 与主线程的数据所有权；
4. 离线冲突策略；
5. 富文本安全策略；
6. 虚拟列表的可访问性取舍；
7. 观测与隐私边界；
8. AI 功能的人类确认边界（若做）。

模板：Context → Decision → Alternatives → Consequences → Evidence → Revisit trigger。ADR 不是为决定辩护，而是让未来团队知道约束变化时何时重选。

## 8. 前端系统设计面试方法

45 分钟建议分配：

1. 5 分钟澄清用户、规模、设备、实时性、合规和成功指标；
2. 5 分钟定义关键旅程与不变量；
3. 10 分钟画数据流和模块边界；
4. 10 分钟深挖一个难点（竞态/缓存/性能/离线）；
5. 8 分钟讲安全、可靠性、可观测和发布；
6. 5 分钟讲演进、成本与替代方案；
7. 2 分钟总结取舍。

不要从“我会用 React Query + Zustand”开始。库是决定之后的实现手段。

## 9. 面试中的 JavaScript 深挖

面对输出题，按执行上下文、求值顺序、抽象操作、任务/微任务画过程；面对手写题，先写 API 契约、错误/取消/复杂度；面对性能题，先要求基线与 profile；面对架构题，先量化规模和失败模式。

如果没做出最优代码，清楚说出当前正确性、复杂度、已知边界和下一步验证，通常比沉默套模板更接近高级表现。

## 10. AI 编码作品证据

可以使用 AI 完成项目，但要保留一份 `AI-usage.md`：

- 哪些任务由你拆分，哪些草稿由 AI 产生；
- 你发现并修复了哪些错误假设；
- 哪些测试/基准/安全审查验证了产出；
- 哪些关键设计由你决定及原因。

大厂越来越看重 AI 工具能力，也更看重代码审查、上下文工程和质量兜底。无法解释的生成代码会削弱而不是增强作品。

## 11. 评分（100 分）

| 维度 | 分值 | 核心证据 |
|---|---:|---|
| 功能与可靠性 | 20 | 慢网/离线/乱序/冲突下不丢数据 |
| JS 与浏览器机制 | 15 | 事件循环、Worker、存储、DOM 所有权正确 |
| React 与状态架构 | 15 | 快照、Effect、身份、外部 store、错误边界正确 |
| 性能与内存 | 15 | profile、CWV、预算、无持续泄漏 |
| 测试与工程 | 10 | 门禁、契约、关键 E2E、可复现构建 |
| 安全与隐私 | 10 | 威胁模型、XSS/CSRF/权限/消息边界 |
| 可访问性 | 5 | 键盘、焦点、语义、读屏证据 |
| 可观测与发布 | 5 | release 关联、灰度、告警与回滚 |
| 文档与答辩 | 5 | ADR、复盘、现场变更 |

85 分及格，且红线项必须全部通过：无可利用越权/XSS、无核心数据丢失、无明显持续内存增长、关键流程可键盘完成、核心逻辑可解释。

## 本章速记

- 高级能力是约束下的正确取舍和证据，不是库数量。
- 先定义不变量和 SLO，再设计数据流与组件。
- 毕业项目必须主动制造慢网、乱序、离线和故障。
- 架构、测试、观测、发布属于同一个系统。
- AI 可以加速实现，不能接管验收责任。

## 自检问题

1. 为什么 URL 状态与服务端状态不应混成一个全局 store？
2. 前端忽略旧响应为什么还不能完全阻止服务端旧写覆盖？
3. 静态资源回滚为什么要考虑 Service Worker 和 API schema？
4. 系统设计为什么必须先问规模和失败模式？
5. 作品如何证明你使用 AI 后仍掌握关键代码？
