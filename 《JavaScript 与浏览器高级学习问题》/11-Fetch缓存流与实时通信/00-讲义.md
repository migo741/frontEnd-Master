# 第 11 章：Fetch、缓存、流与实时通信

## 本章目标

能解释 Fetch 的错误、取消与 body 生命周期，区分 HTTP cache、Cache API 和应用缓存；能从字节流、重试、背压与序列协议设计 SSE/WebSocket 客户端，并用 Network/Performance 证据排查瀑布、错误缓存和无限缓冲。

## 1. Fetch 成功只代表拿到了响应

`fetch()` 在 DNS、连接、TLS、CORS 或取消等网络层失败时 reject；服务器返回 404/500 时通常仍 resolve 为 Response。

```js
const response = await fetch(url, {signal})
if (!response.ok) {
  throw new Error('HTTP ' + response.status)
}
const data = await response.json()
```

错误至少要区分 network、aborted、http、decode/protocol。把所有异常显示成“网络错误”会误导用户和告警，也让 401、429、500 的恢复策略混在一起。

## 2. Request/Response body 通常只能消费一次

Body 是流。读取 `json()`、`text()` 或 reader 后，`bodyUsed` 会变为 true。需要交给两个消费者时可提前 `clone()`，但 clone 不是免费复制：慢消费者仍可能导致缓冲和内存增长。

大型响应不要默认 `json()` 全量缓冲。先检查状态、Content-Type、声明/实际大小上限，再决定整体解析还是流式消费。

错误响应体也不可信且可能巨大；日志只保留限长、安全字段与 request id，不把用户数据整段打印。

## 3. 取消是一条向下传播的协议

组件卸载、用户切换资源、超时和父任务取消，都应汇入 AbortSignal。目标环境支持时可用 `AbortSignal.timeout/any`；否则组合 controller 时必须移除外部 listener 与 timer。

取消 fetch 不等于撤销服务端已经开始的 mutation。写操作仍需幂等 key、服务端事务与查询最终状态。前端“没收到响应”不能推断服务端“没执行”。

## 4. CORS 不是客户端开关

CORS 由响应头和浏览器执行。`mode: 'no-cors'` 不会绕过权限，它通常只得到无法读取内容的 opaque response。

跨源 Cookie 需要客户端 credentials 与服务端明确允许，且仍受 SameSite、第三方 Cookie 策略等约束。预检是协议成本，不能靠删除安全头“优化”。

安全细节在第 14 章展开；本章的原则是把 origin、credentials、可读响应和失败方式写进请求契约。

## 5. HTTP 缓存由响应协议驱动

常见语义：

- `Cache-Control: max-age`：在新鲜期内可直接复用；
- `no-cache`：可以存，但使用前要向服务器验证；
- `no-store`：不应存储；
- `ETag/If-None-Match`：内容验证，未改变返回 304；
- `Vary`：说明缓存 key 还受哪些请求头影响。

304 没有新的完整表示，必须与已有缓存条目合并。没有本地条目却收到 304 是协议/缓存状态异常。

敏感 per-user/tenant 数据不能进入公共共享缓存；CDN、浏览器、Service Worker 与应用内 Map 的 key 都必须包含真正影响表示的身份维度。

## 6. 三种“缓存”不要混称

1. 浏览器 HTTP cache：遵循 HTTP 方法、状态和缓存头，fetch 可通过 `cache` 选项影响查找/验证。
2. Cache API：由应用/Service Worker 显式 `put/match/delete` Request/Response；它不会自动遵守你的业务失效。
3. 应用数据缓存：保存解析后的领域数据、查询状态和订阅；负责 stale、去重、失效与 UI 协调。

同一资源叠三层缓存并不可怕，不知道每层 owner、key、TTL 与清理才可怕。DevTools 勾选 Disable cache 只影响调试情境的一部分，也可能掩盖真实行为。

## 7. 重试必须考虑操作语义

GET 等安全请求遇到瞬时网络错误、部分 5xx、429 时可有限重试；POST 支付等不能因为“超时”就盲重放。

使用指数退避加 full jitter，尊重 `Retry-After`，设置总时限和最大次数。用户明确取消不重试；认证/校验错误不靠重试修好。

写操作若提供服务端幂等 key，重试仍要保存同一个 key。每次重试生成新 key 会把一次意图变成多次操作。

## 8. 流是字节、解码、分帧和领域事件四层

`response.body` 是 ReadableStream，chunk 边界由传输决定，不等于 UTF-8 字符、JSON 行或 SSE event 边界：

```text
Uint8Array -> TextDecoder(stream) -> protocol framing -> parse/validate -> domain
```

每层都要有上限和错误策略。消费者停止时 cancel reader 并释放锁；无限长无分隔输入必须触发上限，不能让 buffer 永久增长。

ReadableStream 的 pull 模型能自然形成一定背压；WebSocket 是 push，浏览器没有替业务自动提供可控的入站背压。

## 9. SSE、WebSocket 与普通请求各有边界

- 普通 HTTP：一次请求/响应、缓存和基础设施最成熟；
- SSE：服务端到客户端文本事件、自动重连语义、适合通知/进度；
- WebSocket：双向消息，适合协作、游戏、实时控制，但协议、重连和背压都由应用承担；
- fetch streaming：适合逐步读取 HTTP body，能自定义 framing 与认证。

选择依据是方向、频率、代理环境、鉴权、消息大小、恢复语义和运维能力，不是“WebSocket 更高级”。

## 10. 实时正确性来自序列协议

连接成功不等于数据正确。生产协议至少回答：

- 首次 snapshot 与后续 delta 如何衔接；
- sequence 重复如何去重，缺口如何发现；
- 断线从 lastSequence 恢复，还是重新取 snapshot；
- 消息能否按 entity 合并，哪些绝不能丢；
- 缓冲上限、超限降级和 stale 提示；
- 客户端版本不认识新事件时怎么办。

网络 `online`、页面 visibility 只是提示，不是事实来源。恢复后仍应验证序列或重新同步。

## 11. 连接也是可释放资源

为 socket、timer、reader、event listener 建立一个 owner。关闭流程要阻止未来重连 timer、移除 handler、关闭/取消传输，并让迟到消息无法提交。

指数退避应在稳定连接一段时间后重置；所有客户端同时断线时加 jitter，避免服务恢复瞬间惊群。心跳超时、网络错误和服务器主动关闭应有可观测的不同原因。

## 12. DevTools 验证路径

- Network 检查 method/status、request/response headers、Timing、Initiator、缓存来源；
- 关闭和开启缓存各录一次，确认 200/304/from memory/disk 的路径；
- 查看 EventStream/WebSocket frames、间隔、大小与断线码；
- Performance/Memory 观察持续流是否造成长 task、DOM 和 buffer 增长；
- 使用可控 fake server 注入慢响应、半包、重复、乱序、断线和 429；
- 记录 request id、attempt、sequence lag、重连次数与缓冲水位。

## 13. React 与 Vue 迁移提示

远端状态优先交给 Router loader/Query 层，而不是每个组件各写一份 fetch Effect/watch。框架负责渲染，不能自动解决 HTTP 缓存 key、取消、幂等和序列缺口。

组件只订阅需要的派生数据；不要把 WebSocket 实例或 ReadableStream 塞进可序列化 store。连接放服务层，state 保存协议状态与领域数据，卸载是否断连由共享所有权决定。

## 14. 评审清单

- HTTP error、network、abort、decode 是否分开？
- body 是否只消费一次，并有限长与清理？
- cache 的层、key、身份、TTL、验证和 owner 是什么？
- mutation 超时后是否可能已成功，幂等如何保证？
- retry 是否有条件、上限、jitter 和 Retry-After？
- 实时协议是否处理 snapshot/sequence/gap/dedupe/backpressure？
- 断开与卸载后是否还会重连或提交迟到数据？

## 本章速记

- Fetch 对 HTTP 4xx/5xx 通常不 reject。
- 304 依赖已有表示；no-cache 不等于 no-store。
- Response body 是一次性字节流，chunk 不是业务消息。
- 重试必须服从幂等与总时限。
- WebSocket 连接状态不等于领域数据一致。
- snapshot + sequence + gap recovery 才是实时正确性的骨架。
