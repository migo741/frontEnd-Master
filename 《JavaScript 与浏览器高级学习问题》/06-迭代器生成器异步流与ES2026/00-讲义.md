# 第 06 章：迭代器、生成器、异步流与 ES2026

> 数组表达“已经拥有全部数据”，迭代器表达“按需取得下一个值”；这一区别决定内存、取消与背压。

## 学习目标

- 区分 iterable、iterator、iterator result 与一次性消费。
- 理解生成器的暂停、双向通信、异常注入和关闭。
- 用 async iterable 建立按消费速度推进的数据管道。
- 能解释早退时的 IteratorClose 与资源清理，并准确区分 ES2026 标准、旧标准与提案能力。

## 1. iterable 与 iterator 是两个角色

iterable 拥有 `[Symbol.iterator]()`，用于取得 iterator。 iterator 拥有 `next()`，每次返回 `{ value, done }`。 一个对象可以同时扮演两者；大多数迭代器的 `[Symbol.iterator]()` 返回自身。 数组通常可重复取得新 iterator；生成器对象通常只能向前消费一次。

```js
const iterator = [10, 20][Symbol.iterator]();
iterator.next(); // { value: 10, done: false }
iterator.next(); // { value: 20, done: false }
iterator.next(); // { value: undefined, done: true }
```

协议关注行为，不要求继承某个具体 class。

## 2. 哪些语法消费 iterable

`for...of`、展开语法、数组解构、Set/Map 构造器都消费同步 iterable。

展开与 `Array.from` 会把结果一次性物化，可能把无限序列变成事故。

`for...of` 可以逐个处理并早退，更适合懒序列。

同一个 iterator 被多个消费者交错读取时，它们共享游标。 API 文档必须说明返回的是可重复 iterable 还是一次性 iterator。

## 3. IteratorClose 是资源语义

iterator 可以实现可选的 `return()`。

`for...of` 因 break、return 或 throw 提前结束时，会尝试关闭 iterator。

生成器的 return 会让控制流进入 finally，从而执行清理。

```js
function* rows(cursor) {
  try {
    while (cursor.hasNext()) yield cursor.next();
  } finally {
    cursor.close();
  }
}
```

手动反复调用 next 却不在早退时调用 return，会绕过这项保障。

## 4. 生成器是可暂停的执行上下文

调用 generator function 不会立即执行函数体，而是返回 generator object。 第一次 next 才运行到第一个 yield。

`next(value)` 把 value 送回上一次暂停的 yield 表达式。

第一次 next 的参数没有可接收的暂停点，通常会被忽略。

`throw(error)` 在暂停点抛入异常，生成器内部可捕获。

`return(value)` 请求提前完成，但 finally 仍会执行。

`yield* iterable` 把 next/throw/return 委托给另一迭代对象。

生成器适合表达协议状态，不代表它自动是并行或异步的。

## 5. 懒操作与终止操作

map、filter、take 可在请求下一个值时才工作，因此可以组合无限序列。 toArray、reduce、forEach、some 等会推进消费，属于终止操作或消费者。 懒管道的错误也会延迟到消费位置出现。 调试时应区分“创建管道成功”与“消费数据成功”。 同步 Iterator Helpers 已进入较早版本标准，可提供 map/filter/take/toArray 等能力。 ES2026 进一步加入 `Iterator.concat(...)`，用于顺序连接多个 iterable。 使用新方法前仍应 feature-detect 并检查目标运行时。

## 6. async iterable 协议

async iterable 拥有 `[Symbol.asyncIterator]()`。 async iterator 的 next 返回 Promise，最终得到 `{ value, done }`。

`for await...of` 每轮等待 next，并在循环体结束后才继续请求下一项。

它也能消费同步 iterable，并通过 Async-from-Sync 包装适配。 这种适配还会等待同步 iterator 产出的 Promise 值。 消费端变慢时，pull-based async generator 自然不会继续拉取，形成基础背压。

## 7. async generator

async generator 同时结合 await 与 yield。 函数内部可 await 上游数据，向下游逐项 yield。 调用方通过 for await 逐项消费，不必等待全部结果完成。

```js
async function* pages(load, signal) {
  for (let page = 1; ; page += 1) {
    const result = await load(page, signal);
    yield* result.items;
    if (!result.next) return;
  }
}
```

取消信号仍需显式传入上游；停止消费只保证调用迭代器关闭协议。

## 8. pull、push 与背压

迭代器是 pull：消费者请求下一个值。 DOM 事件通常是 push：生产者按自身节奏推送。 把无限 push 源转成 async iterable 必须决定缓冲大小和溢出策略。 策略可以是阻塞生产者、丢最旧、丢最新、合并或报错。 如果没有策略，所谓“流”可能只是不断增长的内存数组。 Web ReadableStream 有自己的 reader、队列与取消协议，可与 async iteration 配合。 锁定 reader 后要 releaseLock，取消时还要决定是否 cancel 底层 source。

## 9. Array.fromAsync

ES2026 的 `Array.fromAsync(items, mapper?, thisArg?)` 可从异步或同步 iterable 构建数组。 它会异步消费并等待值及 mapper 结果。 它很适合“最终确实需要完整数组”的有限输入。 它不是并发 map，也不是流式 UI；顺序消费和最终物化意味着全部结果进入内存。 不要用它读取无限流或不受控的大响应体。

## 10. ES2026 能力雷达

截至 2026-08-11，TC39 的 finished proposals 与 ES2026 规范包含以下新增能力：

- Map/WeakMap `getOrInsert` 与 `getOrInsertComputed`。
- `JSON.parse` source text access，用于在 reviver 中访问原始词法文本。
- Iterator sequencing，即 `Iterator.concat`。
- Uint8Array 的 Base64/Hex 转换能力。
- `Math.sumPrecise(iterable)`。
- `Error.isError`。
- `Array.fromAsync`。

这些是标准版本状态，不等于所有目标浏览器已经无需 polyfill。 Async Iterator Helpers 在本章截点仍不是 finished proposal，不能把 `.map/.filter` 当通用原生能力。 主线代码优先使用 async generator 组合；实验提案只能放在隔离示例并标明构建条件。 官方核对入口：[ES2026 规范](https://tc39.es/ecma262/2026/) 与 [TC39 Finished Proposals](https://github.com/tc39/proposals/blob/main/finished-proposals.md)。

## 11. 生产失败案例：把流重新变成大数组

接口返回百万行 NDJSON，本可边读边解析边渲染。 代码先执行 `Array.fromAsync(stream)`，直到全部到齐才进入下一步。 首条数据延迟、峰值内存和失败重试成本全部上升。 根因链：只看到 API 方便 → 忽略终止操作 → 背压边界消失 → 全量物化。 正确方案是 async generator 逐条转换，并由消费者决定何时停止。

## 12. 生产失败案例：早退未关闭游标

代码手动 `await iterator.next()` 找到目标后直接 return。 底层 reader 的 return/cancel 没有执行，连接与锁继续占用。 使用 for await + finally，或手动 try/finally 调用 return，才能表达所有权。 垃圾回收不负责及时关闭网络、文件、锁等外部资源。

## 13. 常见反例

```js
const all = [...infiniteSequence()]; // 永不结束或耗尽内存
```

```js
for await (const event of unboundedPushAdapter()) {
  await slowWrite(event);
}
// 若适配器无缓冲策略，生产速度仍可能压垮内存
```

另一个反例是把 iterator 缓存在全局并让多个组件同时消费，导致数据被“抢走”。

## 14. DevTools 与验证

在 generator 的 try/finally 中打断点，确认 break 时进入清理。 为每次 next/return/throw 记录序号，观察真实协议调用。 Network 面板开启节流，检查 NDJSON 是否逐条出现而非结束后一次出现。 Memory 面板验证消费速度变慢时缓冲是否保持上限。 对新标准使用 `typeof Array.fromAsync === "function"` 等能力检测。 不要仅按浏览器版本字符串推断；构建目标、WebView 和运行时可能不同。

## 15. React/Vue 迁移

流式数据不应每条都触发昂贵的整树更新，可按帧或小批次提交状态。 React 中消费 async iterable 的 Effect 必须在 cleanup 时取消并阻止迟到提交。 Vue 的 onUnmounted/watch cleanup 同样应关闭 iterator 或 AbortController。 两者都不应把一次性 iterator 本身当可重复计算的派生状态。 服务端流、Suspense 边界与浏览器 ReadableStream 的所有权要分别说明。

## 16. 速记与自检

- iterable 产生 iterator；iterator 产生 iterator result。
- 展开与 fromAsync 会物化；for/of 与 for-await/of 可逐项消费。
- 早退必须触发 return/finally，GC 不是资源释放协议。
- pull 自带消费节奏，push 转 pull 必须设计有界缓冲。
- Stage 4/规范收录与运行时可用性是两个问题。
