# 第 15 章：JS 引擎、内存、性能与度量

## 本章目标

学完后，你应能区分规范语义和引擎实现，理解 JIT/内联缓存/GC 只能作为排错模型而非可依赖契约；能用真实用户指标、Performance 与 Heap Snapshot 找到瓶颈；能证明优化有效且没有把问题转移到别处。

## 1. 先分清三层

分析性能时常混淆：

1. ECMAScript 规定可观察语义；
2. 浏览器/Node 的 JS 引擎选择解析、解释、编译和回收策略；
3. 宿主环境负责 DOM、事件循环、网络、渲染和 Web API。

“V8 会这样优化”不是标准保证。浏览器版本、代码形态和反馈信息变化都可能让优化失效。正确优先级是：算法与工作量 → 数据/DOM 边界 → profile 证据 → 最后才考虑引擎形态。

## 2. 从源代码到执行

现代引擎通常包含解析、字节码/基线执行、运行时反馈、优化编译和必要时反优化。你不必背某版 V8 管线名称，但要理解：

- 热代码才可能值得优化；
- 调用点持续看到相似形状/类型，更容易形成稳定快速路径；
- 动态行为、罕见分支和假设失效可能触发慢路径或反优化；
- 第一次执行、预热后执行和不同设备的结果不可混为一谈。

不要为了“保持 monomorphic”写难维护代码，除非生产 profile 指向它。大多数 Web 卡顿来自做了太多 JS、布局或渲染，而不是少一个引擎小技巧。

## 3. 对象形状与内联缓存是解释工具

相同构造路径创建的对象通常更容易共享内部形状：

```js
function Point(x, y) {
  this.x = x
  this.y = y
}
```

有时先后随意添加/删除属性、同一字段在数字和对象间来回切换，会降低优化机会。但“把所有对象冻结”“永不 delete”“所有字段预填 null”也不是普适性能规则。

先用 profiler 找到确实热的函数，再用真实数据 A/B 验证。维护成本和语义清晰度通常比微小引擎收益更有价值。

## 4. GC 回收的是不可达对象

垃圾回收的核心模型是可达性：从全局、当前调用栈、原生句柄等根出发仍能访问到的对象不会被回收。泄漏往往不是 GC 坏了，而是业务忘记切断引用。

常见保持链：

- 全局 Map 只增不减；
- 事件监听器持有组件闭包；
- timer/observer/subscription 没清理；
- 已移出 DOM 的节点仍被 JS 引用；
- Promise/队列长期持有巨大上下文；
- 缓存没有容量、TTL 或所有权。

内存短暂上涨不一定泄漏。泄漏证据是重复同一操作并强制回到稳态后，保留对象/堆基线持续增长。

## 5. WeakMap 不是自动修复

WeakMap 的 key 不阻止该 key 被回收，适合给对象附加元数据；但 value 可以引用其他大对象，key 也可能被别处强引用。WeakRef/FinalizationRegistry 的回收时机不可预测，不能用于业务正确性、资源及时释放或缓存命中承诺。

监听器、socket、Worker、文件句柄等外部资源仍要显式 cleanup。GC 只能回收内存，不能替你完成协议上的取消。

## 6. 性能指标先对应用户问题

截至本课编写日，稳定 Core Web Vitals 为：

- LCP：主要内容加载体验，良好阈值 `<= 2.5s`；
- INP：交互响应性，良好阈值 `<= 200ms`；
- CLS：视觉稳定性，良好阈值 `<= 0.1`。

评价站点应看真实访问的第 75 百分位，并分别关注移动/桌面，而不是开发者高配电脑的一次 Lighthouse 满分。阈值来源：[Core Web Vitals 定义](https://web.dev/articles/defining-core-web-vitals-thresholds)。

实验室数据能稳定复现和定位，真实用户数据能告诉你影响面。两者缺一不可。

## 7. 一次交互的延迟预算

INP 相关交互可粗分：输入延迟 → 事件处理 → 下一帧呈现延迟。优化必须定位哪一段：

- 输入前主线程正被别的 long task 占用；
- 处理器同步计算过重；
- 更新触发大量 style/layout/paint；
- 微任务链不断追加，让浏览器迟迟得不到渲染机会；
- 第三方脚本抢占主线程。

Long Animation Frames API 可提供更接近整帧卡顿的归因，但 2026 年规范仍是 Editor's Draft；使用时先做能力检测，不把实验 API 作为唯一监控。

## 8. Performance 面板的阅读顺序

1. 明确录制动作和设备/网络条件；
2. 从用户可见慢点定位主线程长任务；
3. 展开 Bottom-up/Call tree 找主要函数；
4. 查看 style/layout/paint 与 forced layout；
5. 对照 Network、Screenshots、Web Vitals 和 React tracks；
6. 建立一个最小假设，只改一类成本，再重测。

不要看到红三角就逐个消灭。先按“总贡献 = 次数 × 单次成本 × 影响用户”排序。

## 9. Heap Snapshot 的三快照法

以“打开/关闭详情 20 次后内存上涨”为例：

1. 冷启动、稳定后 GC，拍基线 A；
2. 重复操作，回到初始页面并 GC，拍 B；
3. 再重复并回稳态，拍 C；
4. 比较 B→C 增长对象，查看 retaining path；
5. 修复后用同样步骤验证不再增长。

重点不是谁占内存最大，而是谁本应死亡却被什么路径保留。Detached DOM tree 只是症状，保留它的 listener/Map/closure 才是根因。

## 10. 缓存也有内存预算

任何缓存都要回答：容量、淘汰、TTL、主动失效、按用户隔离、观测和降级。无限 Map 不是缓存，是泄漏。缓存对象体积还包括其引用图，不只是 `JSON.stringify` 的字节数。

React memo、selector cache、图片/Blob URL、Query cache、Service Worker Cache 都消耗不同资源；不要只盯 JS heap。

## 11. 正确做微基准

微基准至少需要：

- 验证两种实现语义等价，防止编译器消除无用结果；
- 预热与多轮采样，报告分布而非最好一次；
- 随机化执行顺序，隔离 GC/温控/后台任务；
- 使用接近生产的数据形状；
- 最后回到端到端用户指标验证。

若两个实现都只占一次交互的 0.2%，即使一个快两倍也不是当前优先级。

## 12. React 性能桥接

React render 次数不是最终指标。一次额外 render 可能没有 DOM 成本，一次少 render 也可能包含巨大同步计算。使用 React Performance Tracks/Profiler 与浏览器 Performance 对齐：哪次交互、哪个组件计算、哪次 commit、随后多少布局与绘制。

React Compiler 处理一类自动 memo 化问题，不会修复大包、网络瀑布、错误 key、泄漏订阅、昂贵 DOM 或十万节点渲染。

## 评审清单

- 用户问题和目标指标是什么？
- 有真实用户数据还是只有本机一次测量？
- 主要成本是 JS、网络、布局、绘制、内存还是第三方？
- 优化前后条件是否一致，是否报告分布？
- 缓存/Worker/memo 是否引入内存与一致性成本？
- 是否有性能预算和自动回归检查？

## 本章速记

- 规范保证语义，引擎优化不是契约。
- GC 回收不可达对象；泄漏是意外保持链。
- 先看用户指标，再沿时间线找到成本。
- 优化必须有基线、假设、对照与回归证据。
- 少做无用工作通常胜过微调代码形状。

## 自检问题

1. 为什么“对象形状更稳定”不能成为全项目的无条件编码规则？
2. detached DOM 为什么不是完整根因？
3. WeakMap 解决了什么，没有解决什么？
4. INP 慢可能发生在哪三个阶段？
5. 为什么 React render 次数不能直接等价为用户性能？
