# 第 13 章：Worker 并行与数据传输

## 本章目标

学完后，你应能判断一项工作该留在主线程、切片执行还是放进 Worker；能设计带请求身份、取消、背压和崩溃恢复的消息协议；能解释 structured clone、transferable 与共享内存的所有权差异。

## 1. 异步不等于并行

`fetch()` 等待网络时不会持续占用主线程，但下面的循环即使用 `async` 包装，仍会阻塞输入与绘制：

```js
async function calculate(rows) {
  return rows.map(expensiveTransform)
}
```

Promise 只安排后续反应，不把同步计算搬到另一条线程。主线程同时承担 JavaScript、事件分发、样式/布局协调和很多渲染工作。超过一个帧预算的 CPU 任务应先考虑：

1. 删除不必要的工作；
2. 用更好算法或数据结构；
3. 分片并在任务间让出主线程；
4. 计算可独立且传输成本合理时，才使用 Worker。

## 2. Worker 的隔离模型

Dedicated Worker 与创建它的页面一对一；Shared Worker 可被同源多个上下文连接；Service Worker 是网络代理和离线生命周期角色，不是通用常驻计算线程。

Worker 有独立全局对象和事件循环，不能直接访问 DOM，也不能共享普通 JavaScript 对象。这个限制迫使你显式设计边界，通常反而改善架构：输入是消息，输出也是消息。

```js
// main.js
const worker = new Worker(new URL('./worker.js', import.meta.url), {type: 'module'})
worker.postMessage({type: 'sum', id: 'r1', values: [1, 2, 3]})

// worker.js
self.onmessage = event => {
  const {type, id, values} = event.data
  if (type === 'sum') postMessage({type: 'result', id, value: values.reduce((a, b) => a + b, 0)})
}
```

## 3. structured clone 不是 JSON

`postMessage` 默认使用结构化克隆。它能处理循环引用、`Map`、`Set`、`Date`、`ArrayBuffer` 等许多值，但函数、DOM 节点和某些宿主对象不可克隆。对象身份不会跨线程保留，原型/私有状态也不应当被当作协议。

消息应使用稳定、可验证的 plain data：

```js
{version: 1, type: 'search', id: '42', payload: {query: 'react'}}
```

不要发送类实例并期待另一侧行为不变；协议边界应像网络 API 一样有版本和校验。

## 4. clone、transfer 与 share

三种数据所有权完全不同：

- clone：两侧得到逻辑副本，简单但大数据复制有成本；
- transfer：把 `ArrayBuffer` 等所有权移动给另一侧，发送方 buffer 会被 detach；
- share：`SharedArrayBuffer` 两侧看到同一内存，必须用 `Atomics` 协调，并要求跨源隔离响应头。

```js
const buffer = new ArrayBuffer(8_000_000)
worker.postMessage({type: 'analyze', buffer}, [buffer])
console.log(buffer.byteLength) // 0，所有权已转移
```

转移后继续读旧 buffer 是所有权 bug。为了“省复制”盲目上共享内存，则会把问题升级成数据竞争、死锁和安全部署约束。

## 5. 一条生产协议至少需要什么

只有 `{type, payload}` 不够。建议协议含：

- `version`：演进与灰度兼容；
- `id`：请求/响应相关联；
- `type`：判别消息；
- `payload`：结构化数据；
- `error`：可序列化的错误码、消息、是否可重试；
- `cancel`：协作式取消指定 id；
- `progress`：大任务进度，可选；
- `generation`：只接受当前页面或当前查询的一代结果。

Worker 内抛出的 `Error` 不应该只靠 `console.error`。把预期业务失败转成协议错误；未捕获异常由主线程 `error`/`messageerror` 监听并计入崩溃策略。

## 6. 取消是协作式的

发送取消消息不能打断正在运行且从不让出的紧密循环。Worker 必须在合理粒度检查取消标记：

```js
for (let i = 0; i < rows.length; i++) {
  if ((i & 1023) === 0 && cancelled.has(id)) throw new DOMException('Aborted', 'AbortError')
  consume(rows[i])
}
```

`worker.terminate()` 是强制终止整个 Worker，适合不可恢复卡死或页面销毁；它会杀死同一 Worker 上其他任务，不能当作每个请求的正常取消。

## 7. 粒度、池与背压

每条消息都有序列化、排队和调度成本。把 1 毫秒工作拆到 Worker 往往更慢；把 5 秒工作一次性塞入也无法及时取消或报告进度。

Worker 池不是越大越好。核心数、移动设备温控、内存和主线程都在竞争资源。常见起点是 `max(1, min(4, hardwareConcurrency - 1))`，但这只是待测假设。

队列必须有限：

- 合并同类任务，例如搜索只保留最新一项；
- 设置最大等待数，明确丢弃/拒绝策略；
- 区分交互优先级和后台优先级；
- 记录排队时间、执行时间和传输时间。

没有背压的 Worker 只是把主线程卡顿变成内存上涨和过期结果堆积。

## 8. SharedArrayBuffer 的部署边界

共享内存需要页面处于 cross-origin isolated 状态，通常要正确设置 COOP/COEP，并确保所有子资源兼容。`Atomics.wait` 不能在主线程使用；共享状态必须定义清晰布局和同步协议。

除非 profile 证明复制/传输是瓶颈，并且算法确实需要低延迟共享，否则优先使用消息与 transfer。易审计的所有权通常比理论峰值更重要。

## 9. DevTools 验证

1. Performance 面板同时观察 Main 与 Worker 轨道；
2. 在优化前记录输入延迟、主线程 long task 和 Worker 排队；
3. 用 `performance.mark/measure` 分开传输、等待、计算；
4. Memory 面板确认任务完成后大 buffer 能释放；
5. 模拟连续输入和页面销毁，确认旧结果不提交、Worker 被终止。

只比较“总计算耗时”会漏掉核心目标：主线程是否更可响应。

## 10. React 集成原则

Worker 是外部系统。创建、订阅和终止应放在清晰生命周期边界；渲染阶段只读取快照，不能 `postMessage`。响应到达时先检查组件会话/请求代次，再更新 state。

`startTransition` 可以降低 React 更新优先级，但不能把 CPU 计算变成并行；Worker 能移走计算，却不能替代虚拟列表、合理状态边界和减少提交成本。

## 评审清单

- 这真是 CPU 瓶颈，还是算法/DOM/网络问题？
- 输入输出是否可结构化克隆，传输成本是否测过？
- 是否有 id、版本、错误、取消和过期结果规则？
- 队列是否有界，页面退出是否释放 Worker？
- transfer 后是否有人继续使用已 detach 的 buffer？
- Worker 崩溃后是重试、降级还是明确失败？

## 本章速记

- Promise 是异步组合，不是 CPU 并行。
- Worker 隔离对象，通过协议通信。
- clone 复制，transfer 移交，share 共同拥有且需同步。
- 取消、背压、崩溃恢复是协议的一部分。
- 优化目标是用户响应性，不只是 Worker 内核跑得快。
