# 第 16 章：调试、测试、可观测与可靠交付

## 本章目标

学完后，你应能把偶发线上故障变成可复现状态机，用正确层级的测试守住风险；能设计低噪声、可关联且不泄密的前端遥测；能让构建、发布、灰度与回滚组成可靠交付闭环。

## 1. 高级调试不是更会猜

高效调试是一条缩小搜索空间的证据链：

1. 定义现象、影响用户和首次出现时间；
2. 固定版本、账号、浏览器、网络和数据条件；
3. 把系统写成事件时间线/状态机；
4. 找到第一个偏离预期的不变量；
5. 用最小改动验证一个假设；
6. 修根因，并增加能防复发的测试/监控。

“加日志后好了”经常说明时间或竞态被扰动，不代表根因消失。

## 2. 从可复现矩阵开始

记录版本维度：前端 commit、后端 API、feature flag、浏览器、扩展、缓存/Service Worker、地区/CDN、账号权限。偶发问题常来自组合而非单个版本。

用二分缩小：禁用一半 flag、回滚一段时间、减少一半事件、替换一半输入。不要同时修改三个可疑点再宣布修复。

## 3. 时间线比散落日志更可靠

异步故障至少记录：操作 id、会话 id、开始/结束、generation、abort 原因、状态转换和错误 cause。所有时间使用单调时钟测时长，服务端时间用于跨系统关联。

```js
performance.mark(`save:${id}:start`)
try {
  await saveDraft(data, {signal})
  performance.measure('draft.save', `save:${id}:start`)
} catch (error) {
  throw new Error(`save draft ${id} failed`, {cause: error})
}
```

不要只打印“request failed”。HTTP 状态、业务错误码、是否取消、重试次数和当前状态决定处理方式。

## 4. 调试器与 Source Map

优先使用断点、条件断点、XHR/fetch breakpoint、DOM breakpoint、event listener breakpoint 和 async stack；`console.log` 适合快速观察，不应成为唯一方法。

生产 Source Map 要能把 minified stack 还原到确切版本。常见策略是构建时上传到受控错误平台，不公开部署 `.map`；artifact 必须与 release id 对应。缺少版本映射的堆栈只是相似代码位置，不是证据。

## 5. 测试层级按风险选择

- 单元：纯函数、解析器、状态机、算法；快且定位清楚。
- 集成：DOM、网络 mock、存储、组件协作；守用户可见行为与边界。
- 契约：前后端 schema、消息协议、事件兼容；阻止独立发布漂移。
- E2E：少量关键旅程与真实浏览器能力；贵但覆盖集成事实。
- 性能/安全/可访问性：不是普通断言的附录，有独立工具和预算。

测试越接近生产越真实，也越慢、越难定位。高级策略不是“全写 E2E”，而是在最便宜且足够真实的层级守住每个风险。

## 6. 异步测试的确定性

把时间、随机、网络、存储和 Worker 作为依赖注入。fake timer 只控制被测试框架接管的时钟，不会自动冲刷所有 Promise、浏览器任务源或网络。

不要写：

```js
await new Promise(r => setTimeout(r, 100))
expect(ui).toBeReady()
```

应等待可观察条件或协议事件，并有明确超时。竞态测试要控制完成顺序：让第二请求先完成、第一请求后完成，才能证明旧结果不会提交。

## 7. 属性与不变量测试

复杂调度器很难穷举例子，但可以反复生成事件序列，验证：

- 并发数永不超限；
- 每个任务最多 settle 一次；
- 取消后不会发布结果；
- reducer 不产生非法状态；
- encode/decode round trip 保持语义。

属性测试失败时必须保存 seed，才能复现。

## 8. 可观测性三件套

- 日志：离散事件和上下文，适合解释“发生了什么”；
- 指标：聚合趋势、SLO 和告警，适合发现“影响多大”；
- trace：跨前端、BFF、服务追踪一次请求链，适合定位“时间花在哪里”。

前端还要采集 Web Vitals、资源/导航时序、JS 错误、unhandled rejection、关键业务状态与发布版本。采集不是越多越好；高基数字段、完整 URL、用户输入会带来成本和隐私风险。

## 9. 错误分类与归属

至少区分：

- 用户取消/页面离开：通常不告警；
- 可预期业务拒绝：展示明确状态，按业务码统计；
- 瞬时网络/服务错误：按幂等性与预算重试；
- 前端不变量破坏：高优先错误，带版本与状态快照；
- 安全/权限拒绝：不向客户端泄漏内部细节，服务端保留审计。

所有错误上报前做脱敏和采样；永远不要上传 token、密码、完整表单、支付信息或未经批准的用户内容。

## 10. SLO、告警与错误预算

“零错误”既不真实也不可操作。给关键旅程定义 SLI：成功率、p75/p95 延迟、崩溃率、数据丢失率。SLO 说明可接受目标，错误预算帮助团队平衡发布速度与可靠性工作。

告警必须可行动：包含影响、版本、首次时间、最近变更和入口 dashboard。只按错误条数告警容易被流量和重试放大。

## 11. 发布闭环

建议门禁：typecheck/lint → unit/integration → build/依赖扫描 → 关键 E2E → 性能/包预算 → preview 验证 → 小流量灰度 → 指标观察 → 扩量或回滚。

Feature flag 必须有所有者、默认值、过期日期和服务端安全边界。回滚要同时考虑静态资源缓存、Service Worker、API 兼容和数据库/消息 schema，不能假设“重新部署上一版”必然安全。

## 12. AI 辅助开发的质量闭环

2026 岗位越来越重视 AI coding，但验收责任仍属于工程师：

1. 给 AI 最小必要上下文和明确约束；
2. 要求它先提出不变量、风险和测试；
3. 独立审查依赖、权限、错误与性能边界；
4. 用现有门禁验证，不把生成结果直接当事实；
5. 记录关键设计决策，避免团队只剩不可解释代码。

会用工具不等于高级；能让工具产出经过可重复验证才是。

## 评审清单

- 故障能否绑定确切 release、flag 和请求链？
- 测试是否控制了竞态顺序而非等待固定毫秒？
- 每个风险是否放在成本最低的合适测试层？
- 日志是否结构化、可关联、已脱敏？
- 告警是否有 SLO、影响面和操作手册？
- 灰度失败时是否能真正回滚，包括缓存与协议？

## 本章速记

- 调试是缩小空间并验证假设，不是堆日志。
- 测试守不变量，层级由风险和成本决定。
- 遥测必须可关联、低噪声、隐私安全。
- 发布、观测、回滚是一条链。
- AI 生成代码仍需人类定义边界和自动化验收。

## 自检问题

1. 为什么固定 `sleep(100)` 的异步测试不可靠？
2. 一次请求为何同时需要 release id、request id 和状态代次？
3. Source Map 与部署 artifact 对不上会发生什么？
4. 什么错误通常不应作为线上异常告警？
5. Feature flag 为什么也会成为长期可靠性风险？
