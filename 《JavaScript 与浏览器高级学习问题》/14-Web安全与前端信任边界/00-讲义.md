# 第 14 章：Web 安全与前端信任边界

## 本章目标

学完后，你应能画出浏览器应用的信任边界，区分 XSS、CSRF、CORS、点击劫持与权限问题；能安全处理 HTML、Cookie、URL 和跨窗口消息；能解释 CSP 与 Trusted Types 为什么是纵深防御而不是输入校验替代品。

## 1. 安全从资产、攻击者和边界开始

不要从“背攻击名词”开始。先问：

- 资产：会话、个人数据、支付操作、源代码、内部接口是什么？
- 攻击者控制什么：URL、表单、富文本、第三方脚本、iframe、依赖包？
- 权限在哪里判定：浏览器 UI、BFF、后端还是数据库？
- 数据从不可信变为可信的唯一位置在哪里？

前端隐藏按钮不是授权。所有敏感动作必须由服务端按当前身份重新鉴权；前端安全主要降低注入、会话滥用、数据泄漏和用户误操作风险。

## 2. origin 与 site 不是一回事

Origin 由 scheme、host、port 组成。`https://a.example.com` 与 `https://b.example.com` 不同源，但通常属于同一 site。Same-Origin Policy 约束脚本读取跨源资源；Cookie 的 Domain/SameSite 又按不同规则工作。

CORS 是服务端通过响应头允许浏览器把跨源响应暴露给调用脚本的协议。它不是认证，也不能阻止攻击者从自己的服务器直接请求你的 API。`mode: 'no-cors'` 得到 opaque response，不是“绕过跨域并读到数据”。

## 3. XSS：不可信数据进入可执行上下文

危险不在字符串本身，而在它进入什么 sink：

```js
preview.innerHTML = location.hash.slice(1) // DOM XSS
```

优先改用安全 DOM API：

```js
preview.textContent = userText
link.href = allowHttpUrl(userUrl)
```

不同上下文需要不同编码：HTML 文本、属性、URL、CSS、JavaScript 字符串不能共用一个 `escape()`。如果业务必须接受富文本，使用成熟、持续维护的 sanitizer 和严格白名单；不要用正则“删除 script 标签”。

React 默认转义 JSX 文本，但 `dangerouslySetInnerHTML` 不会净化内容。第三方组件、Markdown 插件、DOM API、URL scheme 和服务端渲染仍可能把不可信数据带到 sink。

## 4. CSP 与 Trusted Types

CSP 限制页面可加载/执行的资源。基于 nonce/hash 的 strict CSP 比宽泛域名白名单更可靠；先用 Report-Only 收集违规，再逐步强制。CSP 是注入后的损害限制层，不应替代安全 sink。

Trusted Types 让高危 DOM XSS sink 只接受由受控 policy 创建的类型。2026 年 W3C 文档仍将其标为 Working Draft，采用前需检查目标浏览器，但它非常适合大型代码库缩小审计面：

```http
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types app-html
```

policy 如果只是 `input => input`，只是给漏洞盖章。policy 实现、sanitizer 配置和允许创建 policy 的位置都应被额外审查。

参考：[Trusted Types 规范](https://www.w3.org/TR/trusted-types/) · [CSP Level 3](https://www.w3.org/TR/CSP3/)

## 5. CSRF：浏览器自动携带凭证

CSRF 利用的是浏览器对目标站点自动附带 Cookie 等凭证。攻击者不必读取响应，也可能诱导用户发出有副作用请求。

分层措施：

- 有副作用接口不用 GET；
- Cookie 使用合适的 `SameSite`、`Secure`、`HttpOnly`；
- 高风险请求校验不可由第三方站点猜到的 CSRF token；
- 校验 Origin/Referer 作为额外层；
- 关键动作重认证或二次确认。

CORS 不是 CSRF token。简单表单请求可能根本不触发预检；允许凭证的 CORS 配错还会扩大风险。

## 6. Token 放在哪里

没有“localStorage 永远错、Cookie 永远对”的一句话答案，但边界不同：

- `localStorage` 可被同源 JavaScript 读取，XSS 一旦发生容易窃取长期 token；
- HttpOnly Cookie 不可被 JS 读取，但会自动发送，需要 CSRF 防护；
- 内存 token 缩短持久暴露面，但刷新和多标签页流程更复杂；
- 刷新 token 的生命周期、轮换、撤销与日志脱敏比存储 API 名字更重要。

敏感数据不应为了方便写入可长期读取的客户端存储。退出登录必须同时处理服务端会话、缓存、离线数据与其他标签页。

## 7. `postMessage` 的四道门

发送时不要使用 `'*'`（除非数据完全公开且确有需要），接收时同时检查：

1. `event.origin` 精确匹配允许源；
2. `event.source` 是预期窗口；
3. `event.data` 通过运行时 schema；
4. 消息含 nonce/id/时效，敏感动作防重放。

```js
if (event.origin !== PAYMENT_ORIGIN) return
if (event.source !== paymentFrame.contentWindow) return
const message = parsePaymentMessage(event.data)
```

用 `endsWith('example.com')` 会接受 `evil-example.com`。收到“支付成功”也不能直接记账，应由后端查询交易状态。

## 8. 原型污染与对象合并

不可信 key 写入普通对象可能触碰 `__proto__`、`constructor`、`prototype`：

```js
target[userKey] = value
```

解析配置时使用明确 schema 和允许字段；字典可用 `Object.create(null)` 或 `Map`，但仍需限制 key。递归 merge 是高风险边界，不应从网上复制一个“万能实现”。

## 9. 第三方与供应链

页面上执行的第三方脚本通常拥有与你相同的源权限。减少脚本数量、固定 lockfile、审查安装脚本、使用 SRI（适用 CDN 静态资源）、维护依赖更新和响应安全公告，都是前端职责。

AI 生成代码也属于不可信输入：审查它使用的 sink、鉴权假设、依赖和错误处理，并让测试/静态检查/安全门禁验证，而不是因“能运行”就合并。

## 10. React 与服务端组件边界

Server Component 不等于“代码天然在安全区”。只向客户端传最小数据；Server Function 每次调用重新鉴权；不要把服务端秘密经 props、错误栈或序列化缓存送到浏览器。

React 官方在 2025 年公布过 RSC 严重安全问题并发布修复版本。生产框架与 React 补丁必须跟随安全公告，而不是只锁一个旧版本不动。

## 安全评审清单

- 所有外部输入是否在使用点按上下文处理？
- 是否存在 `innerHTML`、`eval`、动态脚本 URL 等高危 sink？
- 服务端是否重新鉴权，前端是否误把 UI 权限当授权？
- Cookie/CORS/CSRF 策略是否作为整体测试？
- `postMessage` 是否同时检查 origin、source、schema、重放？
- 日志、URL、存储、错误上报是否泄漏敏感信息？
- CSP/Trusted Types 是否有 report、灰度和回滚策略？

## 本章速记

- 输入无所谓“已过滤”，只有“对当前 sink 安全”。
- CORS 控制浏览器读响应，不是认证或 CSRF 防护。
- CSP/Trusted Types 是纵深防御，不能修复错误授权。
- `postMessage` 是跨边界协议，应像 API 一样验证。
- 前端权限提升必须由服务端阻断。
