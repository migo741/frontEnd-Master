# 第 08 章：数据结构、算法与前端调度

## 本章目标

不以背题为目标，而是能从数据规模、更新频率和交互预算选择 Array、Map、Set、堆、索引与前缀结构；能把复杂度、内存和主线程响应性一起解释，并用真实数据证明优化。

## 1. 先问约束，再选算法

“哪个算法最快”缺少输入。先写：

- 数据量 n、查询次数 q、更新次数 u；
- 是否要求稳定顺序、去重、增量更新；
- 内存上限与设备等级；
- 一次操作能否阻塞主线程；
- 输入是否可信、结果是否必须完全精确。

一次 O(n) 不一定慢；在每次按键、每一行 render、每个实时事件中重复 O(n)，才可能成为系统瓶颈。

## 2. 大 O 不替代测量

复杂度描述增长趋势，不包含常数、分配、缓存局部性、JIT 和 GC。把 O(n²) 改成 O(n) 通常值得；两个 O(n) 方案仍需基准。

微基准要预热、运行多次、固定输入并消费结果，避免测到死代码或日志。最终还要回到 Performance 录制，确认用户交互真的减少长任务。

## 3. Array、Map、Set 各有数据形状

Array 适合有序遍历、紧凑存储和按整数索引访问。Map 适合任意键、频繁增删和按身份查找。Set 适合成员关系与去重。

```js
// 每个订单都扫描用户：O(orders * users)
orders.map(order => ({
  ...order,
  owner: users.find(user => user.id === order.userId),
}))

// 先建索引：O(users + orders)
const usersById = new Map(users.map(user => [user.id, user]))
const rows = orders.map(order => ({...order, owner: usersById.get(order.userId)}))
```

建索引有时间和内存成本。只查一次的小数组不必机械改 Map；大量重复查询或增量更新才更有收益。

## 4. Object 不是免费的 Map

普通对象继承原型，键被转为 string/symbol，还涉及 `__proto__` 等危险输入。若确实使用字典，至少用 `Object.create(null)` 与 `Object.hasOwn`；业务实体索引通常优先 Map。

Map 以 SameValueZero 比较键，`NaN` 能匹配自身，`0` 与 `-0` 视作相同。对象身份键只在同一引用下相等，跨 JSON 或跨 Worker 复制后不能继续当同一个键。

## 5. 排序必须满足比较器契约

比较器应保持纯、反对称和传递。返回布尔值、读取变化中的时间或随机数，会产生不可预测顺序。

```js
const collator = new Intl.Collator('zh-CN', {numeric: true})
const sorted = items.toSorted((a, b) =>
  b.score - a.score || collator.compare(a.name, b.name)
)
```

现代 JS 排序是稳定的，但稳定不等于比较器正确。昂贵的归一化值先 decorate 一次，再排序，避免在 O(n log n) 次比较中反复计算。

## 6. 只要 Top K，不必全量排序

从百万项取最高 20 项，全量排序是 O(n log n)。维护大小为 k 的最小堆可做到 O(n log k)，并将额外内存限制为 O(k)。

当 k 接近 n、数据很小或代码复杂度不值得时，全量排序更清楚。高级工程不是总用高级结构，而是能写出切换阈值和证据。

## 7. 二分查找依赖单调不变量

二分不是“有序数组模板题”，它查找的是单调边界：第一个满足条件的位置、最后一个不超过阈值的位置。

虚拟列表中，行底部的累积高度单调。固定行高可直接除法；动态行高需要前缀和结构。若每次测量后重算全部前缀，更新 O(n)；Fenwick Tree 可让单点高度更新和前缀查询都为 O(log n)。

## 8. 缓存必须定义淘汰

`memoize(fn)` 若用 Map 永久保存任意参数，会把性能优化变成内存泄漏。LRU 用 Map 的插入顺序可实现固定容量，但还需回答：

- key 是否稳定且足够小；
- 值过期依据是容量、时间还是业务版本；
- 错误和 Promise 是否缓存；
- 谁负责清空租户/会话数据。

浏览器 HTTP 缓存和服务端状态缓存另有协议，不能用一个通用 LRU 取代。

## 9. 合并中间状态可减少无效工作

实时价格在 16ms 内对同一 id 更新十次，若 UI 只关心最新值，可以按 id 合并；订单状态迁移若每一步有审计意义，则不能丢。

```js
const pending = new Map()
function enqueue(delta) {
  pending.set(delta.id, delta)
}
```

“可合并”是领域语义，不是纯性能决定。要记录被合并数量和最大延迟，避免降级悄悄破坏正确性。

## 10. 更快的算法仍可能造成长任务

O(n) 扫描 500 万项仍会冻结主线程。处理顺序：

1. 先减少工作量、选择正确结构；
2. 再按可验证的时间片分块，并允许取消旧任务；
3. 纯计算足够重时移到 Worker；
4. 大数据优先在服务端过滤/聚合，避免无意义传输。

分块会增加总开销，却改善输入延迟。不要用几千个微任务“让出”，微任务队列清空前浏览器通常没有渲染机会；应使用能产生新 task/帧的调度边界。

## 11. 正确性边界比跑分快更重要

算法题常忽略生产输入：

- 金额不能用浮点随意相加；
- 字符串包含 Unicode、大小写和 locale；
- 日期排序涉及时区与无效值；
- `NaN` 会让比较器结果异常；
- 重复 id、缺失引用和恶意超长输入必须有策略；
- 原数组是否允许原地排序要写进契约。

先用慢而清楚的 oracle 验证优化版，再做随机、边界和属性测试。

## 12. DevTools 与基准证据

用 `performance.mark/measure` 标出业务阶段；Performance 面板确认时间花在脚本、布局还是 GC；Memory/Allocation 观察索引是否换来不可接受的常驻内存。

基准报告至少包含数据生成方式、设备、浏览器、冷/热状态、样本次数、p50/p95，以及优化前后结果一致性。单次 `console.time` 不足以支撑架构决定。

## 13. React 与 Vue 迁移提示

React render 或 Vue computed 中反复 `filter().sort().map()`，根因常是数据形状和失效边界，而不是缺一个 memo。先建立按 id 规范化索引，把昂贵派生限制在真实依赖变化时。

优化后还要保持引用语义：每次重建所有行对象会让 React 子组件或 Vue 依赖产生无效更新。增量更新只替换变化实体，选择状态保存 id 而非整行副本。

## 14. 评审清单

- 数据规模、查询/更新频率和交互预算是否量化？
- 是否在循环内做重复查找、解析、分配或排序？
- 索引的创建、失效、内存和重复 id 策略是什么？
- 比较器是否纯且有完整 tie-breaker？
- 缓存是否有容量、版本、owner 和清理？
- 长任务是否支持分块、取消或 Worker？
- 优化结果是否与 oracle 一致，并在真实页面有证据？

## 本章速记

- 先写 n、q、u 和响应预算，再选结构。
- 重复扫描常可用 Map/Set 预索引消除。
- Top K 用堆，单调边界用二分，动态前缀可用 Fenwick Tree。
- 复杂度优化与主线程让出是两个问题。
- 缓存没有淘汰与所有权，就是延迟发生的泄漏。
- 慢实现可作为 oracle，优化实现必须证明等价。
