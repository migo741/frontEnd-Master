# 第 05 章：LLM 与 Agent 基础

## 本章目标

建立不神化模型的工程心智：理解 token、概率输出、context、能力边界，以及什么任务值得用 Agent。

## 1. Agent 是什么

工程上可把 Agent 看成：模型 + instructions + tools + state/memory + control loop + guardrails + eval/observability。模型提出下一步，应用决定允许什么、执行什么、何时停止。

Agent 不是“能聊天的 API”，也不等于完全自治。自治程度应由风险和可逆性决定。

## 2. workflow、single-agent、multi-agent

- 普通代码：规则稳定、输入输出确定，优先使用。
- workflow：步骤已知，模型只完成局部判断/生成。
- single-agent：步骤依输入动态变化，需要选工具/循环。
- multi-agent：角色/上下文/权限确实需隔离，并行或团队边界带来价值。

先选最低不确定性的方案。能写 if/SQL/状态机解决的问题，不交给模型“推理”。

## 3. token 与 context

模型处理 token 而非字符；输入 instructions、历史、工具 Schema、检索文档、工具结果和输出都占预算。更长 context 不保证更好：噪音、冲突、位置效应、延迟和成本都会增加。

Context engineering 是为当前一步选择正确、可信、最少的信息，而不是无限塞历史。

## 4. 概率输出与 sampling

即使温度较低也不等于完全确定；服务端实现、模型版本、并行工具和输入细节可变化。不要以固定字符串 snapshot 测自然语言。对机器消费结果用 structured output；对行为用 invariants/evals。

## 5. 指令层与数据层

developer instructions 描述政策和任务；用户输入/网页/文档/工具输出是数据。模型可能混淆二者，因此应用需要结构化提取、信任标签、权限和审批。Prompt 里的“绝不泄漏”不是技术隔离。

## 6. Tool calling

模型产生结构化 tool request；应用验证参数、授权、执行并返回结果。模型不直接拥有数据库/文件系统。工具结果仍可能错误或含注入内容，应带来源、状态、截断和可信度元数据。

## 7. 常见失败模式

- hallucination：没有证据却生成事实。
- instruction conflict/注入：不可信文本影响行为。
- loop：重复搜索/修复，消耗预算不收敛。
- tool misuse：选错工具、参数、顺序或权限。
- stale state：旧结果覆盖新状态、恢复后重复副作用。
- context rot：历史膨胀、摘要丢关键信息。
- silent partial success：部分工具失败却声称全完成。

## 8. 能力与产品指标

不要只看最终文案。任务可拆：是否正确规划、选工具、参数正确、证据充分、动作安全、在预算内完成、失败能否接管。产品指标还包括任务成功、节省时间、人工修改率和业务结果。

## 9. 模型选择

按能力、延迟、成本、context、structured/tool/multimodal 支持、数据政策和地域可用性选择。可用小模型做路由/抽取，大模型做困难规划，确定性代码做验证。升级必须跑 eval。

## 10. 停止条件与预算

每次 run 明确 max turns/tool calls/time/tokens/cost，检测重复 action 和无进展。到预算应返回部分结果、待处理事项和恢复点，不能伪装完成。

## 11. 官方生产视角

OpenAI 当前 AI 应用路线把 core logic 与 evals 并列为生产基础，并强调 structured outputs/tool calls；这是跨供应商都成立的工程思想。[官方路线](https://developers.openai.com/tracks/ai-application-development#phase-1-foundations)

## 本章速记

Agent 是受控循环，不是会思考的黑箱服务。先判断是否需要 Agent，再为上下文、工具、终止、评测和安全写出显式系统设计。
