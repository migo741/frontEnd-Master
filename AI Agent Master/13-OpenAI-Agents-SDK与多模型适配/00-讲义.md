# 第 13 章：OpenAI Agents SDK 与多模型适配

## 本章目标

掌握当前官方 Agents SDK 的 tools、handoffs、guardrails、sessions 与 tracing，同时用 adapter/eval 避免业务与单一模型供应商深度耦合。

## 1. SDK 定位

OpenAI 官方建议：直接 API 适合普通请求，Agents SDK 适合 code-first orchestration、tools、handoffs、guardrails、tracing 或 sandbox execution；官方同时维护 Python/TypeScript 版本。[官方 SDK 页面](https://developers.openai.com/api/docs/libraries#use-the-agents-sdk)

SDK 不是所有项目的默认答案。简单结构化调用用 Responses/API adapter 更清楚；需要 agent loop 与 trace 时再使用。

## 2. Agent、Runner 与 RunContext

Agent 定义 instructions/model/tools/output；Runner 执行 loop；context 注入已验证依赖。用户身份、数据库 session、权限服务通过 context 进入工具，不要插入模型可编辑参数。

## 3. Function tools

从 Python 函数/Schema 注册工具很方便，但仍要使用第 09 章的 ToolExecutor 做权限、幂等和风险门禁。自动生成 Schema 要 contract test；docstring 不应泄漏内部细节。

## 4. Handoffs 与 agents-as-tools

handoff 把控制权/上下文交给专门 Agent；agent-as-tool 让 orchestrator 把子任务作为工具调用。选择看谁拥有最终循环、上下文隔离和用户体验。不要为“多 Agent”而 handoff。

## 5. Guardrails

input/output guardrail 可早停或验证，但不是授权/沙箱。异步 guardrail 是否与模型并行会影响“早停前已花 token/已执行工具”的语义；高风险门禁必须在工具执行器同步强制。

## 6. Structured output

Agent output type 用 Pydantic；最终结果再做领域验证。工具结果和最终 output 采用不同 Schema。拒绝/中断/预算耗尽不能硬塞成正常业务结果。

## 7. Sessions/状态

SDK session 便利地保留对话，但业务 run/checkpoint、审批、长期记忆仍需自己的数据模型。不要把 session history 当唯一事实源或审计账本。

## 8. Tracing

trace 展示模型、工具、handoff、guardrail；生产要脱敏、采样、访问控制和保留策略。业务 trace id 与 SDK trace 关联。trace 是诊断证据，不是 eval 本身。

## 9. Responses API 与 SDK 的边界

如果要完全掌握循环、跨供应商、独立 durable workflow，使用自有 runtime/图 + direct model adapter；如果 SDK 能显著减少 loop/trace 样板且语义满足，采用 SDK。两者可在不同 workflow 并存。

## 10. 多模型适配

定义能力矩阵而非最小公分母：structured output、parallel tools、MCP、image/audio、reasoning controls、context、stream。业务请求声明 required capabilities，router 选择；不支持就 fail/明确降级。

## 11. 升级策略

固定 SDK 版本；升级读 changelog，跑 contract + eval + cost/latency + safety。模型 id 配置化。历史 trace/replay 要保留原模型信息，不悄悄用新模型改写基线。

## 本章速记

Agents SDK 提供高质量 loop 与观测积木，但授权、业务状态和持久执行仍属于你的系统。用能力矩阵和 eval 控制供应商/模型升级。
