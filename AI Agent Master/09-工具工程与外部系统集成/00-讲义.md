# 第 09 章：工具工程与外部系统集成

## 本章目标

把工具设计成窄、可靠、可授权、可观测的业务能力，而不是把数据库、Shell 或任意 HTTP 直接交给模型。

## 1. 工具边界

好工具对应业务意图，如 `get_order_summary`、`propose_refund`；坏工具如 `execute_sql`、`call_any_url`、`run_shell`。模型应选择业务能力，不应拼底层命令绕过政策。

## 2. Schema 与描述

name 唯一稳定；description 说明前置条件、何时不用、结果；字段写单位/格式/边界。enum 优于自由字符串。不要塞 40 个可选字段，拆成更清楚的工具或两阶段 flow。

## 3. 认证与授权

用户身份从已验证 request/session 注入。每次执行在服务端检查 tenant、resource ownership、scope、业务 policy；模型只能选择业务参数。OAuth token/DB credential 永不进入模型 context。

## 4. 读写风险分级

- L0：本地纯计算。
- L1：低敏只读。
- L2：敏感读取/外发信息。
- L3：可逆写入。
- L4：资金、删除、权限、公开发布等高风险不可逆动作。

风险决定审批、二次认证、速率、日志、预览和补偿。工具名中的“safe”不降低风险。

## 5. 幂等与 exactly-once 幻觉

分布式系统通常至少一次。每个写工具接受应用生成的 operation id；远端支持则传 idempotency key，本地建 unique constraint/outbox。失败后查询已有结果，避免生成新 id 重做。

## 6. 超时、重试、熔断

分别设置 connect/read/operation deadline。错误分类决定 retry；熔断保护下游，但不是把所有失败变成功。Agent 收到 `retryable/next_retry_at` 等有限状态，不拿内部 stack 自己决定无限重试。

## 7. 结果设计

结果小、结构化、带 source/version/freshness/partial。大文档存 artifact，返回 id/摘要/可取片段。工具结果中的文本是不可信数据，尤其网页、邮件、工单和用户生成内容。

## 8. 数据库工具

优先预定义 query/service。若必须 text-to-SQL：只读副本、SQL parser/AST allowlist、行/时间/成本限制、tenant predicate 强制注入、禁止多语句/DDL/DML、结果脱敏、审批和审计。只让模型“不要 DROP”没有意义。

## 9. HTTP/SSRF

禁止任意 URL；域名/IP allowlist、DNS rebinding 防护、禁 metadata/private network、重定向重新校验、响应大小/类型/时间上限。下载文件做 MIME/恶意内容处理。

## 10. Tool contract tests

测试 Schema、权限矩阵、idempotency、timeout/retry、partial、redaction、downstream version、恶意输入。录制外部响应必须脱敏；sandbox/test account 与生产隔离。

## 11. 工具数量

按当前 task 动态提供最小工具集。工具过多增加 token、错误选择和权限面。可先确定性路由到 capability group，再让模型在小集合选择。

## 本章速记

工具是 Agent 的安全内核。模型只提交业务提案，身份、权限、幂等、网络边界、重试和审计全部由工具层强制执行。
