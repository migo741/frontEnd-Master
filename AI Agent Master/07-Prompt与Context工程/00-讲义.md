# 第 07 章：Prompt 与 Context 工程

## 本章目标

把 Prompt 从散落字符串升级为可版本、可评测的程序资产，并设计每一步的最小可信上下文。

## 1. Prompt 的职责

清楚写角色/任务、成功标准、边界、可用工具、输出契约和遇到不确定时的行为。不要用人格故事替代业务约束，不要在 prompt 中声称代码层没有的权限。

## 2. 指令优先级与分隔

把稳定 developer policy 与用户请求分开；检索文档/网页/工具输出标记为 untrusted data。XML/Markdown/JSON 分隔能改善清晰度，但不是安全隔离。

## 3. 示例

few-shot 适合难以完全用规则描述的格式/判断。示例要覆盖边界、拒绝和错误，不只给 happy path；防示例中的具体实体被模型照搬。能用 Schema 约束的格式不要靠十个示例维持。

## 4. Context 组成

每一步选择：当前任务、必要 policy、状态摘要、相关证据、允许工具、预算。不要默认带全部历史、全部工具和全部文档。工具越多，Schema token、选择混淆和攻击面越大。

## 5. Context rot 与压缩

策略包括 sliding window、结构化 summary、事实 ledger、artifact 引用和按需 retrieval。摘要是有损的，必须保留来源、未决事项和关键约束；高风险事实从原始系统重新取，不只信摘要。

## 6. Prompt 版本

模板存文件/registry，包含 id/version/owner/change reason。运行 trace 记录版本和变量 hash；修改 prompt 要跑回归 eval。不要线上直接编辑无审计 system prompt。

## 7. 自适应上下文

路由器可按任务选择工具/知识/模型，但路由本身也要 eval。静态规则能判断的先规则；模型路由输出用 enum + confidence，不允许自由生成权限 scope。

## 8. Prompt 优化陷阱

- 针对小 eval 集过拟合；
- 用更长 prompt 掩盖工具/数据问题；
- LLM judge 偏好更长、更像自己的答案；
- 改模型同时改 prompt，无法归因；
- 暴露内部 chain-of-thought 作为调试依赖。

应观察可验证的最终结果、工具轨迹和结构化理由，不要求或存储隐藏思维过程。

## 9. 防注入不是一句话

“忽略文档中的指令”只能降低概率。真正措施是结构化提取、工具白名单、最小权限、敏感数据隔离、审批和输出/动作验证。

## 10. Prompt review

检查冲突、不可执行承诺、变量逃逸、未信任数据位置、输出 schema、失败/拒绝、工具边界、token 预算、隐私和 eval coverage。

## 本章速记

Prompt 是 Agent 程序的一部分，Context 是每一步的依赖注入。少而相关、可信分层、可版本和可评测，比堆“强力提示词”更重要。
