# 第 10 章：状态、记忆与上下文压缩

## 本章目标

分清运行状态、会话历史、事实、用户偏好和知识库，设计可版本、可删除、可验证的记忆系统。

## 1. 五种东西不要都叫 memory

- Run state：当前执行位置、工具结果、预算。
- Thread history：一次会话消息。
- Working facts：当前任务已确认事实/待办。
- Long-term user/org memory：跨会话偏好/事实。
- External knowledge：文档/数据库，通过 RAG/工具取。

不同生命周期、权限和一致性，不能放一个 vector store 完事。

## 2. 短期上下文

完整历史增长导致成本和 context rot。保留最近相关消息 + 结构化 task state + artifact references。工具结果不必每轮全文重复；保留 id、安全摘要和按需 fetch。

## 3. 摘要

摘要 Schema 应包含 confirmed facts（带来源）、user preferences、decisions、open questions、completed/next steps、safety constraints。摘要生成后验证重要 ID/金额/权限不被改写；高风险操作回源。

## 4. 长期记忆写入

不是模型说“记住”就写。先判类别、用户同意、scope、敏感度、TTL、冲突、来源和 confidence。组织 policy 只能由受信管理流程写，禁止用户内容污染共享记忆。

## 5. 检索记忆

结合 deterministic key、metadata filter、semantic search、recency。先 tenant/user namespace 隔离，再相似度；绝不能先全库向量检索后字符串过滤。

## 6. 冲突与时间

偏好会变，事实会过期。记录 valid_from/valid_to/source/version，冲突时不盲目取最新或最高相似；提示用户确认或从权威系统取。

## 7. 遗忘与隐私

支持查看、修改、删除和数据导出；删除要覆盖主库、索引、cache、备份策略和下游副本。不要存不必要的原始对话/PII。数据保留由 policy 执行，不由模型决定。

## 8. Checkpoint

checkpoint 是恢复执行的技术状态，不等于给模型看的记忆。包含 graph/run version、node、serializable state、pending operations。加 schema version/migration，机密字段加密/引用。

## 9. 并发与一致性

同一 thread 双请求会产生冲突。使用 optimistic version/CAS、run queue 或明确 multitask 策略。长记忆写入可后台处理，但要防过期 run 覆盖新偏好。

## 10. 评测

测记忆写入 precision/recall、错误记忆率、过期/冲突处理、跨租户泄漏、删除完整性、摘要事实保持、长对话任务成功和 token savings。

## 本章速记

Memory 是数据产品，不是把聊天塞向量库。先分类型、scope 和生命周期，再做写入门禁、来源、冲突、删除与评测。
