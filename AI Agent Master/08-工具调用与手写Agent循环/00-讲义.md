# 第 08 章：工具调用与手写 Agent 循环

## 本章目标

不依赖 Agent 框架手写完整控制循环，理解模型请求、工具请求、执行、反馈、预算、终止和恢复的真实状态机。

## 1. 最小 loop

```text
准备 context → 调模型 →
  final output：验证并结束
  tool requests：验证/授权/执行/记录 → 将结果加入 state → 下一轮
  refusal/error：分类处理
```

循环属于应用，不属于模型。模型提出动作，应用保留最终控制权。

## 2. Run state

至少包含 run/tenant/user id、messages/artifacts、tool calls/results、budget、attempt、status、checkpoint version、created/deadline。状态迁移通过函数/事件，不允许各处随意改 dict。

## 3. Tool definition

name 稳定明确，description 说明何时用/不用；参数 Schema 小而严格；结果结构化且有状态。模型不可填写 auth、tenant、user、approval；这些从 RunContext 注入。

## 4. 执行前门禁

按顺序：Schema validate → tool allowlist → identity/scope → policy → risk/approval → budget/rate limit → idempotency → execute。任何一步失败都产生明确 tool result，模型可以改参数或终止，但不能绕过。

## 5. 并行工具

只有无依赖、资源允许、风险可控时并行。保持 call id 对应；一个失败的策略是 fail-fast、partial 或继续，要显式。多个写操作通常不应由模型随意并行。

## 6. 工具结果

返回 `ok/data/error/meta`，限制大小，必要时保存 artifact 并给引用。网页/邮件结果标 untrusted，防其冒充 instruction。不要把 stack trace、token、完整 SQL 或敏感行返回模型。

## 7. 终止与 loop detection

final output 仍要 Schema/业务验证。检测相同 tool+args、来回切换、连续无新证据、总预算。超过时返回 partial/needs_help，不让模型再自我承诺一轮。

## 8. 恢复

模型调用前后、工具执行前后记录事件/checkpoint。副作用工具先生成 operation id，执行后持久化结果。崩溃在“远端成功、本地未记录”之间时，用 operation id 查询/去重。

## 9. 模型不可见的控制面

权限、模型路由上限、secret、成本、审计、杀开关、数据保留在控制面；不要把它们全部放进 prompt 期待模型遵守。

## 10. 为什么先手写

框架会封装 loop，但生产故障仍发生在事件顺序、状态、幂等、取消和权限。手写一次后才能判断框架行为是否满足系统语义。

## 本章速记

Agent loop 本质是带概率决策器的可靠状态机。模型不拥有工具、权限或终止权；每个 tool call 都要经过应用门禁并留下可恢复记录。
