# 第 17 章：Evals、测试与质量闭环

## 本章目标

把“看起来好用”变成可重复测量：建立数据集、分层评分、轨迹评测、回归门禁和线上反馈闭环。

## 1. 测试金字塔

- Unit：Schema、tools、policy、state reducer、chunker、ranker。
- Contract/integration：provider、MCP、数据库、模型能力。
- Scenario eval：完整任务结果/轨迹/安全。
- Online：真实流量指标、抽样审查、A/B、canary。

模型 eval 不能取代普通软件测试；确定逻辑不要交给 LLM judge。

## 2. 定义任务与成功

每条 case 包 input/context、允许工具/动作、expected facts/actions、forbidden actions、rubric、metadata。对开放任务可以没有唯一文本答案，但仍能评事实、引用、约束和业务结果。

## 3. 数据集来源

产品需求、生产失败脱敏、专家边界、合成变体、红队。拆 train/dev/test/holdout，避免 Prompt 针对 test 过拟合。按语言、长度、风险、用户群、工具路径分 slice。

## 4. 分层指标

- 模型输出：Schema、字段、事实、拒答。
- Retrieval：Recall@k、citation support。
- Tool：选择、参数、顺序、成功/重复。
- Trajectory：步骤效率、循环、政策遵循。
- End-to-end：任务完成、人工修改、业务 outcome。
- System：成本、延迟、错误、接管。

一个总平均分会掩盖高风险 slice。

## 5. Grader

优先确定性规则/执行结果；人工是高价值标准；LLM judge 适合开放语义，但需 rubric、盲测、位置/长度/自偏差控制，并与人工样本校准。judge 不应看到被评系统的品牌/无关 trace。

## 6. Pairwise 与 pointwise

版本对比常用 pairwise，减少绝对尺度问题；随机交换 A/B 顺序，允许 tie。pointwise 适合固定门槛。两者都要报告置信区间/样本量，不把 30 条 2% 改善当结论。

## 7. Agent trajectory

只看最终答案会放过危险动作。评 tool allowlist、参数、approval、重复、证据、预算、终止。轨迹不必和唯一 gold path 完全相同，只要满足 invariants 和结果。

## 8. 非确定性

关键 case 重复多次，报告 pass@1、worst-case/variance；固定 seed 不保证 API 完全确定。把 provider/model/prompt/tool versions 记录进 run。

## 9. CI 与发布门禁

PR 跑小型 deterministic/smoke；nightly 跑大 eval；发布前跑安全/高风险和成本。门禁按关键 slice：越权/数据泄漏必须 0 容忍或极严，普通措辞允许权衡。

## 10. Online feedback

thumbs up 不是唯一 truth。结合任务完成、撤销、人工修改、投诉、工具失败、handoff；反馈可能有选择偏差。失败 trace 进入 triage，修系统并增加 regression case。

## 11. Eval 泄漏与治理

数据集含敏感/版权内容需访问控制、脱敏和保留；grader prompt/version 也要审查。不要让模型在运行时检索到测试答案。

## 12. 官方视角

当前官方 AI 应用路线明确把 evals 与 core logic 并列，作为验证正确、guardrail 和持续改进的反馈环。[官方文档](https://developers.openai.com/tracks/ai-application-development#phase-1-foundations)

## 本章速记

Eval 是产品契约的可执行版本。分层、分 slice、看轨迹、校准 judge、重复运行，并让每次生产失败成为新的回归样本。
