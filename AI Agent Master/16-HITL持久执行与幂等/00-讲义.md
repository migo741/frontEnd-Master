# 第 16 章：HITL、持久执行与幂等

## 本章目标

构建能暂停数小时、跨部署恢复、等待人类批准且不重复副作用的长任务 Agent。

## 1. 为什么普通请求不够

Agent 可能等待审批、外部回调、限额恢复或人工补数据。HTTP 请求/进程内 task 不可靠；run 必须是持久状态机，由 worker 租约执行。

## 2. 状态与事件

状态：queued/running/waiting_approval/waiting_external/succeeded/partial/failed/cancelled。状态转移使用 expected version/CAS，写 append-only events；materialized state 可重建/校验。

## 3. Checkpoint

在步骤边界保存 serializable state、workflow/version、pending operations、budget 和 artifact refs。schema migration 支持旧 run；不能 pickle 任意代码对象作为长期协议。

## 4. Replay 与非确定性

时间、随机、模型、HTTP 等非确定操作放 activity/task，结果持久化。恢复时复用已完成结果而非重新调用。workflow control code 尽量确定。

## 5. 幂等

每个 side effect 由 `(run_id, step_id, semantic_operation)` 生成稳定 key。数据库 unique constraint/下游 idempotency；执行前后状态机。若下游不支持，设计查询、业务去重或补偿，不声称 exactly-once。

## 6. Human approval

approval request 包 action preview、参数、来源、风险、expiry；approver 身份/权限验证；approve/edit/reject。edit 生成新 proposal/重新校验。批准与具体 hash/version 绑定。

## 7. 租约与 worker

worker 原子 claim run，定期 heartbeat/renew；租约过期可被接管。旧 worker 恢复后用 fencing token/version 防双写。优雅关闭停止 claim 并 checkpoint。

## 8. 取消

cancel 是 intent，worker 在安全点检查并传播；已开始不可撤销动作可能完成。终态说明完成/未完成；需要补偿另建受审计 workflow。

## 9. Durable framework 选择

LangGraph checkpoint 适合 Agent graph；Temporal/DBOS/Prefect/Restate 等可承载更通用持久执行。PydanticAI 当前也提供多种 durable integrations。[官方概览](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/)

选择依据：历史/重放语义、定时/信号、语言、运维、可观测、吞吐、锁定。不要在一个项目同时引入多个 durable runtime 无清晰边界。

## 10. 测试

故障注入点：调用前、远端成功后本地记录前、checkpoint 前后、审批过期、worker 租约丢失、部署升级、取消竞态。每条证明状态和外部副作用一致。

## 本章速记

持久 Agent 的难点不是“存消息”，而是重放、租约、版本、审批与 side effect 幂等。每个 crash 窗口都要有恢复答案。
