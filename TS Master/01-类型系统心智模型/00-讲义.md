# 第 01 章：TypeScript 类型系统心智模型

## 本章目标

建立贯穿全书的底层模型：类型是值的集合和静态证明，编译后被擦除；TypeScript 采用结构类型并有意保留若干不健全边界。你应能区分“编译器知道”“运行时存在”和“开发者强行承诺”。

## 1. TypeScript 不改变 JavaScript 事实

```ts
type User = {id: string; name: string}
const user: User = JSON.parse(input)
```

`User` 编译后不存在；`JSON.parse` 返回 `any`，坏数据会直接穿过。TypeScript 主要检查程序内已知关系，不验证网络、存储、DOM attribute、环境变量和第三方消息。

把每个系统画成两层：

```text
runtime values / side effects / protocols
---------------- 编译边界 ----------------
static types / inference / assignability
```

类型层能证明的前提来自运行时层；边界输入若未经验证，后面的精确类型只是建立在假设上。

## 2. 类型是值集合

- `string`：所有 JS 字符串；
- `'paid'`：只有一个字面量值；
- `'pending' | 'paid'`：两个集合的并集；
- `A & B`：同时满足 A 和 B 的交集；
- `never`：空集合；
- `unknown`：所有可能值，但使用前必须证明；
- `any`：退出类型检查关系的逃生舱，不等同于“所有值的安全顶类型”。

子类型/可赋值性可用集合包含理解：`'paid'` 可赋给 `string`，反向不行。

## 3. 结构类型

TypeScript 看形状，不看声明名字：

```ts
type Point = {x: number; y: number}
class Vector { constructor(public x: number, public y: number) {} }

const p: Point = new Vector(1, 2) // 形状兼容
```

优点是 JavaScript 生态组合自然；代价是 `UserId`/`OrderId` 都是 string 时会互传。需要名义区分时用 Brand/私有成员等局部策略，第 9 章深入。

结构类型会允许“更多属性的对象”赋给较少属性的目标：函数只承诺读取目标所需字段。对象字面量有额外属性检查，这是常见错误捕获启发式，不是类型系统突然变成精确对象：

```ts
function printUser(user: {name: string}) {}
const value = {name: 'Ada', admin: true}
printUser(value) // 合法
printUser({name: 'Ada', admin: true}) // 字面量处可能报多余属性
```

## 4. 推断优先于重复注解

```ts
const price = 100            // number
const status = 'paid'        // 'paid'
let mutableStatus = 'paid'   // string（可能被重新赋值）
```

TypeScript 根据可变性和使用上下文做 widening。公共函数参数/返回、对象边界和领域模型常需要明确类型；局部显然值让推断工作。重复注解可能把更精确字面量拓宽或让实现与声明维护两份真相。

## 5. 注解、断言与验证

- 注解 `const x: T = value`：编译器检查 value 是否可赋给 T。
- 断言 `value as T`：开发者告诉编译器采用 T，通常不生成运行时检查。
- non-null `value!`：断言排除 null/undefined。
- `satisfies T`：检查表达式满足 T，同时尽量保留表达式自身精确类型。
- Schema/type guard：运行时检查并产生可信缩小。

优先级通常是：推断/注解 → `satisfies` → 真实验证 → 局部可证明断言。双重断言 `as unknown as T` 是明确绕过系统，应出现在隔离 adapter 并有测试。

## 6. 健全性与实用性

完全健全意味着“类型正确程序不会出现某类运行时类型错误”。TypeScript 为兼容 JavaScript 和易用性做权衡，例如：

- 数组/对象可变性与型变可产生别名写入问题；
- 索引访问默认历史行为可能把不存在元素当成 T；
- 类型断言/any；
- 方法参数的部分双变行为；
- 声明文件可能与实现不一致；
- 控制流缩小在函数调用后未必重新失效。

严格 flags、readonly、Schema 和 API 设计是在关键处收紧，不要宣称 TS 让运行时错误归零。

## 7. 类型信息流

高级排错应追踪信息在哪里丢失：

```ts
const routes = ['home', 'settings'] // string[]，字面量关系丢失
```

可能来自：过宽注解、`any` 边界、数组 widening、泛型参数设计、回调上下文不足、声明文件错误。修复源头比下游 `as` 更好。

## 8. 编译器不是唯一消费者

TypeScript 类型还驱动编辑器补全、重构、文档 hover、声明发布和 API 发现。一个理论正确但错误信息 200 行、补全卡顿、调用端难写的类型，是差公共 API。

## 9. 排错算法

1. 运行时值实际可能是什么？
2. 类型从哪里产生：推断、注解、声明还是断言？
3. 是否跨越不可信边界？
4. 当前检查是可赋值性、控制流、泛型推断还是模块解析？
5. 是否因可变别名/any 破坏证明？
6. 更简单的运行时/公共 API 能否替代复杂类型？

## 本章速记

TypeScript 是被擦除的结构化静态类型系统。它能在给定前提下证明关系，但前提必须由运行时边界提供；类型越精确不自动等于程序越安全。
