# 第 15 章：框架类型实战与类型测试

## 本章目标

把前 14 章的类型设计落到 React、Vue、Node 与公共组件/SDK；掌握“公共契约做类型测试，业务行为做运行时测试”的方法。

## 1. 框架不会替你消除边界风险

React props、Vue props、路由参数、表单值和服务端 DTO 都只是编译期视角。URL、DOM、localStorage、接口响应仍是 unknown 边界。框架类型应连接已经验证的领域模型，而不是把 `as User` 散落在组件中。

## 2. React 公共组件

优先让 props 表达合法组合：

```ts
type ButtonProps =
  | {kind: 'link'; href: string; onClick?: never}
  | {kind: 'button'; href?: never; onClick(): void}
```

常见要点：

- 事件使用具体 `React.ChangeEvent<HTMLInputElement>` 等，不把 `any` 传入业务层。
- `children` 是否允许应显式；不是所有组件都应 `PropsWithChildren`。
- 包装原生元素可基于 `ComponentPropsWithoutRef<'button'>`，再精确 omit 冲突字段。
- `ref` 的写法随 React 类型版本和组件 API 而变，发布库必须在支持矩阵测试；不要机械复制旧版 `forwardRef` 模板。
- 泛型 JSX 组件的推断要用 consumer tests 验证，尤其 callback 参数、key selector 和 union rows。

## 3. Vue 3 类型

`defineProps`/`defineEmits`/`defineModel` 使用类型参数表达外部契约；runtime 校验仍需要 validator/Schema。composable 的返回值保留 ref/reactive 语义，不要用断言抹平 unwrapping 差异。

依赖注入使用 `InjectionKey<T>`，并处理 inject 可能 undefined。泛型组件、slot props 和 template inference 要用 `vue-tsc` 验证，而不只跑普通 tsc。

## 4. 服务端与 Node

`process.env.X` 本质是 `string | undefined`；应用启动时集中 Schema parse 成 immutable config。HTTP request params/body/query 均是不可信输入。框架的泛型参数常只是声明，不代表 runtime 已验证。

控制器层：unknown → Schema → application command；领域错误 → 明确 HTTP mapping。不要让 ORM entity 或框架 Request 类型穿透所有层。

## 5. DOM 的窄化

`event.target` 是 `EventTarget | null`，不保证具体元素；`currentTarget` 是监听器绑定对象，通常更适合。选择器结果需 null check，dataset/form values 都是字符串。断言只应紧挨 runtime 证明。

## 6. Headless 组件的类型目标

一个高级 Select/DataTable 不应只是“泛型越多越强”。应保证：

- items 决定 value/callback 类型；
- single/multiple 模式是判别 union；
- controlled/uncontrolled 组合不混用；
- render prop 获得精确上下文；
- 无障碍行为由 runtime tests 保证；
- 错误用法产生短而可理解的报错。

## 7. 类型测试工具

可以使用 `vitest` 的 `expectTypeOf`、`tsd`、`dtslint` 或专用 compile fixtures。核心模式：

```ts
expectTypeOf(result).toEqualTypeOf<User>()

// @ts-expect-error multiple 模式必须是数组
<Select multiple value="a" />
```

`@ts-expect-error` 若下一行不再报错会自己失败，优于 `@ts-ignore`。但它不保证“为何报错”；配合小 fixture、描述和必要的类型等价断言。

## 8. 三类测试不要混淆

- 类型测试：推断、可赋值性、错误调用。
- runtime unit/integration：Schema、状态、事件、错误、并发。
- UI/e2e：焦点、键盘、ARIA、浏览器行为和框架集成。

类型测试不执行代码，e2e 也不自动检查公共泛型推断。

## 9. 跨框架共享什么

共享无框架 core：Schema、领域类型、Result、SDK、状态转换。React/Vue adapter 只负责生命周期和响应式桥接。不要共享“万能 store 抽象”到失去各框架原生能力。

## 10. 评审清单

- 外部数据是否在框架边界完成 runtime 验证？
- props/emits 是否排除了非法组合？
- 泛型是否由真实参数推断，而非调用者手填？
- React/Vue 工具链是否分别跑类型检查？
- public contract 是否有正负类型测试？
- 类型测试、行为测试、可访问性测试是否分工清楚？

## 本章速记

框架类型的价值是把合法状态和公共契约带进组件与服务，而不是给不可信数据盖章。高级工程师同时验证推断质量、运行行为与升级兼容性。
