# 第 18 章：毕业项目、系统设计与高级面试

## 本章目标

把类型系统、运行时边界、模块发布、框架集成、大仓性能和升级治理组合成可演示作品；能像高级工程师一样解释取舍、失败模式和验证证据。

## 1. 毕业项目：Schema 驱动的 SDK 平台

你将构建 `Acme Typed Platform`：从版本化 endpoint/event 定义生成类型安全 client，支持浏览器、Node、React/Vue adapter 与 CLI，并以多个 package 发布。

```text
packages/
  domain          # Brand、Result、错误、状态机
  schema          # runtime Schema 与 Infer
  protocol        # endpoint/event definitions 与版本迁移
  sdk-core        # transport、retry、abort、stream
  sdk-react       # hook adapter
  sdk-vue         # composable adapter
  testing         # fake transport、contract fixtures
apps/
  cli
  demo-react
  demo-vue
```

## 2. 必须实现的能力

- endpoint 定义驱动 path/input/output/error 推断，调用者不能自选返回泛型。
- 所有网络/localStorage/CLI 输入从 unknown 经 Schema。
- ID、Money/Currency、时间与版本使用领域建模。
- Result 区分业务错误；异常/HTTP/协议/取消有清晰 error taxonomy。
- AbortSignal 贯穿，retry 尊重幂等性，流式事件用 AsyncIterable 并限制 buffer。
- 协议事件做版本迁移和 exhaustive handling。
- exports 明确根/子路径，生成声明，真实 tarball 测 ESM/CJS（若承诺）。
- Monorepo project references，浏览器/Node/test globals 隔离。
- 正负类型测试、runtime contract tests、UI/e2e smoke。
- TS 5.9/6.0 兼容矩阵；TS 7 预览 non-blocking 评估。

## 3. 非功能要求

写进 README 的不是“高性能、高可用”口号，而是可验证指标：

- 10 万输入不会一次创建 10 万请求；
- stream 最大单行/总 buffer 有上限；
- 单包增量 typecheck 有预算；
- public declaration size 和 instantiations 有基线；
- package consumer fixtures 从 tgz 运行；
- 日志不泄漏 token/原始敏感响应。

## 4. 架构决策记录

至少写 5 份简短 ADR：

1. 为什么 Schema 是类型的单一来源，或为何不是。
2. ESM-only 还是 ESM+CJS。
3. error 使用 Result、throw 或混合的边界。
4. cache 属于 core 还是 framework adapter。
5. monorepo/package/project-reference 切分。

每份包含背景、决策、替代方案、后果和复审条件。高级能力不是永远选对，而是让取舍可追踪、可验证、可反转。

## 5. Code review 演示

挑 3 个危险 diff 做书面 review：泛型 fetch 断言、过度条件类型、错误双包 exports。评论应指出具体失败场景、影响范围和最小修复，不只说“类型不安全”。

## 6. 系统设计回答框架

面对“设计一个类型安全 API/组件平台”：

1. 澄清消费者、runtime、版本和规模。
2. 列出信任边界和不变量。
3. 画模块/数据流与依赖方向。
4. 设计公共类型和 runtime validation。
5. 处理错误、并发、取消、兼容与发布。
6. 给出测试矩阵、性能预算、迁移和观测。
7. 主动说明舍弃什么，以及规模变化时何时复审。

## 7. 高级面试必须会解释的问题

1. TypeScript 的结构类型与名义类型差异，何时用 Brand？
2. 为什么编译通过仍可能 runtime 崩溃？
3. any、unknown、never 各自表达什么？
4. `satisfies` 与 annotation/`as` 有什么不同？
5. CFA 如何缩小类型，何时失效或不够？
6. 判别 union 如何让状态机排除非法状态？
7. 函数参数型变为何与 callback 安全有关？
8. 条件类型为何分配，怎么关闭分配？
9. 如何避免复杂泛型拖慢 checker 和损害报错？
10. Schema 与 TypeScript type 如何保持单一来源？
11. Promise 为什么没有 error 泛型，预期失败怎么建模？
12. AbortSignal、race、backpressure 分别解决什么？
13. Node ESM 与 bundler 解析为何不同？
14. `paths` 为什么不能保证 runtime 能 import？
15. 如何正确发布多入口类型库并验证？
16. project references 解决什么，代价是什么？
17. 如何迁移 20 万行 JS/宽松 TS 而不停工？
18. 如何审查 AI 生成的 TypeScript？
19. TypeScript 6 升级重点与 TS 7 预览策略是什么？
20. 举例说明一次你愿意牺牲静态精确度换取可维护性。

## 8. 回答标准

每题都应包含：概念、最小例子、真实失败模式、工程取舍、验证方法。只背定义达不到高级要求；能把类型与 runtime、模块、发布、团队成本连起来才算掌握。

## 9. 作品集证据

保留 architecture diagram、ADR、API report、benchmark 前后对比、migration runbook、CI matrix、典型 type test 和一次复盘。面试时讲“我如何证明”比展示 50 个 utility type 更有说服力。

## 10. 毕业门槛

- 能不看答案完成核心项目的 70%，并解释剩余取舍。
- 全部 quality gates 通过，不用 any/断言粉饰边界。
- 随机抽 10 个面试题，8 个能用失败案例和验证回答。
- 在 90 分钟评审中找出至少 8 个跨静态/运行时/发布问题。
- 能写出下一次升级、扩容或框架适配的演进计划。

## 本章速记

“TypeScript 高级”不是复杂类型体操，而是用可信契约管理规模：边界真实、状态可穷尽、API 可消费、构建可扩展、升级可治理，并能用测试和数据证明。
