# 第 17 章：渐进迁移、TS 6→7 与 AI 协作

## 本章目标

能让遗留 JS/宽松 TS 持续交付地走向严格模式；制定 TypeScript 6 基线和 7 预览验证策略；把 AI 当高吞吐协作者而不是类型安全证明器。

## 1. 迁移不是“改后缀”

迁移的目标是降低未知状态和边界风险，同时保持可发布。先盘点：运行环境、构建链、模块协议、全局变量、测试覆盖、热点目录、依赖类型质量、隐式公共 API。按风险与变更频率分批，不按文件名排序。

## 2. JS 到 TS 的渐进路线

可用 `allowJs` 纳入 JS，`checkJs` 或文件级 `// @ts-check` 逐步检查，借 JSDoc 标注公共接口。新文件/高变更模块优先 TS；稳定遗留模块先在边界加 declaration/Schema 和 tests。

不要全仓一次打开错误海洋再长期放弃。建立每阶段可度量目标：

1. 构建与 module resolution 统一。
2. `noImplicitAny`、`strictNullChecks` 等按包推进。
3. 外部边界从 any 改 unknown + validation。
4. 收敛 suppression、断言和第三方 shim。
5. 最终 strict baseline 与 CI 防回退。

## 3. 抑制债务必须可管理

- 禁止新增裸 `@ts-ignore`；用 `@ts-expect-error` + issue/原因。
- 对 `any`、double assertion、non-null assertion 做 lint/统计预算。
- 临时 declaration shim 写最小真实表面，不要 `declare module 'x'` 全 any。
- 每个豁免有 owner、移除条件和截止版本。

错误数下降不等于安全提升；如果只是用 `as any` 清零，指标在说谎。

## 4. 从 5.9 升到 6.0

TypeScript 6.0 是通往原生 TS 7 的过渡版本。升级步骤：

1. 先在当前版本清除已标记 deprecated 配置与 API。
2. 固定依赖，建立 clean typecheck/runtime/test 基线。
3. 在非阻塞 CI 跑 6.0，按配置、模块、lib/types、真实代码分类。
4. 处理 TS 6 默认 `types: []`：每个 target 显式声明环境类型，或用 import 建依赖。
5. 重新核对 module/node 规则和被移除的历史兼容行为。
6. 升级相关 lint、test、build 与框架 type checker。
7. 用真实发布物做 consumer tests，再切主线。

不要把所有新错误归为“编译器坏了”；先做最小复现并查 release notes。

## 5. 为 TS 7 做准备

TS 7 是原生 Go 端口，目标包含大幅性能改善。它不是“语法 7.0 大改”的同义词，但工具集成可能变化。预览验证矩阵应覆盖：

- `tsc` 诊断和 emit/declaration 差异；
- `tsserver`/编辑器体验；
- build mode、project references、watch；
- 依赖 compiler API 的工具、transformer、语言服务插件；
- API report/type tests 和性能基线。

保持 TS 6 稳定车道，TS 7 预览先 non-blocking。只有正确性、工具链和性能都过门槛才切换；不要让业务仓库直接跟随 nightly 漂移。

## 6. Codemod 与批量修复

机械可证明的变更交给 AST codemod：import type、API 重命名、配置迁移。每批小范围运行 formatter/typecheck/tests，审查 diff。Regex 不理解语法边界，适合极简单文本，不适合大规模模块或类型改写。

## 7. AI 生成 TS 的典型假安全

AI 很容易产出“能过编译但契约虚假”的代码：

- 对 fetch JSON 直接 `as T`；
- 用 `any`/双重断言绕过设计矛盾；
- 发明不存在的 API、配置或过时版本行为；
- 写极复杂条件类型证明了无关性质；
- 忽略 abort、race、错误与资源释放；
- 把类型测试当 runtime 校验；
- 修改生成文件、声明和实现不同步。

## 8. AI 协作协议

给 AI 的任务应包含：真实 TS/Node/framework 版本、tsconfig、模块协议、合法/非法示例、runtime 不变量、性能预算和验证命令。要求它先列假设和边界，再给最小 patch。

审查顺序：

1. runtime 行为与数据来源；
2. public contract 和非法状态；
3. any/assertion/unknown 边界；
4. 错误、并发、取消、清理；
5. 模块/版本/依赖真实性；
6. 类型复杂度与错误可读性；
7. 正负类型测试 + runtime tests。

AI 可以提高代码产量，不能转移作者和 reviewer 的责任。

## 9. 迁移治理

每周 dashboard 应看：strict 覆盖、any/suppression 趋势、边界 Schema 覆盖、包迁移状态、构建性能和逃逸缺陷。禁止以“迁移完成率”推动低质量断言；设置 champion、office hours、范例包和升级 runbook。

## 10. 回滚与兼容

升级前固定 lockfile 与可回退分支，避免同时升级 TS、bundler、框架大版本和 Node。若必须并行，分 PR 建兼容层。库发布者明确最低 TS 版本；应用仓库可用双编译器 CI 观察下一个版本。

## 本章速记

迁移成功的标准不是零报错，而是边界更真实、豁免更少、团队仍能发布。TS 6 是稳定基线，TS 7 先以矩阵验证；AI 输出必须经过 runtime-first 的类型审查。
