# 第 06 章：泛型设计、约束与推断控制

## 本章目标

泛型用于保留输入输出关系，不是“把所有类型换成 T”。学会约束、推断来源、默认参数、const type parameters 和 `NoInfer`，让调用端自然且错误清楚。

## 1. 类型参数必须表达关系

```ts
function identity<T>(value: T): T { return value }
```

T 同时出现在输入/输出，保留具体类型。反例：

```ts
function log<T>(message: string): void {} // T 未建立关系，删除
function parse<T>(text: string): T { return JSON.parse(text) } // 调用者凭空选择 T，不安全
```

类型参数若只出现一次，先问普通类型/unknown 是否更诚实。

## 2. 约束不是返回承诺

```ts
function getId<T extends {id: PropertyKey}>(value: T): T['id'] {
  return value.id
}
```

约束表示 T 至少有 id，同时保留更多字段。写 `T extends object` 很少有用：函数可能真正需要的是 `Record<PropertyKey, unknown>`、可调用、可迭代或具体属性。

## 3. key 关联

```ts
function get<T, K extends keyof T>(value: T, key: K): T[K] {
  return value[key]
}
```

K 约束到 T 的 keys，返回与 key 相关。这是库 API 的基本模式。注意 `keyof` 可能含 string|number|symbol；DOM/JSON path 若只支持 string 应显式 `Extract<keyof T, string>`。

## 4. 推断候选冲突

```ts
function pair<T>(a: T, b: T): [T, T] { return [a, b] }
```

多个位置共同推断 T，可能合并、拓宽或失败。API 应决定谁是“源”、谁只是被检查。`NoInfer<T>` 可阻止某位置贡献候选：

```ts
function createFSM<S extends string>(states: readonly S[], initial: NoInfer<S>) {}
```

states 定义 S，initial 只能验证属于 S，不能偷偷把新字符串扩进 S。

## 5. `const` 类型参数

TS 5.0+：

```ts
function defineRoutes<const T extends readonly Route[]>(routes: T): T { return routes }
```

让调用者不写 `as const` 也倾向保留字面量/readonly 推断。约束必须允许 readonly；若约束是可变 `string[]`，候选可能回退拓宽。不要所有泛型都加 const，它会产生更精确/更大的类型并影响可变性。

## 6. 默认类型参数

默认适合常用值，但必须遵守约束，且必选参数不能排在可选默认后。默认 `any` 会掩盖信息；通常 `unknown`/具体默认更安全。

```ts
type ApiResponse<TData, TMeta = {requestId: string}> = {data: TData; meta: TMeta}
```

## 7. 泛型返回构造难题

```ts
function minimumLength<T extends {length: number}>(obj: T, min: number): T {
  if (obj.length >= min) return obj
  return {length: min} // 错：满足约束，不一定是 T
}
```

T 可能还有字段/具体类。约束不是“我能构造任何 T”。让调用者提供 factory，或返回约束类型/联合。

## 8. 泛型类/接口的型变

T 出现在输出位置倾向协变，输入位置倾向逆变，二者都有则不变。TS 支持 variance annotations 的特定场景，但多数业务应由结构自然推导；错误 annotation 会造成不一致，且只影响某些实例化比较。先理解 API 读写能力：

```ts
interface Source<out T> { get(): T }
interface Sink<in T> { set(value: T): void }
```

公共库才谨慎使用显式 annotation，并写型变测试。

## 9. F-bounded/fluent API

返回 `this` 可保留子类链式类型；状态构建器可用泛型状态参数表达步骤，但容易类型爆炸。若运行时顺序可用简单对象/函数表达，不必用五层泛型 builder。

## 10. 泛型 API 评审

- 每个类型参数出现几次，表达什么关系？
- 调用端能推断吗，还是被迫显式传？
- 哪些参数是推断源，哪些只应检查？
- 约束是否是实现真正所需最小能力？
- 是否错误承诺构造/返回 T？
- const/readonly 会否过度精确？
- 错误信息、声明大小和 checker 性能如何？

## 本章速记

好的泛型保存关系；约束限制能力，不能让你构造任意 T。用 `NoInfer` 控制候选来源，用 const type parameter 改善字面量 API，但所有精确度都有复杂度成本。
