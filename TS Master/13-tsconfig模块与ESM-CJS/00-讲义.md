# 第 13 章：tsconfig、模块解析与 ESM/CJS

## 本章目标

建立“源码、TypeScript、打包器、Node、测试工具必须遵守同一模块协议”的心智模型；能定位编辑器正常、构建或运行失败的问题。

## 1. 先分清三件事

- `target` 决定 TypeScript 输出到哪一代 JavaScript；`lib` 决定类型检查时可见的标准库，不会自动加入 polyfill。
- `module` 决定输出模块形态，并会影响解析规则；`moduleResolution` 决定 import 如何找到文件与类型。
- `noEmit` 表示只检查；真正输出由 Vite、esbuild、SWC、Babel 或其他工具负责。

不要靠随机改选项解决报错。先画出“谁负责解析、谁负责转译、谁负责执行”。

## 2. 配置必须匹配运行环境

浏览器打包项目通常使用：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "noEmit": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true
  }
}
```

直接由现代 Node 执行的项目应选择与 Node 语义对应的稳定模式，例如 TS 6 的 `node20`，并理解包的 `"type"`、文件扩展名和 exports 条件。不要把 `moduleResolution: "bundler"` 用作 Node 运行错误的遮羞布。

## 3. Node 中一个文件到底是 ESM 还是 CJS

判断来源包括：

- 最近的 `package.json` 中 `"type": "module" | "commonjs"`；
- `.mts/.mjs` 明确 ESM，`.cts/.cjs` 明确 CJS；
- `.ts/.js` 受 package type 和编译配置影响；
- package `exports` 中 `import`、`require`、`types` 条件。

在 Node ESM 源码里，相对 import 通常要写运行时扩展名，例如 `./util.js`，即使源文件叫 `util.ts`。TypeScript 检查的是最终运行协议。

## 4. 类型 import 必须诚实

```ts
import type { User } from './model.js'
import { createUser } from './model.js'
```

`verbatimModuleSyntax` 让 import/export 更接近所写即所得，迫使纯类型依赖使用 `import type`。这能避免循环依赖、无意的运行时 import 和不同转译器行为不一致。`isolatedModules` 则确保每个文件可单独转译，但它不是完整类型检查的替代品。

## 5. `paths` 不是运行时重写器

```json
{ "paths": { "@/*": ["./src/*"] } }
```

它主要告诉 TypeScript 如何解析；输出中通常仍是 `@/...`。Vite、Node loader、package imports 或构建工具必须有同样映射。库代码优先使用真实 package exports，避免把应用别名泄漏到发布物。

## 6. package exports 是公共边界

```json
{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./codec": {
      "types": "./dist/codec.d.ts",
      "import": "./dist/codec.js",
      "require": "./dist/codec.cjs"
    }
  }
}
```

没有导出的深层路径应视为私有。条件顺序、类型声明与对应 runtime 文件必须一致。双包最危险的问题是同一库 ESM/CJS 被同时实例化，导致 singleton、class identity、symbol registry 分裂。

## 7. TS 6 配置要点

本课程基线是 TypeScript 6.0.3，同时保留 5.9 项目的迁移视角：

- TS 6 默认 `types: []`，不会再把所有可见 `@types` 包自动注入全局；应用要显式写 `types` 或真实 import。
- 多个旧配置被弃用或移除，升级前先清除 deprecation，不要用长期 ignore 掩盖债务。
- Node 模块模式持续收紧为与真实运行环境一致；不要依赖历史宽松解析。
- `skipLibCheck` 只跳过声明文件内部检查，不会修复不兼容依赖，也不应成为永久万能开关。

## 8. 按用途拆配置

推荐 `tsconfig.base.json` 放严格公共规则；应用、Node 工具、测试、脚本分别 extends。浏览器项目不应无故看见 Node globals，生产源码也不应自动看见 Vitest globals。

```text
tsconfig.base.json
tsconfig.app.json
tsconfig.node.json
tsconfig.test.json
```

每个配置明确 `files/include/exclude/types/lib`。注意 exclude 不是“禁止 import”；被 include 文件 import 的依赖仍会进入程序。

## 9. 系统化排错

1. 确认报错发生在编辑器、`tsc`、bundler、test runner 还是 Node runtime。
2. `tsc -p ... --showConfig` 查看最终配置。
3. `--traceResolution` 看模块和类型为何解析到某文件。
4. 检查实际运行产物中的 import specifier。
5. 检查最近 package type、exports、扩展名、重复依赖。
6. 用最小 consumer fixture 同时跑 ESM 与 CJS。

## 10. 评审清单

- target/lib/module/moduleResolution 是否服务于真实 runtime？
- app、Node、test 的全局类型是否隔离？
- 类型 import 是否使用 `import type`？
- paths 是否在运行工具中也实现？
- exports 每个入口是否有配对类型和 runtime？
- 发布前是否从打包后的 tarball 做 consumer 测试？

## 本章速记

TypeScript 能通过不代表 JavaScript 能运行。模块问题要沿“解析—转译—发布—执行”全链路检查，配置的正确答案取决于部署环境。
