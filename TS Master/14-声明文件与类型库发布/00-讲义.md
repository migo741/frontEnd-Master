# 第 14 章：声明文件与类型库发布

## 本章目标

能为 JS/TS 库设计稳定公共类型，正确发布 `.d.ts`，用真实消费者验证类型与运行时一致，并把类型变更纳入语义化版本管理。

## 1. `.d.ts` 是可执行契约的静态投影

声明文件不产生 runtime。它描述真实 JS 已经做的事，不能为了“好看”虚构保证。若 JS 可能返回 null，声明却写 `User`，这是比没有类型更危险的谎言。

TypeScript 库通常用 `declaration: true` 生成声明；JS 库可手写声明、从 JSDoc 生成，或在 DefinitelyTyped 维护。手写时必须有 runtime tests 对齐。

## 2. 公共 API 才是类型设计对象

导出的函数、类型参数、错误策略、可变性和扩展点都会成为兼容承诺。不要让内部 ORM 类型、Schema 库具体类型、复杂条件类型意外泄漏。

```ts
export interface Codec<T> {
  decode(input: unknown): DecodeResult<T>
  encode(value: T): unknown
}
```

优先命名可读的公共类型，限制递归深度，避免消费者错误消息展开数百行。

## 3. declaration emit

常用选项：

```json
{
  "declaration": true,
  "declarationMap": true,
  "emitDeclarationOnly": true,
  "stripInternal": true,
  "composite": true
}
```

`stripInternal` 依赖 `@internal` 约定且可能产生悬空引用，发布前必须检查。声明 map 改善跳转，但会增加文件与源码路径暴露；按发布策略决定。

## 4. ambient module 与 global augmentation

```ts
declare module 'legacy-codec' { /* 描述模块 */ }

declare global {
  interface Window { analytics?: Analytics }
}
export {}
```

全局扩展影响整个程序，应极少使用并放在明确入口。模块增强只能扩充既有声明，不能改变 runtime；若插件没有真的注册方法，类型增强也没用。

## 5. 函数、类与可调用对象的声明

JS 生态常有 function + property、构造器 + namespace、default/CommonJS export 等混合形态。应按真实用法建模，必要时使用 declaration merging 或 `export =`，但先确认包的实际模块协议。不要同时堆 `default`、`export =` 和 esModuleInterop 猜测。

## 6. package 元数据

简单单入口包可用顶层 `types`。现代多入口包应让 exports 的每个 runtime 入口有匹配 types 条件。`.d.mts/.d.cts` 可明确与 ESM/CJS 对应。类型文件里的 import 路径也必须可解析。

`typesVersions` 用于确有必要的旧 TypeScript 差异，不应用来掩盖错误 exports。最低支持 TypeScript 版本要在 README/CI 明示。

## 7. 类型也遵守 SemVer

以下可能是 breaking change：

- 收窄参数、改变泛型默认值或推断；
- 把 property 变 readonly，或反过来影响型变；
- 给公开 union 添加成员，使消费者 exhaustive switch 失败；
- 提高最低 TypeScript/lib/Node types 版本；
- 更改导出路径或 declaration 模块形态；
- 修正过宽的错误类型，虽然 runtime 未变。

类型修复是否 major 要看消费者影响，不能只看 JS runtime。

## 8. 类型测试三层

1. 正向 compile fixture：典型调用能推断到目标类型。
2. 负向 test：错误调用必须失败，可用 `@ts-expect-error`，并写明预期原因。
3. API snapshot/报告：审查公开声明变化。

同时保留 runtime tests；类型测试不能发现实现返回了错误值。

## 9. 发布物验证

永远测试 `npm pack` 产生的 tarball，而不只测 monorepo 源码。fixture 覆盖：

- 支持的最低/当前 TypeScript；
- ESM、CJS（如果承诺）、Node、bundler；
- 根入口和所有子路径；
- declaration map/跳转；
- 未导出深层路径确实不可访问。

## 10. 评审清单

- declaration 与 runtime 是否一一对应？
- 公共类型是否泄漏内部依赖或无法命名类型？
- exports 每个入口是否配对 types？
- 类型升级是否做 consumer impact 分析？
- 是否从 tarball 测最低 TS/Node 与多模块环境？
- `@ts-ignore` 是否被精确的 expect-error 替代？

## 本章速记

发布类型就是发布 API。优秀声明文件不追求炫技，而追求真实、稳定、可推断、错误信息清楚，并在真实消费环境中被持续验证。
