# 第 04 章：对象建模、可选、readonly 与精确边界

## 本章目标

把对象类型当作业务协议，而不是字段清单；理解开放结构、额外属性、readonly 的浅层语义、Patch/merge 的三态，以及为什么 `DeepPartial<T>` 常是危险 API。

## 1. `type` 与 `interface`

两者对普通对象大多可互换。常用取舍：

- interface：对象/类契约、可声明合并、库扩展点；
- type：联合、交叉、映射/条件类型、别名任意类型。

不要用“interface 性能一定更快”作为无条件规范。命名复杂交叉/条件结果有助 checker 与错误信息；真正性能要 trace。

声明合并既是能力也是风险：全局/第三方 interface 可被扩展，适合明确插件协议，不适合业务模型被任意目录偷偷加字段。

## 2. 开放结构与额外属性

```ts
type User = {id: string}
const rich = {id: 'u1', secret: 'x'}
const user: User = rich // 合法；运行时 secret 仍存在
```

对象类型描述“至少有这些可读属性”，通常不是 exact shape。新鲜字面量的 excess property check 只抓拼写/常见错误。跨网络、日志和缓存必须显式投影/Schema strip。

## 3. 可选不是默认值

`x?: T` 表示属性可能缺失；读取通常是 `T | undefined`。它不自动提供默认，也不等于数据库 nullable。默认值要在构造/解析边界应用，并区分调用者显式值。

不要用几十个 optional 表达生命周期：

```ts
type BadOrder = {id?: string; error?: string; receipt?: Receipt}
```

改用创建输入、持久实体、加载状态等不同类型/联合。

## 4. readonly 是赋值视图

```ts
type User = {readonly id: string; tags: readonly string[]}
```

它阻止通过该引用写，不保证对象在其他别名处不会变化，也不运行时冻结。`Readonly<T>` 只浅层。不可变 API 应接受 readonly 输入、返回新值，并控制可变别名；必要时运行时 freeze（同样浅层，深 freeze 有成本）。

数组参数若只读，应写 `readonly T[]`，这样同时接受可变/只读数组且禁止函数内部 push。

## 5. 索引签名与 Record

```ts
type Users = Record<string, User>
```

这在默认索引模式下容易暗示任意 key 存在。若 key 开放且可能缺失，用 `Partial<Record<string, User>>` 或 `Map<string, User>`；若 key 是有限 union，完整 Record 可证明覆盖。

索引签名要求所有显式属性也兼容其值类型。把元数据和动态项混在一个对象常导致 `string | number | ...` 扩散，最好拆 `{meta, items}`。

## 6. 交叉类型不是对象合并算法

```ts
type A = {x: string}
type B = {x: number}
type C = A & B // x: never
```

交叉要求同时满足，两字段冲突可能得到 never；运行时 `{...a, ...b}` 是后者覆盖前者。为 `merge` 建模应表达覆盖：

```ts
type Merge<A, B> = Omit<A, keyof B> & B
```

仍需考虑 symbol、getter、prototype、可选和 runtime spread 语义，不能把类型别名当实现。

## 7. Patch 的三态

常见：缺失=不修改，值=设置，null=清除。若字段本身允许 null，协议需另一表示。不要用 `Partial<T>` 自动定义所有更新 API：

- readonly/id 不应更新；
- 嵌套 Partial 是替换还是深 merge？
- undefined JSON 会消失；
- 字段间不变量可能被破坏。

显式 Patch：

```ts
type UserPatch = {
  displayName?: string
  avatarUrl?: string | null // null 明确清除
}
```

或操作联合：`{op:'set'; path; value} | {op:'clear'; path}`。

## 8. `Partial/Required/Pick/Omit`

这些是浅层结构变换，适合减少重复，但公共 DTO 应命名并审查。`Omit<Entity, 'id'>` 创建 CreateInput 可能在实体新增 serverManaged 字段后意外允许客户端传入；显式 Pick allowlist 更安全。

## 9. `DeepPartial` 陷阱

递归把一切变可选会误处理 Date/Map/Function/tuple/union，丢失互斥状态，并让 merge 语义含糊。表单库内部可有针对性实现；业务 API 应为具体可更新结构建模。

## 10. 对象边界清单

- 类型是内部实体、输入 DTO、输出 DTO、Patch 还是持久化格式？
- optional/null/undefined 分别是什么语义？
- readonly 是静态视图还是运行时不可变承诺？
- dynamic key 是否真的全覆盖？
- 敏感额外字段是否运行时裁剪？
- 合并是 shallow overwrite、deep merge 还是领域操作？

## 本章速记

对象类型通常是开放的最小形状；readonly/utility types 是浅层静态工具。高级建模要拆生命周期和信任边界，明确缺失、清除、替换与合并。
