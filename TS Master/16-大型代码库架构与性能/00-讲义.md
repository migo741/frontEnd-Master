# 第 16 章：大型代码库架构与 TypeScript 性能

## 本章目标

能把大型仓库拆成可独立检查、构建和发布的边界；用测量定位 TypeScript 慢点，而不是靠关闭严格性或盲目升级机器。

## 1. 架构问题会变成类型检查问题

一个包可以 import 整仓任意源码、共享巨型环境声明、导出无限递归类型时，TypeScript 会替混乱架构付费。编译慢、编辑器卡和改一行重建全部，往往是边界缺失的症状。

先确定依赖方向：

```text
domain <- application <- adapters <- apps
                 ^          ^
                 |          +-- react/vue/node
                 +-- ports
```

领域层不 import 框架、数据库、HTTP；adapter 实现 port。类型可以帮助守边界，但需 lint/dependency graph 配合。

## 2. Monorepo 配置分层

根 solution 配置只放 references，通常 `files: []`；每个 package 有自己的 include、rootDir、outDir、types 和 references。公共 base 放严格规则，不要把所有环境 lib/types 注入每个包。

```json
{
  "files": [],
  "references": [
    {"path": "packages/domain"},
    {"path": "packages/sdk"},
    {"path": "apps/web"}
  ]
}
```

## 3. Project References

被引用项目启用 `composite`，并通常生成 declaration。`tsc -b` 按依赖图增量构建；下游通过上游 `.d.ts` 边界检查，而不是把所有源码揉成一个 Program。

收益：构建分块、边界明确、编辑器负担可控。代价：配置/产物管理、循环依赖暴露、声明 API 质量变重要。不要为了“用了 references”把每个小目录拆成包。

## 4. incremental 与缓存

`incremental`/`.tsbuildinfo` 保存程序结构和签名信息。缓存 key 必须包含 TypeScript 版本、配置、源码、依赖声明与生成步骤。CI 缓存错误会产生比慢构建更难查的幽灵问题。

构建工具的 task graph 与 TS references 应一致：声明先于下游检查，runtime build 与 typecheck 责任明确。

## 5. 测量工具

- `--extendedDiagnostics`：文件数、类型数、实例化、内存和阶段时间。
- `--generateTrace`：生成可用分析器查看的 trace/types 数据。
- `--traceResolution`：处理模块/类型解析异常，不是常规性能 profile。
- `--explainFiles`：某文件为何进入 Program。
- `--listFilesOnly`、`--showConfig`：确认范围和最终配置。

先记录稳定基线，再一次改一个变量。冷启动、增量构建、编辑器响应分别测量。

## 6. 常见性能杀手

- 巨型 union 互相做条件分配，组合数量爆炸；
- 无界递归 conditional/mapped type；
- 同一复杂匿名类型重复推断，未命名/未缓存；
- 大量 overload 两两比较；
- 自动生成单文件包含数万 union 成员；
- 重复依赖版本带来多份声明；
- include 过宽，把 dist、fixtures、脚本、所有 tests 拉入应用；
- barrel 造成意外依赖面和循环。

## 7. 优化策略

1. 减少 Program 范围、隔离环境类型。
2. 在 package/API 边界生成简洁声明。
3. 给复杂返回值和中间类型命名，避免重复实例化。
4. 用对象查表/Map 代替超大 union 的全排列类型计算。
5. 为递归类型加入 depth/seen，并接受适度降级。
6. 将极大生成类型按模块切分，或把验证移到 runtime Schema。
7. 用更简单的 interface/基类型复用，而非巨大 intersection。
8. 跑 trace 验证收益，保留回归预算。

不要第一步就关 `strict`。`skipLibCheck` 可作为升级过渡或依赖声明冲突缓解，但要建债务项和移除条件。

## 8. 生成代码

OpenAPI/GraphQL/Protobuf 生成物应：

- 固定生成器版本，结果可复现；
- 生成到独立 package/目录，不手改；
- 上层再包稳定领域 API，避免全仓耦合生成细节；
- 监控文件大小、类型数量和 diff；
- 区分“服务端声称的类型”和“客户端运行时是否验证”。

## 9. API 边界与构建边界

source import 可改善开发体验，但可能绕过 package exports 和声明边界，发布时暴雷。大型仓库至少要有一条 CI 路径按真实发布物/exports 检查。循环 project reference 不允许，通常说明领域切分需要重构或抽出共同协议包。

## 10. TS 7 的性能视角

TypeScript 7 的原生实现目标是显著提升编译器/语言服务性能，但不能替代良好边界。迁移期还要关注 API/工具兼容：依赖 compiler API、语言服务插件、旧 build integration 的工具可能需要等待。性能测试要同时比较正确性、诊断和工具链，不只看秒数。

## 11. 团队性能预算

为关键仓库定义：冷 typecheck、单包增量、编辑器诊断、内存、声明大小、类型实例化数量。超过阈值在 PR 报告趋势；不要把绝对值当跨机器真理，关注固定 runner 的回归比例。

## 本章速记

大型 TypeScript 性能首先是边界与复杂度管理，其次才是编译器调参。先测量 Program 与实例化，再缩范围、简 API、拆图，并把性能纳入持续验收。
