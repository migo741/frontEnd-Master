# 第 11 章：类、标准装饰器与元编程

## 本章目标

掌握类的静态/运行时双重身份、private/abstract/override、组合与 mixin 边界；理解现代标准装饰器和旧实验装饰器不是同一套语义，避免元数据魔法成为不可测试依赖。

## 1. 类既是值也是类型

```ts
class UserService {}
const Ctor = UserService        // runtime constructor value
type Instance = UserService     // instance type
type Static = typeof UserService
```

`implements` 只检查实例侧公共形状，不改变 emit，不验证 static，不能让 class 在运行时自动注册。

## 2. 可见性

- `public/protected/private`：TypeScript 静态限制，private 通常仍是普通 JS 属性（取决 emit）；
- `#private`：JavaScript 运行时私有字段，跨实例/代理/序列化语义不同；
- `readonly`：仅静态写限制，构造后其他别名/运行时仍需理解。

安全秘密不因 private 就安全；对象内存/调试/序列化边界另行处理。

## 3. `abstract` 与 `override`

abstract 定义子类契约但不 runtime instantiate；`noImplicitOverride` 要求覆盖显式 `override`，基类重命名时子类不会静默变成新方法。基类构造期间调用可覆盖方法很危险：子类字段尚未初始化。

优先小接口 + 组合；继承适合稳定 is-a 与框架生命周期，不是复用几行代码的默认工具。

## 4. 参数属性与初始化顺序

```ts
class Service {
  constructor(private readonly api: Api) {}
}
```

简洁但把依赖/字段隐藏在参数，公共库可读性要权衡。class fields 的 define/assign 语义与 target/useDefineForClassFields/JS 标准相关，迁移旧 decorator/继承代码需测试初始化顺序。

## 5. 静态侧泛型限制

class 的 static 成员不能直接引用实例类型参数 T，因为所有实例共享一个 constructor。工厂/伴随对象可携带 schema：

```ts
interface EntityType<T> { new (...args: never[]): T; schema: Schema<T> }
```

## 6. Mixin

```ts
type Constructor<T = object> = abstract new (...args: any[]) => T
```

Mixin 返回扩展 class，能组合行为，但 constructor 参数、private 字段、声明 emit、decorator metadata 和冲突复杂。业务优先对象组合；框架/库内部才谨慎使用并测试 `.d.ts`。

## 7. 标准装饰器 vs legacy decorators

TypeScript 5.0+ 支持与 ECMAScript 提案对齐的新装饰器语义；旧 `experimentalDecorators`/`emitDecoratorMetadata` 是不同模型。两者在签名、执行顺序、metadata、参数装饰器等方面不同，不能只改 tsconfig 就迁移。

现代装饰器接收 value 与 context，可返回替代/初始化逻辑：

```ts
function logged<This, Args extends unknown[], Return>(
  original: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>,
) {
  return function (this: This, ...args: Args): Return {
    console.log(String(context.name))
    return original.call(this, ...args)
  }
}
```

装饰器类型必须保留 this/args/return，不用 `Function/any` 抹掉。

## 8. 元数据与 DI

Nest/Angular 等可能依赖 legacy decorator/metadata/编译器转换。类型注解被擦除，运行时反射只看到有限构造器信息，泛型/union/interface 不存在。DI token 应是运行时 symbol/class/string，不是 interface。

```ts
const USER_REPO = Symbol('UserRepo')
interface UserRepo { /* ... */ }
```

注册表显式 token→factory 往往比全局反射魔法更可测试、tree-shakable。

## 9. 装饰器副作用

执行时机在 class 定义/初始化阶段；可能改变 descriptor/initialization、堆叠顺序。装饰器不应偷偷发网络、读取全局用户、注册不可撤销单例。日志/权限装饰器要处理 sync/async/error 并保持 this。

## 10. 评审清单

- 这是继承真正 is-a，还是组合更简单？
- private 是静态还是 runtime #？
- override/初始化顺序有测试？
- class 的实例侧/静态侧是否混淆？
- 装饰器是哪套语义，目标框架支持吗？
- 装饰器是否保留函数类型、可测试、无隐藏副作用？
- metadata 能否真实表示所需类型，还是需要显式 Schema/token？

## 本章速记

class 同时存在于值/类型世界，implements 不产生 runtime 行为。现代与 legacy decorator 必须分清；元编程越隐式，越需要显式 token、Schema、生命周期和测试。
