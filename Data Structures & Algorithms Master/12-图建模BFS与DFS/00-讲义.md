# 第 12 章：图建模、BFS 与 DFS

> 本章先解决“对象之间有任意关系时，如何表示并遍历”，下一章再在无环依赖图上做拓扑排序。主语言为 strict TypeScript。

## 1. 图不是一张图片，而是一组关系

树要求每个非根节点只有一个父节点且没有环；现实系统经常不满足：

- 一个 npm package 同时依赖多个 package，也被多个应用依赖；
- 用户、团队与资源形成授权关系；
- 服务调用可能互相回调；
- 城市之间有多条道路；
- 网页通过链接形成网络。

图写作 `G = (V, E)`：

- `V` 是顶点（vertex/node）集合；
- `E` 是边（edge）集合；
- 有向边 `(u, v)` 表示从 `u` 指向 `v`；
- 无向边 `{u, v}` 表示双向关系。

“边的方向代表什么”必须写在模型旁。若定义 `app -> ui` 表示 app 依赖 ui，那么“app 的依赖闭包”沿正向走；ui 修改后“谁受影响”要沿反向 `ui -> app` 走。方向画反，算法再正确也会回答错误问题。

## 2. 图的表示

### 2.1 邻接表

```ts
type Graph = ReadonlyMap<string, readonly string[]>;
```

每个节点保存它直接指向的邻居。空间为 `Θ(V + E)`，适合大多数稀疏工程图。

```text
A -> B, C
B -> D
C -> D
D ->

A: [B, C]
B: [D]
C: [D]
D: []
```

有向图每条边存一次。无向图通常把 `{u,v}` 存为 `u -> v` 和 `v -> u` 两个邻接项，复杂度仍写 `O(V + E)`，常数上约存两份。

### 2.2 邻接矩阵

矩阵 `matrix[u][v]` 能在 `O(1)` 判断边是否存在，但需要 `Θ(V²)` 空间。节点少且图非常稠密，或算法本来就做矩阵运算时合适；100 万节点的软件依赖图不可能用普通布尔矩阵。

### 2.3 边列表

`Array<{from,to}>` 适合序列化、批量排序和 Kruskal，却不适合每次从一个节点找邻居，因为可能要扫描全部边。生产系统常同时保存正向邻接、反向邻接或边列表，换取特定查询速度。

## 3. 遍历前先定义输入契约

以下差异常导致线上工具结果不稳定：

- 邻居引用一个未声明节点，是自动补空节点还是拒绝？
- 重复边是无害去重、计数边，还是输入错误？
- 自环是否合法？
- 输出顺序按输入、字典序还是无保证？
- 图在遍历期间能否修改？

本章核心题把图视为遍历期间不可变的闭合邻接表：每个邻居都必须是一个 key。邻接数组顺序决定稳定遍历顺序。生产题在构建索引时去重并排序，使结果不依赖 JSON 到达顺序。

## 4. BFS：按边数一层层扩展

广度优先搜索（Breadth-First Search）使用 FIFO 队列：

```text
A -> B, C
B -> D
C -> E

队列变化：
[A]
取 A，加入 B,C       [B,C]
取 B，加入 D         [C,D]
取 C，加入 E         [D,E]
```

### 4.1 什么时候标记 visited

应在节点“入队时”标记，而不是出队时。若 B 与 C 都指向 D，在 D 出队前，两者都可能把 D 入队；稠密图会产生大量重复。

BFS 不变量：

1. 每个已发现节点最多入队一次。
2. 队列中的距离不递减。
3. 节点首次被发现时得到的距离，是从起点到它的最少边数。

第三点来自分层扩展：在处理距离 `d` 的节点时，新发现邻居的距离是 `d+1`；任何更短路径都应在更早层发现它，与“首次发现”矛盾。

### 4.2 JavaScript 队列不要反复 shift

```ts
const queue = [start];
let head = 0;
while (head < queue.length) {
  const node = queue[head];
  head += 1;
}
```

用 head 下标避免 `shift()` 搬动剩余元素。若这是长期常驻且反复复用的队列，应使用真正环形缓冲，避免已消费数组槽长期保留。

## 5. parent 不只是为了好看

首次从 `u` 发现 `v` 时记录 `parent[v] = u`。从目标沿 parent 回到起点，再反转，就得到一条 BFS 最短路径：

```text
start A -> B -> D -> target F
parent[F]=D, parent[D]=B, parent[B]=A, parent[A]=null
```

parent 还提供“为什么这个节点被认为受影响”的可解释证据。生产分析工具若只返回一万个受影响包，却不能展示任何传播链，很难排查错边和误报。

## 6. DFS：沿一条路径深入再回退

深度优先搜索（Depth-First Search）使用调用栈或显式栈。它天然适合：

- 可达性与连通分量；
- 进入/退出时间；
- 回溯式结构处理；
- 环检测与拓扑排序；
- 树/图的后序聚合。

DFS 有两个重要时刻：

- preorder：第一次进入节点；
- postorder：所有邻居处理完，退出节点。

如果只把邻居压到一个普通栈，容易得到 preorder，却不容易准确产生 postorder。显式 frame 应保存“节点和下一个待处理邻居下标”，模拟递归调用帧：

```text
frame { node: A, nextNeighbor: 0 }
看 A 的第 0 个邻居 B -> push B frame
B 全部处理完 -> pop B，并记录 B postorder
回到 A 的 nextNeighbor 继续
```

来自外部的图可能有十万深链。JavaScript 不应假设递归栈足够，因此生产实现优先显式栈。

## 7. 白、灰、黑三色与 visited 的区别

只做“是否到达”时，`visited Set` 足够。需要理解 DFS 生命周期时常用：

- 白：从未发现；
- 灰：已经进入但尚未退出，位于当前 DFS 路径；
- 黑：已经退出。

有向 DFS 遇到指向灰节点的边，说明存在回到当前路径祖先的 back edge，也就是环。遇到黑节点不表示环，因为对方已经完整结束。下一章会用颜色恢复具体 cycle witness。

无向图则要排除“回到直接父节点”的边；同一个颜色规则在不同图语义下不能机械套用。

## 8. 连通分量要先说是哪一种

无向图的 connected component：分量内任意两个节点彼此可达。算法是在所有节点上循环，每遇到未访问节点就启动一次 BFS/DFS。

有向图至少有两种不同概念：

- weakly connected：忽略边方向后的连通；
- strongly connected：分量中任意两点沿有向边相互可达。

普通一次 DFS 不能直接求强连通分量，需要 Kosaraju、Tarjan 等算法。本章核心练习只实现无向连通分量；生产题允许依赖环，但只问可达性与最短传播链。

## 9. PackageImpactAnalyzer：同一张图的两个方向

定义：

```text
web -> ui       表示 web 依赖 ui
ui  -> tokens   表示 ui 依赖 tokens
```

如果询问 web 构建需要什么，沿正向边得到 `ui, tokens`。如果 tokens 改动可能影响谁，需要反向索引：

```text
tokens -> ui -> web
```

构建时同时保存：

```text
dependenciesByPackage: package -> direct dependencies
dependentsByPackage:   package -> direct dependents
```

多个 package 同时改变时，可把所有 changed package 作为距离 0 的 BFS 起点，形成 multi-source BFS。每个节点第一次发现时记录：

- `distance`：最少经过多少条依赖边；
- `parent`：从哪个已受影响节点传播而来；
- `source`：最终源于哪个 changed package。

同距离有多条链时必须定义 tie-break。本课程把 changed 和邻居排序，使用“首次发现”，从而输出确定但不一定是唯一的最短证据链。

## 10. 环不会让正确 BFS 无限循环

```text
A -> B -> C -> A
```

只要在入队时标记，A/B/C 各入队一次。环会让“拓扑顺序”不存在，却不妨碍可达性分析。工程上不要因为依赖图按理说应是 DAG，就省略 visited；脏数据和遗留系统会打破理想假设。

自环同理。分析器可以选择接受并报告，也可在数据治理层拒绝；算法必须有明示策略。

## 11. 复杂度为何是 O(V + E)

邻接表 BFS/DFS 中：

- 每个可达顶点至多发现一次：`O(V)`；
- 每个已访问顶点扫描其邻接表一次，所有邻接长度总和是 `E`（无向图存两份时为 `2E`）：`O(E)`。

所以时间 `O(V + E)`，visited、parent、queue/stack 最多 `O(V)`。

如果为了确定性对每个邻接表排序，构建成本还包括 `Σ deg(v) log deg(v)`；不能把排序藏进 `O(V+E)`。索引构建一次、多次查询时，这通常值得。

## 12. 测试图算法的方法

固定样例不足以覆盖环、重复边和断开分量。推荐多层证据：

1. 极小手算图：空、单点、链、菱形、环、断开、自环。
2. 不变量：每个输出节点在输入中；parent 边真实存在；BFS parent 距离正好少 1。
3. oracle：用较慢的全边固定点传播验证可达集合。
4. 变形测试：添加不可达分量不应改变起点遍历；重复一条边不应改变集合。
5. 固定 seed 随机图，失败时打印图和 seed。

## 13. 生产边界

- 进程内图是某个时间点的快照。package manifest 在分析中变化时要绑定版本或重建。
- 百万边的字符串对象开销可能远高于边本身；可把名称映射为整数 ID，并用紧凑数组存储。
- 影响可达不等于一定失败。动态导入、平台条件和公开 API 兼容性会影响真实风险。
- 构建工具还需处理生成文件、隐式输入、环境变量与缓存 key，不是一张 package 图就足够。
- 权限图的“可达”不能自动等同授权；deny、条件、时间与资源范围需要领域语义。
