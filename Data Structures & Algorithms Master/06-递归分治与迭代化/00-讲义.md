# 第 06 章：递归、分治与迭代化

> 学习顺序：先读完本讲义，再进入 <code>01-练习</code>，最后使用 <code>02-答案</code> 复盘。  
> 本章不是教你追求“漂亮的递归代码”，而是教你把递归契约、调用栈成本和生产边界说清楚，并在必要时把递归改造成可控的迭代过程。

## 1. 为什么生产代码仍然离不开递归思想

前端和后端都经常遇到天然具有层级结构的问题：

- AST、虚拟 DOM、路由配置、菜单、评论和组织树；
- 文件目录、JSON 文档、权限表达式和工作流定义；
- 把大问题拆为左右两半，再合并结果的排序、索引构建和批处理；
- 对依赖关系做深度遍历，进入节点时准备上下文，离开节点时汇总结果。

递归最有价值的地方不是“函数调用自己”，而是它迫使我们先定义一个清晰的子问题契约：

> 假设较小规模的问题已经能被正确解决，当前这一层需要做哪些工作，才能得到当前问题的答案？

但生产数据不是教科书数据。一个用户导入的 JSON 可能有十万层；一份被错误拼接的配置可能形成对象引用环；一个递归函数可能在每层都复制数组，让看似 <code>O(n log n)</code> 的算法制造大量垃圾回收压力。因此高级工程师必须同时掌握递归表达和迭代化控制。

## 2. 基本术语与调用栈

### 2.1 递归问题的四个组成部分

一个可推导的递归函数至少要说清四件事：

1. **问题规模**：每次调用处理的规模是什么，例如节点数或区间长度。
2. **基例**：规模足够小时如何直接返回。
3. **缩减**：递归调用为什么一定处理更小的问题。
4. **组合**：子问题结果如何组成当前结果。

以数组区间求和为例：

~~~ts
function sumRange(
  values: readonly number[],
  left: number,
  right: number,
): number {
  if (left >= right) return 0;
  const middle = left + Math.floor((right - left) / 2);
  return (
    sumRange(values, left, middle) +
    sumRange(values, middle + 1, right)
  );
}
~~~

这里故意留下了一个错误：当区间约定没有统一时，基例和拆分会遗漏或重复元素。递归代码短，不代表契约清楚。若采用半开区间 <code>[left, right)</code>，一致的版本应为：

~~~ts
function sumRange(
  values: readonly number[],
  left: number,
  right: number,
): number {
  if (right - left <= 1) {
    return left < right ? values[left] : 0;
  }

  const middle = left + Math.floor((right - left) / 2);
  return (
    sumRange(values, left, middle) +
    sumRange(values, middle, right)
  );
}
~~~

### 2.2 调用栈保存了什么

每次尚未返回的函数调用都需要一个栈帧，通常包含参数、局部变量和返回位置。下面的深度优先过程会先不断压栈，再反向弹栈：

~~~text
visit(A)
  visit(B)
    visit(D)

调用栈顶部
┌─────────────┐
│ visit(D)    │
├─────────────┤
│ visit(B)    │
├─────────────┤
│ visit(A)    │
└─────────────┘
调用栈底部
~~~

递归的辅助空间取决于**最大同时未返回的调用数**，也就是递归深度，而不是总调用次数。一棵有百万节点但高度只有 20 的平衡树，递归深度约 20；一条只有五万节点的退化链，深度却是五万。

JavaScript 规范没有承诺所有运行时都执行尾调用优化。Node.js 和主流浏览器中的普通业务代码不能依赖“尾递归不会溢出”。深度来自外部输入时，应把栈深度视为安全边界。

## 3. 递归正确性的核心不变量

递归证明通常不是循环的“初始化—保持—终止”，而是数学归纳式的三步：

1. **基例正确**：最小问题返回正确答案。
2. **归纳假设**：假设所有更小的合法子问题都能正确返回。
3. **组合正确**：当前层的拆分覆盖全部输入、不重不漏，组合规则能从正确子结果推出当前正确结果。

例如对表达式树求值：

~~~text
        (*)
       /   \
     (+)    4
    /   \
   2     3
~~~

可以把递归契约写成：

> <code>evaluate(node)</code> 返回以 <code>node</code> 为根的完整子表达式值；返回前不会遗漏任何后代，也不会读取子树外的节点。

只要叶子返回其数值，二元运算节点先正确求出左右子树，再按当前运算符合并，整个树就正确。

生产代码还要增加资源不变量，例如：

- 每下降一层，剩余深度预算减一；
- 每访问一个节点，剩余节点预算减一；
- 当前路径集合包含所有“已进入但尚未退出”的对象；
- 一旦对象再次出现在当前路径上，就构成引用环。

这些不变量把“算法正确”扩展为“面对恶意或损坏输入也能有界失败”。

## 4. 分治：拆分、求解、合并

### 4.1 分治与普通递归的区别

递归是一种表达方式；分治是一种问题结构。典型分治包含：

1. 把规模为 <code>n</code> 的问题拆成若干更小、相互独立或弱相关的子问题；
2. 求解子问题；
3. 在线性或更低成本下合并结果。

归并排序的结构是：

~~~text
[8 3 6 2 7 1 5 4]
       /       \
[8 3 6 2]   [7 1 5 4]
   /  \         /  \
[8 3][6 2]   [7 1][5 4]
       ... 子区间排序 ...
[2 3 6 8] + [1 4 5 7]
          合并
[1 2 3 4 5 6 7 8]
~~~

若每层拆成两个规模约为一半的子问题，合并成本为 <code>Θ(n)</code>：

~~~text
T(n) = 2T(n/2) + Θ(n)
~~~

递归树第 0 层处理 <code>n</code> 个元素；第 1 层两个子问题各处理 <code>n/2</code>，总量仍为 <code>n</code>；一共有约 <code>log₂n</code> 层，所以总时间为 <code>Θ(n log n)</code>。

### 4.2 分治最容易隐藏的成本

下面的写法在每一层使用 <code>slice()</code>：

~~~ts
const left = values.slice(0, middle);
const right = values.slice(middle);
~~~

渐进时间仍可能是 <code>O(n log n)</code>，但会创建许多短命数组。实际系统中应考虑：

- 用下标区间代替复制；
- 复用一个辅助缓冲区；
- 数据过大时按块处理，而不是一次全部装入内存；
- 先用 profiler 确认分配和 GC 是真实瓶颈。

分治也不适合有大量重叠子问题的场景。若同一子问题被重复计算，可能需要记忆化或动态规划，而不是继续展开递归树。

## 5. 如何把递归机械地改成显式栈

### 5.1 只有“进入动作”的前序遍历

若递归函数在访问子节点之前就完成当前节点工作，可以用一个节点栈：

~~~ts
interface Node {
  readonly id: string;
  readonly children: readonly Node[];
}

function preorder(root: Node): string[] {
  const result: string[] = [];
  const stack: Node[] = [root];

  while (stack.length > 0) {
    const node = stack.pop();
    if (node === undefined) break;
    result.push(node.id);

    for (let index = node.children.length - 1; index >= 0; index -= 1) {
      stack.push(node.children[index]);
    }
  }

  return result;
}
~~~

必须逆序压入子节点，因为栈是后进先出。若希望输出左到右顺序，就先压右孩子。

### 5.2 同时需要“进入”和“退出”的后序计算

表达式求值、目录大小汇总和树形删除常常要等子节点处理完，才能完成父节点。此时显式栈帧必须记录程序执行到哪一阶段：

~~~text
Frame = {
  node,
  phase: "enter" | "exit"
}

弹出 enter(A):
  压入 exit(A)
  再逆序压入各子节点的 enter

弹出 exit(A):
  所有子节点结果都已存在
  可以汇总 A
~~~

这实际上是在手工保存原本由 JavaScript 调用栈保存的“返回位置”。

### 5.3 更一般的帧：保存局部状态

若递归函数需要短路或逐个处理孩子，帧可以保存：

~~~ts
interface Frame {
  readonly node: Node;
  nextChildIndex: number;
  partialResult: number;
}
~~~

迭代化不是把代码里的 <code>recursiveCall()</code> 换成 <code>stack.push()</code> 就结束了，而是要识别每次递归调用前后有哪些局部状态需要保留。

## 6. 环、共享子树与“访问过”的语义

JavaScript 对象可以形成环，即使类型名叫 <code>TreeNode</code> 也不代表运行时一定是树。

~~~text
A -> B -> C
     ^    |
     └────┘
~~~

常见的两个集合语义不同：

- <code>active</code>：当前递归路径上已进入未退出的对象。再次遇到说明存在环。
- <code>visited</code>：整个遍历过程中曾处理过的对象。再次遇到可能是共享子树，也可能是环。

如果合法输入允许两个父节点引用同一个只读子对象，使用全局 <code>visited</code> 并直接报错会误判。若业务要求每个节点只能有一个父节点，则全局重复本来就应被拒绝。算法必须根据数据契约选择，而不是照抄一个 <code>Set</code>。

对于显式 enter/exit 帧：

1. 处理 enter 时把对象加入 <code>active</code>；
2. 处理 exit 时从 <code>active</code> 删除；
3. 处理孩子 enter 前若已在 <code>active</code>，报告当前路径上的环。

## 7. 迭代化没有自动解决事件循环阻塞

把十万层递归改成 <code>while</code> 可以避免调用栈溢出，但十万或千万次同步循环仍可能阻塞浏览器主线程或 Node.js 事件循环。

生产上还要选择：

- 每处理固定数量节点后主动让出执行权；
- 使用异步生成器提供背压，让消费者按需拉取；
- 使用 <code>AbortSignal</code> 支持取消；
- CPU 密集任务移到 Web Worker 或 Node <code>worker_threads</code>；
- 对最大节点数、最大深度和单批耗时设置预算。

注意，<code>await Promise.resolve()</code> 只让出到微任务队列，持续排入微任务仍可能推迟计时器和 I/O。需要真正让出一个事件循环阶段时，在 Node.js 可使用 <code>setImmediate</code>，浏览器可用合适的调度 API。具体方案应基于运行环境，不要在通用库中偷偷绑定某个平台。

## 8. TypeScript / JavaScript 特有陷阱

### 8.1 类型不能阻止运行时环

<code>readonly children: readonly Node[]</code> 只限制通过该引用修改，无法证明对象无环，也无法验证来自 JSON/API 的输入。边界数据仍需运行时校验和预算。

### 8.2 避免在深递归里使用展开运算符

~~~ts
return [node.id, ...flatten(node.children)];
~~~

这种写法会反复复制数组，可能把线性遍历变成平方级复制，并制造大量临时对象。更稳妥的是把结果写入共享输出缓冲区，或通过迭代器逐个产出。

### 8.3 对象身份与业务 ID 不是同一件事

<code>Set<object></code> 按引用身份判断。两个内容相同但不同引用的节点不相等；两个 ID 相同的对象也不相等。检测对象引用环用身份集合，检测业务主键重复用 <code>Set&lt;string&gt;</code>，两者不能混淆。

### 8.4 数值递归可能静默失真

表达式、前缀和或计数超过安全整数后，TypeScript 的 <code>number</code> 类型不会发出运行时警告。需要按业务约定校验 <code>Number.isSafeInteger</code>，或设计 <code>bigint</code> 版本。

### 8.5 异步递归会同时保留 Promise 链

把每层写成 <code>await visit(child)</code> 不代表栈和内存完全免费。大量未完成 Promise、闭包和中间结果仍可能占用内存。更重要的是，无限制地 <code>Promise.all(children.map(...))</code> 会形成并发风暴。

## 9. 常见错误

- 没有证明问题规模严格缩小，导致无限递归。
- 基例只覆盖“正常最小值”，没有覆盖空区间或非法输入。
- 混用闭区间与半开区间，拆分后遗漏中点。
- 只计算总调用次数，忽略最大深度和栈空间。
- 迭代化时忘记保存“返回后继续做什么”的阶段。
- 用一个全局 visited 集合同时承担环检测和去重，改变合法共享结构的语义。
- 遍历外部输入时没有最大深度、最大节点数和取消机制。
- 以为改成 while 循环就不会阻塞事件循环。
- 在递归层层使用 slice、concat 或展开运算符，隐藏大量复制。

## 10. 什么时候不要使用递归或自行分治

- 深度不受信任且运行时没有可靠栈保证时，优先显式栈。
- 线性扫描已经足够清楚且满足预算时，不要为了“算法感”强行分治。
- 子问题高度重叠时，考虑动态规划、记忆化或重新建模。
- 数据放不进内存时，使用流式/外部算法；递归拆数组不会创造更多内存。
- 并行分治只有在任务足够大、合并成本可控、运行环境支持且测量证明有收益时才值得。
- 标准库或成熟解析器已有安全实现时，不要重新实现安全敏感的表达式解析与执行。
