# 第 10 章：堆、优先队列与过期调度

## 1. 生产问题：不断变化的数据里只关心“下一个”

延时任务需要找最早 deadline；监控系统只保留 Top-K；多路有序日志要反复取当前最小项；调度器要取最高优先级任务。每次把整个数组重新排序需要 O(n log n)，而我们通常只关心一个极值。

**优先队列**是抽象接口：插入元素、查看/移除最高优先级元素。**二叉堆**是常见实现：插入和删除极值 O(log n)，查看极值 O(1)，无需维护全部有序。

本章目标：

- 从完全二叉树推导数组下标；
- 写出 heap order invariant 与 sift-up/sift-down；
- 理解 heapify 为什么 O(n) 而不是 O(n log n)；
- 通过序号实现稳定优先级；
- 用 lazy invalidation 支持取消/重排；
- 只用一个底层 timer 调度大量过期项，并处理批量上限、时钟和错误隔离。

## 2. 完全二叉树与数组表示

完全二叉树除了最后一层都填满，最后一层从左到右填。它不需要节点指针，可紧凑存在数组：

```text
数组:      0   1   2   3   4   5
值:       [2,  5,  7,  9,  6,  8]

            2(0)
          /      \
       5(1)      7(2)
      /   \      /
    9(3) 6(4)  8(5)
```

下标 `i`：

```text
parent = floor((i-1)/2)     i>0
left   = 2*i+1
right  = 2*i+2
```

最小堆不变量：对每个非根节点，`parent <= child`（按 comparator）。它只保证祖先不大于后代，不保证兄弟或整数组排序。数组 `[2,5,7,9,6,8]` 是堆，但遍历顺序不是有序序列。

## 3. push：只有一条祖先链可能坏

新元素放数组末尾，完全树形状仍正确。旧节点间堆序未变，唯一可能违规的是新节点与父节点：

```text
append 1:
            2
          /   \
         5     7
        / \   / \
       9  6  8   1  <- 可能违规
```

若新元素优先级高于父，交换并继续向上，称 sift-up。循环不变量：除当前 index 与 parent 这条边外，整个数组满足堆序；交换后可能违规只向上一层移动。树高 O(log n)，所以 push O(log n)。

## 4. pop：用末项补根再下沉

删除根会留下洞。把最后一项放到根并缩短数组，形状恢复；可能违规只在根向下的一条路径。

每次比较左右孩子，选择优先级更高（最小堆中更小）的那个；若 replacement 已不大于该孩子，停止，否则把孩子上移，继续下沉。

为什么不能随便选左孩子？右孩子可能更小。若让 replacement 与左交换，却仍大于右孩子，堆序依然坏。

可减少赋值：不必每层真的 swap replacement，先把较优孩子搬到父位置，最后一次把 replacement 写入最终洞。

## 5. heapify 为什么是 O(n)

把任意数组变成堆：叶节点本身已经是堆，从最后一个非叶 `floor(n/2)-1` 向前对每项 sift-down。

粗略说 n 个节点每个 O(log n) 得 O(n log n)，但这个上界太松。接近一半节点是高度 0 的叶，不做工作；约四分之一高度 1；约八分之一高度 2：

```text
n/4 * 1 + n/8 * 2 + n/16 * 3 + ... = O(n)
```

因此 bottom-up heapify O(n)。逐项 push 构建则 O(n log n) 上界。二者最终都得到合法堆，但数组形态不必相同。

## 6. comparator 与稳定性

通用堆约定 `compare(a,b)<0` 表示 a 应先出队。优先级相等时，普通堆不保证 FIFO。生产调度可装饰：

```ts
interface StableEntry<T> {
  readonly value: T;
  readonly priority: number;
  readonly sequence: number;
}

compare = (a,b) => a.priority-b.priority || a.sequence-b.sequence
```

sequence 必须单调、安全整数并处理溢出。分布式系统中每进程 sequence 不能自动形成全局顺序，需要另一个一致排序键。

比较器必须一致。若比较结果依赖当前时间、外部可变优先级或随机数，元素入堆后父子关系可能悄悄失效。可变优先级应显式 update/decrease-key，或插入新版本并把旧版本标 stale。

## 7. 取消与 lazy invalidation

只持有业务 handle 时，要在堆中找任意元素并删除，扫描 O(n)。两类方案：

1. handle 保存 heap index；每次 swap 同步更新 index，可 O(log n) 删除，但封装和一致性更复杂。
2. lazy invalidation：取消/重排时改变 handle 的 generation/active，再推入新 entry；旧 entry 留在堆里，来到堆顶时丢弃。

lazy 让操作简单，但 stale entry 会占内存。必须监控 `heapSize/activeCount`，超过阈值从活跃 handle O(n) 重建堆，而不是让长期 reschedule 无限增长。

## 8. 一个 timer 管理十万过期项

为每个租约创建 setTimeout 会产生大量运行时对象，取消/恢复也难统一。可维护按 deadline 的最小堆，并始终只为最早有效项设置一个 timer：

```text
schedule/cancel/reschedule -> 清理 stale top -> 为 earliest 设置 timer
timer fire -> 取出所有 deadline<=now（但每批有限）-> 再 arm
```

必须处理：

- deadline 已过：delay=0，但仍异步执行；
- 平台 timer 最大 delay：用 `min(deadline-now,maxDelay)`，长等待分段唤醒；
- 相同 deadline：sequence 保证 FIFO；
- 一次到期十万项：设置 `maxBatch`，处理一批后 0-delay 再续，避免长任务；
- callback 抛错：隔离并报告，不能中断整个队列；
- wall clock 前后跳：每次 fire 重新读取 now；更适合持续时长的场景可使用单调时钟；
- cancel/reschedule 的旧 entry：generation 校验；
- 频繁重排：定期 heap rebuild。

## 9. 正确性不变量

BinaryHeap：

1. data 表示完全二叉树；
2. 对每个 i>0，`compare(parent,i)<=0`；
3. size 等于数组长度；
4. pop 返回调用前 comparator 最小的元素。

ExpirationQueue：

1. 每个 active handle 恰有一个“当前 generation/deadline/sequence”；堆可有多个旧 entry；
2. entry 只有同时满足 owner、active、generation、deadline 才有效；
3. 底层最多一个已登记 timer；
4. timer 目标是当前最早有效 deadline，或因 maxDelay 分段而更早唤醒；
5. 每个 handle 至多成功 cancel/expire 一次。

## 10. 复杂度

| 操作 | 时间 | 备注 |
|---|---:|---|
| peek | O(1) | 清 stale 时可能摊入维护成本 |
| push/pop | O(log n) | n 为堆 entry 数 |
| heapify | O(n) | bottom-up |
| Top-K 扫描 | O(n log k) | 维护大小 k 的堆 |
| lazy cancel | 常见 O(1) + 重新 arm | stale 以后清理 |
| reschedule | O(log n) | 推新版本 |
| rebuild | O(a) | a 为 active 数，摊还触发 |

在过期队列中 n 可能大于 active，因为 stale 未清。监控两者比值是容量工程的一部分。

## 11. TypeScript/JavaScript 陷阱

- Node 与浏览器 setTimeout token 类型不同，库接口可注入 scheduler 或使用 ReturnType<typeof setTimeout>。
- `setTimeout` 不保证精确时刻，只保证不早于语义近似；主线程阻塞会延后。
- `Date.now()` 可能跳变；`performance.now()` 单调但不是 epoch，deadline 单位要统一。
- callback 可能重入 schedule/cancel；内部 firing 标志要防止 timer 状态互相覆盖。
- CPU 密集 onExpire 不应直接在 timer 回调完成，maxBatch 也无法拯救单个超重 callback。

## 12. 测试

堆随机执行 push/pop，与每次排序取最小的慢 oracle 比较；每步扫描所有 parent/child 检查 invariant。测试重复值、逆序、有序、常量 comparator。

过期队列注入 fake clock/scheduler，手动推进时间，不用真实 sleep。断言底层活跃 timer 数<=1；覆盖同 deadline FIFO、cancel、连续 reschedule、时钟后跳、超长 delay 分段、callback 抛错、callback 内 schedule、批次上限与 rebuild。

## 13. 何时不用堆

- 数据一次性排序并全部按序消费：直接稳定排序更简单。
- 需要任意区间查询/有序遍历：平衡树或排序数组更合适。
- 跨进程可靠延时任务：使用持久调度/消息系统；内存堆进程崩溃即丢。
- 优先级会随时间连续变化且无法版本化：需重新建模，堆不会自动感知。
