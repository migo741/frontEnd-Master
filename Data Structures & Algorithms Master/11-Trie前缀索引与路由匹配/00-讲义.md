# 第 11 章：Trie 前缀索引与路由匹配

> 学习顺序：先读讲义，再完成 `01-练习` 的两题，最后用 `02-答案` 复盘。主语言为 strict TypeScript；本章讨论的是内存索引，不把它包装成数据库或搜索引擎的替代品。

## 1. 为什么“前缀”值得拥有专门的数据结构

假设命令面板中有 10 万个命令。用户每输入一个字符，都执行：

```ts
commands.filter((command) => command.startsWith(prefix));
```

若命令总数为 `n`，平均文本长度为 `L`，一次查询最坏要检查 `Θ(nL)` 个字符。数据很小、查询很少时，这正是最简单可靠的方案；但当同一份相对稳定的数据要接受大量前缀查询时，可以把重复比较提前到建索引阶段。

Trie（发音接近 “try”，也叫前缀树）把一个 key 拆成 token，并让有相同前缀的 key 共享路径：

```text
插入 car、card、cat、do

(root)
├─ c
│  └─ a
│     ├─ r  ✓ car
│     │  └─ d  ✓ card
│     └─ t  ✓ cat
└─ d
   └─ o  ✓ do
```

节点上的 `✓` 很重要：`car` 是完整 key，同时又是 `card` 的前缀。只看“节点有没有孩子”无法判断一个 key 是否存在，因此节点必须保存终止标记或完整记录。

Trie 特别适合：

- 字典前缀、命令面板、联系人首字母索引；
- 路由表的路径段匹配；
- IP 前缀、自动补全和敏感词规则的基础模型。

它不天然适合任意子串、模糊编辑距离、按相关性全文检索。那些问题需要倒排索引、后缀结构、n-gram 或专门搜索服务。

## 2. 表示、token 与核心不变量

最直接的节点表示是：

```ts
interface TrieNode {
  terminal: boolean;
  children: Map<string, TrieNode>;
}
```

这里的一个边 token 可以是字节、UTF-16 code unit、Unicode code point、用户可见 grapheme，或 URL path segment。算法不变，语义和成本会改变。本章普通文本 Trie 使用 Unicode code point；路由 Trie 使用 path segment。

核心不变量：

1. 从根到任一节点的边标签拼接，唯一表示一个前缀。
2. 某 key 存在，当且仅当它对应路径存在且末节点 `terminal === true`。
3. 不属于任何已保存 key 前缀的节点可以被删除；仍被其他 key 使用的共享节点不能删除。

若 key 被拆成 `m` 个 token，在常见 `Map` 实现的期望访问成本下：

- 插入：`O(m)`；
- 精确查询：`O(m)`；
- 删除：找到路径 `O(m)`，向上剪枝最多 `O(m)`；
- 枚举此前缀下的 `k` 个结果：至少要输出 `k` 个结果，成本不能小于 `Ω(k)`。

空间更接近“所有不同前缀节点的数量”，上界是所有 key token 数之和。大量短 key 或共享前缀多时效果好；随机长 ID 几乎没有共享，节点、Map 和对象分配反而可能比保存字符串数组昂贵得多。

## 3. 插入、查询和删除为何正确

### 3.1 插入

从根开始，对每个 token：已有边就复用，没有就创建。处理完最后一个 token 后标记终止。

```text
插入 card，已有 car：
root -> c -> a -> r(terminal=true) -> 新建 d(terminal=true)
```

插入不会破坏旧 key，因为它只复用或增加边，不会清除旧终止标记。

### 3.2 精确查询与前缀查询不同

查询 `has("ca")` 时虽然路径存在，但 `a` 节点没有终止标记，所以结果为 false。`startsWith("ca")` 只关心路径，结果为 true。API 必须把这两种问题分开。

### 3.3 删除必须从叶子向上剪枝

删除 `car` 时：

```text
car、card 都存在：只清除 r 的 terminal，不能删除 r，因为它还有 d 子节点。
car 独自存在：清除 terminal 后，r/a/c 若都不再被使用，可以逐层删除。
```

一个节点只有同时满足“不是其他 key 的终点”且“没有孩子”时才可从父节点删除。用插入时记录的 `(parent, token, child)` 路径反向检查，可以避免递归栈。

## 4. 自动补全不只是一棵 Trie

找到前缀节点只解决“候选在哪”。真实自动补全还要回答：

- 按词典序、使用频率、最近使用还是个性化得分排序？
- 热度改变后，是否更新每个祖先节点缓存的 Top K？
- 是否允许拼写错误、拼音、首字母和任意子串？
- 用户输入是否需要大小写折叠、重音折叠或语言相关分词？

基础实现可以从前缀节点做 DFS，收集前 `limit` 个词。若每次都要按热度扫描巨大子树，前缀定位虽是 `O(m)`，后续枚举仍可能很贵。高频查询可在节点缓存 Top K，但代价是写入和热度更新要沿祖先路径维护缓存。

这揭示一个通用原则：索引优化的是特定查询形状，同时把成本转移到内存和更新路径。写多读少时，最简单的数组扫描可能更合适。

## 5. Unicode：相同外观不一定是相同序列

JavaScript 字符串按 UTF-16 保存。`text.length` 统计 code unit；`[...text]` 按 code point 迭代；用户看到的一个字符仍可能由多个 code point 组成。

例如某些带重音字符既可表示为一个预组字符，也可表示为基础字符加组合音标。若产品认为两者相同，应先采用明确规范化策略，例如 NFC：

```ts
const normalized = input.normalize("NFC");
const tokens = [...normalized];
```

大小写折叠也不能随手 `toLowerCase()` 后宣称适用于所有语言。索引的规范化函数必须成为构造参数或稳定契约，并在插入与查询时使用完全相同的逻辑。更改规范化规则相当于更改索引 schema，通常需要重建。

## 6. 压缩 Trie 与 Radix Tree

普通 Trie 每条边只存一个 token，单分支链会产生很多节点：

```text
t -> r -> a -> n -> s -> a -> c -> t -> i -> o -> n
```

Radix Tree（压缩前缀树）把没有分叉的连续 token 合并成一条边，例如 `transaction`。查找时不只比较一个 token，而是比较边标签的最长公共前缀；插入可能把一条边拆成两段。

压缩能减少节点和指针，但实现、更新和 Unicode 边界更复杂。除非 profile 证明节点开销是主要问题，不应只因为“高级”就从普通 Trie 起步。

## 7. 路由为什么也可以看成 Trie

HTTP 路由不是按字符，而是按 path segment 建树：

```text
/users/new
/users/:id
/assets/*path

root
└─ users
   ├─ static "new" -> route A
   └─ param :id    -> route B
└─ assets
   └─ wildcard *path -> route C
```

常见优先级是：

```text
静态 segment > 参数 segment > 通配 segment
```

于是 `/users/new` 应命中静态路由，而不是把 `new` 当成 `id`。

但“每层看见静态就永远选静态”仍可能错误：

```text
已注册 /a/c
已注册 /:name/b
请求     /a/b
```

第一层静态 `/a` 更具体，但它的下一层 `/c` 失败；参数分支 `/:name/b` 却能完整匹配。因此匹配过程要按优先级探索候选，并允许高优先分支整体失败后回退。真正的决定条件是“能完整消费路径并到达一个终止路由”，不是局部某一步更具体。

## 8. RouterIndex 的结构与冲突规则

一个路由节点可以包含：

- 多个静态孩子：`Map<segment, Node>`；
- 至多一个参数孩子；
- 至多一个终止通配路由；
- 当前节点上的终止路由。

为了让行为可审计，本课程采用偏严格契约：同一位置若已有 `:id` 参数，不允许再注册名字不同的 `:name` 参数。很多框架可以保存每条路由自己的参数名，但严格拒绝能让教学实现避免“共享结构究竟用哪个参数名”的歧义。生产框架可以选择更灵活的表示，关键是契约必须明确。

注册时至少拒绝：

- 完全重复的 pattern；
- 同一结构位置的不同参数名冲突；
- 通配符不在最后一个 segment；
- 空参数名、重复参数名；
- 含 query/hash 的 pattern；
- 超过长度或 segment 数上限的 pattern。

冲突不能靠“最后注册覆盖”悄悄解决，否则模块加载顺序会改变线上行为。

## 9. 路径解析是安全边界

路由算法经常在规范化上出错：

1. 应先按原始 `/` 切分，再对每个 segment 做百分号解码。
2. 解码失败应返回明确的 bad request，不应把坏编码当普通文本。
3. 若单个 segment 解码出 `/`（例如 `%2F`），本课程选择拒绝，避免编码字符改变路径层级。
4. 是否区分大小写、是否把尾斜杠视为相同，都必须写入契约。
5. `.`、`..`、重复斜杠及超长 path 要在边界层处理，不能把文件系统规范化规则随意套给 URL。

此外，路由匹配只回答“哪个处理器与哪些参数”，不负责认证和资源授权。`/tenants/:tenantId` 匹配成功绝不表示当前用户有权访问该 tenant。

## 10. 正确性与复杂度

普通 Trie 的正确性来自路径唯一性和终止标记。路由 Trie 还需要如下不变量：

- 每个静态 token 在同一节点至多一条边；
- 参数与通配结构满足注册约束；
- 匹配状态由“当前节点、待消费下标、已捕获参数”完整描述；
- 只有消费完全部 segment 且节点有终止路由，或合法通配路由消费剩余 segment，才算成功。

若路径有 `s` 个 segment，静态查找本身期望为 `O(s)`。存在静态/参数回退时，最坏会探索多个候选；本课程用最大 segment 数限制搜索深度。通用路由器还可能预编译、按 method/host 分层或使用 radix tree，不能从教学实现直接推断框架性能。

## 11. 何时不用 Trie

- 数据只有几十条，简单扫描更易读且已满足预算。
- 需求是任意子串或语言学全文检索。
- 数据主要在数据库，拉到进程内建索引会破坏一致性和分页。
- key 几乎都是随机长 ID，前缀共享很少。
- 更新频繁且每节点维护复杂排名，写放大不可接受。
- 你真正需要的是经过审计、支持 method/host/middleware 的成熟路由框架。
