# 第 19 章：生产数据结构与近似算法

## 1. 生产动机：有限内存里不可能什么都精确保存

缓存希望保留最有用数据；去重希望记住海量 ID；监控希望从无限事件流保留代表样本。若输入持续增长，精确保存全部历史的空间必然持续增长。生产算法必须先承认资源有限，再选择：淘汰、过期、近似、采样或下沉到持久存储。

本章连接四类结构：

- LRU：在容量满时淘汰最久未使用项；
- TTL：时间到后数据失效；
- Bloom filter：用固定 bit 空间回答“可能存在/一定不存在”；
- reservoir sampling：流长度未知时保留固定 k 个均匀样本。

目标不是把它们都塞进一个万能类，而是理解每种结构优化的维度、错误边界与组合代价。

## 2. LRU = Hash Map + 双向链表

LRUCache 需要：

- `get(key)` 快速定位：Map；
- 命中后把任意节点移到最近端：双向链表；
- 容量满时删除最久端：tail；
- set/update：Map 和链表同步。

```text
MRU/head                                LRU/tail
   A <-> C <-> B <-> D

get(B): 摘下 B，移到 head
   B <-> A <-> C <-> D
```

不变量：Map 中每个 key 恰对应链表一个 linked node；链表每节点都能在 Map 找到同一引用；head 最近期、tail 最久未使用；size 同步。

在常见 Map 成本假设下，get/set/delete/move 都是期望 O(1)。仅用 Map 的插入顺序也可做简化 LRU（delete 再 set），但节点/迭代语义、更新和实现常数要实际测量；手写版本训练组合不变量。

## 3. “容量”可以是条数，也可以是重量

1000 个 1KB 对象与 1000 个 20MB 对象完全不同。生产缓存常用 `weightOf(value)` 与 `maxWeight`。一项大于总预算时必须拒绝；set 新项后从 tail 连续淘汰直到总重量合规。

加权 LRU 仍只是启发式：大项可能因为一次访问占据大量空间，扫描式请求可能把热点逐出。可选 LFU、TinyLFU、分段 LRU 等，但复杂策略必须用命中率/延迟/内存证据选择。

## 4. TTL 与 LRU 是两个不同顺序

LRU 按“最近访问时间”排序，TTL 按“到期时刻”排序。同一个链表无法同时让 tail 是最久未用且堆顶是最早过期。

组合方案：

- Map + LRU 双链；
- 最小堆按 expiresAt 保存 expiration entry；
- node 保存 generation；update TTL 时推新 entry，旧 entry lazy stale；
- 每次公共操作先 purge heap 中 `expiresAt<=now` 的当前 entry；
- stale 过多时从 Map 活跃节点重建 heap。

这会把带过期清理的操作成本提高到与 heap pop/push 相关。不要继续宣称“所有操作 O(1)”。若只在 get 时懒检查某 key，操作可简单，但从未访问的过期项会占容量；这是另一份明确契约。

TTL 的时钟也要定义。绝对过期常用 wall clock，可能跳变；进程内持续时长适合单调 clock。测试注入 fake clock，不能 sleep。

## 5. 缓存不是事实来源

- miss 不等于数据不存在；
- stale value 可能不再满足权限/版本；
- 缓存 key 必须含 tenant、locale、权限/版本等语义维度；
- 更新数据库与失效缓存的顺序会产生一致性窗口；
- 单进程 LRU 不提供多实例一致性；
- 缓存穿透、击穿、污染需要 singleflight、negative cache、频率过滤等策略。

本章结构优化性能，不能改变业务正确性的真相来源。

## 6. Bloom filter：一定位不存在，或可能存在

Bloom filter 是 m 个 bit 和 k 个 hash 位置。插入 key 时把 k 位设 1；查询时：

- 任一位为 0：key 一定没被插入（在实现正确且未重置的前提下）；
- 全为 1：key 可能插入过，也可能是其他 key 的位碰撞，存在 false positive。

```text
bits: 0 1 0 1 1 0 1 0
key X -> positions 1,3,6 全为1 -> probably present
key Y -> positions 1,5,6，5为0 -> definitely absent
```

标准 Bloom 没有 false negative，但有前提：相同规范化 key、相同 hash/参数、bit 未清除、没有错误并发写。标准 Bloom 不能直接删除：清一个 bit 可能删掉其他 key 共享的信息；需要 counting Bloom 等变体。

## 7. 容量与误报率必须算

预期插入 n、目标误报 p：

```text
m ≈ -n ln(p) / (ln 2)^2       bits
k ≈ (m/n) ln 2               hash count
```

例如 n=1,000,000，p=1%，m 约 9.6 million bits（约 1.2MB），k 约 7。若实际插入远超 n，bit 越来越接近全 1，误报率恶化。因此结构必须暴露 saturation/insert count，到容量后 rotate/rebuild，而不是永久相信最初 p。

理论公式假设近似独立均匀 hash。教学用双哈希不抗恶意输入；攻击者可构造碰撞/长 key，生产需限制输入、选择成熟实现或密钥化哈希。

Bloom 适合作为昂贵精确查询前的负向过滤：

```text
Bloom says absent -> 可跳过精确 store（前提 filter 与 store 同步且无 false negative）
Bloom says present -> 必须查数据库/精确 Set 才能做不可误拒的决定
```

若直接拒绝“probably present”，业务必须接受把部分新事件误判重复。

## 8. Reservoir Sampling：未知长度流的均匀 k 样本

算法 R：

1. 前 k 项全部进入 reservoir；
2. 第 t 项（1-based，t>k）生成均匀整数 j∈[0,t)；
3. 若 j<k，用当前项替换 reservoir[j]，否则忽略。

为什么最终每项被选概率 k/n？

- 新的第 t 项进入概率 k/t；
- 一个旧样本在第 t 步不被替换概率 `1 - (k/t)*(1/k) = (t-1)/t`；
- 归纳：处理 t-1 项后旧项在样本概率 k/(t-1)，乘 (t-1)/t 得 k/t。

空间 O(k)，每项 O(1)。随机源必须返回 `[0,1)`；测试注入 seeded RNG。普通 reservoir 对“每个事件”等权，不自动保证每租户/类别比例；需要分层采样或加权 reservoir。

## 9. 组合近似结构时要传递误差语义

若先用 Bloom 把 probably-duplicate 丢弃，再对 admitted 流 reservoir sampling，样本只对“admitted 流”均匀，不对原始真实唯一事件均匀，因为 false positive 已引入选择偏差。文档必须说明样本总体是什么。

近似结构 API 不应返回 `boolean exists` 这种过度承诺，使用 `definitelyAbsent/probablyPresent`。监控误报需要抽样查询精确 store；结构升级/参数变化要版本化。

## 10. 复杂度

| 结构 | 时间 | 空间 | 误差/边界 |
|---|---:|---:|---|
| LRU | 期望 O(1) | O(capacity) | 启发式淘汰 |
| LRU+expiry heap | 常见 O(log n) 维护 | O(n+stale) | lazy 清理/重建 |
| Bloom | O(k) | O(m bits) | false positive |
| Reservoir | O(1)/item | O(k) | 对处理流均匀 |

## 11. 测试与度量

LRU 用慢 oracle（为每项记录 lastAccess counter）随机差分；fake clock 覆盖边界 `expiresAt===now`、更新 generation、过期非 tail、容量淘汰与 stale heap rebuild。

Bloom 做确定性性质：插入项绝不能报告 absent；空 filter 全 absent；同 seed/参数位图确定。误报率只能作统计测试且留容差，不应写成永不抖动的精确断言。Reservoir 用固定 RNG 检查步骤，用大量重复实验检查频率近似均匀，但统计测试要设置合理容差。
