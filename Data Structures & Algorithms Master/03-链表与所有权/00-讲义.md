# 第 03 章：链表与所有权

> 链表的难点不在 `next`，而在“哪些引用仍然有效、谁允许修改节点、结构变化后哪些关系必须同时更新”。

## 1. 生产动机

JavaScript 开发中数组通常比链表更常用：数组迭代缓存友好、标准库丰富、引擎优化成熟。但以下场景仍会出现链式结构：

- LRU 缓存需要 `O(1)` 地把任意条目移动到队首。
- 调度器需要通过稳定句柄取消队列中间的任务。
- 编辑器、历史记录和内存池维护可插拔节点。
- React/Vue 运行时、解析器和编译器内部会使用链式工作单元或父子引用。
- 图、树、邻接关系本质上也是对象引用组成的结构。

链表章节真正训练的是引用推理。链表 bug 常表现为：节点丢失、重复挂载、形成环、长度错误、跨容器误删，或因遗留引用导致内存无法释放。

## 2. 术语与节点模型

### 2.1 单向链表

```ts
export interface ListNode<T> {
  value: T;
  next: ListNode<T> | null;
}
```

```text
head
 |
 v
[A|•] -> [B|•] -> [C|null]
```

- head：第一个节点引用，空表为 `null`。
- tail：最后一个节点，满足 `tail.next === null`。
- successor：`node.next` 指向的后继。
- 节点身份：两个节点即使 `value` 相同，只要对象引用不同，就不是同一节点。

### 2.2 双向链表

```ts
interface DoublyNode<T> {
  value: T;
  prev: DoublyNode<T> | null;
  next: DoublyNode<T> | null;
}
```

```text
null <- [A] <-> [B] <-> [C] -> null
         ^                 ^
        head              tail
```

双向链表可在已知节点引用时 `O(1)` 删除，但代价是每次修改必须同时维护前后两个方向。

### 2.3 哨兵节点

哨兵（dummy/sentinel）是不代表真实业务数据的辅助节点，用于统一“删除头节点”和“删除中间节点”等边界：

```text
[dummy] -> [real 1] -> [real 2]
```

它能减少分支，但如果用 `null as unknown as T` 伪造泛型值，会破坏类型可信度。更安全的做法是定义专门的内部节点类型，或用局部结构只读取 `next`。

## 3. 成本模型

| 操作 | 单向链表 | 双向链表 | 普通数组 |
| --- | --- | --- | --- |
| 已知头/尾插入 | `O(1)`（需维护 tail） | `O(1)` | 尾部摊还 `O(1)` |
| 已知节点后插入 | `O(1)` | `O(1)` | 中间 `O(n)` |
| 已知节点删除 | 仍需前驱，通常 `O(n)` | `O(1)` | 中间 `O(n)` |
| 按下标访问 | `O(n)` | `O(n)` | `O(1)` |
| 搜索值 | `O(n)` | `O(n)` | `O(n)` |
| 内存局部性 | 较差 | 较差 | 较好 |

“链表删除是 `O(1)`”有前提：你已经拥有目标节点以及修改所需的前驱/双向链接。若先按值搜索，完整操作仍是 `O(n)`。

## 4. 所有权、别名与 mutation

### 4.1 JavaScript 没有编译期所有权系统

多个变量可以指向同一节点：

```ts
const a = node;
const b = node;
a.next = null;
// b.next 也变成 null，因为 a 与 b 是同一对象的别名。
```

TypeScript 的 `readonly` 主要约束当前静态视图，不会自动深冻结对象，更不会证明“只有我持有该节点”。因此链表 API 必须明确：

- 输入链是否由函数独占，可以原地改写？
- 函数返回的是新节点，还是复用原节点？
- 调用方保存的旧 head、tail 或中间节点引用在操作后是否仍有效？
- 一个节点能否同时属于两个容器？

### 4.2 独占所有权与借用

可用工程契约模拟：

- 独占转移：调用方把链交给函数，之后不再依赖旧链接关系。
- 只读借用：函数只遍历，不修改。
- 可变借用：函数暂时修改，但调用期间不能有其他并发修改者。
- 稳定句柄：调用方持有节点句柄，但只有所属容器能改内部链接。

这些不是 TypeScript 自动强制的语言规则，而是 API、私有字段、测试和代码评审共同维护的约束。

### 4.3 跨容器节点污染

如果一个双向节点被同时插入两条链，第二次写 `prev/next` 会悄悄破坏第一条链。生产容器通常为节点保存：

- `owner`：所属容器的私有 token。
- `linked`：当前是否仍挂载。

删除时先验证 owner 和 linked，避免跨队列误删与二次删除。

## 5. 逐步推导：原地反转单链表

目标：复用原有节点，把：

```text
A -> B -> C -> null
```

变成：

```text
null <- A <- B <- C
                  ^ new head
```

需要三个引用：

- `previous`：已经反转好的链头。
- `current`：当前待处理节点。
- `next`：在改写 `current.next` 前保存剩余链入口。

核心不变量：

```text
已反转前缀                 尚未处理后缀
null <- ... <- previous    current -> ... -> null
```

每轮：

```ts
const next = current.next; // 1. 先保存后缀，否则会丢链
current.next = previous;   // 2. 反转当前箭头
previous = current;        // 3. 扩大已反转区
current = next;            // 4. 进入剩余后缀
```

完整实现：

```ts
export function reverseInPlace<T>(
  head: ListNode<T> | null,
): ListNode<T> | null {
  let previous: ListNode<T> | null = null;
  let current = head;

  while (current !== null) {
    const next = current.next;
    current.next = previous;
    previous = current;
    current = next;
  }

  return previous;
}
```

初始化时已反转区为空；每轮把一个节点从未处理后缀转移到已反转前缀，节点不丢失、不复制。终止时后缀为空，`previous` 包含全部节点且方向正确。

时间 `O(n)`，辅助空间 `O(1)`。递归写法虽然简短，但需要 `O(n)` 调用栈且可能栈溢出。

## 6. 双向链表的结构不变量

一个可靠容器至少维持：

- 空表：`head === null`、`tail === null`、`size === 0`。
- 非空表：`head.prev === null`、`tail.next === null`。
- 对任意 `node.next !== null`，有 `node.next.prev === node`。
- 对任意 `node.prev !== null`，有 `node.prev.next === node`。
- 从 head 沿 next 恰好访问 `size` 个节点并到达 null。
- 所有挂载节点 owner 正确且 linked 为 true。

删除中间节点 `x`：

```text
before <-> x <-> after

before.next = after
after.prev  = before
x.prev = null
x.next = null
```

若 `before` 或 `after` 不存在，还要同步更新 head 或 tail。把这段操作集中在私有 `unlink()` 中，能避免每个公共方法各写一套不完整的边界逻辑。

## 7. 快慢指针与环

Floyd 判圈让 slow 每次走一步、fast 每次走两步。若存在环，fast 最终会在环内追上 slow；若 fast 到达 null，则无环。

```text
A -> B -> C -> D
          ^    |
          |____|
```

时间 `O(n)`、空间 `O(1)`。但要注意：

- 判圈只能告诉你是否有环；寻找入口还需第二阶段推导。
- 对外部可能并发修改的链，遍历期间结构不稳定，证明失效。
- 生产 API 更理想的是从所有权上禁止形成环，而不是每次操作后全链扫描。

## 8. GC 与资源释放

JavaScript 垃圾回收基于可达性。节点彼此形成环并不一定泄漏；只要整个环从 GC roots 不可达，就可以回收。真正危险的是：

- 全局 Map、监听器或定时器仍持有节点。
- 已取消任务的 handle 仍从长寿命容器可达。
- 删除节点后 owner、payload 或闭包引用没有按契约释放。

将已删除节点的 `prev/next` 置空有三点价值：便于调试、避免误复用、切断无必要的可达路径。但它不是替代正确生命周期管理的“GC 魔法”。若 payload 含文件句柄、订阅等外部资源，仍需显式 dispose。

## 9. TypeScript / JavaScript 陷阱

- 未开启 `strictNullChecks` 会让尾节点访问隐藏风险。
- TypeScript 是结构类型系统；两个容器的公开节点接口形状相同，不代表节点可以互换。
- `private` 字段是否为运行时私有取决于写法；`#field` 提供 JavaScript 运行时私有性。
- 递归打印长链可能栈溢出，调试辅助函数也应考虑迭代。
- 对节点做对象展开 `{ ...node }` 只浅复制一层，后续链仍共享。
- 值相等不等于节点身份相等，删除操作通常应基于句柄身份。

## 10. 常见错误

- 改写 `current.next` 前没有保存旧 next，导致剩余链丢失。
- 更新 `head` 忘记更新 `tail`，或反之。
- 删除节点只改一个方向，留下断裂的 prev/next 对称关系。
- size 在异常分支或重复取消时被多减一次。
- 同一个节点加入两个容器。
- 把已删除 handle 再次用于操作，造成结构污染。
- 为追求 `O(1)` 删除暴露可随意修改的公共节点字段，破坏封装。

## 11. 何时不用链表

- 需要大量按下标随机访问。
- 数据规模小，数组的简单性和局部性更重要。
- 只是普通 FIFO 队列，可先用数组加 head 指针，不必创建每项节点对象。
- 需要持久化、跨进程共享或数据库查询，进程内对象链接不合适。
- 删除并不频繁，维护 owner、prev、next 的复杂度收益不足。
