# 第 02 章：数组、字符串、双指针与滑动窗口

> 本章研究如何利用“连续、可索引、有顺序”的数据，把看似需要嵌套枚举的问题压缩为一次扫描。

## 1. 生产动机

前端和 Node.js 服务中最常见的数据形态就是数组与字符串：虚拟列表、埋点事件、日志片段、搜索建议、表单步骤、时间序列、上传分片。很多性能事故并非需要神秘算法，而是因为代码反复做了这些事：

- 在循环里 `slice()`、`filter()`、`includes()`，无意间形成 `O(n²)`。
- 用 `shift()` 维护窗口，导致数组不断搬移。
- 为每个起点重新统计一遍连续区间，错过可复用的窗口状态。
- 把 UTF-16 下标当作用户看到的字符下标，切坏 emoji 或组合字符。
- 为了“函数式”连续创建中间数组，让 GC 成为瓶颈。

数组题的核心不是记住某段模板，而是识别：当前答案是否只依赖一个连续区间？当边界单调移动时，是否能复用上一步的计算？

## 2. 数组与字符串的成本模型

### 2.1 数组

在抽象算法模型里，数组支持：

| 操作 | 常见成本 |
| --- | --- |
| 按下标读取/写入 | `O(1)` |
| 尾部 `push/pop` | 摊还 `O(1)` |
| 头部 `shift/unshift` | `O(n)` |
| `slice/spread` 复制 | `O(k)` 时间与空间 |
| 查找 `indexOf/includes` | `O(n)` |
| 中间插入/删除 | `O(n)` |

JavaScript 数组由引擎实现，不应把它简单等同于 C 的连续裸内存。稀疏数组、混合元素类型、删除属性等行为可能让引擎改变内部表示。不过在算法设计阶段，以上抽象仍然有效。

`readonly T[]` 只提供编译期只读视图；它不做深冻结，也不能阻止其他别名修改同一数组。

### 2.2 字符串

JavaScript 字符串不可变，频繁切片或拼接要考虑分配成本。更重要的是索引单位：

```ts
const icon = "😀";
console.log(icon.length); // 2，UTF-16 code units
console.log([...icon].length); // 1，Unicode code point
```

但 `[...text]` 仍不等于“用户感知字符”。例如字母加组合音标、家庭 emoji 可能由多个 code point 组成。面向用户的截断、光标和字数限制优先考虑：

```ts
const text = "👨‍👩‍👧‍👦中文";
const segmenter = new Intl.Segmenter("zh-CN", { granularity: "grapheme" });
const graphemes = [...segmenter.segment(text)].map((part) => part.segment);
```

转换会占用 `O(n)` 额外空间。API 必须声明下标究竟按 code unit、code point 还是 grapheme cluster 计数。

## 3. 双指针的三类形态

双指针并不是“必须有两个名为 left/right 的变量”，而是两个边界按规则移动，每个位置不会被反复无界访问。

### 3.1 相向指针

适用于有序数组的两数之和、回文验证、两端收缩：

```text
left ->  [ 1, 3, 4, 7, 9 ]  <- right
```

以升序两数之和为例：

- 和太小，只能增大左端。
- 和太大，只能减小右端。
- 有序性保证被排除的组合不可能成为答案。

每个指针最多移动 `n` 次，总时间是 `O(n)`，不是 `O(n²)`。

### 3.2 同向快慢指针

常用于原地压缩、过滤、去重：

```text
已写入有效区        尚未扫描
[0 ...... write) [read ........ n)
```

核心不变量通常是：`[0, write)` 已经是“已扫描前缀”的正确压缩结果；`read` 指向下一项待处理元素。

示例：原地保留非负值。

```ts
function keepNonNegative(values: number[]): number {
  let write = 0;

  for (let read = 0; read < values.length; read += 1) {
    if (values[read]! >= 0) {
      values[write] = values[read]!;
      write += 1;
    }
  }

  return write;
}
```

函数返回有效前缀长度；`[write, values.length)` 的旧数据不属于结果。若需要物理缩短数组，可最后设置 `values.length = write`，但这应由 API 契约明确。

### 3.3 分段指针

合并有序数组、解析 token、分区时，两个指针可能分别属于不同数据源。复杂度要写成 `O(n + m)`，因为每个输入只向前扫描。

## 4. 滑动窗口：复用连续区间状态

窗口通常表示半开区间 `[left, right)`：

```text
已移出       当前窗口                 未加入
[0..left) [left ........ right) [right..n)
```

半开区间的好处：长度永远是 `right - left`，空窗口自然表示为 `left === right`，和 `slice(left, right)` 语义一致。

### 4.1 固定长度窗口

求每个长度为 `k` 的区间和。朴素做法为每个起点重新累加 `k` 项，成本 `O(nk)`；滑动时只加入新元素、移除旧元素：

```ts
function maxFixedWindowSum(values: readonly number[], k: number): number {
  if (!Number.isInteger(k) || k <= 0 || k > values.length) {
    throw new RangeError("k must be in [1, values.length]");
  }

  let sum = 0;
  for (let i = 0; i < k; i += 1) sum += values[i]!;
  let best = sum;

  for (let right = k; right < values.length; right += 1) {
    sum += values[right]! - values[right - k]!;
    best = Math.max(best, sum);
  }

  return best;
}
```

时间 `O(n)`，辅助空间 `O(1)`。

### 4.2 可变长度窗口

典型条件是“窗口不合法时，移动左边界直到重新合法”。例如元素均非负，寻找总和不超过预算的最长连续区间：

```text
1. right 加入一个元素
2. 若 sum > budget，反复移出 left
3. 此时窗口重新满足 sum <= budget
4. 用当前窗口更新答案
```

核心不变量：在记录答案时，当前窗口合法；左侧再多包含一个已移出的元素就会违反约束，或左边界已经为 0。

复杂度证明不是“while 嵌套 for 所以平方级”。`right` 前进 `n` 次，`left` 在整个算法中也最多前进 `n` 次，总移动不超过 `2n`，所以是 `O(n)`。

### 4.3 为什么负数会破坏某些窗口

“总和超过预算就缩左边”依赖单调性：加入非负数不会让总和下降，移除非负数不会让总和上升。若允许负数：

```text
窗口和超标 --继续向右加入负数--> 可能重新合法
```

过早收缩可能丢失最优解。这时可能需要前缀和、单调队列、平衡树或其他结构，不能硬套模板。

## 5. 逐步推导：时间窗口内的峰值事件数

输入是升序时间戳，目标是求任意半开时间区间 `[start, start + windowMs)` 内最多事件数。

当 `right` 指向新事件时，若：

```text
timestamps[right] - timestamps[left] >= windowMs
```

则左右事件不能同时位于同一个半开时间窗中，应推进 `left`。恢复合法后，数组窗口 `[left, right]` 中任意两端时间差都 `< windowMs`，事件数为 `right - left + 1`。

```text
时间轴：  10  12  15  21  22
                [15 ------- 22)  假设 windowMs = 7
数组窗：          L       R
```

核心不变量：

- 时间戳已升序。
- 更新答案前，`timestamps[right] - timestamps[left] < windowMs`。
- `left` 只向右走，所有比它更小且已移出的起点都无法与当前 `right` 共存。

这类算法可用于流量峰值分析、客户端错误风暴、速率限制容量规划。真正的在线限流还涉及并发、分布式时钟和原子存储，不能直接用进程内数组代替。

## 6. Mutation、别名与 API 契约

原地算法节省空间，却可能破坏调用方状态。在 Vue 中尤其要注意：

- 直接排序或压缩响应式数组会触发更新，并改变其他消费者看到的顺序。
- `const next = props.items.sort(...)` 会修改 prop 所引用的数组。
- 浅复制 `[...items]` 只复制数组容器，不复制内部对象。

命名和类型应表达意图：

```ts
declare function compactInPlace<T>(values: T[]): number; // 明确修改
declare function compact<T>(values: readonly T[]): T[];  // 返回新数组
```

不能只为了宣称 `O(1)` 空间而违反产品层面的不可变数据约定。

## 7. 常见错误

- 移动边界后忘记同步更新窗口状态。
- 在答案更新前后混淆窗口是 `[left, right]` 还是 `[left, right)`。
- 把“至多”“至少”“恰好”的收缩条件写反。
- 平局规则未定义，导致返回的起止位置不稳定。
- 每轮用 `slice()` 构造窗口，算法状态虽是 `O(1)`，实际分配却变成 `O(n²)`。
- 用 `shift()` 移除窗口头部。
- 对包含负数的和问题强行使用只适用于非负数的窗口。
- 字符串按 code unit 切片，却把结果当成完整用户字符。

## 8. 何时不用双指针或滑动窗口

- 数据没有可利用的顺序，边界移动不能安全排除候选。
- 目标不是连续区间，而是任意子集。
- 约束不具单调性，收缩后可能错过未来恢复合法的更优窗口。
- 需要频繁随机插入、删除或查询中位数，普通数组移动成本过高。
- 数据无法装入内存，应改用异步迭代器、流式聚合或数据库窗口函数。
