# 第 07 章：排序、选择与外部排序

> 排序不是“会写冒泡排序”。高级工程师需要定义顺序契约，理解稳定性、最坏退化、内存和 I/O 成本，并知道当数据无法装入内存时如何改变问题。

## 1. 生产系统为什么反复排序

排序常常是后续算法成立的前置条件：

- 日志按时间排序后，才能二分定位时间窗口；
- 订单按租户和创建时间稳定排序，才能生成可重复报表；
- 搜索结果按相关度、价格和业务规则做多关键字排序；
- 海量事件先形成有序分片，再做归并、去重和聚合；
- 只需要第 99 百分位或前 100 项时，完整排序可能是浪费。

真实需求中的关键问题不是“选快速排序还是归并排序”，而是：

1. 顺序到底如何定义？
2. 相等元素是否必须保持原顺序？
3. 能否修改输入？
4. 数据是否全部在内存？
5. 是要完整顺序，还是只要第 k 个、Top-K 或若干分位点？
6. 最坏延迟能否接受，还是只关心平均吞吐？

## 2. 排序契约：比较器必须像一个一致的顺序

本课程统一使用：

~~~ts
export type Compare<T> = (left: T, right: T) => number;
~~~

- 返回负数：left 应排在 right 前；
- 返回 0：两者在当前顺序下等价；
- 返回正数：left 应排在 right 后。

比较器至少要满足：

- **自反等价**：<code>compare(a, a) === 0</code>；
- **反对称符号**：若 a 小于 b，则 b 大于 a；
- **传递性**：若 a 小于 b 且 b 小于 c，则 a 小于 c；
- **确定性**：同一对输入在一次排序中不应随时间或外部状态变化。

违反这些条件时，结果可能因引擎、数据布局和调用次数而变化。

错误例子：

~~~ts
items.sort(() => Math.random() - 0.5);
~~~

这不是可靠洗牌，因为比较器不一致且会产生偏差。洗牌应使用 Fisher–Yates。

### 2.1 多关键字比较

~~~ts
interface Order {
  readonly tenantId: string;
  readonly createdAt: number;
  readonly id: string;
}

const compareOrder = (a: Order, b: Order): number =>
  a.tenantId.localeCompare(b.tenantId) ||
  a.createdAt - b.createdAt ||
  a.id.localeCompare(b.id);
~~~

最后加入唯一 ID 能形成确定的全序，便于分页、缓存和可重复构建。若省略唯一 tie-breaker，稳定排序只保证相等项保持本次输入顺序；如果输入来自无顺序保证的数据库查询，结果仍可能跨请求变化。

## 3. 稳定性、原地性与适应性

- **稳定排序**：比较器判为相等的元素保持输入中的相对顺序。
- **原地排序**：只使用常数或很小的额外辅助空间；它通常会修改输入。
- **适应性排序**：能利用“输入已经部分有序”的事实。

例如订单先按创建时间排好，再稳定地按状态排序，同状态内仍保留时间顺序。稳定性也是 UI 列表切换次要排序键时减少无意义跳动的重要条件。

ECMAScript 当前要求 <code>Array.prototype.sort()</code> 稳定，但它会修改原数组。<code>toSorted()</code> 返回副本。标准规定可观察语义，不规定引擎必须使用哪种具体排序算法，也没有给出统一的时间复杂度承诺。

## 4. 经典排序算法应该掌握到什么程度

### 4.1 插入排序

维护前缀 <code>[0, i)</code> 已有序，把第 i 项插入正确位置：

~~~text
已排序前缀          当前项    未处理
[1 3 7 9]           4       [8 6]
        ← 右移 7、9
[1 3 4 7 9]                 [8 6]
~~~

- 最坏时间 <code>O(n²)</code>；
- 已有序时可接近 <code>O(n)</code>；
- 原地、易稳定、常数小。

因此它并非“只能教学”。成熟混合排序常在很小分区上使用插入排序。

### 4.2 归并排序

归并排序把区间分半排序，再线性合并。合并时维护：

- 输出区间已排序；
- 输出恰好包含两个输入区间中已消费的元素；
- 两个指针分别指向各自未消费的最小元素。

~~~text
left : [2, 5, 9]
          ^
right: [3, 5, 8]
       ^
output: [2]
~~~

时间稳定为 <code>O(n log n)</code>，常见数组实现需要 <code>O(n)</code> 辅助空间，容易做成稳定排序，也天然适合合并磁盘上的有序运行段。

### 4.3 快速排序

快速排序围绕 pivot 分区：

~~~text
< pivot | == pivot | 未处理 | > pivot
~~~

平均时间 <code>O(n log n)</code>，原地版本缓存行为通常很好；但糟糕 pivot 可退化为 <code>O(n²)</code> 和深递归。生产实现常采用随机化、三数取中、三路分区和 introsort：递归过深时切换堆排序。

大量重复值时，两路分区会反复处理等于 pivot 的元素；三路分区把它们一次聚在中间。

### 4.4 堆排序

先在线性时间内建堆，再重复取出堆顶。时间 <code>O(n log n)</code>、辅助空间可为 <code>O(1)</code>，最坏时间有界，但通常不稳定，实际局部性也常不如优化后的快速排序。堆的核心将在第 10 章展开。

### 4.5 为什么不把冒泡排序当主线

冒泡排序能解释交换和不变量，却很少是生产数组排序的合理选择。应知道它是 <code>O(n²)</code>，然后把学习时间用于比较器、稳定性、选择、外部排序和退化边界。

## 5. 选择问题：只找第 k 项不必完整排序

若只想找升序后的第 k 个元素：

- 完整排序：<code>O(n log n)</code>；
- 维护大小 k 的堆：<code>O(n log k)</code>，适合流式 Top-K；
- Quickselect：期望 <code>O(n)</code>，会通过分区排除不可能包含答案的一侧；
- 确定性线性选择存在，但实现复杂、常数较大，普通业务少见。

三路 Quickselect 的不变量：

~~~text
left          less        scan          greater       right
| < pivot ... | == pivot | 未分类 ...... | > pivot ... |
~~~

每轮后：

- 若 k 在 < 区，只继续左区；
- 若 k 在 > 区，只继续右区；
- 若 k 在 == 区，pivot 就是答案。

随机 pivot 让固定恶意顺序更难持续触发坏分区，但“期望线性”不是最坏线性。对尾延迟有严格要求时，要设置工作预算、使用堆或成熟库。

## 6. Top-K 的三个不同问题

“取前 k 个”可能指：

1. 只要这 k 个元素，不要求内部有序；
2. 要 k 个元素且内部有序；
3. 数据持续到达，任何时刻都要当前 Top-K。

Quickselect 适合第 1 种，选出后再排序这 k 项适合第 2 种；大小为 k 的堆适合第 3 种。不要只看到“Top-K”就套同一个模板。

若 k 接近 n，完整排序可能更简单且更快；若 k 很小且数据是流，不能复制全部输入做 Quickselect。

## 7. 外部排序：内存放不下时改变数据流

假设有 500 GB 日志，进程只有 2 GB 可用内存。外部归并排序通常分两阶段：

### 7.1 生成有序运行段

~~~text
输入流
  ↓ 每次读取内存预算允许的一块
[chunk 1] --内存排序--> run-001
[chunk 2] --内存排序--> run-002
[chunk 3] --内存排序--> run-003
~~~

每块必须预留运行时、解析对象和排序缓冲空间，不能把“2 GB 限额”等同于读取 2 GB 文本。

### 7.2 k 路归并

每个运行段已经有序。只保留每个段的当前头元素，把 k 个头放进最小堆：

~~~text
run A:  2  8  15 ...
run B:  1  7  20 ...
run C:  3  5  11 ...

heap: [1(B), 2(A), 3(C)]
弹出 1，输出，再从 B 读入 7
heap: [2(A), 3(C), 7(B)]
~~~

若总元素数为 n、运行段数为 k：

- 归并时间 <code>O(n log k)</code>；
- 内存约 <code>O(k + 各输入缓冲 + 输出缓冲)</code>；
- 每项只从一个源读出并写出一次，但实际性能常由顺序 I/O、序列化和缓冲大小主导。

运行段过多时，无法同时打开所有文件，需要多轮归并。文件描述符限制、临时磁盘空间、崩溃清理、校验和与重启检查点都属于算法的一部分。

## 8. 排序生产不变量

一份可上线的排序/归并实现至少验证：

- **有序性**：相邻输出满足 <code>compare(prev, current) &lt;= 0</code>；
- **排列性**：没有丢失、重复或凭空生成元素；
- **稳定性**：若契约要求，相等元素的原输入次序不变；
- **边界内存**：流式算法不会随着 n 把全部数据留在内存；
- **确定性**：相等键有明确 tie-breaker；
- **失败清理**：消费者取消或任一输入失败时关闭资源。

仅测试“结果等于某个数组”难以覆盖排列性。可以用随机小输入和可信标准库做差分测试，再单独检查稳定标签。

## 9. TypeScript / JavaScript 特有陷阱

### 9.1 默认 sort 是字符串顺序

~~~ts
[2, 10, 3].sort(); // 结果不是数值升序
~~~

数值比较器 <code>(a, b) =&gt; a - b</code> 遇到 NaN、Infinity 和超大整数时也需要业务定义。若 ID 超过安全整数，不要先转 number 再比较。

### 9.2 比较器做昂贵派生会被反复调用

~~~ts
items.sort((a, b) => expensiveParse(a).score - expensiveParse(b).score);
~~~

排序可能调用比较器很多次。可先 decorate：为每项计算一次键，再排序，最后 undecorate。但这会增加 <code>O(n)</code> 内存，需要测量。

### 9.3 localeCompare 不是固定字节序

面向用户的语言排序应明确 locale 和选项；用于缓存键、协议和跨环境可重复构建时，通常需要固定、可移植的代码点或字节顺序。不要把展示顺序和存储顺序混为一谈。

### 9.4 sort 修改数组

对传入的 <code>readonly T[]</code>，复制后排序；同时在复杂度中写出这份 <code>O(n)</code> 空间。若数据巨大，复制可能正是不可接受的成本。

### 9.5 异步迭代器需要清理

外部归并中，消费者可能只取前 100 条就停止。异步生成器应在 <code>finally</code> 中调用各输入迭代器的 <code>return()</code>，否则文件、网络流或数据库游标可能泄漏。

## 10. 常见错误

- 比较器不传递，或把布尔值直接当比较结果。
- 需要稳定结果却没有定义相等项顺序。
- Quickselect 在原数组上分区，却未在 API 中声明 mutation。
- 总选首项为 pivot，遇到有序或恶意数据退化。
- 将期望 <code>O(n)</code> 写成无条件最坏 <code>O(n)</code>。
- 为找 10 个最大值先对一亿项完整排序。
- 外部排序仍把所有运行段一次读入内存。
- k 路归并每次线性扫描 k 个头，使时间退化为 <code>O(nk)</code>。
- 忽略临时磁盘、文件描述符、失败清理和重启。
- 只检查有序性，不检查元素是否丢失或重复。

## 11. 什么时候不要排序

- 只做成员查询时，哈希集合或数据库索引更合适。
- 只要 Top-K 或分位点时，选择、堆或近似统计可能更便宜。
- 数据库已有合适索引且可流式返回时，不要拉到应用层重排。
- UI 只显示一个窗口时，可让后端分页排序或使用虚拟化，避免客户端持有全部数据。
- 高频更新集合若每次全量重排，应考虑有序结构、增量索引或事件流聚合。
- 若用户只关心模糊排名，精确全序可能是不必要成本。
