# 第 05 章：哈希表、集合与多索引一致性

## 1. 生产动机：快查找的代价藏在哪里

请求去重、缓存、权限集合、用户会话、实体索引几乎都依赖 Map/Set。开发者很容易形成一句模糊认知：“哈希表就是 O(1)。”真正进入生产后，事故往往来自被省略的前提：

- 两个业务上相等的键，在程序里是否真被视为相等？
- 哈希碰撞怎样处理，输入是否可能恶意制造碰撞？
- 扩容与 tombstone 何时让延迟突然抖动？
- 缓存/去重集合是否有 TTL 和容量上限？
- 主索引更新成功，二级索引失败时怎样保持一致？

本章目标是理解哈希表机制，并把它用于一个带多索引的真实内存模型。你应能准确说“在某种实现和负载假设下的期望/摊还成本”，而不是把实现惯例说成 ECMAScript 规范的严格 O(1) 承诺。

## 2. 从直接寻址到哈希

若键只可能是 `0..999` 的整数，可以直接用数组下标：`table[key]`。访问 O(1)，但键空间巨大或是字符串时会浪费大量内存。

**哈希函数**把任意键映射为固定范围整数：

```text
hash(key) -> 32-bit integer -> bucket index
```

容量 `m` 为 8 时，可用 `hash & (m-1)` 取桶下标（前提 m 是 2 的幂），或 `hash % m`。

好的非密码哈希函数希望常见输入均匀分布、计算快速、小改动产生足够变化。但从大键空间映射到有限桶，**碰撞必然存在**：不同键得到同一桶。哈希表正确性不能依赖“永不碰撞”；命中桶后必须再比较原始键。

## 3. 相等性先于哈希

正确哈希表必须满足：若 `equals(a,b)` 为真，则 `hash(a) === hash(b)`。反向不要求成立；相同 hash 仍要用 equals 区分。

JavaScript `Map/Set` 使用 SameValueZero 一类语义：`NaN` 与 `NaN` 相等，`0` 与 `-0` 相等，对象按引用身份相等。

```ts
new Map([[{ id: 1 }, "a"]]).get({ id: 1 }); // undefined，两个对象引用不同
```

业务复合键不能随便 `JSON.stringify(obj)`：属性顺序、undefined、BigInt、循环引用、Unicode 规范化和分隔符歧义都会影响结果。常见替代：

- 嵌套 Map：`tenant -> userId -> value`；
- 明确定义无歧义编码，例如长度前缀；
- 为实体建立规范化稳定 ID；
- 注入经过审查的 hash/equality。

## 4. 两类碰撞处理

### 4.1 链地址法

每个桶保存一个小列表：

```text
0: -> (cat,V1) -> (act,V2)
1: -> empty
2: -> (dog,V3)
```

查找先定位桶，再遍历桶内项。实现直观，删除简单，但每项额外对象/指针影响内存局部性。

### 4.2 开放寻址

所有条目直接放在槽位数组中。目标槽被占用时按探测序列找下一个位置。线性探测：

```text
index, index+1, index+2, ...（环绕）
```

它局部性较好，但高负载下会出现聚集。教学实现会使用线性探测，生产标准库可能采用更复杂策略。

## 5. 负载因子与扩容

负载因子 `α = occupied / capacity`。开放寻址不能真正装到完全满，否则失败查找可能绕完整表。随着 α 升高，平均探测长度增加；实现通常在某阈值（例如 0.7）前扩容并重新哈希。

扩容一次 O(n)，但容量几何增长时，一串插入的重哈希总成本是几何级数，插入可作摊还分析。阈值不是数学常量；它取决于探测方式、内存预算和实际 workload。

扩容必须重新计算每个条目在新容量下的位置，不能把旧数组原样复制，因为桶下标依赖 capacity。

## 6. 删除为什么需要 tombstone

开放寻址表：

```text
slot 2: A (hash->2)
slot 3: B (hash->2，碰撞后探测)
slot 4: empty
```

若删除 A 后把 slot 2 标成“从未使用的 empty”，查找 B 从 2 开始会立刻停止，错误地认为 B 不存在。必须区分：

- `EMPTY`：这个探测链从未经过，可停止失败查找；
- `DELETED`/tombstone：这里曾有条目，查找必须继续，但插入可复用；
- `OCCUPIED`：比较键。

tombstone 太多会拉长探测，所以除了 size，还可维护 used（occupied + tombstone）；used 比例高时重新哈希，哪怕容量不增长。

### 开放寻址不变量

对任意已存 key，从它的初始桶按探测规则前进，在遇到 EMPTY 前一定能遇到该 key。插入、删除、重哈希都必须保持。

## 7. Map、Set、Object 怎样选

- `Map`：任意类型键、明确 size、迭代、频繁增删，语义最直接。
- `Set`：只关心成员关系，避免 value=true 的伪 Map。
- 普通 Object：适合固定字段的数据记录；把外部字符串当字典键时要考虑原型、`__proto__`、键类型和枚举顺序。
- `Object.create(null)`：无原型字典，但仍只有 string/symbol 键，API 不如 Map 清晰。
- 数组/排序数组：小数据或需要有序遍历时，可能比 Map 更简单、局部性更好。

ECMAScript 对 Map/Set 规定的是平均访问需具备次线性一类性能特征，而非教材式指定“必须用哈希表且所有操作 O(1)”。课程讨论常见哈希实现的期望成本时会明确假设。

## 8. 多索引：读快了，写就变难

工单系统同时需要：

```text
byId: id -> Ticket
byStatus: status -> Set<id>
byAssignee: assignee -> Set<id>
```

按状态查询无需全表扫描，但一次 update 必须同时维护三个视图。核心不变量：

1. `byId` 中每个 ticket，恰好出现在其 status 集合；
2. assignee 非空时，恰好出现在对应 assignee 集合；为空时出现在 null 分组或按契约不建索引；
3. 二级索引中的每个 id 都能在 byId 找到，字段与桶键一致；
4. 空桶按约定删除，避免无界残留；
5. 验证失败或提交中断后，要么保留旧状态，要么完整得到新状态，不能半更新。

先更新主表再更新二级表，中间抛错就会产生幽灵 ID。单线程同步代码也需要事务式顺序：先完整验证，构造修改计划；执行时保留 undo journal；失败按逆序撤销。

这只是内存对象的一致性，不是数据库事务。进程崩溃、跨请求并发、多个实例仍需持久化层约束与事务。

## 9. 安全、容量与退化

- 教学字符串 hash 不能抵抗攻击者构造碰撞；外部可控 key 的哈希洪泛会把期望查找退化到 O(n)。生产运行时可能随机化 hash，但不能据此忽略请求/键长度/集合大小限制。
- 去重 Set 若无 TTL/上限，会成为内存泄漏。精确去重的内存与独特键数线性增长；可接受误报时才考虑 Bloom filter。
- 键应限制长度、规范化规则和租户命名空间，避免跨租户碰撞或混淆。
- `Map` 仍会持有对象键，若需要不阻止对象回收，评估 `WeakMap`；WeakMap 不可枚举且只接受对象/非注册 symbol 键，语义不同。

## 10. 测试与证据

手写哈希表必须强制碰撞，不能只测自然数据。可注入常量 hash，或寻找相同桶键。用原生 Map 作随机操作 oracle，比较 set/get/has/delete/size。

多索引每次写后运行测试专用 `assertInvariants()`；对每个提交步骤注入异常，确认状态与操作前深度快照相同。生产热路径不必全表检查，但可用抽样/指标/后台审计发现漂移。
