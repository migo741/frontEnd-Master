# 第 04 章：栈、队列、双端队列与单调结构

## 1. 生产动机：顺序就是业务语义

浏览器历史记录要后进先出；网络消息通常先到先处理；滑动窗口要不断从两端淘汰；遥测缓冲区必须有硬容量，离线几小时也不能把内存吃光。它们都保存“一段有顺序的数据”，但允许访问的位置不同。

- **栈（stack）**：LIFO，后进先出，只在同一端 push/pop。
- **队列（queue）**：FIFO，先进入的先离开，尾部入、头部出。
- **双端队列（deque）**：两端都可插入和删除。
- **单调队列**：双端队列中的候选值按某种单调关系排列，用于快速回答窗口最值。

本章真正训练的是：把顺序契约、成本、容量和过载策略一起建模，而不是只会调用 `push()`。

## 2. 栈：保存尚未完成的上下文

```text
top
 |
 v
[ C ]  <- pop
[ B ]
[ A ]
```

函数调用栈、括号匹配、表达式求值、DFS、撤销操作都依赖 LIFO。以括号匹配为例，扫描到左括号时入栈；扫描到右括号时，它必须匹配最近一个尚未闭合的左括号，所以弹出栈顶。

核心不变量：扫描完前缀 `text[0..i)` 后，栈从底到顶恰好保存这个前缀中尚未匹配的左括号，且顺序与出现顺序一致。结束时栈为空才全部闭合。

JavaScript 数组的尾部 `push/pop` 适合普通栈。不要为了“数据结构感”无条件手写节点栈；只有需要特殊容量、共享内存或可观测契约时才自定义。

## 3. 队列：为什么不要习惯性 `shift()`

最简单的队列可以用数组和逻辑 head：

```ts
class SimpleQueue<T> {
  private data: T[] = [];
  private head = 0;

  enqueue(value: T): void { this.data.push(value); }
  dequeue(): T | undefined {
    if (this.head >= this.data.length) return undefined;
    const value = this.data[this.head];
    this.head += 1;
    return value;
  }
}
```

`shift()` 的语言规范定义结果语义，不给你跨所有引擎的固定复杂度保证；常见数组表示下，头删可能涉及后续索引移动或重排。高频大队列应使用 head 索引或环形缓冲，而不是假定它稳定 O(1)。

head 索引版本也要压缩：已消费槽位仍在数组中，若不清空引用会延长 payload 生命周期；head 无限增长也会留下巨大底层数组。可在 `head` 超过阈值且占比足够高时 `slice(head)`，这是偶发 O(n)、摊还可控的整理。

## 4. 环形缓冲区：把尾部绕回开头

双端队列可用循环数组表示。维护：

- `buffer`：容量为 `capacity` 的槽位数组；
- `head`：逻辑第一个元素所在物理下标；
- `size`：当前元素数；
- 尾部插入位置：`(head + size) % capacity`。

```text
物理槽位:  0    1    2    3    4    5    6    7
内容:     [D]  [E]  [ ]  [ ]  [ ]  [A]  [B]  [C]
head=5, size=5
逻辑顺序: A, B, C, D, E
```

使用 `size` 区分空和满，就不需要故意浪费一个槽位：

```text
空：size === 0
满：size === capacity
第 i 个逻辑元素：buffer[(head + i) % capacity]
```

### 两端操作

- `pushBack(x)`：写入 `(head+size)%capacity`，size++。
- `popFront()`：读取 head，清空槽位，head 向前一格，size--。
- `pushFront(x)`：head 向前绕一格，再写入，size++。
- `popBack()`：尾元素下标为 `(head+size-1)%capacity`。

### 核心不变量

1. `0 <= size <= capacity`；
2. 从 head 起连续 `size` 个环形位置恰好是逻辑元素，顺序不变；
3. 其他槽位不属于容器，删除时写回 `undefined` 以释放引用；
4. 扩容只改变物理布局，不改变逻辑序列。

扩容时申请通常为两倍的新数组，把逻辑第 `0..size)` 项复制到新数组同下标，最后 `head=0`。单次扩容 O(n)，几何增长使一串尾插的摊还成本 O(1)。若每次只加一个槽，长期总复制量会退化到 O(n²)。

## 5. 单调双端队列：保存“仍可能成为答案”的候选

求长度为 `k` 的每个滑动窗口最大值。朴素方法每个窗口扫描 k 项，时间 `O(nk)`。单调队列保存索引，且对应值从队首到队尾单调不增：

处理新索引 `i`：

1. 队首若 `<= i-k`，它已离开窗口，弹出。
2. 队尾对应值若 `<= nums[i]`，弹出；它更旧且不更大，未来永不可能优于新值。
3. 把 `i` 加到队尾。
4. 窗口形成后，队首就是最大值索引。

```text
值:       1  3 -1 -3  5     k=3
i=0: deque=[0]          值 [1]
i=1: 1 被 3 支配 -> [1] 值 [3]
i=2: [1,2]              值 [3,-1] -> max 3
i=3: [1,2,3]            值 [3,-1,-3] -> max 3
i=4: 1 过期；2、3 被 5 支配 -> [4] -> max 5
```

每个索引最多入队一次、从两端出队一次，所以总时间 O(n)，不是“while 嵌套所以 O(n²)”。

单调队列成立的关键是不变量与支配关系。若要返回所有窗口元素、任意分位数或支持中间修改，它不再足够。

## 6. 有界缓冲与过载策略

无界内存队列不是生产方案。生产缓冲必须定义：

- 容量按条数、字节还是加权成本？
- 满时阻塞、拒绝新项、丢最旧、丢低优先级还是降采样？
- 被丢数据怎样计数和暴露 gap？
- flush 在途数据是否仍占容量？
- flush 失败如何回滚，能否与新到数据保持顺序？

“critical 永不丢且生产者永不阻塞且内存有硬上限”三者不能同时无条件成立。有限资源下必须选择并把丢弃变成可观察事件。

一种安全 drain 协议是 lease：

1. `beginDrain()` 从可见队列拿出批次，但把其字节记为 reserved；
2. flush 成功调用 `commit()`，释放 reserved；
3. flush 失败调用 `rollback()`，把批次放回队首；
4. lease 未完成前，reserved 不能被新事件占用，因此 rollback 不会突破硬上限。

这类似资源事务，但只保证单进程内存状态；进程崩溃仍会丢失。

## 7. 复杂度与实现选择

| 结构 | 典型操作 | 时间 | 备注 |
|---|---|---:|---|
| 数组栈 | 尾 push/pop | 常见摊还 O(1) | 简单优先 |
| head-index 队列 | enqueue/dequeue | 摊还 O(1) | 需整理和清引用 |
| 环形 Deque | 两端操作 | 摊还 O(1) | 扩容单次 O(n) |
| 单调 Deque | 一次全序列窗口最值 | O(n) | 只保存候选索引 |

ECMAScript 不把数组实现细节写成算法教材式复杂度承诺；这里的成本来自常见引擎表示与我们自定义结构的操作计数。生产判断仍应 profile。

## 8. TypeScript / JavaScript 陷阱

- `T | undefined` 返回值无法区分“队列空”与“队列存了 undefined”；关键 API 可返回 `{ok,value}` union。
- `new Array(capacity).fill(object)` 会让每槽指向同一对象；空槽只需 undefined。
- `%` 在 JavaScript 对负数可返回负值；head 前移要用 `(head - 1 + capacity) % capacity`。
- 弹出后要清槽，避免长寿命 buffer 持有大对象。
- 迭代期间修改 deque 必须定义语义：快照、实时或 fail-fast。不要让偶然行为成为契约。
- 字节容量必须由统一编码计算；字符串 `length` 是 UTF-16 code unit，不是 UTF-8 字节数，可用 `TextEncoder` 在边界计算。

## 9. 测试与度量

对 Deque 使用一个慢但可信的数组模型：随机产生两端 push/pop，逐步比较逻辑内容、size 与 peek。让小容量频繁绕回、扩容，专门捕获 off-by-one。

对缓冲区使用 fake clock/假 flush，不用 sleep；检查任意时刻 `bufferedBytes + reservedBytes <= maxBytes`。错误注入覆盖 reject、丢弃、rollback、重复 commit、rollback 后新事件顺序。

## 10. 何时不用这些结构

- 需要跨进程持久、确认与重试：使用数据库/消息系统，而非内存队列。
- 需要按任意键查询：补索引或换 Map/树，不要扫描 deque。
- 需要按优先级取最小项：使用堆，而非每次排序队列。
- 小规模一次性数组转换：清晰的数组 API 往往更好。

## 11. 自检与 AI 追问锚点

1. 环形队列为什么同时保存 head 与 size？
2. 扩容后为何把 head 重置为 0？
3. 单调队列弹出较小旧值为何不会漏答案？
4. 为什么在途批次仍应占用容量预算？
5. “有限内存、永不阻塞、永不丢数据”为什么不可同时保证？

交给 AI 时请附上：两端操作契约、空值语义、扩缩容规则、容量单位、过载策略、迭代期间修改语义。只问“帮我写队列”会省略最重要的工程决策。
