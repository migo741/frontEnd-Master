# 第 16 章：贪心证明与区间调度

## 1. 生产问题：为什么“每次挑最好的”经常出事故

会议排期、部署窗口、广告投放、批处理任务和资源分配看起来都像：当前有很多选择，挑一个最划算的，再处理剩余部分。这个思路叫**贪心**：每一步只根据当前状态作出局部选择，之后不回退。

贪心实现通常很短，真正困难的不是写循环，而是回答：局部最优为什么能导向全局最优？如果无法回答，十行代码也可能稳定地产生错误结果。

本章完成后，你应该能：

- 把时间段统一建模成半开区间 `[start, end)`；
- 区分“最大化不重叠任务数”和“最少资源容纳所有任务”；
- 用交换论证证明贪心选择；
- 主动构造反例，否定看似合理的规则；
- 用扫描线或最小堆处理并发峰值与房间分配；
- 说明贪心不适用时应转向动态规划、搜索或近似算法。

## 2. 先把区间契约说清楚

区间 `[start, end)` 包含 `start`，不包含 `end`。因此 `[09:00, 10:00)` 与 `[10:00, 11:00)` 不重叠，前一个结束后资源可以立刻复用。

半开区间有三个工程优势：

1. 长度恰好是 `end - start`；
2. 相邻区间不会重复包含边界；
3. 空区间可自然表示成 `[x, x)`。

课程默认要求 `start < end`。真实系统若允许零时长事件，应单独定义它是否消耗资源，不能让代码偶然决定。

```ts
interface Interval {
  readonly id: string;
  readonly start: number; // 已规范化的单调时间单位
  readonly end: number;
}
```

“已规范化”很重要。用户输入可能是带时区的日期；算法层应接收已经解析好的 Instant/epoch 值，并在边界层拒绝非法日期。不要在比较器里临时解析本地时间字符串。

## 3. 经典问题：最多能安排多少个互不重叠区间

目标是从所有候选区间中选出**数量最多**的一组互不重叠区间。注意目标是数量，不是总时长、收益或优先级。

四个听起来合理的规则：

- 最早开始；
- 持续时间最短；
- 与其他区间冲突最少；
- 最早结束。

只有“最早结束”对这个目标有标准的贪心保证。直觉是：当前任务结束越早，留给后续任务的时间越多。

算法：

1. 按 `end` 升序排序；相同结束时间再按 `start`、`id` 确定顺序。
2. 维护 `lastEnd`，表示已选最后一个区间的结束时刻。
3. 从左到右扫描；若 `interval.start >= lastEnd`，选择它并更新 `lastEnd`。

```text
候选： A=[1,4)  B=[3,5)  C=[0,6)  D=[5,7)  E=[8,9)
按结束排序：A B C D E

lastEnd=-∞
A 可选 -> 已选 A，lastEnd=4
B 重叠 -> 跳过
C 重叠 -> 跳过
D 可选 -> 已选 A,D，lastEnd=7
E 可选 -> 已选 A,D,E，lastEnd=9
```

### 核心不变量

扫描到排序后第 `i` 个位置前：

1. `selected` 内所有区间两两兼容；
2. `lastEnd` 是 `selected` 最后区间的结束；
3. 对于已经形成的选择数量，当前方案的最后结束时间不会晚于任何可交换的最优前缀。

第三点连接了局部选择与全局最优。

### 交换论证

设贪心第一项是 `g`，某个最优方案第一项是 `o`。因为 `g` 是所有候选中结束最早的，所以 `end(g) <= end(o)`。把最优方案中的 `o` 换成 `g`，不会让后续任何原本可行的区间变得不可行：后续区间若在 `o` 之后开始，也一定不会早于更早结束的 `g`。替换后数量不变，仍是最优方案。

现在问题缩小为 `g` 结束后的候选区间，重复同一论证。因此存在一个以每次贪心选择开头的最优解。

这段证明依赖目标“最大数量”与区间兼容规则。如果区间有不同收益，最早结束不再保证最大总收益；那是加权区间调度，通常需要动态规划。

### 反例是证明能力的一部分

“最早开始”会选 `[0,100)`，错过 `[1,2)、[2,3)、[3,4)`。

“最短持续时间”也可能失败：一个很短但位于中央的区间，可能同时挡住左侧和右侧两个本可共存的区间。不要因为某条规则通过了两个样例就相信它；主动搜索 3～6 个区间的最小反例。

## 4. 另一个问题：容纳全部会议需要多少房间

这里不能丢弃任何区间，目标变成最少资源数。它与上一题看似相近，状态却不同。

只求最少房间数量时，可建立扫描事件：

```text
(start, +1) 表示占用
(end,   -1) 表示释放
```

按时间排序；同一时刻必须先处理 `end` 再处理 `start`，这与 `[start,end)` 契约一致。扫描中的最大累计值就是峰值并发，也就是所需最少房间数。

若还要返回“每场会议分到哪个房间”，只计数不够。按开始时间处理会议，并维护：

- `active`：按最早结束时间排序的最小堆，元素含 `end` 和 `roomId`；
- `freeRooms`：已经释放的房间 ID 最小堆，确保结果稳定；
- `nextRoomId`：没有空闲房间时创建新房间。

处理 `[s,e)` 前，把 `active` 中所有 `end <= s` 的房间释放，再复用最小空闲 ID 或创建新 ID。

### 为什么最小堆合适

每次只关心“最早结束的活动会议”。排序数组能找最小项，但插入/删除可能搬移大量元素；最小堆能在 `O(log n)` 插入和删除最小项。若只求数量，事件排序更简单；若需要稳定分配，堆保存了所需状态。

## 5. 复杂度与隐藏成本

| 算法 | 时间 | 额外空间 | 备注 |
|---|---:|---:|---|
| 最大不重叠区间 | `O(n log n)` | 取决于排序 | 扫描为 `O(n)` |
| 扫描线求峰值 | `O(n log n)` | `O(n)` | 产生 `2n` 个事件 |
| 堆式房间分配 | `O(n log n)` | `O(n)` | 每项至多入/出堆一次 |

如果输入已经按结束时间或开始时间排序，可以把相应排序成本降掉，但契约必须明确，不能默默相信调用方。

JavaScript 的 `sort()` 会原地修改数组；答案默认用 `[...input].sort(...)` 或 `toSorted()` 保持输入不可变。比较器必须满足一致性：不要返回布尔值，不要对可能超过安全整数的差直接相减。

## 6. 何时不要用本章贪心

- 区间带收益，目标最大总收益：考虑加权区间 DP。
- 有复杂前置依赖或人员技能约束：建模为图、匹配、流或约束搜索。
- 允许拆分、抢占、迁移且有切换成本：需要更具体的调度模型。
- 线上会议会频繁新增/取消：一次性排序重算可能不够，需要有序索引、区间树或分批重算。
- 时间来自不同时区/日历规则：先由时间领域层规范化，算法不能替代时区库。

## 7. 测试与生产边界

至少覆盖：空输入、单项、完全相邻、完全重叠、全部相同起点、相同终点、负数时间、大范围数值、无效区间、重复 ID、输入顺序随机化。

性质测试可以验证：

- 输出中的区间两两不重叠；
- 输出都来自输入且不重复；
- 小规模下贪心数量等于穷举 oracle；
- 房间内任意两场会议不重叠；
- 分配使用的房间数等于扫描线峰值。

## 8. 本章速记、自检与 AI 追问

速记：**先冻结目标；能贪心不等于看起来合理，必须有交换论证或其他证明。**

自检：

1. 为什么 `[1,2)` 与 `[2,3)` 可以共用资源？
2. “最早结束”证明的交换步骤用了哪个不等式？
3. 相同时间为什么 end 事件要排在 start 之前？
4. 加入收益后，原证明在哪一步失效？

交给 AI 追问时，请同时附上：目标函数、区间边界语义、是否允许丢弃任务、是否有权重、输入是否已排序。缺少这些前提，“区间调度用什么算法”没有唯一答案。
