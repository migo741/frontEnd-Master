# 第 20 章：依赖任务调度器毕业项目

## 1. 毕业项目的真正目标

前 19 章分别练过数组、Map、链表、队列、堆、图、拓扑、最短路、贪心、DP、搜索与缓存。毕业项目不再问“这题用什么结构”，而是要求你从契约出发，把多个结构组合成一个行为可解释的组件：**单进程、本地、异步 DAG 执行器**。

输入一组任务及依赖，执行器要：

- 在开始前验证全部输入和循环依赖；
- 只有依赖全部成功后才把任务放入 ready；
- 按 priority/ID 在并发上限内启动；
- 失败任务阻断所有下游，但不影响无关分支；
- 支持全局取消并向运行任务传 AbortSignal；
- 输出稳定结果和结构化状态事件；
- 面对深图、大图、observer 抛错、task 同步抛错/异步拒绝时仍保持状态机不变量。

它故意不做持久化、跨进程 lease、分布式 exactly-once 或 shell 沙箱。能清楚划定不保证什么，是高级工程能力的一部分。

## 2. 先写边界：这是 executor core，不是工作流平台

本章允许的世界：

- 一个 JavaScript agent/进程；
- 构造时任务图固定；
- 每任务只运行至多一次；
- run 通过 Promise/值报告结束，通过 throw/reject 报告失败；
- cancellation 是协作式，任务必须监听 signal 才能及时停止；
- 依赖只有“全部成功才运行”一种关系。

不在范围：重试、定时、跨机器、持久恢复、artifact cache、资源标签、动态加节点、部分依赖容忍、补偿事务。它们可以建立在清晰核心上，但不能在一个练习里用模糊 if 假装完成。

## 3. 入场验证（admission）

调度开始后再发现坏图，会留下部分任务已产生副作用。因此构造阶段必须一次完成：

1. 限制 task/edge 数和 ID 长度；
2. 拒绝空/重复 ID、重复/未知 dependency；
3. 验证 priority 有限、run 可调用；
4. 构建 `dependencies`、`dependents`、remaining count；
5. 运行拓扑验证；有环返回 witness，零任务合法；
6. 只有全部成功后发布 executor 并排入初始 ready。

外部任务对象要复制不可变元数据，避免调用方在运行中修改 dependencies；run 函数引用本身可保留。

## 4. 状态机

```text
pending -> ready -> running -> succeeded
                    |   \\-> failed
                    \----> cancelled（全局取消后，等待 run settle）

pending/ready -> blocked   （上游 failed/blocked）
pending/ready -> cancelled （全局取消）
```

终态：succeeded、failed、blocked、cancelled。状态转换必须集中在一个函数中，统一更新 terminalCount 和发事件。不要让每个回调自行改字符串。

核心区别：

- failed：任务确实启动，自己的 run 失败；
- blocked：没启动，因为至少一个祖先失败；
- cancelled：因调用方全局取消而没有完成；
- pending：仍等依赖；ready：依赖完成但没拿到槽；running：已调用 run。

## 5. 组合的数据结构

```text
Map id -> task/state/remaining/controller/result
Map dependency -> dependents[]
MinHeap ready: priority 降序、id 升序
```

ready heap 可能保留已被 blocked/cancelled 的 stale entry；pop 时检查当前 state，lazy 跳过。这样失败传播无需在堆中 O(n) 查找删除。

remaining 只在某依赖 succeeded 时递减。它变 0 时，任务进入 ready。失败则可直接从 failed 节点沿 dependents 迭代标记所有 pending/ready 后代 blocked；这些后代不可能已经 running，因为一个祖先尚未成功时依赖链不可能全部满足。

## 6. 调度 pump 不变量

`pump()` 反复启动任务，直到 runningCount=concurrency 或无 valid ready：

1. runningCount 永远不超过 concurrency；
2. 只有 state=ready 的任务可 start；
3. state=ready 意味所有直接依赖 succeeded；
4. 每任务最多从 ready 到 running 一次；
5. heap tie-break 确定，但只在 ready 集合内比较。

使用 `#pumping` 防止重入。run 放入 Promise microtask：同步 throw 与异步 reject 统一进入 finish。每个 finish 更新状态、释放槽、解锁/阻断下游，再调用 pump。

JavaScript 单线程不等于没有并发状态问题：Promise completion、cancel、observer 和 task 内回调会在不同 microtask/macrotask 交错。集中 mutation 仍然必要。

## 7. 失败传播

任务 X failed 后，从 `dependents[X]` BFS/DFS：

- state 为 pending/ready -> blocked，继续传播其 dependents；
- 已 terminal -> 不重复计数；
- running/succeeded 理论上不应是 X 的后代；若出现说明状态不变量已坏，应在开发检查中报警。

无关分支不在可达集合，继续调度。结果顺序按原输入，而不是完成顺序，便于调用方稳定处理；事件保留真实时间顺序。

## 8. 全局取消的诚实语义

cancel 时：

- pending/ready 立即转 cancelled；
- 每个 running 的 AbortController.abort(reason)；
- running 只有 Promise settle 后才转 cancelled并释放槽；
- 不再启动新任务；
- done 等待所有 running settle。

若 task 忽略 signal 且永不 settle，done 也不会完成。执行器不能安全强杀同线程任意 Promise。强隔离需要 Worker/子进程/容器及外部监督。本章 API 必须文档化这个边界，不能超时后让失控副作用在后台继续却声称任务已终止。

## 9. 观察性不是 console.log

每次状态变化发结构化事件：sequence、taskId、from、to、timestamp。observer 抛错不能破坏 scheduler；交给 onObserverError。事件顺序用本进程 sequence 确定。

生产平台还应记录：队列等待、运行时长、失败类型、取消延迟、ready/running/terminal 数、graph size。不要把整个 payload/error 无限复制进事件；错误序列化要限制大小并避免敏感信息。

## 10. 测试异步调度：用 barrier，不用 sleep

测试任务返回手动控制的 deferred Promise：

```ts
function deferred<T>() {
  let resolve!: (value: T) => void;
  let reject!: (reason?: unknown) => void;
  const promise = new Promise<T>((res, rej) => { resolve=res; reject=rej; });
  return { promise, resolve, reject };
}
```

这样可精确断言：A/B 未 resolve 前 C 不启动；running 最大值；B reject 后哪些任务 blocked；cancel 后 signal.aborted；无需脆弱的 50ms sleep。

性质测试随机生成 DAG（先定一个随机 topo 顺序，只添加向后依赖），任务用受控完成顺序；最终验证每个 succeeded 的所有依赖 succeeded 且结束不晚于它开始（若记录时钟），每任务 run 次数<=1。

## 11. 容量与性能

构图 O(V+E)，topo O((V+E)+V log V 的稳定 ready)，运行阶段每任务最多一次 heap push/pop，约 O(V log V+E)，空间 O(V+E)。

真正瓶颈通常是任务本身、日志和外部 I/O。但百万小任务时对象/字符串/Promise 常数巨大；可以 ID 整数化、批处理、紧凑邻接、限制事件。不要用 Big-O 隐藏每任务一个 Promise/AbortController 的成本。

## 12. 从单机到生产还缺什么

- 持久任务/状态机与崩溃恢复；
- 多 worker claim、lease/heartbeat、可见性超时；
- 幂等 key、结果版本与重复执行；
- retry/backoff/jitter、dead letter 与人工恢复；
- 资源隔离、secret、权限和供应链安全；
- artifact 原子发布、缓存正确性；
- SLO、容量、审计和运维工具。

这些属于 Backend/架构/分布式系统课程。本项目的价值是为它们提供一个可验证的状态核心，不是替代它们。

## 13. 毕业验收

- 讲清每个 Map、heap、counter 的职责与不变量；
- 40+ 定向测试与随机 DAG 测试；
- 100k 节点链不因递归验证栈溢出；
- 失败/取消/observer throw 后状态一致；
- 提交 ADR：选择、替代、边界、容量、回滚；
- benchmark 多个 V/E/concurrency，报告环境、p50/p95、内存，不只给一个“耗时 20ms”；
- 对一段真实项目代码完成模型与证据驱动的重构。

## 14. 自检与 AI 追问

1. 为什么必须在任何 run 前完成 cycle 验证？
2. ready 与 pending 的事实区别是什么？
3. failed 后代为什么不可能已 running？
4. cancel 后为何还等待不合作的 run settle？
5. ready heap 中的 blocked stale entry 怎样安全处理？

交给 AI 时附上完整状态转移表、失败/取消语义、边方向、并发与排序契约、单进程边界。要求 AI 先列不变量和竞态，再评论代码，不要直接改写。
