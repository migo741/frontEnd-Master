# 第 09 章：CSS 架构与样式边界

## 架构目标是控制变化传播

CSS 的全局 cascade 是能力，也是风险。架构要回答：reset、tokens、base、components、utilities、vendor、overrides 谁能影响谁；组件公开哪些稳定样式接口；废弃如何迁移。

常见方案不是互斥宗教：

- 语义 class + layer：运行时轻、易跨框架，需命名纪律。
- CSS Modules：局部类名，无法自动隔离 token/元素规则。
- Vue scoped：通过属性选择器改写，Teleport/深层/slot 边界需理解。
- Utility-first：约束尺度、组合快；动态 class、重复模式和设计一致性需治理。
- CSS-in-JS：可贴近运行时状态，但 SSR、runtime cost、缓存与依赖生态要评估。
- Shadow DOM：真正封装树和样式，但主题、表单、可访问性、第三方工具有新边界。

选择方案看团队/发布/复用边界，不看流行度。一个产品可以由全局 tokens + Modules/scoped components + 少量 utilities 组成。

## 公共样式契约

组件消费者可依赖：公开 custom properties、parts、稳定状态属性、尺寸/variant props。不要让消费者写 `.dialog > div:nth-child(2)` 或滥用 `:deep()`。第三方覆盖放 vendor layer，并通过 adapter 收拢；升级时只改 adapter。

## Specificity budget 与删除能力

建立 selector 深度、important、z-index、token 等 lint 规则，但 lint 只防退化，不能替代设计。每个临时 override 要有 issue/owner/退出条件。架构成熟的标志是旧规则能安全删除。
