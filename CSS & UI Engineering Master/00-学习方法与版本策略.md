# 学习方法与版本策略

## 建立实验环境

准备一个最小 Vite 项目，但第 01～16 章的关键实验优先使用原生 HTML/CSS，避免框架和组件库遮住问题。建议工具：Chrome/Edge 与 Firefox DevTools、Safari 真机或远程调试、axe、Playwright、Lighthouse、WebPageTest，以及一个视觉回归工具。

每题至少保留：失败截图、最小复现、修复后截图、解释、回归检查。只保存最终漂亮页面，会丢失最有价值的推理证据。

## 四步调试法

1. **缩小**：删除框架和无关 DOM，得到最小复现。
2. **观察**：看 Computed、Layout、Accessibility、Layers，而非继续猜属性。
3. **建模**：指出 cascade winner、containing block、formatting context、intrinsic contribution 或 stacking context。
4. **回归**：用长文本、空数据、不同语言、缩放、键盘和浏览器重新验证。

## 新特性分级

- **生产必修**：目标浏览器矩阵已可靠支持，直接使用并测试。
- **渐进增强**：基础体验不依赖它；用 `@supports` 或结构性 fallback 增强。
- **观察项**：理解解决的问题，只做实验，不进入关键生产路径。

课程不会写死“兼容到某个浏览器版本”。发布前以自己的用户数据、MDN compat、Baseline 和真机结果为准。Autoprefixer 只能补语法前缀，不能修复布局语义和运行时行为差异。

## 练习纪律

- 不允许用 `!important`、随机大 z-index、固定高度、隐藏 overflow 蒙混，除非题目要求并解释代价。
- 不允许只在一个 viewport 截图验收。
- 不允许用组件库替代题目的机制实现。
- 动画必须测试 reduced motion；交互必须仅用键盘完成；颜色必须检查对比和强制色。
- 视觉差异先判断是否影响任务，再决定像素阈值；不要追求无意义的全页面零差异。

## 证据目录建议

```text
evidence/
├── screenshots/
├── traces/
├── accessibility/
├── browser-matrix.md
├── decisions.md
└── regressions/
```

每章在 `decisions.md` 写一句：“在什么约束下，我为什么选择这个布局/特性，失败时如何降级。”这句话比属性清单更接近高级工程师工作。
