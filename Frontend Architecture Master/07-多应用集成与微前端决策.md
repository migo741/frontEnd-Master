# 第 07 章：多应用集成与微前端决策

> 版本基线：截至 2026-08-16。微前端与跨端框架的实现会变，本章关注长期成立的边界、契约和运营责任。

## 1. 市场与业务问题

大型企业很少只有一个 Web 应用。

同一业务可能同时存在官网、H5、小程序、App WebView、Electron 桌面端和内部运营台。

多团队还会要求独立发布、分阶段迁移、技术栈共存和区域化交付。

这些压力让“微前端”听起来像自然答案，但多应用并不自动等于微前端。

真正的问题通常是：团队能否自治交付，同时保持用户任务、身份、数据和体验的一致性。

截至 2026 年的官方岗位样本同时强调多端架构、插件生态、独立交付、性能、安全和观测。

市场需要的不是会接入某个微前端库，而是能管理跨运行时兼容成本的人。

## 2. 本章非目标

- 不讲 qiankun、Module Federation 或 iframe 的接入步骤。
- 不重讲 React、Vue、小程序组件或 Electron API。
- 不假设所有页面必须共享组件，也不追求“一套代码运行所有端”。
- 不用微前端掩盖领域边界、团队责任或发布流程本身的混乱。

## 3. 先分清四种边界

**业务边界**回答一个能力为什么变化，例如订单、履约和会员各有不同规则。

**团队边界**回答谁有决策权、值班责任和发布权限。

**部署边界**回答哪些变更必须独立上线或回滚。

**运行时边界**回答代码是否共享全局对象、DOM、内存、网络凭证和故障域。

四种边界可能一致，也可能不同。

只有部署和团队自治是真实刚需时，运行时微前端的成本才可能值得。

一个团队维护五个路由，通常不需要五个运行时。

五个团队共用一个脆弱发布流水线，也不能只靠前端容器获得自治。

## 4. 集成方式是一架梯子

优先选择能满足约束的最低复杂度方案。

1. **导航集成**：应用通过普通链接或统一入口跳转，故障和发布隔离最强。
2. **共享协议**：统一身份、URL、事件和设计语言，但代码库彼此独立。
3. **共享包**：复用稳定的 token、类型、纯逻辑或组件，集成发生在构建期。
4. **服务端组合**：网关或页面服务组合片段，浏览器只接收一个文档。
5. **iframe 边界**：可牺牲部分体验换取较强运行时或遗留隔离；只有采用独立 origin，并按威胁模型配置限制性 `sandbox`、Permissions Policy 且校验 `postMessage` 时，才可把它视为安全隔离，同源 iframe 本身不是安全边界。
6. **运行时微前端**：一个壳在浏览器动态装载多个自治应用。

不要从第 6 层开始，再倒推“我们一定有这个问题”。

## 5. 跨端 capability matrix

| 维度 | Web / PC Web | H5 | 小程序 | App WebView | Electron |
| --- | --- | --- | --- | --- | --- |
| 发布控制 | 服务端与 CDN | 服务端与 CDN | 平台审核、灰度受限 | Web 与 App 双版本 | 安装包更新 + Web 资源 |
| Web 标准完整度 | 最高 | 受移动浏览器影响 | 平台自定义运行时 | 受内核与 App 版本影响 | Chromium / Node 版本固定 |
| 原生能力 | 浏览器权限模型 | 有限传感器与分享 | 平台 API | 依赖 Bridge | 主进程/预加载层可提供 |
| 离线能力 | SW / 本地存储 | 受系统回收影响 | 分包与本地缓存 | App 可托管资源 | 本地制品最强 |
| 安全主边界 | Origin / CSP | Origin / CSP | 平台沙箱与授权 | Bridge、Origin、App 权限 | contextIsolation、IPC、签名 |
| 版本风险 | HTML 与资产错配 | CDN 与机型长尾 | 基础库与审核版本 | App、Bridge、H5 三方错配 | 主进程、渲染进程、插件错配 |
| 观测难点 | 会话与发布关联 | 弱网/后台冻结 | 平台日志受限 | JS 与 Native trace 拼接 | 主/渲染进程与自动更新 |
| 适合复用 | 领域模型、协议、token | 同左，UI 需适配 | 纯逻辑和协议优先 | 协议、逻辑、有限 UI | 协议、逻辑、Web UI 较多 |

这张表的用途不是评选“最好”的端，而是暴露每个端不同的控制面。

## 6. 复用边界：先共享语义，再共享实现

最稳定的复用通常是领域术语、Schema、错误码、埋点字典和设计 token。

其次是无运行时假设的纯函数、状态机和协议适配器。

组件只有在交互、布局、可访问性和发布节奏都相似时才值得共享。

直接共享页面往往把端差异藏进条件分支，最终没有任何端真正可维护。

跨端复用率不是越高越好。

更有意义的是“重复修复率”“差异分支数”和“变更传播时间”。

允许少量有意重复，可能比一个充满环境判断的万能包更便宜。

## 7. Bridge 必须是版本化产品

WebView Bridge 或 Electron IPC 是跨信任域协议，不是随手挂在 `window` 上的函数集合。

协议应有显式版本、能力清单、请求与响应 Schema、错误分类、deadline 和取消语义。

启动时先协商 capability，而不是只比较一个 App 版本字符串。

调用方必须对“能力不存在、权限拒绝、宿主过旧、执行超时、结果未知”分别处理。

宿主只暴露最小能力，校验调用来源和参数，不把文件系统或任意网络代理直接交给页面。

高风险能力需要用户确认、审计和可撤销授权。

Bridge 兼容窗口至少覆盖仍在使用的 App 版本，而不是只覆盖最新商店版本。

## 8. 多版本兼容是常态

H5 可以当天发布，而 App 用户可能数月不升级。

小程序存在基础库、审核、灰度和回滚节奏差异。

Electron 自动更新失败时，旧主进程仍可能装载新远端页面。

因此协议变更默认采用“先扩展消费者、再生产新字段、最后删除旧路径”。

服务端不能用“前端会同时上线”作为唯一兼容保证。

每次请求带 client surface、app/bridge/schema version 和 release id，便于观测真实分布。

发现不兼容时应降级单项能力，而不是让整个应用白屏。

## 9. 运行时微前端何时成立

以下条件应大部分同时成立：

- 存在多个长期自治团队，而非临时项目小组。
- 业务域和页面所有权相对清晰。
- 团队确实需要独立发布与回滚。
- 单体流水线已经成为可测量的组织瓶颈。
- 壳、子应用和共享能力有明确长期所有者。
- 能承担重复依赖、加载、兼容、监控和支持成本。
- 有渐进迁移和退出方案，而非一次性重写。

如果目标只是“仓库太大”“路由太多”或“想同时使用 Vue 和 React”，先解决模块和依赖治理。

## 10. 参考架构

壳只拥有跨域稳定责任：认证入口、主导航、全局错误边界、版本协商和观测上下文。

子应用拥有一个业务域内的页面、状态、API adapter、发布和 SLO。

共享层只包含经治理的设计 token、协议、观测 SDK 和少量稳定组件。

业务数据不通过任意全局事件总线广播。

跨应用协作优先通过 URL、后端事实或带 Schema 的显式消息。

加载失败时壳应能隔离故障、展示可行动降级并保留导航。

版本注册表记录子应用版本、兼容范围、制品完整性和回滚指针。

## 11. 主要选项与权衡

**Build-time package**：类型和优化最好，但所有消费者受发布与升级传播影响。

**Module Federation 类运行时共享**：独立发布更强，但 singleton、版本协商和故障更难证明。

**HTML entry / sandbox 微前端**：适合遗留多栈迁移，代价是 DOM、样式和沙箱语义复杂。

**iframe**：可形成明确的运行时边界，代价是路由、可访问性、尺寸、性能和跨窗通信；安全边界仍取决于独立 origin、沙箱权限与消息校验。

**Server composition**：减少浏览器协调，但增加服务端拼装、缓存和局部失败设计。

没有一种选项同时最大化自治、性能、隔离、调试和一致体验。

## 12. 失败模式与反花架子门槛

- 为了展示技术先进，把一个团队的应用拆成多个子应用。
- 壳逐渐拥有所有业务逻辑，子应用只剩页面，自治名存实亡。
- 共享依赖强制 singleton，却没有版本兼容测试。
- 使用全局事件名传业务对象，没有 Schema、所有者或生命周期。
- CSS、路由、认证刷新和错误边界在组合后互相污染。
- 子应用发布成功，但壳无法发现不兼容版本。
- 每端宣称 90% 复用，实际被环境分支和 Bridge 兼容拖垮。
- 平台只提供接入脚手架，不提供观测、升级和退出支持。

反花架子门槛：没有团队自治指标、独立发布需求和运行时故障预算，就不批准微前端。

## 13. 平台与组织视角

微前端平台团队提供 paved road，不替业务团队承担领域责任。

平台应提供注册、契约校验、隔离默认值、版本可视化、灰度、回滚和故障演练。

子应用团队仍负责用户任务、数据正确性、性能预算和 on-call。

设计系统、身份、观测和发布团队需要共同定义少量跨应用协议。

例外必须可申请、可追踪、有到期日，而不是私下复制壳代码。

架构委员会定期删除不再需要的兼容层，防止平台只增不减。

## 14. 指标

- 子应用独立发布比例与等待其他团队的时间。
- 跨应用变更 lead time、失败率和回滚时间。
- 壳/子应用加载失败率、版本协商失败率和降级成功率。
- 重复运行时字节、长任务和核心旅程 INP/LCP。
- Bridge 调用按能力/宿主版本的错误率与 unknown 比例。
- 各端版本分布、旧版本兼容流量和淘汰周期。
- 平台采用率、例外率、升级耗时和支持工单。
- 跨端复用后的重复缺陷率，而不是单看代码复用百分比。

## 15. 架构评审清单

- 业务、团队、部署和运行时边界分别是什么？
- 不采用微前端时，最低复杂度方案为什么不够？
- 壳的职责是否稳定且足够小？
- 共享依赖的兼容范围如何验证？
- 跨应用消息是否有 Schema、所有者、超时和演进策略？
- Web/H5/小程序/WebView/Electron 各自 capability 是否显式？
- Bridge 如何协商版本、最小授权、审计和失败？
- 子应用失败能否局部降级，壳能否继续工作？
- 新旧端、新旧壳、新旧子应用如何并存？
- 谁负责平台升级、支持、值班和最终退出？
- 哪些指标触发停止扩展或回退？

## 本章结论

多应用架构的目标是让正确的团队在正确边界内安全自治。

微前端只是最高成本的集成选项之一，不是大型前端的毕业证。
先共享语义和协议，再谨慎共享实现；先证明独立发布价值，再承担运行时组合成本。
