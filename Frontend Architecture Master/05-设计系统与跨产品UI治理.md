# 第 05 章：设计系统与跨产品 UI 治理

> 版本基线：截至 2026-08-16。组件框架会变化；语义层级、共同所有权、采用治理和可访问性责任长期成立。

## 1. 市场与业务问题

多个产品重复实现按钮、表单和弹窗，通常只是最表面的浪费。

更昂贵的是同一概念在不同产品里有不同名称、状态、权限提示和错误恢复。

设计系统要降低这种决策重复，让产品更一致、可访问、可演进，而不只是少写 CSS。

官方岗位把组件库、工具链、复杂 B 端和平台复用列为高级能力，但真正门槛是治理和采用。

如果没有设计、产品和工程共同所有权，组件库很容易变成无人敢升级的依赖仓库。

## 2. 本章非目标

- 不教 React/Vue 组件 API、CSS 方案或 Storybook 配置。
- 不追求所有产品视觉完全相同。
- 不把设计稿自动生成代码当作系统治理。
- 不以组件数量、下载量或覆盖率单独证明价值。

## 3. 设计系统的层次

**原则**定义品牌、可访问性、内容和交互的共同方向。

**设计 token**表达颜色、间距、排版、圆角、动效和层级的语义值。

**基础原语**提供布局、文本、焦点、Portal 和响应式能力。

**通用组件**封装稳定交互，例如 Button、Dialog、Form Field。

**模式**描述组合后的用户任务，例如筛选、审批、批量操作和错误恢复。

**产品模板**给出推荐结构，但不夺走业务团队对流程的责任。

越靠下层越应稳定和广泛复用，越靠上层越接近具体业务。

## 4. 组件库不是设计系统

组件库回答“如何复用实现”。

设计系统还要回答为什么这样设计、何时使用、如何写内容、怎样测量和谁来演进。

一个成熟系统包含设计资产、代码、文档、测试、版本、迁移、支持和决策记录。

设计文件与代码若没有共享 token 和变更流程，很快会成为两个事实源。

只有代码没有设计治理，组件会被大量 wrapper 扭曲。

只有设计稿没有可复用实现，业务团队仍会重复造轮子。

## 5. Token 要表达语义

`blue-500` 是原始色值，`color-action-primary` 才表达用途。

语义 token 允许品牌、亮暗主题、高对比和不同产品在不改组件逻辑时变化。

token 层级通常包含原始值、语义值和组件局部别名。

层级过少会让产品直接依赖品牌色；层级过多又会产生难以理解的映射链。

token 是跨设计工具、Web、Native 和文档的协议，需要 Schema、版本和 owner。

删除或改变语义必须经过影响分析，不能只在设计文件里改名。

## 6. 跨产品一致不等于完全统一

统一应优先覆盖身份、导航、状态语言、错误、可访问性和高风险操作。

营销站、数据工作台和创作工具可以拥有不同密度与表达风格。

变体应来自明确产品需求，而不是每个团队的个人偏好。

推荐定义核心层、品牌层和产品扩展层，控制依赖方向。

产品扩展可以组合核心组件，不能修改核心包的私有 DOM 假设。

当差异长期大于共性时，复制一个有 owner 的局部实现可能更健康。

## 7. API 设计关注可组合性

高层组件若承诺处理所有布局、数据和业务状态，会形成巨大 props 矩阵。

过度 headless 又会让每个团队重复可访问性和交互细节。

稳定原语负责焦点、键盘、ARIA 和状态语义，产品负责业务数据与布局组合。

受控扩展点应有明确类型和样式边界，不暴露内部节点选择器。

默认值服务最常见路径，逃生口服务真实例外，并进入使用数据。

组件 API 的破坏性变化要像公开产品 API 一样治理。

## 8. 可访问性是系统级质量属性

基础组件统一焦点、键盘、对比度、语义和错误关联，可以放大收益。

但组件通过自动化检查不代表组合后的页面可访问。

Dialog 能正确陷阱焦点，业务仍可能给出错误标题或嵌套交互。

设计系统应提供键盘路径、读屏说明、内容指南和人工测试基线。

高对比、缩放、减少动效、国际化和右到左布局进入 release gate。

可访问性缺陷按用户任务和阻断程度分级，而不是只统计规则数。

## 9. 版本与兼容策略

组件包、token、图标和设计资产需要同一 release 叙事，但不一定锁成一个版本。

SemVer 只能描述承诺，不能自动发现视觉或行为破坏。

兼容 fixture 应覆盖主产品、主题、locale、浏览器和关键组合。

废弃先给替代、codemod、遥测和期限，再删除旧 API。

重大迁移使用 canary consumer 和分批升级，不要求全公司同日切换。

长期不升级的产品需要明确支持级别，而不是无限兼容。

## 10. 多框架与多端策略

优先共享 token、图标、内容规则、交互规范和测试契约。

React 与 Vue 组件实现是否共享，取决于团队规模、行为复杂度和维护能力。

Web Components 可作为运行时中立边界，但表单、SSR、样式和框架集成仍需验证。

小程序和 Native 更适合共享语义与设计资产，不应强求 Web DOM 组件复用。

复制生成代码能降低运行时耦合，却会增加更新传播和漂移检查。

“一套组件跑五端”必须用缺陷率和升级成本证明，而不是用复用百分比证明。

## 11. 设计系统的参考运营模型

核心团队包含设计、前端、内容、可访问性和产品运营能力。

业务团队通过贡献流程提交需求、实现或真实使用数据。

核心团队拥有稳定层和 release，业务团队拥有具体流程与局部组合。

RFC 记录新增模式、破坏性变化和跨品牌影响。

贡献者得到 review 时限、测试工具和维护责任，不能只把代码“捐给平台”。

定期 office hours、迁移诊所和版本看板比一份静态文档更能推动采用。

## 12. Build、Buy 还是组合

购买或采用开源系统能快速获得基础可访问性和生态。

自建适合品牌差异、复杂业务模式和长期平台能力确有竞争价值的组织。

完全自建意味着承担浏览器兼容、文档、测试、支持和安全响应。

完全套用外部 UI 又可能与业务密度、品牌和多端边界冲突。

常见可行方案是使用成熟无障碍原语，自有 token、视觉层和领域模式。

决策比较五年总成本，不只比较第一个页面的开发天数。

## 13. AI 与设计到代码

AI 可以生成候选页面、迁移调用和检查 token 使用。

模型需要读取当前组件目录、语义、禁用模式和可访问性规则。

生成代码必须只引用公开 API，并通过同一视觉、行为和契约测试。

截图相似不能证明状态、键盘、错误和响应式行为正确。

设计稿到代码流水线若绕开组件 owner，会更快制造不可维护的局部实现。

衡量 AI 产出的采用率、返工、违规和用户任务结果，不衡量生成组件数。

## 14. 失败模式与反花架子门槛

- 把 200 个业务组件搬进仓库，就宣布设计系统完成。
- 只统一颜色和按钮，不统一状态、错误和高风险操作。
- 每个产品包一层 wrapper，核心系统无法升级。
- token 命名按色值而非用途，换主题时全面破坏。
- 为覆盖所有例外构造巨大 props API。
- 用快照数量代替行为、可访问性和真实视觉验证。
- 平台团队追求采用率，却不计算业务迁移成本。
- AI 生成页面看起来一致，但没有键盘、加载和失败语义。

反花架子门槛：没有共同 owner、真实重复基线、迁移预算和采用支持，就先做局部共享，不建设“企业级设计系统”。

## 15. 指标

- 关键产品对核心 token、原语和模式的采用率。
- 同类交互重复实现数、wrapper 数和私有样式覆盖率。
- 新页面从设计到可用的 lead time 与返工率。
- 组件升级中位耗时、版本滞后和迁移失败率。
- 按任务分级的可访问性缺陷和恢复时间。
- 视觉/行为回归逃逸、跨主题和 locale 缺陷。
- 设计系统支持工单、文档搜索无结果和例外数量。
- 用户完成率、一致性投诉和核心流程错误率。
- 平台维护投入与业务节省的净值。

## 16. 架构评审清单

- 需要解决的是视觉差异、实现重复还是业务语义不一致？
- 哪些层应全局共享，哪些允许产品差异？
- token 是否语义化、版本化并跨设计与代码一致？
- 组件边界是否把业务数据和领域规则留给产品？
- 可访问性如何覆盖组合页面和人工验证？
- 多框架、多品牌和多端共享到哪一层最经济？
- Build/Buy 的五年维护、迁移和退出成本是什么？
- 破坏性变更如何发现消费者、灰度和迁移？
- 核心团队、贡献者和业务团队分别拥有何种责任？
- 平台采用是自愿净收益，还是行政推动？
- 哪些数据会证明某个组件不应继续共享？

## 本章结论

设计系统是一项跨产品的决策与交付能力，组件库只是其中一个载体。

成功来自语义 token、可组合边界、共同所有权、迁移支持和用户结果。
一致性不是消灭差异，而是让必要差异有规则、能观测、可持续演进。
