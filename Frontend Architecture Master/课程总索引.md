# 课程总索引

## 总体路线

本指南共 18 章，全部为阅读材料，不设置练习与答案。章节顺序遵循：判断问题 → 划分边界 → 建立共享能力 → 管理生产系统 → 推动持续演进。

## 第一阶段：架构基础

| 章 | 主题 | 读完应能做出的决策 | 优先级 |
| --- | --- | --- | --- |
| 01 | [架构师视角与质量属性](./01-架构师视角与质量属性.md) | 把需求改写成可验证的质量属性场景，识别取舍 | 核心 |
| 02 | [业务领域边界与前端模块化](./02-业务领域边界与前端模块化.md) | 对齐业务域、模块、运行时和团队所有权 | 核心 |
| 03 | [代码库策略与依赖治理](./03-代码库策略与依赖治理.md) | 选择 mono / multi-repo，控制依赖方向、版本和变更传播 | 核心 |

这一阶段先解决“为什么拆、按什么拆、怎样证明拆得对”。如果边界不清，后面的工具和平台只会更快地扩散混乱。

## 三条选修路线

### A. 复杂业务与 AI-native 产品工程师

核心路径 + 05 → 08 → 09 → 12 → 17。

重点是统一体验、全链路边界、渲染与流式交付、可靠发布，以及 AI 参与产品和研发后的治理。

### B. Web Infra / 前端平台工程师

核心路径 + 04 → 05 → 09 → 12 → 17。

重点是构建图、缓存正确性、工具链兼容、共享资产、质量平台、Golden Path 和开发者反馈。若目标岗位明确要求，再继续学习编译器、Rust 或 Node Native Addon。

### C. 多团队前端架构负责人

核心路径 + 05 → 07 → 08 → 09 → 12。

重点是组织边界、多应用集成、设计治理、交付一致性、渐进迁移和跨团队决策。

## 条件式技术索引

| 技术 | 满足什么条件才深入 | 对应章节 |
| --- | --- | --- |
| Monorepo | 多包变更需要原子提交，依赖图和统一策略能带来净收益 | 03、04 |
| Rust bundler / compiler | profiler 证明 JS 工具链是主要瓶颈，并有兼容与维护能力 | 04 |
| 设计系统 | 多产品重复解决相同交互，且有设计与工程共同所有权 | 05 |
| BFF | 客户端需要特有聚合、身份或演进节奏，且不复制领域逻辑 | 06 |
| 微前端 | 多个自治团队确实需要独立发布，运行时成本可被治理 | 07 |
| 跨端共享 | 已有多个运行时，且能先划清领域逻辑、UI 与原生能力的复用边界 | 07、09 |
| RSC | 框架支持、边界与缓存语义明确，收益可由 bundle / 数据瀑布证明 | 08 |
| Edge | 用户地理分布和延迟证明需要靠近用户执行，数据约束允许 | 08、09 |
| 浏览器 OpenTelemetry | 接受实验成熟度，并有抽样、隐私和成本策略 | 11 |
| Feature Flag | 有所有者、到期日、组合风险控制和自动清理 | 13 |
| 内部开发者门户 | 背后已有真正可自助的平台能力，而非只做服务目录页面 | 16 |
| AI Coding Agent | 仓库边界清楚、验证自动化、最小权限、变更可审计 | 17 |

## 章节之间的关键依赖

- 02 的边界决定 03 的代码库结构、06 的 API 责任和 07 的集成方式。
- 03 的依赖图是 04 增量构建、12 影响分析和 15 渐进迁移的基础。
- 08 的渲染选择必须与 09 的缓存、10 的体验数据和 11 的观测一起设计。
- 13 的发布控制依赖 10–12 的指标与验证，否则灰度只是慢一点地发布故障。
- 16 的平台只有在前面各章形成可复用的安全默认值后才值得建设。
- 17 的 AI 放大效应依赖模块、测试、供应链和平台反馈，不能提前绕过。
- 18 把所有决策放回团队所有权、投资组合和复审机制中。

## 阅读顺序的例外

遇到线上事故，可以先查 10、11、13、14；正在做遗留改造，可以先查 02、03、15；正在提案微前端，必须同时读 02、03、07、11、15；正在建内部平台，必须同时读 01、03、12、13、16、18。

## 版本与复审

每章优先引用官方标准、官方文档和可复核研究。对框架版本、实验 API 和岗位状态，按文档日期理解；对边界、反馈、回滚、所有权和演进原则，可作为长期决策框架。
