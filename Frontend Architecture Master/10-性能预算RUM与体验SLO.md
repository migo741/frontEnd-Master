# 第 10 章：性能预算、RUM 与体验 SLO

> 版本说明：涉及 Core Web Vitals 与浏览器能力的结论按 **2026-08-16** 的官方资料理解；阈值和 API 状态变化时，应复核官方文档。

## 本章要解决的市场与业务问题

高级前端不能只证明“我的电脑上很快”，而要回答：哪些真实用户在什么业务旅程中变慢，慢到什么程度，造成了多少失败，以及团队是否能在发布前后持续控制它。

国内大型产品常同时面对低端设备、弱网、WebView、跨地域 CDN、灰度版本和第三方脚本。平均值会把这些真实问题抹平，单次 Lighthouse 高分也不能代表生产体验。

性能治理最终服务三个结果：用户更容易完成任务、回归更早被发现、资源投入能解释收益。

### 非目标

- 不重复讲 Performance API、React memo 或打包器配置；
- 不把某个分数当作所有产品的统一目标；
- 不要求为了“绿色仪表盘”牺牲正确性、可访问性或安全；
- 不用昂贵监控替代清楚的用户旅程和数据责任；
- 不把性能团队变成替业务团队做优化的外包队。

## 1. 从资源速度转向用户旅程

页面加载只是旅程的一段。一个工单系统的真实旅程可能是：

```text
进入列表 → 筛选 → 打开详情 → 编辑 → 提交 → 看见可信确认
```

每一步都需要区分：能否开始、是否响应、是否稳定、是否成功、失败后能否恢复。

因此体验模型至少包含四类信号：

- 结果：任务成功率、放弃率、重复提交率；
- 等待：首次可见、首次可交互、操作到确认的端到端延迟；
- 连续性：布局跳动、输入丢失、导航中断、白屏；
- 恢复：重试、降级、刷新或重新进入后能否继续。

技术指标必须能映射到旅程。LCP 可能解释“主要内容何时可见”，INP 可能解释交互响应，但它们都不证明订单已经提交成功。

## 2. Lab、Synthetic 与 RUM 的职责

**Lab** 在受控环境中复现和诊断，适合 PR 回归、瀑布图、主线程与 bundle 分析。

**Synthetic** 由固定探针周期访问，适合发现区域、DNS、CDN 或关键路径可用性问题。

**RUM（Real User Monitoring）** 从真实会话采样，包含真实设备、网络、缓存、地区、账号状态和版本组合。

三者不是互相替代：

| 方法 | 最擅长 | 主要盲点 |
| --- | --- | --- |
| Lab | 可重复诊断与发布前比较 | 不代表真实人群分布 |
| Synthetic | 主动探测与稳定基线 | 无法覆盖全部交互和账号状态 |
| RUM | 真实分布与业务影响 | 噪声、隐私、采样和归因更难 |

成熟路径通常是 RUM 发现问题，Synthetic 确认外部路径，Lab 复现根因，再由 RUM 验证收益。

## 3. 分位数比平均数更接近用户

截至 2026-08-16，Core Web Vitals 官方“良好”参考仍常以页面访问的第 75 百分位判断：LCP 不高于 2.5 秒、INP 不高于 200 毫秒、CLS 不高于 0.1。

这些阈值是通用参考，不是产品全部 SLO。支付确认、内部操作台和内容详情有不同风险与等待语义。

至少按以下维度检查分布：

- 页面模板或核心旅程；
- 移动端与桌面端；
- 高、中、低设备等级；
- 网络类型与地区；
- 冷缓存、热缓存和 Service Worker 版本；
- release、Feature Flag 和实验 cohort；
- 新用户与高频用户；
- 正常成功、业务拒绝和技术失败。

切片过少会隐藏受害人群，切片过多会制造高基数和偶然结论。每个切片要有最小样本量与保留周期。

## 4. 体验 SLO 的最小模型

一个可操作的 SLO 需要：指标、合格事件、分母、窗口、目标、排除项和负责人。

示例：

```text
过去 28 天，受支持移动设备上符合条件的“保存工单”旅程，
99% 在 3 秒内显示服务端确认，且不发生重复写入。
用户主动取消、明确业务拒绝不进入技术失败分子，但分别计量。
```

这比“接口 p95 小于 500ms”更贴近用户。接口快而主线程阻塞、确认 UI 未提交或重试产生重复，都不算成功。

SLO 不应只有一个总数。通常需要组合：

- 关键旅程正确完成率；
- 旅程端到端延迟分布；
- crash-free / white-screen-free session；
- Core Web Vitals 分位；
- 数据丢失或重复副作用率；
- 可恢复失败比例。

## 5. 性能预算是变更约束

预算不是年终 KPI，而是每次变更可消费的有限空间。

可以分别预算：

- 路由初始 JS、CSS、字体和图片字节；
- 关键请求数量、优先级和最长依赖链；
- 主线程长任务数量与总阻塞；
- hydrate / render / worker 计算时间；
- 第三方脚本字节、CPU、网络和故障影响；
- RUM SDK 自身的 CPU、网络和存储成本；
- 旅程 p75/p95 与错误预算。

预算应按页面模板和设备等级配置，不能用营销页预算阻断复杂运营台，也不能用高端办公机掩盖公共移动端。

### 预算分配原则

1. 从用户目标和当前基线开始；
2. 把总预算分给可拥有的边界；
3. 为必要功能保留容量，而不是把基线永久合法化；
4. 预算变化需要证据、负责人和到期复审；
5. 超预算时比较产品收益、替代方案和恢复计划。

## 6. 参考数据架构

```text
Browser SDK
  → 本地聚合 / 脱敏 / 采样
  → 受限采集端点
  → Schema 校验与反滥用
  → 流式或批量处理
  → 指标仓库 + 事件仓库
  → release / flag / route / journey 维表
  → SLO、预算、回归检测与调查视图
```

浏览器事件必须带稳定、低基数的 `releaseId`、`routeTemplate`、`journeyStep` 和受控环境维度。

不要上报完整 URL、查询参数、输入内容、DOM 文本、Token 或任意错误对象。用户身份若非必要就不要采集；需要关联时使用短期、受控的会话标识。

接收端不能相信浏览器数值。它要限制 body、速率和字段，验证 Schema，隔离租户，并能丢弃异常流量。

## 7. 归因必须承认不确定性

发布后变慢不自动证明代码导致。网络、流量结构、第三方、设备比例和实验分流也会变化。

应比较同时段新旧 release 或 canary/control，并固定页面、设备、网络切片，再用 Lab trace 验证机制。小样本改善不能直接写成业务结论；公开样本量、缺失率、采样策略和不确定区间。

## 8. 发布门禁的三种选择

**硬门禁**：明显突破安全上限或确定性 bundle 预算时阻断；优点是强，缺点是容易被噪声和紧急需求绕过。

**软门禁**：在 PR 显示差异并要求 owner 解释；适合早期治理，但没有责任时会变成背景噪声。

**生产自动判定**：canary 对照真实指标扩量或回滚；最接近真实用户，但依赖可信数据、足够流量和快速恢复。

通常三者组合：确定性制品预算硬阻断，实验室趋势要求评审，真实体验决定渐进扩量。

## 9. 平台与组织视角

平台团队应提供统一事件协议、轻量 SDK、release/flag 关联、查询模板、预算门禁和隐私默认值。

业务团队仍拥有旅程定义、目标阈值、回归处理和产品取舍。平台不能替所有页面设同一个 SLO。

设计、产品、服务端和数据团队要共同解释旅程：前端无法单独修复慢 API，服务端也无法看到主线程或渲染等待。

建议建立“体验 owner”而非“分数 owner”。其责任是推动跨边界结果，不是让某张图永远为绿色。

## 10. 常见失败模式

- 只看全站平均 LCP，忽略低端设备和关键页面；
- 把 Lighthouse 100 分当作生产体验；
- 每次事件上报完整 URL 和用户输入，制造隐私事故；
- RUM SDK 比业务代码更重，或在主线程同步序列化大对象；
- 没有 release/flag 维度，发现回归却无法归因；
- 用错误条数而不是受影响会话比例告警；
- 用统一阈值惩罚不同业务，却不提供优化路径；
- 只优化加载，不测提交确认、恢复和重复操作；
- 指标提升但转化无变化，仍宣称项目成功。

## 11. 反花架子门槛

建设 RUM 或性能平台前，至少满足：

- 已定义三条最重要用户旅程及失败语义；
- 能把事件关联到确切 release 和页面模板；
- 有隐私清单、保留期限、采样和删除机制；
- 有一个真实回归能通过数据发现并复现；
- 超预算有 owner、处理期限、例外到期和升级路径；
- 平台开销本身被测量；
- 指标能触发扩量、回滚、优化或停止投资。

若只是采购 SDK、做大屏、每周播报分数，不算体验治理。

## 12. 建议指标

- 关键旅程成功率与 p75/p95 完成时间；
- LCP、INP、CLS 的 p75 及差设备切片；
- white-screen-free、crash-free session；
- 发布引入的体验回归率；
- 从回归出现到检测、归因、恢复的时间；
- 性能预算例外数量、年龄与按期关闭率；
- 第三方脚本占字节、CPU 与事故比例；
- RUM 覆盖率、缺失率、采样偏差和采集成本；
- 每项优化对应的业务结果或风险下降。

指标用于改善系统，禁止直接按个人页面分数考核，否则团队会删监控、改分母或回避复杂场景。

## 13. 架构评审清单

- 目标是哪个用户旅程，而不是哪个工具分数？
- 分母、窗口、排除项和失败终态是否明确？
- 是否查看分位数和关键人群，而非平均值？
- Lab、Synthetic、RUM 各自承担什么职责？
- 事件能否安全关联 release、flag、route 和后端请求？
- 预算是否覆盖字节、主线程、第三方与端到端结果？
- 数据是否最小化、可删除、有限保留并防高基数？
- canary 数据不足或遥测故障时如何判定？
- 超预算谁处理，例外何时到期？
- 什么证据会让团队放弃当前优化方案？

## 本章结论

体验工程不是把页面分数刷绿，而是把真实用户的关键任务变成可分解、可观测、可预算、可回滚的长期契约。高级前端的价值在于连接浏览器证据、业务结果和组织行动。
