# 第 08 章：渲染架构——SSR、RSC、Edge 与缓存

> 版本基线：截至 2026-08-16。React 与框架功能状态以各自官方文档为准；本章不把 RSC 或 Edge 设为默认答案。

## 1. 市场与业务问题

渲染架构决定用户多久看到有用内容、多久能交互、服务器承担多少工作，以及数据能否安全缓存。
电商落地页、登录后工作台、实时协作和 AI 流式界面显然不应使用同一套默认策略。
现代框架把 CSR、预渲染、SSR、流式、Server Components 和 Edge 放在同一产品中，选择因此更容易被营销名词绑架。
架构师的任务不是选择一种渲染方式统治全站，而是按页面和数据生命周期组合机制。
截至 2026 年，RSC 已进入主流 React 全栈框架，但生态、缓存语义和部署约束仍随框架演进。
Edge 平台已经成熟可用，但“离用户近”不等于“离数据近”，更不保证总延迟更低。

## 2. 本章非目标

- 不重讲 React hydration、Suspense 或 Next.js 路由 API。
- 不给出某个框架配置模板。
- 不把 SEO 当作所有页面 SSR 的充分理由。
- 不用实验室首屏分数掩盖服务器成本、缓存泄漏或交互退化。

## 3. 从页面质量属性开始

每个 route 先回答：

- 内容是否公开、可共享、可缓存？
- 首次可见内容对转化和搜索是否关键？
- 个性化发生在页面、区域还是交互后？
- 数据的新鲜度窗口是多少？
- 用户、数据源和计算资源分别在哪里？
- 页面需要多少客户端交互和离线能力？
- 峰值流量与服务端预算是多少？
- 失败时能否返回陈旧内容或静态壳？

这些答案比“团队喜欢 Next.js”更接近架构事实。

## 4. 渲染选项矩阵

| 方式 | 适合 | 主要收益 | 主要代价 |
| --- | --- | --- | --- |
| CSR | 登录后高交互、SEO 弱、客户端长期会话 | CDN 简单、交互模型统一 | 冷启动、数据瀑布、弱设备成本 |
| SSG | 内容稳定、可批量生成 | 极低源站负载、缓存简单 | 构建爆炸、更新与预览复杂 |
| 按需预渲染 | 大量可缓存页面、允许短暂陈旧 | 兼顾规模与首屏 | 失效、首请求和并发再生语义 |
| SSR | 请求级数据、首屏关键 | 首次内容完整、可流式 | 服务成本、尾延迟、缓存风险 |
| RSC | 可在服务器取数且需减少客户端 JS 的 React 子树 | 服务端组件代码不进客户端包 | 边界、序列化、缓存和框架耦合 |
| Edge render | 计算可在边缘完成且依赖也靠近边缘 | 降低部分网络 RTT | 运行时限制、数据远端、观测和成本 |

一个产品可同时使用以上多种方式。

## 5. 参考决策流程

公开且长时间稳定的页面先考虑静态化。
公开但更新频繁的页面考虑 CDN 缓存 SSR 或按需再生。
高度个性化、交互密集的工作台先评估 CSR + API 是否已满足 SLO。
首屏关键且数据请求瀑布明显时，再比较 SSR、服务端数据装配和 RSC。
需要全球低延迟时先画出用户、边缘、身份源、数据库和第三方的真实距离。
任何升级都从 route 或 island 试点，不直接迁移整个应用。

## 6. RSC 的正确心智模型

RSC 是“哪些组件代码在服务器执行、哪些值跨边界传输”的架构边界。

它不是更快的模板语言，也不自动替代 API、缓存或客户端状态。

Server Component 可以直接接近服务端数据，但必须经过授权和数据最小化。

传给 Client Component 的 props 会跨序列化边界，应视作公开给浏览器的数据。

边界切得太细会制造大量序列化和心智开销。

边界切得太粗又会把交互区域全部推回客户端 bundle。

RSC payload、框架路由、部署制品和缓存通常存在版本耦合，需要原子发布与兼容设计。

采用 RSC 前应证明客户端 JS、取数瀑布或服务端组合确实是主要瓶颈。

## 7. 为什么 RSC 不是默认

纯客户端 B2B 工具可能从它获得很少业务收益。

团队若还不能稳定管理 SSR、缓存和 Server/Client 边界，RSC 会放大而不是消除复杂度。

多区域部署、第三方数据、细粒度权限和离线场景可能限制收益。

框架升级会改变缓存、路由和请求合并行为，平台团队必须拥有兼容测试。

“少发 JavaScript”是可验证假设，不是免评审口号。

## 8. Edge 的正确使用条件

Edge 适合轻量路由、地域选择、A/B 决策、鉴权前置、缓存命中和靠近边缘的数据访问。

若每次 Edge 请求仍需跨洲访问中心数据库，总延迟可能更差。

受限运行时、冷启动、连接复用、包大小和 Node API 兼容都要实测。

数据驻留、密钥、日志和调试能力必须满足合规与运维要求。

Edge 故障应可回源或降级，不能成为新的单点入口。

只有用户地理分布和端到端 trace 证明网络距离是主要瓶颈时，才扩大使用。

## 9. 缓存是一组层，不是一个开关

典型路径包含浏览器缓存、Service Worker、CDN、框架页面缓存、应用数据缓存和数据库缓存。

每层都要说明：key、value、owner、TTL、新鲜度、失效、权限维度和故障行为。

缓存 key 必须覆盖影响响应的 locale、tenant、身份级别、实验和内容版本。

不能把 Authorization header 存在当作“自动私有缓存”的保证。

公开内容可用长 TTL + stale-while-revalidate。

个性化内容默认 private/no-store，除非有可证明的分区策略。

缓存失效事件可能丢失，TTL 和版本仍需兜底。

同一热 key 再生要请求合并，避免缓存击穿压垮数据源。

## 10. 缓存一致性场景

**内容更新**：允许一分钟陈旧，可异步 purge 并保留 stale-if-error。

**价格变化**：展示缓存与结算权威源分离，界面明确最终确认点。

**会员撤权**：不能返回 stale allow，高风险动作重新校验权威状态。

**发布新版本**：页面 payload、客户端 chunks 和 action 协议必须兼容或原子切换。

**多区域**：失效传播有延迟，版本戳比“通知已发送”更可信。

架构文档应逐类写，而不是给全站一个统一 TTL。

## 11. Streaming 的真实收益与风险

Streaming 可以先交付稳定壳和高优先级内容，降低用户感知等待。

它不能让慢依赖本身变快，也可能拉长服务器连接和增加中途错误处理。

边界需要有独立 fallback、超时和取消。

代理、CDN 和压缩链路必须确认不会缓冲整个响应。

客户端应区分“仍在加载、部分失败、整体失败”，不能无限骨架屏。

对 AI 输出还要处理断连续传、内容安全和最终状态确认。

## 12. 身份与安全边界

服务器渲染不意味着可以把 secret 或内部对象序列化到页面。

取数函数必须获得明确 principal/tenant，而非读取不透明全局状态。

共享缓存前先证明响应不含用户差异。

Server Action 或表单写仍需要授权、CSRF、幂等和审计。

错误 payload 不泄漏堆栈、查询或内部标识。

服务端渲染的第三方 HTML 仍需转义和内容策略。

## 13. 失败模式与反花架子门槛

- 全站改 SSR，只因为希望 SEO 更好。
- 把 TTFB 变快当成任务完成更快，忽略 INP 和客户端长任务。
- 在 Edge 执行，但数据库仍在遥远单区。
- 缓存 key 漏 tenant/locale/实验，导致数据串用。
- purge 后立即删除旧制品，长会话的懒加载 chunk 404。
- RSC 边界随文件随意切，没有 bundle 与瀑布基线。
- Streaming 没有超时和局部错误，连接卡住比原来更久。
- 框架默认缓存行为无人能解释，却宣称“自动优化”。

反花架子门槛：没有 route 级基线、数据分类、容量成本和回滚试点，不批准全局渲染迁移。

## 14. 平台与组织视角

平台提供受支持的渲染模板、缓存策略、身份 adapter、trace 和发布兼容检查。

业务团队拥有 route 的新鲜度、数据权限、体验 SLO 和降级内容。

安全团队定义数据可缓存级别，不逐页面手工审批实现细节。

SRE 与前端共同看浏览器 RUM、CDN、渲染服务和数据源的同一条 trace。

框架升级先跑 frozen route fixtures、缓存隔离和多版本兼容测试。

例外策略要有 owner、到期日和复审数据。

## 15. 指标与成本

- 按 route、地区、设备的 LCP、INP、TTFB p75/p95。
- 首屏关键内容时间与核心任务成功率。
- 客户端 JS 字节、执行时间、hydration/RSC 错误。
- CDN/页面/数据缓存命中率和错误命中率。
- 渲染服务 CPU、内存、并发、尾延迟与单请求成本。
- 数据源调用数、瀑布深度和 request collapse 效果。
- Edge 到数据源 RTT、回源率和区域故障率。
- stale served、purge 延迟和权限缓存违规数。

只优化其中一个指标容易把成本推到另一层。

## 16. 架构评审清单

- 决策是 route 级还是被错误扩大到全站？
- 公开、个性化、敏感数据分别如何处理？
- CSR/SSG/SSR/RSC 的可行替代方案比较了吗？
- RSC 减少的 JS 或瀑布有真实基线吗？
- Edge 是否真的更靠近数据和依赖？
- 每层缓存 key、新鲜度、失效和 owner 是什么？
- HTML、RSC payload、chunks 和服务端 action 如何多版本兼容？
- Streaming 的局部超时、错误与取消如何工作？
- 峰值容量、成本、降级和回滚是否演练？
- RUM 能否与 CDN、服务器和数据源关联？
- 哪些反证信号会停止扩展？

## 本章结论

渲染架构是页面、数据和运行环境的组合决策，不是一场框架站队。

RSC 要用 bundle、瀑布和体验收益证明，Edge 要用真实地理链路证明。

先把缓存和多版本语义写清楚，再谈“服务器优先”或“边缘优先”。
