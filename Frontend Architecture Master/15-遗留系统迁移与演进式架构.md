# 第 15 章：遗留系统迁移与演进式架构

> 版本说明：框架迁移建议按 **2026-08-16** 的官方升级文档复核；本章的兼容、证据、单写所有权和渐进删除原则不依赖具体框架。

## 本章要解决的市场与业务问题

遗留系统通常仍在创造收入。它的问题不是“旧”，而是变更成本、故障风险、人才供给或业务边界已经不匹配。

重写最容易画出漂亮目标图，却最难同时承受业务变化、隐藏规则、数据迁移和长期双轨成本。高级工程师的任务是设计一条每一步都可交付、可验证、可回退的演进路径。

### 非目标

- 不因 Vue/React 版本旧就自动迁移；
- 不把微前端当万能迁移框架；
- 不要求目标架构一次完整落地；
- 不长期双写两个真相；
- 不用代码行数或新框架占比代表业务价值；
- 不在没有 owner 和删除期限时增加兼容层。

## 1. 先证明为什么迁移

可成立的驱动包括：

- 关键需求前置时间持续上升；
- 变更失败和恢复时间不可接受；
- 安全版本、浏览器或平台已不受支持；
- 模块边界与团队所有权长期冲突；
- 招聘与维护风险明显；
- 合规、数据或可访问性必须整改。

“技术栈不时髦”不是充分理由。基线必须含用户、业务、质量、成本和组织数据。

## 2. 建立遗留资产地图

至少盘点：

```text
用户旅程 / 页面与路由 / 领域能力 / 数据与写入
API 与事件 / 浏览器与容器 / 构建发布 / 第三方
共享状态 / 认证授权 / 监控告警 / 团队 owner
```

代码依赖图只能看到显式 import，看不到运行时配置、复制代码、运营流程、手工发布和隐式数据契约。

从生产流量、日志、支持工单、数据库访问和访谈补齐“真实使用”，不要仅凭 README 估计。

把资产标记为：保留、替换、封装、合并、冻结、删除、未知。未知项先增加观测，不急着重写。

## 3. 目标是质量属性，不是目录结构

目标状态应写成可验证场景，例如：

- 工单领域的变更不要求修改三个无关应用；
- 新旧客户端在 90 天窗口内都能保存；
- 单路由 canary 可在 10 分钟内回退；
- 关键旅程数据一致且无重复写；
- 迁移期间错误率和 p75 体验不劣于基线；
- 旧路径在确定日期停止流量并删除。

先定义这些约束，再决定 monorepo、模块、BFF 或微前端。

## 4. 迁移模式工具箱

**Strangler by capability**：新请求逐领域/旅程进入新实现，旧系统逐步缩小。

**Branch by abstraction**：先建立稳定 port/facade，再在后面替换实现。

**Parallel change**：先 expand 兼容契约，再切消费者，最后 contract 删除旧结构。

**Shadow/dual read**：新路径不影响用户地运行，比较结果和性能。

**Codemod**：适合语法/API 的机械变更，配合类型、测试和抽样 review。

**Compatibility adapter**：隔离旧协议，但必须有 owner、指标和到期。

**Route cutover**：按路由、租户、地区或 cohort 渐进切流。

这些模式可以组合，但每增加一种过渡状态，都增加观测和支持成本。

## 5. 选择切片方式

优先垂直业务能力，而不是“先重写全部基础组件，再重写全部 API”。垂直切片能交付用户价值并验证端到端边界。

好的首个切片通常：

- 价值可见但风险可控；
- 依赖代表性足够；
- owner 清楚；
- 有真实流量与回退；
- 能暴露目标架构的未知点；
- 不要求同时迁移全部数据。

不要只选完全独立、无真实复杂度的页面，然后据此宣称整场迁移可行。

## 6. 单写所有权是不变量

双读可以对比，双写最危险。两个系统各自写权威状态会产生顺序、部分失败、重试和冲突。

迁移期间明确每项数据的唯一 writer。新系统需要影响旧数据时，通过权威 API、事件或受控 adapter，而不是直接写两份表/Store。

若业务必须短期双写，至少需要：

- 全局 operation id 和幂等；
- 主写与副写的成功语义；
- Outbox/可恢复任务；
- 差异对账和补偿；
- 明确最大窗口；
- 停止双写与选定权威源的计划。

## 7. 状态、身份与导航边界

新旧 UI 共存时最容易出问题的是共享 Session、权限、URL、全局状态、CSS 和事件。

建议通过明确契约传递 principal、tenant、locale 和有限上下文；不要共享一个可任意修改的全局 Store。

URL 是用户书签、刷新、客服和观测契约。迁移路由需要 redirect、deep link、历史链接和 SEO 计划。

认证由可信服务统一，子应用不能各自解释 Token。权限仍在服务端资源边界执行。

## 8. 兼容矩阵与截止时间

记录生产中实际存在的：

- 旧/新 HTML 与静态资产；
- 旧/新 API 和 BFF；
- Service Worker/cache 版本；
- 消息和事件 Schema；
- 浏览器/WebView/客户端版本；
- Flag 和迁移 cohort；
- 数据 Schema 与后台任务。

明确允许组合、测试证据和停止支持日期。没有期限的兼容会成为永久架构。

删除前看真实使用与业务 owner，不只看代码引用；动态加载、外部消费者和离线客户端可能不在静态图里。

## 9. 双轨验证

Shadow 或 dual read 比较时，应区分：

- 语义差异；
- 排序、舍入和时间差异；
- 新旧数据快照时点；
- 权限和租户差异；
- 性能与资源成本；
- 无法比较的非确定结果。

不要仅比较 JSON 字符串。先规范化允许差异，再把不可接受差异按领域分类和审计。

新路径未获得写所有权前，shadow 禁止真实副作用；外部调用用 fake、record/replay 或受控验证器。

## 10. 发布、回退与止损

每个切片都要有：入口 Flag、cohort、观测、数据兼容、回退步骤和旧路径保留时间。

回退不是“切回旧 UI”这么简单。新路径若写入旧版本无法读取的数据，必须先保持向后兼容或提供可验证转换。

定义止损信号：错误预算、业务差异、支持工单、迁移速度、双轨成本、关键人员负担。达到阈值就暂停扩量，而不是用 sunk cost 继续。

## 11. 测试与证据

迁移需要三类证据：

- 行为：关键旅程和业务不变量一致；
- 兼容：兼容窗内仍活跃或可回退的制品、API、缓存和数据可共存；窗口由驻留、缓存、回滚及消费延迟证据决定；
- 运营：canary、回退、对账和 runbook 实际可用。

从生产事故和支持案例建立 golden corpus，但必须脱敏。高价值旅程用真实浏览器和依赖契约验证。

旧测试不一定代表正确需求，新测试也可能只复刻新实现。用领域 owner 和生产事实审查断言。

## 12. 团队与所有权迁移

架构切换而团队边界不变，新的模块很快会恢复旧耦合。

每个能力要指定长期 owner、on-call、变更接口和依赖。临时迁移小组负责方法与加速，不能永久拥有所有新代码。

为业务团队提供 Golden Path、codemod、迁移 office hours 和清晰例外。只发公告要求“月底全部升级”会制造隐藏分叉。

关键知识写进 ADR、契约、测试和平台规则，不只留在重构主 R 的脑中。

## 13. 删除旧系统是交付内容

迁移完成条件包括：

- 生产流量为零并经过观察窗口；
- 外部消费者确认或超过支持期限；
- 数据、审计和保留义务已处理；
- Flag、adapter、双写、旧监控和权限删除；
- 域名、CDN、密钥、runner 与成本释放；
- runbook、文档和 owner 更新；
- 回退窗口关闭有明确批准。

只把旧入口隐藏不算完成，它仍会消耗安全、升级和认知成本。

## 14. 常见失败模式

- 推倒重写两年，业务仍在旧系统变化；
- 只迁组件，不迁领域边界和所有权；
- 新旧系统长期双写，无对账和截止；
- 迁移进度按代码行数，不按用户旅程和旧成本删除；
- 兼容 adapter 无 owner，逐渐变成永久核心；

## 15. 反花架子门槛与指标

迁移启动前至少有：驱动数据、资产地图、首个垂直切片、唯一 writer、兼容窗口、回退和长期 owner。

建议指标：关键变更前置时间、变更失败/恢复、迁移旅程比例、真实流量切换、双轨差异、旧路径调用、adapter/Flag 年龄、旧依赖和基础设施成本、支持工单、目标边界违规、删除完成率。

框架版本覆盖率只能作为过程信号，不能代替业务、质量与认知负担改善。

## 16. 架构评审清单

- 迁移驱动是否有基线和业务价值？
- 每项数据是否只有一个权威 writer？
- 新旧身份、权限、URL、缓存和事件如何兼容？
- dual run 如何防副作用并分类差异？
- 每一步是否可发布、可观测、可暂停、可回退？
- adapter、Flag 和双轨何时删除？
- 什么止损信号会让方案调整或停止？
- 旧系统的域名、密钥、制品和成本如何真正下线？

## 本章结论

演进式架构不是更慢的重写，而是把风险切成可交付、可观测、可撤销的变化。迁移真正完成的标志不是新代码出现，而是旧路径、双轨成本和错误所有权被安全删除。
