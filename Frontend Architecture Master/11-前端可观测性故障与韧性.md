# 第 11 章：前端可观测性、故障与韧性

> 版本说明：截至 **2026-08-16**，OpenTelemetry JavaScript 官方仍把浏览器客户端 instrumentation 标为实验性；生产采用时必须用自有语义层和 adapter 隔离变化。

## 本章要解决的市场与业务问题

浏览器是不可控的分布式运行环境：版本不同、扩展不同、缓存不同，用户可能离线、切后台、关闭页面，网络和 CDN 还会产生部分失败。

真正困难的不是“收集更多日志”，而是把一次用户失败关联到确切 release、flag、资源、请求与业务状态，并在依赖异常时让用户安全恢复。

### 非目标

- 不重复解释 logs、metrics、traces 三个名词；
- 不把浏览器遥测等同于服务端全量 tracing；
- 不承诺捕获每一次崩溃或页面关闭；
- 不用无限重试掩盖可靠性问题；
- 不把 Error Boundary 当作事故已经处理完成；
- 不让观测 SDK 获得无边界的用户数据。

## 1. 先定义前端故障终态

“出现错误”不一定是故障，“没有错误”也不代表成功。

建议按用户结果分类：

- 成功：权威系统确认，UI 与事实一致；
- 业务拒绝：规则明确拒绝，用户知道下一步；
- 可恢复失败：重试、降级或重新进入可继续；
- 不确定结果：请求可能已成功，但客户端未收到确认；
- 不可恢复失败：当前会话无法安全继续；
- 数据风险：可能丢失、重复、错租户或越权；
- 用户取消：通常不是系统错误，但要与超时区分。

告警优先级应由用户伤害和数据风险决定，而不是异常堆栈是否醒目。

## 2. 关联模型比日志数量重要

一次调查至少需要以下身份：

```text
releaseId → sessionId → journeyId → operationId → requestId / traceId
       ↘ flag/experiment ↘ route ↘ resource/chunk ↘ backend result
```

`releaseId` 对应不可变前端制品；`sessionId` 应短期且不直接等于用户身份；`operationId` 关联一次业务意图；`requestId/traceId` 连接网络与服务端。

这些 ID 不能替代认证、授权或幂等键。浏览器提交的 tenant、user 或 baggage 都是不可信输入。

## 3. 事件协议是公共 API

推荐定义小而稳定的事件 envelope：

```json
{
  "schemaVersion": 3,
  "event": "ticket.save.failed",
  "occurredAt": "2026-08-16T08:00:00Z",
  "releaseId": "web@abc123",
  "routeTemplate": "/tickets/:id",
  "journey": "ticket-edit",
  "operationId": "opaque-short-lived-id",
  "outcome": "unknown",
  "errorCode": "NETWORK_AFTER_SEND"
}
```

字段要有类型、枚举、大小上限、所有者和演进规则。禁止把任意对象 spread 进事件。

错误 message、URL、DOM、请求响应体和 breadcrumb 都可能含 PII 或秘密；采集前做 allowlist，而不是事后靠正则脱敏。

## 4. 浏览器证据的天然缺口

页面崩溃、进程被系统回收、用户断网或关闭标签页时，最后事件可能永远发不出去。

因此不要把“没有收到失败事件”当成功。关键业务结果应由服务端权威事件或对账确认，浏览器遥测用于解释体验路径。

`sendBeacon`、keepalive fetch、本地队列都只能提高送达概率，不能提供 exactly-once。接收端应幂等、限流，并容忍延迟与重复。

客户端时钟可能偏移。持续时间用单调时钟；跨系统排序依赖服务端接收时间、序列或业务版本。

## 5. OpenTelemetry 浏览器边界

OpenTelemetry 的价值在开放协议、上下文传播和供应商可替换性，而不是要求所有前端事件都变成 span。

截至 2026-08-16，浏览器端官方状态仍要求谨慎：API、instrumentation 覆盖、语义约定与 bundle 成本可能变化。

采用时建议：

1. 业务代码只依赖内部 `TelemetryPort`；
2. adapter 再对接 OTel SDK 或供应商；
3. 只为导航、关键操作和网络创建有限 span；
4. token、DOM 文本、完整 URL 不进入 attributes；
5. 明确采样、flush、失败与卸载语义；
6. 用 bundle 和主线程预算约束 SDK；
7. 版本升级先在 canary 验证数据连续性。

浏览器自动 instrumentation 不能知道“保存工单是否业务成功”。领域事件仍要显式建模。

## 6. Trace Context 的信任边界

可向同意接收的同源/BFF 请求传播 W3C Trace Context，从而把用户操作与服务端 trace 关联。

不要无条件向第三方域名传播内部 trace 或 baggage；这可能泄漏拓扑、租户和实验信息，也可能触发额外 CORS 预检。

服务端应重新生成或验证规范上下文，不能把浏览器 trace 字段当身份和授权事实。

跨异步、离线重放或长任务时，link 往往比强行维持父子 span 更符合因果关系。

## 7. 错误分类与归属

至少区分：

- 代码不变量：渲染/状态机进入不可能状态；
- 资源故障：JS chunk、CSS、字体、图片加载失败；
- 网络故障：DNS、TLS、断线、代理、超时；
- 服务故障：5xx、限流、不可用或协议不兼容；
- 数据冲突：版本过期、重复操作、不确定提交；
- 环境故障：旧浏览器、WebView、扩展、配额不足；
- 安全拒绝：CSP、权限、完整性或策略阻断；
- 用户/业务事件：取消、校验失败、正常拒绝。

分类决定 UI、重试、采样、owner 和告警。一个 `catch (e) { report(e) }` 无法完成这些决策。

## 8. 韧性来自显式降级

前端可以提供的恢复模式包括：

- 路由级错误域，保留 shell 与其他任务；
- stale-but-labeled 只读数据，明确更新时间；
- 保存本地草稿，但不伪装成服务端成功；
- 对幂等读取做有预算的退避重试；
- 对不确定写入先查询操作状态，不盲目重发；
- chunk 失败时识别版本漂移，安全提示刷新；
- 非关键第三方失败时移除对应能力；
- 实时连接断开后按序列恢复，而不是只重新连；
- 提供人工替代路径和追踪编号。

降级必须在正常发布中演练。没有测过的 fallback 常在主路径故障时一起失败。

## 9. 重试、超时与取消的前端语义

每个用户操作应有总 deadline，而不是请求层、Query 层和组件层各重试三次。

只对可重试且副作用安全的失败重试，尊重 `Retry-After`，使用 backoff+jitter，并在页面离开或新操作取代旧操作时传播取消。

“停止等待”不等于服务端没执行。写请求超时后进入 unknown，而不是直接显示失败并允许无限次提交。

平台 SDK 可以提供默认策略，但业务必须声明操作的幂等性、恢复查询和用户文案。

## 10. Source Map 与 release 服务

生产堆栈只有在 map 与确切制品匹配时才有意义。

平台应在构建时上传私有 source map，绑定 release/digest，部署侧传递同一 release ID，并按保留策略删除。

不要公开部署 `.map`，也不要把源代码和秘密写进 map。上传失败是否阻断发布取决于风险，但必须可见，不能静默生成不可调查版本。

资源和错误平台还应知道 chunk manifest，才能判断 404 是 CDN、清理过早还是 HTML/资产版本漂移。

## 11. 事故响应闭环

```text
发现影响 → 确认范围 → 止血 → 保留证据 → 归因 → 修复
→ 渐进恢复 → 验证用户结果 → 复盘 → 更新门禁/默认值
```

止血可以是回滚、关闭 flag、禁用第三方、切只读或扩大旧资产保留，不一定立即写代码。

事故面板先展示旅程影响、release、flag、地区与时间线，再下钻堆栈。否则值班者必须先猜根因才能找到图。

复盘行动要修改系统：测试、预算、观测、发布规则、owner 或架构边界。只写“加强关注”没有价值。

## 12. 平台与组织视角

平台团队适合拥有：事件 Schema registry、采集入口、SDK adapter、采样/脱敏默认值、release/source-map 服务、告警模板和事故工具。

业务团队拥有：旅程语义、错误归类、降级文案、SLO 和处理行动。

安全与隐私团队定义禁止字段、地域、保留和访问；数据团队帮助控制采样偏差；后端团队保证 request/trace/operation 可关联。

平台 SLA 也要明确。观测不可用时，高风险发布是否暂停，低风险功能是否继续，不能在事故中临时争论。

## 13. 常见失败模式

- 采集所有 console 和网络 body，先泄密再谈观测；
- 用错误条数告警，没有流量或会话分母；
- span 高基数，把用户 id 和真实 URL 放进名称；
- 自动 instrumentation 很丰富，却没有业务终态；
- 错误平台只有 minified stack，找不到 release；
- chunk 加载失败只让用户无限刷新；
- 网络失败对写请求自动重试，产生重复副作用；
- 遥测故障导致主流程报错；
- 各团队自定义不兼容字段，跨应用无法聚合。

## 14. 反花架子门槛与指标

平台上线前至少证明：

- 一次前端操作能关联到 BFF/后端请求；
- source map 与 release 可稳定符号化；
- 敏感字段有自动拒绝测试；
- 一个依赖故障能触发预定降级；
- 告警能指向 owner、runbook 与可执行止血；
- SDK 开销、丢失率和成本有预算。

建议跟踪：旅程失败率、unknown outcome、crash/white-screen-free session、可恢复率、MTTD/MTTR、错误到 release 归因时间、重复事故率、遥测送达/缺失/采样率、source-map 匹配率、SDK 性能与费用。

## 15. 架构评审清单

- 是否先定义用户故障终态，而非异常类型？
- release、session、journey、operation、request 能否关联？
- 浏览器数据是否被视为不可信且可能丢失？
- OTel 是否经内部 adapter，实验状态是否进入风险记录？
- 是否限制跨域 Trace Context 和 baggage？
- 写请求超时后的 unknown 如何对账？
- 降级是否保持正确性并明确陈旧状态？
- source map、chunk manifest 与制品是否同版本？
- 告警是否基于用户伤害并有止血动作？
- 遥测故障会不会破坏主流程？
- 谁拥有 Schema、SLO、runbook 和复盘行动？

## 本章结论

前端可观测性是“用户结果—制品—请求—组织行动”的证据系统；韧性是故障时仍保持正确、可解释、可恢复。SDK 和仪表盘只是实现细节，清楚的终态、关联、降级与责任才是架构能力。
