# 阅读方法与去重说明

## 这不是第六套实现教程

现有五套 Master 已经覆盖语言、框架、后端和 Agent 的大量实现细节。本指南的任务是建立“架构决策层”，所以不会再次从零讲组件、Hook、数据库事务、RAG 或容器命令。

这里所说的“会”，不是能复述定义，而是看到真实约束后能判断：

- 哪些边界必须分开；
- 哪些能力值得共享；
- 哪些风险应当自动阻断；
- 哪些指标能验证方案；
- 哪些流行技术在当前场景不该用。

## 先建立四层地图

阅读任何章节时，都把内容放进四层地图：

1. **产品层**：用户任务、业务目标、合规要求和失败影响。
2. **系统层**：应用、服务、数据、运行时和外部依赖。
3. **交付层**：代码库、构建、测试、发布、观测和恢复。
4. **组织层**：团队所有权、认知负担、协作接口和平台支持。

很多“技术问题”实际发生在不同层。例如重复组件可能是设计治理问题；构建慢可能是依赖边界和缓存正确性问题；微前端冲突可能是团队所有权没有明确，而不是框架能力不足。

## 每章的阅读顺序

### 第一步：先找它要改善的结果

不要从名词开始。先回答：这个主题最终要改善用户任务成功率、交付前置时间、变更失败率、恢复时间、开发者体验，还是合规风险？

若说不清结果，就暂时不要讨论工具选择。

### 第二步：写出约束而不是偏好

典型约束包括：

- 团队数量和所有权；
- 独立发布是否真的必要；
- 首屏、交互、离线或实时要求；
- 数据敏感度和租户隔离；
- 浏览器、地区和设备分布；
- 迁移窗口与兼容期限；
- 云、人员和维护预算。

“团队熟悉 React”可以是迁移成本信息，但“我喜欢 React”不是架构约束。

### 第三步：比较至少两个可行方案

架构决策不是列优点。每个方案至少比较：

- 直接收益；
- 新增复杂度；
- 最坏失败模式；
- 迁移与回滚；
- 持续运营成本；
- 两年后的退出成本。

不要拿一个真实方案与一个明显荒谬的方案比较。好的评审需要多个都能工作的候选项。

### 第四步：指定验证信号

把“更快、更稳、更易维护”改成可观察陈述。例如：

- 主干变更到生产的 p75 时间；
- 受影响任务的缓存命中率与错误复用率；
- 核心页面 LCP / INP 的 p75 与差设备分位；
- 发布后错误预算消耗与自动回滚时间；
- 平台 Golden Path 的采用率、绕过率和支持工单；
- AI 变更的返工率、逃逸缺陷和权限违规数。

指标必须能触发决策，而不是只用于汇报。

### 第五步：明确不采用与退出条件

真正成熟的技术方案会写清：

- 哪些前提不成立时不采用；
- 哪些信号出现时停止扩展；
- 如何保留回退路径；
- 谁决定弃用，谁帮助迁移；
- 何时删除兼容层。

## 六问架构卡

你可以在阅读时反复使用这张心智卡，不需要额外做题：

1. 用户或开发者的真实问题是什么？
2. 哪个质量属性最重要，哪个可以让步？
3. 业务、代码、运行时与团队边界是否一致？
4. 最危险的失败模式是什么，如何观测和恢复？
5. 方案如何渐进上线，又如何退出？
6. 哪组数据会证明我们判断错了？

## 稳定原理与易变实现

阅读时把知识分成两类。

### 稳定原理

- 质量属性存在取舍；
- 边界应降低变更传播；
- 平台必须把用户当作客户；
- 缓存需要可证明的失效语义；
- 发布必须可观察且可回滚；
- 迁移要控制新旧状态并存；
- 自动化不能替代责任归属。

这些内容值得形成长期心智模型。

### 易变实现

- React / Next.js / Vite 的当前版本；
- 某个 bundler 的默认行为；
- 某项浏览器 API 或遥测 SDK 的成熟度；
- 某个云平台的产品名称；
- AI Coding 工具和模型能力。

易变内容要从官方文档确认，并在 RFC 中记录“截至日期”，不要凭课程截图长期固化。

## 识别花架子的七个信号

1. 方案从产品名开始，没有问题陈述。
2. 只写成功路径，没有失败、降级和恢复。
3. 只算开发成本，不算升级、支持和迁移。
4. 强调统一，却没有例外机制和退出机制。
5. 把 demo 延迟、实验室分数或代码生成量当成生产价值。
6. 平台没有用户研究、采用率和支持责任。
7. 技术边界与团队边界长期相反，却期待靠规范解决。

出现三项以上时，应退回问题定义阶段。

## 如何读官方资料

优先级从高到低：

1. 标准、规范、官方版本状态；
2. 官方架构与安全说明；
3. 官方迁移指南和已知限制；
4. 真实团队的事故、性能或迁移复盘；
5. 社区文章与会议分享；
6. 二手摘要和营销比较。

阅读发布说明时尤其关注 breaking changes、实验状态、安全公告、迁移路径和回滚条件，而不是只看新功能列表。

## 架构文档的最小结构

当你以后需要输出方案时，推荐保留以下部分：

- 背景与当前基线；
- 目标、非目标和质量属性；
- 约束与关键假设；
- 系统、数据、运行时和团队边界；
- 两个以上可行方案；
- 决策与理由；
- 安全、隐私、可访问性和运维影响；
- 迁移、灰度、观测、回滚与删除旧路径；
- 成功指标、反证信号与复审日期；
- 负责人和相关 ADR。

文档不是一次性审批材料。决定发生变化时，更新状态或新增 ADR，保留当时上下文。

## 推荐节奏

### 第一遍：建立全貌

按核心路径阅读，每章只抓问题、边界、取舍和指标。不要在工具细节上停留过久。

### 第二遍：映射到一个真实项目

重新阅读与你当前项目最相关的章节，把文中概念映射到已有应用、包、发布流程和团队。即使不写练习，也要让每个名词有现实对象。

### 第三遍：在方案或评审前查阅

本指南最终应成为评审手册。做 Monorepo、微前端、SSR、性能、发布、平台或 AI Coding 决策前，直接回到相应章节的清单。

## 阅读完成的判断

不是“我知道什么是微前端”，而是：

- 你能说明它在什么组织前提下成立；
- 能列出替代方案；
- 能预测主要故障与成本；
- 能定义上线和退出路径；
- 能用数据决定继续还是停止。

当你对多数章节都能做出这种判断时，才真正从技术使用者向架构负责人迈进。
