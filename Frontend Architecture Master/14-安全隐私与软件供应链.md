# 第 14 章：安全、隐私与软件供应链

> 版本说明：供应链框架按 **2026-08-16** 可查的 SLSA 1.2 与相关官方规范理解；法律义务需由组织法务和隐私负责人结合业务、地区与最新法规确认。

## 本章要解决的市场与业务问题

现代前端把 npm 包、构建插件、第三方脚本、CDN、CI 身份和浏览器数据连成一条高权限链。一行依赖升级可能同时改变生产代码、构建权限、遥测数据和用户隐私。

安全不只是阻止 XSS，隐私不只是弹 Cookie 横幅，供应链也不只是跑一次漏洞扫描。架构负责人要知道制品从哪里来、谁能改变、包含什么、访问什么数据、如何撤销和证明。

### 非目标

- 不重复 XSS、CSRF、OIDC 的实现教程；
- 不给出替代律师意见的合规结论；
- 不承诺 SBOM 或签名自动证明代码安全；
- 不用“零漏洞”作为现实目标；
- 不因安全之名无限收集设备与用户数据；
- 不把所有依赖升级都直接阻断生产。

## 1. 资产、边界与攻击路径

前端架构至少保护：

- 用户身份、Token、个人信息和业务内容；
- 源码、source map、配置、签名密钥和 CI 身份；
- npm 包、lockfile、构建器、插件和制品 registry；
- HTML、JS/CSS 资产、Service Worker 与 CDN；
- 遥测、实验、Feature Flag 和第三方 SDK；
- 设计系统、脚手架和 Golden Path 的大范围传播能力。

典型攻击路径不是“黑客直接改页面”，而是依赖接管、恶意安装脚本、CI Token 泄漏、构建机污染、CDN/域名错误、第三方脚本失陷或遥测外传。

## 2. 数据生命周期而非字段清单

隐私评审应跟踪：

```text
目的 → 收集 → 本地处理 → 传输 → 使用/共享
→ 保留 → 访问/更正/删除 → 备份与最终销毁
```

每类数据记录：目的、合法依据、最小字段、主体、敏感度、地域、接收方、保留期、访问角色、删除和事故通知流程。

“以后也许有用”不是收集目的。能在浏览器本地聚合就不要上传原始输入，能用页面模板就不要上传完整 URL。

匿名化很难保证不可重识别；哈希手机号仍可通过字典或外部数据关联。假名化降低暴露，不等于数据不再受治理。

## 3. 浏览器隐私设计

浏览器 SDK 应采用 allowlist 事件协议，默认不收集 DOM 文本、输入值、响应体、Token、精确位置和跨站身份。

Cookie、localStorage、IndexedDB、Service Worker cache 和离线文件都有独立保留/清理语义。退出登录不自动清除所有本地数据。

第三方脚本通常获得同源页面的广泛能力。优先服务端转发或受限 iframe，按目的和风险减少供应商数量，并准备远程禁用。

同意管理不能只控制脚本加载，还要控制后续数据使用、撤回、版本记录和地域差异。必要功能与可选分析应分开。

## 4. 供应链参考模型

```text
source + review + dependency policy
  → isolated build + short-lived identity
  → artifact + digest + SBOM + provenance + signature
  → registry admission
  → deployment verification
  → runtime inventory / vulnerability response
```

每一步都要能回答：输入是什么、谁授权、输出摘要是什么、证据存在哪里、如何撤销。

制品在 CI 构建一次，逐环境晋级同一 digest；生产机器不重新下载不确定依赖再构建。

## 5. SLSA、Provenance 与签名

SLSA 提供逐步提升软件制品完整性的框架，重点是可信构建过程和可验证 provenance。

provenance 描述制品由什么源码、构建定义和构建平台产生；签名证明特定身份认可一份摘要；SBOM 列出组件。三者回答不同问题。

它们都不证明业务逻辑正确，也不保证依赖没有未知漏洞。部署准入要结合代码评审、测试、依赖政策和风险例外。

不要把长期云密钥放 CI。优先使用受保护工作流、最小权限和 OIDC 等短期工作负载身份，并限制哪些分支/仓库能发布。

## 6. SBOM 必须连接运行清单

生成 SBOM 只是起点。安全公告出现时，组织要能回答：

- 哪些源仓和锁文件包含组件？
- 哪些已构建制品包含它？
- 哪些环境和用户正在运行这些制品？
- 漏洞路径在产品中是否可达？
- 有无补丁、隔离、禁用或回滚方案？
- 谁负责，SLA 是多少？

前端制品长期被 CDN 和浏览器缓存，已部署不等于已消失。高危响应需要资产版本、缓存清理和用户刷新策略。

## 7. npm 与构建插件治理

依赖准入关注：来源、维护者变化、发布历史、权限、安装脚本、transitive graph、许可证、体积、浏览器能力和替代方案。

推荐实践：

- 唯一 lockfile 或可追踪锁文件，CI frozen install；
- registry scope 与来源固定，防 dependency confusion；
- 限制或审查 install scripts；
- 发布使用受保护分支、双人审批和可信发布；
- 自动更新先跑契约、制品和 canary；
- 紧急漏洞有跨仓搜索、批量升级和回滚能力；
- 废弃包有 owner、替代品和迁移期限。

版本固定降低漂移但不解决陈旧风险；自动跟最新降低陈旧但扩大未经验证变化。正确答案是可观察的更新流水线。

## 8. 第三方运行时代码

Tag Manager、客服、支付、地图、广告和监控 SDK 会影响性能、隐私、CSP 与可用性。

为每个第三方记录：业务目的、数据、域名、加载条件、SLA、超时、资源预算、CSP、SRI 适用性、禁用方法和退出计划。

SRI 适用于内容地址稳定的外部静态资源，但不能替代域名控制、CSP 和供应商治理；频繁变化脚本若无法固定摘要，应重新评估加载方式。

第三方失败必须被隔离。非关键脚本不应阻塞首屏或核心提交，异常不应触发无限重载。

## 9. Source Map、秘密与配置

前端制品对用户可见，任何打包进去的 key、endpoint 或 Flag 都不是秘密。

source map 可能暴露源代码、内部路径与注释；应私有上传、绑定 release、限制访问和保留，不公开部署。

构建期配置和运行时配置都要分类。公开配置可进浏览器，高权限凭证只在服务端以短期身份使用。

秘密扫描覆盖源码、Git 历史、制品、日志和 map；发现泄漏先轮换/撤销，再删除字符串。

## 10. 安全默认值的平台化

平台可以提供：

- CSP/安全 header 模板与 report-only 迁移；
- 依赖来源、许可证、漏洞和安装脚本政策；
- 可信构建、SBOM、provenance、签名与验证；
- secret scanning 和短期 CI 身份；
- 第三方目录、数据分类与隐私事件 Schema；
- 制品/运行清单和高危批量响应；
- 例外审批、到期与审计。

业务团队仍负责领域授权、数据目的、第三方必要性和漏洞可达性。平台不能靠一个 scanner 理解业务。

## 11. 例外与风险接受

安全门禁需要风险分级。已知被利用、可达、高影响漏洞应快速阻断；开发工具中的不可达低风险项可能有期限例外。

例外必须记录：资产、风险、证据、缓解、owner、批准者、到期、复审和退出计划。

永久 allowlist 等于关闭门禁。到期后自动恢复阻断，不能依赖负责人记得回来删除。

紧急响应要保留受审计 fast lane，最小验证后发布，并在事后补齐证据。

## 12. 常见失败模式

- `npm audit` 为零就宣布供应链安全；
- SBOM 生成后从未用于查询运行制品；
- 构建签名使用仓库共享长期密钥；
- CI 与开发机执行任意安装脚本；
- analytics 上传完整 URL、表单和错误对象；
- Cookie 横幅存在，但撤回不停止后续处理；
- source map 公开且包含内部源码；
- 第三方脚本故障阻塞登录或支付；
- 漏洞升级只改主仓，遗留应用仍在运行；
- 安全例外无 owner、无期限、无补偿控制。

## 13. 反花架子门槛

供应链/隐私平台至少证明：

- 任一生产制品能追溯到 source、build 和 digest；
- 能查询某组件实际运行在哪些应用/环境；
- CI 无长期生产凭证，发布身份有范围约束；
- 一次第三方失陷可远程隔离；
- 一类用户数据能完成收集到删除的演练；
- 高危公告有 owner、SLA、批量升级和验证；
- 例外会到期并重新阻断；
- 安全控制没有把秘密或 PII 写入遥测。

只有扫描大屏和合规文档，没有追溯、撤销与演练，不算治理。

## 14. 建议指标

- 生产制品 provenance/SBOM/签名覆盖率；
- 未知来源制品准入次数；
- 高危漏洞发现到定位、缓解、升级的时间；
- 运行制品与源码 inventory 匹配率；
- 长期 CI 凭证和过度权限数量；
- 第三方脚本数量、字节、数据类别和事故贡献；
- 隐私数据字段、保留超期、删除完成时间；
- 安全例外数量、年龄和逾期率；
- 依赖更新前置时间与变更失败率；
- CSP/Trusted Types 报告趋势和真实阻断事故。

禁止按开发者“漏洞数”排名，这会鼓励隐藏资产和避免升级扫描器。

## 15. 架构评审清单

- 资产、攻击者、信任边界和最坏影响是否明确？
- 每类数据是否有目的、最小字段、地域、保留和删除？
- 浏览器是否从未获得真正秘密？
- 第三方脚本能否隔离、预算和远程禁用？
- lockfile、registry、install scripts 和发布权限是否受控？
- 制品是否有 digest、SBOM、provenance 和可验证签名？
- 部署是否验证证据，而非只生成证据？
- 漏洞能否从组件定位到运行应用与用户影响？
- source map 与遥测是否最小化访问和保留？
- 风险例外是否有补偿控制和自动到期？
- 最近是否演练过密钥泄漏、依赖失陷或数据删除？

## 本章结论

前端安全、隐私和供应链是一条从数据目的、源码、构建身份到浏览器运行的连续证据链。成熟团队不追求“扫描全绿”，而是能最小化、追溯、验证、隔离、撤销并在真实事故中恢复。
