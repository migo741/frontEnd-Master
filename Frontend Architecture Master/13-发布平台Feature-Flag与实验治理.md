# 第 13 章：发布平台、Feature Flag 与实验治理

> 版本说明：Feature Flag 标准与平台能力按 **2026-08-16** 的官方资料理解；产品名称会变，部署与发布分离、可回滚和责任到期是稳定原则。

## 本章要解决的市场与业务问题

把代码部署到生产并不等于让全部用户使用它。大型团队需要在同一制品上控制能力何时、向谁、以什么比例开放，同时区分技术灰度、运营配置和因果实验。

没有治理的 Flag 会产生另一套隐藏代码库：组合无法穷举、权限绕过、旧分支不删除、回滚按钮在事故中失效。

### 非目标

- 不把 Flag 当服务端授权；
- 不用实验平台替产品判断；
- 不要求每个小改动都做 A/B；
- 不把“先发再说”包装成渐进发布；
- 不重讲容器、流水线命令或统计学完整课程；
- 不承诺一次点击能回滚数据库和外部副作用。

## 1. 先分离五个概念

**部署**：把不可变制品放到生产环境。

**发布**：让目标用户开始使用能力。

**渐进交付**：按 cohort 扩量并根据证据继续、暂停或回退。

**Feature Flag**：运行时选择路径的受控配置。

**实验**：通过预先定义的随机分组估计某项变化的因果影响。

Canary 可以只验证安全性，A/B 主要回答产品效果；两者可能共用分流基础设施，但判定逻辑不同。

## 2. Flag 类型与生命周期

常见类型：

- release flag：短期隐藏尚未完全开放的能力；
- experiment flag：稳定分组并记录实验曝光；
- permission/entitlement：长期产品资格，应有权威服务端模型；
- configuration：调参数，不一定是布尔值；
- migration flag：切换新旧实现、读写路径或协议版本。

不同类型需要不同权限、TTL 和审计。不要把所有配置都叫 `isEnabled`。

每个 Flag 至少有：

```text
key / type / owner / purpose / createdAt / expiresAt
default / targeting / dependencies / risk / rollback
data classification / audit / removal issue / lastEvaluatedAt
```

release、experiment、migration flag 必须在创建时生成删除任务；到期不是提醒，而应进入升级、阻断或自动清理流程。

## 3. 参考控制面

```text
代码与制品 ───────────────┐
Flag 定义 / 策略 / 审批 ──┼→ 配置版本 → SDK/Edge/BFF → 稳定 cohort
实验定义 / 指标字典 ──────┘                    ↓
                                      exposure / outcome
                                              ↓
release + RUM + 业务事实 → 分析/判定 → 扩量、暂停、回退、清理
```

控制面管理定义、权限、版本、审批和审计；数据面必须低延迟、缓存、有限失效，并对控制面不可用有确定默认值。

浏览器收到的 Flag 可以被查看和篡改，因此不能保护秘密、权限、价格或风控。高风险判定在服务端执行，前端只决定显示与交互投影。

## 4. 默认值与故障语义

每个 Flag 要明确 SDK 初始化失败、配置过期、网络断开、未知 key 和类型错误时的行为。

选择 `false` 并不自动安全。关闭新支付路径可能把用户送回已删除旧路径；关闭安全修复更危险。

推荐根据风险定义：

- fail closed：危险能力不可用，但可能影响可用性；
- fail open：维持服务，但可能扩大风险；
- last known good：使用已验证版本并设置最大陈旧时间；
- static bootstrap：制品携带最小安全默认配置；
- server resolved：关键结果由 BFF 返回，浏览器不自行评估。

默认值、缓存 TTL 和控制面 SLO 是同一个架构决策。

## 5. 稳定分组与曝光

同一用户或设备应在实验周期内稳定进入 cohort，分配键、hash 算法和版本要记录。

只有用户真正有机会看到或使用变化时才记录 exposure。页面启动时把全部实验都记为曝光会污染分母。

匿名到登录身份切换、跨设备、Cookie 清理、多租户和共享账号都可能破坏稳定分组，实验设计必须提前说明。

分组键属于个人或设备数据时，需要最小化、保留期限和访问控制；不能为了实验便利创建永久跨产品追踪身份。

## 6. 实验不是看图猜结论

实验开始前写清：

- 假设与主要指标；
- guardrail：错误、延迟、安全、投诉和成本；
- 实验单位与随机化方法；
- 目标人群、排除项和样本量；
- 运行时间与停止规则；
- 新奇效应、节假日和并发实验风险；
- 决策规则与负责人；
- 未显著、负向和数据异常时怎么办。

不要每天查看结果，一出现正向就停止；也不要在结果出来后不断更换主要指标。

Sample Ratio Mismatch、曝光丢失、机器人流量和分组不稳定，应先视为数据质量事故，而不是业务结论。

## 7. 技术 canary 的判定

Canary 目标是证明新版本没有不可接受伤害。

比较新旧 cohort 的：

- 核心旅程成功和 unknown outcome；
- 前端错误、白屏、chunk 加载；
- LCP/INP 与业务等待分位；
- API、BFF 和依赖错误；
- 数据重复/冲突与安全拒绝；
- 支持工单和人工接管；
- 成本、缓存命中和资源饱和。

低流量时数据不足，不能自动判为成功。发布系统应显示置信度、最小观察窗口和遥测延迟。

## 8. 真正的回滚面

回滚可能涉及：

- Flag 指向旧路径；
- 前端静态制品与 HTML 入口；
- Service Worker 与离线缓存；
- BFF / API 的已声明兼容窗口；窗口要覆盖可观测到的长驻标签页、WebView、缓存 JS、离线客户端和延迟消费者，而不是机械假设 N / N-1；
- 数据 Schema 与已写入新字段；
- 事件、队列和外部副作用；
- 实验分组与用户会话；
- 配置、内容和第三方版本。

代码回滚不能撤销已发送消息、已付款项或破坏性数据迁移。高风险发布先设计补偿、对账和冻结开关。

kill switch 要定期演练，权限要少而可审计，并有恢复条件；永不使用的按钮不是能力。

## 9. Flag 组合爆炸

N 个布尔 Flag 理论上有 `2^N` 组合。现实中依赖、互斥、版本和用户条件会更复杂。

控制方法：

- Flag 按领域与 owner 分区；
- 显式声明依赖/互斥和允许状态；
- 对高风险组合生成测试矩阵；
- 限制单页面活跃 Flag 数；
- 旧 Flag 到期并删除代码分支；
- telemetry 记录受控 flag 摘要，不上报全部用户画像；
- 迁移完成后收敛为一个真相。

Flag 不是永久架构抽象。长期 entitlement、套餐和权限应进入领域模型。

## 10. 平台与组织视角

平台团队拥有：定义 Schema、评估 SDK、控制面/数据面可靠性、审计、到期自动化、实验分析基础和发布集成。

业务团队拥有：Flag 目的、用户影响、默认值、指标、扩量决策和删除代码。

数据团队维护指标字典、实验质量检查和统计方法；安全团队控制高风险 targeting 与隐私；值班团队需要可用 kill switch 和 runbook。

OpenFeature 一类开放规范可减少供应商锁定，但不能自动提供实验正确性、业务 owner 或回滚语义。

## 11. 常见失败模式

- 前端 Flag 被当作授权，改本地值即可越权；
- 新旧路径永久共存，认知负担持续翻倍；
- 默认 false，却没有可运行旧路径；
- Flag 服务故障导致全站启动失败；
- exposure 在页面加载时记录，用户从未看到功能；
- 实验结果不显著却反复切指标寻找正向；
- 事故时不知道谁有关闭权限，或开关从未演练。

## 12. 反花架子门槛

上线发布/实验平台前，至少证明：

- 部署与发布可独立发生；
- cohort 稳定且曝光语义正确；
- Flag 有 owner、到期、删除任务和审计；
- 控制面故障有验证过的默认行为；
- canary 指标能驱动自动/人工暂停；
- 一条真实路径完成过回滚演练；
- 数据和外部副作用有补偿/对账；
- 平台能报告活跃 Flag 数、年龄和组合风险。

如果平台只提供漂亮开关页面，却不能删除旧分支、解释曝光或恢复事故，它只是配置门户。

## 13. 建议指标

- canary 自动暂停准确率与恢复时间；
- 活跃 Flag 数、p75 年龄、逾期率、删除前置时间；
- 无 owner、无到期、无访问记录的 Flag；
- 控制面/数据面可用性与陈旧配置比例；
- release 引入的错误预算消耗；
- kill switch 演练成功率；
- 回滚后仍需人工修复的数据/副作用数量；

## 14. 架构评审清单

- 当前讨论的是部署、发布、canary 还是实验？
- Flag 类型、owner、默认、到期和删除任务是否完整？
- 浏览器结果是否仅用于展示，不承担授权？
- cohort 与 exposure 在身份切换时是否稳定？
- 实验假设、主要指标、guardrail 和停止规则是否预注册？
- 数据不足、SRM 或遥测故障时是否停止扩量？
- 新旧代码、API、Schema、缓存能否在窗口内共存？
- 回滚能否处理已发生的数据与外部副作用？
- 组合风险如何限制和测试？
- kill switch 最近何时演练，谁有权限？
- 完成后何时删 Flag 和旧路径？

## 本章结论

成熟发布平台把“代码已部署”变成一个可观察、可暂停、可回滚、会清理的决策过程。Flag 是短期控制结构，实验是因果测量；二者只有在权限、数据、到期和真实恢复都成立时才产生价值。
