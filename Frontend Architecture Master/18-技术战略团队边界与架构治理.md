# 第 18 章：技术战略、团队边界与架构治理

> 版本说明：组织框架、效能研究和技术生态按 **2026-08-16** 的公开资料理解；组织设计必须根据业务与人员变化定期复审，不能照抄范式。

## 本章要解决的市场与业务问题

Staff/架构负责人面对的不是“选哪个状态库”，而是如何让多个团队在不确定业务中朝同一方向演进，同时保持局部自主、生产责任和可撤销性。

技术战略失败常有两种形态：一份与业务无关的技术愿望清单，或一个审批所有决定的架构委员会。前者没有行动，后者成为瓶颈。

### 非目标

- 不把“统一技术栈”当战略，也不照抄其他公司的组织图；
- 不要求架构师审批所有 PR 和依赖，不用 DORA/SPACE 给个人排名；
- 不把 ADR、RFC 或会议数量当治理效果，也不因长期目标跳过渐进迁移；
- 不把平台团队设成无边界共享服务队。

## 1. 技术战略的最小结构

有效战略包含：

1. 诊断与原则：哪些业务和系统约束最关键，面对取舍时如何选择；
2. 协同行动与结果信号：哪些投资、迁移、停止与能力建设互相支持，如何知道方向有效或错误；
3. 复审：假设何时、由谁根据什么变化更新。

“迁移到 React”“建设中台”“全面 AI 化”都是动作口号，不是完整战略。

## 2. 从业务能力与质量属性出发

把业务目标翻译为质量属性场景：

```text
在大促流量与一个 CDN 区域故障下，
移动用户仍能在 3 秒内开始结算，
支付结果不重复，值班团队 10 分钟内可切换降级路径。
```

场景包含刺激、环境、系统部分、响应和度量，能驱动边界、平台和投资。

不同业务阶段的重点不同：探索期偏反馈与可逆，增长期偏容量与一致性，受监管业务偏审计与数据边界。战略必须声明取舍。

## 3. 建立技术投资组合

把工作分为：

- run / improve：维持安全可靠，同时减少成本、事故和认知负担；
- migrate / retire：结束遗留风险与不兼容，并真正删除旧能力；
- explore：小成本验证新能力；

每项投资要有业务驱动、owner、容量、里程碑、反证信号和退出计划。

只投资 explore 会形成 demo 墓地；只投资 run 会积累战略落后；只建设不 retire 会让复杂度永久增长。

## 4. 团队边界是架构边界

系统会反映沟通结构。若一个业务旅程每次都需五个团队串行审批，代码模块再漂亮也无法独立演进。

设计团队边界时观察：

- 长期业务能力、变化节奏、生产责任和 on-call；
- 数据与写入所有权；
- 认知负担、技能稀缺及依赖的稳定性与交互频率；
- 独立交付的真实需要；
- 合规、地域和供应商边界。

组织图不是静态真相。业务变了，模块、平台和团队拓扑也需要演进。

## 5. 四类团队的使用边界

Team Topologies 常用视角：

- stream-aligned：围绕业务价值流，端到端拥有结果；
- platform：提供自助公共能力，降低认知负担；
- enabling：短期帮助团队获得能力，不永久接管；
- complicated subsystem：拥有需要稀缺专业知识的子系统。

标签不是荣誉等级。一个团队同时承担平台、业务需求、全公司救火和专家审批，会在冲突优先级中失败。

平台团队不能因“共享”而接收所有无 owner 代码；complicated subsystem 也需要清楚 API，不能成为黑盒权力中心。

## 6. 团队交互模式

**X-as-a-Service**：接口稳定、自助为主，适合成熟平台能力。

**Collaboration**：两个团队短期共同探索高不确定边界，需结束条件。

**Facilitating**：enabling team 帮助学习和迁移，不接管长期 owner。

交互模式要写入时间和目标。永久 collaboration 往往说明边界未收敛，永久工单则说明平台没有自助能力。

依赖关系应通过契约、SLO、版本和支持范围表达，而不是靠私聊特定专家。

## 7. 决策权分层

不同决定需要不同范围：

- 团队局部：组件内部、可逆实现；
- 领域级：数据、API、关键旅程；
- 平台/组织级：Golden Path、共享协议、身份、安全基线、供应链和重大投资；
- 紧急：事故 commander 按 runbook 临时决策。

原则是决定尽量靠近信息和责任，同时让跨边界影响被看见。

每类决定说明 proposer、consulted、decider、executor、owner 和复审者。不要让“大家共识”掩盖无人负责。

## 8. RFC 与 ADR 的不同职责

RFC 用于重要决定前公开问题、选项、影响和迁移，获得必要反馈。

ADR 记录已做决定的上下文、选择、后果、状态和重访触发器。

文档应分风险：局部可逆变更不需长 RFC；跨团队协议、数据、安全和不可逆投资需要更严格证据。

ADR 不能只写“选择 X，因为流行”。至少包含约束、替代、失败、迁移、回滚、指标和 owner。

决定变化时 supersede 旧 ADR，保留历史；不要静默改写过去。

## 9. 原则、标准与 Golden Path

**原则**帮助新问题取舍，例如“业务事实由权威服务端确认”。

**标准**规定跨团队必须一致的契约，例如 trace header 或制品 provenance。

**Golden Path**把常见标准做成可用产品。

**指南**给出推荐和例子，允许情境判断。

四者混在一个百页规范中会失效。强制项必须少、可验证、有 owner 和例外；推荐项不要伪装成审计门禁。

## 10. 架构适应度函数

把关键边界变成持续证据：

- 依赖图无禁止方向/循环，package 公共 API 与大小符合预算；
- API / 事件在已声明的消费者兼容窗口内保持契约；窗口由客户端驻留、缓存、回滚和消费延迟数据决定，核心旅程同时符合体验与错误预算；
- tenant/权限和隐私不变量；
- 制品 provenance、依赖政策、平台版本与迁移期限；
- owner、SLO 与 runbook 完整性。

不是所有原则都能自动化。人类评审开放权衡，机器守明确不变量；不要让 LLM judge 决定确定性政策。

## 11. 技术雷达与生命周期

技术雷达应表达组织证据和行动：adopt、trial、assess、hold，而不是列个人喜欢的产品。

每项有适用场景、owner、证据、风险、支持状态和复审日期。

生命周期还需要：proposed → supported → preferred → deprecated → retired。

新增技术容易，退休最难。deprecated 必须有替代、迁移工具、支持期限和最终阻断；否则只会增加选择而不减少复杂度。

## 12. 渐进迁移的组织治理

第 15 章处理单系统迁移，本章关注组合层：如何排序几十个应用、分配容量、管理例外并真正删除旧能力。

建议步骤：

1. 按业务风险与变化频率分群，选设计伙伴验证 Golden Path；
2. 沉淀 codemod、adapter、兼容和支持；
3. 设迁移 waves，由平台与业务共同承担容量；
4. 对例外给出复审与支持边界，用真实流量和 inventory 验证；
5. 删除旧 runner、权限、依赖和文档。

迁移不是发公告后的业务团队额外工作。若组织不投入容量，目标架构只会停在幻灯片。

## 13. 治理中的例外

例外是战略反馈，不是道德失败。

记录：违反哪项标准、业务原因、影响、补偿控制、owner、到期、复审和回归路径。

按例外聚类：大量同类例外说明标准或平台不适用；单个团队长期例外可能是迁移/所有权问题。

禁止没有期限的豁免，也禁止为了“统一率”拒绝合理差异。

## 14. 指标与组织行为

组合观察：

- 业务旅程、体验 SLO、变更前置、失败与恢复；
- 跨团队等待、依赖数量及平台采用、绕过、支持和版本新鲜度；
- 架构边界违规、兼容层、例外年龄、事故重复和退休完成；
- 团队认知负担、满意度和流动风险；
- 技术投资的成本、收益和机会成本。

指标用于发现系统约束。把频率、提交数、AI 使用率用于个人绩效，会破坏数据和协作。

## 15. 战略复审节奏

季度检查假设、指标、例外和投资组合；重大事故、并购、监管、用户结构或供应商变化触发额外复审。

复审不是每季改方向。区分短期噪声与前提变化，保留决策历史。

每项战略赌注选择 continue、adjust、pause 或 stop，并重新分配明确容量。

技术负责人要公开“不做什么”，保护团队免受无限并行倡议。

## 16. 常见失败模式

- 战略只是框架升级清单，架构委员会又审批一切；
- 平台团队同时承接所有共享代码和救火；
- RFC 只在决定后盖章，ADR 永不复审；
- 标准不可自动验证，只靠宣讲；
- 技术雷达只增不退；
- 迁移截止日期统一，却不给容量和工具；
- 例外藏在私聊，又用单一效能数字排名团队和个人。

## 17. 反花架子门槛

战略至少要连接业务约束、一组彼此配合的行动、明确容量、owner、反证信号和停止事项。

治理必须证明：局部决定更快、跨边界风险更早暴露、例外可见且到期、标准能执行、迁移能删除旧成本。

若产物只有组织图、技术雷达和会议，没有改变投资、边界、平台或生产结果，就是治理表演。

## 18. 建议指标

- 战略目标对应的业务/体验/SLO 变化，以及从 RFC 到首个证据的时间；
- 跨团队等待与高耦合依赖趋势；
- ADR 复审/supersede、过期标准、适应度函数覆盖和违规修复时间；
- 例外数量、年龄、原因聚类和回归率；
- 平台采用/绕过及认知负担；
- 迁移 wave 完成和旧资产退休率；
- 技术投资组合比例、重复事故与组织级恢复时间。

## 19. 架构评审清单

- 战略诊断是否来自业务和生产证据，原则能否帮助真实取舍？
- 行动是否协同、获分配容量并写清停止项？
- 代码、运行时、数据与团队边界是否相互支持，交互模式是否有结束条件？
- 决策是否靠近信息与责任，跨界影响是否可见？
- RFC/ADR/标准/指南是否各司其职，关键原则是否有适应度函数或人工复审？
- 技术生命周期是否包含 deprecate 和 retire？
- 迁移是否提供平台、工具、容量和分 wave 支持？
- 例外是否透明、有补偿、到期并反馈战略？
- 指标会不会诱发个人排名和数字游戏？
- 什么变化会触发 adjust、pause 或 stop？

## 本章结论

技术战略把业务诊断变成一组有容量、有证据、会停止的协同行动；架构治理让决定靠近责任，同时守住跨团队不变量。资深影响力不来自审批更多，而来自让组织更快做出可逆、可验证且能真正收尾的变化。
