# 第 12 章：测试架构与质量平台

> 版本说明：工具名称与浏览器矩阵按 **2026-08-16** 理解；本章关注长期稳定的风险分层、反馈速度和责任边界。

## 本章要解决的市场与业务问题

当仓库、应用和团队增多，测试会同时出现两种抱怨：“什么都测了仍出事故”和“流水线太慢不敢提交”。根因通常不是缺少一种框架，而是没有把业务风险、系统边界和反馈成本映射到测试组合。

质量平台的目标不是集中替团队写测试，而是提供可信环境、可复用能力和可执行政策，让最重要风险在最便宜且足够真实的层级被发现。

### 非目标

- 不重复 Vitest、RTL、Playwright 的基础用法；
- 不追求统一覆盖率数字；
- 不要求所有测试都在每个 PR 全量执行；
- 不以 snapshot 数量或 E2E 数量衡量成熟度；
- 不让平台团队成为失败用例的永久 owner；
- 不用 AI 生成大量测试代替风险判断。

## 1. 从风险目录开始

先列出系统不能接受的失败：

- 用户无法完成关键旅程，或数据丢失、重复、错租户；
- API/事件演进打断旧客户端；
- 浏览器、地区、可访问性、性能或资源加载回归；
- 权限、XSS、CSRF、供应链漏洞；
- 灰度、缓存、Feature Flag、依赖与恢复路径组合故障。

为每项风险记录影响、发生概率、可检测层级、owner 和生产逃逸后的恢复成本。

## 2. 测试组合而非测试金字塔教条

不同层保护不同事实：

| 层级 | 保护的主要事实 | 代价与盲点 |
| --- | --- | --- |
| 静态检查 | 类型、依赖方向、规则、已知危险模式 | 看不到真实运行时 |
| 单元/属性 | 纯逻辑、状态机、不变量、边界组合 | 不能证明集成配置 |
| 组件/集成 | DOM、交互、网络边界、存储协作 | 浏览器与部署仍可能不同 |
| 契约 | API、事件、Schema、发布物兼容 | 不能证明完整用户旅程 |
| E2E | 关键旅程与真实浏览器/环境 | 慢、定位难、组合爆炸 |
| 非功能 | 性能、安全、视觉、a11y、韧性 | 需要专用基线与判定 |

“测试越接近用户越好”并不完整。应该在能发现该风险的最低成本层级做主要防线，再用少量高层测试验证集成事实。

## 3. 契约是独立发布的前提

前端与 BFF、微应用、SDK、事件和设计系统都可能独立发布，因此需要机器可验证的消费者契约。

契约至少包含：

- 字段含义、可选性、错误与分页语义；
- 鉴权、租户和缓存相关 header；
- 幂等、版本、排序和时间语义；
- 弃用期限和兼容矩阵；
- 示例不是唯一合法值；
- 运行时 Schema 与生成类型的关系。

契约测试不能只比较 TypeScript 类型，因为类型在运行时消失；也不能直接暴露数据库模型，否则内部迁移变成客户端 breaking change。

## 4. 变更影响图决定测试范围

平台需要知道：文件属于哪个 package、package 影响哪些应用、哪些契约/旅程/owner 依赖它。

```text
Git diff → package graph → build outputs → contracts → journeys
         → risk rules → selected test plan → evidence
```

只按目录匹配会漏掉生成代码、运行时配置、共享 CSS、设计 token 和基础镜像变化。

影响分析必须保守且可解释。无法证明安全时回退到更大集合，不能为了缓存命中率静默漏测。

## 5. 参考质量平台

```text
Change intake
  → 依赖与风险分类
  → 可复现执行环境 / 测试数据
  → 静态、单元、契约、浏览器任务 DAG
  → 分片 / 缓存 / 重试策略
  → 证据与失败归因
  → PR、发布、canary 门禁
  → 生产失败回流风险库
```

平台提供 runner、浏览器、artifact、trace/video、数据工厂、契约仓库和结果 API；业务仓库声明旅程、不变量和 owner。

## 6. 缓存正确性优先于速度

测试缓存 key 至少包含源码、依赖、配置、工具链、运行环境、生成步骤和相关外部契约。

错误复用绿色结果比不缓存更危险。平台必须：

- 可解释某结果为什么命中；
- 随机抽样重跑验证缓存；
- 工具/基础镜像升级时整体失效；
- 对非确定或依赖真实时间的任务禁用缓存；
- 记录输入摘要、输出和 provenance；
- 允许一键旁路并比较结果。

## 7. E2E 只守高价值旅程

E2E 优先覆盖：登录/授权、核心写入、支付或审批、恢复路径、跨应用导航和发布兼容。

不要把每个组件状态都做成 E2E。大量重复测试会增加排队、flaky 和维护成本，却不增加风险覆盖。

E2E 应基于稳定业务语义定位，控制测试数据和时间，等待可观察状态，不用任意 sleep。

失败时保存浏览器版本、release、网络、console、trace、截图/视频和后端关联 ID，但对敏感内容脱敏和限期保留。

## 8. 视觉与可访问性质量

视觉 diff 适合发现布局、字体、主题和组件变化，但像素不同不自动等于缺陷。

建立受控字体、viewport、动画和数据；把差异归到组件/页面 owner；重大基线更新需要设计审查，不能“一键全部接受”。

可访问性自动扫描能发现部分语义、名称、对比度问题，无法替代键盘、焦点、屏幕阅读器和真实任务测试。

设计系统应集中测试 primitives，业务应用测试组合和旅程，避免每个仓库重复证明同一按钮实现。

## 9. 性能与韧性测试

性能检查分三类：确定性制品预算、受控 Lab 趋势、生产 RUM 验证。不要因单次 CI 噪声阻断全部发布。

韧性测试主动注入：慢响应、断线、chunk 404、过期缓存、重复事件、存储配额、旧 API 和 Feature Flag 组合。

测试不仅断言出现 fallback，还要断言：没有重复副作用、用户知道状态、恢复后事实一致、遥测能解释过程。

## 10. 测试数据和环境

共享 staging 容易产生串扰、顺序依赖和权限污染。选项包括：

- 每测试事务/命名空间隔离；
- 每 PR 短寿命环境；
- 受控共享环境加租户隔离；
- 服务虚拟化与少量真实依赖契约；
- 生产流量脱敏回放，但需合规审批。

越真实的环境越贵且越慢；越多 fake 越可能偏离生产。关键是明确每个 fake 替代了什么事实，并用契约或少量真实集成验证它。

禁止把生产 Token、用户数据或长期云密钥复制进测试。环境销毁和数据保留也要被验证。

## 11. Flaky 是平台可靠性事件

flaky 会训练团队忽略红色。治理流程：

1. 保存失败证据与 seed；
2. 归类产品缺陷、测试缺陷、环境缺陷或未知；
3. 指定 owner 和修复期限；
4. 隔离时仍保留可见性，不静默删除；
5. 只对已知基础设施瞬时故障做有限自动重试；
6. 统计首次失败而非只展示重试后的绿色；
7. 修复后增加反复/乱序压力验证。

“重跑到绿”会掩盖竞态和资源泄漏，不能算恢复。

## 12. 门禁应按风险分级

**立即阻断**：越权、数据损坏、已知高危漏洞、确定 breaking contract、核心旅程失败。

**需批准例外**：性能趋势、小范围视觉变化、非核心 flaky；要求 owner、原因、到期和缓解。

**观察**：低风险实验、信息性趋势；不能用红色样式制造虚假紧急感。

紧急修复可有 fast lane，但应运行最小安全集合、记录审批，并在发布后补齐完整验证。

## 13. AI 生成测试的边界

AI 适合扩展边界组合、生成 fixture 草稿、解释失败和迁移机械断言。

AI 不知道真正业务风险，可能把实现细节写成断言、重复当前 bug，或制造看似丰富却无判别力的测试。

生成测试必须经过同样 review，证明先在错误实现上失败、修复后通过，并检查权限、数据和依赖。

## 14. 平台与组织视角

质量平台是内部产品，需要平台 SLO、文档、支持、迁移和用户研究。

集中所有测试代码会削弱业务所有权；完全分散又会重复基础设施。合理边界是平台拥有执行与证据协议，领域团队拥有风险与断言。

设置质量架构委员会时，其职责应是维护少量跨团队标准和例外机制，不逐个审批测试文件。

生产事故必须回流：更新风险目录、增加最合适层级的回归，并检查为何旧门禁没有发现。

## 15. 常见失败模式

- 覆盖率达到 90%，关键旅程仍无断言；
- 所有测试都 mock 网络，契约早已漂移；
- 所有风险都塞进 E2E，流水线超过一小时；
- 失败自动重试三次，只展示最终绿色；
- PR 全量跑整仓，团队开始跳过 CI；
- affected 算法漏测，却无人抽样验证；
- 视觉基线由开发者批量接受；
- 测试环境持有生产数据与长期秘密；
- 平台强推模板，没有迁移支持和逃生口；

## 16. 反花架子门槛与指标

质量平台投资前，至少有跨仓重复痛点、明确风险目录和可量化基线。

建议指标：变更到首个可信反馈的 p50/p75、关键风险覆盖、逃逸缺陷、变更失败率、flaky 首次失败率与年龄、缓存命中及错误复用审计、E2E 队列/执行时间、失败可归因率、例外债务、平台采用/绕过/支持工单。

禁止用测试数量、覆盖率或开发者排名作为单一绩效，否则会优化数字而不是风险。

## 17. 架构评审清单

- 风险目录是否来自用户和业务事实？
- 每项风险是否放在最低成本且足够真实的层？
- 独立发布边界是否有运行时契约测试？
- affected 结果能否解释并保守回退？
- 缓存 key 是否包含所有影响结果的输入？
- E2E 是否只守高价值旅程和恢复？
- 测试数据、租户、秘密和销毁是否受控？
- flaky 是否有 owner、期限和首次失败数据？
- 门禁是否按风险分级并有到期例外？
- 事故是否回流到风险库与正确测试层？

## 本章结论

测试架构把风险放到正确证据层，质量平台把执行、环境和反馈做成可靠公共能力。高级前端要优化的是“发现重要问题的速度与可信度”，不是让仓库拥有最多测试。
